설정 스크립트는 하나의 코어 디바이스에 대한 AWS IoT 아이덴티티를 생성하고, Ubuntu 26.04 x86_64 EC2 인스턴스를 시작하고, AWS Systems Manager를 통해 클래식 Greengrass nucleus를 설치합니다. 생성한 내용을 `.greengrass-tutorial.env`에 기록하며, 계정, 리전 및 접두사에 바인딩되므로 `cleanup` 작업이 나중에 정확히 해당 리소스를 삭제합니다.

| 리소스 | 이름 | 생성자 |
| --- | --- | --- |
| IoT thing group | `<prefix>-group` | Script |
| IoT thing | `<prefix>-core` | Script |
| Token exchange role 및 액세스 정책 | `<prefix>-token-exchange`, `<prefix>-token-exchangeAccess` | Script |
| IoT role alias | `<prefix>-alias` | Script |
| Device IoT policy | `<prefix>-device-policy` | Script |
| EC2 instance | 태그 `Name=<prefix>-core` | Script |
| 디바이스 인증서 및 프라이빗 키 | 인스턴스에서 생성됨 | Nucleus installer |
| role alias용 IoT policy | `GreengrassTESCertificatePolicy<prefix>-alias` | Nucleus installer |

설치 프로그램은 인스턴스 프로파일의 임시 자격 증명으로 인스턴스에서 실행됩니다. 디바이스 프라이빗 키는 인스턴스에서 생성되어 `/greengrass/v2` 아래에 유지됩니다. 스크립트가 Systems Manager를 통해 전송하는 원격 명령에는 리소스 이름만 포함되므로 키나 자격 증명이 Systems Manager 명령 기록에 들어가지 않습니다.

## 작업 1: 인스턴스 프로파일 생성

스크립트는 인스턴스 프로파일을 생성하지 않습니다. 사용자가 소유하므로 설치 프로그램이 수행할 수 있는 작업을 제어합니다. 해당 역할에는 `AmazonSSMManagedInstanceCore`가 필요하므로 Systems Manager가 설치 명령을 실행할 수 있으며, 설치 프로그램의 `--provision true` 경로에 대한 임시 정책이 추가됩니다.

```bash
export TUTORIAL_ACCOUNT_ID=$(aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" \
  sts get-caller-identity --query Account --output text)

cat > /tmp/greengrass-tutorial-ec2-trust.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Principal": { "Service": "ec2.amazonaws.com" }, "Action": "sts:AssumeRole" }
  ]
}
EOF

aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam create-role \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --assume-role-policy-document file:///tmp/greengrass-tutorial-ec2-trust.json
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam attach-role-policy \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore
```

임시 설치 프로그램 정책은 [설치 프로그램을 위한 최소 IAM 정책](https://docs.aws.amazon.com/greengrass/v2/developerguide/provision-minimal-iam-policy.html)을 따릅니다. `CreateIoTResources` 문은 공식 문입니다. IAM 문은 공식 `CreateTokenExchangeRole` 문보다 좁습니다. 스크립트가 설치 프로그램이 실행되기 전에 토큰 교환 역할과 해당 `<role>Access` 정책을 생성하므로 설치 프로그램은 이를 읽기만 하고 `iam:CreateRole`, `iam:CreatePolicy` 또는 `iam:AttachRolePolicy`가 필요하지 않습니다.

```bash
cat > /tmp/greengrass-tutorial-installer.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReuseTokenExchangeRole",
      "Effect": "Allow",
      "Action": ["iam:GetRole", "iam:PassRole", "iam:GetPolicy"],
      "Resource": [
        "arn:aws:iam::${TUTORIAL_ACCOUNT_ID}:role/${TUTORIAL_PREFIX}-token-exchange",
        "arn:aws:iam::${TUTORIAL_ACCOUNT_ID}:policy/${TUTORIAL_PREFIX}-token-exchangeAccess",
        "arn:aws:iam::aws:policy/${TUTORIAL_PREFIX}-token-exchangeAccess"
      ]
    },
    {
      "Sid": "CreateIoTResources",
      "Effect": "Allow",
      "Action": [
        "iot:AddThingToThingGroup",
        "iot:AttachPolicy",
        "iot:AttachThingPrincipal",
        "iot:CreateKeysAndCertificate",
        "iot:CreatePolicy",
        "iot:CreateRoleAlias",
        "iot:CreateThing",
        "iot:CreateThingGroup",
        "iot:DescribeEndpoint",
        "iot:DescribeRoleAlias",
        "iot:DescribeThingGroup",
        "iot:GetPolicy"
      ],
      "Resource": "*"
    }
  ]
}
EOF

aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam put-role-policy \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --policy-name greengrass-installer-bootstrap \
  --policy-document file:///tmp/greengrass-tutorial-installer.json
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam create-instance-profile \
  --instance-profile-name "${TUTORIAL_PREFIX}-instance"
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam add-role-to-instance-profile \
  --instance-profile-name "${TUTORIAL_PREFIX}-instance" \
  --role-name "${TUTORIAL_PREFIX}-instance"
```

작업 4는 디바이스가 프로비저닝되면 `greengrass-installer-bootstrap`을 다시 제거합니다.

## 작업 2: Ubuntu 26.04 x86_64 이미지 선택

Canonical은 현재 이미지 ID를 공개 Systems Manager 파라미터로 게시합니다. amd64의 Ubuntu 26.04용 이미지를 읽은 다음 사용하기 전에 소유자, 아키텍처 및 이름을 확인합니다.

```bash
export TUTORIAL_AMI_ID=$(aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ssm get-parameter \
  --name /aws/service/canonical/ubuntu/server/26.04/stable/current/amd64/hvm/ebs-gp3/ami-id \
  --query Parameter.Value --output text)

aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ec2 describe-images \
  --image-ids "$TUTORIAL_AMI_ID" \
  --query 'Images[0].[OwnerId,Architecture,Name]' --output text
```

출력에는 소유자 `099720109477`(Canonical), 아키텍처 `x86_64`, 그리고 `ubuntu-resolute-26.04-amd64-server`를 포함하는 이름이 표시되어야 합니다. 스크립트는 동일한 세 가지 값을 확인하고 다른 이미지는 거부합니다.

Ubuntu 26.04는 두 가지 이유로 사용됩니다. 생성된 레시피의 `Run` 단계가 고정하는 인터프리터인 `python3.14`를 제공합니다. 또한 기본 `sudo`로 `sudo-rs`를 제공하는데, 이는 IPC 환경이 손실되기 때문에 Nucleus 2.18.3에서 IPC 컴포넌트가 시작되지 않도록 할 수 있습니다. 스크립트는 `openjdk-21-jre-headless`, `unzip`, `python3.14` 및 `/usr/bin/sudo.ws`를 제공하는 클래식 `sudo` 패키지를 설치한 다음 `/usr/bin/sudo.ws`를 `sudo`로 선택하고 nucleus를 설치하기 전에 선택을 확인합니다. Canonical 이미지에는 `sudo`와 `sudo-rs`가 모두 사전 설치되어 있으므로 alternatives 전환이 효과적인 단계입니다. <Link path="guides/greengrass-component#문제-해결-및-서비스-제한">컴포넌트 문제 해결 노트</Link>를 참조하세요.

## 작업 3: 설정 스크립트 다운로드 및 실행

이 문서 사이트에서 스크립트를 다운로드하고 읽은 다음 워크스페이스 루트에서 실행합니다.

<Code lang="bash" code={`curl -fsSLo setup-greengrass-tutorial.sh ${setupScriptUrl}\nchmod +x setup-greengrass-tutorial.sh\nless setup-greengrass-tutorial.sh`} />

동일한 파일이 `docs/public/greengrass/setup-tutorial.sh`의 리포지토리에 체크인되어 있습니다.

```bash
./setup-greengrass-tutorial.sh setup \
  --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" --prefix "$TUTORIAL_PREFIX" \
  --ami-id "$TUTORIAL_AMI_ID" --instance-profile "${TUTORIAL_PREFIX}-instance"
```

리전에 기본 VPC가 없는 경우 `--subnet-id <subnet-id>`를 전달합니다. 기본 `t3.small`을 변경하려면 `--instance-type`을 전달합니다.

스크립트는 다음 단계를 순서대로 수행하고 생성된 각 리소스 후에 상태 파일을 작성합니다.

1. 호출자 아이덴티티를 확인하고, 이미지를 검증하고, 인스턴스 프로파일이 존재하는지 확인합니다.
2. 위 표의 리소스가 아직 존재하지 않는지 확인합니다. 접두사 아래에 기존 thing group, thing, role, policy 또는 role alias가 있으면 스크립트가 아무것도 생성하기 전에 중지됩니다.
3. thing group과 thing, 액세스 정책이 있는 토큰 교환 역할, role alias 및 디바이스 IoT 정책을 생성합니다. IoT 정책은 개발자 가이드의 [최소 코어 디바이스 정책](https://docs.aws.amazon.com/greengrass/v2/developerguide/device-auth.html#greengrass-core-minimal-iot-policy)에 `arn:aws:iot:<region>:<account-id>:topic/tutorial/greengrass/heartbeat`에 대한 `iot:Publish`를 추가한 것입니다.
4. 인스턴스 프로파일과 IMDSv2가 필요한 인스턴스를 시작하고, Systems Manager에 등록될 때까지 기다린 다음, 필수 구성 요소를 설치하고, `sudo`를 전환하고, `greengrass-nucleus-latest.zip`을 다운로드하고, `--provision true --setup-system-service true`, 위의 thing, group, policy, role 및 alias 이름, 그리고 `--component-default-user ggc_user:ggc_group`로 설치 프로그램을 실행하는 하나의 `AWS-RunShellScript` 명령을 보냅니다.
5. 명령이 완료될 때까지 폴링한 다음 설치 프로그램이 thing에 연결한 인증서를 기록하고 코어 디바이스가 Greengrass에 나타날 때까지 기다립니다.

설정은 약 10분이 걸립니다. 완료되면 기록된 값을 셸에 로드하고 상태 파일을 Git에서 제외합니다.

```bash
source .greengrass-tutorial.env
echo .greengrass-tutorial.env >> .gitignore
```

상태 파일은 `TUTORIAL_THING_NAME`, `TUTORIAL_THING_GROUP_ARN`, `TUTORIAL_TOKEN_EXCHANGE_ROLE_ARN`, `TUTORIAL_INSTANCE_ID`, `TUTORIAL_CERTIFICATE_ARN` 및 바인딩된 아이덴티티를 내보냅니다. 모듈 3은 이 중 두 개를 CDK 스택에 전달합니다.

<Aside type="note" title="재실행 및 실패">
성공적인 실행 후 `setup`을 다시 실행하면 기존 인스턴스를 보고하고 아무것도 변경하지 않습니다. 예를 들어 설치 명령이 실패하여 실행이 중간에 중지되면 상태 파일은 진행 상황을 기록하고 재실행은 계속을 거부합니다. 동일한 프로파일, 리전 및 접두사로 `cleanup`을 실행하고 원인을 수정한 다음 `setup`을 다시 실행합니다. Cleanup은 상태 파일이 기록한 리소스만 건드리고, 이미 사라진 객체를 허용하며, 다른 오류에서는 중지됩니다.
</Aside>

## 작업 4: 임시 설치 프로그램 권한 제거

설치 프로그램이 완료되었습니다. 부트스트랩 정책을 제거하여 인스턴스가 Systems Manager 액세스만 유지하도록 합니다.

```bash
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam delete-role-policy \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --policy-name greengrass-installer-bootstrap
```

## 작업 5: 디바이스 확인

nucleus는 첫 시작 시 코어 디바이스를 등록합니다. 클라우드에서 확인합니다.

```bash
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" greengrassv2 get-core-device \
  --core-device-thing-name "$TUTORIAL_THING_NAME" \
  --query '{status: status, coreVersion: coreVersion, platform: platform, architecture: architecture}'
```

`HEALTHY`, `linux` 및 `amd64`가 예상됩니다. 인스턴스에서 로그를 읽으려면 파라미터 파일과 함께 Systems Manager 명령을 보냅니다. 첫 번째 줄은 `AWS-RunShellScript`가 존중하는 shebang입니다.

```bash
cat > /tmp/greengrass-tutorial-command.json <<'EOF'
{ "commands": ["#!/bin/bash", "tail -n 20 /greengrass/v2/logs/greengrass.log"] }
EOF

TUTORIAL_COMMAND_ID=$(aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ssm send-command \
  --instance-ids "$TUTORIAL_INSTANCE_ID" --document-name AWS-RunShellScript \
  --parameters file:///tmp/greengrass-tutorial-command.json \
  --query Command.CommandId --output text)
sleep 5
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ssm get-command-invocation \
  --command-id "$TUTORIAL_COMMAND_ID" --instance-id "$TUTORIAL_INSTANCE_ID" \
  --query StandardOutputContent --output text
```

모듈 3은 동일한 패턴을 사용하여 컴포넌트 자체 로그를 읽습니다.
