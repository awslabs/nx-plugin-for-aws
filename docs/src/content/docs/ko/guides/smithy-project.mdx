[Smithy](https://smithy.io/)는 서비스와 서비스가 교환하는 데이터를 설명하기 위한 인터페이스 정의 언어입니다. Smithy 프로젝트 생성기는 Smithy 모델을 포함하는 프로젝트를 생성합니다.

Smithy 프로젝트에는 두 가지 종류가 있습니다:

- **Service** (`--type=service`) — 서비스와 그 작업을 정의하는 모델입니다. 이것은 <Link path="guides/ts-smithy-api">`ts#api --framework=smithy` 생성기</Link>가 TypeScript 구현과 함께 생성하는 것입니다.
- **Shape library** (`--type=shapes`) — 재사용 가능한 shape을 정의하지만 서비스는 정의하지 않는 모델입니다. shape 라이브러리를 Smithy 프로젝트에 연결하여 각 프로젝트에서 정의를 복제하는 대신 shape을 공유할 수 있습니다.

:::tip
구현이 포함된 API를 원한다면 <Link path="guides/ts-smithy-api">`ts#api` 생성기</Link>를 대신 사용하세요. 이것은 Smithy 모델 프로젝트 _와_ 이를 구현하는 TypeScript 서버를 생성합니다.
:::

shape 라이브러리는 shape만 정의합니다:

```smithy
$version: "2.0"

namespace com.example

structure Customer {
    @required
    id: String

    name: String
    email: String
}
```

shape 라이브러리는 서비스가 없으므로 `smithy-build.json`은 코드 생성을 구성하지 않습니다 — 빌드하면 모델을 검증하고 `dist/<my-shapes>/build/model.json`에 단일 JSON 모델 파일로 조립합니다.

  - my-service

    - ssdk.rolldown.config.mjs 생성된 TypeScript Server SDK를 번들링
    - project.json 프로젝트 구성 및 빌드 타겟

서비스 모델은 서비스 shape과 노출하는 작업을 정의합니다:

```smithy
$version: "2.0"

namespace com.example

use aws.protocols#restJson1

@title("MyService")
@restJson1
service MyService {
    version: "1.0.0"
    operations: [
        Echo
    ]
}
```

서비스 프로젝트를 빌드하면 OpenAPI 사양과 TypeScript Server SDK가 `dist/<my-service>/build/`에 생성됩니다.

</OptionFilter>

## 빌드

Smithy 프로젝트는 [Smithy CLI](https://smithy.io/2.0/guides/smithy-cli/index.html)로 빌드되며, 모델을 검증합니다:

<NxCommands commands={['build my-shapes']} />

macOS와 Linux에서는 빌드가 필요에 따라 가져오는 [mise](https://mise.jdx.dev/)에 의해 CLI가 해결되므로 설치할 것이 없습니다 — 처음 빌드할 때 고정된 버전을 다운로드하고 캐시합니다.

### Windows에서 빌드하기

`mise`는 npm에 Windows 패키지를 게시하지 않으므로 Windows에서는 Smithy CLI를 직접 설치해야 합니다. [Smithy CLI 설치 가이드](https://smithy.io/2.0/guides/smithy-cli/cli_installation.html)를 따라 한 번 설치하고(예: `winget install smithy` 또는 `scoop install smithy`), `smithy`가 `PATH`에 있는지 확인하세요. Windows에서 생성된 Smithy 프로젝트는 `mise`를 통하지 않고 `smithy`를 직접 실행합니다.

:::caution[CLI 업그레이드]
CLI가 워크스페이스에 고정되지 않고 전역으로 설치되기 때문에 `nx migrate`로 워크스페이스를 업그레이드해도 CLI는 업그레이드되지 **않습니다**. 마이그레이션이 Smithy 의존성을 앞으로 이동할 때 전역 Smithy CLI를 일치하는 버전으로 직접 업그레이드하세요 — CLI는 더 새로운 `smithy-model`에 대해 빌드된 모델을 로드할 수 없습니다.
:::

### Smithy CLI 직접 사용하기

기본적으로 macOS와 Linux는 `mise`를 통해 CLI를 해결하고 Windows는 전역으로 설치된 CLI를 사용하지만, 프로젝트의 `project.json`에서 `compile` 타겟의 명령을 편집하여 모든 플랫폼에서 두 접근 방식 중 하나를 선택할 수 있습니다.

`mise` 대신 전역으로 설치된 Smithy CLI를 사용하려면 `mise` 접두사를 단순한 `smithy`로 바꾸세요:

```json title="packages/my-shapes/project.json" del={5} ins={6}
{
  "targets": {
    "compile": {
      "options": {
        "commands": ["... npx -y mise@<version> exec smithy@<version> -- smithy build ..."]
        "commands": ["... smithy build ..."]
      }
    }
  }
}
```

`mise`가 CLI를 해결하도록 되돌리려면 `npx -y mise@<version> exec smithy@<version> --` 접두사를 복원하세요.

:::caution
CLI를 직접 호출하면 버전이 더 이상 워크스페이스에 고정되지 않으므로 `nx migrate`가 이를 앞으로 이동할 수 없습니다 — 워크스페이스를 업그레이드할 때 전역 Smithy CLI를 독립적으로 업그레이드하세요.
:::

## Shape Library에 의존하기

shape 라이브러리를 빌드하면 조립된 모델이 `dist/<my-shapes>/build/model.json`에 작성됩니다. 이 단일 파일에는 라이브러리가 정의하는 모든 shape과 의존하는 모든 shape이 포함되어 있으므로 소비자는 직접 참조하는 라이브러리만 선언하면 됩니다.

다른 Smithy 프로젝트에서 shape 라이브러리에 의존하려면 소비 프로젝트에 두 가지 변경을 수행하세요:

<Steps>

1. 소비 프로젝트의 `smithy-build.json`에서 라이브러리의 빌드된 모델을 `imports`에 추가하세요. 경로는 해당 파일을 기준으로 상대적이므로 `../` 세그먼트의 수는 소비 프로젝트가 중첩된 깊이와 일치합니다 — 아래 `packages/my-api/model`의 경우 세 개입니다:

   ```json ins={4}
   {
     "version": "1.0",
     "sources": ["src/"],
     "imports": ["../../../dist/packages/my-shapes/build/model.json"],
     ...
   }
   ```

2. 소비자가 빌드되기 전에 모델이 존재하도록 `project.json`의 소비 프로젝트 `compile` 타겟의 의존성으로 라이브러리의 `build` 타겟을 추가하세요:

   ```json ins={4}
   {
     "targets": {
       "compile": {
         "dependsOn": ["@my-scope/my-shapes:build"],
         ...
       }
     }
   }
   ```

</Steps>

이제 모델에서 `use`를 사용하여 라이브러리의 shape을 참조할 수 있습니다:

```smithy
$version: "2.0"

namespace com.example.api

use com.example.shared#Customer

structure GetCustomerOutput {
    @required
    customer: Customer
}
```

shape 라이브러리는 같은 방식으로 다른 shape 라이브러리에 의존할 수 있습니다. 각 라이브러리의 빌드된 모델에는 이미 자체 의존성이 포함되어 있으므로 직접 참조하는 라이브러리에 대해서만 이러한 단계를 반복하면 됩니다. 둘 이상의 경로로 도달하는 라이브러리는 한 번만 해결됩니다 — Smithy는 중복되지만 동등한 shape 정의를 무시합니다.
