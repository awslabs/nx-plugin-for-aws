[tRPC](https://trpc.io/)는 엔드투엔드 타입 안전성을 갖춘 TypeScript API를 구축하기 위한 프레임워크입니다. tRPC를 사용하면 API 작업 입력 및 출력에 대한 업데이트가 프로젝트를 다시 빌드할 필요 없이 클라이언트 코드에 즉시 반영되고 IDE에서 확인할 수 있습니다.

tRPC API 생성기는 AWS CDK 또는 Terraform 인프라 설정과 함께 새로운 tRPC API를 생성합니다. 생성된 백엔드는 AWS API Gateway API를 통해 노출되며, [Zod](https://zod.dev/)를 사용한 스키마 검증을 포함합니다. 구조화된 로깅 및 CloudWatch 메트릭을 포함한 관찰성을 위해 [AWS Lambda Powertools](https://docs.powertools.aws.dev/lambda/typescript/latest/)를 설정합니다.

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambda hosting">
AWS X-Ray 추적도 설정됩니다.

프로시저는 AWS Lambda에서 실행되므로 관리할 서버가 없으며 제공하는 요청에 대해서만 비용을 지불합니다.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="ECS hosting">
프로시저는 API Gateway HTTP API 뒤의 Amazon ECS 컨테이너에서 장기 실행 HTTP 서버로 실행됩니다. X-Ray 추적이 거기서 추적을 생성하지 않는 이유를 포함하여 변경되는 내용은 <a href="#running-on-amazon-ecs">Running on Amazon ECS</a>를 참조하세요.
</OptionFilter>

      - logger.ts middleware for configuring AWS Powertools for Lambda logging

      - metrics.ts middleware for configuring AWS Powertools for Lambda metrics

    - client

  - tsconfig.lib.json TypeScript configuration for the library sources

## tRPC API 구현

높은 수준에서 tRPC API는 특정 프로시저에 요청을 위임하는 라우터로 구성됩니다. 각 프로시저는 Zod 스키마로 정의된 입력과 출력을 가집니다.

### 스키마

`src/schema` 디렉토리에는 클라이언트와 서버 코드 간에 공유되는 타입이 포함되어 있습니다. 이 패키지에서 이러한 타입은 TypeScript 우선 스키마 선언 및 검증 라이브러리인 [Zod](https://zod.dev/)를 사용하여 정의됩니다.

예제 스키마는 다음과 같을 수 있습니다:

```ts
import { z } from 'zod';

// Schema definition
export const UserSchema = z.object({
  name: z.string(),
  height: z.number(),
  dateOfBirth: z.string().datetime(),
});

// Corresponding TypeScript type
export type User = z.TypeOf<typeof UserSchema>;
```

위 스키마가 주어지면 `User` 타입은 다음 TypeScript와 동일합니다:

```ts
interface User {
  name: string;
  height: number;
  dateOfBirth: string;
}
```

스키마는 서버와 클라이언트 코드 모두에서 공유되므로 API에서 사용되는 구조를 변경할 때 업데이트할 단일 위치를 제공합니다.

스키마는 tRPC API에 의해 런타임에 자동으로 검증되므로 백엔드에서 사용자 정의 검증 로직을 수작업으로 작성할 필요가 없습니다.

Zod는 `.merge`, `.pick`, `.omit` 등과 같이 스키마를 결합하거나 파생하는 강력한 유틸리티를 제공합니다. 자세한 내용은 [Zod 문서 웹사이트](https://zod.dev/?id=basic-usage)에서 확인할 수 있습니다.

### 라우터 및 프로시저

tRPC 라우터는 `src/router.ts`에 정의되어 있으며 모든 프로시저를 등록합니다. 각 프로시저는 예상되는 입력, 출력 및 구현을 정의합니다.

<OptionFilter not when={{ infra: 'http-ecs' }} description="The Lambda entry point">
Lambda 핸들러 진입점은 `src/handler.ts`에 있으며 요청을 라우터로 전달합니다.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="The container entry point">
진입점은 `src/<api-name>-container/server.ts`이며, 컨테이너가 실행하는 HTTP 서버로 요청을 라우터로 전달합니다.
</OptionFilter>

생성된 샘플 라우터에는 `echo`라는 단일 작업이 있습니다:

```ts
import { echo } from './procedures/echo.js';

export const appRouter = router({
  echo,
});
```

예제 `echo` 프로시저는 `src/procedures/echo.ts`에 생성됩니다:

```ts
export const echo = publicProcedure
  .input(EchoInputSchema)
  .output(EchoOutputSchema)
  .query((opts) => ({ message: opts.input.message }));
```

위 내용을 분석하면:

- `publicProcedure`는 `src/middleware`에 설정된 미들웨어를 포함하여 API의 공개 메서드를 정의합니다. 이 미들웨어에는 로깅, 추적 및 메트릭을 위한 AWS Lambda Powertools 통합이 포함됩니다.
- `input`은 작업에 대한 예상 입력을 정의하는 Zod 스키마를 받습니다. 이 작업에 대해 전송된 요청은 이 스키마에 대해 자동으로 검증됩니다.
- `output`은 작업에 대한 예상 출력을 정의하는 Zod 스키마를 받습니다. 스키마에 맞지 않는 출력을 반환하면 구현에서 타입 오류가 표시됩니다.
- `query`는 API의 구현을 정의하는 함수를 받습니다. 이 구현은 `opts`를 받으며, 여기에는 작업에 전달된 `input`과 미들웨어에 의해 설정된 다른 컨텍스트(`opts.ctx`에서 사용 가능)가 포함됩니다. `query`에 전달된 함수는 `output` 스키마에 맞는 출력을 반환해야 합니다.

구현을 정의하기 위해 `query`를 사용하는 것은 작업이 변경을 일으키지 않음을 나타냅니다. 데이터를 검색하는 메서드를 정의하는 데 사용하세요. 변경을 일으키는 작업을 구현하려면 대신 `mutation` 메서드를 사용하세요.

새 프로시저를 추가하는 경우 `src/router.ts`의 라우터에 추가하여 등록해야 합니다.

<OptionFilter when={{ infra: 'rest-lambda' }} description="Streaming subscriptions — REST API only, uses SSE">
### 구독 (스트리밍)

tRPC 구독을 사용하면 [Server-Sent Events (SSE)](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events)를 사용하여 서버에서 클라이언트로 데이터를 스트리밍할 수 있습니다. 컴퓨팅 유형으로 `rest-lambda`를 선택하면 생성기가 스트리밍에 필요한 인프라와 스트리밍 Lambda 핸들러 및 `ZodAsyncIterable` 스키마 헬퍼를 자동으로 구성합니다.

구독 프로시저를 정의하려면 비동기 생성기 함수와 함께 `.subscription` 메서드를 사용하세요. `src/schema/z-async-iterable.ts`의 `ZodAsyncIterable` 헬퍼를 사용하여 출력 스키마를 정의하세요:

```ts
import { publicProcedure } from '../init.js';
import { z } from 'zod';
import { ZodAsyncIterable } from '../schema/z-async-iterable.js';

const InputSchema = z.object({ query: z.string() });
const ChunkSchema = z.object({ text: z.string() });

export const myStream = publicProcedure
  .input(InputSchema)
  .output(
    ZodAsyncIterable({
      yield: ChunkSchema,
    }),
  )
  .subscription(async function* (opts) {
    // Yield data to the client as it becomes available
    for (const chunk of await getResults(opts.input.query)) {
      yield { text: chunk };
    }
  });
```

다른 프로시저와 마찬가지로 라우터에 구독을 등록하세요:

```ts
export const appRouter = router({
  echo,
  myStream,
});
```

생성된 인프라는 모든 REST API 작업에 대해 API Gateway에서 `ResponseTransferMode.STREAM`을 사용하는 스트리밍 Lambda 핸들러를 사용하므로 구독이 일반 쿼리 및 뮤테이션과 함께 작동할 수 있습니다.
</OptionFilter>

## tRPC API 사용자 정의

### 오류

구현에서 `TRPCError`를 throw하여 클라이언트에 오류 응답을 반환할 수 있습니다. 이는 오류 유형을 나타내는 `code`를 받습니다. 예를 들어:

```ts
throw new TRPCError({
  code: 'NOT_FOUND',
  message: 'The requested resource could not be found',
});
```

### 작업 구성

API가 성장함에 따라 관련 작업을 함께 그룹화하고 싶을 수 있습니다.

중첩된 라우터를 사용하여 작업을 함께 그룹화할 수 있습니다. 예를 들어:

```ts
import { getUser } from './procedures/users/get.js';
import { listUsers } from './procedures/users/list.js';

const appRouter = router({
   users: router({
      get: getUser,
      list: listUsers,
   }),
   ...
})
```

클라이언트는 이 작업 그룹화를 받습니다. 예를 들어 이 경우 `listUsers` 작업을 호출하는 것은 다음과 같을 수 있습니다:

```ts
client.users.list.query();
```

### 로깅

AWS Lambda Powertools 로거는 `src/middleware/logger.ts`에 구성되어 있으며 `opts.ctx.logger`를 통해 API 구현에서 액세스할 수 있습니다. 이를 사용하여 CloudWatch Logs에 로그를 기록하거나 모든 구조화된 로그 메시지에 포함할 추가 값을 제어할 수 있습니다. 예를 들어:

```ts {5}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      opts.ctx.logger.info('Operation called with input', opts.input);

      return ...;
   });
```

로거에 대한 자세한 내용은 [AWS Lambda Powertools Logger 문서](https://docs.powertools.aws.dev/lambda/typescript/latest/core/logger/)를 참조하세요.

### 메트릭 기록

AWS Lambda Powertools 메트릭은 `src/middleware/metrics.ts`에 구성되어 있으며 `opts.ctx.metrics`를 통해 API 구현에서 액세스할 수 있습니다. 이를 사용하여 AWS SDK를 가져오고 사용할 필요 없이 CloudWatch에 메트릭을 기록할 수 있습니다. 예를 들어:

```ts {5}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      opts.ctx.metrics.addMetric('Invocations', 'Count', 1);

      return ...;
   });
```

자세한 내용은 [AWS Lambda Powertools Metrics 문서](https://docs.powertools.aws.dev/lambda/typescript/latest/core/metrics/)를 참조하세요.

### X-Ray 추적 미세 조정

AWS Lambda Powertools 추적기는 `src/middleware/tracer.ts`에 구성되어 있으며 `opts.ctx.tracer`를 통해 API 구현에서 액세스할 수 있습니다. 이를 사용하여 AWS X-Ray로 추적을 추가하여 API 요청의 성능과 흐름에 대한 자세한 인사이트를 제공할 수 있습니다. 예를 들어:

```ts {5-7}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      const subSegment = opts.ctx.tracer.getSegment()!.addNewSubsegment('MyAlgorithm');
      // ... my algorithm logic to capture
      subSegment.close();

      return ...;
   });
```

자세한 내용은 [AWS Lambda Powertools Tracer 문서](https://docs.powertools.aws.dev/lambda/typescript/latest/core/tracer/)를 참조하세요.

<OptionFilter when={{ infra: 'http-ecs' }} description="X-Ray produces no traces on ECS">
:::caution[ECS에서 추적 없음]
위의 호출은 컨테이너에서 오류 없이 실행되지만 추적을 생성하지 않습니다. Powertools는 Lambda에서 실행되지 않을 때 추적기를 끄므로 `getSegment()`는 어디에도 전송되지 않는 플레이스홀더 하위 세그먼트를 반환합니다. 얻을 수 있는 것과 추적이 필요한 경우 추가할 내용은 <a href="#observability">Observability</a>를 참조하세요.
:::
</OptionFilter>

### 사용자 정의 미들웨어 구현

미들웨어를 구현하여 프로시저에 제공되는 컨텍스트에 추가 값을 추가할 수 있습니다.

예를 들어, `src/middleware/identity.ts`에서 API를 호출하는 사용자에 대한 세부 정보를 추출하는 미들웨어를 구현해 보겠습니다.

<OptionFilter when={{ auth: 'iam', infra: ['rest-lambda', 'http-lambda'] }} description="Identity middleware example for IAM-authenticated APIs on Lambda">
이 예제는 `IAM` 인증을 위한 ID 미들웨어를 안내합니다. API Gateway 이벤트에서 추출한 sub를 사용하여 Cognito에서 호출자를 조회합니다.

조회는 생성된 tRPC API의 종속성이 아닌 Cognito Identity Provider 클라이언트를 사용합니다. 먼저 API 프로젝트에 설치하세요:

먼저 컨텍스트에 추가할 내용을 정의합니다:

```ts
export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
```

컨텍스트에 추가 _선택적_ 속성을 정의합니다. tRPC는 이 미들웨어를 올바르게 구성한 프로시저에서 이것이 정의되도록 관리합니다.

다음으로 미들웨어 자체를 구현합니다. 다음과 같은 구조를 가집니다:

```ts

      // Add logic here to run before the procedure
```

우리의 경우 호출하는 Cognito 사용자에 대한 세부 정보를 추출하려고 합니다. API Gateway 이벤트에서 사용자의 주체 ID(또는 "sub")를 추출하고 Cognito에서 사용자 세부 정보를 검색하여 이를 수행합니다. 구현은 REST API 또는 HTTP API에 의해 함수에 이벤트가 제공되었는지에 따라 다릅니다:

<Tabs syncKey="http-rest">
<TabItem label="REST API" _filter={{ infra: 'rest-lambda' }}>
```ts
import { CognitoIdentityProvider } from '@aws-sdk/client-cognito-identity-provider';
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEvent } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext & CreateAWSLambdaContextOptions<APIGatewayProxyEvent>
    >()
    .create();

  const cognito = new CognitoIdentityProvider();

  return t.procedure.use(async (opts) => {
    const cognitoAuthenticationProvider =
      opts.ctx.event.requestContext?.identity?.cognitoAuthenticationProvider;

    let sub: string | undefined = undefined;
    if (cognitoAuthenticationProvider) {
      const providerParts = cognitoAuthenticationProvider.split(':');
      sub = providerParts[providerParts.length - 1];
    }

    if (!sub) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `Unable to determine calling user`,
      });
    }

    const { Users } = await cognito.listUsers({
      // Assumes user pool id is configured in lambda environment
      UserPoolId: process.env.USER_POOL_ID!,
      Limit: 1,
      Filter: `sub="${sub}"`,
    });

    if (!Users || Users.length !== 1) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `No user found with subjectId ${sub}`,
      });
    }

    // Provide the identity to other procedures in the context
    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username: Users[0].Username!,
        },
      },
    });
  });
};
```

<Tabs syncKey="http-rest">

REST API의 Cognito User Pools 권한 부여자는 클레임을 `event.requestContext.authorizer.claims`에 배치합니다:

```ts
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEvent } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext & CreateAWSLambdaContextOptions<APIGatewayProxyEvent>
    >()
    .create();

  return t.procedure.use(async (opts) => {
    const claims = opts.ctx.event.requestContext?.authorizer?.claims as
      | Record<string, string>
      | undefined;

    const sub = claims?.sub;
    const username = claims?.username ?? claims?.['cognito:username'];

    if (!sub || !username) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: 'Unable to determine calling user',
      });
    }

    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username,
        },
      },
    });
  });
};
```
</TabItem>

```ts
import { publicProcedure } from '../init.js';
import { createIdentityPlugin } from '../middleware/identity.js';

export const me = publicProcedure
  .concat(createIdentityPlugin())
  .output(z.object({ sub: z.string(), username: z.string() }))
  .query(({ ctx }) => ({
    sub: ctx.identity!.sub,
    username: ctx.identity!.username,
```

여기서는 `aws-jwt-verify`나 다른 JWT 확인 라이브러리가 필요하지 않습니다 — API Gateway Cognito User Pools 권한 부여자가 Lambda가 실행되기 전에 이미 서명, 발급자, 범위 및 만료를 확인했습니다. 이러한 검사 중 하나라도 실패하면 API Gateway는 `401 Unauthorized`를 반환하고 핸들러는 호출되지 않습니다.
:::

## tRPC API 배포

tRPC API 생성기는 선택한 `iac`를 기반으로 CDK 또는 Terraform 인프라 코드를 생성합니다. 이를 사용하여 tRPC API를 배포할 수 있습니다.

<Infrastructure>
<Fragment slot="cdk">
API를 배포하기 위한 CDK 구성은 `common/constructs` 폴더에 있습니다. 이를 CDK 애플리케이션에서 사용할 수 있습니다. 예를 들어:

<OptionFilter when={{ auth: ['iam', 'custom'], infra: ['rest-lambda', 'http-lambda'] }} description="CDK usage for IAM or Custom authentication on Lambda">
```ts {6-8}
import { MyApi } from '@my-scope/common-constructs';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string) {
    // Add the api to your stack
    const api = new MyApi(this, 'MyApi', {
      integrations: MyApi.defaultIntegrations(this).build(),
    });
  }
}
```

:::caution[Custom Lambda Authorizer]
`Custom` 인증을 사용하는 경우 구성은 생성된 `src/authorizer.ts` 파일에서 내부적으로 Lambda Authorizer를 생성하며, 이는 **기본적으로 모든 요청을 거부합니다**. API가 트래픽을 수락하기 전에 해당 파일에서 권한 부여 로직을 구현해야 합니다.

권한 부여자 결과는 `Authorization` 헤더를 키로 하여 5분 동안 캐시되므로 취소된 토큰이 캐시된 결과가 만료될 때까지 수락될 수 있습니다. 더 빠른 취소가 필요한 경우 생성된 인프라에서 캐시 기간을 줄이세요.
:::
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="CDK usage when the API runs on ECS — pass the VPC">
`defaultIntegrations`는 서비스가 실행되는 VPC를 가져와 그 안에 모든 것을 빌드합니다: ECS 서비스, 그 앞의 내부 로드 밸런서, 그리고 API Gateway가 해당 로드 밸런서에 도달하는 VPC 링크. 구성은 VPC를 생성하지 않으므로 스택에서 VPC를 생성하거나 가져와야 합니다.

```ts {10,13-15}
import { MyApi } from '@my-scope/common-constructs';
import { Stack } from 'aws-cdk-lib';
import { Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string) {
    super(scope, id);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    const api = new MyApi(this, 'MyApi', {
      integrations: MyApi.defaultIntegrations(this, { vpc }).build(),
    });
  }
}
```

기존 VPC를 사용하려면 `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })`로 조회하고 `vpc`로 전달하세요.

컨테이너 서비스 자체를 변경하려면 `service`를 전달하세요 — `cpu`, `memoryLimitMiB`, `desiredCount`, `environment` 또는 태스크 역할에 권한을 부여하는 `grantTaskRole`:

```ts
MyApi.defaultIntegrations(this, {
  vpc,
  service: {
    cpu: 512,
    memoryLimitMiB: 1024,
    grantTaskRole: (taskRole) => myTable.grantReadWriteData(taskRole),
  },
}).build();
```

`auth`가 `cognito`로 설정된 경우 위의 Cognito 예제처럼 구성에 `identity`도 전달하세요.

```hcl
# Create an IAM policy to allow invoking the API
resource "aws_iam_policy" "api_invoke_policy" {
  name        = "MyApiInvokePolicy"
  description = "Policy to allow invoking the tRPC API"

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Action = "execute-api:Invoke"
        Resource = "${module.my_api.api_execution_arn}/*/*"
      }
    ]
  })
}

# Attach the policy to an IAM role (e.g., for authenticated users)
resource "aws_iam_role_policy_attachment" "api_invoke_access" {
  role       = aws_iam_role.authenticated_user_role.name
  policy_arn = aws_iam_policy.api_invoke_policy.arn
}

# Or attach to an existing role by name
resource "aws_iam_role_policy_attachment" "api_invoke_access_existing" {
  role       = "MyExistingRole"
  policy_arn = aws_iam_policy.api_invoke_policy.arn
}
```

- `module.my_api.api_execution_arn` - execute-api:Invoke 권한 부여용
- `module.my_api.api_arn` - API Gateway ARN
- `module.my_api.lambda_function_arn` - Lambda 함수 ARN

<OptionFilter when={{ infra: 'http-ecs' }} description="How ECS hosting works, what it costs and what it limits">
## Running on Amazon ECS

`infra`가 `http-ecs`로 설정된 경우 프로시저는 Lambda 함수가 아닌 컨테이너에서 장기 실행 HTTP 서버로 실행됩니다. 요청은 다음 경로를 따릅니다:

1. 호출자는 유일한 공개 진입점인 API Gateway HTTP API에 요청을 서명합니다. 모든 라우트는 선택한 `auth`에 대한 권한 부여자를 전달하므로 인증되지 않은 요청은 엣지에서 거부됩니다.
2. API Gateway는 VPC 링크를 통해 요청을 전달하며, 이는 VPC로의 프라이빗 경로입니다.
3. VPC 링크는 내부 로드 밸런서에 도달합니다. 로드 밸런서에는 공개 주소가 없으며 유일한 인바운드 규칙은 리스너 포트에서 VPC 링크의 보안 그룹을 허용합니다.
4. 로드 밸런서는 태스크로 요청을 전달합니다. 태스크의 유일한 인바운드 규칙은 컨테이너 포트에서 로드 밸런서의 보안 그룹을 허용하므로 VPC의 다른 어떤 것도 연결을 열 수 없습니다.

태스크는 프라이빗 서브넷에서 실행되며 공개 IP 주소를 받지 않습니다. 이 경로의 어떤 것도 주소 범위 인바운드를 허용하지 않습니다.

기본적으로 서비스, 로드 밸런서 및 VPC 링크는 NAT 게이트웨이를 통해 AWS에 도달하는 VPC의 `PRIVATE_WITH_EGRESS` 서브넷에 배치됩니다. `defaultIntegrations`에 `vpcSubnets: { subnetType: SubnetType.PRIVATE_ISOLATED }`를 전달하면 NAT 게이트웨이와 시간당 요금이 제거되지만 격리된 서브넷에는 외부 경로가 없으므로 VPC는 태스크가 시작되기 위해 4개의 VPC 엔드포인트가 필요합니다: 이미지를 가져오기 위한 `ecr.api` 및 `ecr.dkr`에 대한 인터페이스 엔드포인트, 이미지 레이어가 S3 객체이기 때문에 S3 게이트웨이 엔드포인트, 그리고 `awslogs` 드라이버가 쓸 수 있도록 `logs`에 대한 인터페이스 엔드포인트. 이것들이 없으면 태스크는 이미지를 가져올 수 없고 ECS는 이유를 말하지 않고 회로 차단기에서 배포를 롤백합니다.

VPC 링크, 로드 밸런서, 리스너, 대상 그룹 및 로드 밸런서가 액세스 로그를 쓰는 버킷은 `common/constructs`의 `core/api/ecs-http-endpoint.ts` 구성에 의해 생성되며, ECS에서 호스팅되는 모든 API가 공유합니다. API 자체의 구성은 컨테이너 서비스의 이름을 지정하고 모든 작업을 해당 엔드포인트로 라우팅합니다.

### 컨테이너에서 실행되는 것

`src/<api-name>-container/server.ts`는 두 가지 작업을 수행하는 `node:http` 서버입니다. `GET /health`는 `{"status":"ok"}`로 응답하며, 이는 로드 밸런서의 대상 그룹과 컨테이너 상태 확인이 호출하는 것입니다. 다른 모든 요청은 라우터에 대해 해결하는 [tRPC standalone adapter](https://trpc.io/docs/server/adapters/standalone)로 이동합니다.

컨테이너에는 API Gateway 이벤트가 없으므로 프로시저 컨텍스트는 `event`, `context` 또는 `info` 필드를 전달하지 않습니다: `http-ecs`의 경우 제공된 `IMiddlewareContext`는 미들웨어가 배치하는 것만 명명합니다. 권한 부여자는 여전히 요청이 컨테이너에 도달할지 여부를 결정하지만 클레임은 요청과 함께 도착하지 않으므로 위의 ID 미들웨어 예제는 적용되지 않습니다. 프로시저에서 호출자의 ID를 읽으려면 API 구성에서 권한 부여자의 컨텍스트를 요청 헤더에 매핑하고 해당 헤더를 읽으세요.

### 관찰성

로그 및 메트릭은 Lambda에서와 같이 작동합니다: 컨테이너는 자체 CloudWatch 로그 그룹에 쓰고 메트릭 플러그인은 CloudWatch Logs가 추출할 임베디드 메트릭 형식으로 각 요청의 메트릭을 게시합니다.

메트릭 플러그인은 각 요청에 대한 메트릭 객체를 빌드하고 `opts.ctx.metrics`로 프로시저에 전달하므로 한 요청이 추가하는 메트릭은 다른 요청과 함께 게시되지 않습니다. 이는 처음부터 끝까지 하나의 호출이 메트릭을 소유하는 Lambda보다 여기서 더 중요합니다. 이 서버는 동시에 요청을 처리합니다. 프로세스의 모든 요청에서 하나의 저장소를 공유하는 자체 `Metrics` 객체가 아닌 `opts.ctx.metrics`를 통해 자체 메트릭을 추가하세요.

AWS X-Ray 추적은 그렇지 않습니다. Powertools는 Lambda 외부에서 추적기를 끄고 태스크에 세그먼트를 수신할 X-Ray 데몬이 없으므로 `opts.ctx.tracer` 호출은 오류 없이 실행되고 추적을 생성하지 않습니다. 필요한 경우 컨테이너 서비스에 사이드카로 데몬을 추가하세요.

API Gateway HTTP API의 액세스 로그는 API에 도달하는 모든 요청을 기록합니다. 로드 밸런서는 `EcsHttpEndpoint` 구성이 생성하는 버킷에 자체 액세스 로그를 쓰며, 여기서 어떤 태스크가 요청을 처리했는지와 무엇을 응답했는지 확인할 수 있습니다.

### 이미지 빌드 및 스캔

컨테이너 생성기는 API 이름을 따서 명명된 이미지 타겟을 제공합니다:

- `<api-name>-container-docker`는 linux/arm64 이미지를 빌드하며, 먼저 `bundle`을 실행하여 이미지가 번들된 서버를 보유하도록 합니다.
- `<api-name>-container-trivy`는 해당 이미지의 취약점을 스캔합니다.

이미지가 빌드되는 방법은 <Link path="/guides/ts-container">TypeScript Container Service</Link>를 참조하고, 배포 시 게시되는 방법은 <Link path="/guides/docker-bundling">Docker Bundling</Link>을 참조하세요.

### 제한 사항

- **통합 타임아웃.** API Gateway HTTP API는 통합을 약 30초로 제한합니다. 컨테이너가 계속 작동하더라도 그보다 오래 걸리는 프로시저는 게이트웨이에서 실패합니다.
- **스트리밍 없음.** tRPC 구독에는 `rest-lambda` 인프라가 필요합니다. HTTP API는 응답을 스트리밍할 수 없습니다.
- **페이로드 크기.** 요청 및 응답은 API Gateway의 10MB 제한을 따릅니다.
- **모든 작업에 대한 하나의 서비스.** `integrationPattern`은 `shared`입니다: 하나의 컨테이너 서비스가 있고 모든 라우트가 여기로 라우팅됩니다. 이 인프라의 경우 옵션은 항상 `shared`로 해결되며 `isolated`는 경고와 함께 무시됩니다.

### 비용

로드 밸런서는 요청당 비용을 지불하고 유휴 상태일 때 아무것도 지불하지 않는 Lambda와 비교하여 새로운 고정 비용입니다. 데이터 전송 전 us-east-1의 대략적인 월별 수치:

```ts
import { createMyApiClient } from '@my-scope/my-api';
```
