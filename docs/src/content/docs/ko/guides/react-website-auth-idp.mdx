<Link path="guides/react-website-auth">웹사이트 인증</Link>은 Amazon Cognito 사용자 풀을 생성하며, 기본적으로 해당 풀에 사용자 이름과 비밀번호가 있는 사용자만 로그인할 수 있습니다. 직원이나 고객이 Okta, Auth0 또는 Microsoft Entra ID와 같은 아이덴티티 프로바이더(IdP)에 이미 계정을 가지고 있다면, 웹사이트를 위해 별도의 두 번째 계정이 필요하게 됩니다.

이 생성기는 사용자 풀에 외부 [OpenID Connect](https://openid.net/developers/how-connect-works/) (OIDC) 아이덴티티 프로바이더를 추가합니다. 그러면 로그인 페이지에 사용자 이름과 비밀번호 양식 옆에 아이덴티티 프로바이더를 위한 버튼이 표시됩니다.

## 작동 방식

- 웹사이트는 여전히 사용자를 Cognito 로그인 페이지로 보냅니다. 이제 페이지에는 아이덴티티 프로바이더의 이름이 붙은 버튼이 있습니다.
- 버튼을 선택한 사용자는 아이덴티티 프로바이더에서 로그인합니다. 아이덴티티 프로바이더는 리디렉션 URI인 `https://<cognito domain>/oauth2/idpresponse`로 사용자를 Cognito로 다시 보냅니다.
- Cognito는 사용자 풀에 페더레이션 사용자를 생성하고, 매핑한 클레임(예: `email`)을 사용자의 속성으로 복사합니다.
- 그런 다음 Cognito는 로컬 사용자에게 발급하는 것과 동일한 종류의 토큰을 발급합니다. API, 에이전트 및 아이덴티티 풀은 변경 없이 이를 수락합니다.

풀에 사용자 이름과 비밀번호가 있는 사용자는 여전히 로그인할 수 있습니다.

## 아이덴티티 프로바이더 설정

생성기를 실행한 후 첫 번째 배포는 Secrets Manager에서 클라이언트 시크릿을 읽습니다. 시크릿이 존재하지 않으면 배포가 실패합니다. 다음 단계를 이 순서대로 따르세요. 생성기는 완료 시 이러한 단계도 출력합니다.

1. 아이덴티티 프로바이더에 애플리케이션을 등록하고 클라이언트 ID와 클라이언트 시크릿을 기록합니다. 4단계에서 리디렉션 URI를 추가합니다. `--clientId`를 클라이언트 ID로 설정하여 이 생성기를 실행합니다.
2. `clientSecretName` 옵션의 이름(기본값은 `<name>-oidc-client-secret`)으로 Secrets Manager에 클라이언트 시크릿을 저장합니다:

   ```bash
   aws secretsmanager create-secret --name TestIdp-oidc-client-secret --secret-string <client secret>
   ```

3. 배포합니다.
4. 아이덴티티 프로바이더의 애플리케이션에 리디렉션 URI를 추가합니다.

## 속성 매핑

생성된 사용자 풀에는 `email`, `given_name` 및 `family_name` 속성이 필요합니다. Cognito는 매 로그인 시 아이덴티티 프로바이더의 클레임에서 이를 채웁니다. 아이덴티티 프로바이더가 이 중 하나를 보내지 않으면 사용자의 첫 번째 로그인이 실패합니다. 따라서 생성기는 세 가지 중 하나라도 누락된 `attributeMapping`을 거부합니다.

`attributeMapping`은 JSON 객체입니다. 각 키는 사용자 풀 속성이고, 각 값은 아이덴티티 프로바이더의 클레임 이름입니다. 기본값은 각 속성을 동일한 이름의 클레임에 매핑합니다:

```json
{"email":"email","given_name":"given_name","family_name":"family_name"}
```

- 키는 `name` 또는 `phone_number`와 같은 [표준 속성](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html#cognito-user-pools-standard-attributes) 또는 `custom:department`와 같은 사용자 정의 속성일 수 있습니다.
- Cognito는 매핑된 이메일 주소를 미확인으로 처리합니다. 이메일 주소를 자체적으로 확인하는 아이덴티티 프로바이더에서만 `email_verified`를 매핑하세요. 그렇지 않으면 사용자가 아이덴티티 프로바이더에서 다른 사람의 주소를 설정하고 풀에서 확인된 것으로 표시될 수 있습니다.
- 아이덴티티 프로바이더에서 사용자의 이메일 주소가 변경되면 Cognito는 사용자의 다음 로그인 시 사용자 풀에 새 주소를 씁니다. `email_verified`는 `false`로 유지됩니다.
- 사용자 정의 속성은 사용자 풀에 이미 존재해야 하며 변경 가능해야 합니다.

Terraform 아이덴티티 프로바이더 파일은 또한 Cognito가 아이덴티티 프로바이더를 반환할 때 추가하는 두 가지 값을 설정합니다: `attribute_mapping`의 `"username" = "sub"` 및 `provider_details`의 `attributes_url_add_attributes = "false"`. 파일이 이를 설정하기 때문에 첫 번째 배포 후 두 번째 `terraform plan`은 아이덴티티 프로바이더에 대한 변경 사항을 표시하지 않습니다. 다른 아이덴티티 프로바이더를 사용하여 두 번째 플랜이 여전히 `provider_details`의 변경 사항을 표시하는 경우, 플랜이 Cognito가 반환하는 것으로 표시하는 값으로 해당 키를 파일에 추가하세요.

## 아이덴티티 프로바이더 참고 사항

아래 설정은 각 공급업체의 문서에서 가져온 것입니다. 아이덴티티 프로바이더 역할을 하는 Cognito 사용자 풀만 이 생성기로 테스트되었습니다. 해당 테스트는 이 생성기의 릴리스에 필요한 AWS 확인입니다.

### Okta

테스트되지 않음. Okta에서 OIDC 웹 애플리케이션을 생성합니다. 발급자는 Okta 도메인인 `https://<your-org>.okta.com` 또는 `https://<your-org>.okta.com/oauth2/default`와 같은 사용자 정의 권한 부여 서버입니다. 기본 범위인 `openid email profile`은 `email`, `given_name` 및 `family_name`을 반환하므로 기본 매핑이 작동합니다.

### Auth0

테스트되지 않음. Auth0에서 Regular Web Application을 생성합니다. 발급자는 `https://<your-tenant>.auth0.com/`이며, Auth0 토큰의 `iss` 클레임에 슬래시가 있으므로 후행 슬래시를 포함합니다. Auth0은 사용자의 연결이 제공하는 경우에만 `given_name` 및 `family_name`을 반환합니다. 이를 제공하지 않는 연결의 사용자는 다른 클레임을 매핑할 때까지 로그인할 수 없습니다.

### Microsoft Entra ID

테스트되지 않음. Entra ID에서 단일 테넌트 애플리케이션을 등록합니다. 발급자는 `https://login.microsoftonline.com/<tenant-id>/v2.0`입니다. 생성기는 모든 Entra ID 테넌트의 사용자를 수락하기 때문에 다중 테넌트 발급자(`/common/`, `/organizations/` 및 `/consumers/`)를 거부합니다. Entra ID는 애플리케이션의 ID 토큰에 선택적 클레임으로 추가한 경우에만 `given_name` 및 `family_name`을 보냅니다. `email` 클레임은 확인되지 않으므로 Entra ID에서 `email_verified`를 매핑하지 마세요.

### Cognito user pool

다른 Cognito 사용자 풀을 아이덴티티 프로바이더로 테스트하려면 발급자 `https://cognito-idp.<region>.amazonaws.com/<user pool id>`를 사용하세요. 앱 클라이언트에 클라이언트 시크릿, 권한 부여 코드 부여 및 범위 `openid email profile`을 제공합니다.

## 보안

- `email`이 아닌 `sub` 클레임(사용자 풀의 사용자 고유 ID)으로 사용자를 식별하세요. 페더레이션 사용자는 이메일이 로컬 사용자와 일치하더라도 자체 `sub`를 가진 풀의 새 사용자입니다. 플러그인이 생성하는 코드는 `sub`를 사용합니다.
- 단일 테넌트 발급자를 사용하세요. 다중 테넌트 발급자는 모든 조직의 사용자가 로그인할 수 있도록 합니다.
- <Link path="guides/react-website-auth">웹사이트 인증</Link>에서 설명하는 대로 프로덕션 스테이지에서 `http://localhost` 콜백 URL을 제거하세요. 페더레이션은 콜백 URL을 추가하지 않습니다.

## 페더레이션이 수행하지 않는 작업

- 사용자 풀에서 요구하는 MFA(다단계 인증)는 페더레이션 사용자에게 적용되지 않습니다. Cognito는 인증을 아이덴티티 프로바이더에 맡기므로 아이덴티티 프로바이더에서 MFA를 적용하세요.
- 웹사이트에서 로그아웃하면 Cognito 세션만 종료됩니다. OIDC 아이덴티티 프로바이더에서 사용자의 세션을 종료하지 않으므로 버튼을 통한 다음 로그인은 비밀번호 없이 완료될 수 있습니다. 공유 컴퓨터에서 사용자는 아이덴티티 프로바이더에서도 로그아웃해야 합니다.
- 사용자 메뉴에는 Cognito 사용자 이름이 표시됩니다. 페더레이션 사용자의 경우 아이덴티티 프로바이더 이름, 밑줄 및 아이덴티티 프로바이더에서의 사용자 `sub`가 소문자로 표시됩니다. 예를 들어 `testidp_00u1abcd`입니다.

## 클라이언트 시크릿

Cognito는 아이덴티티 프로바이더의 설정에 클라이언트 시크릿을 보관합니다. 사용자 풀에서 `cognito-idp:DescribeIdentityProvider`를 호출할 수 있는 권한이 있는 사람은 누구나 이를 읽을 수 있습니다. 이것은 사용하는 IaC 프로바이더에 관계없이 Cognito가 작동하는 방식입니다.

<Infrastructure>
  <Fragment slot="cdk">
구성은 시크릿을 [동적 참조](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/dynamic-references-secretsmanager.html)인 `{{resolve:secretsmanager:<clientSecretName>:SecretString:::}}`로 CloudFormation에 전달합니다. 합성된 템플릿에는 해당 참조만 포함됩니다. CloudFormation은 아이덴티티 프로바이더를 생성하거나 업데이트할 때 시크릿을 읽습니다. 시크릿을 교체하면 나중 배포에서 아이덴티티 프로바이더 리소스가 변경될 때만 Cognito가 새 값을 가져옵니다.
  </Fragment>
  <Fragment slot="terraform">
모듈은 `data "aws_secretsmanager_secret_version"` 데이터 소스로 시크릿을 읽으므로 `terraform plan`은 이를 `(sensitive value)`로 표시합니다. Terraform 상태는 여전히 데이터 소스에 대해 한 번, 아이덴티티 프로바이더에 대해 한 번 시크릿을 일반 텍스트로 보관합니다. 상태 버킷의 상태 객체를 읽을 수 있는 사람은 누구나 시크릿을 읽을 수 있습니다. 이에 따라 상태 버킷에 대한 읽기 액세스를 제한하세요.
  </Fragment>
</Infrastructure>

이 생성기에 대한 AWS 확인은 CDK를 사용하여 CloudFormation이 아이덴티티 프로바이더의 설정 내에서 `{{resolve:secretsmanager:...}}` 참조를 채우는 것을 확인했습니다. 페더레이션 로그인이 작동하며 배포된 템플릿에는 참조만 보관됩니다. 시크릿이 교체된 후 다른 변경 사항이 없는 배포는 Cognito에 이전 시크릿을 남겼습니다. CloudFormation은 아이덴티티 프로바이더 리소스가 변경될 때만 시크릿을 읽기 때문입니다.

교체된 시크릿을 Cognito로 보내려면:

<Infrastructure>
  <Fragment slot="cdk">
교체 후 배포에서 아이덴티티 프로바이더 리소스를 변경합니다. 한 가지 방법은 참조를 시크릿의 새 버전으로 지정하는 것입니다. 아이덴티티 프로바이더 구성인 `identity-providers/<name>.ts`에서 `aws secretsmanager put-secret-value`가 출력하는 버전 ID를 `SecretValue.secretsManager` 호출에 추가하고 `.unsafeUnwrap()`을 유지합니다:

```ts
SecretValue.secretsManager('TestIdp-oidc-client-secret', { versionId: '<version id>' })
```

그러면 템플릿의 참조가 변경되므로 CloudFormation은 아이덴티티 프로바이더를 업데이트하고 해당 버전의 시크릿을 읽습니다. 각 교체 시 버전 ID를 다시 변경하세요. 이는 동적 참조에 대한 CloudFormation 문서를 따르며 AWS에서 테스트되지 않았습니다.
  </Fragment>
  <Fragment slot="terraform">
교체 후 `terraform plan` 및 `terraform apply`를 실행합니다. 데이터 소스는 모든 플랜에서 시크릿의 현재 버전을 읽으므로 플랜은 아이덴티티 프로바이더의 제자리 업데이트를 표시하고 `apply`는 새 시크릿을 Cognito로 보냅니다. 이는 생성된 작업 공간이 사용하는 `hashicorp/aws` 프로바이더 6.69.1의 소스에서 읽은 것입니다: `provider_details`의 변경은 아이덴티티 프로바이더를 제자리에서 업데이트하며 교체하지 않습니다. AWS에서 테스트되지 않았습니다.
  </Fragment>
</Infrastructure>

## 기타 앱 클라이언트

앱 클라이언트는 애플리케이션이 로그인하는 Cognito 구성입니다. 생성기는 웹사이트의 앱 클라이언트인 웹 클라이언트에만 아이덴티티 프로바이더를 추가합니다. 동일한 사용자 풀의 다른 앱 클라이언트는 아이덴티티 프로바이더를 추가한 경우에만 페더레이션 사용자를 수락합니다. 예를 들어 <Link path="guides/ts-dcr-proxy">DCR 프록시</Link>(MCP 클라이언트, Model Context Protocol을 사용하는 AI 도구가 Cognito를 통해 로그인할 수 있도록 함)에 대해 생성하는 앱 클라이언트에는 이것이 필요합니다. 그렇지 않으면 페더레이션 사용자가 MCP 서버에 로그인할 수 없습니다. CDK에서 아이덴티티 프로바이더의 `provider.providerName`을 해당 클라이언트의 `supportedIdentityProviders`에 추가하세요.

## 에이전트 채팅을 위한 토큰

Cognito 인증을 사용하는 <Link path="guides/ts-agent">TypeScript 에이전트</Link>의 `<agent>-chat` 대상은 `AGENT_ACCESS_TOKEN` 환경 변수에서 Cognito 액세스 토큰을 읽습니다. 페더레이션 사용자에게는 Cognito 비밀번호가 없으므로 `admin-initiate-auth`가 작동하지 않습니다. 대신 웹사이트에 로그인하고 브라우저의 개발자 도구를 열고 세션 스토리지의 `oidc.user:...` 항목에서 `access_token`을 복사하세요.
