TypeScript 프로젝트 생성기는 [ECMAScript Modules (ESM)](https://www.typescriptlang.org/docs/handbook/modules/reference.html), TypeScript [프로젝트 참조](https://www.typescriptlang.org/docs/handbook/project-references.html), 테스트 실행을 위한 [Vitest](https://vitest.dev/), 린팅 및 포매팅을 위한 [Biome](https://biomejs.dev/)과 같은 모범 사례로 구성된 현대적인 [TypeScript](https://www.typescriptlang.org/) 라이브러리 또는 애플리케이션을 생성하는 데 사용할 수 있습니다.

## 생성기 출력

생성기는 `<directory>/<name>` 디렉토리에 다음과 같은 프로젝트 구조를 생성합니다:

<FileTree>

  - src TypeScript 소스 코드
    - index.ts
  - README.md
  - package.json 프로젝트의 패키지 이름과 의존성을 정의하는 프로젝트 매니페스트
  - project.json 프로젝트 구성 및 빌드 타겟
  - tsconfig.json 이 프로젝트의 기본 TypeScript 구성 (워크스페이스 루트 tsconfig.base.json을 확장)
  - tsconfig.lib.json 라이브러리를 위한 TypeScript 구성 (런타임 또는 패키징된 소스)
  - tsconfig.spec.json 테스트를 위한 TypeScript 구성
  - vitest.config.mts Vitest 구성

</FileTree>

:::tip[프로젝트 package.json]
프로젝트의 `package.json`은 최소한으로 시작합니다. 런타임 의존성을 추가하면 여기에 선언됩니다 (공유 빌드/테스트 도구는 워크스페이스 루트에 유지됨) — 자세한 내용은 [아래](#dependencies)에서 확인할 수 있습니다.
:::

워크스페이스 루트의 다음 파일에서도 일부 변경 사항을 확인할 수 있습니다:

<FileTree>

  - nx.json Nx 구성이 업데이트되어 프로젝트에 대한 @nx/js/typescript 플러그인을 구성합니다
  - tsconfig.base.json 워크스페이스의 다른 프로젝트에서 가져올 수 있도록 프로젝트에 대한 TypeScript 별칭이 설정됩니다
  - tsconfig.json 프로젝트에 대한 TypeScript 프로젝트 참조가 추가됩니다
  - vitest.config.mts 프로젝트 자체의 vitest.config.mts가 확장하는 공유 Vitest 구성 (첫 번째 TypeScript 프로젝트에 의해 생성됨)
  - package.json 공유 빌드 및 테스트 도구가 추가됩니다
  - pnpm-workspace.yaml 프로젝트가 워크스페이스에 추가되고 의존성 버전이 [카탈로그](#catalogs)에 추가됩니다 (패키지 매니저에 해당하는 파일)
  - .gitignore 빌드 및 테스트 출력 경로가 무시됩니다

</FileTree>

## TypeScript 소스 코드 작성

`src` 디렉토리에 TypeScript 코드를 추가하세요.

### ESM Import 구문

TypeScript 프로젝트가 ES Module이므로 파일 확장자를 명시적으로 참조하는 올바른 ESM 구문으로 import 문을 작성해야 합니다:

```ts title="index.ts" ".js"
import { sayHello } from './hello.js';
```

:::note[TypeScript 참조]
TypeScript를 사용하고 있고 `sayHello`가 `hello.ts`에 정의되어 있더라도 import에서 `.js` 파일 확장자를 사용합니다. 이에 대한 자세한 내용은 [여기](https://www.typescriptlang.org/docs/handbook/modules/reference.html)에서 확인할 수 있습니다.
:::

### 다른 TypeScript 프로젝트를 위한 내보내기

TypeScript 프로젝트의 진입점은 `src/index.ts`입니다. 다른 프로젝트에서 가져올 수 있도록 하려는 모든 것을 여기에 내보낼 수 있습니다:

```ts title="src/index.ts"
export { sayHello } from './hello.js';
export * from './algorithms/index.js';
```

### 다른 프로젝트에서 라이브러리 코드 가져오기

프로젝트에 대한 [TypeScript 별칭](https://www.typescriptlang.org/docs/handbook/modules/reference.html#paths)은 워크스페이스 `tsconfig.base.json`에 구성되어 있으며, 이를 통해 다른 TypeScript 프로젝트에서 TypeScript 프로젝트를 참조할 수 있습니다:

```ts title="packages/my-other-project/src/index.ts"
import { sayHello } from '@my-scope/my-library';
```

워크스페이스에서 새 프로젝트에 대한 import 문을 처음 추가하면 IDE에서 다음과 유사한 오류가 표시될 수 있습니다:

<details>
<summary>Import 오류</summary>

```bash wrap
File '/path/to/my/workspace/packages/my-library/src/index.ts' is not under 'rootDir' '/path/to/my/workspace/packages/my-consumer'. 'rootDir' is expected to contain all source files.
  File is ECMAScript module because '/path/to/my/workspace/package.json' has field "type" with value "module" ts(6059)
File '/path/to/my/workspace/packages/my-library/src/index.ts' is not listed within the file list of project '/path/to/my/workspace/packages/my-consumer/tsconfig.lib.json'. Projects must list all files or use an 'include' pattern.
  File is ECMAScript module because '/path/to/my/workspace/package.json' has field "type" with value "module" ts(6307)
```

</details>

이는 [프로젝트 참조](https://www.typescriptlang.org/docs/handbook/project-references.html)가 아직 설정되지 않았고, 가져온 프로젝트가 프로젝트의 `package.json`에 워크스페이스 의존성으로 아직 선언되지 않았기 때문입니다.

워크스페이스는 두 가지를 모두 관리하는 동기화 생성기로 구성되어 있으므로 수동으로 구성할 필요가 없습니다. 다음 명령을 실행하기만 하면 Nx가 필요한 구성을 추가합니다:

<NxCommands commands={['sync']} />

```bash wrap
 NX   The workspace is out of sync

[@nx/js:typescript-sync]: Some TypeScript configuration files are missing project references to the projects they depend on, contain stale project references, or have duplicate project references.
[@aws/nx-plugin:ts#sync]: Local project dependencies are out of sync. The following workspace dependencies will be declared:
packages/my-other-project/package.json:
- @my-scope/my-library: workspace:*

Syncing the workspace...
The workspace was synced successfully!
```

Nx의 TypeScript 동기화 생성기는 프로젝트 참조를 추가하고, 플러그인의 `ts#sync` 생성기는 가져온 프로젝트를 프로젝트의 `package.json`에 선언하므로 (패키지 매니저가 워크스페이스 프로토콜을 지원하는 경우 `workspace:*`, npm 및 yarn classic에서는 `*`) 패키지 매니저가 설치 시 로컬 프로젝트를 연결합니다. 이후 IDE의 오류가 사라지고 라이브러리를 사용할 준비가 됩니다.

:::tip[빌드 단축키]
프로젝트를 빌드하기만 해도 됩니다 — 동기화 생성기가 먼저 실행되고 미해결 변경 사항을 적용하라는 메시지가 표시됩니다:

```bash wrap
 NX   The workspace is out of sync

...

? Would you like to sync the identified changes to get your workspace up to date? …
Yes, sync the changes and run the tasks
No, run the tasks without syncing the changes
```

`Yes`를 선택하여 Nx가 워크스페이스를 동기화하도록 허용하세요.
:::

### 경로 별칭 동기화 유지

프로젝트의 `tsconfig.json`에 사용자 정의 `compilerOptions.paths` 항목을 추가하면 TypeScript는 `tsconfig.base.json`에 정의된 워크스페이스 별칭 상속을 중단합니다. 숨겨진 `ts#sync` 생성기는 `compile` 타겟 전에 실행되어 (`nx.json`에 구성됨) 이미 `paths`를 선언하는 `tsconfig.json`, `tsconfig.lib.json` 및 `tsconfig.app.json` 파일에 누락된 기본 별칭을 복사합니다. 옵트아웃하려면 `nx.json`의 `targetDefaults.compile.syncGenerators`에서 `@aws/nx-plugin:ts#sync`를 제거하세요.

### 의존성

각 TypeScript 프로젝트는 자체 `package.json`에 서드파티 런타임 의존성을 선언합니다. 프로젝트 간에 공유되는 빌드 및 테스트 도구는 루트 `package.json`에 정의됩니다.

프로젝트에 런타임 의존성을 추가하려면 해당 프로젝트에 설치하세요:

<InstallCommand pkg="some-npm-package" project="@my-scope/my-library" />

프로젝트 디렉토리 내에서 패키지 매니저의 일반 `add`/`install` 명령을 실행할 수도 있습니다.

공유 개발 도구를 추가하려면 워크스페이스 루트에 설치하세요:

<InstallCommand pkg="some-dev-tool" dev />

:::note
Biome의 [`noUndeclaredDependencies`](https://biomejs.dev/linter/rules/no-undeclared-dependencies/) 린트 규칙은 프로젝트의 소스가 자체 `package.json`에 선언된 패키지만 가져오도록 강제합니다. 구성 파일, 빌드 스크립트 및 테스트는 제외되므로 공유 도구는 루트에 유지할 수 있습니다.
:::

#### 카탈로그

카탈로그를 지원하는 패키지 매니저([pnpm](https://pnpm.io/catalogs), [yarn](https://yarnpkg.com/features/catalogs) 및 [bun](https://bun.com/docs/install/catalogs))의 경우, 생성기는 각 버전을 카탈로그에 기록하고 `catalog:` 프로토콜로 참조합니다 (예: `"zod": "catalog:"`). 따라서 어떤 프로젝트가 의존성을 선언하든 카탈로그가 버전의 단일 진실 공급원이 됩니다. 이는 [단일 버전 정책](https://nx.dev/concepts/decisions/dependency-management#single-version-policy)을 따르는 데 도움이 되며, 타입 충돌과 배포 번들에서 패키지의 여러 복사본을 방지합니다.

새 의존성을 직접 추가할 때도 카탈로그에 유지하세요:

<Tabs syncKey="package-manager">
  <TabItem label="pnpm">
    워크스페이스는 [`catalogMode: strict`](https://pnpm.io/settings#catalogmode)를 설정하므로 `pnpm add`는 버전을 카탈로그에 기록하고 자동으로 참조합니다 — 추가 단계가 필요 없습니다.

    ```bash
    pnpm add some-npm-package --filter my-library
    ```
  </TabItem>
  <TabItem label="yarn">
    yarn의 `catalog:` 프로토콜은 기존 카탈로그 항목만 *참조*합니다 — 생성할 수 없습니다 — 따라서 먼저 버전을 기록하세요.

    <Steps>
    1. `.yarnrc.yml`의 `catalog` 아래에 버전을 추가하세요:

       ```yaml title=".yarnrc.yml"
       catalog:
         some-npm-package: ^1.0.0
       ```

    2. 프로젝트에서 참조하세요:

       ```bash
       yarn workspace @my-scope/my-library add some-npm-package@catalog:
       ```
    </Steps>
  </TabItem>
  <TabItem label="bun">
    bun의 `catalog:` 프로토콜은 기존 카탈로그 항목만 *참조*합니다 — 생성할 수 없습니다 — 따라서 먼저 버전을 기록하세요.

    <Steps>
    1. 루트 `package.json`의 `catalog` 아래에 버전을 추가하세요:

       ```json title="package.json"
       {
         "catalog": {
           "some-npm-package": "^1.0.0"
         }
       }
       ```

    2. 프로젝트에서 참조하세요:

       ```bash
       bun add some-npm-package@catalog: --cwd packages/my-library
       ```
    </Steps>
  </TabItem>
</Tabs>

:::tip[npm에서 버전 정렬]
npm에는 카탈로그 기능이 없으므로 버전이 각 `package.json`에 직접 선언됩니다. 프로젝트 간에 일관성을 유지하려면 [syncpack](https://github.com/JamieMason/syncpack) (`npx syncpack lint`)을 권장합니다.
:::

##### 카탈로그 옵트아웃

카탈로그는 기본적으로 활성화되어 있습니다. 비활성화하려면 `--catalog false`로 워크스페이스를 생성하세요:

<CreateNxWorkspaceCommand workspace="my-project" extraArgs="--catalog false" />

또는 언제든지 `aws-nx-plugin.config.mts`에서 설정하세요:

```ts title="aws-nx-plugin.config.mts"
export default {
  packageManager: {
    catalogs: false,
  },
} satisfies AwsNxPluginConfig;
```

카탈로그가 비활성화되면 생성기는 의존성 버전을 각 프로젝트의 `package.json`에 직접 작성하며, 프로젝트 간 버전 정렬을 유지하는 것은 사용자의 책임입니다.

#### 루트에 모든 의존성 선언

모든 의존성을 루트 `package.json`에만 선언하는 것을 선호하는 경우 (프로젝트별 의존성 선언 없음), 워크스페이스 `biome.json`에서 린트 규칙을 비활성화하세요:

```json title="biome.json"
{
  "linter": {
    "rules": {
      "correctness": {
        "noUndeclaredDependencies": "off"
      }
    }
  }
}
```

프로젝트는 빌드 시 루트에 설치된 패키지를 해결하므로 모든 것이 여전히 빌드됩니다 — 각 프로젝트의 의존성에 대한 정확한 기록으로서 프로젝트별 매니페스트를 포기하게 됩니다 (나중에 프로젝트를 게시하거나 저장소를 분할하는 경우 중요함).

#### 런타임 코드

TypeScript 프로젝트를 런타임 코드로 사용하는 경우 (예: AWS Lambda 함수의 핸들러로), 프로젝트를 번들링하기 위해 [Rolldown](https://rolldown.rs/)과 같은 도구를 사용하는 것이 좋습니다. 이는 [트리 쉐이킹](https://rolldown.rs/in-depth/why-bundlers)을 통해 프로젝트가 실제로 참조하는 의존성만 포함되도록 보장할 수 있기 때문입니다.

`project.json` 파일에 다음과 같은 타겟을 추가하여 이를 달성할 수 있습니다:

```json
{
  ...
  "targets": {
    ...
    "bundle": {
      "cache": true,
      "inputs": ["default"],
      "executor": "nx:run-commands",
      "outputs": ["{workspaceRoot}/dist/packages/my-library/bundle"],
      "options": {
        "command": "rolldown -c rolldown.config.ts",
        "cwd": "{projectRoot}"
      },
      "dependsOn": ["compile"]
    },
  },
}
```

`cwd`는 `rolldown`이 구성을 찾을 수 있게 해줍니다: 이것이 없으면 명령이 워크스페이스 루트에서 실행되는데, 거기에는 `rolldown.config.ts`가 존재하지 않습니다.

그리고 다음과 같이 `rolldown.config.ts` 파일을 추가하세요:

```ts
// rolldown.config.ts
import { defineConfig } from 'rolldown';

export default defineConfig([
  {
    tsconfig: 'tsconfig.lib.json',
    input: 'src/index.ts',
    output: {
      file: '../../dist/packages/my-library/bundle/index.js',
      format: 'cjs',
      codeSplitting: false,
    },
    platform: 'node',
  },
]);
```

:::note[번들 구성]
위 타겟에서 번들의 진입점으로 `src/index.ts`를 선택했으며, 이는 이 파일에서 내보낸 코드가 모든 의존성과 함께 번들에 포함된다는 것을 의미합니다.
:::

:::tip[Lambda 함수]
AWS Lambda 함수를 빌드하는 경우 <Link path="/ko/guides/ts-lambda-function">`ts#lambda-function`</Link> 생성기를 확인하세요. 이는 번들링을 구성할 뿐만 아니라 인프라를 생성하고 관찰 가능성 및 타입 안전성을 추가합니다.
:::

### 빌드

TypeScript 프로젝트는 `build` 타겟으로 구성되어 있으며 (`project.json`에 정의됨), 다음을 통해 실행할 수 있습니다:

<NxCommands commands={['build <project-name>']} />

여기서 `<project-name>`은 프로젝트의 정규화된 이름입니다.

`build` 타겟은 프로젝트를 컴파일, 린트 및 테스트합니다.

빌드 출력은 워크스페이스의 루트 `dist` 폴더에서 찾을 수 있으며, 패키지 및 타겟에 대한 디렉토리 내부에 있습니다. 예: `dist/packages/<my-library>/tsc`

워크스페이스의 모든 프로젝트를 빌드하려면 다음을 실행하세요:

<NxCommands commands={['run-many --target build']} />

또는 단축 명령을 사용하세요:

<PackageManagerShortCommand commands={["build"]} />

### Assembling

프로젝트에는 배포에 기여하는 모든 것(예: 컴파일되거나 번들링된 출력)을 생성하는 `assemble` 타겟도 있으며, 린트, 테스트 또는 타입 체크 게이트를 실행하지 않습니다.

<NxCommands commands={['assemble <project-name>']} />

<Link path="guides/typescript-infrastructure#deploying-to-aws">배포 타겟</Link>은 `assemble`에 의존하므로 배포 시 배포하려는 것만 빌드합니다.

:::caution[파이프라인에서 `build` 사용]
`assemble`은 개발 중 더 빠른 반복을 위해 사용됩니다. 프로덕션 배포 전에 프로젝트가 품질 게이트를 통과하는지 확인하려면 CI 파이프라인에서 `build`를 실행하세요.
:::

## 테스트

[Vitest](https://vitest.dev/)가 프로젝트 테스트를 위해 구성되어 있습니다.

### 테스트 작성

테스트는 프로젝트의 `src` 폴더에 함께 위치한 `.spec.ts` 또는 `.test.ts` 파일에 작성해야 합니다.

예를 들어:

<FileTree>
  - src
    - hello.ts 라이브러리 소스 코드
    - hello.spec.ts hello.ts에 대한 테스트
</FileTree>

Vitest는 `describe`, `it`, `test` 및 `expect`와 같은 유틸리티와 함께 Jest와 유사한 구문을 제공합니다.

```ts title="hello.spec.ts"
import { sayHello } from './hello.js';

describe('sayHello', () => {
  it('should greet the caller', () => {
    expect(sayHello('Darth Vader')).toBe('Hello, Darth Vader!');
  });
});
```

테스트 작성 방법 및 의존성 모킹과 같은 기능에 대한 자세한 내용은 [Vitest 문서](https://vitest.dev/guide/#writing-tests)를 참조하세요.

### 테스트 실행

테스트는 프로젝트의 `build` 타겟의 일부로 실행되지만 `test` 타겟을 실행하여 별도로 실행할 수도 있습니다:

<NxCommands commands={['test <project-name>']} />

Vitest의 `-t` 플래그를 사용하여 개별 테스트 또는 테스트 스위트를 실행할 수 있습니다. Nx가 자체 `--target` 옵션으로 사용하지 않고 Vitest로 전달하도록 `--` 구분 기호 뒤에 전달하세요:

<NxCommands commands={["test <project-name> -- -t 'sayHello'"]} />

:::tip[VSCode 통합]
VSCode 사용자인 경우 [Vitest Runner for VSCode that actually works](https://marketplace.visualstudio.com/items?itemName=rluvaton.vscode-vitest) 확장 프로그램을 설치하는 것이 좋습니다. 이를 통해 IDE에서 테스트를 실행, 감시 또는 디버그할 수 있습니다.
:::

### 테스트 커버리지

커버리지를 수집하려면 `--` 구분 기호 뒤에 Vitest의 `--coverage` 플래그를 전달하세요:

<NxCommands commands={['test <project-name> -- --coverage']} />

보고서는 `dist/<project-root>/test-output/vitest/coverage`에 작성되며, HTML 보고서는 `index.html`에 있습니다.

## 린팅

TypeScript 프로젝트는 린팅 및 포매팅을 위해 [Biome](https://biomejs.dev/)를 사용합니다. Biome는 워크스페이스 루트 `biome.json` 파일에 구성되어 있으며 — 이에 대한 변경 사항은 워크스페이스의 모든 TypeScript 프로젝트에 적용되고 일관성을 보장합니다.

### 린터 실행

프로젝트를 확인하기 위해 린터를 호출하려면 `lint` 타겟을 실행할 수 있습니다.

<NxCommands commands={["lint <project-name>"]} />

### 린트 문제 수정

대부분의 린팅 또는 포매팅 문제는 `--configuration=fix` 인수를 사용하여 실행하면 자동으로 수정할 수 있습니다.

<NxCommands commands={["lint <project-name> --configuration=fix"]} />

마찬가지로 워크스페이스의 모든 패키지에서 모든 린트 문제를 수정하려면 다음을 실행할 수 있습니다:

<NxCommands commands={["run-many --target lint --all --configuration=fix"]} />

:::tip[단축 명령]
워크스페이스 루트에서 단축 명령이 있습니다:

<PackageManagerShortCommand commands={["lint"]} />
:::

### 린트 문제 건너뛰기

개발 중에 린팅 문제로 인해 속도가 느려지는 것을 방지하려면 (특히 프로젝트에 자동 수정할 수 없는 문제가 있는 경우) `skip-lint` 구성으로 빌드를 실행할 수 있습니다:

<NxCommands commands={["run-many --target build --configuration=skip-lint"]} />

이렇게 하면 빌드 중에 린트 타겟을 완전히 건너뜁니다.

:::tip[단축 명령]
워크스페이스 루트에서 단축 명령이 있습니다:

<PackageManagerShortCommand commands={["build:skip-lint"]} />
:::
