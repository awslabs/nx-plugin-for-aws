이 생성기는 기존 TypeScript 프로젝트에 컨테이너화된 HTTP 서비스를 추가합니다. `GET /health` 라우트와 샘플 `GET /hello` 라우트가 있는 작은 HTTP 서버, Dockerfile, 그리고 서버를 로컬에서 실행하고 이미지를 빌드하고 스캔하는 타겟을 얻게 됩니다. 또한 [Amazon Elastic Container Service (Amazon ECS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html)에서 이미지를 실행하는 CDK 또는 Terraform 코드를 얻게 됩니다. Amazon ECS는 컨테이너를 실행하고 확장하는 AWS 서비스입니다.

## 작동 방식

서비스는 [AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html)에서 실행되며, 관리할 서버 없이 각 컨테이너를 실행합니다. 컨테이너의 각 실행 복사본은 ECS 작업입니다. 작업은 자체 VPC(가상 프라이빗 클라우드, AWS 계정의 격리된 네트워크) 내에서 실행됩니다. 보안 그룹(작업에 연결된 방화벽 규칙 세트)은 어떤 네트워크 트래픽이 작업에 도달하고 떠날 수 있는지 제어합니다.

서비스는 비공개입니다. 로드 밸런서, API, 퍼블릭 IP 주소가 없습니다. 보안 그룹에는 인바운드 규칙이 없으므로 호출자를 허용할 때까지 아무것도 서비스에 연결을 열 수 없습니다. 서비스는 여전히 아웃바운드 호출을 할 수 있습니다. 예를 들어 데이터베이스나 다른 AWS 서비스로의 호출입니다.

## 생성기 출력

생성기는 프로젝트에 다음 파일을 추가합니다. 소스 폴더는 `name` 옵션의 이름을 따르거나, 생략하면 `service`로 명명됩니다:

<FileTree>
  - your-project/
    - src/
      - service/ (또는 선택한 이름)
        - server.ts HTTP 라우트: `GET /health` 및 샘플 라우트 `GET /hello`
        - index.ts `PORT`를 읽고 서버를 시작하는 진입점. 번들과 `<name>-serve` 타겟이 이 파일에서 시작됩니다
        - Dockerfile 컨테이너 이미지 정의
        - .dockerignore 이미지 빌드 컨텍스트에서 제외되는 파일
    - rolldown.config.ts `index.ts`에 대한 번들 엔트리로 업데이트됨
    - project.json `bundle` 타겟과 서비스를 위한 `<name>-serve`, `<name>-docker`, `<name>-trivy` 타겟으로 업데이트됨
</FileTree>

타겟 이름은 `name` 옵션으로 시작하거나, 생략하면 `service`로 시작합니다. 예를 들어, 이름 없이는 타겟이 `service-serve`, `service-docker`, `service-trivy`이고, `--name=orders`의 경우 `orders-serve`, `orders-docker`, `orders-trivy`입니다. `bundle` 타겟은 프로젝트의 모든 번들된 진입점에서 공유됩니다.

## 로컬에서 서비스 실행하기

`<name>-serve` 타겟은 컨테이너 없이 머신에서 서버를 실행합니다:

<NxCommands commands={['run your-project:service-serve']} />

서버는 `PORT` 환경 변수의 포트에서 수신합니다. `<name>-serve` 타겟은 생성기가 할당한 포트로 설정하며, 8081부터 시작하여 워크스페이스의 다른 프로젝트가 이미 사용 중인 포트는 건너뜁니다. 컨테이너 내부에서 서버는 포트 8080에서 수신합니다.

서버는 `HOST` 환경 변수의 주소에서 수신하며, 기본값은 `127.0.0.1`이므로 `<name>-serve` 타겟은 자신의 머신에서만 연결을 수락합니다. 이미지는 `HOST=0.0.0.0`을 설정하므로 작업 내부에서 서버는 작업 자체의 네트워크 인터페이스에서 수신합니다. 작업의 보안 그룹은 여전히 누가 연결할 수 있는지 결정합니다.

상태 200과 `{"status":"ok"}`를 반환하는 헬스 라우트로 서버가 실행 중인지 확인하세요:

```bash
curl http://localhost:<port>/health
```

서버에는 자체 라우트로 교체할 샘플 라우트도 있습니다. `GET /hello?name=<x>`는 `{"message":"Hello, <x>!"}`를 반환하며, `name`의 기본값은 `world`입니다. 다른 경로는 상태 404를 반환합니다.

## 이미지 빌드 및 스캔

`<name>-docker` 타겟은 서비스의 linux/arm64 이미지를 빌드합니다. 먼저 `bundle` 타겟을 실행하므로 이미지에는 번들된 서버가 포함됩니다. 그런 다음 `Dockerfile`과 `.dockerignore`를 번들 출력 폴더 `dist/<project root>/bundle/container/<name>`에 복사하고, 해당 폴더를 빌드 컨텍스트(이미지 빌드가 읽을 수 있는 파일)로 사용하여 이미지를 빌드합니다. 워크스페이스에 설정된 컨테이너 엔진인 `docker` 또는 [Finch](https://runfinch.com/)를 사용합니다. 이 타겟은 프로젝트의 모든 이미지를 빌드하는 집계 `docker` 타겟의 일부로 실행됩니다.

<NxCommands commands={['run your-project:service-docker']} />

ECS에서는 헬스 체크 명령이 컨테이너 내부에서 실행되어 컨테이너 포트에서 `GET /health`를 호출합니다. 인바운드 액세스가 필요하지 않습니다. ECS는 헬스 체크가 계속 실패하는 작업을 교체합니다. ECS는 Dockerfile의 `HEALTHCHECK` 명령을 무시합니다. 이미지가 빌드되고 게시되는 방법에 대한 자세한 내용은 <Link path="/guides/docker-bundling">Docker Bundling</Link>을 참조하세요.

## 서비스 배포하기

### 인프라에 서비스 추가하기

구성과 모듈은 VPC를 생성하지 않습니다. 스택이나 루트 모듈에서 VPC를 생성하거나 가져와서 전달합니다. 작업은 송신이 가능한 프라이빗 서브넷에서 실행되며, NAT 게이트웨이(프라이빗 서브넷이 아웃바운드 연결을 할 수 있게 하는 관리형 게이트웨이) 또는 VPC 엔드포인트(VPC에서 AWS 서비스로의 프라이빗 연결)를 통해 AWS 서비스에 도달합니다.

<Infrastructure>
<Fragment slot="cdk">
CDK 구성은 `common/constructs`에 생성되며 서비스 이름을 따릅니다. 새 VPC를 사용한 예제:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyService } from '@my-scope/common-constructs';
import { Stack, StackProps } from 'aws-cdk-lib';
import { SubnetType, Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ApplicationStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    new MyService(this, 'MyService', {
      vpc,
      vpcSubnets: { subnetType: SubnetType.PRIVATE_WITH_EGRESS },
    });
  }
}
```

기존 VPC를 사용하려면 `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })`로 조회하고 `vpc`로 전달하세요.
</Fragment>
<Fragment slot="terraform">
Terraform 모듈은 `common/terraform`에 생성됩니다. 서비스의 이미지는 공유 자산 리포지토리에 게시되므로, 배포당 한 번 `core/asset-ecr` 모듈을 인스턴스화하고 그 출력을 모든 서비스 모듈에 전달합니다. 또한 서비스가 <Link path="/guides/runtime-config">런타임 구성</Link>을 읽는 AWS AppConfig 애플리케이션을 보유한 공유 `runtime_config_appconfig` 모듈의 출력도 전달합니다:

```hcl title="packages/infra/src/main.tf"
module "asset_ecr" {
  source = "../../common/terraform/src/core/asset-ecr"
}

module "my_service" {
  source = "../../common/terraform/src/app/services/my-service"

  vpc_id     = aws_vpc.main.id
  subnet_ids = aws_subnet.private[*].id

  asset_ecr_repository_url = module.asset_ecr.repository_url
  asset_ecr_repository_arn = module.asset_ecr.repository_arn

  appconfig_application_id  = module.runtime_config_appconfig.application_id
  appconfig_application_arn = module.runtime_config_appconfig.application_arn
}
```
</Fragment>
</Infrastructure>

### NAT Gateway 없이 실행하기

작업이 시작되면 ECS는 이미지를 가져오고 대신 로그를 전송합니다. 서버 코드도 AWS 서비스를 호출할 수 있습니다. NAT 게이트웨이가 없는 프라이빗 서브넷에서는 이러한 각 호출에 VPC 엔드포인트가 필요합니다. 올바른 엔드포인트가 없으면 작업이 시작에 실패하거나 AWS를 호출할 때 타임아웃됩니다.

VPC에 다음 엔드포인트를 생성하고, `<region>`을 AWS 리전으로 교체하세요:

| 엔드포인트 | 유형 | 사용처 |
| --- | --- | --- |
| `com.amazonaws.<region>.ecr.api` | Interface | ECS, Amazon ECR로 인증하고 이미지 조회 |
| `com.amazonaws.<region>.ecr.dkr` | Interface | ECS, Amazon ECR에서 이미지 가져오기 |
| `com.amazonaws.<region>.s3` | Gateway | ECS, Amazon ECR이 Amazon S3에 저장하는 이미지 레이어 다운로드 |
| `com.amazonaws.<region>.logs` | Interface | 컨테이너의 로그 출력, Amazon CloudWatch Logs로 전송 |
| `com.amazonaws.<region>.secretsmanager` | Interface | ECS, 작업 시작 시 컨테이너에 전달하는 시크릿 읽기 |
| `com.amazonaws.<region>.appconfigdata` | Interface | 코드, AWS AppConfig에서 <Link path="/guides/runtime-config">런타임 구성</Link> 읽기 |
| `com.amazonaws.<region>.sts` | Interface | 코드, AWS STS에서 임시 자격 증명 요청 시(예: 다른 역할 가정) |

인터페이스 엔드포인트는 작업에서 HTTPS(포트 443)를 허용하는 보안 그룹이 필요합니다. Amazon ECR 엔드포인트에 대한 자세한 내용은 [Amazon ECR interface VPC endpoints](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html)를 참조하세요.

### 보안 기본값

생성된 인프라는 기본적으로 다음 설정을 적용합니다:

- 서비스의 보안 그룹에는 인바운드 규칙이 없습니다. 규칙을 추가할 때까지 VPC 내부 또는 외부의 어떤 호출자도 작업에 연결할 수 없습니다.
- 작업은 프라이빗 서브넷에서 실행되며 퍼블릭 IP 주소를 받지 않습니다.
- 생성기는 서비스 앞에 로드 밸런서와 API를 생성하지 않습니다.
- 작업은 포트 443에서만 아웃바운드 트래픽을 보낼 수 있습니다. 데이터베이스 연결은 데이터베이스 포트를 추가합니다.
- 작업 역할(서버 코드가 실행되는 역할)은 사용자나 연결이 더 많은 권한을 부여할 때까지 AWS AppConfig에서 런타임 구성만 읽을 수 있습니다.
- 실행 역할(ECS가 작업을 시작하는 데 사용하는 역할)은 서비스의 이미지를 가져오고, 로그 그룹에 쓰고, 나열한 시크릿만 읽을 수 있습니다.
- 시크릿은 AWS Secrets Manager 또는 AWS Systems Manager Parameter Store에 대한 참조로만 컨테이너에 도달하며, 일반 환경 값으로는 절대 전달되지 않습니다.
- 컨테이너는 쓰기 가능한 `/tmp` 폴더가 있는 읽기 전용 루트 파일 시스템을 가지며 uid 1000, 비루트 사용자로 실행됩니다. ECS Exec(실행 중인 작업에 대한 셸 액세스)는 꺼져 있습니다.
- 헬스 체크에 실패한 배포는 중지되고 이전 버전으로 롤백됩니다.
- 로그 그룹은 AWS KMS 키로 암호화되며, 로그는 1년 동안 보관됩니다.

### 호출자가 서비스에 도달하도록 허용하기

생성된 대로는 아무것도 서비스를 호출할 수 없습니다. VPC의 다른 워크로드가 서비스를 호출해야 하는 경우, 예를 들어 Lambda 함수나 다른 ECS 서비스의 경우, 서비스의 보안 그룹에 인바운드 규칙을 직접 추가합니다. 생성기는 인바운드 규칙을 추가하지 않습니다. 보안 그룹으로 명명된 호출자 하나를 컨테이너 포트에서 허용하고, 주소 범위는 절대 허용하지 마세요.

<Infrastructure>
<Fragment slot="cdk">
구성은 `IConnectable`을 구현하므로 `connections`를 통해 호출자의 보안 그룹을 허용합니다:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { Port } from 'aws-cdk-lib/aws-ec2';

const svc = new MyService(this, 'MyService', { vpc });
svc.connections.allowFrom(callerSecurityGroup, Port.tcp(8080));
```

호출자의 보안 그룹이 CDK 앱에서 정의되고 아웃바운드 트래픽을 제한하는 경우, `allowFrom`은 일치하는 아웃바운드 규칙도 추가합니다.
</Fragment>
<Fragment slot="terraform">
서비스 모듈이 `security_group_id`로 출력하는 서비스의 보안 그룹에 호출자의 보안 그룹을 소스로 하는 인바운드 규칙을 추가합니다:

```hcl title="packages/infra/src/main.tf"
resource "aws_vpc_security_group_ingress_rule" "caller_to_my_service" {
  security_group_id            = module.my_service.security_group_id
  referenced_security_group_id = aws_security_group.caller.id
  from_port                    = 8080
  to_port                      = 8080
  ip_protocol                  = "tcp"
}
```

호출자의 보안 그룹이 아웃바운드 트래픽을 제한하는 경우, 호출자의 그룹에서 서비스의 보안 그룹으로의 `aws_vpc_security_group_egress_rule`도 추가하세요.
</Fragment>
</Infrastructure>

호출자는 작업의 프라이빗 IP 주소에 연결합니다. 생성기는 서비스 디스커버리를 설정하지 않으며, ECS가 작업을 교체하면 작업의 주소가 변경됩니다. 호출자에게 안정적인 이름을 제공하려면 서비스 디스커버리를 직접 설정하세요. 예를 들어 [Amazon ECS Service Connect](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect.html)를 사용합니다.

### 고급 구성

생성된 서비스는 이름과 이미지를 설정합니다. 아래 예제는 생성된 서비스가 전달하지 않는 설정을 위해 범용 `EcsService` 구성과 `ecs-service` 모듈을 직접 사용합니다.

CDK에서 `common-constructs` 패키지는 서비스 구성 옆에 `EcsService`를 내보내므로 동일한 방식으로 가져옵니다: `import { EcsService } from '@my-scope/common-constructs'`. 생성된 구성은 `EcsService`를 확장하고 다른 모든 prop을 전달합니다. 예를 들어 `cluster`, `environment`, `secrets`, `grantTaskRole`입니다. 선택적 `image` prop은 프로젝트에서 빌드된 이미지를 대체합니다.

Terraform에서 서비스 모듈은 `ecs-service` 모듈의 일부 변수만 설정할 수 있습니다: `vpc_id`, `subnet_ids`, `cluster_arn`, `environment`, `secrets`, `task_role_policy_statements`, `tags`입니다. 다른 변수를 설정하려면 서비스 모듈의 `module "ecs_service"` 블록을 편집하세요.

#### 사전 빌드된 이미지

이미 빌드된 이미지를 실행하려면, 예를 들어 퍼블릭 레지스트리에서, URI를 전달합니다. 로컬에서는 아무것도 빌드되지 않습니다. 프라이빗 Amazon ECR 리포지토리의 이미지의 경우, CDK는 해당 리포지토리에 대한 실행 역할 풀 액세스를 부여합니다. Terraform은 `image_repository_arn`도 전달할 때만 풀 액세스를 부여합니다.

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'Prebuilt', {
  serviceName: 'Prebuilt',
  vpc,
  image: { imageUri: 'public.ecr.aws/my-org/my-image@sha256:<digest>' },
});
```

</Fragment>
<Fragment slot="terraform">

```hcl
module "prebuilt" {
  source = "../../common/terraform/src/core/container/ecs-service"

  service_name = "Prebuilt"
  vpc_id       = aws_vpc.main.id
  subnet_ids   = aws_subnet.private[*].id
  image_uri    = "public.ecr.aws/my-org/my-image@sha256:<digest>"
  # For an image in a private Amazon ECR repository, also pass:
  # image_repository_arn = aws_ecr_repository.my_image.arn
}
```

</Fragment>
</Infrastructure>

#### 하나의 스택에 여러 서비스

각 서비스는 전달하지 않는 한 자체 ECS 클러스터를 생성합니다. 여러 서비스를 하나의 클러스터에서 실행하려면 각각에 동일한 클러스터를 전달하세요.

<Infrastructure>
<Fragment slot="cdk">

```ts
const cluster = new Cluster(this, 'Cluster', { vpc });

new MyService(this, 'MyService', { vpc, cluster });
new MyOtherService(this, 'MyOtherService', { vpc, cluster });
```

</Fragment>
<Fragment slot="terraform">
각 `ecs-service` 모듈에 동일한 `cluster_arn`을 전달합니다. 첫 번째 서비스의 `cluster_arn` 출력이 하나를 제공합니다:

```hcl
cluster_arn = module.my_service.cluster_arn
```

</Fragment>
</Infrastructure>

#### 환경 변수 및 시크릿

일반 설정은 `environment`에 넣습니다. 작업 정의를 읽을 수 있는 사람은 누구나 읽을 수 있으므로 시크릿 값은 절대 넣지 마세요. 대신 시크릿을 참조로 전달합니다. 실행 역할은 나열한 시크릿만 읽을 수 있습니다.

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'MyService', {
  // ...
  environment: { LOG_LEVEL: 'info' },
  secrets: { API_KEY: Secret.fromSecretsManager(apiKeySecret) },
});
```

</Fragment>
<Fragment slot="terraform">

```hcl
environment = { LOG_LEVEL = "info" }
secrets     = { API_KEY = aws_secretsmanager_secret.api_key.arn }
```

</Fragment>
</Infrastructure>

#### 크기 조정 및 스케일링

각 작업은 기본적으로 256 CPU 단위(vCPU의 1/4)와 512MiB의 메모리를 받습니다. 서비스는 하나의 작업을 시작하고, 오토스케일링은 평균 CPU 사용량이 70%를 초과하면 작업을 추가하여 1개에서 2개 사이의 작업을 유지합니다.

| 설정 | CDK prop | Terraform 변수 | 기본값 |
| --- | --- | --- | --- |
| 작업당 CPU 단위 | `cpu` | `cpu` | 256 |
| 작업당 메모리 (MiB) | `memoryLimitMiB` | `memory` | 512 |
| 시작 시 작업 수 | `desiredCount` | `desired_count` | 1 |
| 최소 작업 수 | `minCapacity` | `min_capacity` | 1 |
| 최대 작업 수 | `maxCapacity` | `max_capacity` | 2 |
| 목표 평균 CPU (%) | `targetCpuUtilizationPercent` | `target_cpu_utilization` | 70 |

#### 작업 역할 권한

서비스 구성이나 모듈의 작업 역할은 런타임 구성에 대한 읽기 액세스만으로 시작합니다. 코드에 필요한 권한을 추가하세요:

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'MyService', {
  // ...
  grantTaskRole: (taskRole) => myTable.grantReadData(taskRole),
});
```

</Fragment>
<Fragment slot="terraform">

```hcl
task_role_policy_statements = [{
  Effect   = "Allow"
  Action   = ["dynamodb:GetItem", "dynamodb:Query"]
  Resource = [aws_dynamodb_table.my_table.arn]
}]
```

</Fragment>
</Infrastructure>

#### 컨테이너 사용자

작업 정의는 컨테이너를 uid 1000, 비루트 사용자로 실행합니다. 이는 제공된 Dockerfile이 설정하는 `node` 사용자와 일치합니다. 다른 사용자로 실행하려면 CDK `user` prop 또는 Terraform `container_user` 변수를 설정하세요. Terraform은 `0`과 `root`를 거부합니다.

| 설정 | CDK prop | Terraform 변수 | 기본값 |
| --- | --- | --- | --- |
| 컨테이너가 실행되는 사용자 | `user` | `container_user` | `'1000'` (CDK), `"1000:1000"` (Terraform) |

Terraform에서 `container_user`는 `ecs-service` 모듈의 변수입니다. 서비스 모듈은 이를 전달하지 않으므로 `module "ecs_service"` 블록에서 설정하세요.

### 비용

컨테이너 서비스는 Lambda 함수와 달리 유휴 상태일 때도 요금이 청구됩니다. 다음 부분은 서비스를 호출하는지 여부와 관계없이 시간당 요금이 청구됩니다:

- Fargate 작업, vCPU당 및 GB 메모리당. `desiredCount`와 `minCapacity`는 최소 하나의 작업을 실행 상태로 유지합니다.
- 인터페이스 VPC 엔드포인트, 각 가용 영역에서 시간당, 또는 NAT 게이트웨이, 시간당 및 처리하는 데이터 GB당.
- CloudWatch Logs의 로그 스토리지 및 Amazon ECR의 이미지 스토리지.

리전 및 트래픽에 대한 비용을 추정하려면 [AWS Pricing Calculator](https://calculator.aws/)를 사용하세요.

### 서비스 삭제하기

서비스를 제거하려면 서비스를 보유한 스택 또는 Terraform 구성을 삭제합니다:

<Infrastructure>
<Fragment slot="cdk">
`cdk destroy`를 실행하는 인프라 프로젝트의 `destroy` 타겟을 실행합니다:

<NxCommands commands={['run infra:destroy']} />
</Fragment>
<Fragment slot="terraform">
인프라 프로젝트의 `destroy` 타겟을 실행합니다:

<NxCommands commands={['run infra:destroy']} />
</Fragment>
</Infrastructure>

그런 다음 AWS 콘솔 또는 AWS CLI로 ECS 서비스와 클러스터가 삭제되었는지 확인합니다. Terraform의 경우 destroy는 서비스의 로그 그룹도 삭제하고 7일 후 삭제를 위해 AWS KMS 키를 예약합니다. CDK의 경우 destroy는 서비스의 로그 그룹과 AWS KMS 키를 유지합니다. CDK는 제거 정책이 달리 명시하지 않는 한 로그 그룹과 키를 유지하기 때문입니다. 더 이상 로그가 필요하지 않으면 직접 삭제하세요. 이미지는 Amazon ECR의 CDK 자산 리포지토리 또는 공유 `asset-ecr` 리포지토리에 남아 있습니다. 더 이상 필요하지 않으면 삭제하세요. VPC는 사용자의 것이므로 서비스를 삭제해도 그대로 유지됩니다.
