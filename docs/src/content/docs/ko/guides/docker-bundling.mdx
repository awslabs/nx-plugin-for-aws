:::tip[Docker 또는 Finch]
이미지를 빌드하는 데 사용되는 컨테이너 엔진은 워크스페이스 생성 시 `--containers` 플래그(`docker`, `finch` 또는 `infer` — 기본값 — 설치된 것을 자동 감지)를 통해 선택됩니다. [Finch](https://runfinch.com/)는 Docker의 오픈 소스 대체 도구입니다. 선택 사항은 `aws-nx-plugin.config.mts`에 기록되며 컨테이너 빌드 명령을 생성하는 모든 제너레이터에 적용됩니다. CDK 이미지 자산 빌드는 `CDK_DOCKER` 환경 변수를 통해 이 선택을 존중합니다.
:::

## 패턴

```d2
direction: right

src: src/
dockerfile: Dockerfile {
  shape: document
}
bundle: "bundle target\nRolldown / uv"
ctx: "dist/.../bundle/\n(build context)" {
  shape: page
}

src -> bundle -> ctx
dockerfile -> ctx
```

권장 패턴은 세 가지 요소로 구성됩니다:

1. **`bundle` 타겟** - 런타임 아티팩트의 자체 포함 디렉토리를 생성하는 프로젝트의 타겟입니다. TypeScript의 경우 [Rolldown](https://rolldown.rs/)에서 생성한 트리 셰이킹된 단일 파일 JavaScript 번들이고, Python의 경우 [uv](https://docs.astral.sh/uv/)에서 생성한 `requirements.txt` 및 설치된 종속성입니다.
2. **최소한의 `Dockerfile`** - 번들 출력을 베이스 이미지에 단순히 `COPY`합니다. 번들링이 이미 트리 셰이킹과 종속성 설치를 처리했기 때문에 `Dockerfile`은 `npm install` 또는 `uv sync`를 실행할 필요가 없습니다.
3. **`docker` 타겟** - `Dockerfile`을 번들 출력과 함께 복사하여(Docker 빌드 컨텍스트에 런타임에 필요한 파일만 포함되도록) `docker build`를 실행합니다.

Docker 빌드 컨텍스트는 프로젝트의 `dist` 폴더에 작성됩니다. 그런 다음 코드형 인프라(CDK 또는 Terraform)가 해당 디렉토리를 가리켜 이미지를 ECR에 푸시합니다.

:::tip[Dockerfile 외부에서 번들링하는 이유는?]
번들 단계를 Nx에 유지하면(`Dockerfile` 내부가 아닌) 다음과 같은 이점이 있습니다:

- Nx가 번들 타겟을 **캐시**할 수 있습니다 — 출력이 디스크의 디렉토리이므로 캐시 히트 시 실제로 복원됩니다.
- `Dockerfile`은 모노레포, 프라이빗 레지스트리 또는 빌드 시간 시크릿에 액세스할 필요가 없습니다.
- 이미지 레이어가 작습니다 — 이미 빌드된 아티팩트의 단일 `COPY`이며, 전이적인 `node_modules` 또는 빌드 툴체인이 없습니다.
:::

## TypeScript

### Bundle 타겟

Rolldown을 호출하는 `bundle` 타겟을 구성합니다. <Link path="/ko/guides/typescript-project">`ts#project`</Link>에서 시작하는 경우 `project.json`에 다음을 추가합니다:

```json
{
  "targets": {
    "bundle": {
      "cache": true,
      "inputs": ["default"],
      "executor": "nx:run-commands",
      "outputs": ["{workspaceRoot}/dist/{projectRoot}/bundle"],
      "options": {
        "command": "rolldown -c rolldown.config.ts",
        "cwd": "{projectRoot}"
      },
      "dependsOn": ["compile"]
    }
  }
}
```

그리고 프로젝트 루트에 `rolldown.config.ts`를 추가합니다:

```ts
// rolldown.config.ts
import { defineConfig } from 'rolldown';

export default defineConfig([
  {
    tsconfig: 'tsconfig.lib.json',
    input: 'src/index.ts',
    output: {
      file: '../../dist/packages/my-project/bundle/index.js',
      format: 'cjs',
      codeSplitting: false,
    },
    platform: 'node',
  },
]);
```

번들 타겟을 실행하여 `dist/packages/my-project/bundle/index.js`를 생성합니다:

<NxCommands commands={['bundle my-project']} />

:::tip[번들링할 수 없는 종속성]
일부 npm 패키지는 동적 `require`, 네이티브 바인딩 또는 런타임 파일 경로 확인에 의존하기 때문에 번들링할 수 없습니다. `rolldown.config.ts`의 `external` 배열에 추가하여 런타임 `require()` 호출로 남겨두고 대신 `Dockerfile` 내부에 설치합니다(아래 참조):

```ts
{
  // ...
  external: ['@aws/aws-distro-opentelemetry-node-autoinstrumentation'],
}
```
:::

### Dockerfile

프로젝트 소스 디렉토리에 `Dockerfile`을 생성합니다. 이 파일은 번들을 Node 베이스 이미지에 `COPY`하는 것 외에는 아무것도 하지 않으며, 번들링할 수 없는 `external` 패키지를 `npm install`합니다. `RUN npm install` 단계를 `COPY` **이전에** 배치하여 Docker가 설치된 `node_modules` 레이어를 캐시하고 종속성 목록이 실제로 변경될 때만 다시 실행하도록 합니다:

```dockerfile
FROM public.ecr.aws/docker/library/node:lts

WORKDIR /app

# Install packages that cannot be bundled (declared as "external" in rolldown.config.ts).
# Kept above the COPY so this layer is cached and only invalidated when the install list changes.
RUN npm install @aws/aws-distro-opentelemetry-node-autoinstrumentation@0.10.0

# Copy bundled application
COPY index.js /app

EXPOSE 8080

CMD ["node", "index.js"]
```

:::tip[종속성 고정]
`Dockerfile` 내부에 설치된 모든 종속성을 정확한 버전으로 고정하세요(위와 같이) — 그렇지 않으면 다음에 빌드할 때 `npm install`이 자동으로 최신 릴리스를 선택하여 빌드 시점에 따라 다르게 동작하는 이미지가 생성됩니다.
:::

### Docker 타겟

다음을 수행하는 `docker` 타겟을 추가합니다:

1. `Dockerfile`을 번들 출력 디렉토리에 복사하고(빌드 컨텍스트에 번들 + `Dockerfile`만 포함되도록),
2. `docker build`를 실행합니다(CDK의 경우 선택 사항 — 아래 참조).

```json
{
  "targets": {
    "docker": {
      "cache": false,
      "executor": "nx:run-commands",
      "options": {
        "commands": [
          "shx cp packages/my-project/src/Dockerfile dist/packages/my-project/bundle/Dockerfile",
          "docker build --platform linux/arm64 -t my-scope-my-project:latest dist/packages/my-project/bundle"
        ],
        "parallel": false
      },
      "dependsOn": ["bundle"]
    }
  }
}
```

:::caution[이미지 빌드를 캐시하지 마세요]
이미지 빌드 타겟에 `"cache": false`를 설정하세요. 빌드된 이미지는 파일 시스템의 `outputs` 경로에 작성되지 않으므로 Nx는 캐시 히트 시 복원할 것이 없습니다. 컨테이너 엔진은 어쨌든 이미지 레이어를 캐시하므로 성능 저하가 없습니다.
:::

:::tip[크로스 플랫폼 파일 복사]
`shx` 패키지는 크로스 플랫폼 `cp`, `rm` 및 `mkdir` 명령을 제공하여 셸 내장 명령(Windows에서 사용 불가)을 피합니다. 워크스페이스 루트에 `pnpm add -D -w shx`로 설치하세요.

디렉토리를 복사하려면 `-R`과 소스에 후행 `/.`가 필요합니다 — `shx cp -R src/. dst` — 이는 내용을 `dst`에 병합합니다. `/.` 없이는 소스가 `dst` 내부에 중첩되며, `src/*` 글로브와 달리 여전히 dotfile을 포함합니다.
:::

이 타겟을 실행하면 `dist/packages/my-project/bundle/`의 최소 컨텍스트에서 빌드된 `my-scope-my-project:latest` 태그가 지정된 로컬 이미지가 생성됩니다:

<NxCommands commands={['docker my-project']} />

:::note[CDK가 이미지를 직접 빌드함]
CDK로만 배포하는 경우 위의 `docker build` 명령은 선택 사항입니다 — CDK의 `DockerImageAsset`([Infrastructure](#infrastructure) 아래 표시)이 synth 시간에 이미지를 빌드합니다. CDK가 찾을 수 있도록 `Dockerfile`을 빌드 컨텍스트 디렉토리에 복사해야 합니다. 제너레이터는 `docker run`으로 이미지를 빠르게 스모크 테스트할 수 있는 방법을 제공하기 위해 로컬 `docker build` 단계를 유지합니다.

Terraform의 경우 `docker build` 단계가 필요합니다 — 아래의 `null_resource` 패턴은 로컬로 태그가 지정된 이미지를 푸시합니다.
:::

## Python

### Bundle 타겟

`uv`를 사용하여 대상 플랫폼의 종속성을 내보내고 설치하는 `bundle` 타겟을 구성합니다. <Link path="/ko/guides/python-project">`py#project`</Link> 제너레이터와 <Link path="/ko/guides/python-lambda-function">`py#lambda-function`</Link> 제너레이터는 모두 이를 구성합니다. 타겟 구성은 다음과 같습니다:

```json
{
  "targets": {
    "bundle-arm": {
      "cache": true,
      "executor": "nx:run-commands",
      "outputs": ["{workspaceRoot}/dist/{projectRoot}/bundle-arm"],
      "options": {
        "commands": [
          "uv export --frozen --no-dev --no-editable --project {projectRoot} --package my_project -o dist/{projectRoot}/bundle-arm/requirements.txt",
          "uv pip install -n --no-deps --no-installer-metadata --no-compile-bytecode --python-platform aarch64-manylinux_2_28 --target dist/{projectRoot}/bundle-arm -r dist/{projectRoot}/bundle-arm/requirements.txt"
        ],
        "parallel": false
      },
      "dependsOn": ["compile"]
    }
  }
}
```

:::tip[대상 아키텍처]
Docker 이미지가 x86_64에서 실행될 경우 `--python-platform`을 `x86_64-manylinux_2_28`로 변경하세요.
:::

`nx bundle my-project`를 실행하면 프로젝트의 소스, 종속성 및 `requirements.txt`를 포함하는 `dist/packages/my-project/bundle-arm/`이 생성됩니다 — 이미지가 런타임에 필요한 모든 것입니다.

### Dockerfile

`Dockerfile`은 단순히 번들을 Python 베이스 이미지에 복사합니다. `uv`가 이미 모든 종속성을 번들 디렉토리에 설치했기 때문에 이미지 내부에서 `pip install`을 실행할 필요가 없습니다:

```dockerfile
FROM public.ecr.aws/docker/library/python:3.14-slim

WORKDIR /app

# Copy bundled package (source + installed dependencies)
COPY . /app

EXPOSE 8080

ENV PYTHONPATH=/app
ENV PATH="/app/bin:${PATH}"

CMD ["python", "-m", "my_project.main"]
```

### Docker 타겟

`Dockerfile`을 번들 출력 디렉토리에 복사한 다음 `docker build`를 실행하는 `docker` 타겟을 추가합니다:

```json
{
  "targets": {
    "docker": {
      "cache": false,
      "executor": "nx:run-commands",
      "options": {
        "commands": [
          "shx rm -rf dist/packages/my-project/docker",
          "shx mkdir -p dist/packages/my-project/docker",
          "shx cp -R dist/packages/my-project/bundle-arm/. dist/packages/my-project/docker",
          "shx cp packages/my-project/src/Dockerfile dist/packages/my-project/docker/Dockerfile",
          "docker build --platform linux/arm64 -t my-scope-my-project:latest dist/packages/my-project/docker"
        ],
        "parallel": false
      },
      "dependsOn": ["bundle-arm"]
    }
  }
}
```

이것은 출력 디렉토리를 지운 다음 번들 내용과 `Dockerfile`을 모두 `dist/.../docker`에 복사하여 Docker 빌드 컨텍스트가 됩니다.

<NxCommands commands={['docker my-project']} />

## Trivy로 이미지 스캔

알려진 취약점에 대해 이미지를 스캔하는 것이 좋습니다. 이 패턴을 따르는 제너레이터는 [Trivy](https://trivy.dev/)로 빌드된 이미지를 스캔하는 `trivy` 타겟을 추가하며, [ECR 호스팅 Trivy 이미지](https://gallery.ecr.aws/aquasecurity/trivy)에서 실행되고 `HIGH` 또는 `CRITICAL` 발견 시 0이 아닌 값으로 종료합니다.

`docker` 타겟에 `dependsOn`하는 `trivy` 타겟을 추가합니다. 빌드된 이미지를 tarball로 저장하고 워크스페이스 상대 바인드 마운트를 통해 스캔하므로 `docker`와 `finch` 모두에서 동일한 명령이 작동합니다:

<Code lang="json" code={trivyTarget} />

각 프로젝트의 이미지별 스캔 타겟은 워크스페이스 전체 `trivy` 타겟 아래에 집계되며, 제공된 `trivy` 루트 스크립트가 실행합니다(`nx run-many --target trivy`).

<PackageManagerShortCommand commands={['trivy']} />

:::tip[CI에서 Trivy 실행]
Trivy의 취약점 데이터베이스가 새로운 CVE로 지속적으로 업데이트되므로 개발 중 반복 작업 시 불필요한 마찰을 초래할 수 있어 스캔은 의도적으로 `build`에 연결되지 않습니다.

대신 프로덕션 단계에 배포하기 전에 CI 파이프라인에서 전용 단계로 위 명령을 실행하는 것을 권장합니다.
:::

:::note[발견 사항 억제]
Trivy는 프로젝트 루트에서 `.trivyignore` 파일(한 줄에 하나씩 취약점 ID 목록)을 읽습니다. `--ignore-unfixed`는 사용 가능한 수정이 없는 취약점을 건너뛰므로 `Dockerfile`의 툴링을 업그레이드하여 조치할 수 있는 문제에 대해서만 스캔이 실패합니다. 자세한 내용은 [Trivy 필터링 문서](https://trivy.dev/latest/docs/configuration/filtering/#by-finding-ids)를 참조하세요.
:::

:::tip[배포판의 보안 업데이트 적용]
베이스 이미지 태그는 배포판의 보안 제품군보다 뒤처지므로 OS 패키지에는 이미 게시된 수정 사항이 있는 취약점이 포함되어 있습니다. 빌드의 첫 번째 단계로 이를 업그레이드하여 다른 명령보다 먼저 수행하면 이후 레이어가 업그레이드된 패키지에 대해 설치됩니다. Debian 기반 베이스 이미지의 경우(위의 Node 및 Python 이미지에서 사용됨):

```dockerfile
RUN apt-get update && \
    apt-get upgrade -y --no-install-recommends && \
    rm -rf /var/lib/apt/lists/*
```

생성된 `Dockerfile`은 이를 자동으로 수행합니다.
:::

## Infrastructure

결과 빌드 컨텍스트 디렉토리를 코드형 인프라에 연결하는 것은 TypeScript와 Python 모두 동일합니다 — 빌드 컨텍스트 디렉토리 경로만 다릅니다(TypeScript의 경우 `dist/packages/my-project/bundle`, Python의 경우 `dist/packages/my-project/docker`).

<Infrastructure>
<Fragment slot="cdk">
빌드 컨텍스트 디렉토리를 가리키는 CDK의 [`DockerImageAsset`](https://docs.aws.amazon.com/cdk/api/v2/docs/aws-cdk-lib.aws_ecr_assets.DockerImageAsset.html)을 사용합니다. CDK는 배포 시 이미지를 빌드하고 CDK 자산 ECR 리포지토리에 게시합니다:

```d2
direction: right

app: Application {
  bundle: "bundle target\nRolldown / uv"
  dockerfile: Dockerfile {
    shape: document
  }
  ctx: "dist/.../bundle/" {
    shape: page
  }
  bundle -> ctx
  dockerfile -> ctx
}

infra: Infrastructure {
  asset: "DockerImageAsset\ndirectory: dist/.../bundle"
}

ecr: "CDK asset ECR" {
  shape: cylinder
}

infra.asset -> app.ctx: references
infra.asset -> ecr: cdk deploy\nbuilds + pushes
```



`findWorkspaceRoot` 헬퍼는 <Link path="/ko/guides/typescript-infrastructure">`ts#infra`</Link> 제너레이터에 의해 생성되고 `@my-scope/common-constructs`에서 내보내집니다. 공유 구성을 사용하지 않는 경우 `cdk`가 호출되는 위치(일반적으로 워크스페이스 루트)에서 `dist` 디렉토리로의 경로를 하드코딩하고 `findWorkspaceRoot` 호출을 완전히 생략할 수 있습니다.

:::note[synth 전에 번들 실행]
CDK는 `bundle`/`docker` 타겟을 자동으로 실행하지 않습니다 — `cdk deploy` 전에 `nx build my-project`를 실행해야 합니다(또는 배포 타겟이 `build`에 의존하도록 연결). 이 패턴을 사용하는 제너레이터는 `docker` 및 `bundle`을 `build`의 종속성으로 선언하여 이것이 투명하게 발생하도록 합니다.
:::

<Fragment slot="terraform">
Terraform의 AWS 프로바이더에는 일급 "Docker 이미지 빌드 및 푸시" 리소스가 없습니다. 제너레이터가 사용하는 패턴은 다음과 같습니다:

1. 프로젝트의 `build` 타겟이 `docker build`를 실행하여 `my-scope-my-project:latest` 태그가 지정된 로컬 이미지를 생성합니다.
2. `core/asset-ecr` 모듈을 사용하는 공유 ECR 리포지토리
3. ECR에 인증하고, 로컬로 빌드된 이미지를 콘텐츠 다이제스트로 다시 태그하고, 푸시하는 `local-exec` 프로비저너가 있는 `null_resource`입니다.
4. 다운스트림 리소스(예: `aws_ecs_task_definition`)는 불변의 다이제스트 기반 태그로 이미지를 참조합니다.

하나의 리포지토리가 모든 이미지를 보관하기 때문에 각 태그는 이미지 소유자와 다이제스트로 네임스페이스가 지정되므로 레지스트리를 공유하는 이미지가 충돌하지 않습니다.

```hcl
module "asset_ecr" {
  source = "../../common/terraform/src/core/asset-ecr"
}

# Invalidate the push whenever the locally-built image digest changes
data "external" "docker_digest" {
  program = ["sh", "-c", "echo '{\"digest\":\"'$(docker inspect my-scope-my-project:latest --format '{{.Id}}')'\"}'"]
}

locals {
  # Content-based, immutable image tag derived from the local image digest, and
  # namespaced by owner so images sharing the registry never collide
  image_tag = "my-project-${replace(data.external.docker_digest.result.digest, "sha256:", "")}"
}

resource "null_resource" "docker_publish" {
  triggers = {
    docker_digest  = data.external.docker_digest.result.digest
    repository_url = module.asset_ecr.repository_url
    image_tag      = local.image_tag
  }

  provisioner "local-exec" {
    command = <<-EOT
      aws ecr get-login-password --region ${data.aws_region.current.id} \
        | docker login --username AWS --password-stdin ${self.triggers.repository_url}
      docker tag my-scope-my-project:latest ${self.triggers.repository_url}:${self.triggers.image_tag}
      docker push ${self.triggers.repository_url}:${self.triggers.image_tag}
    EOT
  }
}
```

`data.external.docker_digest` 블록은 로컬 이미지 해시가 변경될 때마다 `null_resource`가 다시 실행되도록 하여 의미 있는 코드 변경마다 새로운 푸시를 트리거합니다. 이미지는 다이제스트에서 파생된 불변의 콘텐츠 기반 태그로 푸시되므로 공유 리포지토리는 `IMMUTABLE` 태그 변경 가능성을 사용하고 기존 태그를 덮어쓰려는 모든 시도를 거부합니다.

:::note[apply 전에 번들 실행]
`nx apply <project>`는 이미지 태그 `my-scope-my-project:latest`가 이미 로컬에 존재해야 합니다. `nx apply <project>` 전에 `nx build my-project`(또는 `nx docker my-project`)를 실행하세요.
:::
