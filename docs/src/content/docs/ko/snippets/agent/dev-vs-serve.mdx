#### `-dev` vs `-serve`

제너레이터는 동일한 포트에서 동일한 서버를 실행하는 두 개의 타겟을 추가합니다. 이들은 설정하는 환경에서만 차이가 있습니다:

| Target | Environment | Use for |
| --- | --- | --- |
| `<your-agent-name>-dev` | `PORT`, `LOCAL_DEV=true` | Local development |
| `<your-agent-name>-serve` | `PORT` | Exercising the deployed code path locally |

**로컬 개발에는 `<your-agent-name>-dev`를 사용하세요.** `LOCAL_DEV=true`는 에이전트를 로컬 코드 경로로 전환합니다: 세션 상태는 워크스페이스 루트의 `tmp/agents/` 아래 디스크에 기록되며, 연결된 MCP 서버는 AgentCore를 통하지 않고 직접 HTTP를 통해 접근됩니다. 또한 프로젝트 레벨 `dev` 타겟이 집계하는 타겟이며, `<your-agent-name>-chat` 타겟이 실행 중일 것으로 예상하는 타겟입니다.

`<your-agent-name>-serve`는 배포된 에이전트와 동일한 코드 경로를 실행하며, AppConfig의 <Link path="guides/runtime-config">Runtime Configuration</Link>에서 세션 스토리지와 연결된 런타임 ARN을 확인합니다. 이를 위해서는 `RUNTIME_CONFIG_APP_ID`가 배포의 AppConfig 애플리케이션 ID(배포된 스택에서 `RuntimeConfigApplicationId`로 출력됨)로 설정되어야 하며, 이를 읽을 수 있는 AWS 자격 증명이 필요합니다:

```bash
RUNTIME_CONFIG_APP_ID=<app-id> nx run your-project:agent-serve
```

:::caution[`-serve`에는 배포된 구성이 필요합니다]
`RUNTIME_CONFIG_APP_ID` 없이 시작된 `<your-agent-name>-serve`는 요청을 수락하지만 모든 호출이 `RUNTIME_CONFIG_APP_ID is not set — cannot resolve connected agent ARNs from AppConfig.`로 실패합니다.

대신 로컬 코드 경로를 사용하려면 `LOCAL_DEV=true`를 설정하세요 — 이것이 바로 `<your-agent-name>-dev`가 이미 수행하는 작업입니다.
:::
