#### `-dev` vs `-serve`

The generator adds two targets that run the same server on the same port. They differ only in the environment they set:

| Target | Environment | Use for |
| --- | --- | --- |
| `<your-agent-name>-dev` | `PORT`, `LOCAL_DEV=true` | Local development |
| `<your-agent-name>-serve` | `PORT` | Exercising the deployed code path locally |

**Use `<your-agent-name>-dev` for local development.** `LOCAL_DEV=true` switches the agent onto its local code paths: session state is written to disk under `tmp/agents/` at the workspace root, and any connected MCP servers are reached over direct HTTP rather than through AgentCore. It is also the target the project-level `dev` target aggregates, and the one the `<your-agent-name>-chat` target expects to find running.

`<your-agent-name>-serve` runs the same code path as your deployed agent, which resolves session storage and connected runtime ARNs from <Link path="guides/runtime-config">Runtime Configuration</Link> in AppConfig. That requires `RUNTIME_CONFIG_APP_ID` to be set to the AppConfig application id of a deployment (output as `RuntimeConfigApplicationId` by the deployed stack), along with AWS credentials permitted to read it:

```bash
RUNTIME_CONFIG_APP_ID=<app-id> nx run your-project:agent-serve
```

:::caution[`-serve` needs deployed configuration]
Started without `RUNTIME_CONFIG_APP_ID`, `<your-agent-name>-serve` accepts requests but every invocation fails with `RUNTIME_CONFIG_APP_ID is not set — cannot resolve connected agent ARNs from AppConfig.`

Set `LOCAL_DEV=true` to take the local code paths instead — which is what `<your-agent-name>-dev` already does for you.
:::
