This generator adds a containerised HTTP service to an existing TypeScript project. You get a small HTTP server with a `GET /health` route, a Dockerfile, and targets to run the server locally, build its image and scan the image. You also get CDK or Terraform code that runs the image on [Amazon Elastic Container Service (Amazon ECS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html), the AWS service that runs and scales containers.

The service runs on [AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), which runs each container without servers for you to manage. It runs in your own VPC (virtual private cloud, an isolated network in your AWS account), behind an internal [Application Load Balancer](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html) (ALB) that only addresses inside the VPC can reach. By default an [Amazon API Gateway HTTP API](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api.html) receives requests from callers and passes them to the ALB through a VPC link (API Gateway's private connection into a VPC). Callers get an authenticated HTTPS endpoint, and the load balancer never faces the internet.

### Options

The `infra`, `ingress` and `auth` options depend on each other. With `infra` set to `none` the generator vends no infrastructure, and it ignores `ingress` and `auth` with a warning. `ingress` applies only with `infra` set to `ecs`. `auth` applies only with `ingress` set to `http-api`, because a `private` service has no HTTP API to authenticate.

## Running Your Service Locally

The `<name>-serve` target runs the server on your machine, without a container:

<NxCommands commands={['run your-project:service-serve']} />

The server listens on the port in the `PORT` environment variable. The `<name>-serve` target sets it to a port the generator assigns, starting at 8081 and skipping ports other projects in your workspace already use. Inside the container the server listens on port 8080.

Check that the server is up with its health route, which returns status 200 and `{"status":"ok"}`:

```bash
curl http://localhost:<port>/health
```

The server also has a sample route that you replace with your own routes. `GET /hello?name=<x>` returns `{"message":"Hello, <x>!"}`, and `name` defaults to `world`. Any other path returns status 404.

## Building and Scanning the Image

The `<name>-docker` target builds a linux/arm64 image of your service. It runs the `bundle` target first, so the image holds the bundled server. It then copies the `Dockerfile` and `.dockerignore` into the bundle output folder, `dist/<project root>/bundle/container/<name>`, and builds the image with that folder as the build context (the files the image build can read). It uses the container engine your workspace is set up with, `docker` or [Finch](https://runfinch.com/). The target runs as part of the aggregate `docker` target, which builds every image in the project.

<NxCommands commands={['run your-project:service-docker']} />

Only the load balancer's target group (the list of tasks the load balancer sends requests to) checks `GET /health`, to decide whether a task is ready for traffic. ECS ignores a `HEALTHCHECK` instruction in the Dockerfile. For more on how images are built and published, see <Link path="/guides/docker-bundling">Docker Bundling</Link>.

## Deploying Your Service

### Adding the Service to Your Infrastructure

The construct and the module never create a VPC. You create or import one in your stack or root module and pass it in. The tasks and the load balancer run in private subnets with egress, which reach AWS services through a NAT gateway (a managed gateway that lets private subnets make outbound connections) or through VPC endpoints (private connections from your VPC to AWS services).

<Infrastructure>
<Fragment slot="cdk">
The CDK construct is created in `common/constructs` and named after your service. Example usage with a new VPC:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyService } from '@my-scope/common-constructs';
import { Stack, StackProps } from 'aws-cdk-lib';
import { SubnetType, Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ApplicationStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    new MyService(this, 'MyService', {
      vpc,
      vpcSubnets: { subnetType: SubnetType.PRIVATE_WITH_EGRESS },
    });
  }
}
```

To use an existing VPC, look it up with `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` and pass it as `vpc`.
</Fragment>
<Fragment slot="terraform">

The service's image is published to the shared asset repository, so instantiate the `core/asset-ecr` module once per deployment and pass its outputs to every service module.   appconfig_application_arn = module.runtime_config_appconfig.application_arn


### Request Limits

API Gateway stops waiting for your service after 30 seconds and returns an error to the caller. You cannot raise this integration timeout. The largest request payload the HTTP API accepts is 10 MB, and you cannot raise this limit either. Both values come from the [Amazon API Gateway quotas for HTTP APIs](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-quotas.html) page.

So requests that run longer than 30 seconds, and responses that stream data over a long time, do not work through the HTTP API. For those, set `ingress` to `private` and call the internal load balancer from inside the VPC.
</OptionFilter>

<OptionFilter when={{ infra: 'ecs' }} description="Networking, security, calling, advanced configuration, cost and destroy">
### Running Without a NAT Gateway

When your tasks start, ECS pulls the image and sends logs on their behalf. Your server code may also call AWS services. In private subnets with no NAT gateway, each of these calls needs a VPC endpoint. Without the right endpoints, tasks fail to start or time out when they call AWS.

Create these endpoints in the VPC, replacing `<region>` with your AWS Region:

| Endpoint | Type | What uses it |
| --- | --- | --- |
| `com.amazonaws.<region>.ecr.api` | Interface | ECS, to authenticate with Amazon ECR and look up the image |
| `com.amazonaws.<region>.ecr.dkr` | Interface | ECS, to pull the image from Amazon ECR |
| `com.amazonaws.<region>.s3` | Gateway | ECS, to download image layers, which Amazon ECR stores in Amazon S3 |
| `com.amazonaws.<region>.logs` | Interface | The container's log output, sent to Amazon CloudWatch Logs |
| `com.amazonaws.<region>.secretsmanager` | Interface | ECS, to read the secrets you pass to the container when a task starts |
| `com.amazonaws.<region>.appconfigdata` | Interface | Your code, to read <Link path="/guides/runtime-config">runtime configuration</Link> from AWS AppConfig |
| `com.amazonaws.<region>.sts` | Interface | Your code, when it requests temporary credentials from AWS STS (for example to assume another role) |

Interface endpoints need a security group that allows HTTPS (port 443) from the tasks. For details on the Amazon ECR endpoints, see [Amazon ECR interface VPC endpoints](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html).

### Security Defaults

The generated infrastructure applies these settings by default:

- The load balancer is internal. No security group allows inbound traffic from `0.0.0.0/0` or `::/0`.
- Tasks run in private subnets and never get a public IP address.
- The load balancer accepts traffic only from the VPC link (`http-api`) or from the VPC's address range (`private`). The tasks accept traffic only from the load balancer, on the container port.
- Tasks may send outbound traffic only on port 443. Connections to databases add the database port.
- The task role (the role your server code runs as) may only read runtime configuration from AWS AppConfig until you or a connection grant more.
- The execution role (the role ECS uses to start your task) may only pull the service's image, write to its log group and read the secrets you list.
- Secrets reach the container only as references to AWS Secrets Manager or AWS Systems Manager Parameter Store, never as plain environment values.
- The container has a read-only root file system and runs as uid 1000, a non-root user. ECS Exec (shell access into a running task) is off.
- A deployment that fails its health checks stops and rolls back to the previous version.
- The HTTP API writes access logs and throttles requests. It authenticates with IAM unless you choose otherwise.
- Logs are kept for one year.

The generated code suppresses these [Checkov](https://www.checkov.io/) checks (Checkov scans infrastructure code for insecure settings), and states the reason next to each suppression:

- `CKV_AWS_91` asks for load balancer access logs. The HTTP API access logs, or your service's own logs, record the requests instead.
- `CKV_AWS_2` and `CKV_AWS_103` ask for an HTTPS listener with TLS. The load balancer listens on plain HTTP because it is internal and only callers inside the VPC can reach it. With `http-api`, TLS ends at API Gateway.

The Terraform module also skips `CKV2_AWS_20` and `CKV_AWS_378` for the same HTTP listener reason, and `CKV_AWS_150` because load balancer deletion protection is off so that the service can be destroyed.

### Calling Your Service

The service's URL is written to <Link path="/guides/runtime-config">runtime configuration</Link> as `connection.services.<NameClassName>`, where `<NameClassName>` is the service name in PascalCase. For `--name=orders` the key is `Orders`. Without a name, the service name is `<project>-service`, so for a project called `my-project` the key is `MyProjectService`. The source folder and the target prefix are still `service` in that case.

### Advanced Configuration

The generated service sets its name, `ingress` and `auth` for you. The examples below use the generic `EcsService` construct and `ecs-service` module directly, for settings the generated service does not pass or to choose `ingress` and `auth` per instance.

In CDK, your `common-constructs` package exports `EcsService` next to your service's construct, so you import it the same way: `import { EcsService } from '@my-scope/common-constructs'`. The generated construct extends `EcsService` and passes every other prop through, for example `cluster`, `loadBalancer`, `environment`, `secrets` and `grantTaskRole`. Its optional `image` prop replaces the image built from your project. It has no `auth` prop. A Cognito service takes `identity` instead, and other services always use the `auth` they were generated with.

In Terraform, your service's module lets you set only some of the `ecs-service` module's variables: `vpc_id`, `subnet_ids`, `cluster_arn`, `environment`, `secrets`, `task_role_policy_statements` and `tags`, plus `user_pool_id` and `user_pool_client_ids` for a Cognito service. To set any other variable, edit the `module "ecs_service"` block in your service's module.

#### Sizing and Scaling

Each task gets 256 CPU units (a quarter of a vCPU) and 512 MiB of memory by default. The service starts one task, and autoscaling keeps between one and two tasks running, adding tasks when average CPU use goes above 70%.

| Setting | CDK prop | Terraform variable | Default |
| --- | --- | --- | --- |
| CPU units per task | `cpu` | `cpu` | 256 |
| Memory per task (MiB) | `memoryLimitMiB` | `memory` | 512 |
| Tasks at start | `desiredCount` | `desired_count` | 1 |
| Fewest tasks | `minCapacity` | `min_capacity` | 1 |
| Most tasks | `maxCapacity` | `max_capacity` | 2 |
| Target average CPU (%) | `targetCpuUtilizationPercent` | `target_cpu_utilization` | 70 |

#### Container User

The task definition runs the container as uid 1000, a non-root user. This matches the `node` user that the vended Dockerfile sets. To run as another user, set the CDK `user` prop or the Terraform `container_user` variable. Terraform rejects `0` and `root`.

| Setting | CDK prop | Terraform variable | Default |
| --- | --- | --- | --- |
| User the container runs as | `user` | `container_user` | `'1000'` (CDK), `"1000:1000"` (Terraform) |

#### CORS and Throttling

These settings apply only with `ingress` set to `http-api`. CORS (cross-origin resource sharing) decides which websites may call your service from a browser. By default the HTTP API accepts browser requests from any origin, with any method, and with the `authorization`, `content-type`, `x-amz-content-sha256`, `x-amz-date` and `x-amz-security-token` headers. The last three are the headers a SigV4 signature adds. The HTTP API also throttles requests to a steady rate of 10,000 per second, with bursts of up to 5,000.

| Setting | CDK | Terraform variable | Default |
| --- | --- | --- | --- |
| Allowed CORS origins | `restrictCorsTo(...origins)` method, or `corsPreflight` prop | `cors_allow_origins` | any origin (`["*"]`) |
| Other CORS settings | `corsPreflight` prop | none | any method, and the headers above |
| Throttling | `throttle` prop | none | `{ rateLimit: 10000, burstLimit: 5000 }` |

A `corsPreflight` prop replaces the whole default, so list every header your callers send. The `restrictCorsTo` method keeps the other CORS settings and changes only the allowed origins:

```ts
const service = new MyService(this, 'MyService', { vpc });
service.restrictCorsTo('https://app.example.com');
```

In Terraform, `cors_allow_origins` and `container_user` are variables of the `ecs-service` module. Your service's module does not pass them, so set them in its `module "ecs_service"` block. The throttling values are fixed in `ecs-service.tf`.

### Cost

A container service bills while it is idle, unlike a Lambda function. These parts bill by the hour whether or not anyone calls the service:

- Fargate tasks, per vCPU and per GB of memory. `desiredCount` and `minCapacity` keep at least one task running.
- The Application Load Balancer, per hour and per load balancer capacity unit.
- Interface VPC endpoints, per hour in each Availability Zone, or a NAT gateway, per hour and per GB of data it processes.
- Log storage in CloudWatch Logs, and image storage in Amazon ECR.

The HTTP API bills per request. To estimate the cost for your Region and traffic, use the [AWS Pricing Calculator](https://calculator.aws/).
