The `connection` generator lets a <Link path="guides/ts-container">TypeScript container service</Link> use a <Link path="guides/ts-rdb">Relational Database</Link> project. It adds a module that returns the database's Prisma client, and prepares the service's Docker image for SSL connections to Amazon Aurora.

## How this works

A container service with `infra=ecs` runs as tasks on Amazon ECS (Elastic Container Service) in your VPC. Each task runs as the service's task role, an IAM role that has no permissions until you grant them, and sits in the service's security group, which allows outbound traffic on port 443 only. To use the database, the service needs two things that it does not have by default:

- IAM permission for `rds-db:connect`, so it can sign in to the database with IAM authentication.
- A security group rule pair on the database port: an inbound rule on the database's security group, and an outbound rule on the service's security group. Without the outbound rule the service cannot reach the database, because its security group allows only port 443 out.

The generator rejects a service with `infra=none`, because such a service has no task role to grant access to.

## Prerequisites

Before using this generator, ensure you have:

1. A container service with `infra=ecs` (generated using the <Link path="guides/ts-container">`ts#container`</Link> generator)
2. A <Link path="guides/ts-rdb">`ts#rdb`</Link> project

## Using the Database in the Service

Import the getter in your service's code and call it where you handle a request:

```ts title="packages/my-project/src/my-service/orders.ts"
import { getMyDatabase } from './my-database.js';

export const listOrders = async () => {
  const myDatabase = await getMyDatabase();
  return myDatabase.order.findMany();
};
```

The database client reads the database's connection details from <Link path="guides/runtime-config">runtime configuration</Link>, using the `RUNTIME_CONFIG_APP_ID` environment variable.

## Infrastructure

The generator does not change your stack or root Terraform module. Instead it prints the code to add, which is shown below for a service named `my-service` and a database named `my-database`. Until you add it, the service cannot reach the database port and the database refuses its IAM authentication.

<Infrastructure>
<Fragment slot="cdk">

In the example, `myService` is your `MyService` construct and `myDatabase` is your `MyDatabase` construct:

```ts title="packages/infra/src/stacks/application-stack.ts"
myDatabase.allowDefaultPortFrom(myService);
myDatabase.grantConnect(myService.taskRole);
```

`allowDefaultPortFrom` adds the inbound rule on the database's security group and the outbound rule on the service's security group. `grantConnect` grants `rds-db:connect` to the service's task role.

</Fragment>
<Fragment slot="terraform">

In the example, `module "my_service"` deploys the service and `module "my_database"` deploys the database. The `data "aws_region" "current"` and `data "aws_caller_identity" "current"` data sources are declared in the generated `providers.tf`:

```hcl title="packages/infra/src/main.tf"
resource "aws_iam_role_policy" "my_service_my_database_connect" {
  name = "my-service-my-database-connect"
  role = module.my_service.task_role_name

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect   = "Allow"
        Action   = ["rds-db:connect"]
        Resource = ["arn:aws:rds-db:${data.aws_region.current.region}:${data.aws_caller_identity.current.account_id}:dbuser:${module.my_database.connect_resource_id}/${module.my_database.database_runtime_user}"]
      },
    ]
  })
}

resource "aws_vpc_security_group_ingress_rule" "my_service_to_my_database" {
  description                  = "Allow the my-service container service to connect to the database"
  security_group_id            = module.my_database.security_group_id
  referenced_security_group_id = module.my_service.security_group_id
  from_port                    = module.my_database.cluster_port
  to_port                      = module.my_database.cluster_port
  ip_protocol                  = "tcp"
}

resource "aws_vpc_security_group_egress_rule" "my_service_to_my_database" {
  description                  = "Allow the my-service container service to reach the database"
  security_group_id            = module.my_service.security_group_id
  referenced_security_group_id = module.my_database.security_group_id
  from_port                    = module.my_database.cluster_port
  to_port                      = module.my_database.cluster_port
  ip_protocol                  = "tcp"
}
```

### SSL Requirements When Connecting Without RDS Proxy

When the service connects to the Aurora cluster directly, without RDS Proxy, Node.js must trust the Amazon RDS certificate authority. The generator adds this step to the service's Dockerfile, before its `EXPOSE` line:

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends curl ca-certificates && \
    rm -rf /var/lib/apt/lists/* && \
    curl -fsSL "https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem" \
    -o /usr/local/share/ca-certificates/rds-bundle.crt && \
    update-ca-certificates
```

Set the `NODE_EXTRA_CA_CERTS` environment variable of the service to `/usr/local/share/ca-certificates/rds-bundle.crt`, so Node.js reads the bundle. When using RDS Proxy you do not need to set it. For more details, see the [Amazon RDS SSL/TLS documentation](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.SSL.html).
