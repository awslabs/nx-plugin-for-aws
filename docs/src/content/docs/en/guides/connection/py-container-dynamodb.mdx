The `connection` generator lets a <Link path="guides/py-container">Python container service</Link> use a <Link path="guides/py-dynamodb">Python DynamoDB</Link> project. It adds the DynamoDB package as a dependency of the service's project, configures local development so the service and DynamoDB Local start together, and prints the grants the service needs.

## How this works

A container service with `infra=ecs` runs as tasks on Amazon ECS (Elastic Container Service). Each task runs as the service's task role, an IAM role that has no permissions until you grant them. To read and write the table, the task role needs the DynamoDB actions on the table and its indexes, and use of the table's AWS KMS encryption key.

The generator rejects a service with `infra=none`, because such a service has no task role to grant access to.

## Prerequisites

Before using this generator, ensure you have:

1. A container service with `infra=ecs` (generated using the <Link path="guides/py-container">`py#container`</Link> generator)
2. A <Link path="guides/py-dynamodb">`py#dynamodb`</Link> project

## Generator Output

The generator adds the DynamoDB package to the service project's `pyproject.toml` as a workspace dependency, and updates the service's `<service-name>-serve` target in `project.json` to depend on the DynamoDB project's `dev` target.

## Using DynamoDB in the Service

Import entity classes from the DynamoDB package and use them where you handle a request:

```python title="packages/my_project/my_project/my_service/examples.py"
from my_scope_my_table.entities.example import ExampleModel


def list_examples() -> list[dict]:
    return [item.attribute_values for item in ExampleModel.scan()]
```

## Infrastructure

The generator does not change your stack or root Terraform module. Instead it prints the code to add, which is shown below for a service named `my-service` and a table named `my-table`. Until you add it, the service's requests to the table are denied.

<Infrastructure>
<Fragment slot="cdk">

In the example, `myService` is your `MyService` construct and `myTable` is your `MyTable` construct:

```ts title="packages/infra/src/stacks/application-stack.ts"
myTable.grantReadWriteData(myService.taskRole);
```

`grantReadWriteData` grants both the DynamoDB and the KMS permissions to the service's task role.

</Fragment>
<Fragment slot="terraform">

In the example, `module "my_service"` deploys the service and `module "my_table"` deploys the table:

```hcl title="packages/infra/src/main.tf"
resource "aws_iam_role_policy" "my_service_my_table_access" {
  name = "my-service-my-table-access"
  role = module.my_service.task_role_name

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Action = [
          "dynamodb:GetItem", "dynamodb:PutItem", "dynamodb:UpdateItem",
          "dynamodb:DeleteItem", "dynamodb:Query", "dynamodb:Scan",
          "dynamodb:BatchGetItem", "dynamodb:BatchWriteItem",
        ]
        Resource = [
          module.my_table.table_arn,
          "${module.my_table.table_arn}/index/*",
        ]
      },
      {
        Effect = "Allow"
        Action = [
          "kms:Encrypt",
          "kms:Decrypt",
          "kms:ReEncrypt*",
          "kms:GenerateDataKey*",
          "kms:DescribeKey",
        ]
        Resource = [module.my_table.kms_key_arn]
      },
    ]
  })
}
```

## Local Development

<NxCommands commands={["<service-name>-serve <project-name>"]} />

This starts the service and DynamoDB Local. With `LOCAL_DEV=true` set, `is_local()` returns `True` and your PynamoDB entities connect to DynamoDB Local instead of AWS.
