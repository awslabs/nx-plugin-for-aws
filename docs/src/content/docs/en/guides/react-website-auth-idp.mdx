<Link path="guides/react-website-auth">Website authentication</Link> creates an Amazon Cognito user pool, and by default only users who have a username and password in that pool can sign in. If your staff or customers already have accounts at an identity provider (IdP), such as Okta, Auth0 or Microsoft Entra ID, they would otherwise need a second account just for your website.

This generator adds an external [OpenID Connect](https://openid.net/developers/how-connect-works/) (OIDC) identity provider to the user pool. The sign-in page then shows a button for the identity provider next to the username and password form.

## How this works

- Your website still sends users to the Cognito sign-in page. The page now has a button named after the identity provider.
- A user who chooses the button signs in at the identity provider. The identity provider sends them back to Cognito at its redirect URI, `https://<cognito domain>/oauth2/idpresponse`.
- Cognito creates a user in your user pool for them, a federated user, and copies the claims you map (for example `email`) into the user's attributes.
- Cognito then issues the same kind of tokens it issues to a local user. Your APIs, agents and identity pool accept them without any change.

Users with a username and password in the pool can still sign in.

## Usage

### Add an identity provider

You will need a website that has authentication from the <Link path="guides/react-website-auth">`ts#website#auth`</Link> generator. Run this generator once for each identity provider.

## Set up your identity provider

The first deploy after you run the generator reads the client secret from Secrets Manager. If the secret does not exist, the deploy fails. Follow these steps in this order. The generator also prints them when it finishes.

1. Register an application at the identity provider, and note its client ID and client secret. You add its redirect URI in step 4. Run this generator with `--clientId` set to the client ID.
2. Store the client secret in Secrets Manager, under the name in the `clientSecretName` option (`<name>-oidc-client-secret` by default):

   ```bash
   aws secretsmanager create-secret --name TestIdp-oidc-client-secret --secret-string <client secret>
   ```

3. Deploy.
4. Add the redirect URI to the application at the identity provider.

## Attribute mapping

The generated user pool requires the `email`, `given_name` and `family_name` attributes. Cognito fills them from the identity provider's claims on every sign-in. If the identity provider does not send one of them, the user's first sign-in fails. The generator therefore refuses an `attributeMapping` that leaves out any of the three.

`attributeMapping` is a JSON object. Each key is a user pool attribute, and each value is the name of the identity provider's claim. The default maps each attribute to the claim with the same name:

```json
{"email":"email","given_name":"given_name","family_name":"family_name"}
```

- A key can be any [standard attribute](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html#cognito-user-pools-standard-attributes), such as `name` or `phone_number`, or a custom attribute such as `custom:department`.
- Cognito treats a mapped email address as unverified. Map `email_verified` only from an identity provider that verifies email addresses itself. Otherwise a user could set someone else's address at the identity provider and have it marked as verified in your pool.
- If a user's email address changes at the identity provider, Cognito writes the new address to the user pool at the user's next sign-in. `email_verified` stays `false`.
- A custom attribute must already exist in the user pool, and it must be mutable.

The Terraform identity provider file also sets two values that Cognito adds when it returns the identity provider: `"username" = "sub"` in `attribute_mapping` and `attributes_url_add_attributes = "false"` in `provider_details`. Because the file sets them, a second `terraform plan` after the first deploy shows no change to the identity provider. If a second plan still shows a change in `provider_details` with another identity provider, add that key to the file with the value the plan shows Cognito returning.

## Identity provider notes

The settings below come from each vendor's documentation. Only a Cognito user pool acting as the identity provider has been tested with this generator. That test is the AWS check that a release of this generator needs.

### Okta

Not tested. Create an OIDC web application in Okta. The issuer is your Okta domain, `https://<your-org>.okta.com`, or a custom authorization server such as `https://<your-org>.okta.com/oauth2/default`. The default scopes, `openid email profile`, return `email`, `given_name` and `family_name`, so the default mapping works.

### Auth0

Not tested. Create a Regular Web Application in Auth0. The issuer is `https://<your-tenant>.auth0.com/`, including the trailing slash, because the `iss` claim in Auth0 tokens has one. Auth0 returns `given_name` and `family_name` only when the user's connection provides them. Users of a connection without them cannot sign in until you map other claims.

### Microsoft Entra ID

Not tested. Register a single-tenant application in Entra ID. The issuer is `https://login.microsoftonline.com/<tenant-id>/v2.0`. The generator refuses the multi-tenant issuers (`/common/`, `/organizations/` and `/consumers/`), because they accept users from any Entra ID tenant. Entra ID sends `given_name` and `family_name` only if you add them as optional claims to the application's ID token. Its `email` claim is not verified, so do not map `email_verified` from Entra ID.

### Cognito user pool

To test with another Cognito user pool as the identity provider, use the issuer `https://cognito-idp.<region>.amazonaws.com/<user pool id>`. Give its app client a client secret, the authorization code grant and the scopes `openid email profile`.

## Security

- Identify users by the `sub` claim (the user's unique ID in your user pool), never by `email`. A federated user is a new user in your pool with their own `sub`, even when their email matches a local user. The code the plugin generates uses `sub`.
- Use a single-tenant issuer. A multi-tenant issuer lets users from any organization sign in.
- Remove the `http://localhost` callback URLs from production stages, as <Link path="guides/react-website-auth">website authentication</Link> describes. Federation adds no callback URL.

## What federation does not do

- MFA (multi-factor authentication) required in your user pool does not apply to federated users. Cognito leaves their authentication to the identity provider, so enforce MFA at the identity provider.
- Signing out of your website ends the Cognito session only. It does not end the user's session at an OIDC identity provider, so the next sign-in through the button can complete without a password. On a shared computer, users must also sign out at the identity provider.
- The user menu shows the Cognito username. For a federated user it is the identity provider name, an underscore and the user's `sub` at the identity provider, in lowercase, for example `testidp_00u1abcd`.

## Other app clients

An app client is the Cognito configuration that an application signs in through. The generator adds the identity provider to the website's app client, the web client, only. Another app client in the same user pool accepts federated users only if you add the identity provider to it too. For example, the app client you create for a <Link path="guides/ts-dcr-proxy">DCR proxy</Link> (which lets MCP clients, the AI tools that use the Model Context Protocol, sign in through Cognito) needs it. Otherwise federated users cannot sign in to your MCP server. In CDK, add the identity provider's `provider.providerName` to that client's `supportedIdentityProviders`.

## Tokens for the agent chat

The `<agent>-chat` target of a <Link path="guides/ts-agent">TypeScript agent</Link> with Cognito authentication reads a Cognito access token from the `AGENT_ACCESS_TOKEN` environment variable. A federated user has no Cognito password, so `admin-initiate-auth` does not work for them. Instead, sign in to your website, open the browser's developer tools, and copy `access_token` from the `oidc.user:...` entry in session storage.
