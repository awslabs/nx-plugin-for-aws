<Link path="guides/react-website-auth">Website authentication</Link> creates an Amazon Cognito user pool, and by default only users who have a username and password in that pool can sign in. If your staff or customers already have accounts at an identity provider (IdP), such as Okta, Auth0 or Microsoft Entra ID, they would otherwise need a second account just for your website.

Running `ts#website#auth` with `--federation=oidc` lets you add external [OpenID Connect](https://openid.net/developers/how-connect-works/) (OIDC) identity providers to the user pool. You list the identity providers in your infrastructure code: the `oidcIdentityProviders` prop of `UserIdentity` in CDK, or the `oidc_identity_providers` variable of the `user_identity` module in Terraform. The sign-in page then shows a button for each identity provider next to the username and password form.

## How this works

- Your website still sends users to the Cognito sign-in page. The page now has a button named after each identity provider.
- A user who chooses a button signs in at that identity provider. The identity provider sends them back to Cognito at its redirect URI, `https://<cognito domain>/oauth2/idpresponse`.
- Cognito creates a user in your user pool for them, a federated user, and copies the claims you map (for example `email`) into the user's attributes.
- Cognito then issues the same kind of tokens it issues to a local user. Your APIs, agents and identity pool accept them without any change.

Users with a username and password in the pool can still sign in.

## Who can sign in

Adding an identity provider can let many more people into your website than you expect. The `allowSignup` option of `ts#website#auth` does not apply to federated users. Cognito creates a federated user the first time someone signs in through the identity provider, even when the user pool does not let users sign themselves up. Each federated user also gets the identity pool's authenticated role, so they can call your APIs and agents as any signed-in user can.

The identity providers apply to the whole user pool. Every website that uses the pool shows their buttons and accepts their users.

The identity provider therefore decides who can sign in. Set it up so that it signs in only the people who need your website:

- Microsoft Entra ID: in the application's enterprise application properties, set "Assignment required?" to Yes, and assign only the users or groups who need access. With the default, No, every user in your tenant can sign in.
- Okta: assign the application only to the groups who need access.
- Auth0: disable sign-ups on each connection the application uses, and enable for the application only the connections whose users need access. Otherwise anyone who signs up through an enabled connection, for example a social connection, can sign in.

## Usage

### Add OpenID Connect federation

Run the <Link path="guides/react-website-auth">`ts#website#auth`</Link> generator with `--federation=oidc`. You can run it on a website that has no authentication yet, or on a website that already has it. Both give the same result.

<RunGenerator generator="ts#website#auth" requiredParameters={{ federation: 'oidc' }} />

The generator adds no identity provider. The list starts empty, so sign-in works as before until you add an entry. You add identity providers to your infrastructure code, so adding a second one does not need another generator run.

Running the generator again with `--federation=oidc` changes no file. Running it with `--federation=none`, or without `--federation`, keeps the federation that is already there.

Add an entry for each identity provider, then deploy. The client secret never goes into your code. You store it in AWS Secrets Manager and give its name, as [Set up your identity provider](#set-up-your-identity-provider) describes.

### Options

Each identity provider in the list has these properties. The generator options are described in <Link path="guides/react-website-auth">website authentication</Link>.

| CDK prop | Terraform attribute | Required | Default | Description |
|---|---|---|---|---|
| `name` | `name` | Yes | | Shown on the sign-in button. Cognito prefixes federated usernames with it in lower case (`<name>_<sub>`). 3-32 letters, digits and hyphens, starting with a letter. Not `COGNITO`. Unique in the list, ignoring case. In CDK it must be a literal string, not a token. |
| `issuerUrl` | `issuer_url` | Yes | | The issuer exactly as it appears in the `iss` claim of the identity provider's tokens. Must use `https://`. |
| `clientId` | `client_id` | Yes | | Client ID of the application registered at the identity provider. |
| `clientSecretName` | `client_secret_name` | Yes | | Name of the Secrets Manager secret that holds the client secret as a plain string. A name, not an ARN. |
| `scopes` | `scopes` | No | `openid`, `email`, `profile` | OAuth scopes to request. Must include `openid`. |
| `attributeMapping` | `attribute_mapping` | No | `email`, `given_name` and `family_name`, each to the claim with the same name | User pool attribute to identity provider claim. See [Attribute mapping](#attribute-mapping). |
| `identifiers` | `identifiers` | No | None | Identifiers, such as email domains, that Cognito can use to send a user to this identity provider. |

### Validation

The vended code checks each entry before anything is deployed:

<Infrastructure>
  <Fragment slot="cdk">
`UserIdentity` throws when you create it with an entry that breaks a rule, so `cdk synth` fails. The infra project's build runs `cdk synth`. The message names the entry, for example `UserIdentity: oidcIdentityProviders[1] (Entra): Microsoft Entra ID issuers have no trailing slash. Use https://login.microsoftonline.com/<tenant-id>/v2.0`.

A value that is a token, for example one read from AWS Systems Manager Parameter Store, is not checked. A wrong value then fails the deploy instead of the synth. `name` must not be a token.
  </Fragment>
  <Fragment slot="terraform">
The module's `oidc_identity_providers` variable has one `validation` block for each rule. Its error messages do not name the entry that breaks the rule.

When you write the list as a literal in the `user_identity` module block, `terraform validate` checks it. The project's `validate` target runs `terraform validate`. When the list comes from a root variable, as in the `.tfvars` pattern above, `terraform plan` checks it instead.
  </Fragment>
</Infrastructure>

The rules:

- `name`: 3-32 letters, digits and hyphens, starting with a letter. Not `COGNITO` in any case, because Cognito reserves it for sign-in with the user pool itself.
- Names are unique in the list, ignoring case, because Cognito prefixes federated usernames with the lower-case name. For example, `Okta` and `OKTA` cannot both be in the list. `test-idp` and `testidp` can, because their prefixes differ.
- The issuer uses `https://` and has no query, fragment, user name, password or whitespace. In CDK it must also parse as a URL. In Terraform a regular expression checks it, which accepts a few malformed URLs that CDK refuses.
- Microsoft Entra ID: the multi-tenant issuers (`common`, `organizations`, `consumers` and `9188040d-6c67-4c5b-b112-36a304b66dad`) are refused, and the issuer must not end with a slash.
- Auth0: an issuer on `*.auth0.com` must end with a slash.
- The client ID is not empty.
- The secret name is 1-512 letters, digits and `/ _ + = . @ -`. These are the Secrets Manager naming rules, so an ARN is refused.
- The scopes include `openid`. In CDK each scope must also be non-empty and have no whitespace.
- The attribute mapping keys and values follow the rules in [Attribute mapping](#attribute-mapping).
- At most 50 identifiers. Each is 1-40 letters, digits, spaces or `_ + = . @ -`.

## Set up your identity provider

The deploy that adds an identity provider reads its client secret from Secrets Manager. If the secret does not exist, the deploy fails. Follow these steps in this order. The generator also prints them when it finishes.

1. Run `ts#website#auth` with `--federation=oidc`, and deploy once.
2. Find the redirect URI of your user pool. All identity providers of the pool use the same one.

<Infrastructure>
  <Fragment slot="cdk">
The stack that contains `UserIdentity` has an output whose key starts with `<id>OidcIdentityProvidersIdpRedirectUri`, where `<id>` is the construct ID you gave `UserIdentity`, for example `IdentityOidcIdentityProvidersIdpRedirectUri`. You can also work it out before you deploy, from the `cognitoDomain` you chose for `ts#website#auth`, your AWS account ID and your region:

```
https://<cognitoDomain>-<account>.auth.<region>.amazoncognito.com/oauth2/idpresponse
```
  </Fragment>
  <Fragment slot="terraform">
The Cognito domain has a random suffix, so the redirect URI is known only after the deploy. The `user_identity` module outputs it as `idp_redirect_uri`. To see it, add an output to your root module, for example `packages/infra/src/main.tf`:

```hcl
output "idp_redirect_uri" { value = module.user_identity.idp_redirect_uri }
```
  </Fragment>
</Infrastructure>

3. Register an application at the identity provider with that redirect URI, and note its client ID and client secret. Register only this `/oauth2/idpresponse` URI at the identity provider. Your website's own URLs are registered with Cognito, not with the identity provider.
4. Store the client secret in Secrets Manager:

   ```bash
   aws secretsmanager create-secret --name okta-oidc-client-secret --secret-string <client secret> --region <region>
   ```

   Set `--region` to your stack's region. The secret must exist in that region before the deploy that adds the identity provider. Store the secret as a plain string, not JSON, because Cognito receives the whole secret value as the client secret. In the Secrets Manager console, choose Plaintext, not Key/value.

5. Add the identity provider to the list, with the secret's name as `clientSecretName` (`client_secret_name` in Terraform), as [Add identity providers](#add-identity-providers) shows. Then deploy.

## Attribute mapping

The generated user pool requires the `email`, `given_name` and `family_name` attributes. Cognito fills them from the identity provider's claims on every sign-in. If the identity provider does not send one of them, the user's first sign-in fails. `UserIdentity` and the Terraform variable therefore refuse an attribute mapping that leaves out any of the three.

`attributeMapping` (`attribute_mapping` in Terraform) maps user pool attributes to claims. Each key is a user pool attribute, and each value is the name of the identity provider's claim, 1-128 characters long. A mapping you give replaces the default. The default maps each required attribute to the claim with the same name:

<Infrastructure>
  <Fragment slot="cdk">
```ts
attributeMapping: { email: 'email', given_name: 'given_name', family_name: 'family_name' },
```
  </Fragment>
  <Fragment slot="terraform">
```hcl
attribute_mapping = { email = "email", given_name = "given_name", family_name = "family_name" }
```
  </Fragment>
</Infrastructure>

- A key can be any [standard attribute](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html#cognito-user-pools-standard-attributes), such as `name` or `phone_number`, `phone_number_verified`, or a custom attribute such as `custom:department` (up to 20 letters, digits or underscores after `custom:`). Keys use the Cognito attribute names in both CDK and Terraform. `username` is refused.
- Cognito treats a mapped email address as unverified. Map `email_verified` only from an identity provider that verifies email addresses itself. Otherwise a user could set someone else's address at the identity provider and have it marked as verified in your pool.
- If a user's email address changes at the identity provider, Cognito writes the new address to the user pool at the user's next sign-in. `email_verified` stays `false`.
- A custom attribute must already exist in the user pool, and it must be mutable.

The Terraform identity provider resource, in `identity/oidc-identity-providers.tf`, also sets two values that Cognito adds when it returns the identity provider: `username = "sub"` in `attribute_mapping` and `attributes_url_add_attributes = "false"` in `provider_details`. Because the file sets them, a second `terraform plan` after the first deploy shows no change to the identity provider. If a second plan still shows a change in `provider_details` with another identity provider, add that key to the file with the value the plan shows Cognito returning.

## Identity provider notes

The settings below come from each vendor's documentation. Okta has been tested on AWS with both CDK and Terraform. The Auth0 and Microsoft Entra ID settings were checked against each vendor's published OpenID discovery document, but not with a live sign-in.

### Okta

Tested on AWS with CDK and Terraform. Create an OIDC Web Application in Okta, with the Authorization Code grant and a client secret. Set its sign-in redirect URI to the `/oauth2/idpresponse` redirect URI from step 2 of [Set up your identity provider](#set-up-your-identity-provider). It needs no sign-out redirect URI. The issuer is your Okta domain, `https://<your-org>.okta.com`, which is the form that was tested. A custom authorization server, such as `https://<your-org>.okta.com/oauth2/default`, also has an issuer, but that form has not been tested. The default scopes, `openid email profile`, return `email`, `given_name` and `family_name`, so the default mapping works. Each user needs an email, a first name and a last name set in Okta. Assign the application only to the users or groups who need access.

### Auth0

Checked against Auth0's discovery document, not tested with a live sign-in. Create a Regular Web Application in Auth0. The issuer is `https://<your-tenant>.auth0.com/`, including the trailing slash.

:::caution
The `iss` claim in Auth0 tokens ends with a slash, so an issuer without it makes sign-in fail. The vended code refuses an issuer on `*.auth0.com` without the slash. It cannot recognize an Auth0 custom domain, so check the slash yourself when you use one.
:::

Auth0 returns `given_name` and `family_name` only when the user's connection provides them. Users of a connection without them cannot sign in until you map other claims.

### Microsoft Entra ID

Checked against Microsoft's discovery document, not tested with a live sign-in. Register a single-tenant application in Entra ID. The issuer is `https://login.microsoftonline.com/<tenant-id>/v2.0`. The vended code refuses the multi-tenant issuers (`common`, `organizations` and `consumers`), because they accept users from any Entra ID tenant. It also refuses the tenant `9188040d-6c67-4c5b-b112-36a304b66dad`, which accepts any personal Microsoft account.

The issuer must not end with a slash: use `/v2.0`, not `/v2.0/`. The `iss` claim in Entra ID tokens has no slash, so sign-in would fail. The vended code refuses the form with the slash.

Add `email`, `given_name` and `family_name` as optional claims to the application's ID token. Entra ID sends them only if you do. Each user needs the Mail field set. Otherwise the `email` claim is empty, and the user's first sign-in fails, because the user pool requires `email`. Entra ID's `email` claim is not verified, so do not map `email_verified` from Entra ID.

### Cognito user pool

To test with another Cognito user pool as the identity provider, use the issuer `https://cognito-idp.<region>.amazonaws.com/<user pool id>`. Give its app client a client secret, the authorization code grant and the scopes `openid email profile`.

## Security

- Identify users by the `sub` claim (the user's unique ID in your user pool), never by `email`. A federated user is a new user in your pool with their own `sub`, even when their email matches a local user. The code the plugin generates uses `sub`.
- Use a single-tenant issuer. A multi-tenant issuer lets users from any organization sign in.
- Remove the `http://localhost` callback URLs from production stages, as <Link path="guides/react-website-auth">website authentication</Link> describes. Federation adds no callback URL.

## What federation does not do

- MFA (multi-factor authentication) required in your user pool does not apply to federated users. Cognito leaves their authentication to the identity provider, so enforce MFA at the identity provider.
- Signing out of your website ends the Cognito session only. It does not end the user's session at an OIDC identity provider, so the next sign-in through the button can complete without a password. On a shared computer, users must also sign out at the identity provider.
- The user menu shows the Cognito username. For a federated user it is the identity provider name, an underscore and the user's `sub` at the identity provider, in lowercase, for example `okta_00u1abcd`.
- Removing or disabling a user at the identity provider stops only their next sign-in through it. Cognito renews tokens with its own refresh token and does not ask the identity provider, and the website renews tokens without the user noticing. The user can therefore keep access until the refresh token expires, up to 30 days after their last sign-in. To end the user's access at once, also sign them out of every session and disable them in the user pool. Their username is `<identity provider name in lowercase>_<sub>`:

  ```bash
  aws cognito-idp admin-user-global-sign-out --user-pool-id <user pool id> --username okta_<sub>
  aws cognito-idp admin-disable-user --user-pool-id <user pool id> --username okta_<sub>
  ```

  This has been tested on AWS. After `admin-user-global-sign-out` and `admin-disable-user`, the identity provider still signs the user in, but Cognito refuses them.

  A shorter refresh token validity on the web client (`refreshTokenValidity` in CDK, `refresh_token_validity` in Terraform) shortens the time a removed user keeps access. This has not been tested on AWS.

## The client secret

Cognito holds the client secret in the identity provider's settings. Anyone allowed to call `cognito-idp:DescribeIdentityProvider` on your user pool can read it. This is how Cognito works, whichever IaC provider you use.

## Other app clients

An app client is the Cognito configuration that an application signs in through. The generator adds the identity providers to the website's app client, the web client, only. Another app client in the same user pool accepts federated users only if it lists the identity providers too. For example, the app client you create for a <Link path="guides/ts-dcr-proxy">DCR proxy</Link> (which lets MCP clients, the AI tools that use the Model Context Protocol, sign in through Cognito) needs them. Otherwise federated users cannot sign in to your MCP server.

<Infrastructure>
  <Fragment slot="cdk">

  </Fragment>
  <Fragment slot="terraform">

## Tokens for the agent chat

The `<agent>-chat` target of a <Link path="guides/ts-agent">TypeScript agent</Link> with Cognito authentication reads a Cognito access token from the `AGENT_ACCESS_TOKEN` environment variable. A federated user has no Cognito password, so `admin-initiate-auth` does not work for them. Instead, sign in to your website, open the browser's developer tools, and copy `access_token` from the `oidc.user:...` entry in session storage.
