[tRPC](https://trpc.io/) là một framework để xây dựng API trong TypeScript với tính an toàn kiểu từ đầu đến cuối. Sử dụng tRPC, các cập nhật đối với đầu vào và đầu ra của các thao tác API được phản ánh ngay lập tức trong mã client và hiển thị trong IDE của bạn mà không cần phải rebuild dự án.

Trình tạo API tRPC tạo một API tRPC mới với cấu hình cơ sở hạ tầng AWS CDK hoặc Terraform. Backend được tạo được expose thông qua AWS API Gateway API, và bao gồm xác thực schema sử dụng [Zod](https://zod.dev/). Nó thiết lập [AWS Lambda Powertools](https://docs.powertools.aws.dev/lambda/typescript/latest/) để quan sát, bao gồm structured logging và CloudWatch metrics.

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambda hosting">
AWS X-Ray tracing cũng được thiết lập.

Các procedure của bạn chạy trên AWS Lambda, vì vậy không có server để quản lý và bạn chỉ trả tiền cho các request bạn phục vụ.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="ECS hosting">
Các procedure của bạn chạy như một HTTP server tồn tại lâu dài trong một container trên Amazon ECS, đằng sau một API Gateway HTTP API. Xem <a href="#running-on-amazon-ecs">Running on Amazon ECS</a> để biết những gì thay đổi, bao gồm lý do tại sao X-Ray tracing không tạo ra trace ở đó.
</OptionFilter>

## Triển khai API tRPC của bạn

Ở mức độ cao, các API tRPC bao gồm một router ủy quyền các request đến các procedure cụ thể. Mỗi procedure có một đầu vào và đầu ra, được định nghĩa dưới dạng schema Zod.

### Schema

Thư mục `src/schema` chứa các kiểu được chia sẻ giữa mã client và server của bạn. Trong package này, các kiểu này được định nghĩa bằng [Zod](https://zod.dev/), một thư viện khai báo và xác thực schema ưu tiên TypeScript.

Một schema ví dụ có thể trông như sau:

```ts
import { z } from 'zod';

// Schema definition
export const UserSchema = z.object({
  name: z.string(),
  height: z.number(),
  dateOfBirth: z.string().datetime(),
});

// Corresponding TypeScript type
export type User = z.TypeOf<typeof UserSchema>;
```

Với schema trên, kiểu `User` tương đương với TypeScript sau:

```ts
interface User {
  name: string;
  height: number;
  dateOfBirth: string;
}
```

Schema được chia sẻ bởi cả mã server và client, cung cấp một nơi duy nhất để cập nhật khi thực hiện thay đổi đối với các cấu trúc được sử dụng trong API của bạn.

Schema được tự động xác thực bởi API tRPC của bạn tại runtime, giúp tiết kiệm việc tạo logic xác thực tùy chỉnh thủ công trong backend của bạn.

Zod cung cấp các tiện ích mạnh mẽ để kết hợp hoặc suy ra schema như `.merge`, `.pick`, `.omit` và nhiều hơn nữa. Bạn có thể tìm thêm thông tin trên [trang tài liệu Zod](https://zod.dev/?id=basic-usage).

### Router và Procedures

Router tRPC của bạn được định nghĩa trong `src/router.ts`, đăng ký tất cả các procedure. Mỗi procedure định nghĩa đầu vào, đầu ra và triển khai mong đợi.

<OptionFilter not when={{ infra: 'http-ecs' }} description="The Lambda entry point">
Entry point của Lambda handler nằm trong `src/handler.ts`, chuyển tiếp các request đến router của bạn.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="The container entry point">
Entry point là `src/<api-name>-container/server.ts`, HTTP server mà container chạy, chuyển tiếp các request đến router của bạn.
</OptionFilter>

Router mẫu được tạo cho bạn có một thao tác duy nhất, được gọi là `echo`:

```ts
import { echo } from './procedures/echo.js';

export const appRouter = router({
  echo,
});
```

Procedure `echo` ví dụ được tạo cho bạn trong `src/procedures/echo.ts`:

```ts
export const echo = publicProcedure
  .input(EchoInputSchema)
  .output(EchoOutputSchema)
  .query((opts) => ({ message: opts.input.message }));
```

Để phân tích phần trên:

- `publicProcedure` định nghĩa một phương thức công khai trên API, bao gồm middleware được thiết lập trong `src/middleware`. Middleware này bao gồm tích hợp AWS Lambda Powertools cho logging, tracing và metrics.
- `input` chấp nhận một schema Zod định nghĩa đầu vào mong đợi cho thao tác. Các request được gửi cho thao tác này được tự động xác thực theo schema này.
- `output` chấp nhận một schema Zod định nghĩa đầu ra mong đợi cho thao tác. Bạn sẽ thấy lỗi kiểu trong triển khai của mình nếu bạn không trả về đầu ra phù hợp với schema.
- `query` chấp nhận một hàm định nghĩa triển khai cho API của bạn. Triển khai này nhận `opts`, chứa `input` được truyền cho thao tác của bạn, cũng như ngữ cảnh khác được thiết lập bởi middleware, có sẵn trong `opts.ctx`. Hàm được truyền cho `query` phải trả về một đầu ra phù hợp với schema `output`.

Việc sử dụng `query` để định nghĩa triển khai cho biết rằng thao tác không thay đổi dữ liệu. Sử dụng điều này để định nghĩa các phương thức truy xuất dữ liệu. Để triển khai một thao tác thay đổi dữ liệu, hãy sử dụng phương thức `mutation` thay thế.

Nếu bạn thêm một procedure mới, hãy đảm bảo bạn đăng ký nó bằng cách thêm nó vào router trong `src/router.ts`.

<OptionFilter when={{ infra: 'rest-lambda' }} description="Streaming subscriptions — REST API only, uses SSE">
### Subscriptions (Streaming)

tRPC subscriptions cho phép bạn stream dữ liệu từ server đến client bằng [Server-Sent Events (SSE)](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events). Khi bạn chọn `rest-lambda` làm loại compute của mình, generator tự động cấu hình cơ sở hạ tầng cần thiết cho streaming, cũng như một streaming Lambda handler và schema helper `ZodAsyncIterable`.

Để định nghĩa một subscription procedure, sử dụng phương thức `.subscription` với một hàm async generator. Sử dụng helper `ZodAsyncIterable` từ `src/schema/z-async-iterable.ts` để định nghĩa schema đầu ra:

```ts
import { publicProcedure } from '../init.js';
import { z } from 'zod';
import { ZodAsyncIterable } from '../schema/z-async-iterable.js';

const InputSchema = z.object({ query: z.string() });
const ChunkSchema = z.object({ text: z.string() });

export const myStream = publicProcedure
  .input(InputSchema)
  .output(
    ZodAsyncIterable({
      yield: ChunkSchema,
    }),
  )
  .subscription(async function* (opts) {
    // Yield data to the client as it becomes available
    for (const chunk of await getResults(opts.input.query)) {
      yield { text: chunk };
    }
  });
```

Đăng ký subscription trong router của bạn giống như bất kỳ procedure nào khác:

```ts
export const appRouter = router({
  echo,
  myStream,
});
```

Cơ sở hạ tầng được tạo sử dụng một streaming Lambda handler với `ResponseTransferMode.STREAM` trong API Gateway cho tất cả các thao tác REST API, cho phép subscriptions hoạt động cùng với các query và mutation thông thường.
</OptionFilter>

## Tùy chỉnh API tRPC của bạn

### Lỗi

Trong triển khai của bạn, bạn có thể trả về các response lỗi cho client bằng cách throw một `TRPCError`. Chúng chấp nhận một `code` cho biết loại lỗi, ví dụ:

```ts
throw new TRPCError({
  code: 'NOT_FOUND',
  message: 'The requested resource could not be found',
});
```

### Tổ chức các Operation của bạn

Khi API của bạn phát triển, bạn có thể muốn nhóm các thao tác liên quan lại với nhau.

Bạn có thể nhóm các thao tác lại với nhau bằng cách sử dụng nested router, ví dụ:

```ts
import { getUser } from './procedures/users/get.js';
import { listUsers } from './procedures/users/list.js';

const appRouter = router({
   users: router({
      get: getUser,
      list: listUsers,
   }),
   ...
})
```

Client sau đó nhận được nhóm thao tác này, ví dụ: gọi thao tác `listUsers` trong trường hợp này có thể trông như sau:

```ts
client.users.list.query();
```

### Logging

AWS Lambda Powertools logger được cấu hình trong `src/middleware/logger.ts`, và có thể được truy cập trong triển khai API thông qua `opts.ctx.logger`. Bạn có thể sử dụng điều này để log vào CloudWatch Logs, và/hoặc kiểm soát các giá trị bổ sung để bao gồm trong mọi thông báo log có cấu trúc. Ví dụ:

```ts {5}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      opts.ctx.logger.info('Operation called with input', opts.input);

      return ...;
   });
```

Để biết thêm thông tin về logger, vui lòng tham khảo [tài liệu AWS Lambda Powertools Logger](https://docs.powertools.aws.dev/lambda/typescript/latest/core/logger/).

### Ghi lại Metrics

AWS Lambda Powertools metrics được cấu hình trong `src/middleware/metrics.ts`, và có thể được truy cập trong triển khai API thông qua `opts.ctx.metrics`. Bạn có thể sử dụng điều này để ghi lại metrics trong CloudWatch mà không cần import và sử dụng AWS SDK, ví dụ:

```ts {5}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      opts.ctx.metrics.addMetric('Invocations', 'Count', 1);

      return ...;
   });
```

Để biết thêm thông tin, vui lòng tham khảo [tài liệu AWS Lambda Powertools Metrics](https://docs.powertools.aws.dev/lambda/typescript/latest/core/metrics/).

### Tinh chỉnh X-Ray Tracing

AWS Lambda Powertools tracer được cấu hình trong `src/middleware/tracer.ts`, và có thể được truy cập trong triển khai API thông qua `opts.ctx.tracer`. Bạn có thể sử dụng điều này để thêm trace với AWS X-Ray để cung cấp thông tin chi tiết về hiệu suất và luồng của các request API. Ví dụ:

```ts {5-7}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      const subSegment = opts.ctx.tracer.getSegment()!.addNewSubsegment('MyAlgorithm');
      // ... my algorithm logic to capture
      subSegment.close();

      return ...;
   });
```

Để biết thêm thông tin, vui lòng tham khảo [tài liệu AWS Lambda Powertools Tracer](https://docs.powertools.aws.dev/lambda/typescript/latest/core/tracer/).

<OptionFilter when={{ infra: 'http-ecs' }} description="X-Ray produces no traces on ECS">
:::caution[Không có trace trên ECS]
Các lệnh gọi trên chạy mà không có lỗi trong một container, nhưng không tạo ra trace. Powertools tắt tracer của nó khi không chạy trong Lambda, vì vậy `getSegment()` trả về một subsegment giữ chỗ không bao giờ được gửi đi đâu cả. Xem <a href="#observability">Observability</a> để biết những gì bạn nhận được và những gì cần thêm nếu bạn cần trace.
:::
</OptionFilter>

### Triển khai Custom Middleware

Bạn có thể thêm các giá trị bổ sung vào ngữ cảnh được cung cấp cho các procedure bằng cách triển khai middleware.

Ví dụ, hãy triển khai một số middleware để trích xuất một số chi tiết về người dùng đang gọi từ API của chúng ta trong `src/middleware/identity.ts`.

<OptionFilter when={{ auth: 'iam', infra: ['rest-lambda', 'http-lambda'] }} description="Identity middleware example for IAM-authenticated APIs on Lambda">
Ví dụ này hướng dẫn identity middleware cho xác thực `IAM`. Chúng ta tra cứu người gọi trong Cognito bằng cách sử dụng sub được trích xuất từ API Gateway event.

Việc tra cứu sử dụng Cognito Identity Provider client, không phải là dependency của API tRPC được tạo. Cài đặt nó vào dự án API của bạn trước:

<InstallCommand pkg={`@aws-sdk/client-cognito-identity-provider@${TS_VERSIONS['@aws-sdk/client-cognito-identity-provider']}`} project="@my-scope/my-api" />

Đầu tiên, chúng ta định nghĩa những gì chúng ta sẽ thêm vào ngữ cảnh:

```ts
export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}
```

Lưu ý rằng chúng ta định nghĩa một thuộc tính _tùy chọn_ bổ sung cho ngữ cảnh. tRPC quản lý việc đảm bảo rằng điều này được định nghĩa trong các procedure đã cấu hình middleware này một cách chính xác.

Tiếp theo, chúng ta sẽ triển khai middleware. Nó có cấu trúc sau:

```ts
export const createIdentityPlugin = () => {
   const t = initTRPC.context<...>().create();
   return t.procedure.use(async (opts) => {
      // Add logic here to run before the procedure

      const response = await opts.next(...);

      // Add logic here to run after the procedure

      return response;
   });
};
```

Trong trường hợp của chúng ta, chúng ta muốn trích xuất chi tiết về người dùng Cognito đang gọi. Chúng ta sẽ làm điều đó bằng cách trích xuất ID chủ thể của người dùng (hoặc "sub") từ API Gateway event, và truy xuất chi tiết người dùng từ Cognito. Việc triển khai khác nhau tùy thuộc vào việc event được cung cấp cho hàm của chúng ta bởi REST API hay HTTP API:

<Tabs syncKey="http-rest">
<TabItem label="REST API" _filter={{ infra: 'rest-lambda' }}>
```ts
import { CognitoIdentityProvider } from '@aws-sdk/client-cognito-identity-provider';
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEvent } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext & CreateAWSLambdaContextOptions<APIGatewayProxyEvent>
    >()
    .create();

  const cognito = new CognitoIdentityProvider();

  return t.procedure.use(async (opts) => {
    const cognitoAuthenticationProvider =
      opts.ctx.event.requestContext?.identity?.cognitoAuthenticationProvider;

    let sub: string | undefined = undefined;
    if (cognitoAuthenticationProvider) {
      const providerParts = cognitoAuthenticationProvider.split(':');
      sub = providerParts[providerParts.length - 1];
    }

    if (!sub) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `Unable to determine calling user`,
```

```ts
import { publicProcedure } from '../init.js';
```

```ts {10,13-15}
      integrations: MyApi.defaultIntegrations(this, { vpc }).build(),
```

<OptionFilter when={{ infra: 'http-ecs' }} description="How ECS hosting works, what it costs and what it limits">
## Running on Amazon ECS

Với `infra` được đặt thành `http-ecs`, các procedure của bạn chạy như một HTTP server tồn tại lâu dài trong một container thay vì trong một hàm Lambda. Một request đi theo đường dẫn này:

1. Người gọi ký một request đến API Gateway HTTP API, đây là điểm vào công khai duy nhất. Mọi route đều mang authorizer cho `auth` bạn đã chọn, vì vậy một request không được xác thực sẽ bị từ chối tại edge.
2. API Gateway chuyển tiếp request thông qua VPC link, đây là đường dẫn riêng tư của nó vào VPC của bạn.
3. VPC link tiếp cận một internal load balancer. Load balancer không có địa chỉ công khai, và quy tắc inbound duy nhất của nó cho phép security group của VPC link trên listener port.
4. Load balancer chuyển tiếp request đến một task. Quy tắc inbound duy nhất của các task cho phép security group của load balancer trên container port, vì vậy không có gì khác trong VPC có thể mở kết nối đến chúng.

Các task chạy trong private subnet và không bao giờ nhận địa chỉ IP công khai. Không có gì trong đường dẫn này cho phép một dải địa chỉ inbound.

Theo mặc định, service, load balancer và VPC link nằm trong các subnet `PRIVATE_WITH_EGRESS` của VPC, tiếp cận AWS thông qua NAT gateway. Truyền `vpcSubnets: { subnetType: SubnetType.PRIVATE_ISOLATED }` cho `defaultIntegrations` loại bỏ NAT gateway và chi phí hàng giờ của nó, nhưng các isolated subnet không có route ra ngoài, vì vậy VPC sau đó cần bốn VPC endpoint để các task khởi động: interface endpoint cho `ecr.api` và `ecr.dkr` để pull image, một S3 gateway endpoint vì các image layer là các đối tượng S3, và một interface endpoint cho `logs` để driver `awslogs` có thể ghi. Không có chúng, một task không thể pull image của nó và ECS roll back deployment trên circuit breaker mà không nói tại sao.

VPC link, load balancer, listener của nó, target group và bucket mà load balancer ghi access log của nó được tạo bởi một construct, `core/api/ecs-http-endpoint.ts` trong `common/constructs`, mà mọi API được host trên ECS chia sẻ. Construct của chính API của bạn đặt tên cho container service của nó và route mọi thao tác đến endpoint đó.

### What Runs in the Container

`src/<api-name>-container/server.ts` là một server `node:http` với hai công việc. `GET /health` trả lời `{"status":"ok"}`, đó là những gì target group của load balancer và container health check gọi. Mọi request khác đi đến [tRPC standalone adapter](https://trpc.io/docs/server/adapters/standalone), giải quyết nó với router của bạn.

Không có API Gateway event trong container, vì vậy procedure context không mang trường `event`, `context` hoặc `info`: đối với `http-ecs`, `IMiddlewareContext` được vend chỉ đặt tên những gì middleware đặt ở đó. Authorizer vẫn quyết định liệu một request có tiếp cận container hay không, nhưng các claim của nó không đến cùng với request, vì vậy các ví dụ identity middleware ở trên không áp dụng. Để đọc danh tính của người gọi trong một procedure, ánh xạ ngữ cảnh của authorizer lên một request header trong API construct của bạn và đọc header đó.

### Observability

Log và metric hoạt động như chúng làm trên Lambda: container ghi vào CloudWatch log group của riêng nó, và metrics plugin xuất bản metric của mỗi request ở định dạng embedded metric để CloudWatch Logs trích xuất.

Metrics plugin xây dựng một đối tượng metric cho mỗi request và trao nó cho các procedure của bạn dưới dạng `opts.ctx.metrics`, vì vậy một metric mà một request thêm vào không bao giờ được xuất bản với metric của request khác. Điều đó quan trọng hơn ở đây so với trên Lambda, nơi một invocation sở hữu các metric từ đầu đến cuối; server này xử lý các request cùng một lúc. Thêm metric của riêng bạn thông qua `opts.ctx.metrics` thay vì một đối tượng `Metrics` của riêng bạn, điều này sẽ chia sẻ một store trên mọi request trong process.

AWS X-Ray tracing thì không. Powertools tắt tracer của nó bên ngoài Lambda, và không có X-Ray daemon trong task để nhận các segment, vì vậy các lệnh gọi `opts.ctx.tracer` chạy mà không có lỗi và không tạo ra trace. Thêm một daemon như một sidecar trong container service của bạn nếu bạn cần chúng.

Access log của API Gateway HTTP API ghi lại mọi request tiếp cận API. Load balancer ghi access log của riêng nó vào một bucket mà construct `EcsHttpEndpoint` tạo, đó là nơi bạn có thể thấy task nào phục vụ một request và nó trả lời gì.

### Image Build and Scanning

Container generator vend các image target, được đặt tên theo API của bạn:

- `<api-name>-container-docker` xây dựng một image linux/arm64, chạy `bundle` trước để image chứa bundled server.
- `<api-name>-container-trivy` quét image đó để tìm lỗ hổng.

Xem <Link path="/guides/ts-container">TypeScript Container Service</Link> để biết cách image được xây dựng, và <Link path="/guides/docker-bundling">Docker Bundling</Link> để biết cách nó được xuất bản tại thời điểm deploy.

### Limits

- **Integration timeout.** API Gateway HTTP API giới hạn một integration ở khoảng 30 giây. Một procedure mất nhiều thời gian hơn thế sẽ thất bại tại gateway dù container tiếp tục hoạt động bao lâu.
- **No streaming.** tRPC subscription cần cơ sở hạ tầng `rest-lambda`. Một HTTP API không thể stream một response.
- **Payload size.** Request và response tuân theo giới hạn 10 MB của API Gateway.
- **One service for every operation.** `integrationPattern` là `shared`: có một container service, và mọi route được route đến nó. Tùy chọn luôn giải quyết thành `shared` cho cơ sở hạ tầng này, và `isolated` bị bỏ qua với một cảnh báo.

### Cost

Load balancer là chi phí cố định mới so với Lambda, nơi bạn trả tiền cho mỗi request và không có gì khi idle. Các con số hàng tháng gần đúng ở us-east-1, trước khi truyền dữ liệu:

| Item | Approximately |
| --- | --- |
| Internal load balancer | $16 cộng với load balancer capacity units |
| Fargate task, 0.25 vCPU / 0.5 GB arm64 | $7 mỗi task |
| NAT gateway, nếu VPC của bạn có một | $33 |
| VPC link | không có phí hàng giờ |
| S3 storage cho access log của load balancer | cent mỗi GB một tháng |

Vì vậy, một service một task có giá khoảng $23 một tháng trước khi có bất kỳ traffic nào, và nhiều hơn nếu VPC bạn truyền vào có NAT gateway. Access log tăng theo traffic: thêm một lifecycle rule vào `endpoint.accessLogsBucket` để hết hạn chúng. Kiểm tra các trang giá [Elastic Load Balancing](https://aws.amazon.com/elasticloadbalancing/pricing/) và [AWS Fargate](https://aws.amazon.com/fargate/pricing/) để biết giá hiện tại trong Region của bạn.

## Local tRPC Server

Bạn có thể sử dụng target `serve` để chạy một server cục bộ cho API của mình, ví dụ:

<NxCommands commands={['serve my-api']} />

<OptionFilter not when={{ infra: 'http-ecs' }} description="Local server entry point for the Lambda variants">
Entry point cho server cục bộ là `src/local-server.ts`.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="Local server entry point when the API runs on ECS">
Entry point cho server cục bộ là `src/<api-name>-container/index.ts`, cùng file mà container chạy. Nó lắng nghe trên địa chỉ trong `HOST`, mặc định là `127.0.0.1`, vì vậy server cục bộ chỉ chấp nhận kết nối từ máy của chính bạn. Image đặt `HOST=0.0.0.0` để server lắng nghe trên network interface của chính task, nơi security group của task quyết định ai có thể kết nối.

Kiểm tra rằng server đang hoạt động với health route của nó, trả về status 200 và `{"status":"ok"}`:

```bash
curl http://localhost:2022/health
```
</OptionFilter>

Điều này sẽ tự động reload khi bạn thực hiện thay đổi đối với API của mình.

## Gọi API tRPC của bạn

Bạn có thể tạo một tRPC client để gọi API của mình theo cách an toàn kiểu. Nếu bạn đang gọi API tRPC của mình từ một backend khác, bạn có thể sử dụng client trong `src/client/index.ts`, ví dụ:

```ts
import { createMyApiClient } from '@my-scope/my-api';

const client = createMyApiClient({ url: 'https://my-api-url.example.com/' });

await client.echo.query({ message: 'Hello world!' });
```

Nếu bạn đang gọi API của mình từ một website React, hãy xem xét sử dụng generator <Link path="guides/connection/react-trpc">Connection</Link> để cấu hình client.
