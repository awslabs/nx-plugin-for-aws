Generator này thêm một dịch vụ HTTP được đóng gói container vào dự án TypeScript hiện có. Bạn sẽ có một HTTP server nhỏ với route `GET /health` và route mẫu `GET /hello`, một Dockerfile, và các target để chạy server cục bộ, build image và quét image. Bạn cũng nhận được mã CDK hoặc Terraform chạy image trên [Amazon Elastic Container Service (Amazon ECS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html), dịch vụ AWS chạy và mở rộng quy mô container.

## Cách Hoạt Động

Dịch vụ chạy trên [AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), chạy mỗi container mà không cần server để bạn quản lý. Mỗi bản sao đang chạy của container của bạn là một ECS task. Các task chạy trong VPC của riêng bạn (virtual private cloud, một mạng cô lập trong tài khoản AWS của bạn). Một security group (một tập hợp các quy tắc tường lửa được gắn vào các task) kiểm soát lưu lượng mạng nào có thể đến và rời khỏi chúng.

Dịch vụ là riêng tư. Nó không có load balancer, không có API và không có địa chỉ IP công khai. Security group của nó không có quy tắc inbound, vì vậy không có gì có thể mở kết nối đến dịch vụ cho đến khi bạn cho phép một người gọi. Dịch vụ vẫn có thể thực hiện các cuộc gọi outbound, ví dụ đến database hoặc các dịch vụ AWS khác.

## Đầu ra của Generator

<FileTree>
  - your-project/
    - src/
      - service/ (hoặc tên bạn đã chọn)
        - server.ts HTTP routes: `GET /health` và route mẫu `GET /hello`
        - index.ts Entry point đọc `PORT` và khởi động server. Bundle và target `<name>-serve` bắt đầu từ file này

## Chạy Dịch vụ của Bạn Cục bộ

Target `<name>-serve` chạy server trên máy của bạn, không có container:

<NxCommands commands={['run your-project:service-serve']} />

Server lắng nghe trên cổng trong biến môi trường `PORT`. Target `<name>-serve` đặt nó thành một cổng mà generator chỉ định, bắt đầu từ 8081 và bỏ qua các cổng mà các dự án khác trong workspace của bạn đã sử dụng. Bên trong container, server lắng nghe trên cổng 8080.

Server lắng nghe trên địa chỉ trong biến môi trường `HOST`, mặc định là `127.0.0.1`, vì vậy target `<name>-serve` chỉ chấp nhận kết nối từ máy của chính bạn. Image đặt `HOST=0.0.0.0`, vì vậy bên trong một task, server lắng nghe trên giao diện mạng của chính task đó. Security group của task vẫn quyết định ai có thể kết nối.

Kiểm tra xem server đã hoạt động chưa với health route của nó, trả về status 200 và `{"status":"ok"}`:

```bash
curl http://localhost:<port>/health
```

Server cũng có một route mẫu mà bạn thay thế bằng các route của riêng bạn. `GET /hello?name=<x>` trả về `{"message":"Hello, <x>!"}`, và `name` mặc định là `world`. Bất kỳ đường dẫn nào khác trả về status 404.

## Build và Quét Image

Target `<name>-docker` build một linux/arm64 image của dịch vụ của bạn. Nó chạy target `bundle` trước, vì vậy image chứa server đã được bundle. Sau đó nó sao chép `Dockerfile` và `.dockerignore` vào thư mục đầu ra bundle, `dist/<project root>/bundle/container/<name>`, và build image với thư mục đó làm build context (các file mà image build có thể đọc). Nó sử dụng container engine mà workspace của bạn được thiết lập, `docker` hoặc [Finch](https://runfinch.com/). Target chạy như một phần của target tổng hợp `docker`, build mọi image trong dự án.

<NxCommands commands={['run your-project:service-docker']} />

Trên ECS, một lệnh health check chạy bên trong container và gọi `GET /health` trên container port. Nó không cần quyền truy cập inbound. ECS thay thế một task mà health check của nó liên tục thất bại. ECS bỏ qua chỉ thị `HEALTHCHECK` trong Dockerfile. Để biết thêm về cách image được build và xuất bản, xem <Link path="/guides/docker-bundling">Docker Bundling</Link>.

## Triển khai Dịch vụ của Bạn

### Thêm Dịch vụ vào Infrastructure của Bạn

Construct và module không bao giờ tạo VPC. Bạn tạo hoặc import một VPC trong stack hoặc root module của bạn và truyền nó vào. Các task chạy trong private subnet với egress, tiếp cận các dịch vụ AWS thông qua NAT gateway (một gateway được quản lý cho phép private subnet thực hiện kết nối outbound) hoặc thông qua VPC endpoint (kết nối riêng tư từ VPC của bạn đến các dịch vụ AWS).

<Infrastructure>
<Fragment slot="cdk">
CDK construct được tạo trong `common/constructs` và được đặt tên theo dịch vụ của bạn. Ví dụ sử dụng với VPC mới:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyService } from '@my-scope/common-constructs';
import { Stack, StackProps } from 'aws-cdk-lib';
import { SubnetType, Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ApplicationStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    new MyService(this, 'MyService', {
      vpc,
      vpcSubnets: { subnetType: SubnetType.PRIVATE_WITH_EGRESS },
    });
  }
}
```

Để sử dụng VPC hiện có, tra cứu nó với `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` và truyền nó làm `vpc`.
</Fragment>
<Fragment slot="terraform">
Terraform module được tạo trong `common/terraform`. Image của dịch vụ được xuất bản vào shared asset repository, vì vậy hãy khởi tạo module `core/asset-ecr` một lần cho mỗi deployment và truyền đầu ra của nó cho mọi service module. Cũng truyền đầu ra của shared `runtime_config_appconfig` module, chứa ứng dụng AWS AppConfig mà dịch vụ đọc <Link path="/guides/runtime-config">runtime configuration</Link> của nó từ đó:

```hcl title="packages/infra/src/main.tf"
module "asset_ecr" {
  source = "../../common/terraform/src/core/asset-ecr"
}

module "my_service" {
  source = "../../common/terraform/src/app/services/my-service"

  vpc_id     = aws_vpc.main.id
  subnet_ids = aws_subnet.private[*].id

  asset_ecr_repository_url = module.asset_ecr.repository_url
  asset_ecr_repository_arn = module.asset_ecr.repository_arn

  appconfig_application_id  = module.runtime_config_appconfig.application_id
  appconfig_application_arn = module.runtime_config_appconfig.application_arn
}
```

### Chạy Không có NAT Gateway

Khi các task của bạn khởi động, ECS pull image và gửi log thay mặt cho chúng. Mã server của bạn cũng có thể gọi các dịch vụ AWS. Trong private subnet không có NAT gateway, mỗi lệnh gọi này cần một VPC endpoint. Không có endpoint phù hợp, các task sẽ không khởi động được hoặc timeout khi chúng gọi AWS.

Tạo các endpoint này trong VPC, thay thế `<region>` bằng AWS Region của bạn:

| Endpoint | Loại | Cái gì sử dụng nó |
| --- | --- | --- |
| `com.amazonaws.<region>.ecr.api` | Interface | ECS, để xác thực với Amazon ECR và tra cứu image |
| `com.amazonaws.<region>.ecr.dkr` | Interface | ECS, để pull image từ Amazon ECR |
| `com.amazonaws.<region>.s3` | Gateway | ECS, để tải xuống các image layer, mà Amazon ECR lưu trữ trong Amazon S3 |
| `com.amazonaws.<region>.logs` | Interface | Đầu ra log của container, được gửi đến Amazon CloudWatch Logs |
| `com.amazonaws.<region>.secretsmanager` | Interface | ECS, để đọc các secret bạn truyền vào container khi một task khởi động |
| `com.amazonaws.<region>.appconfigdata` | Interface | Mã của bạn, để đọc <Link path="/guides/runtime-config">runtime configuration</Link> từ AWS AppConfig |
| `com.amazonaws.<region>.sts` | Interface | Mã của bạn, khi nó yêu cầu temporary credential từ AWS STS (ví dụ để assume một role khác) |

Interface endpoint cần một security group cho phép HTTPS (cổng 443) từ các task. Để biết chi tiết về các Amazon ECR endpoint, xem [Amazon ECR interface VPC endpoints](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html).

### Mặc định Bảo mật

Infrastructure được tạo áp dụng các cài đặt này theo mặc định:

- Security group của dịch vụ không có quy tắc inbound. Không có người gọi nào bên trong hoặc bên ngoài VPC có thể kết nối đến các task cho đến khi bạn thêm một quy tắc.
- Các task chạy trong private subnet và không bao giờ nhận địa chỉ IP công khai.
- Generator không tạo load balancer và không có API phía trước dịch vụ.
- Các task chỉ có thể gửi outbound traffic trên cổng 443. Kết nối đến database thêm database port.
- Task role (role mà mã server của bạn chạy với) chỉ có thể đọc runtime configuration từ AWS AppConfig cho đến khi bạn hoặc một kết nối cấp thêm.
- Execution role (role mà ECS sử dụng để khởi động task của bạn) chỉ có thể pull image của dịch vụ, ghi vào log group của nó và đọc các secret bạn liệt kê.
- Các secret chỉ đến container dưới dạng tham chiếu đến AWS Secrets Manager hoặc AWS Systems Manager Parameter Store, không bao giờ là giá trị môi trường thuần túy.
- Container có hệ thống file gốc chỉ đọc với thư mục `/tmp` có thể ghi, và chạy với uid 1000, một người dùng không phải root. ECS Exec (truy cập shell vào một task đang chạy) bị tắt.
- Một deployment thất bại health check sẽ dừng và rollback về phiên bản trước đó.
- Log group được mã hóa bằng AWS KMS key, và log được giữ trong một năm.

### Cho phép Người gọi Truy cập Dịch vụ của Bạn

Không có gì có thể gọi dịch vụ như được tạo. Nếu một workload khác trong VPC cần gọi nó, ví dụ như một Lambda function hoặc một ECS service khác, bạn tự thêm một quy tắc inbound vào security group của dịch vụ. Generator không thêm quy tắc inbound nào. Cho phép một người gọi được đặt tên theo security group của họ, trên container port, và không bao giờ cho phép một dải địa chỉ.

<Infrastructure>
<Fragment slot="cdk">
Construct triển khai `IConnectable`, vì vậy cho phép security group của người gọi thông qua `connections` của nó:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { Port } from 'aws-cdk-lib/aws-ec2';

const svc = new MyService(this, 'MyService', { vpc });
svc.connections.allowFrom(callerSecurityGroup, Port.tcp(8080));
```

Nếu security group của người gọi được định nghĩa trong CDK app của bạn và giới hạn outbound traffic, `allowFrom` cũng thêm quy tắc outbound tương ứng vào nó.
</Fragment>
<Fragment slot="terraform">
Thêm một quy tắc inbound vào security group của dịch vụ, mà module của dịch vụ của bạn xuất ra dưới dạng `security_group_id`, với security group của người gọi làm nguồn:

```hcl title="packages/infra/src/main.tf"
resource "aws_vpc_security_group_ingress_rule" "caller_to_my_service" {
  security_group_id            = module.my_service.security_group_id
  referenced_security_group_id = aws_security_group.caller.id
  from_port                    = 8080
  to_port                      = 8080
  ip_protocol                  = "tcp"
}
```

Nếu security group của người gọi giới hạn outbound traffic, cũng thêm một `aws_vpc_security_group_egress_rule` trên group của người gọi đến security group của dịch vụ.
</Fragment>
</Infrastructure>

Người gọi kết nối đến địa chỉ IP riêng tư của một task. Generator không thiết lập service discovery, và địa chỉ của một task thay đổi khi ECS thay thế task. Để cung cấp cho người gọi một tên ổn định, hãy tự thiết lập service discovery, ví dụ với [Amazon ECS Service Connect](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect.html).

### Cấu hình Nâng cao

Dịch vụ được tạo đặt tên và image của nó cho bạn. Các ví dụ dưới đây sử dụng construct `EcsService` generic và module `ecs-service` trực tiếp, cho các cài đặt mà dịch vụ được tạo không truyền.

Trong CDK, package `common-constructs` của bạn xuất `EcsService` bên cạnh construct của dịch vụ của bạn, vì vậy bạn import nó theo cùng một cách: `import { EcsService } from '@my-scope/common-constructs'`. Construct được tạo mở rộng `EcsService` và truyền mọi prop khác qua, ví dụ `cluster`, `environment`, `secrets` và `grantTaskRole`. Prop `image` tùy chọn của nó thay thế image được build từ dự án của bạn.

Trong Terraform, module của dịch vụ của bạn chỉ cho phép bạn đặt một số biến của module `ecs-service`: `vpc_id`, `subnet_ids`, `cluster_arn`, `environment`, `secrets`, `task_role_policy_statements` và `tags`. Để đặt bất kỳ biến nào khác, hãy chỉnh sửa block `module "ecs_service"` trong module của dịch vụ của bạn.

#### Image Được Build Sẵn

Để chạy một image đã được build, ví dụ từ registry công khai, hãy truyền URI của nó. Không có gì được build cục bộ. Đối với image trong Amazon ECR repository riêng tư, CDK cấp quyền pull access cho execution role trên repository đó. Terraform chỉ cấp quyền pull access khi bạn cũng truyền ARN của repository dưới dạng `image_repository_arn`.

```ts
new EcsService(this, 'Prebuilt', {
  serviceName: 'Prebuilt',

  image: { imageUri: 'public.ecr.aws/my-org/my-image@sha256:<digest>' },
});
```

</Fragment>
<Fragment slot="terraform">

```hcl

  source = "../../common/terraform/src/core/container/ecs-service"
```

#### Biến Môi trường và Secret

Cài đặt thuần túy đi vào `environment`. Không bao giờ đặt giá trị secret ở đó, vì bất kỳ ai có thể đọc task definition đều có thể đọc chúng. Thay vào đó, hãy truyền secret dưới dạng tham chiếu. Execution role chỉ có thể đọc các secret bạn liệt kê.

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'MyService', {
  // ...
  environment: { LOG_LEVEL: 'info' },
  secrets: { API_KEY: Secret.fromSecretsManager(apiKeySecret) },
});
```

</Fragment>
<Fragment slot="terraform">

```hcl
environment = { LOG_LEVEL = "info" }
secrets     = { API_KEY = aws_secretsmanager_secret.api_key.arn }
```

</Fragment>
</Infrastructure>

#### Kích thước và Mở rộng

Mỗi task nhận 256 CPU unit (một phần tư vCPU) và 512 MiB bộ nhớ theo mặc định. Dịch vụ khởi động một task, và autoscaling giữ từ một đến hai task đang chạy, thêm task khi mức sử dụng CPU trung bình vượt quá 70%.

| Cài đặt | CDK prop | Terraform variable | Mặc định |
| --- | --- | --- | --- |
| CPU unit mỗi task | `cpu` | `cpu` | 256 |
| Bộ nhớ mỗi task (MiB) | `memoryLimitMiB` | `memory` | 512 |
| Task khi khởi động | `desiredCount` | `desired_count` | 1 |
| Ít task nhất | `minCapacity` | `min_capacity` | 1 |
| Nhiều task nhất | `maxCapacity` | `max_capacity` | 2 |
| CPU trung bình mục tiêu (%) | `targetCpuUtilizationPercent` | `target_cpu_utilization` | 70 |

#### Quyền Task Role

Task role của construct hoặc module dịch vụ của bạn bắt đầu chỉ với quyền đọc runtime configuration. Thêm các quyền mà mã của bạn cần:

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'MyService', {
  // ...
  grantTaskRole: (taskRole) => myTable.grantReadData(taskRole),
});
```

</Fragment>
<Fragment slot="terraform">

```hcl
task_role_policy_statements = [{
  Effect   = "Allow"
  Action   = ["dynamodb:GetItem", "dynamodb:Query"]
  Resource = [aws_dynamodb_table.my_table.arn]
}]
```

</Fragment>
</Infrastructure>

#### Container User

Task definition chạy container với uid 1000, một người dùng không phải root. Điều này khớp với user `node` mà Dockerfile được cung cấp đặt. Để chạy với user khác, hãy đặt CDK prop `user` hoặc Terraform variable `container_user`. Terraform từ chối `0` và `root`.

| Cài đặt | CDK prop | Terraform variable | Mặc định |
| --- | --- | --- | --- |
| User mà container chạy với | `user` | `container_user` | `'1000'` (CDK), `"1000:1000"` (Terraform) |

Trong Terraform, `container_user` là một biến của module `ecs-service`. Module của dịch vụ của bạn không truyền nó, vì vậy hãy đặt nó trong block `module "ecs_service"` của nó.

### Chi phí

Container service tính phí khi nó nhàn rỗi, không giống như Lambda function. Các phần này tính phí theo giờ cho dù có ai gọi dịch vụ hay không:

- Fargate task, mỗi vCPU và mỗi GB bộ nhớ. `desiredCount` và `minCapacity` giữ ít nhất một task đang chạy.
- Interface VPC endpoint, mỗi giờ trong mỗi Availability Zone, hoặc NAT gateway, mỗi giờ và mỗi GB dữ liệu nó xử lý.
- Lưu trữ log trong CloudWatch Logs, và lưu trữ image trong Amazon ECR.

Để ước tính chi phí cho Region và traffic của bạn, hãy sử dụng [AWS Pricing Calculator](https://calculator.aws/).

### Hủy Dịch vụ của Bạn

Để xóa dịch vụ, hãy hủy stack hoặc cấu hình Terraform chứa nó:

<Infrastructure>
<Fragment slot="cdk">
Chạy target `destroy` của dự án infrastructure của bạn, chạy `cdk destroy`:

<NxCommands commands={['run infra:destroy']} />
</Fragment>
<Fragment slot="terraform">
Chạy target `destroy` của dự án infrastructure của bạn:

<NxCommands commands={['run infra:destroy']} />
</Fragment>
</Infrastructure>

Sau đó kiểm tra trong AWS console hoặc với AWS CLI rằng ECS service và cluster đã biến mất. Với Terraform, destroy cũng xóa log group của dịch vụ và lên lịch xóa AWS KMS key của nó sau 7 ngày. Với CDK, destroy giữ log group của dịch vụ và AWS KMS key của nó, vì CDK giữ log group và key trừ khi removal policy nói khác. Tự xóa chúng nếu bạn không còn cần log nữa. Các image vẫn ở trong Amazon ECR, trong CDK assets repository hoặc shared `asset-ecr` repository. Xóa chúng nếu bạn không còn cần chúng nữa. VPC là của bạn, vì vậy việc hủy dịch vụ sẽ để nó nguyên vị trí.
