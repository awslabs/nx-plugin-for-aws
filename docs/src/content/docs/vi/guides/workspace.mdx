## Nx

Nx là một hệ thống build không phụ thuộc ngôn ngữ cho monorepo, quản lý các phụ thuộc giữa các dự án được viết bằng bất kỳ ngôn ngữ lập trình nào và các tác vụ để xây dựng chúng. Bạn có thể tìm hiểu thêm trên [trang web Nx](https://nx.dev/getting-started/intro).

### Projects

Một Nx monorepo được tạo thành từ một hoặc nhiều project, mỗi project có một file `project.json`. File `project.json` định nghĩa các tác vụ của project, được gọi là _target_, xác định cách một project được xây dựng, chạy cục bộ, kiểm thử, v.v. Nó cũng định nghĩa các phụ thuộc giữa các target trong hoặc giữa các project.

Ví dụ, một `project.json` có thể định nghĩa một `build` target phụ thuộc vào tất cả các project upstream được xây dựng trước:

```json title="packages/my-project/project.json"
{
  "name": "@my-workspace/my-project",
  "targets": {
    "build": {
      "executor": "@nx/js:tsc",
      "dependsOn": ["^build"]
    },
    "test": {
      "command": "vitest run"
    }
  }
}
```

:::tip
Đối với các project bằng ngôn ngữ không được Nx Plugin for AWS hỗ trợ trực tiếp, bạn thường có thể tìm thấy một generator trong [Nx Plugin Registry](https://nx.dev/plugin-registry) để hỗ trợ. Tuy nhiên, việc thêm một project bằng bất kỳ ngôn ngữ nào vào monorepo của bạn rất đơn giản — chỉ cần thêm một file `project.json` và định nghĩa `build` target của nó để chạy lệnh build cụ thể cho một project của ngôn ngữ đó.
:::

Để biết chi tiết về cách các project TypeScript và Python được thiết lập, hãy tham khảo hướng dẫn generator <Link path="guides/typescript-project">ts#project</Link> và <Link path="guides/python-project">py#project</Link>.

### Caching

Nx lưu cache đầu ra của các target đã thực thi trước đó và phát lại chúng khi các đầu vào không thay đổi. Điều này tăng tốc đáng kể quá trình build, test và linting — đặc biệt trong CI. Nếu bạn gặp phải hành vi cũ hoặc không mong đợi, hãy đặt lại cache bằng:

<NxCommands commands={['reset']} />

Để biết thêm chi tiết, xem [tài liệu caching của Nx](https://nx.dev/features/cache-task-results).

### Parallelism

Các workspace mới đặt `parallel` trong `nx.json`, điều khiển số lượng tác vụ mà Nx chạy đồng thời:

```json title="nx.json"
{
  "parallel": 8
}
```

Giảm nó xuống nếu bạn đang build trên một máy có ít core hơn hoặc bộ nhớ hạn chế:

```json title="nx.json"
{
  "parallel": 3
}
```

Bạn cũng có thể ghi đè nó cho mỗi lần gọi:

<NxCommands commands={['run-many --target build --parallel=4']} />

## Single Version Policy

Thiết lập monorepo mặc định sử dụng [single version policy](https://nx.dev/concepts/decisions/dependency-management#single-version-policy) cho cả các project dựa trên Node và Python.

Điều này có nghĩa là tất cả các project trong monorepo của bạn sử dụng cùng một phiên bản của các dependency theo mặc định, giảm các vấn đề liên quan đến các package trong cùng một monorepo gặp phải vấn đề không khớp phiên bản.

Từ góc độ Node, điều này có nghĩa là một lockfile duy nhất ở root, với các dependency được cài đặt một lần và liên kết vào mỗi project. Mỗi project Node khai báo các runtime dependency mà source code của nó import trong `package.json` riêng của nó, trong khi các công cụ build/test dùng chung nằm trong `devDependencies` của `package.json` ở root. Thêm một runtime dependency của project bằng cách cài đặt nó vào project đó:

<InstallCommand pkg="some-npm-package" project="@my-scope/my-project" />

Đối với các package manager có hỗ trợ catalog ([pnpm](https://pnpm.io/catalogs), [yarn](https://yarnpkg.com/features/catalogs) và [bun](https://bun.com/docs/install/catalogs)), các phiên bản dependency được ghi lại trong catalog và tham chiếu bằng protocol `catalog:`, giữ một nguồn chân lý duy nhất cho các phiên bản trên mọi `package.json` của mỗi project. Đối với npm workspaces, chúng tôi khuyên dùng [syncpack](https://github.com/JamieMason/syncpack) để căn chỉnh các phiên bản được khai báo trên nhiều file `package.json`.

Từ góc độ Python, điều này có nghĩa là một `.venv` duy nhất ở root của monorepo với tất cả các dependency được cài đặt vào đó. Mỗi project Python có `pyproject.toml` riêng của nó, nhưng các phiên bản của những dependency đó được quản lý bởi UV workspace và sau đó được ghi ra file `uv.lock` ở root.

## Những Gì Được Bao Gồm

### Linting

Các workspace mới được cấu hình với [Biome](https://biomejs.dev/) cho phân tích tĩnh và định dạng code. Chạy `lint` kiểm tra tất cả các project để tìm vấn đề, và `lint --configuration=fix` tự động sửa chúng.

### Git Secrets

Các workspace được thiết lập với các pre-commit hook của [git-secrets](https://github.com/awslabs/git-secrets) quét các file được staged để tìm các mẫu credential của AWS trước mỗi commit. Điều này ngăn chặn việc vô tình commit các access key, secret key và các giá trị nhạy cảm khác.

Script được vendored vào workspace tại `.git-secrets/git-secrets` và chạy bởi hook `.husky/pre-commit`, vì vậy không có gì cần cài đặt — nhưng nó không có trong `PATH` của bạn, vì vậy hãy gọi nó bằng đường dẫn thay vì dùng `git secrets`.

#### Loại Bỏ False Positive

Các mẫu trong git-secrets sử dụng [biểu thức chính quy tương thích egrep](https://github.com/awslabs/git-secrets#options-for-add). Nếu git-secrets chặn một commit không chứa credential thực:

```sh
# Allow a specific regex pattern (-a is the allowed flag)
bash .git-secrets/git-secrets --add -a -- 'my-regex-pattern'

# Allow a literal string, escaping special characters (-l is the literal flag)
bash .git-secrets/git-secrets --add -a -l -- 'my-literal+string'

# List what is currently allowed
git config --get-all secrets.allowed
```

Những cấu hình này được ghi lại trong git config cục bộ của bạn, vì vậy chúng chỉ áp dụng cho bản clone của riêng bạn. Để chia sẻ một suppression với nhóm của bạn, hãy thêm nó vào file `.gitallowed` ở root của repository — một regex tương thích egrep trên mỗi dòng, được khớp với `<path>:<line-number>:<line-contents>`:

```text title=".gitallowed"
# Allow test fixtures
tests/fixtures/.*
# Allow a specific string
EXAMPLE[A-Z]{16}
```

Để biết đầy đủ chi tiết về quản lý các mẫu, xem [tài liệu git-secrets](https://github.com/awslabs/git-secrets#readme).

## Cấu hình Nx Plugin for AWS

Workspace đi kèm với một file `aws-nx-plugin.config.mts` ở root. Các generator đọc file này để chọn các giá trị mặc định hợp lý để bạn không phải truyền cùng các flag mỗi lần:

```typescript
// aws-nx-plugin.config.mts
import { AwsNxPluginConfig } from '@aws/nx-plugin';

export default {
  iac: {
    provider: 'cdk', // or 'terraform'
  },
  containers: {
    engine: 'docker', // or 'finch'
  },
  packageManager: {
    catalogs: true, // or false
  },
} satisfies AwsNxPluginConfig;
```

- **`iac.provider`** — infrastructure-as-code provider mặc định (`cdk` hoặc `terraform`) được sử dụng bởi các generator phát ra infrastructure (ví dụ: `ts#infra`, `ts#api`, `py#api`). Các generator chấp nhận flag `--iac` mặc định là `inherit`, đọc giá trị này.
- **`containers.engine`** — container CLI (`docker` hoặc `finch`) được tích hợp vào các lệnh build/push/login được tạo ra. Các CDK image-asset build cũng nhận điều này thông qua biến môi trường `CDK_DOCKER`. Xem <Link path="guides/docker-bundling">hướng dẫn Docker bundling</Link> để biết chi tiết.
- **`packageManager.catalogs`** — liệu các generator có ghi lại các phiên bản dependency trong catalog của package manager và tham chiếu chúng bằng protocol `catalog:` hay không (xem [Single Version Policy](#single-version-policy)). Đặt nó thành `false` để các generator ghi trực tiếp các version range vào `package.json` của mỗi project. Nó không có hiệu lực với npm, vốn không có catalog.

<Link path="guides/license">License generator</Link> thêm một key `license` vào cùng file này để cấu hình hành vi của chính nó.

Bạn có thể chỉnh sửa bất kỳ cài đặt nào bất cứ lúc nào — các lần chạy generator tiếp theo sẽ nhận giá trị mới.
