<Link path="guides/react-website-auth">ウェブサイト認証</Link>はAmazon Cognitoユーザープールを作成し、デフォルトではそのプールにユーザー名とパスワードを持つユーザーのみがサインインできます。スタッフや顧客がOkta、Auth0、Microsoft Entra IDなどのアイデンティティプロバイダー（IdP）に既にアカウントを持っている場合、ウェブサイト専用の2つ目のアカウントが必要になってしまいます。

`ts#website#auth`を`--federation=oidc`で実行すると、外部の[OpenID Connect](https://openid.net/developers/how-connect-works/)（OIDC）アイデンティティプロバイダーをユーザープールに追加できます。アイデンティティプロバイダーをインフラストラクチャコードにリストします：CDKでは`UserIdentity`の`oidcIdentityProviders`プロパティ、Terraformでは`user_identity`モジュールの`oidc_identity_providers`変数です。サインインページには、ユーザー名とパスワードフォームの横に各アイデンティティプロバイダー用のボタンが表示されるようになります。

## 仕組み

- ウェブサイトは引き続きユーザーをCognitoサインインページに送信します。このページには、各アイデンティティプロバイダーにちなんだ名前のボタンが表示されます。
- ボタンを選択したユーザーは、そのアイデンティティプロバイダーでサインインします。アイデンティティプロバイダーは、リダイレクトURI `https://<cognito domain>/oauth2/idpresponse` でユーザーをCognitoに送り返します。
- Cognitoは、ユーザープールにフェデレーテッドユーザーとしてユーザーを作成し、マッピングしたクレーム（例：`email`）をユーザーの属性にコピーします。
- その後、Cognitoはローカルユーザーに発行するのと同じ種類のトークンを発行します。API、エージェント、アイデンティティプールは、変更なしでそれらを受け入れます。

プールにユーザー名とパスワードを持つユーザーは、引き続きサインインできます。

## サインインできるユーザー

アイデンティティプロバイダーを追加すると、予想よりも多くの人がウェブサイトにアクセスできるようになる可能性があります。`ts#website#auth`の`allowSignup`オプションは、フェデレーテッドユーザーには適用されません。Cognitoは、ユーザープールがユーザーの自己サインアップを許可していない場合でも、誰かがアイデンティティプロバイダーを通じて初めてサインインしたときにフェデレーテッドユーザーを作成します。各フェデレーテッドユーザーは、アイデンティティプールの認証済みロールも取得するため、サインインしたユーザーと同様にAPIやエージェントを呼び出すことができます。

アイデンティティプロバイダーは、ユーザープール全体に適用されます。プールを使用するすべてのウェブサイトで、それらのボタンが表示され、ユーザーが受け入れられます。

したがって、アイデンティティプロバイダーがサインインできるユーザーを決定します。ウェブサイトを必要とする人だけがサインインできるように設定してください：

- Microsoft Entra ID：アプリケーションのエンタープライズアプリケーションプロパティで、「割り当てが必要ですか？」を「はい」に設定し、アクセスが必要なユーザーまたはグループのみを割り当てます。デフォルトの「いいえ」では、テナント内のすべてのユーザーがサインインできます。
- Okta：アクセスが必要なグループにのみアプリケーションを割り当てます。
- Auth0：アプリケーションが使用する各接続でサインアップを無効にし、ユーザーがアクセスを必要とする接続のみをアプリケーションに対して有効にします。そうしないと、有効な接続（例：ソーシャル接続）を通じてサインアップした人は誰でもサインインできます。

## 使用方法

### OpenID Connectフェデレーションの追加

<Link path="guides/react-website-auth">`ts#website#auth`</Link>ジェネレーターを`--federation=oidc`で実行します。まだ認証がないウェブサイトでも、既に認証があるウェブサイトでも実行できます。どちらも同じ結果になります。

<RunGenerator generator="ts#website#auth" requiredParameters={{ federation: 'oidc' }} />

ジェネレーターはアイデンティティプロバイダーを追加しません。リストは空で開始されるため、エントリを追加するまでサインインは以前と同じように機能します。アイデンティティプロバイダーはインフラストラクチャコードに追加するため、2つ目を追加するのに別のジェネレーター実行は必要ありません。

`--federation=oidc`でジェネレーターを再度実行してもファイルは変更されません。`--federation=none`で実行するか、`--federation`なしで実行すると、既に存在するフェデレーションが保持されます。

### アイデンティティプロバイダーの追加

各アイデンティティプロバイダーに対してエントリを追加し、デプロイします。クライアントシークレットはコードに含まれません。[アイデンティティプロバイダーの設定](#set-up-your-identity-provider)で説明されているように、AWS Secrets Managerに保存してその名前を指定します。

### オプション

リスト内の各アイデンティティプロバイダーには、これらのプロパティがあります。ジェネレーターオプションは<Link path="guides/react-website-auth">ウェブサイト認証</Link>で説明されています。

| CDK prop | Terraform attribute | Required | Default | Description |
|---|---|---|---|---|
| `name` | `name` | Yes | | サインインボタンに表示されます。Cognitoは小文字でフェデレーテッドユーザー名にプレフィックスを付けます（`<name>_<sub>`）。3-32文字の英字、数字、ハイフンで、英字で始まります。`COGNITO`は不可。リスト内で大文字小文字を無視して一意。CDKではトークンではなくリテラル文字列である必要があります。 |
| `issuerUrl` | `issuer_url` | Yes | | アイデンティティプロバイダーのトークンの`iss`クレームに表示される通りの発行者。`https://`を使用する必要があります。 |
| `clientId` | `client_id` | Yes | | アイデンティティプロバイダーに登録されたアプリケーションのクライアントID。 |
| `clientSecretName` | `client_secret_name` | Yes | | クライアントシークレットをプレーン文字列として保持するSecrets Managerシークレットの名前。ARNではなく名前。 |
| `scopes` | `scopes` | No | `openid`, `email`, `profile` | リクエストするOAuthスコープ。`openid`を含める必要があります。 |
| `attributeMapping` | `attribute_mapping` | No | `email`、`given_name`、`family_name`、それぞれ同じ名前のクレームに | ユーザープール属性からアイデンティティプロバイダークレームへのマッピング。[属性マッピング](#attribute-mapping)を参照してください。 |
| `identifiers` | `identifiers` | No | None | Cognitoがこのアイデンティティプロバイダーにユーザーを送信するために使用できる、メールドメインなどの識別子。 |

### 検証

ベンドされたコードは、何かがデプロイされる前に各エントリをチェックします：

  <Fragment slot="cdk">
`UserIdentity`は、ルールを破るエントリで作成されると例外をスローするため、`cdk synth`が失敗します。infraプロジェクトのビルドは`cdk synth`を実行します。メッセージはエントリに名前を付けます。例：`UserIdentity: oidcIdentityProviders[1] (Entra): Microsoft Entra ID issuers have no trailing slash. Use https://login.microsoftonline.com/<tenant-id>/v2.0`。

  </Fragment>
  <Fragment slot="terraform">
モジュールの`oidc_identity_providers`変数には、各ルールに対して1つの`validation`ブロックがあります。そのエラーメッセージは、ルールを破るエントリに名前を付けません。

`user_identity`モジュールブロックにリストをリテラルとして記述すると、`terraform validate`がチェックします。プロジェクトの`validate`ターゲットは`terraform validate`を実行します。上記の`.tfvars`パターンのようにリストがルート変数から来る場合、代わりに`terraform plan`がチェックします。
  </Fragment>
</Infrastructure>

ルール：

- `name`：3-32文字の英字、数字、ハイフンで、英字で始まります。Cognitoがユーザープール自体でのサインイン用に予約しているため、大文字小文字に関係なく`COGNITO`は不可。
- Cognitoがフェデレーテッドユーザー名に小文字の名前をプレフィックスとして付けるため、名前は大文字小文字を無視してリスト内で一意です。例えば、`Okta`と`OKTA`の両方をリストに含めることはできません。`test-idp`と`testidp`は、プレフィックスが異なるため可能です。
- 発行者は`https://`を使用し、クエリ、フラグメント、ユーザー名、パスワード、空白を含みません。CDKではURLとして解析できる必要もあります。Terraformでは正規表現でチェックされ、CDKが拒否するいくつかの不正な形式のURLを受け入れます。
- Microsoft Entra ID：マルチテナント発行者（`common`、`organizations`、`consumers`、`9188040d-6c67-4c5b-b112-36a304b66dad`）は拒否され、発行者はスラッシュで終わってはいけません。
- Auth0：`*.auth0.com`上の発行者はスラッシュで終わる必要があります。
- クライアントIDは空ではありません。
- シークレット名は1-512文字の英字、数字、`/ _ + = . @ -`です。これらはSecrets Managerの命名規則であるため、ARNは拒否されます。
- スコープには`openid`が含まれます。CDKでは、各スコープも空でなく、空白を含まない必要があります。
- 属性マッピングのキーと値は、[属性マッピング](#attribute-mapping)のルールに従います。
- 最大50個の識別子。各識別子は1-40文字の英字、数字、スペース、`_ + = . @ -`です。

## アイデンティティプロバイダーの設定

アイデンティティプロバイダーを追加するデプロイでは、Secrets Managerからクライアントシークレットを読み取ります。シークレットが存在しない場合、デプロイは失敗します。

<Infrastructure>
  <Fragment slot="cdk">
CloudFormationは、スタックの実行ロール（デフォルトでは`cdk-hnb659fds-cfn-exec-role-<account>-<region>`）でシークレットを読み取ります。そのロールには、シークレットに対する`secretsmanager:GetSecretValue`と、シークレットがカスタマー管理のAWS KMSキーで暗号化されている場合はキーに対する`kms:Decrypt`が必要です。
  </Fragment>
  <Fragment slot="terraform">
`terraform apply`を実行するアイデンティティがシークレットを読み取ります。シークレットに対する`secretsmanager:GetSecretValue`と、シークレットがカスタマー管理のAWS KMSキーで暗号化されている場合はキーに対する`kms:Decrypt`が必要です。
  </Fragment>
</Infrastructure>

この順序で次の手順に従ってください。ジェネレーターは、完了時にこれらも出力します。

1. `ts#website#auth`を`--federation=oidc`で実行し、一度デプロイします。
2. ユーザープールのリダイレクトURIを見つけます。プールのすべてのアイデンティティプロバイダーは同じものを使用します。

<Infrastructure>
  <Fragment slot="cdk">
`UserIdentity`を含むスタックには、`<id>OidcIdentityProvidersIdpRedirectUri`で始まるキーを持つ出力があります。ここで`<id>`は`UserIdentity`に与えたコンストラクトIDです。例：`IdentityOidcIdentityProvidersIdpRedirectUri`。デプロイ前に、`ts#website#auth`用に選択した`cognitoDomain`、AWSアカウントID、リージョンから計算することもできます：

```
https://<cognitoDomain>-<account>.auth.<region>.amazoncognito.com/oauth2/idpresponse
```
  </Fragment>
  <Fragment slot="terraform">
Cognitoドメインにはランダムなサフィックスがあるため、リダイレクトURIはデプロイ後にのみ判明します。`user_identity`モジュールは、それを`idp_redirect_uri`として出力します。それを確認するには、ルートモジュールに出力を追加します（例：`packages/infra/src/main.tf`）：

```hcl
output "idp_redirect_uri" { value = module.user_identity.idp_redirect_uri }
```
  </Fragment>
</Infrastructure>

3. そのリダイレクトURIでアイデンティティプロバイダーにアプリケーションを登録し、そのクライアントIDとクライアントシークレットをメモします。アイデンティティプロバイダーには、この`/oauth2/idpresponse` URIのみを登録してください。ウェブサイト自体のURLは、アイデンティティプロバイダーではなくCognitoに登録されます。
4. クライアントシークレットをSecrets Managerに保存します。コマンドライン引数としてではなく、ファイルで渡してください。引数はシェル履歴に残り、コマンドの実行中は同じコンピューターの他のユーザーがプロセスリストで確認できます：

   ```bash
   (
     umask 077
     d=$(mktemp -d) || exit
     trap 'rm -rf "$d"' EXIT
     trap 'exit 1' HUP INT TERM
     unset CLIENT_SECRET
     IFS= read -rs CLIENT_SECRET || exit 1
     printf '%s' "$CLIENT_SECRET" > "$d/secret" || exit 1
     unset CLIENT_SECRET
     aws secretsmanager create-secret --name okta-oidc-client-secret --secret-string "file://$d/secret" --region <region>
   )
   ```

   コマンドは括弧の間でサブシェルで実行されます。`read`はクライアントシークレットを貼り付けてEnterを押すのを待ち、表示しません。2つの`unset`コマンドは、以前に`CLIENT_SECRET`をエクスポートした場合でも、`aws`コマンドの環境からシークレットを除外します。`IFS=`と`-r`は、両端のスペースやバックスラッシュを含め、貼り付けた通りにシークレットを保持します。`mktemp -d`は、あなただけが開くことができる新しいディレクトリ（モード700）を作成し、`printf`は末尾に改行なしでシークレットを書き込みます。AWS CLIは`file://`の後に指定されたファイルから`--secret-string`の値を読み取り、変更せずに渡すため、ファイルの末尾の改行はシークレットの一部になります。サブシェルが終了すると、`trap`コマンドがディレクトリを削除します。`aws`コマンドが失敗した場合やCtrl-Cを押した場合も同様です。コマンドはbashとzsh（LinuxとmacOSのデフォルトシェル）で動作します。Windowsについては、[Mitigate the risks of using the AWS CLI to store your AWS Secrets Manager secrets](https://docs.aws.amazon.com/secretsmanager/latest/userguide/security_cli-exposure-risks.html)を参照してください。

   `--region`をスタックのリージョンに設定します。アイデンティティプロバイダーを追加するデプロイの前に、そのリージョンにシークレットが存在する必要があります。Cognitoはシークレット値全体をクライアントシークレットとして受け取るため、シークレットをJSONではなくプレーン文字列として保存してください。Secrets Managerコンソールでは、Key/valueではなくPlaintextを選択してください。

5. [アイデンティティプロバイダーの追加](#add-identity-providers)で示されているように、シークレットの名前を`clientSecretName`（Terraformでは`client_secret_name`）としてリストにアイデンティティプロバイダーを追加します。その後、デプロイします。

## 属性マッピング

生成されたユーザープールには、`email`、`given_name`、`family_name`属性が必要です。Cognitoは、サインインのたびにアイデンティティプロバイダーのクレームからこれらを入力します。アイデンティティプロバイダーがそれらのいずれかを送信しない場合、ユーザーの最初のサインインは失敗します。`UserIdentity`とTerraform変数は、3つのいずれかを省略した属性マッピングを拒否します。

`attributeMapping`（Terraformでは`attribute_mapping`）は、ユーザープール属性をクレームにマッピングします。各キーはユーザープール属性で、各値はアイデンティティプロバイダーのクレームの名前で、1-128文字の長さです。指定したマッピングはデフォルトを置き換えます。デフォルトでは、各必須属性を同じ名前のクレームにマッピングします：

<Infrastructure>
  <Fragment slot="cdk">
```ts
attributeMapping: { email: 'email', given_name: 'given_name', family_name: 'family_name' },
```
  </Fragment>
  <Fragment slot="terraform">
```hcl
attribute_mapping = { email = "email", given_name = "given_name", family_name = "family_name" }
```
  </Fragment>
</Infrastructure>

- キーは、`name`や`phone_number`などの[標準属性](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html#cognito-user-pools-standard-attributes)、`phone_number_verified`、または`custom:department`などのカスタム属性（`custom:`の後に最大20文字の英字、数字、アンダースコア）にすることができます。キーは、CDKとTerraformの両方でCognito属性名を使用します。`username`は拒否されます。
- Cognitoは、マッピングされたメールアドレスを未検証として扱います。メールアドレスを自身で検証するアイデンティティプロバイダーからのみ`email_verified`をマッピングしてください。そうしないと、ユーザーがアイデンティティプロバイダーで他人のアドレスを設定し、プールで検証済みとしてマークされる可能性があります。
- ユーザーのメールアドレスがアイデンティティプロバイダーで変更された場合、Cognitoはユーザーの次回サインイン時に新しいアドレスをユーザープールに書き込みます。`email_verified`は`false`のままです。
- カスタム属性は、ユーザープールに既に存在し、変更可能である必要があります。

Terraformアイデンティティプロバイダーリソース（`identity/oidc-identity-providers.tf`内）は、Cognitoがアイデンティティプロバイダーを返すときに追加する2つの値も設定します：`attribute_mapping`の`username = "sub"`と`provider_details`の`attributes_url_add_attributes = "false"`。ファイルがこれらを設定するため、最初のデプロイ後の2回目の`terraform plan`では、アイデンティティプロバイダーへの変更は表示されません。別のアイデンティティプロバイダーで2回目のプランが`provider_details`の変更を表示する場合は、プランがCognitoが返すことを示す値でそのキーをファイルに追加してください。

## アイデンティティプロバイダーに関する注意事項

以下の設定は、各ベンダーのドキュメントから取得したものです。OktaはCDKとTerraformの両方でAWSでテストされています。Auth0とMicrosoft Entra IDの設定は、各ベンダーが公開しているOpenIDディスカバリードキュメントに対して確認されましたが、実際のサインインではテストされていません。

### Okta

CDKとTerraformでAWSでテストされています。Oktaで、Authorization Codeグラントとクライアントシークレットを持つOIDC Web Applicationを作成します。サインインリダイレクトURIを、[アイデンティティプロバイダーの設定](#set-up-your-identity-provider)の手順2の`/oauth2/idpresponse`リダイレクトURIに設定します。サインアウトリダイレクトURIは不要です。発行者はOktaドメイン`https://<your-org>.okta.com`で、これがテストされた形式です。`https://<your-org>.okta.com/oauth2/default`などのカスタム認証サーバーにも発行者がありますが、その形式はテストされていません。デフォルトのスコープ`openid email profile`は、`email`、`given_name`、`family_name`を返すため、デフォルトのマッピングが機能します。各ユーザーには、Oktaでメール、名、姓が設定されている必要があります。アクセスが必要なユーザーまたはグループにのみアプリケーションを割り当ててください。

### Auth0

Auth0のディスカバリードキュメントに対して確認されましたが、実際のサインインではテストされていません。Auth0でRegular Web Applicationを作成します。発行者は`https://<your-tenant>.auth0.com/`で、末尾のスラッシュを含みます。

:::caution
Auth0トークンの`iss`クレームは末尾にスラッシュがあるため、スラッシュなしの発行者ではサインインが失敗します。ベンドされたコードは、`*.auth0.com`上のスラッシュなしの発行者を拒否します。Auth0カスタムドメインを認識できないため、使用する場合はスラッシュを自分で確認してください。
:::

Auth0は、ユーザーの接続が提供する場合にのみ`given_name`と`family_name`を返します。それらのない接続のユーザーは、他のクレームをマッピングするまでサインインできません。

### Microsoft Entra ID

Microsoftのディスカバリードキュメントに対して確認されましたが、実際のサインインではテストされていません。Entra IDでシングルテナントアプリケーションを登録します。発行者は`https://login.microsoftonline.com/<tenant-id>/v2.0`です。ベンドされたコードは、マルチテナント発行者（`common`、`organizations`、`consumers`）を拒否します。これらは任意のEntra IDテナントからのユーザーを受け入れるためです。また、任意の個人用Microsoftアカウントを受け入れるテナント`9188040d-6c67-4c5b-b112-36a304b66dad`も拒否します。

発行者は末尾にスラッシュを付けてはいけません：`/v2.0/`ではなく`/v2.0`を使用してください。Entra IDトークンの`iss`クレームにはスラッシュがないため、サインインは失敗します。ベンドされたコードは、スラッシュ付きの形式を拒否します。

アプリケーションのIDトークンにオプションのクレームとして`email`、`given_name`、`family_name`を追加します。Entra IDは、追加した場合にのみそれらを送信します。各ユーザーにはMailフィールドが設定されている必要があります。そうしないと、`email`クレームが空になり、ユーザープールが`email`を必要とするため、ユーザーの最初のサインインは失敗します。Entra IDの`email`クレームは検証されていないため、Entra IDから`email_verified`をマッピングしないでください。

### Cognito user pool

アイデンティティプロバイダーとして別のCognitoユーザープールでテストするには、発行者`https://cognito-idp.<region>.amazonaws.com/<user pool id>`を使用します。そのアプリクライアントに、クライアントシークレット、認証コードグラント、スコープ`openid email profile`を付与します。

## セキュリティ

- ユーザーを`sub`クレーム（ユーザープール内のユーザーの一意のID）で識別し、`email`では識別しないでください。フェデレーテッドユーザーは、メールがローカルユーザーと一致する場合でも、独自の`sub`を持つプール内の新しいユーザーです。プラグインが生成するコードは`sub`を使用します。
- シングルテナント発行者を使用してください。マルチテナント発行者は、任意の組織からのユーザーのサインインを許可します。
- <Link path="guides/react-website-auth">ウェブサイト認証</Link>で説明されているように、本番ステージから`http://localhost`コールバックURLを削除してください。フェデレーションはコールバックURLを追加しません。

## フェデレーションが行わないこと

- ユーザープールで必要なMFA（多要素認証）は、フェデレーテッドユーザーには適用されません。Cognitoは認証をアイデンティティプロバイダーに任せるため、アイデンティティプロバイダーでMFAを強制してください。
- ウェブサイトからサインアウトすると、Cognitoセッションのみが終了します。OIDCアイデンティティプロバイダーでのユーザーのセッションは終了しないため、ボタンを介した次回のサインインはパスワードなしで完了できます。共有コンピューターでは、ユーザーはアイデンティティプロバイダーでもサインアウトする必要があります。
- ユーザーメニューには、Cognitoユーザー名が表示されます。フェデレーテッドユーザーの場合、それはアイデンティティプロバイダー名、アンダースコア、アイデンティティプロバイダーでのユーザーの`sub`を小文字にしたものです（例：`okta_00u1abcd`）。
- アイデンティティプロバイダーでユーザーを削除または無効化しても、そのユーザーの次回のサインインのみが停止されます。Cognitoは独自のリフレッシュトークンでトークンを更新し、アイデンティティプロバイダーに問い合わせません。また、ウェブサイトはユーザーが気付かないうちにトークンを更新します。したがって、ユーザーはリフレッシュトークンが期限切れになるまで、最後のサインインから最大30日間アクセスを維持できます。ユーザーが新しいトークンを取得できないようにするには、すべてのセッションからサインアウトさせ、ユーザープールで無効化します。ユーザー名は`<identity provider name in lowercase>_<sub>`です：

  ```bash
  aws cognito-idp admin-user-global-sign-out --user-pool-id <user pool id> --username okta_<sub>
  aws cognito-idp admin-disable-user --user-pool-id <user pool id> --username okta_<sub>
  ```

  これはAWSでテストされています。`admin-user-global-sign-out`と`admin-disable-user`の後、アイデンティティプロバイダーは依然としてユーザーをサインインさせますが、Cognitoはそれらを拒否します。

  これらのコマンドは、ユーザーが既に持っているアクセスを終了しません。[`admin-user-global-sign-out`](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminUserGlobalSignOut.html)はユーザーのリフレッシュトークンを取り消すため、ウェブサイトはそれらの新しいトークンを取得できず、`admin-disable-user`は次回のサインインを停止します。Cognitoが既に発行したIDトークンとアクセストークンは、期限が切れるまで有効なままです。デフォルトでは、発行から1時間後です（[ID and access token validity](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_CreateUserPoolClient.html#CognitoUserPools-CreateUserPoolClient-request-IdTokenValidity)）。アイデンティティプールが既にウェブサイトに付与したAWS認証情報も、期限が切れるまで有効なままです。発行から1時間後です（[identity pools authentication flow](https://docs.aws.amazon.com/cognito/latest/developerguide/concepts.html#authentication-flow-enhanced)）。期限が切れるまで、ユーザーは引き続きウェブサイトとアイデンティティプールの認証済みロールを使用できます。

  これらのコマンドを実行しない場合、Webクライアントのリフレッシュトークン有効期間を短くする（CDKでは`refreshTokenValidity`、Terraformでは`refresh_token_validity`）と、削除されたユーザーがアクセスを維持する時間が短縮されます。IDトークンとアクセストークンの有効期間を短くする（CDKでは`idTokenValidity`と`accessTokenValidity`、Terraformでは`id_token_validity`と`access_token_validity`）と、コマンドを実行した後に既に発行されたトークンが有効なままである時間が短縮されますが、常にある程度の時間は残ります。どちらもAWSではテストされていません。

## クライアントシークレット

Cognitoは、アイデンティティプロバイダーの設定にクライアントシークレットを保持します。ユーザープールで`cognito-idp:DescribeIdentityProvider`を呼び出すことが許可されている人は誰でもそれを読み取ることができます。これは、使用するIaCプロバイダーに関係なく、Cognitoの動作方法です。

<Infrastructure>
  <Fragment slot="cdk">
コンストラクトは、シークレットを[動的参照](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/dynamic-references-secretsmanager.html)として`{{resolve:secretsmanager:<clientSecretName>:SecretString:::}}`でCloudFormationに渡します。合成されたテンプレートには、その参照のみが含まれます。CloudFormationは、アイデンティティプロバイダーを作成または更新するときにシークレットを読み取ります。シークレットをローテーションした場合、Cognitoは後のデプロイでアイデンティティプロバイダーリソースが変更されたときにのみ新しい値を取得します。

CloudFormationは、アイデンティティプロバイダーの設定（`ProviderDetails`）内で参照を解決するため、フェデレーテッドサインインは保存されたシークレットで機能し、デプロイされたテンプレートには参照のみが保持されます。ローテーション後、他の変更のないデプロイでは、古いシークレットがCognitoに残ります。両方ともAWSで確認されています。
  </Fragment>
  <Fragment slot="terraform">
モジュールは、`data "aws_secretsmanager_secret_version"`データソースでシークレットを読み取るため、`terraform plan`は`(sensitive value)`として表示します。Terraform stateは、データソース用に1回、アイデンティティプロバイダー用に1回、プレーンテキストでシークレットを保持します。ステートバケット内のステートオブジェクトを読み取ることができる人は誰でもシークレットを読み取ることができます。それに応じてステートバケットへの読み取りアクセスを制限してください。

`terraform plan -out`などの保存されたプランファイルも、プレーンテキストでシークレットを保持します。ステートバケットでバージョニングが有効になっている場合、`terraform destroy`後も古いバージョンのステートにシークレットが保持されます。スタックを削除するときは、それらのバージョンも削除してください。テスト後は、アイデンティティプロバイダーでクライアントシークレットをローテーションしてください。
  </Fragment>
</Infrastructure>

ローテーションされたシークレットをCognitoに送信するには：

<Infrastructure>
  <Fragment slot="cdk">
ローテーションに続くデプロイでアイデンティティプロバイダーリソースを変更します。1つの方法は、ローテーションされたシークレットを新しい名前で保存し、`clientSecretName`をその名前に設定することです。テンプレート内の参照が変更されるため、CloudFormationはアイデンティティプロバイダーを更新し、新しいシークレットを読み取ります。その後、古いシークレットを削除します。これは、動的参照に関するCloudFormationドキュメントに従っており、AWSではテストされていません。
  </Fragment>
  <Fragment slot="terraform">
ローテーション後に`terraform plan`と`terraform apply`を実行します。データソースはプランのたびにシークレットの現在のバージョンを読み取るため、プランはアイデンティティプロバイダーのインプレース更新を示し、`apply`は新しいシークレットをCognitoに送信します。`hashicorp/aws`プロバイダーソースでは、`provider_details`への変更は、アイデンティティプロバイダーをインプレースで更新し、置き換えません。これはAWSではテストされていません。
  </Fragment>
</Infrastructure>

## その他のアプリクライアント

アプリクライアントは、アプリケーションがサインインするCognito設定です。ジェネレーターは、ウェブサイトのアプリクライアント（Webクライアント）にのみアイデンティティプロバイダーを追加します。同じユーザープール内の別のアプリクライアントは、アイデンティティプロバイダーもリストしている場合にのみフェデレーテッドユーザーを受け入れます。たとえば、<Link path="guides/ts-dcr-proxy">DCRプロキシ</Link>用に作成するアプリクライアント（MCPクライアント、Model Context Protocolを使用するAIツールがCognitoを通じてサインインできるようにする）には、それらが必要です。そうしないと、フェデレーテッドユーザーはMCPサーバーにサインインできません。

<Infrastructure>
  <Fragment slot="cdk">
`UserIdentity`の後に`supportedIdentityProviders`なしで`identity.userPool.addClient(...)`で作成するアプリクライアントは、プールのすべてのアイデンティティプロバイダーと`COGNITO`をリストします。DCRプロキシの例はこれを行います。アプリクライアントが`supportedIdentityProviders`を設定する場合は、プールのアイデンティティプロバイダーを追加します：

```ts
import { UserPoolClientIdentityProvider } from 'aws-cdk-lib/aws-cognito';

supportedIdentityProviders: [
  UserPoolClientIdentityProvider.COGNITO,
  ...identity.userPool.identityProviders.map((p) =>
    UserPoolClientIdentityProvider.custom(p.providerName),
  ),
],
```
  </Fragment>
  <Fragment slot="terraform">
各アイデンティティプロバイダーの`name`をアプリクライアントの`supported_identity_providers`に追加し、アプリクライアントを`module.user_identity`に依存させて、アイデンティティプロバイダーが最初に存在するようにします。
  </Fragment>
</Infrastructure>

## エージェントチャット用のトークン

Cognito認証を使用する<Link path="guides/ts-agent">TypeScriptエージェント</Link>の`<agent>-chat`ターゲットは、`AGENT_ACCESS_TOKEN`環境変数からCognitoアクセストークンを読み取ります。フェデレーテッドユーザーにはCognitoパスワードがないため、`admin-initiate-auth`は機能しません。代わりに、ウェブサイトにサインインし、ブラウザーの開発者ツールを開き、セッションストレージの`oidc.user:...`エントリから`access_token`をコピーします。
