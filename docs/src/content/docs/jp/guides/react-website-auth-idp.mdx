<Link path="guides/react-website-auth">ウェブサイト認証</Link>はAmazon Cognitoユーザープールを作成し、デフォルトではそのプールにユーザー名とパスワードを持つユーザーのみがサインインできます。スタッフや顧客がOkta、Auth0、Microsoft Entra IDなどのアイデンティティプロバイダー（IdP）に既にアカウントを持っている場合、ウェブサイト専用の2つ目のアカウントが必要になってしまいます。

このジェネレーターは、外部の[OpenID Connect](https://openid.net/developers/how-connect-works/)（OIDC）アイデンティティプロバイダーをユーザープールに追加します。サインインページには、ユーザー名とパスワードフォームの横にアイデンティティプロバイダー用のボタンが表示されるようになります。

## 仕組み

- ウェブサイトは引き続きユーザーをCognitoサインインページに送信します。このページには、アイデンティティプロバイダーにちなんだ名前のボタンが表示されます。
- ボタンを選択したユーザーは、アイデンティティプロバイダーでサインインします。アイデンティティプロバイダーは、リダイレクトURI `https://<cognito domain>/oauth2/idpresponse` でユーザーをCognitoに送り返します。
- Cognitoは、ユーザープールにフェデレーテッドユーザーとしてユーザーを作成し、マッピングしたクレーム（例：`email`）をユーザーの属性にコピーします。
- その後、Cognitoはローカルユーザーに発行するのと同じ種類のトークンを発行します。API、エージェント、アイデンティティプールは、変更なしでそれらを受け入れます。

プールにユーザー名とパスワードを持つユーザーは、引き続きサインインできます。

## アイデンティティプロバイダーの設定

ジェネレーターを実行した後の最初のデプロイでは、Secrets Managerからクライアントシークレットを読み取ります。シークレットが存在しない場合、デプロイは失敗します。この順序で次の手順に従ってください。ジェネレーターは、完了時にこれらも出力します。

1. アイデンティティプロバイダーにアプリケーションを登録し、そのクライアントIDとクライアントシークレットをメモします。リダイレクトURIは手順4で追加します。クライアントIDを`--clientId`に設定してこのジェネレーターを実行します。
2. クライアントシークレットをSecrets Managerに、`clientSecretName`オプションの名前（デフォルトでは`<name>-oidc-client-secret`）で保存します：

   ```bash
   aws secretsmanager create-secret --name TestIdp-oidc-client-secret --secret-string <client secret>
   ```

3. デプロイします。
4. アイデンティティプロバイダーのアプリケーションにリダイレクトURIを追加します。

## 属性マッピング

生成されたユーザープールには、`email`、`given_name`、`family_name`属性が必要です。Cognitoは、サインインのたびにアイデンティティプロバイダーのクレームからこれらを入力します。アイデンティティプロバイダーがそれらのいずれかを送信しない場合、ユーザーの最初のサインインは失敗します。したがって、ジェネレーターは3つのいずれかを省略した`attributeMapping`を拒否します。

`attributeMapping`はJSONオブジェクトです。各キーはユーザープール属性で、各値はアイデンティティプロバイダーのクレームの名前です。デフォルトでは、各属性を同じ名前のクレームにマッピングします：

```json
{"email":"email","given_name":"given_name","family_name":"family_name"}
```

- キーは、`name`や`phone_number`などの[標準属性](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html#cognito-user-pools-standard-attributes)、または`custom:department`などのカスタム属性にすることができます。
- Cognitoは、マッピングされたメールアドレスを未検証として扱います。メールアドレスを自身で検証するアイデンティティプロバイダーからのみ`email_verified`をマッピングしてください。そうしないと、ユーザーがアイデンティティプロバイダーで他人のアドレスを設定し、プールで検証済みとしてマークされる可能性があります。
- ユーザーのメールアドレスがアイデンティティプロバイダーで変更された場合、Cognitoはユーザーの次回サインイン時に新しいアドレスをユーザープールに書き込みます。`email_verified`は`false`のままです。
- カスタム属性は、ユーザープールに既に存在し、変更可能である必要があります。

Terraformアイデンティティプロバイダーファイルは、Cognitoがアイデンティティプロバイダーを返すときに追加する2つの値も設定します：`attribute_mapping`の`"username" = "sub"`と`provider_details`の`attributes_url_add_attributes = "false"`。ファイルがこれらを設定するため、最初のデプロイ後の2回目の`terraform plan`では、アイデンティティプロバイダーへの変更は表示されません。別のアイデンティティプロバイダーで2回目のプランが`provider_details`の変更を表示する場合は、プランがCognitoが返すことを示す値でそのキーをファイルに追加してください。

## アイデンティティプロバイダーに関する注意事項

以下の設定は、各ベンダーのドキュメントから取得したものです。このジェネレーターでテストされたのは、アイデンティティプロバイダーとして機能するCognitoユーザープールのみです。そのテストは、このジェネレーターのリリースに必要なAWSチェックです。

### Okta

未テスト。OktaでOIDC Webアプリケーションを作成します。発行者はOktaドメイン`https://<your-org>.okta.com`、またはカスタム認証サーバー（例：`https://<your-org>.okta.com/oauth2/default`）です。デフォルトのスコープ`openid email profile`は、`email`、`given_name`、`family_name`を返すため、デフォルトのマッピングが機能します。

### Auth0

未テスト。Auth0でRegular Web Applicationを作成します。発行者は`https://<your-tenant>.auth0.com/`で、末尾のスラッシュを含みます。これは、Auth0トークンの`iss`クレームにスラッシュがあるためです。Auth0は、ユーザーの接続が提供する場合にのみ`given_name`と`family_name`を返します。それらのない接続のユーザーは、他のクレームをマッピングするまでサインインできません。

### Microsoft Entra ID

未テスト。Entra IDでシングルテナントアプリケーションを登録します。発行者は`https://login.microsoftonline.com/<tenant-id>/v2.0`です。ジェネレーターは、マルチテナント発行者（`/common/`、`/organizations/`、`/consumers/`）を拒否します。これらは任意のEntra IDテナントからのユーザーを受け入れるためです。Entra IDは、アプリケーションのIDトークンにオプションのクレームとして追加した場合にのみ`given_name`と`family_name`を送信します。その`email`クレームは検証されていないため、Entra IDから`email_verified`をマッピングしないでください。

### Cognito user pool

アイデンティティプロバイダーとして別のCognitoユーザープールでテストするには、発行者`https://cognito-idp.<region>.amazonaws.com/<user pool id>`を使用します。そのアプリクライアントに、クライアントシークレット、認証コードグラント、スコープ`openid email profile`を付与します。

## セキュリティ

- ユーザーを`sub`クレーム（ユーザープール内のユーザーの一意のID）で識別し、`email`では識別しないでください。フェデレーテッドユーザーは、メールがローカルユーザーと一致する場合でも、独自の`sub`を持つプール内の新しいユーザーです。プラグインが生成するコードは`sub`を使用します。
- シングルテナント発行者を使用してください。マルチテナント発行者は、任意の組織からのユーザーのサインインを許可します。
- <Link path="guides/react-website-auth">ウェブサイト認証</Link>で説明されているように、本番ステージから`http://localhost`コールバックURLを削除してください。フェデレーションはコールバックURLを追加しません。

## フェデレーションが行わないこと

- ユーザープールで必要なMFA（多要素認証）は、フェデレーテッドユーザーには適用されません。Cognitoは認証をアイデンティティプロバイダーに任せるため、アイデンティティプロバイダーでMFAを強制してください。
- ウェブサイトからサインアウトすると、Cognitoセッションのみが終了します。OIDCアイデンティティプロバイダーでのユーザーのセッションは終了しないため、ボタンを介した次回のサインインはパスワードなしで完了できます。共有コンピューターでは、ユーザーはアイデンティティプロバイダーでもサインアウトする必要があります。
- ユーザーメニューには、Cognitoユーザー名が表示されます。フェデレーテッドユーザーの場合、それはアイデンティティプロバイダー名、アンダースコア、アイデンティティプロバイダーでのユーザーの`sub`を小文字にしたものです（例：`testidp_00u1abcd`）。

## クライアントシークレット

Cognitoは、アイデンティティプロバイダーの設定にクライアントシークレットを保持します。ユーザープールで`cognito-idp:DescribeIdentityProvider`を呼び出すことが許可されている人は誰でもそれを読み取ることができます。これは、使用するIaCプロバイダーに関係なく、Cognitoの動作方法です。

  <Fragment slot="cdk">

## その他のアプリクライアント

アプリクライアントは、アプリケーションがサインインするCognito設定です。ジェネレーターは、ウェブサイトのアプリクライアント（Webクライアント）にのみアイデンティティプロバイダーを追加します。同じユーザープール内の別のアプリクライアントは、アイデンティティプロバイダーもそれに追加した場合にのみフェデレーテッドユーザーを受け入れます。たとえば、<Link path="guides/ts-dcr-proxy">DCRプロキシ</Link>用に作成するアプリクライアント（MCPクライアント、Model Context Protocolを使用するAIツールがCognitoを通じてサインインできるようにする）には、それが必要です。そうしないと、フェデレーテッドユーザーはMCPサーバーにサインインできません。CDKでは、アイデンティティプロバイダーの`provider.providerName`をそのクライアントの`supportedIdentityProviders`に追加します。

## エージェントチャット用のトークン

Cognito認証を使用する<Link path="guides/ts-agent">TypeScriptエージェント</Link>の`<agent>-chat`ターゲットは、`AGENT_ACCESS_TOKEN`環境変数からCognitoアクセストークンを読み取ります。フェデレーテッドユーザーにはCognitoパスワードがないため、`admin-initiate-auth`は機能しません。代わりに、ウェブサイトにサインインし、ブラウザーの開発者ツールを開き、セッションストレージの`oidc.user:...`エントリから`access_token`をコピーします。
