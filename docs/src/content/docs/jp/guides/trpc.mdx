[tRPC](https://trpc.io/)は、TypeScriptでエンドツーエンドの型安全性を持つAPIを構築するためのフレームワークです。tRPCを使用すると、API操作の入力と出力の更新がクライアントコードに即座に反映され、プロジェクトを再ビルドすることなくIDEで確認できます。

tRPC APIジェネレーターは、AWS CDKまたはTerraformインフラストラクチャのセットアップを含む新しいtRPC APIを作成します。生成されたバックエンドは、AWS API Gateway APIを介して公開され、[Zod](https://zod.dev/)を使用したスキーマ検証が含まれます。また、構造化ロギングとCloudWatch Metricsを含む可観測性のために[AWS Lambda Powertools](https://docs.powertools.aws.dev/lambda/typescript/latest/)をセットアップします。

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambdaホスティング">
AWS X-Rayトレーシングもセットアップされます。

プロシージャはAWS Lambda上で実行されるため、管理するサーバーはなく、提供するリクエストに対してのみ支払いが発生します。
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="ECSホスティング">
プロシージャは、API Gateway HTTP APIの背後にあるAmazon ECS上のコンテナで長時間実行されるHTTPサーバーとして実行されます。X-Rayトレーシングがそこでトレースを生成しない理由を含め、何が変わるかについては<a href="#running-on-amazon-ecs">Running on Amazon ECS</a>を参照してください。
</OptionFilter>

## tRPC APIの実装

高レベルでは、tRPC APIは特定のプロシージャにリクエストを委譲するルーターで構成されます。各プロシージャには、Zodスキーマとして定義された入力と出力があります。

### スキーマ

`src/schema`ディレクトリには、クライアントとサーバーコード間で共有される型が含まれています。このパッケージでは、これらの型はTypeScriptファーストのスキーマ宣言および検証ライブラリである[Zod](https://zod.dev/)を使用して定義されています。

スキーマの例は次のようになります:

```ts
import { z } from 'zod';

// Schema definition
export const UserSchema = z.object({
  name: z.string(),
  height: z.number(),
  dateOfBirth: z.string().datetime(),
});

// Corresponding TypeScript type
export type User = z.TypeOf<typeof UserSchema>;
```

上記のスキーマを考えると、`User`型は次のTypeScriptと同等です:

```ts
interface User {
  name: string;
  height: number;
  dateOfBirth: string;
}
```

スキーマはサーバーとクライアントの両方のコードで共有されるため、APIで使用される構造を変更する際に更新する場所が1つになります。

スキーマはtRPC APIによって実行時に自動的に検証されるため、バックエンドでカスタム検証ロジックを手作業で作成する必要がありません。

Zodは、`.merge`、`.pick`、`.omit`などのスキーマを組み合わせたり派生させたりする強力なユーティリティを提供します。詳細については、[Zodドキュメントウェブサイト](https://zod.dev/?id=basic-usage)を参照してください。

### ルーターとプロシージャ

tRPCルーターは`src/router.ts`で定義され、すべてのプロシージャを登録します。各プロシージャは、期待される入力、出力、および実装を定義します。

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambdaエントリーポイント">
Lambdaハンドラーのエントリーポイントは`src/handler.ts`にあり、リクエストをルーターに転送します。
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="コンテナエントリーポイント">
エントリーポイントは`src/<api-name>-container/server.ts`で、コンテナが実行するHTTPサーバーであり、リクエストをルーターに転送します。
</OptionFilter>

生成されたサンプルルーターには、`echo`という単一の操作があります:

```ts
import { echo } from './procedures/echo.js';

export const appRouter = router({
  echo,
});
```

例の`echo`プロシージャは`src/procedures/echo.ts`に生成されます:

```ts
export const echo = publicProcedure
  .input(EchoInputSchema)
  .output(EchoOutputSchema)
  .query((opts) => ({ message: opts.input.message }));
```

上記を分解すると:

- `publicProcedure`は、`src/middleware`でセットアップされたミドルウェアを含む、API上のパブリックメソッドを定義します。このミドルウェアには、ロギング、トレーシング、メトリクスのためのAWS Lambda Powertools統合が含まれます。
- `input`は、操作の期待される入力を定義するZodスキーマを受け入れます。この操作に送信されたリクエストは、このスキーマに対して自動的に検証されます。
- `output`は、操作の期待される出力を定義するZodスキーマを受け入れます。スキーマに準拠しない出力を返すと、実装で型エラーが表示されます。
- `query`は、APIの実装を定義する関数を受け入れます。この実装は、操作に渡された`input`を含む`opts`と、ミドルウェアによってセットアップされた他のコンテキスト(`opts.ctx`で利用可能)を受け取ります。`query`に渡される関数は、`output`スキーマに準拠する出力を返す必要があります。

実装を定義するための`query`の使用は、操作が変更を伴わないことを示します。データを取得するメソッドを定義するために使用します。変更を伴う操作を実装するには、代わりに`mutation`メソッドを使用します。

新しいプロシージャを追加する場合は、`src/router.ts`のルーターに追加して登録してください。

<OptionFilter when={{ infra: 'rest-lambda' }} description="ストリーミングサブスクリプション — REST APIのみ、SSEを使用">
### サブスクリプション(ストリーミング)

tRPCサブスクリプションを使用すると、[Server-Sent Events (SSE)](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events)を使用してサーバーからクライアントにデータをストリーミングできます。コンピュートタイプとして`rest-lambda`を選択すると、ジェネレーターはストリーミングに必要なインフラストラクチャ、ストリーミングLambdaハンドラー、および`ZodAsyncIterable`スキーマヘルパーを自動的に構成します。

サブスクリプションプロシージャを定義するには、非同期ジェネレーター関数で`.subscription`メソッドを使用します。`src/schema/z-async-iterable.ts`の`ZodAsyncIterable`ヘルパーを使用して出力スキーマを定義します:

```ts
import { publicProcedure } from '../init.js';
import { z } from 'zod';
import { ZodAsyncIterable } from '../schema/z-async-iterable.js';

const InputSchema = z.object({ query: z.string() });
const ChunkSchema = z.object({ text: z.string() });

export const myStream = publicProcedure
  .input(InputSchema)
  .output(
    ZodAsyncIterable({
      yield: ChunkSchema,
    }),
  )
  .subscription(async function* (opts) {
    // Yield data to the client as it becomes available
    for (const chunk of await getResults(opts.input.query)) {
      yield { text: chunk };
    }
  });
```

他のプロシージャと同様に、ルーターにサブスクリプションを登録します:

```ts
export const appRouter = router({
  echo,
  myStream,
});
```

生成されたインフラストラクチャは、すべてのREST API操作に対してAPI Gatewayで`ResponseTransferMode.STREAM`を使用するストリーミングLambdaハンドラーを使用し、サブスクリプションが通常のクエリやミューテーションと並行して動作できるようにします。
</OptionFilter>

## tRPC APIのカスタマイズ

### エラー

実装では、`TRPCError`をスローすることで、クライアントにエラーレスポンスを返すことができます。これらは、エラーのタイプを示す`code`を受け入れます。例:

```ts
throw new TRPCError({
  code: 'NOT_FOUND',
  message: 'The requested resource could not be found',
});
```

### 操作の整理

APIが成長するにつれて、関連する操作をグループ化したい場合があります。

ネストされたルーターを使用して操作をグループ化できます。例:

```ts
import { getUser } from './procedures/users/get.js';
import { listUsers } from './procedures/users/list.js';

const appRouter = router({
   users: router({
      get: getUser,
      list: listUsers,
   }),
   ...
})
```

クライアントはこの操作のグループ化を受け取ります。例えば、この場合の`listUsers`操作の呼び出しは次のようになります:

```ts
client.users.list.query();
```

### ロギング

AWS Lambda Powertoolsロガーは`src/middleware/logger.ts`で構成されており、API実装では`opts.ctx.logger`を介してアクセスできます。これを使用してCloudWatch Logsにログを記録したり、すべての構造化ログメッセージに含める追加の値を制御したりできます。例:

```ts {5}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      opts.ctx.logger.info('Operation called with input', opts.input);

      return ...;
   });
```

ロガーの詳細については、[AWS Lambda Powertoolsロガードキュメント](https://docs.powertools.aws.dev/lambda/typescript/latest/core/logger/)を参照してください。

### メトリクスの記録

AWS Lambda Powertoolsメトリクスは`src/middleware/metrics.ts`で構成されており、API実装では`opts.ctx.metrics`を介してアクセスできます。これを使用して、AWS SDKをインポートして使用することなく、CloudWatchにメトリクスを記録できます。例:

```ts {5}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      opts.ctx.metrics.addMetric('Invocations', 'Count', 1);

      return ...;
   });
```

詳細については、[AWS Lambda Powertoolsメトリクスドキュメント](https://docs.powertools.aws.dev/lambda/typescript/latest/core/metrics/)を参照してください。

### X-Rayトレーシングの微調整

AWS Lambda Powertoolsトレーサーは`src/middleware/tracer.ts`で構成されており、API実装では`opts.ctx.tracer`を介してアクセスできます。これを使用して、AWS X-Rayでトレースを追加し、APIリクエストのパフォーマンスとフローに関する詳細な洞察を提供できます。例:

```ts {5-7}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      const subSegment = opts.ctx.tracer.getSegment()!.addNewSubsegment('MyAlgorithm');
      // ... my algorithm logic to capture
      subSegment.close();

      return ...;
   });
```

詳細については、[AWS Lambda Powertoolsトレーサードキュメント](https://docs.powertools.aws.dev/lambda/typescript/latest/core/tracer/)を参照してください。

<OptionFilter when={{ infra: 'http-ecs' }} description="X-RayはECS上でトレースを生成しない">
:::caution[ECS上ではトレースなし]
上記の呼び出しはコンテナ内でエラーなく実行されますが、トレースは生成されません。PowertoolsはLambda外で実行されている場合にトレーサーをオフにするため、`getSegment()`はどこにも送信されないプレースホルダーサブセグメントを返します。何が得られるか、およびトレースが必要な場合に何を追加するかについては、<a href="#observability">Observability</a>を参照してください。
:::
</OptionFilter>

### カスタムミドルウェアの実装

ミドルウェアを実装することで、プロシージャに提供されるコンテキストに追加の値を追加できます。

例として、`src/middleware/identity.ts`でAPIの呼び出し元ユーザーに関する詳細を抽出するミドルウェアを実装してみましょう。

<OptionFilter when={{ auth: 'iam', infra: ['rest-lambda', 'http-lambda'] }} description="Lambda上のIAM認証APIの識別ミドルウェアの例">
この例では、`IAM`認証の識別ミドルウェアについて説明します。API Gatewayイベントから抽出されたsubを使用して、Cognitoで呼び出し元を検索します。

検索にはCognito Identity Providerクライアントを使用しますが、これは生成されたtRPC APIの依存関係ではありません。まず、APIプロジェクトにインストールします:

<InstallCommand pkg={`@aws-sdk/client-cognito-identity-provider@${TS_VERSIONS['@aws-sdk/client-cognito-identity-provider']}`} project="@my-scope/my-api" />

まず、コンテキストに追加する内容を定義します:

```ts
export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}
```

コンテキストに追加の_オプション_プロパティを定義していることに注意してください。tRPCは、このミドルウェアを正しく構成したプロシージャでこれが定義されていることを保証します。

次に、ミドルウェア自体を実装します。これには次の構造があります:

```ts
export const createIdentityPlugin = () => {
   const t = initTRPC.context<...>().create();
   return t.procedure.use(async (opts) => {
      // Add logic here to run before the procedure

      const response = await opts.next(...);

      // Add logic here to run after the procedure

      return response;
   });
};
```

この場合、呼び出し元のCognitoユーザーに関する詳細を抽出したいと思います。API GatewayイベントからユーザーのサブジェクトID(または「sub」)を抽出し、Cognitoからユーザーの詳細を取得します。実装は、イベントがREST APIまたはHTTP APIのどちらから関数に提供されたかによって異なります:

<Tabs syncKey="http-rest">
<TabItem label="REST API" _filter={{ infra: 'rest-lambda' }}>
```ts
import { CognitoIdentityProvider } from '@aws-sdk/client-cognito-identity-provider';
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEvent } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext & CreateAWSLambdaContextOptions<APIGatewayProxyEvent>
    >()
    .create();

  const cognito = new CognitoIdentityProvider();

  return t.procedure.use(async (opts) => {
    const cognitoAuthenticationProvider =
      opts.ctx.event.requestContext?.identity?.cognitoAuthenticationProvider;

    let sub: string | undefined = undefined;
    if (cognitoAuthenticationProvider) {
      const providerParts = cognitoAuthenticationProvider.split(':');
      sub = providerParts[providerParts.length - 1];
    }

    if (!sub) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `Unable to determine calling user`,
      });
    }

    const { Users } = await cognito.listUsers({
      // Assumes user pool id is configured in lambda environment
      UserPoolId: process.env.USER_POOL_ID!,
      Limit: 1,
      Filter: `sub="${sub}"`,
    });

    if (!Users || Users.length !== 1) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `No user found with subjectId ${sub}`,
      });
    }

    // Provide the identity to other procedures in the context
    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username: Users[0].Username!,
        },
      },
    });
  });
};
```

```ts
import { CognitoIdentityProvider } from '@aws-sdk/client-cognito-identity-provider';
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEventV2WithIAMAuthorizer } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext &
        CreateAWSLambdaContextOptions<APIGatewayProxyEventV2WithIAMAuthorizer>
    >()
    .create();

  const cognito = new CognitoIdentityProvider();

  return t.procedure.use(async (opts) => {
    const cognitoIdentity = opts.ctx.event.requestContext?.authorizer?.iam
      ?.cognitoIdentity as unknown as
      | {
          amr: string[];
        }
      | undefined;

    const sub = (cognitoIdentity?.amr ?? [])
      .flatMap((s) => (s.includes(':CognitoSignIn:') ? [s] : []))
      .map((s) => {
        const parts = s.split(':');
        return parts[parts.length - 1];
      })?.[0];

    if (!sub) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `Unable to determine calling user`,
      });
    }

    const { Users } = await cognito.listUsers({
      // Assumes user pool id is configured in lambda environment
      UserPoolId: process.env.USER_POOL_ID!,
      Limit: 1,
      Filter: `sub="${sub}"`,
    });

    if (!Users || Users.length !== 1) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `No user found with subjectId ${sub}`,
      });
    }

    // Provide the identity to other procedures in the context
    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username: Users[0].Username!,
        },
      },
    });
  });
};
```
</TabItem>
</Tabs>
</OptionFilter>

<OptionFilter when={{ auth: 'cognito', infra: ['rest-lambda', 'http-lambda'] }} description="Lambda上のCognito認証APIの識別ミドルウェアの例">
`auth: 'cognito'`でデプロイすると、API Gateway Cognitoオーソライザーは、呼び出し元が`Authorization`ヘッダーで提供するJWTを検証し、検証されたクレームをLambdaイベントに配置します。ミドルウェアはこれらのクレームを読み取るだけです — 追加のAWS SDK呼び出しも、手動のJWT検証も必要ありません。

まず、コンテキストに追加する内容を定義します:

```ts
export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}
```

コンテキストに追加の_オプション_プロパティを定義していることに注意してください。tRPCは、このミドルウェアを正しく構成したプロシージャでこれが定義されていることを保証します。

次に、ミドルウェア自体です。イベントタイプとクレームの場所はREST APIとHTTP APIで異なるため、実装は選択した`infra`によって異なります:

<Tabs syncKey="http-rest">
<TabItem label="REST API" _filter={{ infra: 'rest-lambda' }}>
REST APIのCognito User Poolsオーソライザーは、クレームを`event.requestContext.authorizer.claims`に配置します:

```ts
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEvent } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext & CreateAWSLambdaContextOptions<APIGatewayProxyEvent>
    >()
    .create();

  return t.procedure.use(async (opts) => {
    const claims = opts.ctx.event.requestContext?.authorizer?.claims as
      | Record<string, string>
      | undefined;

    const sub = claims?.sub;
    const username = claims?.username ?? claims?.['cognito:username'];

    if (!sub || !username) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: 'Unable to determine calling user',
      });
    }

    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username,
        },
      },
    });
  });
};
```
</TabItem>
<TabItem label="HTTP API" _filter={{ infra: 'http-lambda' }}>
HTTP APIのJWTオーソライザーは、クレームが1レベル深い`event.requestContext.authorizer.jwt.claims`にあるpayload-v2イベントを配信します。コンテキストは、生成された`publicProcedure`が使用するものと一致するように`APIGatewayProxyEventV2WithJWTAuthorizer`で型付けする必要があります — そうしないと、`.concat()`がtRPCの`Context mismatch`エラーで失敗します:

```ts
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEventV2WithJWTAuthorizer } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext &
        CreateAWSLambdaContextOptions<APIGatewayProxyEventV2WithJWTAuthorizer>
    >()
    .create();

  return t.procedure.use(async (opts) => {
    const claims = opts.ctx.event.requestContext?.authorizer?.jwt?.claims as
      | Record<string, string>
      | undefined;

    const sub = claims?.sub;
    const username = claims?.username ?? claims?.['cognito:username'];

    if (!sub || !username) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: 'Unable to determine calling user',
      });
    }

    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username,
        },
      },
    });
  });
};
```
</TabItem>
</Tabs>

その後、呼び出し元の識別情報が必要なプロシージャにプラグインをミックスインできます:

```ts
import { publicProcedure } from '../init.js';
import { createIdentityPlugin } from '../middleware/identity.js';
import { z } from 'zod';

export const me = publicProcedure
  .concat(createIdentityPlugin())
  .output(z.object({ sub: z.string(), username: z.string() }))
  .query(({ ctx }) => ({
    sub: ctx.identity!.sub,
    username: ctx.identity!.username,
  }));
```

:::tip[トークン検証は不要]
ここでは`aws-jwt-verify`や他のJWT検証ライブラリは必要ありません — API Gateway Cognito User Poolsオーソライザーは、Lambdaが実行される前に署名、発行者、スコープ、有効期限をすでに検証しています。これらのチェックのいずれかが失敗すると、API Gatewayは`401 Unauthorized`を返し、ハンドラーは呼び出されません。
:::
</OptionFilter>

## Running on Amazon ECS

`infra`を`http-ecs`に設定すると、プロシージャはLambda関数ではなく、コンテナ内の長時間実行されるHTTPサーバーとして実行されます。リクエストは次のパスを取ります:

1. 呼び出し元は、唯一のパブリックエントリーポイントであるAPI Gateway HTTP APIへのリクエストに署名します。すべてのルートは選択した`auth`のオーソライザーを持つため、認証されていないリクエストはエッジで拒否されます。
2. API Gatewayは、VPCへのプライベートパスであるVPCリンクを介してリクエストを転送します。
3. VPCリンクは内部ロードバランサーに到達します。ロードバランサーにはパブリックアドレスがなく、唯一のインバウンドルールはリスナーポートでVPCリンクのセキュリティグループを許可します。
4. ロードバランサーはリクエストをタスクに転送します。タスクの唯一のインバウンドルールは、コンテナポートでロードバランサーのセキュリティグループを許可するため、VPC内の他のものはそれらへの接続を開くことができません。

タスクはプライベートサブネットで実行され、パブリックIPアドレスを取得することはありません。このパスでは、アドレス範囲のインバウンドを許可するものはありません。

デフォルトでは、サービス、ロードバランサー、VPCリンクは、NATゲートウェイを介してAWSに到達するVPCの`PRIVATE_WITH_EGRESS`サブネットに配置されます。`defaultIntegrations`に`vpcSubnets: { subnetType: SubnetType.PRIVATE_ISOLATED }`を渡すと、NATゲートウェイとその時間料金が削除されますが、分離されたサブネットには外部へのルートがないため、タスクが起動するためにVPCには4つのVPCエンドポイントが必要です: イメージをプルするための`ecr.api`と`ecr.dkr`のインターフェースエンドポイント、イメージレイヤーがS3オブジェクトであるためのS3ゲートウェイエンドポイント、および`awslogs`ドライバーが書き込めるようにするための`logs`のインターフェースエンドポイント。これらがないと、タスクはイメージをプルできず、ECSは理由を言わずにサーキットブレーカーでデプロイメントをロールバックします。

VPCリンク、ロードバランサー、そのリスナー、ターゲットグループ、およびロードバランサーがアクセスログを書き込むバケットは、`common/constructs`の`core/api/ecs-http-endpoint.ts`という1つのコンストラクトによって作成され、ECS上でホストされるすべてのAPIが共有します。API独自のコンストラクトは、コンテナサービスに名前を付け、すべての操作をそのエンドポイントにルーティングします。

### コンテナで実行されるもの

`src/<api-name>-container/server.ts`は、2つのジョブを持つ`node:http`サーバーです。`GET /health`は`{"status":"ok"}`を返し、これはロードバランサーのターゲットグループとコンテナヘルスチェックが呼び出すものです。他のすべてのリクエストは、ルーターに対して解決する[tRPC standalone adapter](https://trpc.io/docs/server/adapters/standalone)に送られます。

コンテナにはAPI Gatewayイベントがないため、プロシージャコンテキストには`event`、`context`、`info`フィールドがありません: `http-ecs`の場合、提供される`IMiddlewareContext`はミドルウェアがそこに配置するもののみを指定します。オーソライザーは、リクエストがコンテナに到達するかどうかを決定しますが、そのクレームはリクエストと一緒に到着しないため、上記の識別ミドルウェアの例は適用されません。プロシージャで呼び出し元の識別情報を読み取るには、APIコンストラクトでオーソライザーのコンテキストをリクエストヘッダーにマップし、そのヘッダーを読み取ります。

### 可観測性

ログとメトリクスはLambda上と同じように機能します: コンテナは独自のCloudWatchロググループに書き込み、メトリクスプラグインは各リクエストのメトリクスを埋め込みメトリック形式でCloudWatch Logsが抽出するために公開します。

メトリクスプラグインは各リクエストのメトリクスオブジェクトを構築し、`opts.ctx.metrics`としてプロシージャに渡すため、1つのリクエストが追加したメトリクスは別のリクエストと一緒に公開されることはありません。これは、1つの呼び出しが最初から最後までメトリクスを所有するLambda上よりもここで重要です; このサーバーは同時にリクエストを処理します。独自の`Metrics`オブジェクトではなく、`opts.ctx.metrics`を介して独自のメトリクスを追加してください。独自のオブジェクトは、プロセス内のすべてのリクエストで1つのストアを共有します。

AWS X-Rayトレーシングは機能しません。PowertoolsはLambda外でトレーサーをオフにし、タスクにセグメントを受信するX-Rayデーモンがないため、`opts.ctx.tracer`呼び出しはエラーなく実行されますが、トレースは生成されません。必要な場合は、コンテナサービスにサイドカーとしてデーモンを追加してください。

API Gateway HTTP APIのアクセスログは、APIに到達するすべてのリクエストを記録します。ロードバランサーは、`EcsHttpEndpoint`コンストラクトが作成するバケットに独自のアクセスログを書き込みます。これは、どのタスクがリクエストを処理し、何を応答したかを確認できる場所です。

### イメージのビルドとスキャン

コンテナジェネレーターは、APIにちなんで名付けられたイメージターゲットを提供します:

- `<api-name>-container-docker`は、linux/arm64イメージをビルドし、最初に`bundle`を実行してイメージがバンドルされたサーバーを保持するようにします。
- `<api-name>-container-trivy`は、そのイメージの脆弱性をスキャンします。

イメージのビルド方法については<Link path="/guides/ts-container">TypeScript Container Service</Link>を、デプロイ時の公開方法については<Link path="/guides/docker-bundling">Docker Bundling</Link>を参照してください。

### デプロイと削除

`deploy-sandbox`は<Link path="/guides/typescript-infrastructure#deploying-your-sandbox-stage">CloudFormation expressモード</Link>でデプロイします。これは、ECSサービスが安定状態に達するのを待つのではなく、各リソースの構成が適用されると戻ります。そのため、最初のタスクがまだ起動している間にターゲットが終了する可能性があり、タスクが15秒間隔で2回のヘルスチェックに合格するまで、ロードバランサーにはリクエストを送信するターゲットがなく、`503`を返します。1〜2分待ってから再度呼び出してください。クリアされない`503`は、遅い起動ではなく実際の失敗です: タスクが正常にならない場合、サービスのデプロイメントサーキットブレーカーがロールバックします。

APIのURLはスタック出力ですが、推測する名前ではありません。`CfnOutput`はAPIコンストラクト内で作成され、論理IDをオーバーライドするものはないため、CDKはコンストラクトのパスと8文字のハッシュから出力キーを構築します: `new MyApi(this, 'MyApi', …)`として追加されたAPIは、`MyApiUrl`ではなく`MyApiMyApiUrl`とそのハッシュを出力します。`cdk deploy`は値を出力し、スクリプトはキー全体ではなくサフィックスで一致する必要があります:

```bash
aws cloudformation describe-stacks --stack-name <stack-name> \
  --query "Stacks[0].Outputs[?contains(OutputKey, 'Url')].OutputValue" --output text
```

`destroy-sandbox`は、HTTP APIのアクセスログループとそれを暗号化する顧客管理のKMSキーを残します。どちらも削除ポリシーを設定しないため、CDKのデフォルトの`Retain`が適用され、CloudFormationはそれらを削除するのではなくスキップします。スタックを削除する前にそれらをリストします。削除されたスタックはもはやそのリソースを報告しないためです:

```bash
aws cloudformation describe-stack-resources --stack-name <stack-name> \
  --query "StackResources[?contains(LogicalResourceId, 'AccessLogs') && (ResourceType=='AWS::Logs::LogGroup' || ResourceType=='AWS::KMS::Key')].[ResourceType,PhysicalResourceId]" \
  --output text
```

次に、`aws logs delete-log-group --log-group-name <log-group-name>`と`aws kms schedule-key-deletion --key-id <key-id> --pending-window-in-days 7`でそれらを削除します。7日間はKMSが受け入れる最短のウィンドウです。

### 制限

- **統合タイムアウト。** API Gateway HTTP APIは、統合を約30秒に制限します。それより長くかかるプロシージャは、コンテナがどれだけ長く動作していても、ゲートウェイで失敗します。
- **ストリーミングなし。** tRPCサブスクリプションには`rest-lambda`インフラストラクチャが必要です。HTTP APIはレスポンスをストリーミングできません。
- **ペイロードサイズ。** リクエストとレスポンスは、API Gatewayの10 MB制限に従います。
- **すべての操作に対して1つのサービス。** `integrationPattern`は`shared`です: 1つのコンテナサービスがあり、すべてのルートがそれにルーティングされます。このインフラストラクチャでは、オプションは常に`shared`に解決され、`isolated`は警告とともに無視されます。

### コスト

ロードバランサーは、リクエストごとに支払い、アイドル時には何も支払わないLambdaと比較した場合の新しい固定コストです。データ転送前のus-east-1での大まかな月額数値:

| --- | --- |

| NATゲートウェイ、VPCに1つある場合 | $33 |

## ローカルtRPCサーバー

`serve`ターゲットを使用して、APIのローカルサーバーを実行できます。例:

<NxCommands commands={['serve my-api']} />

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambdaバリアントのローカルサーバーエントリーポイント">
ローカルサーバーのエントリーポイントは`src/local-server.ts`です。
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="APIがECS上で実行される場合のローカルサーバーエントリーポイント">
ローカルサーバーのエントリーポイントは`src/<api-name>-container/index.ts`で、コンテナが実行するのと同じファイルです。`HOST`のアドレスでリッスンし、デフォルトは`127.0.0.1`なので、ローカルサーバーは自分のマシンからの接続のみを受け入れます。イメージは`HOST=0.0.0.0`を設定するため、サーバーはタスク自身のネットワークインターフェースでリッスンし、タスクのセキュリティグループが誰が接続できるかを決定します。

ヘルスルートでサーバーが起動していることを確認します。これはステータス200と`{"status":"ok"}`を返します:

```bash
curl http://localhost:2022/health
```
</OptionFilter>

これにより、APIに変更を加えると自動的にリロードされます。

## tRPC APIの呼び出し

tRPCクライアントを作成して、型安全な方法でAPIを呼び出すことができます。別のバックエンドからtRPC APIを呼び出す場合は、`src/client/index.ts`のクライアントを使用できます。例:

```ts
import { createMyApiClient } from '@my-scope/my-api';

const client = createMyApiClient({ url: 'https://my-api-url.example.com/' });

await client.echo.query({ message: 'Hello world!' });
```

ReactウェブサイトからAPIを呼び出す場合は、<Link path="guides/connection/react-trpc">Connection</Link>ジェネレーターを使用してクライアントを構成することを検討してください。
