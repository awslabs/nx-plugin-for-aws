[FastAPI](https://fastapi.tiangolo.com/)は、PythonでAPIを構築するためのフレームワークです。

FastAPIジェネレーターは、AWS CDKまたはTerraformインフラストラクチャのセットアップを含む新しいFastAPIを作成します。生成されたバックエンドは、AWS API Gateway APIを介して公開されます。可観測性のために[AWS Lambda Powertools](https://docs.powertools.aws.dev/lambda/python/latest/)をセットアップし、構造化ロギングとCloudWatchメトリクスを含みます。

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambdaホスティング">
バックエンドはサーバーレスデプロイメントにAWS Lambdaを使用し、AWS X-Rayトレーシングもセットアップされます。
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="ECSホスティング">
APIは、Lambda関数ではなく、Amazon ECS上のコンテナ内で長時間実行されるuvicornサーバーとして、API Gateway HTTP APIの背後で実行されます。X-Rayトレーシングがそこでトレースを生成しない理由を含め、何が変わるかについては<a href="#running-on-amazon-ecs">Running on Amazon ECS</a>を参照してください。
</OptionFilter>

:::caution[実験的]
`http-ecs`は実験的です。生成される出力は、既存のワークスペースを引き継ぐマイグレーションなしにリリース間で変更される可能性があるため、アップグレード時にこれらの変更を自分で調整することを期待してください。

CDK IaCプロバイダーが必要です: Terraformサポートはまだ実装されていません。ワークスペースがTerraformに解決される場合、ジェネレーターは修正方法を示すメッセージで失敗します。

`integrationPattern`はここでは常に`shared`です。`http-ecs`と一緒に`--integrationPattern=isolated`を渡しても失敗しません: ジェネレーターはオプションが無視されることを警告し、`shared`を使用します。ジェネレーターを対話的に実行すると、`infra`の前に`integrationPattern`を尋ね、`isolated`が事前選択されているため、事前選択をそのままにして`http-ecs`を選択すると、その警告が表示されます。このページのコマンドビルダーでは、`http-ecs`を選択すると`isolated`が無効になり、選択されていた場合はクリアされるため、書き込まれるコマンドにフラグが含まれることはありません。

`architecture`オプションは、コンテナが`ARM64`または`X86_64`のどちらで実行されるかを設定し、バンドル内のPythonホイールもそれに従います。ジェネレーターを実行するマシンのアーキテクチャを使用するには、省略してください。コンテナガイドの<Link path="/guides/py-container#cpu-architecture">CPU Architecture</Link>を参照してください。
:::

<FileTree>

## FastAPIの実装

メインのAPI実装は`main.py`にあります。ここでAPIルートとその実装を定義します。以下は例です:

```python
from pydantic import BaseModel
from .init import app, tracer

class Item(BaseModel):
  name: str

@app.get("/items/{item_id}")
@tracer.capture_method
def get_item(item_id: int) -> Item:
    return Item(name=f"Item {item_id}")

@app.post("/items")
@tracer.capture_method
def create_item(item: Item) -> Item:
    return item
```

ジェネレーターは、いくつかの機能を自動的にセットアップします:

1. 可観測性のためのAWS Lambda Powertools統合
2. エラーハンドリングミドルウェア
3. リクエスト/レスポンスの相関
4. メトリクス収集

<OptionFilter not when={{ infra: 'http-ecs' }} description="ストリーミング、REST APIが必要">
型安全なストリーミングも、`rest-lambda`インフラストラクチャのみでセットアップされます。
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambdaバリアントがアプリを提供する方法">
アプリは、uvicornを実行する[Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter)によってLambda関数内で提供されます。
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="ECSバリアントがアプリを提供する方法">

### AWS Lambda Powertoolsによる可観測性

#### ロギング

ジェネレーターは、AWS Lambda Powertoolsを使用して構造化ロギングを設定します。ルートハンドラーでロガーにアクセスできます:

```python
from .init import app, logger

@app.get("/items/{item_id}")
def read_item(item_id: int):
    logger.info("Fetching item", extra={"item_id": item_id})
    return {"item_id": item_id}
```

ロガーは自動的に以下を含みます:

- リクエストトレーシングのための相関ID
- リクエストパス、マッチしたルート、メソッド

#### トレーシング

AWS X-Rayトレーシングは自動的に設定されます。トレースにカスタムサブセグメントを追加できます:

```python
from .init import app, tracer

@app.get("/items/{item_id}")
@tracer.capture_method
def read_item(item_id: int):
    # Creates a new subsegment
    with tracer.provider.in_subsegment("fetch-item-details"):
        # Your logic here
        return {"item_id": item_id}
```

<OptionFilter when={{ infra: 'http-ecs' }} description="X-RayはECS上でトレースを生成しません">
:::caution[ECS上ではトレースなし]
上記のデコレーターとサブセグメントはコンテナ内でエラーなく実行されますが、トレースを生成しません。PowertoolsはLambda内で実行されていない場合、トレーサーをオフにします。取得できるものと、トレースが必要な場合に追加するものについては、<a href="#observability">Observability</a>を参照してください。
:::
</OptionFilter>

#### メトリクス

CloudWatchメトリクスは、各リクエストに対して自動的に収集されます。カスタムメトリクスを追加できます:

```python
from .init import app, metrics
from aws_lambda_powertools.metrics import MetricUnit

@app.get("/items/{item_id}")
def read_item(item_id: int):
    metrics.add_metric(name="ItemViewed", unit=MetricUnit.Count, value=1)
    return {"item_id": item_id}
```

デフォルトのメトリクスには以下が含まれます:

- リクエスト数
- 成功/失敗数
- ルートごとのメトリクス(`<method> <path>`の`route`ディメンション経由)

### エラーハンドリング

ジェネレーターには包括的なエラーハンドリングが含まれています:

```python
from fastapi import HTTPException

@app.get("/items/{item_id}")
def read_item(item_id: int):
    if item_id < 0:
        raise HTTPException(status_code=400, detail="Item ID must be positive")
    return {"item_id": item_id}
```

未処理の例外はミドルウェアによってキャッチされ、以下を行います:

1. スタックトレースを含む完全な例外をログに記録
2. 失敗メトリクスを記録
3. クライアントに安全な500レスポンスを返す
4. 相関IDを保持

:::tip[レスポンスモデル]
`connection`ジェネレーターを使用する場合、より良いコード生成のために、API操作のレスポンスモデルを指定することをお勧めします。<Link path="guides/connection/react-fastapi#errors">詳細はこちらを参照してください</Link>。
:::

### 呼び出し元ユーザーへのアクセス

<OptionFilter when={{ infra: 'http-ecs' }} description="ECS上のID — オーソライザーコンテキストは到着しません">
ECS上では、Lambda Web AdapterもAPI Gatewayリクエストコンテキストヘッダーもありません: API Gatewayは、プライベートロードバランサー統合にオーソライザーのクレームを転送しません。オーソライザーは、リクエストがコンテナに到達するかどうかを決定しますが、ハンドラーは以下に記載されているようにリクエストから呼び出し元を読み取ることはできません。

操作で呼び出し元のIDを読み取るには、APIコンストラクト内でオーソライザーのコンテキストをリクエストヘッダーにマッピングし、FastAPIの`Request`からそのヘッダーを読み取ります。
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambdaバリアント上のID">
APIが認証によって保護されている場合、ルートハンドラーは誰が呼び出しているかを知る必要があることがよくあります。生成されたFastAPIは、[Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter)を介してAWS Lambda内で実行され、API Gatewayリクエストコンテキストを`x-amzn-request-context`ヘッダーにJSON形式で転送します。FastAPIの`Request`から読み取って、呼び出し元のIDを抽出できます。

例として、呼び出し元ユーザーの詳細を返す`/me`エンドポイントを追加しましょう。抽出を[FastAPI依存関係](https://fastapi.tiangolo.com/tutorial/dependencies/)として実装し、ルート間で再利用できるようにします。リクエストコンテキストの形状、したがってIDを抽出する方法は、選択した`auth`メソッドとREST APIまたはHTTP APIのどちらをデプロイしたかの両方に依存します。
</OptionFilter>

<OptionFilter when={{ auth: 'iam' }} description="IAM認証APIのID抽出">
`IAM`認証の場合、API Gatewayリクエストコンテキストから抽出されたsubを使用してCognitoで呼び出し元を検索します。これには`boto3`が必要です。APIプロジェクトに追加します:

<NxCommands commands={[`run my-api:add boto3${PY_VERSIONS.boto3}`]} />

```python
import json
import os
from typing import Annotated

from boto3 import client
from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel

cognito = client("cognito-idp")


class Identity(BaseModel):
    sub: str
    username: str


def get_identity(request: Request) -> Identity:
    # The Lambda Web Adapter forwards the API Gateway request context as JSON
    request_context_header = request.headers.get("x-amzn-request-context")
    if not request_context_header:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    request_context = json.loads(request_context_header)
    provider = request_context.get("identity", {}).get("cognitoAuthenticationProvider")

    sub = provider.split(":")[-1] if provider else None
    if not sub:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    users = cognito.list_users(
        # Assumes user pool id is configured in lambda environment
        UserPoolId=os.environ["USER_POOL_ID"],
        Limit=1,
        Filter=f'sub="{sub}"',
    ).get("Users", [])

    if len(users) != 1:
        raise HTTPException(status_code=403, detail=f"No user found with subjectId {sub}")

    return Identity(sub=sub, username=users[0]["Username"])


CurrentUser = Annotated[Identity, Depends(get_identity)]
```

import json
from typing import Annotated

from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel


class Identity(BaseModel):
    sub: str
    username: str


def get_identity(request: Request) -> Identity:
    # The Lambda Web Adapter forwards the API Gateway request context as JSON
    request_context_header = request.headers.get("x-amzn-request-context")

    username = claims.get("username")

<OptionFilter when={{ infra: 'rest-lambda' }} description="ストリーミング — REST APIのみ">
### ストリーミング

生成されたFastAPIは、REST APIを使用する場合、すぐにストリーミングレスポンスをサポートします。インフラストラクチャは、[AWS Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter)を使用してLambda内でuvicorn経由でFastAPIを実行するように設定されており、すべてのREST API操作に対してAPI Gatewayで`ResponseTransferMode.STREAM`を使用し、ストリーミング操作と非ストリーミング操作を並行して動作させることができます。

#### `JsonStreamingResponse`の使用

生成された`init.py`は、適切なOpenAPIスキーマ生成を伴う型安全なストリーミングを提供する`JsonStreamingResponse`クラスをエクスポートします。これにより、<Link path="guides/connection/react-fastapi">`connection`ジェネレーター</Link>が正しく型付けされたストリーミングクライアントメソッドを生成できます。

```python
from pydantic import BaseModel
from .init import app, JsonStreamingResponse

class Chunk(BaseModel):
    message: str

async def generate_chunks():
    for i in range(100):
        yield Chunk(message=f"This is chunk {i}")

@app.post(
    "/stream",
    response_class=JsonStreamingResponse,
    responses={200: JsonStreamingResponse.openapi_response(Chunk, "Stream of chunks")},
)
async def my_stream() -> JsonStreamingResponse:
    return JsonStreamingResponse(generate_chunks())
```

`JsonStreamingResponse`クラスは:

1. Pydanticモデルを[JSON Lines](https://jsonlines.org/)形式(`application/jsonl`)にシリアライズ
2. `itemSchema`を含む正しいOpenAPIスキーマを生成する`openapi_response`ヘルパーを提供し、<Link path="guides/connection/react-fastapi#consuming-a-stream">`connection`ジェネレーター</Link>が型安全なストリーミングクライアントメソッドを生成できるようにします

#### 消費

レスポンスのストリームを消費するには、<Link path="guides/connection/react-fastapi#consuming-a-stream">`connection`ジェネレーター</Link>を利用できます。これにより、ストリーミングされたチャンクを反復処理するための型安全なメソッドが提供されます。
</OptionFilter>

`defaultIntegrations`は、サービスが実行されるVPCを受け取り、その中にすべてを構築します: ECSサービス、その前の内部ロードバランサー、およびAPI Gatewayがそのロードバランサーに到達するVPCリンク。コンストラクトはVPCを作成しないため、スタック内でVPCを作成またはインポートします。

```ts {10,13-15}
import { MyApi } from '@my-scope/common-constructs';
import { Stack } from 'aws-cdk-lib';
import { Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string) {
    super(scope, id);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    const api = new MyApi(this, 'MyApi', {
      integrations: MyApi.defaultIntegrations(this, { vpc }).build(),
    });
  }
}
```

既存のVPCを使用するには、`Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })`で検索し、`vpc`として渡します。

コンテナサービス自体を変更するには`service`を渡します — その`cpu`、`memoryLimitMiB`、`desiredCount`、`environment`、またはタスクロールに権限を与えるための`grantTaskRole`:

```ts
MyApi.defaultIntegrations(this, {
  vpc,
  service: {
    cpu: 512,
    memoryLimitMiB: 1024,
    grantTaskRole: (taskRole) => myTable.grantReadWriteData(taskRole),
  },
}).build();
```

これにより、選択した`auth`メソッドに基づく認証を持つAWS API Gateway HTTP API、コンテナを実行するAmazon ECSサービス、その前の内部ロードバランサー、およびAPI Gatewayがそのロードバランサーに到達するVPCリンクがセットアップされます。

## Running on Amazon ECS

`infra`が`http-ecs`に設定されている場合、APIは、Lambda Web Adapterの背後のLambda関数ではなく、コンテナ内で長時間実行されるuvicornサーバーとして実行されます。リクエストは次のパスを取ります:

1. 呼び出し元は、唯一のパブリックエントリーポイントであるAPI Gateway HTTP APIへのリクエストに署名します。すべてのルートは選択した`auth`のオーソライザーを持っているため、認証されていないリクエストはエッジで拒否されます。
2. API Gatewayは、VPCへのプライベートパスであるVPCリンクを介してリクエストを転送します。
3. VPCリンクは内部ロードバランサーに到達します。ロードバランサーにはパブリックアドレスがなく、唯一のインバウンドルールはリスナーポートでVPCリンクのセキュリティグループを許可します。
4. ロードバランサーはリクエストをタスクに転送します。タスクの唯一のインバウンドルールは、コンテナポートでロードバランサーのセキュリティグループを許可するため、VPC内の他のものはタスクへの接続を開くことができません。

タスクはプライベートサブネットで実行され、パブリックIPアドレスを取得することはありません。このパスのどこにも、アドレス範囲のインバウンドを許可するものはありません。

デフォルトでは、サービス、ロードバランサー、VPCリンクは、VPCの`PRIVATE_WITH_EGRESS`サブネットに配置され、NATゲートウェイを介してAWSに到達します。`defaultIntegrations`に`vpcSubnets: { subnetType: SubnetType.PRIVATE_ISOLATED }`を渡すと、NATゲートウェイとその時間料金が削減されますが、分離されたサブネットには外部へのルートがないため、VPCはタスクが起動するために4つのVPCエンドポイントが必要になります: イメージをプルするための`ecr.api`と`ecr.dkr`のインターフェースエンドポイント、イメージレイヤーがS3オブジェクトであるためのS3ゲートウェイエンドポイント、および`awslogs`ドライバーが書き込めるようにするための`logs`のインターフェースエンドポイント。これらがないと、タスクはイメージをプルできず、ECSは理由を言わずにサーキットブレーカーでデプロイメントをロールバックします。

VPCリンク、ロードバランサー、そのリスナー、ターゲットグループ、およびロードバランサーがアクセスログを書き込むバケットは、`common/constructs`の`core/api/ecs-http-endpoint.ts`という1つのコンストラクトによって作成され、ECS上でホストされるすべてのAPIが共有します。API独自のコンストラクトは、コンテナサービスに名前を付け、すべての操作をそのエンドポイントにルーティングします。

### コンテナ内で実行されるもの

`<module_name>/<api_name>_container/main.py`は、`main.py`からアプリをインポートするため、記述したすべての操作はLambda上とまったく同じように提供されます。独自に2つのものを追加します:

- `GET /health`、ロードバランサーのターゲットグループとコンテナヘルスチェックが呼び出します。`include_in_schema=False`として宣言されているため、OpenAPI仕様から除外され、したがってAPI Gatewayルートと生成されたクライアントからも除外されます。また、リクエストメトリクスからも除外されるため、ターゲットグループの15秒ごとの呼び出しはAPIリクエストとしてカウントされません。
- APIの独自のミドルウェアが収集するメトリクスを書き出すミドルウェア。Lambdaでは、ハンドラーが各呼び出しの最後にそれを行います。このサーバーはリクエスト間で存続するため、自分でフラッシュします。

API Gatewayルートは依然としてOpenAPI仕様から取得されるため、追加した操作は`nx build`が仕様を再生成すると展開されます。

### 可観測性

ログとメトリクスは、Lambda上と同じように機能します: コンテナは独自のCloudWatchロググループに書き込み、メトリクスはCloudWatch Logsが抽出するための埋め込みメトリクス形式で書き込まれます。

メトリクスについて1つ異なる点があり、ダッシュボードを読んだり独自のメトリクスを追加したりする前に知っておく価値があります。上記の<a href="#metrics">Metrics</a>セクションで`.init`からインポートするように指示されているオブジェクト`metrics`は、Powertoolsの`Metrics`であり、プロセス内のすべての`Metrics`オブジェクトは1つのメトリクスストアを共有します。Lambdaでは、1つの呼び出しが最初から最後までそのストアを所有します。uvicornサーバーは同時にリクエストを処理し、APIの独自のリクエストごとのメトリクスと追加したメトリクスの両方がその1つのストアに送られるため、同時に実行中の2つのリクエストは、メトリクスが1つのドキュメントに書き出され、最初に追加されたルートに帰属される可能性があります。もう一方のリクエストのドキュメントは、`route`ディメンションがまったくなく、最初のフラッシュ後に追加されたメトリクスのみを保持して出力される可能性があり、Powertoolsは発生時に`PowertoolsUserWarning: Dimension 'route' has already been added`をログに記録します。リクエストがめったに重複しない軽いトラフィックでは、これは表示されません。

したがって、ECS上では、ルートごとの`RequestCount`と`Success`を概算として扱ってください。正確に1つのリクエストに帰属するメトリクスが必要な場合は、リクエスト内で作成した`EphemeralMetrics`に追加し、返す前にフラッシュします。これは独自のストアを保持します:

```python
from aws_lambda_powertools.metrics import EphemeralMetrics, MetricUnit

@app.get("/items/{item_id}")
def read_item(item_id: int):
    request_metrics = EphemeralMetrics()
    request_metrics.add_metric(name="ItemViewed", unit=MetricUnit.Count, value=1)
    request_metrics.flush_metrics()
    return {"item_id": item_id}
```

AWS X-Rayトレーシングはそうではありません。`@tracer.capture_method`はLambda外ではno-opであり、セグメントを受信するX-Rayデーモンもタスク内にありません。トレースが必要な場合は、コンテナサービスにサイドカーとして追加してください。

API Gateway HTTP APIのアクセスログは、APIに到達するすべてのリクエストを記録します。ロードバランサーは、`EcsHttpEndpoint`コンストラクトが作成するバケットに独自のアクセスログを書き込みます。これは、どのタスクがリクエストを処理し、何を応答したかを確認できる場所です。

### イメージビルドとスキャン

コンテナジェネレーターは、APIにちなんで名付けられたイメージターゲットを提供します:

- `<api-name>-container-docker`は、`architecture`オプションのCPUアーキテクチャ、`linux/arm64`または`linux/amd64`のイメージをビルドします。オプションはジェネレーターを実行するマシンのアーキテクチャにデフォルト設定され、`--architecture`で設定します。ターゲットは最初に一致するバンドルターゲット、`bundle-arm`または`bundle-x86`を実行するため、イメージにはそのアーキテクチャ用にビルドされたパッケージとその依存関係が保持されます。
- `<api-name>-container-trivy`は、そのイメージの脆弱性をスキャンします。

イメージのビルド方法については<Link path="/guides/py-container">Python Container Service</Link>を、デプロイ時の公開方法については<Link path="/guides/docker-bundling">Docker Bundling</Link>を参照してください。

### デプロイと削除

`deploy-sandbox`は<Link path="/guides/typescript-infrastructure#deploying-your-sandbox-stage">CloudFormation expressモード</Link>でデプロイします。これは、ECSサービスが安定状態に達するのを待つのではなく、各リソースの設定が適用されると戻ります。そのため、最初のタスクがまだ起動している間にターゲットが完了する可能性があり、タスクが15秒間隔で2回のヘルスチェックに合格するまで、ロードバランサーにはリクエストを送信するターゲットがなく、`503`を返します。デプロイが戻った後、約1分間それを予期してください。1〜2分待ってから再度呼び出してください。クリアされない`503`は、遅い起動ではなく実際の失敗です: タスクが正常にならない場合、サービスのデプロイメントサーキットブレーカーがロールバックします。

ECSはコンテナ内で独自のヘルスチェックを実行します。30秒ごとに`GET /health`を呼び出し、タスク開始後の最初の30秒間の失敗はカウントされません。そのチェックが最初に報告されるまで、`aws ecs describe-tasks`はタスクに`UNKNOWN`の`healthStatus`を与え、合格すると`HEALTHY`に変わります。`UNKNOWN`は、チェックが失敗したのではなく、まだ報告されていないことを意味します。

APIのURLはスタック出力ですが、推測する名前ではありません。`CfnOutput`はAPIコンストラクト内で作成され、何もその論理IDをオーバーライドしないため、CDKはコンストラクトのパスに8文字のハッシュを加えて出力キーを構築します: `new MyApi(this, 'MyApi', …)`として追加されたAPIは、`MyApiUrl`ではなく`MyApiMyApiUrl`とそのハッシュを出力します。`cdk deploy`は値を出力し、スクリプトはキー全体ではなくサフィックスでマッチする必要があります:

```bash
aws cloudformation describe-stacks --stack-name <stack-name> \
  --query "Stacks[0].Outputs[?contains(OutputKey, 'Url')].OutputValue" --output text
```

`destroy-sandbox`は、HTTP APIのアクセスログループとそれを暗号化する顧客管理KMSキーを残します。どちらも削除ポリシーを設定しないため、CDKのデフォルトの`Retain`が適用され、CloudFormationはそれらを削除するのではなくスキップします。削除されたスタックはそのリソースを報告しなくなるため、スタックを削除する前にそれらをリストアップしてください:

```bash
aws cloudformation describe-stack-resources --stack-name <stack-name> \
  --query "StackResources[?contains(LogicalResourceId, 'AccessLogs') && (ResourceType=='AWS::Logs::LogGroup' || ResourceType=='AWS::KMS::Key')].[ResourceType,PhysicalResourceId]" \
  --output text
```

次に、`aws logs delete-log-group --log-group-name <log-group-name>`と`aws kms schedule-key-deletion --key-id <key-id> --pending-window-in-days 7`で削除します。7日間はKMSが受け入れる最短のウィンドウです。

### 制限

- **統合タイムアウト。** API Gateway HTTP APIは、統合を約30秒に制限します。それより長くかかる操作は、コンテナがどれだけ長く動作していても、ゲートウェイで失敗します。
- **ストリーミングなし。** ストリーミング操作には`rest-lambda`インフラストラクチャが必要です。HTTP APIはレスポンスをストリーミングできません。
- **ペイロードサイズ。** リクエストとレスポンスは、API Gatewayの10 MB制限に従います。
- **すべての操作に対して1つのサービス。** `integrationPattern`は`shared`です: 1つのコンテナサービスがあり、すべてのルートがそれにルーティングされます。このインフラストラクチャでは、オプションは常に`shared`に解決され、`isolated`は警告とともに無視されます。

### コスト

ロードバランサーは、リクエストごとに支払い、アイドル時には何も支払わないLambdaと比較して、新しい固定コストです。データ転送前の、us-east-1での大まかな月額数値:

| 項目 | おおよそ |
| --- | --- |
| 内部ロードバランサー | $16 + ロードバランサー容量ユニット |
| Fargateタスク、0.25 vCPU / 0.5 GB | ARM64でタスクあたり$7、X86_64ではさらに多く、FargateはvCPUあたりおよびGBあたりより高いレートで請求します |
| NATゲートウェイ、VPCに存在する場合 | $33 |
| VPCリンク | 時間料金なし |
| ロードバランサーのアクセスログ用S3ストレージ | 月あたりGBあたり数セント |

したがって、1タスクサービスは、トラフィックがない状態でARM64で月額約$23かかり、渡すVPCにNATゲートウェイがある場合はさらに多くなります。アクセスログはトラフィックとともに増加します: `endpoint.accessLogsBucket`にライフサイクルルールを追加して期限切れにしてください。リージョンの現在の価格については、[Elastic Load Balancing](https://aws.amazon.com/elasticloadbalancing/pricing/)および[AWS Fargate](https://aws.amazon.com/fargate/pricing/)の価格ページを確認してください。
