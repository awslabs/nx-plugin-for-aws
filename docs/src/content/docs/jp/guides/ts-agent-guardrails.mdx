<Link path="guides/ts-agent">TypeScript Agent</Link>に[Amazon Bedrock Guardrail](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html)をアタッチします。ガードレールは、エージェントがモデルに送信するメッセージとモデルの回答に対してAmazon Bedrockが適用する一連のルールです。ガードレールがない場合、ユーザーはエージェントにあらゆるトピックについて質問でき、モデルは回答の中でメールアドレスなどの個人データを繰り返すことができます。

ジェネレーターは、ルールを保持するポリシーファイル、エージェントのモデルにガードレールを適用するコード、およびAWSアカウントにガードレールを作成するインフラストラクチャを追加します。

## 仕組み

- `agent.ts`の隣にある`guardrail.json`がルールを保持します：エージェントが拒否する必要があるトピックと、隠すかブロックする必要がある個人データ（PII、個人を特定できる情報）のタイプです。
- CDKコンストラクトまたはTerraformモジュールは、合成または計画時に`guardrail.json`を読み取ります。ガードレールとその番号付きバージョンを作成します。ガードレールバージョンは、ルールの読み取り専用スナップショットです。
- インフラストラクチャは、ガードレールのIDとバージョン番号を<Link path="guides/runtime-config">runtime config</Link>に書き込みます。runtime configは、インフラストラクチャがデプロイされたリソースの詳細を保存するAWS AppConfigアプリケーションです。エントリは`agentcore.guardrails.<AgentClass>`で、エージェントのクラスにちなんで名付けられます。例えば`agentcore.guardrails.MyAgent`です。ガードされた各エージェントには独自のエントリがあります。
- `guardrail.ts`は、`new Agent({...})`呼び出しが使用するBedrockモデルを構築します。各モデル呼び出しの前に、モデルはruntime configからエージェントのエントリを読み取り、そのガードレールを適用します。

### すでにモデルを設定しているエージェント

`new Agent({...})`呼び出しがすでに`model`を設定している場合、ジェネレーターは`agent.ts`を変更しません。ファイル名と追加する行を出力します。独自のモデルオプションを保持するには、`guardrail.ts`の`GuardrailedBedrockModel`クラスでモデルを作成します。これは`BedrockModel`と同じオプションを受け取ります。例：

```ts title="agent.ts"
import { GuardrailedBedrockModel } from './guardrail.js';

const agent = new Agent({
  model: new GuardrailedBedrockModel({ modelId: 'my-model-id' }),
  // ...
});
```

## ガードレールがチェックする内容

ガードレールは、すべてのモデル呼び出しで2つのことをチェックします：

- ユーザーの最新メッセージを含む、エージェントがモデルに送信する会話
- エージェントがユーザーにストリーミングする前のモデルの回答

ガードレールがユーザーのメッセージをブロックすると、ユーザーは`blockedInputMessaging`テキストを受け取り、モデルは呼び出されません。Strandsは、エージェントの会話履歴内のブロックされたメッセージを`[User input redacted.]`に置き換えます。回答をブロックすると、ユーザーは`blockedOutputsMessaging`テキストを受け取ります。`ANONYMIZE`ルールが一致すると、回答には値の代わりに`{EMAIL}`などのプレースホルダーが含まれます。

ガードレールは、ツール定義、モデルがツールに渡す引数、またはツールが返す結果をチェックしません。たとえば、ツールがデータベースから顧客のメールアドレスを返す場合、ガードレールはそれをモデルから隠しません。<Link path="guides/ts-agent">TypeScript Agentガイド</Link>の「Securing your Agent」で説明されているように、ツールの結果を信頼できないものとして扱ってください。

## guardrail.jsonの編集

提供されるポリシーは、生成された数学エージェントの例です。投資アドバイスを拒否し、3種類の個人データを隠すかブロックします：

```json title="guardrail.json"
{
  "blockedInputMessaging": "Sorry, I can't help with that request.",
  "blockedOutputsMessaging": "Sorry, I can't share that answer.",
  "deniedTopics": [
    {
      "name": "Investment advice",
      "definition": "Recommendations about which specific stocks, funds or other investments to buy or sell.",
      "examples": ["Which stocks should I buy this year?"]
    }
  ],
  "piiEntities": [
    { "type": "EMAIL", "action": "ANONYMIZE" },
    { "type": "PHONE", "action": "ANONYMIZE" },
    { "type": "US_SOCIAL_SECURITY_NUMBER", "action": "BLOCK" }
  ]
}
```

フィールドは次のとおりです：

- `blockedInputMessaging`：ガードレールがメッセージをブロックしたときにユーザーが受け取る返信。最大500文字。
- `blockedOutputsMessaging`：ガードレールがモデルの回答をブロックしたときにユーザーが受け取る返信。最大500文字。
- `deniedTopics`：エージェントが拒否する必要があるトピック。各トピックには、`name`（最大100文字の英字、数字、スペース、および文字`-_!?.`）、トピックを説明する最大1000文字の`definition`、およびオプションで各最大100文字の`examples`があります。
- `piiEntities`：アクションを実行する個人データのタイプ。`type`は、`EMAIL`、`PHONE`、`US_SOCIAL_SECURITY_NUMBER`などの[機密情報タイプ](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-sensitive-filters.html)です。`action`は、値をプレースホルダーに置き換える`ANONYMIZE`、またはメッセージまたは回答全体をブロックする`BLOCK`です。

トピック自体を説明する`definition`を書いてください。たとえば、「Recommendations about which specific stocks to buy」は「Do not give investment advice」よりもうまく機能します。

### バージョンが番号付けされている理由

`guardrail.json`を変更してデプロイするたびに、インフラストラクチャは新しい番号付きガードレールバージョンを作成し、runtime configに書き込みます。バージョンの説明には`guardrail.json`のSHA-256ハッシュが保持されるため、ファイルへの変更は説明を変更し、新しいバージョンが古いバージョンを置き換えます。CDKコンストラクトでは、ハッシュは渡すガードレールプロパティもカバーします。

実行中のエージェントは再起動する必要がありません。runtime configから読み取った内容を5秒間キャッシュするため、AppConfigデプロイメントから5秒以内に新しいバージョンを使用します。古いバージョンはAppConfigデプロイメント後に削除されます：CloudFormationはクリーンアップステップで削除し、Terraformは[ガードレールをエージェントに配線する](#ガードレールをエージェントに配線する)で示されているように、ガードレールモジュールをそのモジュールの`depends_on`に追加すると、デプロイメントモジュールの後に削除します。

エージェントは`DRAFT`バージョンを使用しません。`DRAFT`は常に最新のルールを保持するため、AWSコンソールで行われた編集は、デプロイメントなしで実行中のエージェントに到達します。`guardrail.ts`は、runtime config内のバージョンがバージョン番号でない場合にエラーをスローします。

## ガードレールをエージェントに配線する

ジェネレーターは、`ts#agent`ジェネレーターがエージェントのデプロイをユーザーに任せるのと同じように、スタックまたはルートTerraformモジュールを変更しません。完了すると、エージェントの名前が入力された以下のコードを出力します。これを追加して、ガードレールを作成し、そのruntime configエントリを書き込み、エージェントがガードレールを適用できるようにします：

<Infrastructure>
  <Fragment slot="cdk">
```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyAgent, MyAgentGuardrail } from '@my-scope/common-constructs';

const agent = new MyAgent(this, 'MyAgent');
new MyAgentGuardrail(this, 'MyAgentGuardrail', { agent });
```

コンストラクトは、ガードレールのIDとバージョンを`agentcore.guardrails.MyAgent`のruntime configに書き込み、`agent`にガードレールを適用する権限を付与します。エージェントコンストラクトは、すでにエージェントがruntime configを読み取ることを許可しています。

コンストラクトは以下を公開します：

- `guardrail`（`CfnGuardrail`）および`version`（`CfnGuardrailVersion`）
- `guardrailId`、`guardrailArn`、`guardrailVersion`
- `grantApply(grantee)`、別のプリンシパルにガードレールに対して`bedrock:ApplyGuardrail`を付与します

また、`GuardrailId`および`GuardrailVersion`スタック出力も追加します。そのpropsは`agent`と任意の`CfnGuardrail`プロパティです。`CfnGuardrail`プロパティは`guardrail.json`よりも優先されます。たとえば、コンテンツフィルターを追加します：

```ts
new MyAgentGuardrail(this, 'MyAgentGuardrail', {
  agent,
  contentPolicyConfig: {
    filtersConfig: [
      { type: 'HATE', inputStrength: 'HIGH', outputStrength: 'HIGH' },
    ],
  },
});
```
  </Fragment>
  <Fragment slot="terraform">
示されているように`my_agent_guardrail`モジュールを追加します。エージェントをデプロイするルートモジュールで、既存の`my_agent`モジュールブロックにその`additional_iam_policy_statements`行を追加します。`runtime_config_appconfig_deployment`モジュールの`depends_on`リストに`module.my_agent_guardrail`を追加して、デプロイメントにガードレールのruntime configエントリが含まれ、Terraformがデプロイメント後にのみ古いガードレールバージョンを削除するようにします。ルートモジュールがまだエージェントをデプロイしていない場合は、<Link path="guides/ts-agent#infrastructure-as-code">TypeScript Agentガイド</Link>で説明されているように、最初にエージェントのモジュールを追加してください。

```hcl title="packages/infra/src/main.tf"
module "my_agent_guardrail" {
  source = "../../common/terraform/src/app/guardrails/my-agent"
}

module "my_agent" {
  source = "../../common/terraform/src/app/agents/my-agent"
  # ...existing arguments...
  additional_iam_policy_statements = module.my_agent_guardrail.iam_policy_statements
}

module "runtime_config_appconfig_deployment" {
  # ...existing arguments...
  depends_on = [
    # ...existing modules...
    module.my_agent_guardrail,
  ]
}
```

エージェントモジュールがすでに`additional_iam_policy_statements`を設定している場合は、リストを組み合わせます：

```hcl
  additional_iam_policy_statements = concat(module.my_agent_guardrail.iam_policy_statements, local.my_statements)
```

モジュールは、ガードレールのIDとバージョンを`agentcore.guardrails.MyAgent`のruntime configに書き込みます。`agentcore`名前空間は、runtime configモジュールのデフォルトの`namespaces`に含まれているため、追加する必要はありません。エージェントモジュールは、すでにエージェントがruntime configを読み取ることを許可しています。

モジュールは`tags`変数を受け取り、`guardrail_id`、`guardrail_arn`、`guardrail_version`、`iam_policy_statements`を出力します。コンテンツフィルターなどの他のガードレールポリシーを追加するには、モジュール内の`aws_bedrock_guardrail`リソースを編集します。

モジュールはガードレールバージョンに`create_before_destroy`を設定するため、Terraformは古いバージョンを削除する前に新しいバージョンを作成します。
  </Fragment>
</Infrastructure>

### runtime configエントリの欠落

配線を忘れると、runtime configにエージェントのエントリがありません。モデルはBedrockを呼び出す前にエラーをスローするため、エージェントはガードレールなしでは実行されません。`MyAgent`の場合、エラーは次のとおりです：

```
No guardrail for this agent in runtime config at agentcore.guardrails.MyAgent. Add the MyAgentGuardrail construct (CDK) or the guardrails/my-agent module (Terraform) to your infrastructure.
```

エージェントはすべてのプロトコル（`http`、`a2a`、`ag-ui`）で起動し、各リクエストはこのエラーで失敗します。

## ローカル開発

`<agent>-dev`ターゲットは`LOCAL_DEV=true`を設定します。`LOCAL_DEV`が`true`で`RUNTIME_CONFIG_APP_ID`環境変数が設定されていない場合、`guardrail.ts`はruntime configを読み取りません。一度警告を出力し、エージェントはガードレールなしで実行されます：

<NxCommands commands={['agent-dev your-project']} />

ルールをローカルでテストするには、最初にガードレールをデプロイします。次に、`RuntimeConfigApplicationId`スタック出力（CDK）または`module.runtime_config_appconfig.application_id`（Terraform）から、デプロイされたruntime configアプリケーションのIDに`RUNTIME_CONFIG_APP_ID`を設定します。シェルには、AppConfigを読み取り、ガードレールを適用できるAWS認証情報も必要です：

<NxCommands commands={['agent-dev your-project']} env={{ RUNTIME_CONFIG_APP_ID: '<application-id>' }} />

エージェントは自分のエントリのみを読み取るため、複数のガードされたエージェントが同じアプリケーションに対してローカルで実行できます。エージェントがruntime configを読み取れない場合、またはエントリが欠落している場合は、一度警告を出力し、ガードレールなしで実行されます。

`<agent>-serve`ターゲットは`LOCAL_DEV`を設定しないため、`RUNTIME_CONFIG_APP_ID`とデプロイされたエントリが必要です。そうでない場合、各リクエストは上記のように失敗します。`<agent>-chat`ターゲットは実行中のエージェントに接続し、runtime config自体は必要ありません。

## コストとレイテンシ

Amazon Bedrockは、入力と回答の両方でテキストを評価する各ガードレールポリシーに対して課金します。[Amazon Bedrock pricing](https://aws.amazon.com/bedrock/pricing/)を参照してください。

各モデル呼び出しも長くなります。これは、ガードレールがエージェントがユーザーにストリーミングする前に回答をチェックするためです。

## 制限事項

- このジェネレーターは、`ts#agent`で作成されたエージェントをサポートします。AgentCore Harnessはサポートしていません。
- `guardrail.json`は、拒否されたトピックとPIIエンティティのみを保持します。コンテンツフィルターやワードフィルターなどの他のポリシーは、コンストラクトのprops（CDK）を使用するか、モジュールを編集（Terraform）して追加します。
- ガードレールは、[ガードレールがチェックする内容](#ガードレールがチェックする内容)で説明されているように、ツールの結果をチェックしません。
