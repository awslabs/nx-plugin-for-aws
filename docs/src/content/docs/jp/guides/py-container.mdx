このジェネレーターは、既存のPythonプロジェクトにコンテナベースのHTTPサービスを追加します。小さな[FastAPI](https://fastapi.tiangolo.com/)サーバーが提供され、[uvicorn](https://www.uvicorn.org/)ウェブサーバーで実行され、`GET /health`ルートとサンプルの`GET /echo`ルート、Dockerfile、およびサーバーをローカルで実行し、イメージをビルドしてスキャンするためのターゲットが含まれます。また、[Amazon Elastic Container Service (Amazon ECS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html)上でイメージを実行するCDKまたはTerraformコードも取得できます。これは、コンテナを実行およびスケーリングするAWSサービスです。

## 仕組み

サービスは[AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html)上で実行され、管理するサーバーなしで各コンテナを実行します。コンテナの実行中のコピーはそれぞれECSタスクです。タスクは独自のVPC（仮想プライベートクラウド、AWSアカウント内の分離されたネットワーク）内で実行されます。セキュリティグループ（タスクに接続されたファイアウォールルールのセット）は、どのネットワークトラフィックがタスクに到達し、タスクから出ていくかを制御します。

サービスはプライベートです。ロードバランサー、API、パブリックIPアドレスはありません。セキュリティグループにはインバウンドルールがないため、呼び出し元を許可するまで、何もサービスへの接続を開くことができません。サービスは、データベースや他のAWSサービスなどへのアウトバウンド呼び出しを行うことができます。

## サービスのローカル実行

`<name>-serve`ターゲットは、コンテナなしでマシン上でサーバーを実行します：

<NxCommands commands={['run your-project:service-serve']} />

サーバーは`PORT`環境変数のポートでリッスンします。`<name>-serve`ターゲットは、ジェネレーターが割り当てるポートに設定し、8081から始まり、ワークスペース内の他のプロジェクトがすでに使用しているポートをスキップします。コンテナ内では、サーバーはポート8080でリッスンします。

サーバーは`HOST`環境変数のアドレスでリッスンします。これはデフォルトで`127.0.0.1`なので、`<name>-serve`ターゲットは自分のマシンからの接続のみを受け入れます。イメージは`HOST=0.0.0.0`を設定するため、タスク内ではサーバーはタスク自身のネットワークインターフェースでリッスンします。タスクのセキュリティグループは、誰が接続できるかを決定します。

ヘルスルートでサーバーが起動していることを確認します。これはステータス200と`{"status":"ok"}`を返します：

```bash
curl http://localhost:<port>/health
```

サーバーには、独自のルートに置き換えるサンプルルートもあります。`GET /echo?message=<x>`は`{"message":"<x>"}`を返します。`message`パラメータは必須で、最大1024文字です。パラメータなし、または長い値のリクエストは、ステータス422を取得します。

## イメージのビルドとスキャン

`<name>-docker`ターゲットは、サービスのlinux/arm64イメージをビルドします。最初に`bundle-arm`ターゲットを実行し、コードとlinux/arm64依存関係を`dist/<project root>/bundle-arm`に書き込みます。集約`bundle`ターゲットは`bundle-arm`に依存します。次に、`<name>-docker`ターゲットは、そのフォルダー、`Dockerfile`、`.dockerignore`を`dist/<project root>/docker/<name>`にコピーし、そのフォルダーをビルドコンテキスト（イメージビルドが読み取れるファイル）としてイメージをビルドします。ワークスペースが設定されているコンテナエンジン、`docker`または[Finch](https://runfinch.com/)を使用します。ターゲットは、プロジェクト内のすべてのイメージをビルドする集約`docker`ターゲットの一部として実行されます。

<NxCommands commands={['run your-project:service-docker']} />

ECS上では、ヘルスチェックコマンドがコンテナ内で実行され、コンテナポートで`GET /health`を呼び出します。インバウンドアクセスは必要ありません。ECSは、ヘルスチェックが失敗し続けるタスクを置き換えます。ECSはDockerfileの`HEALTHCHECK`命令を無視します。イメージのビルドと公開方法の詳細については、<Link path="/guides/docker-bundling">Docker Bundling</Link>を参照してください。

## サービスのデプロイ

### インフラストラクチャへのサービスの追加

コンストラクトとモジュールはVPCを作成しません。スタックまたはルートモジュールでVPCを作成またはインポートし、それを渡します。タスクは、NATゲートウェイ（プライベートサブネットがアウトバウンド接続を行えるようにする管理ゲートウェイ）またはVPCエンドポイント（VPCからAWSサービスへのプライベート接続）を通じてAWSサービスに到達する、エグレス付きプライベートサブネットで実行されます。

<Infrastructure>
<Fragment slot="cdk">
CDKコンストラクトは`common/constructs`に作成され、サービスにちなんで名付けられます。新しいVPCでの使用例：

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyService } from '@my-scope/common-constructs';
import { Stack, StackProps } from 'aws-cdk-lib';
import { SubnetType, Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ApplicationStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    new MyService(this, 'MyService', {
      vpc,
      vpcSubnets: { subnetType: SubnetType.PRIVATE_WITH_EGRESS },
    });
  }
}
```

既存のVPCを使用するには、`Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })`で検索し、`vpc`として渡します。
</Fragment>
<Fragment slot="terraform">
Terraformモジュールは`common/terraform`に作成されます。サービスのイメージは共有アセットリポジトリに公開されるため、デプロイごとに`core/asset-ecr`モジュールを1回インスタンス化し、その出力をすべてのサービスモジュールに渡します。また、サービスが<Link path="/guides/runtime-config">ランタイム設定</Link>を読み取るAWS AppConfigアプリケーションを保持する共有`runtime_config_appconfig`モジュールの出力も渡します：

```hcl title="packages/infra/src/main.tf"
module "asset_ecr" {
  source = "../../common/terraform/src/core/asset-ecr"
}

module "my_service" {
  source = "../../common/terraform/src/app/services/my-service"

  vpc_id     = aws_vpc.main.id
  subnet_ids = aws_subnet.private[*].id

  asset_ecr_repository_url = module.asset_ecr.repository_url
  asset_ecr_repository_arn = module.asset_ecr.repository_arn

  appconfig_application_id  = module.runtime_config_appconfig.application_id
  appconfig_application_arn = module.runtime_config_appconfig.application_arn
}
```
</Fragment>
</Infrastructure>

### NATゲートウェイなしでの実行

タスクが起動すると、ECSはイメージをプルし、タスクに代わってログを送信します。サーバーコードもAWSサービスを呼び出す可能性があります。NATゲートウェイのないプライベートサブネットでは、これらの呼び出しのそれぞれにVPCエンドポイントが必要です。適切なエンドポイントがないと、タスクは起動に失敗するか、AWSを呼び出すときにタイムアウトします。

VPCにこれらのエンドポイントを作成し、`<region>`をAWSリージョンに置き換えます：

| エンドポイント | タイプ | 使用者 |
| --- | --- | --- |
| `com.amazonaws.<region>.ecr.api` | Interface | ECS、Amazon ECRで認証し、イメージを検索するため |
| `com.amazonaws.<region>.ecr.dkr` | Interface | ECS、Amazon ECRからイメージをプルするため |
| `com.amazonaws.<region>.s3` | Gateway | ECS、Amazon ECRがAmazon S3に保存するイメージレイヤーをダウンロードするため |
| `com.amazonaws.<region>.logs` | Interface | コンテナのログ出力、Amazon CloudWatch Logsに送信される |
| `com.amazonaws.<region>.secretsmanager` | Interface | ECS、タスク起動時にコンテナに渡すシークレットを読み取るため |
| `com.amazonaws.<region>.appconfigdata` | Interface | コード、AWS AppConfigから<Link path="/guides/runtime-config">ランタイム設定</Link>を読み取るため |
| `com.amazonaws.<region>.sts` | Interface | コード、AWS STSから一時的な認証情報を要求するとき（例：別のロールを引き受けるため） |

インターフェースエンドポイントには、タスクからのHTTPS（ポート443）を許可するセキュリティグループが必要です。Amazon ECRエンドポイントの詳細については、[Amazon ECR interface VPC endpoints](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html)を参照してください。

### セキュリティのデフォルト

生成されたインフラストラクチャは、デフォルトで以下の設定を適用します：

- サービスのセキュリティグループにはインバウンドルールがありません。ルールを追加するまで、VPC内外の呼び出し元はタスクに接続できません。
- タスクはプライベートサブネットで実行され、パブリックIPアドレスを取得しません。
- ジェネレーターは、サービスの前にロードバランサーやAPIを作成しません。
- タスクは、ポート443でのみアウトバウンドトラフィックを送信できます。データベースへの接続は、データベースポートを追加します。
- タスクロール（サーバーコードが実行されるロール）は、ユーザーまたは接続がさらに許可するまで、AWS AppConfigからランタイム設定を読み取ることのみができます。
- 実行ロール（ECSがタスクを起動するために使用するロール）は、サービスのイメージをプルし、ロググループに書き込み、リストしたシークレットを読み取ることのみができます。
- シークレットは、AWS Secrets ManagerまたはAWS Systems Manager Parameter Storeへの参照としてのみコンテナに到達し、プレーンな環境値としては決して到達しません。
- コンテナには書き込み可能な`/tmp`フォルダーを持つ読み取り専用のルートファイルシステムがあり、uid 1000、非rootユーザーとして実行されます。ECS Exec（実行中のタスクへのシェルアクセス）はオフです。
- ヘルスチェックに失敗したデプロイは停止し、以前のバージョンにロールバックします。
- ロググループはAWS KMSキーで暗号化され、ログは1年間保持されます。

### 呼び出し元がサービスに到達できるようにする

生成されたままでは、何もサービスを呼び出すことができません。VPC内の別のワークロード、例えばLambda関数や別のECSサービスがサービスを呼び出す必要がある場合は、サービスのセキュリティグループに自分でインバウンドルールを追加します。ジェネレーターはインバウンドルールを追加しません。セキュリティグループによって名前付きの呼び出し元を1つ、コンテナポートで許可し、アドレス範囲を許可しないでください。

<Infrastructure>
<Fragment slot="cdk">
コンストラクトは`IConnectable`を実装しているため、`connections`を通じて呼び出し元のセキュリティグループを許可します：

```ts title="packages/infra/src/stacks/application-stack.ts"
import { Port } from 'aws-cdk-lib/aws-ec2';

const svc = new MyService(this, 'MyService', { vpc });
svc.connections.allowFrom(callerSecurityGroup, Port.tcp(8080));
```

呼び出し元のセキュリティグループがCDKアプリで定義されており、アウトバウンドトラフィックを制限している場合、`allowFrom`は一致するアウトバウンドルールもそれに追加します。
</Fragment>
<Fragment slot="terraform">
サービスのセキュリティグループにインバウンドルールを追加します。サービスのモジュールは`security_group_id`として出力します。呼び出し元のセキュリティグループをソースとして指定します：

```hcl title="packages/infra/src/main.tf"
resource "aws_vpc_security_group_ingress_rule" "caller_to_my_service" {
  security_group_id            = module.my_service.security_group_id
  referenced_security_group_id = aws_security_group.caller.id
  from_port                    = 8080
  to_port                      = 8080
  ip_protocol                  = "tcp"
}
```

呼び出し元のセキュリティグループがアウトバウンドトラフィックを制限している場合は、呼び出し元のグループからサービスのセキュリティグループへの`aws_vpc_security_group_egress_rule`も追加します。
</Fragment>
</Infrastructure>

呼び出し元はタスクのプライベートIPアドレスに接続します。ジェネレーターはサービスディスカバリーを設定せず、ECSがタスクを置き換えるとタスクのアドレスが変わります。呼び出し元に安定した名前を提供するには、例えば[Amazon ECS Service Connect](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect.html)を使用して、サービスディスカバリーを自分で設定します。

### 高度な設定

生成されたサービスは、名前とイメージを設定します。以下の例では、生成されたサービスが渡さない設定のために、汎用の`EcsService`コンストラクトと`ecs-service`モジュールを直接使用します。

CDKでは、`common-constructs`パッケージがサービスのコンストラクトの横に`EcsService`をエクスポートするため、同じ方法でインポートします：`import { EcsService } from '@my-scope/common-constructs'`。生成されたコンストラクトは`EcsService`を拡張し、他のすべてのプロパティを渡します。例えば、`cluster`、`environment`、`secrets`、`grantTaskRole`です。オプションの`image`プロパティは、プロジェクトからビルドされたイメージを置き換えます。

Terraformでは、サービスのモジュールは`ecs-service`モジュールの変数の一部のみを設定できます：`vpc_id`、`subnet_ids`、`cluster_arn`、`environment`、`secrets`、`task_role_policy_statements`、`tags`です。他の変数を設定するには、サービスのモジュールの`module "ecs_service"`ブロックを編集します。

#### ビルド済みイメージ

すでにビルドされているイメージ、例えばパブリックレジストリからのイメージを実行するには、そのURIを渡します。ローカルでは何もビルドされません。プライベートAmazon ECRリポジトリのイメージの場合、CDKはそのリポジトリに対する実行ロールのプルアクセスを付与します。Terraformは、`image_repository_arn`としてリポジトリのARNも渡す場合にのみプルアクセスを付与します。

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'Prebuilt', {
  serviceName: 'Prebuilt',
  vpc,
  image: { imageUri: 'public.ecr.aws/my-org/my-image@sha256:<digest>' },
});
```

</Fragment>
<Fragment slot="terraform">

```hcl
module "prebuilt" {
  source = "../../common/terraform/src/core/container/ecs-service"

  service_name = "Prebuilt"
  vpc_id       = aws_vpc.main.id
  subnet_ids   = aws_subnet.private[*].id
  image_uri    = "public.ecr.aws/my-org/my-image@sha256:<digest>"
  # For an image in a private Amazon ECR repository, also pass:
  # image_repository_arn = aws_ecr_repository.my_image.arn
}
```

</Fragment>
</Infrastructure>

#### 環境変数とシークレット

プレーン設定は`environment`に入れます。タスク定義を読み取れる人は誰でも読み取れるため、シークレット値をそこに入れないでください。代わりに、シークレットを参照として渡します。実行ロールは、リストしたシークレットのみを読み取ることができます。

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'MyService', {

  environment: { LOG_LEVEL: 'info' },

```

</Fragment>
<Fragment slot="terraform">

```hcl

```

#### サイジングとスケーリング

各タスクは、デフォルトで256 CPUユニット（vCPUの4分の1）と512 MiBのメモリを取得します。サービスは1つのタスクを開始し、オートスケーリングは1つから2つのタスクを実行し続け、平均CPU使用率が70%を超えるとタスクを追加します。

| 設定 | CDKプロパティ | Terraform変数 | デフォルト |
| --- | --- | --- | --- |
| タスクあたりのCPUユニット | `cpu` | `cpu` | 256 |
| タスクあたりのメモリ（MiB） | `memoryLimitMiB` | `memory` | 512 |
| 起動時のタスク | `desiredCount` | `desired_count` | 1 |
| 最小タスク数 | `minCapacity` | `min_capacity` | 1 |
| 最大タスク数 | `maxCapacity` | `max_capacity` | 2 |
| ターゲット平均CPU（%） | `targetCpuUtilizationPercent` | `target_cpu_utilization` | 70 |

サービスのコンストラクトまたはモジュールのタスクロールは、ランタイム設定への読み取りアクセスのみで開始します。コードが必要とする権限を追加します：

#### コンテナユーザー

タスク定義は、uid 1000、非rootユーザーとしてコンテナを実行します。提供されるDockerfileはそれに一致します：uidとgid 1000でユーザー`app`を作成し、`USER 1000:1000`を設定します。別のユーザーとして実行するには、CDK `user`プロパティまたはTerraform `container_user`変数を設定します。Terraformは`0`と`root`を拒否します。

| 設定 | CDKプロパティ | Terraform変数 | デフォルト |
| --- | --- | --- | --- |
| コンテナが実行されるユーザー | `user` | `container_user` | `'1000'`（CDK）、`"1000:1000"`（Terraform） |

Terraformでは、`container_user`は`ecs-service`モジュールの変数です。サービスのモジュールはそれを渡さないため、`module "ecs_service"`ブロックで設定します。

### コスト

コンテナサービスは、Lambda関数とは異なり、アイドル状態でも課金されます。これらの部分は、誰かがサービスを呼び出すかどうかに関係なく、時間単位で課金されます：

- Fargateタスク、vCPUごとおよびメモリのGBごと。`desiredCount`と`minCapacity`は少なくとも1つのタスクを実行し続けます。
- インターフェースVPCエンドポイント、各アベイラビリティゾーンで時間ごと、またはNATゲートウェイ、時間ごとおよび処理するデータのGBごと。
- CloudWatch Logsのログストレージ、およびAmazon ECRのイメージストレージ。

リージョンとトラフィックのコストを見積もるには、[AWS Pricing Calculator](https://calculator.aws/)を使用してください。

### サービスの破棄

サービスを削除するには、それを保持するスタックまたはTerraform設定を破棄します：

<NxCommands commands={['run infra:destroy']} />
</Fragment>
<Fragment slot="terraform">
インフラストラクチャプロジェクトの`destroy`ターゲットを実行します：

<NxCommands commands={['run infra:destroy']} />
</Fragment>

次に、AWSコンソールまたはAWS CLIで、ECSサービスとクラスターがなくなったことを確認します。Terraformでは、destroyはサービスのロググループも削除し、7日後に削除するためにAWS KMSキーをスケジュールします。CDKでは、destroyはサービスのロググループとAWS KMSキーを保持します。これは、CDKが削除ポリシーで指定されない限り、ロググループとキーを保持するためです。ログが不要になった場合は、自分で削除してください。イメージはAmazon ECRに残り、CDKアセットリポジトリまたは共有`asset-ecr`リポジトリにあります。不要になった場合は削除してください。VPCはあなたのものなので、サービスを破棄してもそのまま残ります。
