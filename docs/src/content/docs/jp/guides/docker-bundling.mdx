いくつかのジェネレーター（<Link path="/jp/guides/ts-agent">`ts#agent`</Link> や <Link path="/jp/guides/py-agent">`py#agent`</Link> など）は、Amazon ECR にプッシュされ、AWS インフラストラクチャによって使用される Docker イメージを生成します。このガイドでは、これらが従うパターンについて説明し、他のユースケース（たとえば、Amazon ECS で <Link path="/jp/guides/fastapi">FastAPI</Link> プロジェクトを実行したり、コンテナ化された Express サーバーをデプロイしたりする場合）に適用できるようにします。

:::tip[Docker または Finch]
イメージのビルドに使用されるコンテナエンジンは、ワークスペース作成時に `--containers` フラグ（`docker`、`finch`、または `infer` — デフォルト — インストールされているものを自動検出します）を介して選択されます。[Finch](https://runfinch.com/) は、Docker のオープンソースのドロップイン代替品です。選択は `aws-nx-plugin.config.mts` に記録され、コンテナビルドコマンドを出力するすべてのジェネレーターに適用されます。CDK イメージアセットビルドは、`CDK_DOCKER` 環境変数を介してこの選択を尊重します。
:::

## パターン

```d2
direction: right

src: src/
dockerfile: Dockerfile {
  shape: document
}
bundle: "bundle target\nRolldown / uv"
ctx: "dist/.../bundle/\n(build context)" {
  shape: page
}

src -> bundle -> ctx
dockerfile -> ctx
```

推奨されるパターンには 3 つの要素があります：

1. **`bundle` ターゲット** - ランタイムアーティファクトの自己完結型ディレクトリを生成するプロジェクトのターゲット。TypeScript の場合、これは [Rolldown](https://rolldown.rs/) によって生成されるツリーシェイクされた単一ファイルの JavaScript バンドルです。Python の場合、これは [uv](https://docs.astral.sh/uv/) によって生成される `requirements.txt` とインストールされた依存関係です。
2. **最小限の `Dockerfile`** - バンドル出力をベースイメージに単純に `COPY` するだけのもの。バンドリングがすでにツリーシェイクと依存関係のインストールを処理しているため、`Dockerfile` は `npm install` や `uv sync` を実行する必要がありません。
3. **`docker` ターゲット** - `Dockerfile` をバンドル出力と一緒にコピーし（Docker ビルドコンテキストにランタイムに必要なファイルのみが含まれるようにします）、その後 `docker build` を実行します。

Docker ビルドコンテキストは、プロジェクトの `dist` フォルダーに書き込まれます。その後、インフラストラクチャコード（CDK または Terraform）がそのディレクトリを指して、イメージを ECR にプッシュします。

:::tip[なぜ Dockerfile の外でバンドルするのか？]
バンドルステップを Nx 内に保持する（`Dockerfile` 内ではなく）ことは、次のことを意味します：

- Nx はバンドルターゲットを**キャッシュ**できます — その出力はディスク上のディレクトリであるため、キャッシュヒットは本当にそれを復元します。
- `Dockerfile` は、モノレポ、プライベートレジストリ、またはビルド時のシークレットにアクセスする必要がありません。
- イメージレイヤーは小さくなります — すでにビルドされたアーティファクトの単一の `COPY` で、推移的な `node_modules` やビルドツールチェーンはありません。
:::

## TypeScript

### Bundle ターゲット

Rolldown を呼び出す `bundle` ターゲットを設定します。<Link path="/jp/guides/typescript-project">`ts#project`</Link> から始める場合は、`project.json` に以下を追加します：

```json
{
  "targets": {
    "bundle": {
      "cache": true,
      "inputs": ["default"],
      "executor": "nx:run-commands",
      "outputs": ["{workspaceRoot}/dist/{projectRoot}/bundle"],
      "options": {
        "command": "rolldown -c rolldown.config.ts",
        "cwd": "{projectRoot}"
      },
      "dependsOn": ["compile"]
    }
  }
}
```

そして、プロジェクトのルートに `rolldown.config.ts` を作成します：

```ts
// rolldown.config.ts
import { defineConfig } from 'rolldown';

export default defineConfig([
  {
    tsconfig: 'tsconfig.lib.json',
    input: 'src/index.ts',
    output: {
      file: '../../dist/packages/my-project/bundle/index.js',
      format: 'cjs',
      codeSplitting: false,
    },
    platform: 'node',
  },
]);
```

バンドルターゲットを実行して `dist/packages/my-project/bundle/index.js` を生成します：

<NxCommands commands={['bundle my-project']} />

:::tip[バンドル不可能な依存関係]
一部の npm パッケージは、動的な `require`、ネイティブバインディング、またはランタイムファイルパス解決に依存しているため、バンドルできません。これらを `rolldown.config.ts` の `external` 配列に追加して、ランタイム `require()` 呼び出しとして残し、代わりに `Dockerfile` 内でインストールします（以下を参照）：

```ts
{
  // ...
  external: ['@aws/aws-distro-opentelemetry-node-autoinstrumentation'],
}
```
:::

### Dockerfile

プロジェクトのソースディレクトリに `Dockerfile` を作成します。このファイルは、[ベースイメージのセキュリティアップデートを適用](#ディストリビューションのセキュリティアップデートを適用する)し、バンドルを Node ベースイメージに `COPY` するだけで、バンドルできなかった `external` パッケージを `npm install` します。`RUN npm install` ステップを `COPY` の**前に**配置して、Docker がインストールされた `node_modules` レイヤーをキャッシュし、依存関係リストが実際に変更された場合にのみ再実行できるようにします：

```dockerfile
FROM public.ecr.aws/docker/library/node:lts

# Apply the distribution's security updates: base image tags lag behind the
# security suite, so their OS packages carry vulnerabilities that already have a
# published fix.
RUN apt-get update && \
    apt-get upgrade -y --no-install-recommends && \
    rm -rf /var/lib/apt/lists/*

WORKDIR /app

# Install packages that cannot be bundled (declared as "external" in rolldown.config.ts).
# Kept above the COPY so this layer is cached and only invalidated when the install list changes.
RUN npm install @aws/aws-distro-opentelemetry-node-autoinstrumentation@0.10.0

# Copy bundled application
COPY index.js /app

EXPOSE 8080

CMD ["node", "index.js"]
```

:::tip[依存関係をピン留めする]
`Dockerfile` 内でインストールされるすべての依存関係を正確なバージョンにピン留めします（上記のように）— そうしないと、次回ビルドするときに `npm install` が新しいリリースを黙って取得し、ビルドされた時期によって異なる動作をするイメージが生成されます。
:::

### Docker ターゲット

以下を行う `docker` ターゲットを追加します：

1. `Dockerfile` をバンドル出力ディレクトリにコピーします（ビルドコンテキストにバンドル + `Dockerfile` のみが含まれるようにします）、そして
2. `docker build` を実行します（CDK の場合はオプション — 以下を参照）。

```json
{
  "targets": {
    "docker": {
      "cache": false,
      "executor": "nx:run-commands",
      "options": {
        "commands": [
          "shx cp packages/my-project/src/Dockerfile dist/packages/my-project/bundle/Dockerfile",
          "docker build --platform linux/arm64 -t my-scope-my-project:latest dist/packages/my-project/bundle"
        ],
        "parallel": false
      },
      "dependsOn": ["bundle"]
    }
  }
}
```

:::caution[Do not cache image builds]
イメージビルドターゲットには `"cache": false` を設定します。ビルドされたイメージはファイルシステムの `outputs` パスに書き込まれないため、Nx はキャッシュヒット時に復元するものがありません。コンテナエンジンはイメージレイヤーをキャッシュするため、パフォーマンスペナルティはありません。
:::

:::tip[クロスプラットフォームファイルコピー]
`shx` パッケージは、クロスプラットフォームの `cp`、`rm`、`mkdir` コマンドを提供し、シェルビルトイン（Windows では利用できません）を回避します。ワークスペースのルートでインストールします：

<InstallCommand pkg="shx" dev />
:::

このターゲットを実行すると、`dist/packages/my-project/bundle/` の最小限のコンテキストからビルドされた、`my-scope-my-project:latest` とタグ付けされたローカルイメージが生成されます：

<NxCommands commands={['docker my-project']} />

:::note[CDK はイメージ自体をビルドします]
CDK でのみデプロイする場合、上記の `docker build` コマンドはオプションです — CDK の `DockerImageAsset`（[Infrastructure](#infrastructure) の下に表示）は、synth 時にイメージをビルドします。CDK が見つけられるように、`Dockerfile` をビルドコンテキストディレクトリにコピーする必要があります。ジェネレーターは、`docker run` でイメージを簡単にスモークテストできるように、ローカルの `docker build` ステップを保持しています。

Terraform の場合、`docker build` ステップが必要です — 以下の `null_resource` パターンは、ローカルにタグ付けされたイメージをプッシュします。
:::

## Python

### Bundle ターゲット

`uv` を使用してターゲットプラットフォームの依存関係をエクスポートおよびインストールする `bundle` ターゲットを設定します。<Link path="/jp/guides/python-project">`py#project`</Link> ジェネレーターと <Link path="/jp/guides/python-lambda-function">`py#lambda-function`</Link> ジェネレーターの両方がこれを設定します。ターゲット設定は次のようになります：

```json
{
  "targets": {
    "bundle-arm": {
      "cache": true,
      "executor": "nx:run-commands",
      "outputs": ["{workspaceRoot}/dist/{projectRoot}/bundle-arm"],
      "options": {
        "commands": [
          "uv export --frozen --no-dev --no-editable --project {projectRoot} --package my_project -o dist/{projectRoot}/bundle-arm/requirements.txt",
          "uv pip install -n --no-deps --no-installer-metadata --no-compile-bytecode --python-platform aarch64-manylinux_2_28 --target dist/{projectRoot}/bundle-arm -r dist/{projectRoot}/bundle-arm/requirements.txt"
        ],
        "parallel": false
      },
      "dependsOn": ["compile"]
    }
  }
}
```

:::tip[ターゲットアーキテクチャ]
Docker イメージが x86_64 で実行される場合は、`--python-platform` を `x86_64-manylinux_2_28` に変更します。
:::

`nx bundle my-project` を実行すると、プロジェクトのソース、その依存関係、および `requirements.txt` を含む `dist/packages/my-project/bundle-arm/` が生成されます — イメージがランタイムに必要とするすべてのものです。

### Dockerfile

`Dockerfile` は、[ベースイメージのセキュリティアップデートを適用](#ディストリビューションのセキュリティアップデートを適用する)し、その後バンドルを Python ベースイメージにコピーします。`uv` がすでにすべての依存関係をバンドルディレクトリにインストールしているため、イメージ内で `pip install` を実行する必要はありません：

```dockerfile
FROM public.ecr.aws/docker/library/python:3.14-slim

# Apply the distribution's security updates: base image tags lag behind the
# security suite, so their OS packages carry vulnerabilities that already have a
# published fix.
RUN apt-get update && \
    apt-get upgrade -y --no-install-recommends && \
    rm -rf /var/lib/apt/lists/*

WORKDIR /app

# Copy bundled package (source + installed dependencies)
COPY . /app

EXPOSE 8080

ENV PYTHONPATH=/app
ENV PATH="/app/bin:${PATH}"

CMD ["python", "-m", "my_project.main"]
```

### Docker ターゲット

`Dockerfile` をバンドル出力ディレクトリにコピーし、その後 `docker build` を実行する `docker` ターゲットを追加します：

```json
{
  "targets": {
    "docker": {
      "cache": false,
      "executor": "nx:run-commands",
      "options": {
        "commands": [
          "shx rm -rf dist/packages/my-project/docker",
          "shx mkdir -p dist/packages/my-project/docker",
          "shx cp -R dist/packages/my-project/bundle-arm/. dist/packages/my-project/docker",
          "shx cp packages/my-project/src/Dockerfile dist/packages/my-project/docker/Dockerfile",
          "docker build --platform linux/arm64 -t my-scope-my-project:latest dist/packages/my-project/docker"
        ],
        "parallel": false
      },
      "dependsOn": ["bundle-arm"]
    }
  }
}
```

これにより、出力ディレクトリがクリアされ、バンドルの内容と `Dockerfile` の両方が `dist/.../docker` にコピーされ、これが Docker ビルドコンテキストになります。

<NxCommands commands={['docker my-project']} />

## Trivy でイメージをスキャンする

イメージに既知の脆弱性がないかスキャンすることは良い習慣です。このパターンに従うジェネレーターは、[Trivy](https://trivy.dev/) でビルドされたイメージをスキャンする `trivy` ターゲットを追加します。これは [ECR でホストされている Trivy イメージ](https://gallery.ecr.aws/aquasecurity/trivy)から実行され、`HIGH` または `CRITICAL` の検出結果でゼロ以外の終了コードを返します。

ターゲットは、プロジェクトのルートから `.trivyignore` をスキャンディレクトリにコピーし、`--ignorefile` で Trivy に渡すため、最初にそのファイルを作成します — 空のファイルで問題なく、後で[検出結果を抑制](#検出結果の抑制)する場所です：

```bash
touch packages/my-project/.trivyignore
```

次に、`docker` ターゲットに `dependsOn` する `trivy` ターゲットを追加します。ビルドされたイメージを tarball に保存し、ワークスペース相対のバインドマウントを介してスキャンするため、同じコマンドが `docker` と `finch` の両方で機能します：

<Code lang="json" code={trivyTarget} />

各プロジェクトのイメージごとのスキャンターゲットは、ワークスペース全体の `trivy` ターゲットの下に集約され、提供される `trivy` ルートスクリプトが実行します（`nx run-many --target trivy`）。

<PackageManagerShortCommand commands={['trivy']} />

:::tip[CI で Trivy を実行する]
Trivy の脆弱性データベースは新しい CVE で継続的に更新されるため、開発中の反復時に不要な摩擦が生じる可能性があるため、スキャンは意図的に `build` に組み込まれていません。

代わりに、本番ステージへのデプロイ前に、CI パイプラインで専用のステップとして上記のコマンドを実行することをお勧めします。
:::

:::note[検出結果の抑制]
Trivy は、プロジェクトのルートから `.trivyignore` ファイル（脆弱性 ID のリスト、1 行に 1 つ）を読み取ります。`--ignore-unfixed` は、利用可能な修正がない脆弱性をスキップするため、スキャンは `Dockerfile` のツールをアップグレードすることでアクションできる問題でのみ失敗します。詳細については、[Trivy フィルタリングドキュメント](https://trivy.dev/latest/docs/configuration/filtering/#by-finding-ids)を参照してください。
:::

:::tip[ディストリビューションのセキュリティアップデートを適用する]
ベースイメージタグはディストリビューションのセキュリティスイートより遅れているため、その OS パッケージには既に公開された修正がある脆弱性が含まれています。ビルドの最初のステップとしてそれらをアップグレードし、他の命令より前に配置することで、後のレイヤーがアップグレードされたパッケージに対してインストールされるようにします。Debian 派生のベースイメージ（上記の Node および Python イメージで使用されているもの）の場合：

```dockerfile
RUN apt-get update && \
    apt-get upgrade -y --no-install-recommends && \
    rm -rf /var/lib/apt/lists/*
```

生成された `Dockerfile` はこれを自動的に行います。
:::

## Infrastructure

結果のビルドコンテキストディレクトリをインフラストラクチャコードに接続することは、TypeScript と Python の両方で同じです — ビルドコンテキストディレクトリへのパスのみが異なります（TypeScript の場合は `dist/packages/my-project/bundle`、Python の場合は `dist/packages/my-project/docker`）。

<Infrastructure>
<Fragment slot="cdk">
ビルドコンテキストディレクトリを指す CDK の [`DockerImageAsset`](https://docs.aws.amazon.com/cdk/api/v2/docs/aws-cdk-lib.aws_ecr_assets.DockerImageAsset.html) を使用します。CDK は、デプロイ時にイメージをビルドし、CDK アセット ECR リポジトリに公開します：

```d2
direction: right

app: Application {
  bundle: "bundle target\nRolldown / uv"
  dockerfile: Dockerfile {
    shape: document
  }
  ctx: "dist/.../bundle/" {
    shape: page
  }
  bundle -> ctx
  dockerfile -> ctx
}

infra: Infrastructure {
  asset: "DockerImageAsset\ndirectory: dist/.../bundle"
}

ecr: "CDK asset ECR" {
  shape: cylinder
}

infra.asset -> app.ctx: references
infra.asset -> ecr: cdk deploy\nbuilds + pushes
```


```ts
import { DockerImageAsset, Platform } from 'aws-cdk-lib/aws-ecr-assets';
import { findWorkspaceRoot } from '@my-scope/common-constructs';
import * as path from 'path';
import * as url from 'url';

const image = new DockerImageAsset(this, 'MyImage', {
  directory: path.join(
    // Resolve from the compiled construct location to the workspace root
    findWorkspaceRoot(url.fileURLToPath(new URL(import.meta.url))),
    'dist/packages/my-project/bundle',
  ),
  platform: Platform.LINUX_ARM64,
});
```

`findWorkspaceRoot` ヘルパーは、<Link path="/jp/guides/typescript-infrastructure">`ts#infra`</Link> ジェネレーターによって生成され、`@my-scope/common-constructs` からエクスポートされます。共有コンストラクトを使用していない場合は、`cdk` が呼び出される場所（通常はワークスペースルート）からの `dist` ディレクトリへのパスをハードコードし、`findWorkspaceRoot` 呼び出しを完全に省略できます。

:::note[synth 前にバンドルを実行する]
CDK は `bundle`/`docker` ターゲットを自動的に実行しません — `cdk deploy` の前に `nx build my-project` を実行する（またはデプロイターゲットが `build` に依存するように接続する）必要があります。このパターンを使用するジェネレーターは、`docker` と `bundle` を `build` の依存関係として宣言しているため、これは透過的に行われます。
:::

`DockerImageAsset` を、コンテナイメージを受け入れる任意の AWS コンストラクトで使用します。たとえば、`aws_ecs.ContainerImage.fromDockerImageAsset(image)` などです。
</Fragment>
<Fragment slot="terraform">
Terraform の AWS プロバイダーには、「Docker イメージをビルドしてプッシュする」ファーストクラスのリソースがありません。ジェネレーターが使用するパターンは次のとおりです：

1. プロジェクトの `build` ターゲットが `docker build` を実行し、`my-scope-my-project:latest` とタグ付けされたローカルイメージを生成します。
2. `core/asset-ecr` モジュールを使用した共有 ECR リポジトリ
3. ECR に認証し、ローカルにビルドされたイメージをそのコンテンツダイジェストで再タグ付けし、プッシュする `local-exec` プロビジョナーを持つ `null_resource`。
4. ダウンストリームリソース（例：`aws_ecs_task_definition`）は、不変のダイジェストベースのタグでイメージを参照します。

1 つのリポジトリがすべてのイメージを保持するため、各タグはイメージの所有者とそのダイジェストによって名前空間が付けられ、レジストリを共有するイメージが衝突することはありません。

```d2
direction: down

app: Application {
  bundle: "bundle target\nRolldown / uv"
  dockerfile: Dockerfile {
    shape: document
  }
  ctx: "dist/.../bundle/" {
    shape: page
  }
  build: "docker target\ndocker build"
  img: "local image\nmy-scope-my-project:latest" {
    shape: cylinder
  }

  bundle -> ctx
  dockerfile -> ctx
  ctx -> build -> img
}

infra: Infrastructure {
  direction: right
  publish: "null_resource\nlocal-exec: docker push"
  repo: "core/asset-ecr\n(shared)"
  publish -> repo: tag + push
}

ecr: "Amazon ECR" {
  shape: cylinder
}

infra.publish -> app.img: reads local image
infra.repo -> ecr
```


```hcl
module "asset_ecr" {
  source = "../../common/terraform/src/core/asset-ecr"
}

# Invalidate the push whenever the locally-built image digest changes
data "external" "docker_digest" {
  program = ["sh", "-c", "echo '{\"digest\":\"'$(docker inspect my-scope-my-project:latest --format '{{.Id}}')'\"}'"]
}

locals {
  # Content-based, immutable image tag derived from the local image digest, and
  # namespaced by owner so images sharing the registry never collide
  image_tag = "my-project-${replace(data.external.docker_digest.result.digest, "sha256:", "")}"
}

resource "null_resource" "docker_publish" {
  triggers = {
    docker_digest  = data.external.docker_digest.result.digest
    repository_url = module.asset_ecr.repository_url
    image_tag      = local.image_tag
  }

  provisioner "local-exec" {
    command = <<-EOT
      aws ecr get-login-password --region ${data.aws_region.current.id} \
        | docker login --username AWS --password-stdin ${self.triggers.repository_url}
      docker tag my-scope-my-project:latest ${self.triggers.repository_url}:${self.triggers.image_tag}
      docker push ${self.triggers.repository_url}:${self.triggers.image_tag}
    EOT
  }
}
```

`data.external.docker_digest` ブロックは、ローカルイメージハッシュが変更されるたびに `null_resource` が再実行されることを保証し、意味のあるコード変更ごとに新しいプッシュをトリガーします。イメージは、そのダイジェストから派生した不変のコンテンツベースのタグでプッシュされるため、共有リポジトリは `IMMUTABLE` タグの可変性を使用し、既存のタグを上書きしようとする試みを拒否します。

:::note[apply 前にバンドルを実行する]
`nx apply <project>` には、イメージタグ `my-scope-my-project:latest` がローカルに既に存在している必要があります。`nx apply <project>` の前に `nx build my-project`（または `nx docker my-project`）を実行します。
:::
