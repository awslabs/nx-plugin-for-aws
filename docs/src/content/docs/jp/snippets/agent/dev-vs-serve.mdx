#### `-dev` vs `-serve`

ジェネレーターは、同じポートで同じサーバーを実行する2つのターゲットを追加します。これらは設定する環境のみが異なります：

| ターゲット | 環境 | 用途 |
| --- | --- | --- |
| `<your-agent-name>-dev` | `PORT`, `LOCAL_DEV=true` | ローカル開発 |
| `<your-agent-name>-serve` | `PORT` | デプロイされたコードパスをローカルで実行 |

**ローカル開発には `<your-agent-name>-dev` を使用してください。** `LOCAL_DEV=true` はエージェントをローカルコードパスに切り替えます：セッション状態はワークスペースルートの `tmp/agents/` 配下のディスクに書き込まれ、接続されたMCPサーバーはAgentCoreを経由せず直接HTTPで到達されます。これはプロジェクトレベルの `dev` ターゲットが集約するターゲットでもあり、`<your-agent-name>-chat` ターゲットが実行中であることを期待するターゲットでもあります。

`<your-agent-name>-serve` はデプロイされたエージェントと同じコードパスを実行し、AppConfigの<Link path="guides/runtime-config">Runtime Configuration</Link>からセッションストレージと接続されたランタイムARNを解決します。これには、`RUNTIME_CONFIG_APP_ID` をデプロイメントのAppConfigアプリケーションID（デプロイされたスタックから `RuntimeConfigApplicationId` として出力される）に設定し、それを読み取る権限を持つAWS認証情報が必要です：

```bash
RUNTIME_CONFIG_APP_ID=<app-id> nx run your-project:agent-serve
```

:::caution[`-serve` にはデプロイされた設定が必要です]
`RUNTIME_CONFIG_APP_ID` なしで起動された場合、`<your-agent-name>-serve` はリクエストを受け付けますが、すべての呼び出しは `RUNTIME_CONFIG_APP_ID is not set — cannot resolve connected agent ARNs from AppConfig.` で失敗します。

代わりにローカルコードパスを使用するには `LOCAL_DEV=true` を設定してください — これは `<your-agent-name>-dev` がすでに行っていることです。
:::
