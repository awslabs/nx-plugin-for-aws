## タスク 1: Game API の実装

このセクションでは、以下の API を実装します：

1. `saveGame` - ゲームを作成または更新します。
2. `queryGames` - サインインしているプレイヤーの保存されたゲームのページネーション付きリストを返します。
3. `queryInventory` - プレイヤーのインベントリ内のアイテムのページネーション付きリストを返します。
4. `queryActions` - 指定されたゲームの会話履歴を返します。

:::note[各状態の保存場所]
- `games` と `inventory` は **DynamoDB**（ElectroDB 経由）にあります — Game API の Lambda と Inventory MCP サーバーがそれらを読み書きします。
- `actions`（チャットトランスクリプト）は **S3** にあります — Story Agent の `S3SessionManager` がターンごとに 1 つの JSON ブロブを書き込み、Game API の `queryActions` がそれらを読み戻して、UI がページリロード時に履歴を再生できるようにします。`saveAction` プロシージャはありません。エージェントが唯一の書き込み者です。
:::

:::tip[すべてがサインインしているプレイヤーにスコープされています]
両方のストアは呼び出し元をキーとしているため、あるプレイヤーが別のプレイヤーの冒険を見ることはできません：

- **Games** は DynamoDB でユーザーの Cognito `sub` でパーティション化されているため、`queryGames` はテーブルをスキャンする代わりにそのパーティションをクエリします。2 人のプレイヤーが同じヒーロー名を選んでも衝突しません。
- **Conversations** はエージェントによって名前空間化されているため、キーは `session_u-<sub>-<threadId>/…` のようになります。
- **Inventory** は呼び出し元エージェントのセッションとプレイヤー名をキーとしています。Inventory MCP サーバーは、モデルが渡す `playerName` を信頼するのではなく、リクエストコンテキストからそのセッションを読み取ります — モデルの引数は信頼境界ではありません。

`userId` も名前空間もリクエストボディから取得されません — ウェブサイトがそれについて嘘をつく可能性があります。`identity.ts` の `requireUserId` は、Cognito Identity Pool が設定する IAM オーソライザーコンテキスト（`requestContext.authorizer.iam.cognitoIdentity.amr`、これには `…:CognitoSignIn:<sub>` エントリが含まれます）から呼び出し元を読み取ります。その値は Identity Pool のトークン交換によって生成されるため、ブラウザによって提供されるのではなく信頼できるものであり、それがないリクエストは拒否されます。tRPC プラグインとしてのこの再利用可能なバージョンについては、<Link path="guides/trpc">カスタムミドルウェアの実装</Link>を参照してください。
:::

### エンティティモデリング

これがアプリケーションの ER 図です。

```d2
direction: right

game: Game {
  shape: sql_table
  playerName: "string  PK"
  genre: string
  lastUpdated: string
}

item: Item {
  shape: sql_table
  playerName: "string  PK"
  itemName: "string  SK"
  emoji: "string  (optional)"
  lastUpdated: string
  quantity: number
}

game -> item: 1..*
```

`ts#dynamodb` ジェネレーターは [ElectroDB](https://electrodb.dev/en/core-concepts/introduction/) をセットアップしており、これを使用してデータをモデル化します。会話履歴を S3 に永続化するため、S3 クライアントへの依存関係を追加します：

<Aside title="プロジェクトの依存関係">
S3 クライアントは `game-api` プロジェクト自身の `package.json` に追加されます。これは、そのプロジェクトのソースがそれをインポートするためです。バージョンは、パッケージマネージャーの依存関係カタログ（サポートされている場合）を介してワークスペース全体で引き続き調整されます（[単一バージョンポリシー](https://nx.dev/concepts/decisions/dependency-management#single-version-policy)）。詳細については、<Link path="guides/typescript-project#dependencies">ts#project ガイド</Link>を参照してください。
</Aside>

ElectroDB を使用すると、型を定義するだけでなく、タイムスタンプなどの特定の値のデフォルトを提供することもできます。さらに、ElectroDB は [シングルテーブル設計](https://electrodb.dev/en/core-concepts/single-table-relationships/)に従っており、これは DynamoDB を使用する際のベストプラクティスです。

## タスク 4: Game API のローカルテスト

API を試すために AWS にデプロイする必要はありません — `dev` ターゲットは [DynamoDB Local](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DynamoDBLocal.html) に対して Game API を実行します。モジュール 1 で Game API を `DungeonDb` プロジェクトに接続したため、このターゲットは DynamoDB Local も自動的に起動します。

まず、lint の問題を修正します：

<PackageManagerShortCommand commands={["lint"]} />

次に、コードベースをビルドします：

<PackageManagerShortCommand commands={["build"]} />

### ローカルサーバーの起動

`dev` ターゲットを使用して Game API をローカルで起動します。これにより DynamoDB Local も起動されます：

<NxCommands commands={["dev game-api"]} />

<Aside type="tip" title="初回実行">
初回実行時は DynamoDB Local コンテナイメージをプルするため、少し時間がかかる場合があります。このターミナルでサーバーを実行したままにして、以下の `curl` コマンド用に 2 つ目のターミナルを開いてください。
</Aside>

### API のテスト

サーバーが起動して実行されたら、（空の）ゲームリストをクエリします：

```bash
curl -X GET 'http://localhost:2022/games.query?input=%7B%7D'
```

:::note[URL エンコーディング]
API をテストするために渡す `%7B%7D` は、URI エンコードされた空の JSON オブジェクト（`{}`）です。
:::

空のリストが表示されます：

```json
{"result":{"data":{"items":[],"cursor":null}}}
```

次に、ゲームを保存します：

```bash
curl -X POST 'http://localhost:2022/games.save' \
  -H 'Content-Type: application/json' \
  -d '{"playerName":"Alice","genre":"zombie"}'
```

保存すると、永続化されたゲームが返されます（エンティティが設定する `lastUpdated` タイムスタンプ付き）：

```json
{"result":{"data":{"playerName":"Alice","genre":"zombie","lastUpdated":"..."}}}
```

再度クエリして、DynamoDB Local に永続化されていることを確認します：

```bash
curl -X GET 'http://localhost:2022/games.query?input=%7B%7D'
```

このレスポンスには、保存されたゲームが含まれるようになりました：

```json
{"result":{"data":{"items":[{"playerName":"Alice","genre":"zombie","lastUpdated":"..."}],"cursor":null}}}
```

完了したら、ローカルサーバーを停止できます（`Ctrl+C`）。

## タスク 5: Inventory MCP サーバーのローカルテスト

生成された `mcp-server-inspect` ターゲットを使用して、[MCP Inspector](https://github.com/modelcontextprotocol/inspector) で MCP サーバーのツールを試すことができます：

<NxCommands commands={["mcp-server-inspect inventory"]} />

これにより、MCP サーバーがローカルで提供され（DynamoDB Local も起動されます）、`http://localhost:6274` で MCP Inspector が起動し、それに接続するように事前設定されます。**Connect** をクリックし、**Tools** タブに切り替え、**List Tools** をクリックして、`add-to-inventory`（例：`playerName: Alice`、`itemName: Rusty Sword`、`emoji: ⚔️`）を試し、その後 `list-inventory-items` を実行して DynamoDB Local に永続化されていることを確認します。完了したら、サーバーを停止します（`Ctrl+C`）。
