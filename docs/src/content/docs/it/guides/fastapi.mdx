[FastAPI](https://fastapi.tiangolo.com/) è un framework per la creazione di API in Python.

Il generatore FastAPI crea una nuova FastAPI con configurazione dell'infrastruttura AWS CDK o Terraform. Il backend generato è esposto tramite un'API AWS API Gateway. Configura [AWS Lambda Powertools](https://docs.powertools.aws.dev/lambda/python/latest/) per l'osservabilità, inclusi logging strutturato e metriche CloudWatch.

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambda hosting">
Il backend utilizza AWS Lambda per il deployment serverless, e anche il tracing AWS X-Ray è configurato.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="ECS hosting">
La tua API viene eseguita come server uvicorn di lunga durata in un container su Amazon ECS, dietro un'API Gateway HTTP API, anziché in una funzione Lambda. Vedi <a href="#running-on-amazon-ecs">Running on Amazon ECS</a> per cosa cambia, incluso il motivo per cui il tracing X-Ray non produce tracce lì.
</OptionFilter>

Seleziona `rest-lambda` (predefinito) come `infra` se intendi creare operazioni di streaming.

L'opzione `integrationPattern` è predefinita su `isolated`, che crea un Lambda per operazione FastAPI. Seleziona `shared` se preferisci un singolo handler Lambda condiviso per l'intera API, con override opzionali per operazione.

<OptionFilter when={{ infra: 'http-ecs' }} description="ECS hosting is experimental">
:::caution[Sperimentale]
`http-ecs` è sperimentale. Il suo output generato può cambiare tra le versioni senza una migrazione per portare avanti un workspace esistente, quindi aspettati di riconciliare queste modifiche tu stesso quando aggiorni.

Richiede il provider IaC CDK: il supporto Terraform non è ancora implementato, e il generatore fallisce con un messaggio che indica la soluzione.

`integrationPattern` è sempre `shared` qui, poiché un singolo servizio container risponde a ogni operazione. Passare `--integrationPattern=isolated` insieme a `http-ecs` non fallisce: il generatore avverte che l'opzione viene ignorata e usa `shared`. Eseguendo il generatore in modo interattivo, chiede `integrationPattern` prima di `infra`, con `isolated` preselezionato, quindi quell'avviso è ciò che vedi se lasci la preselezione invariata e poi scegli `http-ecs`.
:::
</OptionFilter>

## Output del generatore

Il generatore creerà la seguente struttura di progetto nella directory `<directory>/<api-name>`:

<FileTree>

- project.json Configurazione del progetto e target di build
- pyproject.toml Configurazione del progetto Python e dipendenze
- run.sh Script di bootstrap Lambda Web Adapter per avviare l'app FastAPI tramite uvicorn
- \<module_name>
  - \_\_init\_\_.py Inizializzazione del modulo
  - init.py Configura l'app FastAPI e configura il middleware powertools
  - main.py Implementazione dell'API
- scripts
  - generate_open_api.py Script per generare uno schema OpenAPI dall'app FastAPI

</FileTree>

<OptionFilter when={{ infra: 'http-ecs' }} description="Files that differ when the API runs on ECS">
Con `infra` impostato su `http-ecs` l'API viene eseguita come proprio server HTTP anziché dietro il Lambda Web Adapter, quindi `run.sh` non viene generato. Al suo posto ottieni una cartella container all'interno del tuo modulo, denominata come la tua API:

<FileTree>
- \<module_name>
  - \<api_name>_container
    - main.py Entry point: aggiunge `GET /health`, scrive le metriche che l'API raccoglie e avvia uvicorn su `HOST` e `PORT`. Il bundle, l'immagine e il target `serve` partono tutti da questo file
    - Dockerfile Definizione dell'immagine del container
    - .dockerignore File esclusi dal contesto di build dell'immagine
</FileTree>

I tuoi `init.py`, `main.py` e le operazioni che aggiungi ad essi sono gli stessi per ogni valore di `infra`.

## Implementare la tua FastAPI

L'implementazione principale dell'API si trova in `main.py`. Qui è dove definisci le route dell'API e le loro implementazioni. Ecco un esempio:

```python
from pydantic import BaseModel
from .init import app, tracer

class Item(BaseModel):
  name: str

@app.get("/items/{item_id}")
@tracer.capture_method
def get_item(item_id: int) -> Item:
    return Item(name=f"Item {item_id}")

@app.post("/items")
@tracer.capture_method
def create_item(item: Item) -> Item:
    return item
```

Il generatore configura automaticamente diverse funzionalità:

1. Integrazione AWS Lambda Powertools per l'osservabilità
2. Middleware per la gestione degli errori
3. Correlazione richiesta/risposta
4. Raccolta delle metriche

<OptionFilter not when={{ infra: 'http-ecs' }} description="Streaming, which needs a REST API">
Anche lo streaming type-safe è configurato, solo per l'infrastruttura `rest-lambda`.
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="How the Lambda variants serve the app">
L'app viene servita in una funzione Lambda dal [Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter) che esegue uvicorn.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="How the ECS variant serves the app">
L'app viene servita da uvicorn nel container, senza Lambda Web Adapter. Vedi <a href="#running-on-amazon-ecs">Running on Amazon ECS</a>.
</OptionFilter>

### Osservabilità con AWS Lambda Powertools

#### Logging

Il generatore configura il logging strutturato utilizzando AWS Lambda Powertools. Puoi accedere al logger nei tuoi handler di route:

```python
from .init import app, logger

@app.get("/items/{item_id}")
def read_item(item_id: int):
    logger.info("Fetching item", extra={"item_id": item_id})
    return {"item_id": item_id}
```

Il logger include automaticamente:

- ID di correlazione per il tracciamento delle richieste
- Percorso della richiesta, route corrispondente e metodo

#### Tracing

Il tracing AWS X-Ray è configurato automaticamente. Puoi aggiungere subsegmenti personalizzati alle tue tracce:

```python
from .init import app, tracer

@app.get("/items/{item_id}")
@tracer.capture_method
def read_item(item_id: int):
    # Creates a new subsegment
    with tracer.provider.in_subsegment("fetch-item-details"):
        # Your logic here
        return {"item_id": item_id}
```

<OptionFilter when={{ infra: 'http-ecs' }} description="X-Ray produces no traces on ECS">
:::caution[Nessuna traccia su ECS]
Il decorator e il subsegmento sopra vengono eseguiti senza errori in un container, ma non producono tracce. Powertools disattiva il suo tracer quando non è in esecuzione in Lambda. Vedi <a href="#observability">Observability</a> per cosa ottieni e cosa aggiungere se hai bisogno di tracce.
:::
</OptionFilter>

#### Metriche

Le metriche CloudWatch vengono raccolte automaticamente per ogni richiesta. Puoi aggiungere metriche personalizzate:

```python
from .init import app, metrics
from aws_lambda_powertools.metrics import MetricUnit

@app.get("/items/{item_id}")
def read_item(item_id: int):
    metrics.add_metric(name="ItemViewed", unit=MetricUnit.Count, value=1)
    return {"item_id": item_id}
```

Le metriche predefinite includono:

- Conteggi delle richieste
- Conteggi di successo/fallimento
- Metriche per route (tramite una dimensione `route` di `<method> <path>`)

### Gestione degli errori

Il generatore include una gestione completa degli errori:

```python
from fastapi import HTTPException

@app.get("/items/{item_id}")
def read_item(item_id: int):
    if item_id < 0:
        raise HTTPException(status_code=400, detail="Item ID must be positive")
    return {"item_id": item_id}
```

Le eccezioni non gestite vengono catturate dal middleware e:

1. Registrano l'eccezione completa con stack trace
2. Registrano una metrica di fallimento
3. Restituiscono una risposta 500 sicura al client
4. Preservano l'ID di correlazione

:::tip[Modelli di risposta]
Si consiglia di specificare modelli di risposta per le operazioni API per una migliore generazione del codice se si utilizza il generatore `connection`. <Link path="guides/connection/react-fastapi#errors">Vedi qui per maggiori dettagli</Link>.
:::

### Accedere all'utente chiamante

<OptionFilter when={{ infra: 'http-ecs' }} description="Identity on ECS — the authorizer context does not arrive">
Su ECS non c'è Lambda Web Adapter e nessun header del contesto della richiesta API Gateway: API Gateway non inoltra i claim dell'autorizzatore a un'integrazione di load balancer privato. L'autorizzatore decide ancora se una richiesta raggiunge il container, ma i tuoi handler non possono leggere il chiamante dalla richiesta come scritto di seguito.

Per leggere l'identità del chiamante in un'operazione, mappa il contesto dell'autorizzatore su un header della richiesta nel tuo costrutto API e leggi quell'header dalla `Request` FastAPI.
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="Identity on the Lambda variants">
Quando la tua API è protetta da autenticazione, i tuoi gestori di route spesso devono sapere chi sta chiamando. La FastAPI generata viene eseguita all'interno di AWS Lambda tramite il [Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter), che inoltra il contesto della richiesta API Gateway come JSON nell'header `x-amzn-request-context`. Puoi leggerlo dalla `Request` FastAPI per estrarre l'identità del chiamante.

Come esempio, aggiungiamo un endpoint `/me` che restituisce dettagli sull'utente chiamante. Implementeremo l'estrazione come una [dipendenza FastAPI](https://fastapi.tiangolo.com/tutorial/dependencies/) in modo che possa essere riutilizzata tra le route. La forma del contesto della richiesta — e quindi come estrarre l'identità — dipende sia dal metodo `auth` selezionato sia dal fatto che tu abbia distribuito una REST o HTTP API.
</OptionFilter>

<OptionFilter when={{ auth: 'iam' }} description="Estrazione dell'identità per API autenticate con IAM">
Per l'autenticazione `IAM`, cerchiamo il chiamante in Cognito utilizzando il sub estratto dal contesto della richiesta API Gateway, che richiede `boto3`. Aggiungilo al tuo progetto API:

<NxCommands commands={[`run my-api:add boto3${PY_VERSIONS.boto3}`]} />

```python
import json
import os
from typing import Annotated

from boto3 import client
from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel

cognito = client("cognito-idp")


class Identity(BaseModel):
    sub: str
    username: str


def get_identity(request: Request) -> Identity:
    # The Lambda Web Adapter forwards the API Gateway request context as JSON
    request_context_header = request.headers.get("x-amzn-request-context")
    if not request_context_header:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    request_context = json.loads(request_context_header)
    provider = request_context.get("identity", {}).get("cognitoAuthenticationProvider")

    sub = provider.split(":")[-1] if provider else None
    if not sub:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    users = cognito.list_users(
        # Assumes user pool id is configured in lambda environment
        UserPoolId=os.environ["USER_POOL_ID"],
        Limit=1,
        Filter=f'sub="{sub}"',
    ).get("Users", [])

    if len(users) != 1:
        raise HTTPException(status_code=403, detail=f"No user found with subjectId {sub}")

    return Identity(sub=sub, username=users[0]["Username"])


CurrentUser = Annotated[Identity, Depends(get_identity)]
```
</TabItem>

    username: str

    if not request_context_header:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    request_context = json.loads(request_context_header)
    amr = (
        request_context.get("authorizer", {})
        .get("iam", {})
        .get("cognitoIdentity", {})

    if len(users) != 1:
        raise HTTPException(status_code=403, detail=f"No user found with subjectId {sub}")

from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel

### Streaming

La FastAPI generata supporta le risposte in streaming out of the box quando si utilizza una REST API. L'infrastruttura è configurata per utilizzare il [AWS Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter) per eseguire la tua FastAPI tramite uvicorn all'interno di Lambda, con `ResponseTransferMode.STREAM` in API Gateway per tutte le operazioni REST API, che consente allo streaming di funzionare insieme alle operazioni non in streaming.

#### Utilizzo di `JsonStreamingResponse`

Il file `init.py` generato esporta una classe `JsonStreamingResponse` che fornisce streaming type-safe con generazione corretta dello schema OpenAPI. Questo garantisce che il <Link path="guides/connection/react-fastapi">generatore `connection`</Link> possa produrre metodi client di streaming correttamente tipizzati.

```python
from pydantic import BaseModel
from .init import app, JsonStreamingResponse

class Chunk(BaseModel):
    message: str

async def generate_chunks():
    for i in range(100):
        yield Chunk(message=f"This is chunk {i}")

@app.post(
    "/stream",
    response_class=JsonStreamingResponse,
    responses={200: JsonStreamingResponse.openapi_response(Chunk, "Stream of chunks")},
)
async def my_stream() -> JsonStreamingResponse:
    return JsonStreamingResponse(generate_chunks())
```

La classe `JsonStreamingResponse`:

1. Serializza i modelli Pydantic nel formato [JSON Lines](https://jsonlines.org/) (`application/jsonl`)
2. Fornisce un helper `openapi_response` che genera lo schema OpenAPI corretto con `itemSchema`, consentendo al <Link path="guides/connection/react-fastapi#consuming-a-stream">generatore `connection`</Link> di produrre metodi client di streaming type-safe

#### Consumo

Per consumare uno stream di risposte, puoi utilizzare il <Link path="guides/connection/react-fastapi#consuming-a-stream">generatore `connection`</Link> che fornirà un metodo type-safe per iterare sui tuoi chunk in streaming.
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="CDK usage for the Lambda variants">
Il costrutto CDK per distribuire la tua API nella cartella `common/constructs`. Puoi utilizzarlo in un'applicazione CDK:

```ts {6-8}
import { MyApi } from '@my-scope/common-constructs';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string) {
    // Add the api to your stack
    const api = new MyApi(this, 'MyApi', {
      integrations: MyApi.defaultIntegrations(this).build(),
    });
  }
}
```

Questo configura:

1. Una funzione AWS Lambda per ogni operazione nell'applicazione FastAPI
2. API Gateway HTTP/REST API come trigger della funzione
3. Ruoli IAM e permessi
4. Gruppo di log CloudWatch
5. Configurazione del tracing X-Ray
6. Namespace delle metriche CloudWatch
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="CDK usage when the API runs on ECS — pass the VPC">
`defaultIntegrations` prende il VPC in cui viene eseguito il tuo servizio e costruisce tutto al suo interno: il servizio ECS, il load balancer interno davanti ad esso e il VPC link attraverso cui API Gateway raggiunge quel load balancer. Il costrutto non crea mai un VPC, quindi ne crei o importi uno nel tuo stack.

```ts {10,13-15}
import { MyApi } from '@my-scope/common-constructs';
import { Stack } from 'aws-cdk-lib';
import { Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string) {
    super(scope, id);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    const api = new MyApi(this, 'MyApi', {
      integrations: MyApi.defaultIntegrations(this, { vpc }).build(),
    });
  }
}
```

Per utilizzare un VPC esistente, cercalo con `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` e passalo come `vpc`.

Passa `service` per modificare il servizio container stesso — il suo `cpu`, `memoryLimitMiB`, `desiredCount`, `environment`, o `grantTaskRole` per dare un permesso al task role:

```ts
MyApi.defaultIntegrations(this, {
  vpc,
  service: {
    cpu: 512,
    memoryLimitMiB: 1024,
    grantTaskRole: (taskRole) => myTable.grantReadWriteData(taskRole),
  },
}).build();
```

Questo configura un'API Gateway HTTP API con autenticazione basata sul metodo `auth` scelto, un servizio Amazon ECS che esegue il tuo container, un load balancer interno davanti ad esso e il VPC link attraverso cui API Gateway raggiunge quel load balancer.
</OptionFilter>

<OptionFilter when={{ auth: 'custom' }} description="Utilizzo del Lambda Authorizer personalizzato con CDK">
:::caution[Lambda Authorizer personalizzato]
Quando si utilizza l'autenticazione `Custom`, il costrutto crea internamente un Lambda Authorizer dal file `authorizer.py` generato, che **nega tutte le richieste per impostazione predefinita**. Devi implementare la tua logica di autorizzazione in quel file prima che la tua API accetti qualsiasi traffico.

I risultati dell'autorizzatore vengono memorizzati nella cache per 5 minuti, con chiave sull'header `Authorization`, quindi un token revocato potrebbe essere accettato fino alla scadenza del risultato memorizzato nella cache. Riduci la durata della cache nell'infrastruttura generata se hai bisogno di una revoca più rapida.
:::
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="How ECS hosting works, what it costs and what it limits">
## Running on Amazon ECS

Con `infra` impostato su `http-ecs`, la tua API viene eseguita come server uvicorn di lunga durata in un container anziché in una funzione Lambda dietro il Lambda Web Adapter. Una richiesta segue questo percorso:

1. Un chiamante firma una richiesta all'API Gateway HTTP API, che è l'unico punto di ingresso pubblico. Ogni route porta l'autorizzatore per l'`auth` che hai scelto, quindi una richiesta non autenticata viene rifiutata al bordo.
2. API Gateway inoltra la richiesta attraverso un VPC link, che è il suo percorso privato nel tuo VPC.
3. Il VPC link raggiunge un load balancer interno. Il load balancer non ha indirizzo pubblico e la sua unica regola in entrata consente il security group del VPC link sulla porta del listener.
4. Il load balancer inoltra la richiesta a un task. L'unica regola in entrata dei task consente il security group del load balancer sulla porta del container, quindi nient'altro nel VPC può aprire una connessione ad essi.

I task vengono eseguiti in subnet private e non ottengono mai un indirizzo IP pubblico. Niente in questo percorso consente un intervallo di indirizzi in entrata.

Per impostazione predefinita il servizio, il load balancer e il VPC link vanno nelle subnet `PRIVATE_WITH_EGRESS` del VPC, che raggiungono AWS attraverso un NAT gateway. Passare `vpcSubnets: { subnetType: SubnetType.PRIVATE_ISOLATED }` a `defaultIntegrations` elimina il NAT gateway e il suo costo orario, ma le subnet isolate non hanno una route in uscita, quindi il VPC ha bisogno di quattro VPC endpoint affinché i task possano avviarsi: endpoint di interfaccia per `ecr.api` e `ecr.dkr` per estrarre l'immagine, un endpoint gateway S3 perché i layer dell'immagine sono oggetti S3, e un endpoint di interfaccia per `logs` in modo che il driver `awslogs` possa scrivere. Senza di essi un task non può estrarre la sua immagine e ECS riporta indietro il deployment sul circuit breaker senza dire perché.

Il VPC link, il load balancer, il suo listener, il target group e il bucket in cui il load balancer scrive i suoi log di accesso sono creati da un costrutto, `core/api/ecs-http-endpoint.ts` in `common/constructs`, che ogni API ospitata su ECS condivide. Il costrutto della tua API nomina il suo servizio container e instrada ogni operazione a quell'endpoint.

### What Runs in the Container

`<module_name>/<api_name>_container/main.py` importa l'app dal tuo `main.py`, quindi ogni operazione che scrivi viene servita esattamente come su Lambda. Aggiunge due cose proprie:

- `GET /health`, che il target group del load balancer e il controllo di salute del container chiamano. È dichiarato `include_in_schema=False`, quindi rimane fuori dalla tua specifica OpenAPI e quindi fuori dalle route API Gateway e dai client generati. È anche escluso dalle metriche delle richieste, quindi la chiamata del target group ogni 15 secondi non conta come richiesta API.
- Un middleware che scrive le metriche che il middleware dell'API raccoglie. Su Lambda l'handler lo fa alla fine di ogni invocazione; questo server vive attraverso le richieste, quindi le scarica da solo.

Le route API Gateway provengono ancora dalla tua specifica OpenAPI, quindi un'operazione che aggiungi viene distribuita una volta che `nx build` ha rigenerato la specifica.

### Observability

Log e metriche funzionano come su Lambda: il container scrive nel proprio gruppo di log CloudWatch e le metriche vengono scritte nel formato di metrica incorporato per l'estrazione da parte di CloudWatch Logs.

Una cosa sulle metriche è diversa qui, e vale la pena saperlo prima di leggere una dashboard o aggiungere una metrica propria. `metrics`, l'oggetto che la sezione <a href="#metrics">Metrics</a> sopra ti dice di importare da `.init`, è un `Metrics` di Powertools, e ogni oggetto `Metrics` in un processo condivide un unico archivio di metriche. Su Lambda un'invocazione possiede quell'archivio dall'inizio alla fine. Un server uvicorn gestisce le richieste contemporaneamente, e sia le metriche per richiesta dell'API che quelle che aggiungi vanno a quell'unico archivio, quindi due richieste in volo insieme possono avere le loro metriche scritte in un documento e attribuite a qualsiasi route sia stata aggiunta per prima. Il documento dell'altra richiesta può uscire senza alcuna dimensione `route`, contenendo solo le metriche aggiunte dopo il primo flush, e Powertools registra `PowertoolsUserWarning: Dimension 'route' has already been added` quando succede. Con traffico leggero, dove le richieste raramente si sovrappongono, non lo vedrai.

Quindi tratta `RequestCount` e `Success` per route come approssimativi su ECS. Se hai bisogno di una metrica attribuita esattamente a una richiesta, aggiungila a un `EphemeralMetrics` che crei nella richiesta e scarica prima di restituire, che mantiene un proprio archivio:

```python
from aws_lambda_powertools.metrics import EphemeralMetrics, MetricUnit

@app.get("/items/{item_id}")
def read_item(item_id: int):
    request_metrics = EphemeralMetrics()
    request_metrics.add_metric(name="ItemViewed", unit=MetricUnit.Count, value=1)
    request_metrics.flush_metrics()
    return {"item_id": item_id}
```

Il tracing AWS X-Ray non funziona. `@tracer.capture_method` è un no-op fuori da Lambda, e non c'è nemmeno un daemon X-Ray nel task per ricevere segmenti. Aggiungine uno come sidecar nel tuo servizio container se hai bisogno di tracce.

Il log di accesso dell'API Gateway HTTP API registra ogni richiesta che raggiunge l'API. Il load balancer scrive i propri log di accesso in un bucket che il costrutto `EcsHttpEndpoint` crea, che è dove puoi vedere quale task ha servito una richiesta e cosa ha risposto.

### Image Build and Scanning

Il generatore di container fornisce i target dell'immagine, denominati come la tua API:

- `<api-name>-container-docker` costruisce un'immagine linux/arm64, eseguendo prima il bundle in modo che l'immagine contenga il tuo pacchetto e le sue dipendenze.
- `<api-name>-container-trivy` scansiona quell'immagine per vulnerabilità.

Vedi <Link path="/guides/py-container">Python Container Service</Link> per come viene costruita l'immagine, e <Link path="/guides/docker-bundling">Docker Bundling</Link> per come viene pubblicata al momento del deploy.

### Limiti

- **Timeout di integrazione.** Le API Gateway HTTP API limitano un'integrazione a circa 30 secondi. Un'operazione che impiega più tempo fallisce al gateway per quanto tempo il container continui a lavorare.
- **Nessuno streaming.** Le operazioni di streaming richiedono l'infrastruttura `rest-lambda`. Un'HTTP API non può trasmettere una risposta in streaming.
- **Dimensione del payload.** Richieste e risposte seguono il limite di 10 MB di API Gateway.
- **Un servizio per ogni operazione.** `integrationPattern` è `shared`: c'è un servizio container e ogni route viene instradata ad esso. L'opzione si risolve sempre in `shared` per questa infrastruttura, e `isolated` viene ignorato con un avviso.

### Costo

Il load balancer è il nuovo costo fisso rispetto a Lambda, dove paghi per richiesta e nulla quando inattivo. Cifre mensili approssimative in us-east-1, prima del trasferimento dati:

| Elemento | Approssimativamente |
| --- | --- |
| Load balancer interno | $16 più unità di capacità del load balancer |
| Task Fargate, 0.25 vCPU / 0.5 GB arm64 | $7 per task |
| NAT gateway, se il tuo VPC ne ha uno | $33 |
| VPC link | nessun costo orario |
| Storage S3 per i log di accesso del load balancer | centesimi per GB al mese |

Quindi un servizio a un task costa circa $23 al mese prima di qualsiasi traffico, e di più se il VPC che passi ha un NAT gateway. I log di accesso crescono con il traffico: aggiungi una regola del ciclo di vita a `endpoint.accessLogsBucket` per farli scadere. Controlla le pagine dei prezzi di [Elastic Load Balancing](https://aws.amazon.com/elasticloadbalancing/pricing/) e [AWS Fargate](https://aws.amazon.com/fargate/pricing/) per i prezzi attuali nella tua Region.
