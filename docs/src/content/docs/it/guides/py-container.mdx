Questo generatore aggiunge un servizio HTTP containerizzato a un progetto Python esistente. Ottieni un piccolo server [FastAPI](https://fastapi.tiangolo.com/), eseguito dal web server [uvicorn](https://www.uvicorn.org/), con una route `GET /health` e una route di esempio `GET /echo`, un Dockerfile e target per eseguire il server localmente, costruire la sua immagine e scansionare l'immagine. Ottieni anche codice CDK o Terraform che esegue l'immagine su [Amazon Elastic Container Service (Amazon ECS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html), il servizio AWS che esegue e scala i container.

## Come Funziona

Il servizio viene eseguito su [AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), che esegue ogni container senza server da gestire. Ogni copia in esecuzione del tuo container è un task ECS. I task vengono eseguiti nel tuo VPC (virtual private cloud, una rete isolata nel tuo account AWS). Un security group (un insieme di regole firewall collegate ai task) controlla quale traffico di rete può raggiungerli e lasciarli.

Il servizio è privato. Non ha load balancer, nessuna API e nessun indirizzo IP pubblico. Il suo security group non ha regole in entrata, quindi nulla può aprire una connessione al servizio finché non consenti un chiamante. Il servizio può comunque effettuare chiamate in uscita, ad esempio a un database o ad altri servizi AWS.

## Eseguire il Servizio Localmente

Il target `<name>-serve` esegue il server sulla tua macchina, senza un container:

<NxCommands commands={['run your-project:service-serve']} />

Il server ascolta sulla porta nella variabile d'ambiente `PORT`. Il target `<name>-serve` la imposta su una porta che il generatore assegna, partendo da 8081 e saltando le porte che altri progetti nel tuo workspace già utilizzano. All'interno del container il server ascolta sulla porta 8080.

Il server ascolta sull'indirizzo nella variabile d'ambiente `HOST`, che per impostazione predefinita è `127.0.0.1`, quindi il target `<name>-serve` accetta connessioni solo dalla tua macchina. L'immagine imposta `HOST=0.0.0.0`, quindi all'interno di un task il server ascolta sull'interfaccia di rete del task stesso. Il security group del task decide comunque chi può connettersi.

Verifica che il server sia attivo con la sua route di health, che restituisce lo stato 200 e `{"status":"ok"}`:

```bash
curl http://localhost:<port>/health
```

Il server ha anche una route di esempio che sostituisci con le tue route. `GET /echo?message=<x>` restituisce `{"message":"<x>"}`. Il parametro `message` è obbligatorio e può essere lungo al massimo 1024 caratteri. Una richiesta senza di esso, o con un valore più lungo, ottiene lo stato 422.

## Costruire e Scansionare l'Immagine

Il target `<name>-docker` costruisce un'immagine linux/arm64 del tuo servizio. Esegue prima il target `bundle-arm`, che scrive il tuo codice e le sue dipendenze linux/arm64 in `dist/<project root>/bundle-arm`. Il target aggregato `bundle` dipende da `bundle-arm`. Il target `<name>-docker` quindi copia quella cartella, il `Dockerfile` e il `.dockerignore` in `dist/<project root>/docker/<name>`, e costruisce l'immagine con quella cartella come contesto di build (i file che la build dell'immagine può leggere). Utilizza il motore di container con cui è configurato il tuo workspace, `docker` o [Finch](https://runfinch.com/). Il target viene eseguito come parte del target aggregato `docker`, che costruisce ogni immagine nel progetto.

<NxCommands commands={['run your-project:service-docker']} />

Su ECS, un comando di health check viene eseguito all'interno del container e chiama `GET /health` sulla porta del container. Non necessita di accesso in entrata. ECS sostituisce un task il cui health check continua a fallire. ECS ignora un'istruzione `HEALTHCHECK` nel Dockerfile. Per maggiori informazioni su come vengono costruite e pubblicate le immagini, vedi <Link path="/guides/docker-bundling">Docker Bundling</Link>.

## Distribuire il Servizio

### Aggiungere il Servizio alla Tua Infrastruttura

Il costrutto e il modulo non creano mai un VPC. Crei o importi uno nel tuo stack o modulo root e lo passi. I task vengono eseguiti in subnet private con egress, che raggiungono i servizi AWS attraverso un NAT gateway (un gateway gestito che consente alle subnet private di effettuare connessioni in uscita) o attraverso VPC endpoint (connessioni private dal tuo VPC ai servizi AWS).

<Infrastructure>
<Fragment slot="cdk">
Il costrutto CDK viene creato in `common/constructs` e denominato secondo il tuo servizio. Esempio di utilizzo con un nuovo VPC:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyService } from '@my-scope/common-constructs';
import { Stack, StackProps } from 'aws-cdk-lib';
import { SubnetType, Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ApplicationStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    new MyService(this, 'MyService', {
      vpc,
      vpcSubnets: { subnetType: SubnetType.PRIVATE_WITH_EGRESS },
    });
  }
}
```

Per utilizzare un VPC esistente, cercalo con `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` e passalo come `vpc`.
</Fragment>
<Fragment slot="terraform">
Il modulo Terraform viene creato in `common/terraform`. L'immagine del servizio viene pubblicata nel repository di asset condiviso, quindi istanzia il modulo `core/asset-ecr` una volta per distribuzione e passa i suoi output a ogni modulo di servizio. Passa anche gli output del modulo condiviso `runtime_config_appconfig`, che contengono l'applicazione AWS AppConfig da cui il servizio legge la sua <Link path="/guides/runtime-config">configurazione runtime</Link>:

```hcl title="packages/infra/src/main.tf"
module "asset_ecr" {
  source = "../../common/terraform/src/core/asset-ecr"
}

module "my_service" {
  source = "../../common/terraform/src/app/services/my-service"

  vpc_id     = aws_vpc.main.id
  subnet_ids = aws_subnet.private[*].id

  asset_ecr_repository_url = module.asset_ecr.repository_url
  asset_ecr_repository_arn = module.asset_ecr.repository_arn

  appconfig_application_id  = module.runtime_config_appconfig.application_id
  appconfig_application_arn = module.runtime_config_appconfig.application_arn
}
```
</Fragment>
</Infrastructure>

### Eseguire Senza un NAT Gateway

Quando i tuoi task si avviano, ECS estrae l'immagine e invia i log per loro conto. Il codice del tuo server può anche chiamare i servizi AWS. Nelle subnet private senza NAT gateway, ognuna di queste chiamate necessita di un VPC endpoint. Senza gli endpoint giusti, i task non riescono ad avviarsi o vanno in timeout quando chiamano AWS.

Crea questi endpoint nel VPC, sostituendo `<region>` con la tua Regione AWS:

| Endpoint | Tipo | Chi lo usa |
| --- | --- | --- |
| `com.amazonaws.<region>.ecr.api` | Interface | ECS, per autenticarsi con Amazon ECR e cercare l'immagine |
| `com.amazonaws.<region>.ecr.dkr` | Interface | ECS, per estrarre l'immagine da Amazon ECR |
| `com.amazonaws.<region>.s3` | Gateway | ECS, per scaricare i layer dell'immagine, che Amazon ECR memorizza in Amazon S3 |
| `com.amazonaws.<region>.logs` | Interface | L'output dei log del container, inviato ad Amazon CloudWatch Logs |
| `com.amazonaws.<region>.secretsmanager` | Interface | ECS, per leggere i segreti che passi al container quando un task si avvia |
| `com.amazonaws.<region>.appconfigdata` | Interface | Il tuo codice, per leggere la <Link path="/guides/runtime-config">configurazione runtime</Link> da AWS AppConfig |
| `com.amazonaws.<region>.sts` | Interface | Il tuo codice, quando richiede credenziali temporanee da AWS STS (ad esempio per assumere un altro ruolo) |

Gli endpoint di interfaccia necessitano di un security group che consenta HTTPS (porta 443) dai task. Per dettagli sugli endpoint Amazon ECR, vedi [Amazon ECR interface VPC endpoints](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html).

### Impostazioni di Sicurezza Predefinite

L'infrastruttura generata applica queste impostazioni per impostazione predefinita:

- Il security group del servizio non ha regole in entrata. Nessun chiamante all'interno o all'esterno del VPC può connettersi ai task finché non aggiungi una regola.
- I task vengono eseguiti in subnet private e non ottengono mai un indirizzo IP pubblico.
- Il generatore non crea load balancer né API davanti al servizio.
- I task possono inviare traffico in uscita solo sulla porta 443. Le connessioni ai database aggiungono la porta del database.
- Il ruolo del task (il ruolo con cui viene eseguito il codice del tuo server) può solo leggere la configurazione runtime da AWS AppConfig finché tu o una connessione non concedete di più.
- Il ruolo di esecuzione (il ruolo che ECS utilizza per avviare il tuo task) può solo estrarre l'immagine del servizio, scrivere nel suo log group e leggere i segreti che elenchi.
- I segreti raggiungono il container solo come riferimenti ad AWS Secrets Manager o AWS Systems Manager Parameter Store, mai come valori di ambiente in chiaro.
- Il container ha un file system root di sola lettura con una cartella `/tmp` scrivibile, e viene eseguito come uid 1000, un utente non root. ECS Exec (accesso shell in un task in esecuzione) è disattivato.
- Una distribuzione che non supera i controlli di salute si ferma e torna alla versione precedente.
- Il log group è crittografato con una chiave AWS KMS e i log vengono conservati per un anno.

### Consentire a un Chiamante di Raggiungere il Servizio

Nulla può chiamare il servizio come generato. Se un altro carico di lavoro nel VPC deve chiamarlo, ad esempio una funzione Lambda o un altro servizio ECS, aggiungi tu stesso una regola in entrata al security group del servizio. Il generatore non aggiunge regole in entrata. Consenti un chiamante nominato tramite il suo security group, sulla porta del container, e non consentire mai un intervallo di indirizzi.

<Infrastructure>
<Fragment slot="cdk">
Il costrutto implementa `IConnectable`, quindi consenti il security group del chiamante attraverso le sue `connections`:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { Port } from 'aws-cdk-lib/aws-ec2';

const svc = new MyService(this, 'MyService', { vpc });
svc.connections.allowFrom(callerSecurityGroup, Port.tcp(8080));
```

Se il security group del chiamante è definito nella tua app CDK e limita il traffico in uscita, `allowFrom` aggiunge anche la regola in uscita corrispondente ad esso.
</Fragment>
<Fragment slot="terraform">
Aggiungi una regola in entrata al security group del servizio, che il modulo del tuo servizio restituisce come `security_group_id`, con il security group del chiamante come sorgente:

```hcl title="packages/infra/src/main.tf"
resource "aws_vpc_security_group_ingress_rule" "caller_to_my_service" {
  security_group_id            = module.my_service.security_group_id
  referenced_security_group_id = aws_security_group.caller.id
  from_port                    = 8080
  to_port                      = 8080
  ip_protocol                  = "tcp"
}
```

Se il security group del chiamante limita il traffico in uscita, aggiungi anche un `aws_vpc_security_group_egress_rule` sul gruppo del chiamante verso il security group del servizio.
</Fragment>
</Infrastructure>

Il chiamante si connette all'indirizzo IP privato di un task. Il generatore non configura service discovery e l'indirizzo di un task cambia quando ECS sostituisce il task. Per dare ai chiamanti un nome stabile, configura tu stesso il service discovery, ad esempio con [Amazon ECS Service Connect](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect.html).

### Configurazione Avanzata

Il servizio generato imposta il suo nome e la sua immagine per te. Gli esempi seguenti utilizzano direttamente il costrutto generico `EcsService` e il modulo `ecs-service`, per impostazioni che il servizio generato non passa.

In CDK, il tuo pacchetto `common-constructs` esporta `EcsService` accanto al costrutto del tuo servizio, quindi lo importi allo stesso modo: `import { EcsService } from '@my-scope/common-constructs'`. Il costrutto generato estende `EcsService` e passa ogni altra prop, ad esempio `cluster`, `environment`, `secrets` e `grantTaskRole`. La sua prop opzionale `image` sostituisce l'immagine costruita dal tuo progetto.

In Terraform, il modulo del tuo servizio ti consente di impostare solo alcune delle variabili del modulo `ecs-service`: `vpc_id`, `subnet_ids`, `cluster_arn`, `environment`, `secrets`, `task_role_policy_statements` e `tags`. Per impostare qualsiasi altra variabile, modifica il blocco `module "ecs_service"` nel modulo del tuo servizio.

Terraform concede l'accesso pull solo quando passi anche l'ARN del repository come `image_repository_arn`.

#### Dimensionamento e Scalabilità

Ogni task ottiene 256 unità CPU (un quarto di una vCPU) e 512 MiB di memoria per impostazione predefinita. Il servizio avvia un task e l'autoscaling mantiene tra uno e due task in esecuzione, aggiungendo task quando l'uso medio della CPU supera il 70%.

| Impostazione | Prop CDK | Variabile Terraform | Predefinito |
| --- | --- | --- | --- |
| Unità CPU per task | `cpu` | `cpu` | 256 |
| Memoria per task (MiB) | `memoryLimitMiB` | `memory` | 512 |
| Task all'avvio | `desiredCount` | `desired_count` | 1 |
| Minimo di task | `minCapacity` | `min_capacity` | 1 |
| Massimo di task | `maxCapacity` | `max_capacity` | 2 |
| CPU media target (%) | `targetCpuUtilizationPercent` | `target_cpu_utilization` | 70 |

Il ruolo del task del costrutto o modulo del tuo servizio inizia con accesso in lettura solo alla configurazione runtime. Aggiungi i permessi di cui il tuo codice ha bisogno:


#### Utente del Container

La definizione del task esegue il container come uid 1000, un utente non root. Il Dockerfile fornito corrisponde: crea un utente `app` con uid e gid 1000 e imposta `USER 1000:1000`. Per eseguire come un altro utente, imposta la prop CDK `user` o la variabile Terraform `container_user`. Terraform rifiuta `0` e `root`.

| Impostazione | Prop CDK | Variabile Terraform | Predefinito |
| --- | --- | --- | --- |
| Utente con cui viene eseguito il container | `user` | `container_user` | `'1000'` (CDK), `"1000:1000"` (Terraform) |

In Terraform, `container_user` è una variabile del modulo `ecs-service`. Il modulo del tuo servizio non la passa, quindi impostala nel suo blocco `module "ecs_service"`.

### Costo

Un container service fattura mentre è inattivo, a differenza di una funzione Lambda. Queste parti fatturano all'ora indipendentemente dal fatto che qualcuno chiami o meno il servizio:

- Task Fargate, per vCPU e per GB di memoria. `desiredCount` e `minCapacity` mantengono almeno un task in esecuzione.
- Endpoint VPC di interfaccia, per ora in ogni Zona di Disponibilità, o un NAT gateway, per ora e per GB di dati che elabora.
- Archiviazione dei log in CloudWatch Logs e archiviazione delle immagini in Amazon ECR.

Per stimare il costo per la tua Regione e traffico, usa il [AWS Pricing Calculator](https://calculator.aws/).

### Distruggere il Servizio

Per rimuovere il servizio, distruggi lo stack o la configurazione Terraform che lo contiene:

<Infrastructure>
<Fragment slot="cdk">
Esegui il target `destroy` del tuo progetto di infrastruttura, che esegue `cdk destroy`:

<NxCommands commands={['run infra:destroy']} />
</Fragment>
<Fragment slot="terraform">
Esegui il target `destroy` del tuo progetto di infrastruttura:

<NxCommands commands={['run infra:destroy']} />
</Fragment>
</Infrastructure>

Quindi verifica nella console AWS o con l'AWS CLI che il servizio ECS e il cluster siano spariti. Con Terraform, destroy elimina anche il log group del servizio e pianifica la sua chiave AWS KMS per l'eliminazione dopo 7 giorni. Con CDK, destroy mantiene il log group del servizio e la sua chiave AWS KMS, perché CDK mantiene i log group e le chiavi a meno che una removal policy non dica diversamente. Eliminali tu stesso se non hai più bisogno dei log. Le immagini rimangono in Amazon ECR, nel repository degli asset CDK o nel repository condiviso `asset-ecr`. Eliminale se non ne hai più bisogno. Il VPC è tuo, quindi distruggere il servizio lo lascia al suo posto.
</OptionFilter>

## Connettere il Servizio

Usa il generatore <Link path="/guides/connection">`connection`</Link> per connettere il tuo servizio ad altri progetti nel tuo workspace:

Il tuo servizio può utilizzare un database relazionale o una tabella DynamoDB. Ogni connessione ha la sua guida:

Una connessione necessita di un servizio con `infra` impostato su `ecs`.
