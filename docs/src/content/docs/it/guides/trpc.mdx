[tRPC](https://trpc.io/) è un framework per la creazione di API in TypeScript con type safety end-to-end. Utilizzando tRPC, gli aggiornamenti agli input e output delle operazioni API si riflettono immediatamente nel codice client e sono visibili nel tuo IDE senza la necessità di ricostruire il progetto.

Il generatore di API tRPC crea una nuova API tRPC con configurazione dell'infrastruttura AWS CDK o Terraform. Il backend generato è esposto tramite un'API AWS API Gateway e include la validazione dello schema utilizzando [Zod](https://zod.dev/). Configura [AWS Lambda Powertools](https://docs.powertools.aws.dev/lambda/typescript/latest/) per l'osservabilità, inclusi logging strutturato e metriche CloudWatch.

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambda hosting">
Anche il tracing AWS X-Ray è configurato.

Le tue procedure vengono eseguite su AWS Lambda, quindi non c'è alcun server da gestire e paghi solo per le richieste che servi.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="ECS hosting">
Le tue procedure vengono eseguite come server HTTP di lunga durata in un container su Amazon ECS, dietro un'API Gateway HTTP API. Vedi <a href="#running-on-amazon-ecs">Running on Amazon ECS</a> per cosa cambia, incluso il motivo per cui il tracing X-Ray non produce tracce lì.
</OptionFilter>

`http-ecs` è sperimentale. Il suo output generato può cambiare tra le versioni senza una migrazione per portare avanti un workspace esistente, quindi aspettati di riconciliare queste modifiche tu stesso quando aggiorni.

## Implementare la tua API tRPC

Ad alto livello, le API tRPC consistono in un router che delega le richieste a procedure specifiche. Ogni procedura ha un input e un output, definiti come schema Zod.

### Schema

La directory `src/schema` contiene i tipi condivisi tra il codice client e server. In questo package, questi tipi sono definiti utilizzando [Zod](https://zod.dev/), una libreria di dichiarazione e validazione di schemi TypeScript-first.

Un esempio di schema potrebbe apparire come segue:

```ts
import { z } from 'zod';

// Schema definition
export const UserSchema = z.object({
  name: z.string(),
  height: z.number(),
  dateOfBirth: z.string().datetime(),
});

// Corresponding TypeScript type
export type User = z.TypeOf<typeof UserSchema>;
```

Dato lo schema sopra, il tipo `User` è equivalente al seguente TypeScript:

```ts
interface User {
  name: string;
  height: number;
  dateOfBirth: string;
}
```

Gli schemi sono condivisi sia dal codice server che client, fornendo un unico punto da aggiornare quando si apportano modifiche alle strutture utilizzate nella tua API.

Gli schemi vengono automaticamente validati dalla tua API tRPC a runtime, il che evita di dover creare manualmente logica di validazione personalizzata nel tuo backend.

Zod fornisce potenti utility per combinare o derivare schemi come `.merge`, `.pick`, `.omit` e altro. Puoi trovare maggiori informazioni sul [sito della documentazione Zod](https://zod.dev/?id=basic-usage).

### Router e Procedure

Il tuo router tRPC è definito in `src/router.ts`, che registra tutte le procedure. Ogni procedura definisce l'input, l'output e l'implementazione previsti.

<OptionFilter not when={{ infra: 'http-ecs' }} description="The Lambda entry point">
Il punto di ingresso dell'handler Lambda è in `src/handler.ts`, che inoltra le richieste al tuo router.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="The container entry point">
Il punto di ingresso è `src/<api-name>-container/server.ts`, il server HTTP che il container esegue, che inoltra le richieste al tuo router.
</OptionFilter>

Il router di esempio generato per te ha una singola operazione, chiamata `echo`:

```ts
import { echo } from './procedures/echo.js';

export const appRouter = router({
  echo,
});
```

La procedura di esempio `echo` viene generata per te in `src/procedures/echo.ts`:

```ts
export const echo = publicProcedure
  .input(EchoInputSchema)
  .output(EchoOutputSchema)
  .query((opts) => ({ message: opts.input.message }));
```

Per analizzare quanto sopra:

- `publicProcedure` definisce un metodo pubblico sull'API, incluso il middleware configurato in `src/middleware`. Questo middleware include l'integrazione AWS Lambda Powertools per logging, tracing e metriche.
- `input` accetta uno schema Zod che definisce l'input previsto per l'operazione. Le richieste inviate per questa operazione vengono automaticamente validate rispetto a questo schema.
- `output` accetta uno schema Zod che definisce l'output previsto per l'operazione. Vedrai errori di tipo nella tua implementazione se non restituisci un output conforme allo schema.
- `query` accetta una funzione che definisce l'implementazione per la tua API. Questa implementazione riceve `opts`, che contiene l'`input` passato alla tua operazione, così come altro contesto configurato dal middleware, disponibile in `opts.ctx`. La funzione passata a `query` deve restituire un output conforme allo schema `output`.

L'uso di `query` per definire l'implementazione indica che l'operazione non è mutativa. Usalo per definire metodi per recuperare dati. Per implementare un'operazione mutativa, usa invece il metodo `mutation`.

Se aggiungi una nuova procedura, assicurati di registrarla aggiungendola al router in `src/router.ts`.

<OptionFilter when={{ infra: 'rest-lambda' }} description="Streaming subscriptions — REST API only, uses SSE">
### Subscriptions (Streaming)

Le subscriptions tRPC ti permettono di trasmettere dati dal server al client utilizzando [Server-Sent Events (SSE)](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events). Quando selezioni `rest-lambda` come tipo di compute, il generatore configura automaticamente l'infrastruttura richiesta per lo streaming, così come un handler Lambda di streaming e l'helper di schema `ZodAsyncIterable`.

Per definire una procedura subscription, usa il metodo `.subscription` con una funzione generatore asincrona. Usa l'helper `ZodAsyncIterable` da `src/schema/z-async-iterable.ts` per definire lo schema di output:

```ts
import { publicProcedure } from '../init.js';
import { z } from 'zod';
import { ZodAsyncIterable } from '../schema/z-async-iterable.js';

const InputSchema = z.object({ query: z.string() });
const ChunkSchema = z.object({ text: z.string() });

export const myStream = publicProcedure
  .input(InputSchema)
  .output(
    ZodAsyncIterable({
      yield: ChunkSchema,
    }),
  )
  .subscription(async function* (opts) {
    // Yield data to the client as it becomes available
    for (const chunk of await getResults(opts.input.query)) {
      yield { text: chunk };
    }
  });
```

Registra la subscription nel tuo router proprio come qualsiasi altra procedura:

```ts
export const appRouter = router({
  echo,
  myStream,
});
```

L'infrastruttura generata utilizza un handler Lambda di streaming con `ResponseTransferMode.STREAM` in API Gateway per tutte le operazioni REST API, il che consente alle subscriptions di funzionare insieme a query e mutations regolari.
</OptionFilter>

## Personalizzare la tua API tRPC

### Errori

Nella tua implementazione, puoi restituire risposte di errore ai client lanciando un `TRPCError`. Questi accettano un `code` che indica il tipo di errore, per esempio:

```ts
throw new TRPCError({
  code: 'NOT_FOUND',
  message: 'The requested resource could not be found',
});
```

### Organizzare le Tue Operazioni

Man mano che la tua API cresce, potresti voler raggruppare operazioni correlate insieme.

Puoi raggruppare operazioni insieme utilizzando router annidati, per esempio:

```ts
import { getUser } from './procedures/users/get.js';
import { listUsers } from './procedures/users/list.js';

const appRouter = router({
   users: router({
      get: getUser,
      list: listUsers,
   }),
   ...
})
```

I client ricevono quindi questo raggruppamento di operazioni, per esempio invocare l'operazione `listUsers` in questo caso potrebbe apparire come segue:

```ts
client.users.list.query();
```

### Logging

Il logger AWS Lambda Powertools è configurato in `src/middleware/logger.ts`, e può essere accessibile in un'implementazione API tramite `opts.ctx.logger`. Puoi usarlo per registrare su CloudWatch Logs, e/o controllare valori aggiuntivi da includere in ogni messaggio di log strutturato. Per esempio:

```ts {5}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      opts.ctx.logger.info('Operation called with input', opts.input);

      return ...;
   });
```

Per maggiori informazioni sul logger, consulta la [documentazione AWS Lambda Powertools Logger](https://docs.powertools.aws.dev/lambda/typescript/latest/core/logger/).

### Registrare Metriche

Le metriche AWS Lambda Powertools sono configurate in `src/middleware/metrics.ts`, e possono essere accessibili in un'implementazione API tramite `opts.ctx.metrics`. Puoi usarle per registrare metriche in CloudWatch senza la necessità di importare e utilizzare l'AWS SDK, per esempio:

```ts {5}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      opts.ctx.metrics.addMetric('Invocations', 'Count', 1);

      return ...;
   });
```

Per maggiori informazioni, consulta la [documentazione AWS Lambda Powertools Metrics](https://docs.powertools.aws.dev/lambda/typescript/latest/core/metrics/).

### Ottimizzare il Tracing X-Ray

Il tracer AWS Lambda Powertools è configurato in `src/middleware/tracer.ts`, e può essere accessibile in un'implementazione API tramite `opts.ctx.tracer`. Puoi usarlo per aggiungere tracce con AWS X-Ray per fornire informazioni dettagliate sulle prestazioni e il flusso delle richieste API. Per esempio:

```ts {5-7}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      const subSegment = opts.ctx.tracer.getSegment()!.addNewSubsegment('MyAlgorithm');
      // ... my algorithm logic to capture
      subSegment.close();

      return ...;
   });
```

Per maggiori informazioni, consulta la [documentazione AWS Lambda Powertools Tracer](https://docs.powertools.aws.dev/lambda/typescript/latest/core/tracer/).

<OptionFilter when={{ infra: 'http-ecs' }} description="X-Ray produces no traces on ECS">
:::caution[Nessuna traccia su ECS]
Le chiamate sopra vengono eseguite senza errori in un container, ma non producono tracce. Powertools disattiva il suo tracer quando non è in esecuzione in Lambda, quindi `getSegment()` restituisce un subsegment placeholder che non viene mai inviato da nessuna parte. Vedi <a href="#observability">Observability</a> per cosa ottieni e cosa aggiungere se hai bisogno di tracce.
:::
</OptionFilter>

### Implementare Middleware Personalizzato

Puoi aggiungere valori aggiuntivi al contesto fornito alle procedure implementando middleware.

Come esempio, implementiamo del middleware per estrarre alcuni dettagli sull'utente chiamante dalla nostra API in `src/middleware/identity.ts`.

<OptionFilter when={{ auth: 'iam', infra: ['rest-lambda', 'http-lambda'] }} description="Identity middleware example for IAM-authenticated APIs on Lambda">
Questo esempio illustra il middleware di identità per l'autenticazione `IAM`. Cerchiamo il chiamante in Cognito utilizzando il sub estratto dall'evento API Gateway.

La ricerca utilizza il client Cognito Identity Provider, che non è una dipendenza di un'API tRPC generata. Installalo prima nel tuo progetto API:

<InstallCommand pkg={`@aws-sdk/client-cognito-identity-provider@${TS_VERSIONS['@aws-sdk/client-cognito-identity-provider']}`} project="@my-scope/my-api" />

Prima, definiamo cosa aggiungeremo al contesto:

```ts
export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}
```

Nota che definiamo una proprietà aggiuntiva _opzionale_ al contesto. tRPC gestisce l'assicurazione che questa sia definita nelle procedure che hanno configurato correttamente questo middleware.

Successivamente, implementeremo il middleware stesso. Questo ha la seguente struttura:

```ts
export const createIdentityPlugin = () => {
   const t = initTRPC.context<...>().create();
   return t.procedure.use(async (opts) => {
      // Add logic here to run before the procedure

      const response = await opts.next(...);

      // Add logic here to run after the procedure

      return response;
   });
};
```

Nel nostro caso, vogliamo estrarre dettagli sull'utente Cognito chiamante. Lo faremo estraendo l'ID soggetto dell'utente (o "sub") dall'evento API Gateway e recuperando i dettagli dell'utente da Cognito. L'implementazione varia a seconda che l'evento sia stato fornito alla nostra funzione da una REST API o da un'HTTP API:

<Tabs syncKey="http-rest">
<TabItem label="REST API" _filter={{ infra: 'rest-lambda' }}>
```ts
import { CognitoIdentityProvider } from '@aws-sdk/client-cognito-identity-provider';
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEvent } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext & CreateAWSLambdaContextOptions<APIGatewayProxyEvent>
    >()
    .create();

  const cognito = new CognitoIdentityProvider();

  return t.procedure.use(async (opts) => {
    const cognitoAuthenticationProvider =
      opts.ctx.event.requestContext?.identity?.cognitoAuthenticationProvider;

    let sub: string | undefined = undefined;
    if (cognitoAuthenticationProvider) {
      const providerParts = cognitoAuthenticationProvider.split(':');
      sub = providerParts[providerParts.length - 1];
    }

    if (!sub) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `Unable to determine calling user`,
      });
    }

    const { Users } = await cognito.listUsers({
      // Assumes user pool id is configured in lambda environment
      UserPoolId: process.env.USER_POOL_ID!,
      Limit: 1,
      Filter: `sub="${sub}"`,
    });

    if (!Users || Users.length !== 1) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `No user found with subjectId ${sub}`,
      });
    }

    // Provide the identity to other procedures in the context
    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username: Users[0].Username!,
        },
      },
    });
  });
};
```
</TabItem>

import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEventV2WithIAMAuthorizer } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext &
        CreateAWSLambdaContextOptions<APIGatewayProxyEventV2WithIAMAuthorizer>

    .create();

  const cognito = new CognitoIdentityProvider();

  return t.procedure.use(async (opts) => {
    const cognitoIdentity = opts.ctx.event.requestContext?.authorizer?.iam
      ?.cognitoIdentity as unknown as
      | {
          amr: string[];
        }
      | undefined;

    const sub = (cognitoIdentity?.amr ?? [])
      .flatMap((s) => (s.includes(':CognitoSignIn:') ? [s] : []))
      .map((s) => {
        const parts = s.split(':');
        return parts[parts.length - 1];

        code: 'FORBIDDEN',
        message: `Unable to determine calling user`,

      // Assumes user pool id is configured in lambda environment

    });

    if (!Users || Users.length !== 1) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `No user found with subjectId ${sub}`,
      });
    }

    // Provide the identity to other procedures in the context
    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username: Users[0].Username!,

<OptionFilter when={{ auth: 'cognito', infra: ['rest-lambda', 'http-lambda'] }} description="Identity middleware example for Cognito-authenticated APIs on Lambda">
Quando effettui il deploy con `auth: 'cognito'`, l'authorizer Cognito di API Gateway verifica il JWT che il chiamante fornisce nell'header `Authorization` e posiziona i claims verificati sull'evento Lambda. Il nostro middleware legge semplicemente quei claims — nessuna chiamata AWS SDK extra, nessuna verifica JWT manuale.

Prima, definiamo cosa aggiungeremo al contesto:

```ts
export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}
```

Nota che definiamo una proprietà aggiuntiva _opzionale_ sul contesto. tRPC gestisce l'assicurazione che questa sia definita nelle procedure che hanno configurato correttamente questo middleware.

Successivamente, il middleware stesso. Il tipo di evento e la posizione dei claims differiscono tra una REST API e un'HTTP API, quindi l'implementazione dipende dalla tua `infra` selezionata:

<Tabs syncKey="http-rest">
<TabItem label="REST API" _filter={{ infra: 'rest-lambda' }}>
L'authorizer Cognito User Pools di una REST API posiziona i claims in `event.requestContext.authorizer.claims`:

```ts
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEvent } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext & CreateAWSLambdaContextOptions<APIGatewayProxyEvent>
    >()
    .create();

  return t.procedure.use(async (opts) => {
    const claims = opts.ctx.event.requestContext?.authorizer?.claims as
      | Record<string, string>
      | undefined;

    const sub = claims?.sub;
    const username = claims?.username ?? claims?.['cognito:username'];

    if (!sub || !username) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: 'Unable to determine calling user',
      });
    }

    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username,
        },
      },
    });
  });
};
```
</TabItem>
<TabItem label="HTTP API" _filter={{ infra: 'http-lambda' }}>
L'authorizer JWT di un'HTTP API fornisce un evento payload-v2 i cui claims si trovano un livello più in profondità, in `event.requestContext.authorizer.jwt.claims`. Il contesto deve essere tipizzato su `APIGatewayProxyEventV2WithJWTAuthorizer` per corrispondere a quello utilizzato dal `publicProcedure` generato — altrimenti `.concat()` fallisce con l'errore `Context mismatch` di tRPC:

```ts
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEventV2WithJWTAuthorizer } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext &
        CreateAWSLambdaContextOptions<APIGatewayProxyEventV2WithJWTAuthorizer>
    >()
    .create();

  return t.procedure.use(async (opts) => {
    const claims = opts.ctx.event.requestContext?.authorizer?.jwt?.claims as
      | Record<string, string>
      | undefined;

    const sub = claims?.sub;
    const username = claims?.username ?? claims?.['cognito:username'];

    if (!sub || !username) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: 'Unable to determine calling user',
      });
    }

    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username,
        },
      },
    });
  });
};
```
</TabItem>
</Tabs>

Puoi quindi mescolare il plugin in qualsiasi procedura che necessita dell'identità del chiamante:

```ts
import { publicProcedure } from '../init.js';
import { createIdentityPlugin } from '../middleware/identity.js';
import { z } from 'zod';

export const me = publicProcedure
  .concat(createIdentityPlugin())
  .output(z.object({ sub: z.string(), username: z.string() }))
  .query(({ ctx }) => ({
    sub: ctx.identity!.sub,
    username: ctx.identity!.username,
  }));
```

Non hai bisogno di `aws-jwt-verify` o di qualsiasi altra libreria di verifica JWT qui — l'authorizer Cognito User Pools di API Gateway ha già verificato la firma, l'emittente, gli scope e la scadenza prima che il tuo Lambda venga eseguito. Se uno di questi controlli fallisce, API Gateway restituisce `401 Unauthorized` e il tuo handler non viene mai invocato.
:::

<OptionFilter when={{ infra: 'http-ecs' }} description="How ECS hosting works, what it costs and what it limits">
## Running on Amazon ECS

Con `infra` impostato su `http-ecs`, le tue procedure vengono eseguite come server HTTP di lunga durata in un container anziché in una funzione Lambda. Una richiesta segue questo percorso:

1. Un chiamante firma una richiesta all'API Gateway HTTP API, che è l'unico punto di ingresso pubblico. Ogni route porta l'authorizer per l'`auth` che hai scelto, quindi una richiesta non autenticata viene rifiutata al bordo.
2. API Gateway inoltra la richiesta attraverso un VPC link, che è il suo percorso privato nel tuo VPC.
3. Il VPC link raggiunge un load balancer interno. Il load balancer non ha indirizzo pubblico e la sua unica regola in entrata consente il security group del VPC link sulla porta del listener.
4. Il load balancer inoltra la richiesta a un task. L'unica regola in entrata dei task consente il security group del load balancer sulla porta del container, quindi nient'altro nel VPC può aprire una connessione ad essi.

I task vengono eseguiti in subnet private e non ottengono mai un indirizzo IP pubblico. Niente in questo percorso consente un intervallo di indirizzi in entrata.

Per impostazione predefinita il servizio, il load balancer e il VPC link vanno nelle subnet `PRIVATE_WITH_EGRESS` del VPC, che raggiungono AWS attraverso un NAT gateway. Passare `vpcSubnets: { subnetType: SubnetType.PRIVATE_ISOLATED }` a `defaultIntegrations` elimina il NAT gateway e il suo costo orario, ma le subnet isolate non hanno una route in uscita, quindi il VPC ha poi bisogno di quattro VPC endpoint affinché i task si avviino: endpoint di interfaccia per `ecr.api` e `ecr.dkr` per estrarre l'immagine, un endpoint gateway S3 perché i layer dell'immagine sono oggetti S3, e un endpoint di interfaccia per `logs` in modo che il driver `awslogs` possa scrivere. Senza di essi un task non può estrarre la sua immagine e ECS riporta indietro il deployment sul circuit breaker senza dire perché.

Il VPC link, il load balancer, il suo listener, il target group e il bucket in cui il load balancer scrive i suoi access log sono creati da un costrutto, `core/api/ecs-http-endpoint.ts` in `common/constructs`, che ogni API ospitata su ECS condivide. Il costrutto della tua API nomina il suo servizio container e instrada ogni operazione a quell'endpoint.

### What Runs in the Container

`src/<api-name>-container/server.ts` è un server `node:http` con due compiti. `GET /health` risponde `{"status":"ok"}`, che è ciò che chiamano il target group del load balancer e il health check del container. Ogni altra richiesta va al [tRPC standalone adapter](https://trpc.io/docs/server/adapters/standalone), che la risolve rispetto al tuo router.

Non c'è evento API Gateway nel container, quindi il contesto della procedura non porta alcun campo `event`, `context` o `info`: per `http-ecs` l'`IMiddlewareContext` fornito nomina solo ciò che il middleware ci mette. L'authorizer decide ancora se una richiesta raggiunge il container, ma i suoi claims non arrivano con la richiesta, quindi gli esempi di middleware di identità sopra non si applicano. Per leggere l'identità del chiamante in una procedura, mappa il contesto dell'authorizer su un header di richiesta nel tuo costrutto API e leggi quell'header.

### Observability

Log e metriche funzionano come su Lambda: il container scrive nel suo gruppo di log CloudWatch e il plugin delle metriche pubblica le metriche di ogni richiesta nel formato di metrica incorporato affinché CloudWatch Logs le estragga.

Il plugin delle metriche costruisce un oggetto metriche per ogni richiesta e lo passa alle tue procedure come `opts.ctx.metrics`, quindi una metrica che una richiesta aggiunge non viene mai pubblicata con quella di un'altra. Questo conta di più qui che su Lambda, dove un'invocazione possiede le metriche dall'inizio alla fine; questo server gestisce le richieste contemporaneamente. Aggiungi le tue metriche attraverso `opts.ctx.metrics` piuttosto che un oggetto `Metrics` tuo, che condividerebbe un archivio attraverso ogni richiesta nel processo.

Il tracing AWS X-Ray no. Powertools disattiva il suo tracer fuori da Lambda e non c'è daemon X-Ray nel task per ricevere segmenti, quindi le chiamate `opts.ctx.tracer` vengono eseguite senza errori e non producono tracce. Aggiungi un daemon come sidecar nel tuo servizio container se ne hai bisogno.

Il log di accesso dell'API Gateway HTTP API registra ogni richiesta che raggiunge l'API. Il load balancer scrive i suoi access log in un bucket che il costrutto `EcsHttpEndpoint` crea, che è dove puoi vedere quale task ha servito una richiesta e cosa ha risposto.

### Image Build and Scanning

Il generatore di container fornisce i target dell'immagine, denominati come la tua API:

- `<api-name>-container-docker` costruisce un'immagine linux/arm64, eseguendo prima `bundle` in modo che l'immagine contenga il server bundled.
- `<api-name>-container-trivy` scansiona quell'immagine per vulnerabilità.

Vedi <Link path="/guides/ts-container">TypeScript Container Service</Link> per come viene costruita l'immagine e <Link path="/guides/docker-bundling">Docker Bundling</Link> per come viene pubblicata al momento del deploy.

### Limits

- **Integration timeout.** Le API Gateway HTTP API limitano un'integrazione a circa 30 secondi. Una procedura che impiega più tempo di quello fallisce al gateway per quanto a lungo il container continui a lavorare.
- **No streaming.** Le subscriptions tRPC necessitano dell'infrastruttura `rest-lambda`. Un'HTTP API non può trasmettere una risposta in streaming.
- **Payload size.** Richieste e risposte seguono il limite di 10 MB di API Gateway.
- **One service for every operation.** `integrationPattern` è `shared`: c'è un servizio container e ogni route è instradata ad esso. L'opzione si risolve sempre in `shared` per questa infrastruttura e `isolated` viene ignorato con un avviso.

### Cost

Il load balancer è il nuovo costo fisso rispetto a Lambda, dove paghi per richiesta e niente quando inattivo. Cifre mensili approssimative in us-east-1, prima del trasferimento dati:

| Elemento | Approssimativamente |
| --- | --- |
| Load balancer interno | $16 più unità di capacità del load balancer |
| Task Fargate, 0.25 vCPU / 0.5 GB arm64 | $7 per task |
| NAT gateway, se il tuo VPC ne ha uno | $33 |
| VPC link | nessun costo orario |
| Storage S3 per gli access log del load balancer | centesimi per GB al mese |

Quindi un servizio a un task costa circa $23 al mese prima di qualsiasi traffico, e di più se il VPC che passi ha un NAT gateway. Gli access log crescono con il traffico: aggiungi una regola del ciclo di vita a `endpoint.accessLogsBucket` per farli scadere. Controlla le pagine dei prezzi di [Elastic Load Balancing](https://aws.amazon.com/elasticloadbalancing/pricing/) e [AWS Fargate](https://aws.amazon.com/fargate/pricing/) per i prezzi correnti nella tua Region.
</OptionFilter>
