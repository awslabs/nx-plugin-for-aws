#### `-dev` vs `-serve`

Il generatore aggiunge due target che eseguono lo stesso server sulla stessa porta. Differiscono solo nell'ambiente che impostano:

| Target | Ambiente | Usare per |
| --- | --- | --- |
| `<your-agent-name>-dev` | `PORT`, `LOCAL_DEV=true` | Sviluppo locale |
| `<your-agent-name>-serve` | `PORT` | Esercitare il percorso del codice distribuito localmente |

**Usa `<your-agent-name>-dev` per lo sviluppo locale.** `LOCAL_DEV=true` commuta l'agente sui suoi percorsi di codice locali: lo stato della sessione viene scritto su disco sotto `tmp/agents/` alla radice del workspace, e qualsiasi server MCP connesso viene raggiunto tramite HTTP diretto anziché attraverso AgentCore. È anche il target che il target `dev` a livello di progetto aggrega, e quello che il target `<your-agent-name>-chat` si aspetta di trovare in esecuzione.

`<your-agent-name>-serve` esegue lo stesso percorso di codice del tuo agente distribuito, che risolve lo storage della sessione e gli ARN di runtime connessi dalla <Link path="guides/runtime-config">Configurazione Runtime</Link> in AppConfig. Ciò richiede che `RUNTIME_CONFIG_APP_ID` sia impostato sull'id dell'applicazione AppConfig di una distribuzione (output come `RuntimeConfigApplicationId` dallo stack distribuito), insieme alle credenziali AWS autorizzate a leggerlo:

```bash
RUNTIME_CONFIG_APP_ID=<app-id> nx run your-project:agent-serve
```

:::caution[`-serve` necessita di configurazione distribuita]
Avviato senza `RUNTIME_CONFIG_APP_ID`, `<your-agent-name>-serve` accetta richieste ma ogni invocazione fallisce con `RUNTIME_CONFIG_APP_ID is not set — cannot resolve connected agent ARNs from AppConfig.`

Imposta `LOCAL_DEV=true` per utilizzare invece i percorsi di codice locali — che è ciò che `<your-agent-name>-dev` fa già per te.
:::
