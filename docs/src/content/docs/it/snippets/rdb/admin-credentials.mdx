---
title: Credenziali Admin
---
import Infrastructure from '@components/infrastructure.astro';

La password dell'utente admin (master) di Aurora viene generata e ruotata da Aurora stesso in AWS Secrets Manager, utilizzando [password utente master gestite da RDS](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/rds-secrets-manager.html). Il tuo codice di infrastruttura non riceve mai la password, quindi non può trapelare in un template CloudFormation o in un file di stato Terraform. Aurora ruota il segreto ogni 7 giorni senza alcuna funzione di rotazione da distribuire o mantenere.

Il segreto è crittografato con la stessa chiave KMS gestita dal cliente del cluster.

La tua applicazione non utilizza mai queste credenziali. Si connette come utente database con privilegi minimi utilizzando l'autenticazione IAM — solo i gestori di migrazione e create-db-user leggono il segreto admin, e a ciascuno viene concesso l'accesso solo a quel segreto e alla sua chiave KMS.

<Infrastructure>
<Fragment slot="cdk">

Il segreto admin è esposto come `secret.secretArn` sul cluster sottostante, e `grantSecretRead` concede a un consumatore l'accesso in lettura ad esso:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyDatabase } from '@my-scope/common-constructs';

const db = new MyDatabase(this, 'Db', { ... });

db.grantSecretRead(myFunction);
```
</Fragment>
<Fragment slot="terraform">

L'ARN del segreto admin è esposto come output `secret_arn`, insieme al `kms_key_arn` necessario per decrittografarlo:

```hcl title="packages/infra/src/main.tf"
module "my_database" {
  source = "../../common/terraform/src/app/dbs/my-database"
  ...
}

output "database_secret_arn" {
  value = module.my_database.secret_arn
}
```

Un segreto gestito da RDS contiene un oggetto JSON con solo `username` e `password` — nessun dettaglio di connessione. Prendi l'host, la porta e il nome del database dagli output `writer_endpoint`, `cluster_port` e `database_name` del modulo.
</Fragment>
</Infrastructure>

:::caution[Rotazione manuale]
La rotazione della password admin al di fuori della pianificazione di Aurora viene eseguita tramite l'API RDS (`modify-db-cluster --rotate-master-user-password --apply-immediately`), non tramite Secrets Manager. L'associazione della propria funzione di rotazione a un segreto gestito da RDS viene rifiutata.
:::
