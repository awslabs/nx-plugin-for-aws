Lo script di configurazione crea l'identità AWS IoT per un dispositivo core, avvia un'istanza EC2 Ubuntu 26.04 x86_64 e installa il nucleus Greengrass classico su di essa tramite AWS Systems Manager. Registra ciò che ha creato in `.greengrass-tutorial.env`, associato al tuo account, Region e prefisso, in modo che la sua operazione `cleanup` elimini esattamente quelle risorse in seguito.

| Risorsa | Nome | Creato da |
| --- | --- | --- |
| Gruppo di thing IoT | `<prefix>-group` | Script |
| Thing IoT | `<prefix>-core` | Script |
| Ruolo di scambio token e la sua policy di accesso | `<prefix>-token-exchange`, `<prefix>-token-exchangeAccess` | Script |
| Alias del ruolo IoT | `<prefix>-alias` | Script |
| Policy IoT del dispositivo | `<prefix>-device-policy` | Script |
| Istanza EC2 | Taggata `Name=<prefix>-core` | Script |
| Certificato del dispositivo e chiave privata | Generati sull'istanza | Installer del nucleus |
| Policy IoT per l'alias del ruolo | `GreengrassTESCertificatePolicy<prefix>-alias` | Installer del nucleus |

L'installer viene eseguito sull'istanza con le credenziali temporanee del profilo di istanza. La chiave privata del dispositivo viene creata sull'istanza e rimane sotto `/greengrass/v2`. Il comando remoto che lo script invia tramite Systems Manager contiene solo nomi di risorse, quindi nessuna chiave o credenziale entra nella cronologia dei comandi di Systems Manager.

## Task 1: Crea il profilo di istanza

Lo script non crea il profilo di istanza. Tu ne sei il proprietario, quindi controlli cosa è consentito fare all'installer. Il suo ruolo necessita di `AmazonSSMManagedInstanceCore`, in modo che Systems Manager possa eseguire il comando di installazione, più una policy temporanea per il percorso `--provision true` dell'installer.

```bash
export TUTORIAL_ACCOUNT_ID=$(aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" \
  sts get-caller-identity --query Account --output text)

cat > /tmp/greengrass-tutorial-ec2-trust.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Principal": { "Service": "ec2.amazonaws.com" }, "Action": "sts:AssumeRole" }
  ]
}
EOF

aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam create-role \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --assume-role-policy-document file:///tmp/greengrass-tutorial-ec2-trust.json
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam attach-role-policy \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore
```

La policy temporanea dell'installer segue la [policy IAM minima per l'installer](https://docs.aws.amazon.com/greengrass/v2/developerguide/provision-minimal-iam-policy.html). L'istruzione `CreateIoTResources` è quella ufficiale. L'istruzione IAM è più ristretta dell'istruzione ufficiale `CreateTokenExchangeRole`: lo script crea il ruolo di scambio token e la sua policy `<role>Access` prima che l'installer venga eseguito, quindi l'installer le legge solamente e non ha mai bisogno di `iam:CreateRole`, `iam:CreatePolicy` o `iam:AttachRolePolicy`.

```bash
cat > /tmp/greengrass-tutorial-installer.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReuseTokenExchangeRole",
      "Effect": "Allow",
      "Action": ["iam:GetRole", "iam:PassRole", "iam:GetPolicy"],
      "Resource": [
        "arn:aws:iam::${TUTORIAL_ACCOUNT_ID}:role/${TUTORIAL_PREFIX}-token-exchange",
        "arn:aws:iam::${TUTORIAL_ACCOUNT_ID}:policy/${TUTORIAL_PREFIX}-token-exchangeAccess",
        "arn:aws:iam::aws:policy/${TUTORIAL_PREFIX}-token-exchangeAccess"
      ]
    },
    {
      "Sid": "CreateIoTResources",
      "Effect": "Allow",
      "Action": [
        "iot:AddThingToThingGroup",
        "iot:AttachPolicy",
        "iot:AttachThingPrincipal",
        "iot:CreateKeysAndCertificate",
        "iot:CreatePolicy",
        "iot:CreateRoleAlias",
        "iot:CreateThing",
        "iot:CreateThingGroup",
        "iot:DescribeEndpoint",
        "iot:DescribeRoleAlias",
        "iot:DescribeThingGroup",
        "iot:GetPolicy"
      ],
      "Resource": "*"
    }
  ]
}
EOF

aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam put-role-policy \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --policy-name greengrass-installer-bootstrap \
  --policy-document file:///tmp/greengrass-tutorial-installer.json
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam create-instance-profile \
  --instance-profile-name "${TUTORIAL_PREFIX}-instance"
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam add-role-to-instance-profile \
  --instance-profile-name "${TUTORIAL_PREFIX}-instance" \
  --role-name "${TUTORIAL_PREFIX}-instance"
```

Il Task 4 rimuove `greengrass-installer-bootstrap` nuovamente una volta che il dispositivo è stato sottoposto a provisioning.

## Task 2: Seleziona l'immagine Ubuntu 26.04 x86_64

Canonical pubblica i suoi ID immagine correnti come parametri pubblici di Systems Manager. Leggi quello per Ubuntu 26.04 su amd64, quindi conferma il proprietario, l'architettura e il nome prima di utilizzarlo:

```bash
export TUTORIAL_AMI_ID=$(aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ssm get-parameter \
  --name /aws/service/canonical/ubuntu/server/26.04/stable/current/amd64/hvm/ebs-gp3/ami-id \
  --query Parameter.Value --output text)

aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ec2 describe-images \
  --image-ids "$TUTORIAL_AMI_ID" \
  --query 'Images[0].[OwnerId,Architecture,Name]' --output text
```

L'output deve mostrare il proprietario `099720109477` (Canonical), l'architettura `x86_64` e un nome contenente `ubuntu-resolute-26.04-amd64-server`. Lo script controlla gli stessi tre valori e rifiuta qualsiasi altra immagine.

Ubuntu 26.04 viene utilizzato per due motivi. Include `python3.14`, che è l'interprete che il passaggio `Run` della ricetta generata fissa. Include anche `sudo-rs` come `sudo` predefinito, che può impedire l'avvio dei componenti IPC sotto Nucleus 2.18.3 perché l'ambiente IPC viene perso. Lo script installa `openjdk-21-jre-headless`, `unzip`, `python3.14` e il pacchetto `sudo` classico, che fornisce `/usr/bin/sudo.ws`, quindi seleziona `/usr/bin/sudo.ws` come `sudo` e verifica la selezione prima di installare il nucleus. Nell'immagine Canonical sia `sudo` che `sudo-rs` sono preinstallati, quindi il cambio delle alternative è il passaggio effettivo. Vedi le <Link path="guides/greengrass-component#risoluzione-dei-problemi-e-limiti-del-servizio">note sulla risoluzione dei problemi del componente</Link>.

## Task 3: Scarica ed esegui lo script di configurazione

Scarica lo script da questo sito di documentazione, leggilo, quindi eseguilo dalla radice del workspace:

<Code lang="bash" code={`curl -fsSLo setup-greengrass-tutorial.sh ${setupScriptUrl}\nchmod +x setup-greengrass-tutorial.sh\nless setup-greengrass-tutorial.sh`} />

Lo stesso file è registrato nel repository in `docs/public/greengrass/setup-tutorial.sh`.

```bash
./setup-greengrass-tutorial.sh setup \
  --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" --prefix "$TUTORIAL_PREFIX" \
  --ami-id "$TUTORIAL_AMI_ID" --instance-profile "${TUTORIAL_PREFIX}-instance"
```

Passa `--subnet-id <subnet-id>` quando la Region non ha un VPC predefinito. Passa `--instance-type` per modificare il valore predefinito `t3.small`.

Lo script esegue questi passaggi in ordine e scrive il file di stato dopo ogni risorsa creata:

1. Risolve l'identità del chiamante, convalida l'immagine e verifica che il profilo di istanza esista.
2. Verifica che nessuna delle risorse nella tabella sopra esista ancora. Un gruppo di thing, thing, ruolo, policy o alias del ruolo esistente sotto il prefisso ferma lo script prima che crei qualsiasi cosa.
3. Crea il gruppo di thing e il thing, il ruolo di scambio token con la sua policy di accesso, l'alias del ruolo e la policy IoT del dispositivo. La policy IoT è la [policy minima del dispositivo core](https://docs.aws.amazon.com/greengrass/v2/developerguide/device-auth.html#greengrass-core-minimal-iot-policy) dalla guida per sviluppatori, più `iot:Publish` su `arn:aws:iot:<region>:<account-id>:topic/tutorial/greengrass/heartbeat`.
4. Avvia l'istanza con il profilo di istanza e IMDSv2 richiesto, attende che si registri con Systems Manager e invia un comando `AWS-RunShellScript` che installa i prerequisiti, cambia `sudo`, scarica `greengrass-nucleus-latest.zip` ed esegue l'installer con `--provision true --setup-system-service true`, i nomi di thing, gruppo, policy, ruolo e alias sopra, e `--component-default-user ggc_user:ggc_group`.
5. Interroga il comando fino al suo completamento, quindi registra il certificato che l'installer ha allegato al thing e attende che il dispositivo core appaia in Greengrass.

La configurazione richiede circa dieci minuti. Quando termina, carica i valori registrati nella tua shell e mantieni il file di stato fuori da Git:

```bash
source .greengrass-tutorial.env
echo .greengrass-tutorial.env >> .gitignore
```

Il file di stato esporta `TUTORIAL_THING_NAME`, `TUTORIAL_THING_GROUP_ARN`, `TUTORIAL_TOKEN_EXCHANGE_ROLE_ARN`, `TUTORIAL_INSTANCE_ID`, `TUTORIAL_CERTIFICATE_ARN` e l'identità a cui è associato. Il Modulo 3 passa due di essi allo stack CDK.

<Aside type="note" title="Riesecuzioni e fallimenti">
Eseguire nuovamente `setup` dopo un'esecuzione riuscita riporta l'istanza esistente e non cambia nulla. Se un'esecuzione si interrompe a metà, ad esempio perché il comando di installazione fallisce, il file di stato registra fino a dove è arrivato e una riesecuzione rifiuta di continuare. Esegui `cleanup` con lo stesso profilo, Region e prefisso, correggi la causa, quindi esegui nuovamente `setup`. La pulizia tocca solo le risorse che il file di stato registra, tollera gli oggetti che sono già spariti e si ferma su qualsiasi altro errore.
</Aside>

## Task 4: Rimuovi i permessi temporanei dell'installer

L'installer ha terminato. Rimuovi la policy di bootstrap in modo che l'istanza mantenga solo l'accesso a Systems Manager:

```bash
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam delete-role-policy \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --policy-name greengrass-installer-bootstrap
```

## Task 5: Controlla il dispositivo

Il nucleus registra il dispositivo core al suo primo avvio. Confermalo dal cloud:

```bash
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" greengrassv2 get-core-device \
  --core-device-thing-name "$TUTORIAL_THING_NAME" \
  --query '{status: status, coreVersion: coreVersion, platform: platform, architecture: architecture}'
```

Aspettati `HEALTHY`, `linux` e `amd64`. Per leggere un log sull'istanza, invia un comando Systems Manager con un file di parametri. La prima riga è uno shebang, che `AWS-RunShellScript` rispetta:

```bash
cat > /tmp/greengrass-tutorial-command.json <<'EOF'
{ "commands": ["#!/bin/bash", "tail -n 20 /greengrass/v2/logs/greengrass.log"] }
EOF

TUTORIAL_COMMAND_ID=$(aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ssm send-command \
  --instance-ids "$TUTORIAL_INSTANCE_ID" --document-name AWS-RunShellScript \
  --parameters file:///tmp/greengrass-tutorial-command.json \
  --query Command.CommandId --output text)
sleep 5
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ssm get-command-invocation \
  --command-id "$TUTORIAL_COMMAND_ID" --instance-id "$TUTORIAL_INSTANCE_ID" \
  --query StandardOutputContent --output text
```

Il Modulo 3 utilizza lo stesso pattern per leggere il log del componente stesso.
