## Task 1: Implementare l'API del gioco

Implementeremo le seguenti API in questa sezione:

1. `saveGame` - creare o aggiornare un gioco.
2. `queryGames` - restituire un elenco paginato dei giochi salvati del giocatore autenticato.
3. `queryInventory` - restituire un elenco paginato di oggetti nell'inventario di un giocatore.
4. `queryActions` - restituire la cronologia delle conversazioni per un determinato gioco.

:::note[Dove risiede ogni parte dello stato]
- `games` e `inventory` sono in **DynamoDB** (tramite ElectroDB) — le lambda dell'API del gioco e il server MCP Inventory li leggono/scrivono.
- `actions` (trascrizione della chat) è in **S3** — l'`S3SessionManager` dello Story Agent scrive un blob JSON per turno, e `queryActions` nell'API del gioco li legge in modo che l'UI possa riprodurre la cronologia al ricaricamento della pagina. Non esiste una procedura `saveAction`; l'agente è l'unico scrittore.
:::

:::tip[Tutto è limitato al giocatore autenticato]
Entrambi gli archivi sono indicizzati sul chiamante, quindi un giocatore non può mai vedere le avventure di un altro:

- **Games** sono partizionati in DynamoDB sul `sub` Cognito dell'utente, quindi `queryGames` interroga quella partizione invece di scansionare la tabella. Due giocatori possono anche scegliere lo stesso nome dell'eroe senza collisioni.
- **Conversations** sono organizzate in namespace dall'agente, quindi le chiavi appaiono come `session_u-<sub>-<threadId>/…`.
- **Inventory** è indicizzato sulla sessione dell'agente chiamante più il nome del giocatore. Il server MCP Inventory legge quella sessione dal contesto della richiesta piuttosto che fidarsi del `playerName` che il modello passa — un argomento del modello non è un confine di fiducia.

Né il `userId` né il namespace vengono presi dal corpo della richiesta — il sito web potrebbe mentire al riguardo. `requireUserId` in `identity.ts` legge il chiamante dal contesto dell'autorizzatore IAM che il Cognito Identity Pool popola (`requestContext.authorizer.iam.cognitoIdentity.amr`, che contiene una voce `…:CognitoSignIn:<sub>`). Quel valore è prodotto dallo scambio di token dell'Identity Pool, quindi è affidabile piuttosto che fornito dal browser, e le richieste senza di esso vengono rifiutate. Vedi <Link path="guides/trpc">Implementing Custom Middleware</Link> per la versione riutilizzabile di questo come plugin tRPC.
:::

## Task 4: Testare l'API del gioco localmente

Non è necessario distribuire su AWS per provare la nostra API — il target `dev` esegue l'API del gioco contro [DynamoDB Local](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DynamoDBLocal.html). Poiché abbiamo collegato l'API del gioco al progetto `DungeonDb` nel Modulo 1, questo target avvia anche DynamoDB Local automaticamente.

### Avviare il server locale

Avvia l'API del gioco localmente con il target `dev`, che avvia anche DynamoDB Local:

<NxCommands commands={["dev game-api"]} />

<Aside type="tip" title="Prima esecuzione">
La prima esecuzione scarica l'immagine del container DynamoDB Local, che potrebbe richiedere un momento. Lascia il server in esecuzione in questo terminale e apri un secondo terminale per i comandi `curl` qui sotto.
</Aside>

### Testare l'API

Una volta che il server è attivo e funzionante, interroga l'elenco (vuoto) dei giochi:

```bash
curl -X GET 'http://localhost:2022/games.query?input=%7B%7D'
```

:::note[Codifica URL]
Il `%7B%7D` che passiamo per testare l'API è un oggetto JSON vuoto codificato in URI (`{}`).
:::

Vedrai un elenco vuoto:

```json
{"result":{"data":{"items":[],"cursor":null}}}
```

Ora salva un gioco:

```bash
curl -X POST 'http://localhost:2022/games.save' \
  -H 'Content-Type: application/json' \
  -d '{"playerName":"Alice","genre":"zombie"}'
```

Il salvataggio restituisce il gioco persistito (con il timestamp `lastUpdated` che l'entità imposta per te):

```json
{"result":{"data":{"playerName":"Alice","genre":"zombie","lastUpdated":"..."}}}
```

Interroga di nuovo per confermare che è persistito in DynamoDB Local:

```bash
curl -X GET 'http://localhost:2022/games.query?input=%7B%7D'
```

Questa risposta ora include il gioco salvato:

```json
{"result":{"data":{"items":[{"playerName":"Alice","genre":"zombie","lastUpdated":"..."}],"cursor":null}}}
```

Puoi fermare il server locale (`Ctrl+C`) una volta terminato.

## Task 5: Testare il server MCP Inventory localmente

Possiamo provare gli strumenti del server MCP con l'[MCP Inspector](https://github.com/modelcontextprotocol/inspector) utilizzando il target generato `mcp-server-inspect`:

<NxCommands commands={["mcp-server-inspect inventory"]} />

Questo serve il server MCP localmente (avviando anche DynamoDB Local) e lancia l'MCP Inspector su `http://localhost:6274` preconfigurato per connettersi ad esso. Clicca su **Connect**, passa alla scheda **Tools**, clicca su **List Tools** e prova `add-to-inventory` (ad es. `playerName: Alice`, `itemName: Rusty Sword`, `emoji: ⚔️`) seguito da `list-inventory-items` per vederlo persistito in DynamoDB Local. Ferma il server (`Ctrl+C`) quando hai finito.
