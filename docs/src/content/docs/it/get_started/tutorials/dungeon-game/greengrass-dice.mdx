Mantieni il dungeon che hai distribuito nel <Link path="get_started/tutorials/dungeon-game/4">Modulo 4</Link>.
Prima di distruggerlo, fornisci al suo Story Agent un dispositivo per i dadi:

> "Provo a scassinare la serratura. Lancia un d20 per vedere se ci riesco."

L'agente chiama `roll-dice`. Un componente Python su un core Greengrass produce
il lancio, e lo strumento MCP restituisce quel risultato del dispositivo all'agente. La risposta
può quindi dire "d20: 17" e descrivere l'esito.

Questo percorso opzionale utilizza un core EC2 con un simulatore di dadi software. Puoi
successivamente sostituire la sua funzione di numeri casuali con input da un vassoio di dadi fisico.
Il <Link path="get_started/tutorials/greengrass/overview">tutorial Greengrass autonomo</Link>
rimane un modo separato per imparare la generazione di componenti da un workspace vuoto.

## Cosa aggiungerai

```d2
direction: right
player: Player
agent: Story Agent
tool: "Inventory MCP server\nroll-dice"
dice_shadow: "AWS IoT Core\nnamed shadow: dungeon-dice"
device: "Greengrass core\ncom.example.DungeonDice"
player -> agent: "Attempt an action"
agent -> tool: "roll-dice(sides=20)"
tool -> dice_shadow: "Desired request + request ID"
dice_shadow -> device: "MQTT delta through IPC"
device -> dice_shadow: "Reported result + same ID"
dice_shadow -> tool: "Correlated result"
tool -> agent: "d20 = 17"
agent -> player: "Result and consequence"
```

Lo shadow cloud contiene una richiesta in sospeso e il risultato più recente. Lo
strumento attende fino a 12 secondi; non genera mai un lancio di fallback. Un controllo
di versione impedisce ai chiamanti concorrenti di sostituire una richiesta attiva. Il dispositivo
memorizza il suo ultimo risultato prima di pubblicare, quindi la riconsegna MQTT e un riavvio
del componente non rilanciano la stessa richiesta.

Questa sandbox condivide un dispositivo per i dadi tra i giocatori. Un dispositivo occupato restituisce un
errore. Non aggiunge una coda a livello di flotta né associa dispositivi personali con
utenti Cognito. Queste sono estensioni separate per un prodotto multi-giocatore.

## 1. Provisiona un core senza smantellare il dungeon

Utilizza lo stesso account AWS e la stessa Region del dungeon distribuito. Imposta il profilo
esplicitamente; utilizza un nuovo prefisso per le risorse del dispositivo:

```bash
export TUTORIAL_AWS_PROFILE=<your-dungeon-profile>
export TUTORIAL_AWS_REGION=<your-dungeon-region>
export TUTORIAL_PREFIX=gg-dungeon-dice
```

Segui <Link path="get_started/tutorials/greengrass/2">Provisiona il dispositivo core</Link>
dal **workspace del dungeon**, inclusa la rimozione della policy temporanea dell'installer.
Quella pagina crea l'istanza e scrive `.greengrass-tutorial.env`.
Non creare un altro workspace Nx né eseguire i moduli heartbeat autonomi.
Le impostazioni predefinite esistenti dello script di setup rimangono invariate.

```bash
source .greengrass-tutorial.env
export DICE_IOT_ENDPOINT=$(aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" \
  iot describe-endpoint --endpoint-type iot:Data-ATS --query endpointAddress --output text)
```

Inizializza lo shadow nominato del nuovo dispositivo una volta, prima di abilitare lo strumento. Non
eseguire questo reset su un dispositivo con una richiesta di dadi attiva:

```bash
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" \
  iot-data update-thing-shadow --endpoint-url "https://${DICE_IOT_ENDPOINT}" \
  --thing-name "$TUTORIAL_THING_NAME" --shadow-name dungeon-dice \
  --cli-binary-format raw-in-base64-out \
  --payload '{"state":{"desired":{"command":null},"reported":{"command":null,"result":null}}}' \
  /tmp/dungeon-dice-shadow.json
```

La procedura EC2 utilizza x86_64 Linux. Un Raspberry Pi con Linux a 64 bit utilizza
`linux-arm64` invece; sia la ricetta generata che le dipendenze native devono
targetizzare quell'architettura. Vedi <Link path="guides/greengrass-component#hardware-e-sistemi-operativi">supporto hardware</Link>.
Un ESP32 può fornire input da sensori a un gateway, ma non può eseguire questo componente Python.

Mantieni il resto dello stack dell'applicazione esistente. `DiceResources` possiede i
parametri del dispositivo, la concessione dell'artifact, il componente e il suo
deployment.

Ci sono tre confini di permessi:

- La policy del certificato IoT esistente del core consente la pubblicazione, la sottoscrizione
  e la ricezione su `$aws/things/<thing-name>/shadow/*`, che include già
  lo shadow nominato `dungeon-dice`. Non è necessaria alcuna policy del certificato aggiuntiva.
- La ricetta dice concede al componente l'accesso a quei topic tramite IPC.
- Il runtime Inventory MCP ottiene `GetThingShadow` e `UpdateThingShadow` su
  solo lo shadow nominato `dungeon-dice` di questa thing.

La concessione dell'artifact consente al ruolo di scambio token del core di recuperare solo
`com.example.DungeonDice/*`. Il deployment dipende dalla pubblicazione del componente.

```bash
  --output table
```

## 5. Lascia che l'agente lanci

Apri il gioco distribuito, avvia una nuova conversazione o ricarica quella esistente,
e chiedi:

> "Lancia un d20 sul dispositivo dei dadi per il mio tentativo di scassinare questa serratura."

L'agente dovrebbe invocare `roll-dice` e descrivere il valore restituito e la
conseguenza. Leggi lo shadow cloud per confrontare il suo `reported.result` con il
risultato dello strumento e la risposta dell'agente:

```bash
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" \
  iot-data get-thing-shadow --endpoint-url "https://${DICE_IOT_ENDPOINT}" \
  --thing-name "$TUTORIAL_THING_NAME" --shadow-name dungeon-dice \
  /tmp/dungeon-dice-shadow.json
cat /tmp/dungeon-dice-shadow.json
```

Un risultato riuscito include `requestId`, `sides`, `value` e `rolledAt`.
Il log del dispositivo in `/greengrass/v2/logs/com.example.DungeonDice.log` registra lo
stesso ID di richiesta e valore. Un deployment riuscito da solo non prova questo
round trip.

Per esercitare il percorso di fallimento, ferma il servizio Greengrass su questo core usa e getta
tramite il suo terminale Systems Manager, richiedi un altro lancio e verifica
che lo strumento riporti un errore dopo la sua attesa limitata. L'agente dovrebbe dirti
che il dispositivo non è disponibile invece di decidere la sfida. Riavvia il
servizio prima di continuare. Una richiesta in sospeso scaduta non deve lanciare quando il
dispositivo si riconnette; una nuova chiamata dello strumento crea una nuova richiesta.

Per un esercizio di aggiornamento della versione, modifica il messaggio di log del componente, ricompila ed
esegui lo stesso comando deploy. `NEXT_PATCH` pubblica una nuova versione. Conferma la
nuova versione in esecuzione, quindi richiedi un altro lancio.

## 6. Continua a giocare o rimuovi tutto

Per rimuovere solo l'estensione:

1. Registra gli output `DiceArtifactBucket`, `DiceComponentArn` e `DiceDeploymentId`
   dallo stack dell'applicazione.
2. Rimuovi `this.deployment.addComponent(component)` da
   `packages/infra/src/dice-resources.ts`. Ridistribuisci con gli stessi parametri.
   Questo invia una revisione del deployment vuota; attendi fino a quando
   `list-installed-components` non elenca più `com.example.DungeonDice`.
3. Ripristina il <Link path="get_started/tutorials/dungeon-game/3">prompt base dello Story Agent</Link>,
   rimuovi l'import e la chiamata di `registerDiceTool`, e ripristina lo
   <Link path="get_started/tutorials/dungeon-game/2#collegare-lo-stack">stack dell'applicazione del Modulo 2</Link>.
   Ricompila e distribuisci il dungeon. Questo rimuove i permessi MCP e la sua
   configurazione dei dadi.
4. Elimina i record del deployment Greengrass conservati, le versioni dei componenti e
   il bucket degli artifact utilizzando <Link path="get_started/tutorials/greengrass/cleanup#task-3-eliminare-le-risorse-greengrass-conservate">la procedura di pulizia delle risorse conservate</Link>.
   Sostituisci `com.example.DungeonDice` con `com.example.Pulse` e utilizza gli
   output dei dadi registrati. Includi ogni versione/revisione creata dal tuo esercizio
   di aggiornamento.
5. Elimina lo shadow nominato, quindi esegui la pulizia dello script di setup e rimuovi il
   profilo dell'istanza e il ruolo gestiti dal proprietario come descritto nella
   <Link path="get_started/tutorials/greengrass/cleanup">guida alla pulizia del dispositivo</Link>.

```bash
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" \
  iot-data delete-thing-shadow --endpoint-url "https://${DICE_IOT_ENDPOINT}" \
  --thing-name "$TUTORIAL_THING_NAME" --shadow-name dungeon-dice \
  /tmp/dungeon-dice-shadow-deleted.json
```

Il dungeon rimane distribuito dopo questi passaggi. Per rimuovere l'intera applicazione,
continua con <Link path="get_started/tutorials/dungeon-game/wrap-up#distruzione-delle-risorse">Distruzione delle risorse</Link>,
incluso il suo user pool conservato, il ruolo SMS e il bucket della cronologia delle conversazioni.

## Ulteriori esperimenti

- Utilizza un Raspberry Pi con un OS a 64 bit e un sensore fisico. Mantieni l'ID di richiesta
  e il contratto di timeout mentre sostituisci `secrets.randbelow`.
- Utilizza un ESP32 per leggere il sensore e inviare il suo risultato al gateway Linux.
  Questo aggiunge firmware e autenticazione del dispositivo; non è un altro target CPU
  per questo componente Python.
- Dividi il componente in un motore di dadi locale e un bridge MQTT connesso
  tramite pub/sub Greengrass.
