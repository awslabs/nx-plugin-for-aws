#### `-dev` vs `-serve`

O gerador adiciona dois targets que executam o mesmo servidor na mesma porta. Eles diferem apenas no ambiente que definem:

| Target | Ambiente | Usar para |
| --- | --- | --- |
| `<your-agent-name>-dev` | `PORT`, `LOCAL_DEV=true` | Desenvolvimento local |
| `<your-agent-name>-serve` | `PORT` | Exercitar o caminho de código implantado localmente |

**Use `<your-agent-name>-dev` para desenvolvimento local.** `LOCAL_DEV=true` alterna o agente para seus caminhos de código locais: o estado da sessão é gravado em disco em `tmp/agents/` na raiz do workspace, e quaisquer servidores MCP conectados são acessados por HTTP direto em vez de através do AgentCore. É também o target que o target `dev` no nível do projeto agrega, e aquele que o target `<your-agent-name>-chat` espera encontrar em execução.

`<your-agent-name>-serve` executa o mesmo caminho de código que seu agente implantado, que resolve o armazenamento de sessão e ARNs de runtime conectados a partir da <Link path="guides/runtime-config">Runtime Configuration</Link> no AppConfig. Isso requer que `RUNTIME_CONFIG_APP_ID` seja definido como o id da aplicação AppConfig de uma implantação (saída como `RuntimeConfigApplicationId` pela stack implantada), juntamente com credenciais AWS permitidas para lê-lo:

```bash
RUNTIME_CONFIG_APP_ID=<app-id> nx run your-project:agent-serve
```

:::caution[`-serve` precisa de configuração implantada]
Iniciado sem `RUNTIME_CONFIG_APP_ID`, `<your-agent-name>-serve` aceita requisições, mas cada invocação falha com `RUNTIME_CONFIG_APP_ID is not set — cannot resolve connected agent ARNs from AppConfig.`

Defina `LOCAL_DEV=true` para usar os caminhos de código locais em vez disso — que é o que `<your-agent-name>-dev` já faz para você.
:::
