Este gerador cria um site de documentação alimentado por [Astro](https://astro.build/)
e o tema de documentação [Starlight](https://starlight.astro.build/). Ele configura
localização, snippets de conteúdo reutilizáveis, links internos com reconhecimento de localidade e um
plugin [`starlight-blog`](https://starlight-blog-docs.vercel.app/) por padrão.

Por padrão, ele também cria um pipeline de tradução automatizado alimentado por um
[Strands Agent](https://strandsagents.com/) no
[Amazon Bedrock](https://aws.amazon.com/bedrock/).

## Saída do Gerador

Por padrão, o gerador cria a seguinte estrutura de projeto em `docs/` na
raiz do workspace (configurável através das opções `name`, `directory` e `subDirectory`):

<FileTree>
  - astro.config.mjs Astro + Starlight configuration (locales, sidebar, blog plugin)
  - tsconfig.json Extends astro/tsconfigs/strict with @components / @assets path aliases
  - project.json Nx project with `build`, `start`, `preview` (and `translate` if enabled) targets
  - scripts
    - translate.ts Translation driver — a Strands agent with a scoped file-editor tool (omitted with `--noTranslation`)
    - translate.config.json Source/target locales, glob patterns, model id, region (omitted with `--noTranslation`)
  - .gitignore Ignores Astro's build output and generated types
  - src
    - content.config.ts Starlight's docs content collection definition
    - components
      - link.astro Locale-aware link component (resolves paths against the current locale)
      - snippet.astro Locale-aware snippet loader component
    - content
      - docs
        - en
          - index.mdx Landing page
          - guides
            - getting-started.mdx Sample guide referencing the link and snippet components
          - blog
            - welcome.mdx Sample blog post (omitted with `--noBlog`)
          - snippets
            - example.mdx Sample reusable snippet
    - styles
      - custom.css Starlight theme overrides
  - README.md Project README
</FileTree>

### Localização

O gerador usa como padrão uma única localidade (`en`) e redireciona a URL raiz para
ela. Para adicionar mais idiomas:

1. Adicione uma entrada em `locales` no `astro.config.mjs` (por exemplo `ko: { label: '한국어' }`).
2. Crie um diretório correspondente em `src/content/docs/<locale>/`.
3. Preencha-o manualmente ou use o target de tradução descrito abaixo.

## Tradução

A menos que você tenha passado `--noTranslation`, o gerador adiciona um target `translate` ao
`project.json`. Quais localidades ele traduz vem de `targetLanguages` em
`scripts/translate.config.json`, que vem vazio — então comece nomeando as
localidades que você deseja na linha de comando:

<NxCommands commands={[
  'translate docs -- --languages jp,ko',
  'translate docs -- --languages jp,ko --dry-run',
]} />

Uma vez que você tenha preenchido `targetLanguages` (veja [Configurando a
tradução](#configurando-a-tradução)), `--languages` se torna opcional e as
localidades configuradas são usadas:

<NxCommands commands={[
  'translate docs -- --all',
  'translate docs -- --dry-run',
]} />

:::caution[Configure seus idiomas de destino primeiro]
Sem `--languages` e com `targetLanguages` ainda vazio, o target sai com
código diferente de zero com `ERROR No target languages configured`.
:::

Quando executado sem `--all`, o script traduz apenas os arquivos que foram alterados
desde o último commit de tradução no branch atual — o que significa que você pode
executá-lo novamente com segurança em cada PR de documentação sem retraduzir todo o site.

Traduções cujo arquivo de origem não existe mais são excluídas, então renomear ou
remover uma página não deixa cópias obsoletas em cada localidade.

Cada tradução é escrita como um arquivo completo. O agente recebe o código-fonte, a
tradução existente e um diff do que mudou, e reutiliza a redação existente
para seções que o diff deixou intactas — então apenas a prosa que o diff tocou é
retraduzida, e blocos de código são copiados do código-fonte como estão.

### Configurando a tradução

Edite `scripts/translate.config.json` para alterar:

| Campo | Propósito |
| --- | --- |
| `sourceLanguage` | Localidade para traduzir **de** (padrão `en`). |
| `targetLanguages` | Localidades para traduzir **para**. Vazio por padrão. Por exemplo `["fr", "de", "es", "ja", "ko"]`. |
| `docsDir` | Caminho para o diretório de conteúdo de documentação, relativo à raiz do projeto. |
| `include` | Padrões glob (relativos a `<docsDir>/<sourceLanguage>`) para arquivos a traduzir. |
| `exclude` | Padrões glob a ignorar. |
| `modelId` | Modelo Bedrock a usar para traduções. |
| `awsRegion` | Região AWS com a qual o cliente Bedrock está configurado. Também pode ser definido via `AWS_REGION`. |
| `concurrency` | Número máximo de invocações simultâneas do agente. |
| `translationCommitMessage` | Marcador de mensagem de commit para commits de tradução. Não está na configuração gerada — adicione a chave para substituir seu padrão `docs: update translations`. |

### Links internos com reconhecimento de localidade

O gerador fornece um componente `Link` que resolve automaticamente caminhos internos
de documentação em relação à localidade atual, então uma única fonte de verdade produz
a URL correta em todos os idiomas:

```mdx
import Link from '@components/link.astro';

<Link path="guides/getting-started">Read the getting-started guide</Link>
```

### Snippets

Fragmentos de conteúdo reutilizáveis ficam em `src/content/docs/<locale>/snippets/`. O
componente `Snippet` gerado carrega o snippet que corresponde à localidade
atual:

```mdx
import Snippet from '@components/snippet.astro';

<Snippet name="example" />
```

### Configurando CI

Nenhum workflow de CI é gerado por padrão — adicione um que:

1. Configure credenciais AWS com permissão para invocar Bedrock `InvokeModel` no
   modelo configurado.
2. Execute o target `translate` em pull requests que tocam sua documentação no idioma de origem:

   <NxCommands commands={['translate docs']} />

3. Faça commit das traduções resultantes de volta ao branch do PR, usando
   `docs: update translations` como mensagem de commit, para que execuções
   incrementais subsequentes possam detectar o commit de linha de base e apenas
   retraduzir os arquivos que mudaram desde então. Para usar uma mensagem diferente, adicione uma
   chave `translationCommitMessage` em `scripts/translate.config.json` e corresponda
   esse valor em vez disso.
