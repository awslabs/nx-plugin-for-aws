<Link path="guides/react-website-auth">Autenticação de website</Link> cria um user pool do Amazon Cognito, e por padrão apenas usuários que têm um nome de usuário e senha nesse pool podem fazer login. Se sua equipe ou clientes já têm contas em um provedor de identidade (IdP), como Okta, Auth0 ou Microsoft Entra ID, eles precisariam de uma segunda conta apenas para o seu website.

Este gerador adiciona um provedor de identidade [OpenID Connect](https://openid.net/developers/how-connect-works/) (OIDC) externo ao user pool. A página de login então mostra um botão para o provedor de identidade ao lado do formulário de nome de usuário e senha.

## Como isso funciona

- Seu website ainda envia usuários para a página de login do Cognito. A página agora tem um botão nomeado após o provedor de identidade.
- Um usuário que escolhe o botão faz login no provedor de identidade. O provedor de identidade os envia de volta ao Cognito em seu URI de redirecionamento, `https://<cognito domain>/oauth2/idpresponse`.
- O Cognito cria um usuário no seu user pool para eles, um usuário federado, e copia as claims que você mapeia (por exemplo `email`) nos atributos do usuário.
- O Cognito então emite o mesmo tipo de tokens que emite para um usuário local. Suas APIs, agentes e identity pool os aceitam sem nenhuma alteração.

Usuários com um nome de usuário e senha no pool ainda podem fazer login.

## Quem pode fazer login

Adicionar um provedor de identidade pode permitir que muito mais pessoas entrem no seu website do que você espera. A opção `allowSignup` de `ts#website#auth` não se aplica a usuários federados. O Cognito cria um usuário federado na primeira vez que alguém faz login através do provedor de identidade, mesmo quando o user pool não permite que os usuários se cadastrem. Cada usuário federado também recebe a função autenticada do identity pool, para que possam chamar suas APIs e agentes como qualquer usuário conectado pode.

O provedor de identidade, portanto, decide quem pode fazer login. Configure-o para que faça login apenas das pessoas que precisam do seu website:

- Microsoft Entra ID: nas propriedades da aplicação empresarial da aplicação, defina "Assignment required?" como Yes e atribua apenas os usuários ou grupos que precisam de acesso. Com o padrão, No, todos os usuários no seu tenant podem fazer login.
- Okta: atribua a aplicação apenas aos grupos que precisam de acesso.
- Auth0: desabilite cadastros em cada conexão que a aplicação usa e habilite para a aplicação apenas as conexões cujos usuários precisam de acesso. Caso contrário, qualquer pessoa que se cadastre através de uma conexão habilitada, por exemplo uma conexão social, pode fazer login.

## Configurar seu provedor de identidade

O primeiro deploy após executar o gerador lê o client secret do Secrets Manager. Se o secret não existir, o deploy falha. Siga estas etapas nesta ordem. O gerador também as imprime quando termina.

1. Registre uma aplicação no provedor de identidade e anote seu client ID e client secret. Você adiciona seu URI de redirecionamento na etapa 4. Execute este gerador com `--clientId` definido como o client ID.
2. Armazene o client secret no Secrets Manager, sob o nome na opção `clientSecretName` (`<name>-oidc-client-secret` por padrão):

   ```bash
   aws secretsmanager create-secret --name TestIdp-oidc-client-secret --secret-string <client secret> --region <region>
   ```

   Defina `--region` para a região da sua stack. O secret deve existir nessa região antes do primeiro deploy. Armazene o secret como uma string simples, não JSON, porque o Cognito recebe o valor inteiro do secret como o client secret. No console do Secrets Manager, escolha Plaintext, não Key/value.

3. Faça o deploy.
4. Adicione o URI de redirecionamento à aplicação no provedor de identidade.

## Mapeamento de atributos

O user pool gerado requer os atributos `email`, `given_name` e `family_name`. O Cognito os preenche a partir das claims do provedor de identidade em cada login. Se o provedor de identidade não enviar um deles, o primeiro login do usuário falha. Portanto, o gerador recusa um `attributeMapping` que deixe de fora qualquer um dos três.

`attributeMapping` é um objeto JSON. Cada chave é um atributo do user pool, e cada valor é o nome da claim do provedor de identidade. O padrão mapeia cada atributo para a claim com o mesmo nome:

```json
{"email":"email","given_name":"given_name","family_name":"family_name"}
```

- Uma chave pode ser qualquer [atributo padrão](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html#cognito-user-pools-standard-attributes), como `name` ou `phone_number`, ou um atributo personalizado como `custom:department`.
- O Cognito trata um endereço de email mapeado como não verificado. Mapeie `email_verified` apenas de um provedor de identidade que verifica endereços de email por si só. Caso contrário, um usuário poderia definir o endereço de outra pessoa no provedor de identidade e tê-lo marcado como verificado no seu pool.
- Se o endereço de email de um usuário mudar no provedor de identidade, o Cognito escreve o novo endereço no user pool no próximo login do usuário. `email_verified` permanece `false`.
- Um atributo personalizado já deve existir no user pool, e deve ser mutável.

O arquivo do provedor de identidade Terraform também define dois valores que o Cognito adiciona quando retorna o provedor de identidade: `"username" = "sub"` em `attribute_mapping` e `attributes_url_add_attributes = "false"` em `provider_details`. Como o arquivo os define, um segundo `terraform plan` após o primeiro deploy não mostra nenhuma alteração no provedor de identidade. Se um segundo plan ainda mostrar uma alteração em `provider_details` com outro provedor de identidade, adicione essa chave ao arquivo com o valor que o plan mostra o Cognito retornando.

## Notas sobre provedores de identidade

As configurações abaixo vêm da documentação de cada fornecedor. Okta foi testado na AWS com CDK e Terraform. As configurações de Auth0 e Microsoft Entra ID foram verificadas contra o documento de descoberta OpenID publicado por cada fornecedor, mas não com um login ao vivo.

### Okta

Testado na AWS com CDK e Terraform. Crie uma OIDC Web Application no Okta, com o Authorization Code grant e um client secret. Defina seu URI de redirecionamento de login para o URI de redirecionamento `/oauth2/idpresponse` da etapa 4 de [Configurar seu provedor de identidade](#configurar-seu-provedor-de-identidade). Ele não precisa de URI de redirecionamento de logout. O issuer é seu domínio Okta, `https://<your-org>.okta.com`, que é a forma que foi testada. Um servidor de autorização personalizado, como `https://<your-org>.okta.com/oauth2/default`, também tem um issuer, mas essa forma não foi testada. Os escopos padrão, `openid email profile`, retornam `email`, `given_name` e `family_name`, então o mapeamento padrão funciona. Cada usuário precisa de um email, um primeiro nome e um sobrenome definidos no Okta. Atribua a aplicação apenas aos usuários ou grupos que precisam de acesso.

### Auth0

Verificado contra o documento de descoberta do Auth0, não testado com um login ao vivo. Crie uma Regular Web Application no Auth0. O issuer é `https://<your-tenant>.auth0.com/`, incluindo a barra final.

**Aviso:** o gerador também aceita o issuer sem a barra final, mas o login então falha, porque a claim `iss` nos tokens Auth0 tem a barra.

O Auth0 retorna `given_name` e `family_name` apenas quando a conexão do usuário os fornece. Usuários de uma conexão sem eles não podem fazer login até que você mapeie outras claims.

### Microsoft Entra ID

Verificado contra o documento de descoberta da Microsoft, não testado com um login ao vivo. Registre uma aplicação single-tenant no Entra ID. O issuer é `https://login.microsoftonline.com/<tenant-id>/v2.0`. O gerador recusa os issuers multi-tenant (`/common/`, `/organizations/` e `/consumers/`), porque eles aceitam usuários de qualquer tenant do Entra ID.

**Aviso:** o issuer não deve terminar com uma barra. Use `/v2.0`, não `/v2.0/`. O gerador aceita a forma com a barra, mas o login então falha, porque a claim `iss` nos tokens do Entra ID não tem barra.

Adicione `email`, `given_name` e `family_name` como claims opcionais ao token ID da aplicação. O Entra ID os envia apenas se você fizer isso. Cada usuário precisa ter o campo Mail definido. Caso contrário, a claim `email` fica vazia, e o primeiro login do usuário falha, porque o user pool requer `email`. A claim `email` do Entra ID não é verificada, então não mapeie `email_verified` do Entra ID.

### User pool do Cognito

Para testar com outro user pool do Cognito como provedor de identidade, use o issuer `https://cognito-idp.<region>.amazonaws.com/<user pool id>`. Dê ao seu app client um client secret, o authorization code grant e os escopos `openid email profile`.

## Segurança

- Identifique usuários pela claim `sub` (o ID único do usuário no seu user pool), nunca por `email`. Um usuário federado é um novo usuário no seu pool com seu próprio `sub`, mesmo quando seu email corresponde a um usuário local. O código que o plugin gera usa `sub`.
- Use um issuer single-tenant. Um issuer multi-tenant permite que usuários de qualquer organização façam login.
- Remova as URLs de callback `http://localhost` dos estágios de produção, conforme <Link path="guides/react-website-auth">autenticação de website</Link> descreve. A federação não adiciona nenhuma URL de callback.

## O que a federação não faz

- MFA (autenticação multifator) exigida no seu user pool não se aplica a usuários federados. O Cognito deixa sua autenticação para o provedor de identidade, então imponha MFA no provedor de identidade.
- Fazer logout do seu website encerra apenas a sessão do Cognito. Não encerra a sessão do usuário no provedor de identidade OIDC, então o próximo login através do botão pode ser concluído sem uma senha. Em um computador compartilhado, os usuários também devem fazer logout no provedor de identidade.
- O menu do usuário mostra o nome de usuário do Cognito. Para um usuário federado, é o nome do provedor de identidade, um underscore e o `sub` do usuário no provedor de identidade, em minúsculas, por exemplo `testidp_00u1abcd`.
- Remover ou desabilitar um usuário no provedor de identidade interrompe apenas o próximo login dele através dele. O Cognito renova tokens com seu próprio refresh token e não pergunta ao provedor de identidade, e o website renova tokens sem que o usuário perceba. O usuário pode, portanto, manter o acesso até que o refresh token expire, até 30 dias após seu último login. Para encerrar o acesso do usuário imediatamente, também desconecte-o de todas as sessões e desabilite-o no user pool. Seu nome de usuário é `<identity provider name in lowercase>_<sub>`:

  ```bash
  aws cognito-idp admin-user-global-sign-out --user-pool-id <user pool id> --username testidp_<sub>
  aws cognito-idp admin-disable-user --user-pool-id <user pool id> --username testidp_<sub>
  ```

  Isso foi testado na AWS. Após `admin-user-global-sign-out` e `admin-disable-user`, o provedor de identidade ainda faz o login do usuário, mas o Cognito os recusa.

  Uma validade de refresh token mais curta no web client (`refreshTokenValidity` no CDK, `refresh_token_validity` no Terraform) reduz o tempo que um usuário removido mantém o acesso. Isso não foi testado na AWS.

## O client secret

O Cognito mantém o client secret nas configurações do provedor de identidade. Qualquer pessoa autorizada a chamar `cognito-idp:DescribeIdentityProvider` no seu user pool pode lê-lo. É assim que o Cognito funciona, qualquer que seja o provedor IaC que você use.

## Outros app clients

Um app client é a configuração do Cognito através da qual uma aplicação faz login. O gerador adiciona o provedor de identidade apenas ao app client do website, o web client. Outro app client no mesmo user pool aceita usuários federados apenas se você adicionar o provedor de identidade a ele também. Por exemplo, o app client que você cria para um <Link path="guides/ts-dcr-proxy">DCR proxy</Link> (que permite que clientes MCP, as ferramentas de IA que usam o Model Context Protocol, façam login através do Cognito) precisa dele. Caso contrário, usuários federados não podem fazer login no seu servidor MCP. No CDK, adicione o `provider.providerName` do provedor de identidade aos `supportedIdentityProviders` desse client.

## Tokens para o chat do agente

O target `<agent>-chat` de um <Link path="guides/ts-agent">agente TypeScript</Link> com autenticação Cognito lê um access token do Cognito da variável de ambiente `AGENT_ACCESS_TOKEN`. Um usuário federado não tem senha do Cognito, então `admin-initiate-auth` não funciona para eles. Em vez disso, faça login no seu website, abra as ferramentas de desenvolvedor do navegador e copie `access_token` da entrada `oidc.user:...` no session storage.
