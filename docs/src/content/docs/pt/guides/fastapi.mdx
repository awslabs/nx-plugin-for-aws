[FastAPI](https://fastapi.tiangolo.com/) é um framework para construir APIs em Python.

O gerador FastAPI cria um novo FastAPI com configuração de infraestrutura AWS CDK ou Terraform. O backend gerado é exposto via uma API AWS API Gateway. Ele configura [AWS Lambda Powertools](https://docs.powertools.aws.dev/lambda/python/latest/) para observabilidade, incluindo logging estruturado e métricas CloudWatch.

<OptionFilter not when={{ infra: 'http-ecs' }} description="Hospedagem Lambda">
O backend usa AWS Lambda para implantação serverless, e o rastreamento AWS X-Ray também é configurado.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="Hospedagem ECS">
Sua API é executada como um servidor uvicorn de longa duração em um contêiner no Amazon ECS, atrás de uma API Gateway HTTP API, em vez de em uma função Lambda. Veja <a href="#running-on-amazon-ecs">Executando no Amazon ECS</a> para o que isso muda, incluindo por que o rastreamento X-Ray não produz rastreamentos lá.
</OptionFilter>

<Snippet name="api/api-choice-note" />

:::tip[Tipo de API]
Selecione `rest-lambda` (padrão) como seu `infra` se você pretende construir quaisquer operações de streaming.
:::

:::tip[Padrão de Integração]
A opção `integrationPattern` tem como padrão `isolated`, que cria um Lambda por operação FastAPI. Selecione `shared` se você preferir um único manipulador Lambda compartilhado para toda a API, com substituições opcionais por operação.

Com `infra` definido como `http-ecs` a opção é sempre `shared`, já que um serviço de contêiner responde a todas as operações.
:::

<OptionFilter when={{ infra: 'http-ecs' }} description="Hospedagem ECS é experimental">
:::caution[Experimental]
`http-ecs` é experimental. Sua saída gerada pode mudar entre versões sem uma migração para transportar um workspace existente, então espere reconciliar essas mudanças você mesmo quando atualizar.

Ele precisa do provedor IaC CDK: o suporte ao Terraform ainda não está implementado. Se o workspace resolver para Terraform, o gerador falha com uma mensagem nomeando a correção.

`integrationPattern` é sempre `shared` aqui. Passar `--integrationPattern=isolated` junto com `http-ecs` não falha: o gerador avisa que a opção é ignorada e usa `shared`. Executando o gerador interativamente, ele pergunta por `integrationPattern` antes de `infra`, com `isolated` pré-selecionado, então esse aviso é o que você vê se deixar a pré-seleção sozinha e depois escolher `http-ecs`. No construtor de comandos nesta página, escolher `http-ecs` desabilita `isolated` e o limpa se foi selecionado, então o comando que ele escreve nunca carrega a flag.

A opção `architecture` define se o contêiner é executado em `ARM64` ou `X86_64`, e as wheels Python em seu bundle seguem isso. Deixe-a de fora para usar a arquitetura da máquina em que você executa o gerador. Veja <Link path="/guides/py-container#cpu-architecture">CPU Architecture</Link> no guia de contêiner.
:::
</OptionFilter>

## Saída do Gerador

O gerador criará a seguinte estrutura de projeto no diretório `<directory>/<api-name>`:

<FileTree>

- project.json Configuração do projeto e alvos de build
- pyproject.toml Configuração do projeto Python e dependências
- run.sh Script de bootstrap do Lambda Web Adapter para iniciar o app FastAPI via uvicorn
- \<module_name>
  - \_\_init\_\_.py Inicialização do módulo
  - init.py Configura o app FastAPI e configura o middleware powertools
  - main.py Implementação da API
- scripts
  - generate_open_api.py Script para gerar um esquema OpenAPI a partir do app FastAPI

</FileTree>

<OptionFilter when={{ infra: 'http-ecs' }} description="Arquivos que diferem quando a API é executada no ECS">
Com `infra` definido como `http-ecs` a API é executada como seu próprio servidor HTTP em vez de atrás do Lambda Web Adapter, então `run.sh` não é gerado. Em seu lugar você obtém uma pasta de contêiner dentro do seu módulo, nomeada após sua API:

<FileTree>
- \<module_name>
  - \<api_name>_container
    - main.py Ponto de entrada: adiciona `GET /health`, escreve as métricas que a API coleta e inicia o uvicorn em `HOST` e `PORT`. O bundle, a imagem e o alvo `serve` todos começam a partir deste arquivo
    - Dockerfile Definição da imagem do contêiner
    - .dockerignore Arquivos deixados fora do contexto de build da imagem
</FileTree>

Seu `init.py`, `main.py` e as operações que você adiciona a eles são os mesmos para cada valor de `infra`.
</OptionFilter>

## Implementando seu FastAPI

A implementação principal da API está em `main.py`. É aqui que você define suas rotas de API e suas implementações. Aqui está um exemplo:

```python
from pydantic import BaseModel
from .init import app, tracer

class Item(BaseModel):
  name: str

@app.get("/items/{item_id}")
@tracer.capture_method
def get_item(item_id: int) -> Item:
    return Item(name=f"Item {item_id}")

@app.post("/items")
@tracer.capture_method
def create_item(item: Item) -> Item:
    return item
```

O gerador configura vários recursos automaticamente:

1. Integração AWS Lambda Powertools para observabilidade
2. Middleware de tratamento de erros
3. Correlação de solicitação/resposta
4. Coleta de métricas

<OptionFilter not when={{ infra: 'http-ecs' }} description="Streaming, que precisa de uma REST API">
Streaming type-safe também é configurado, apenas para a infraestrutura `rest-lambda`.
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="Como as variantes Lambda servem o app">
O app é servido em uma função Lambda pelo [Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter) executando uvicorn.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="Como a variante ECS serve o app">
O app é servido pelo uvicorn no contêiner, sem Lambda Web Adapter. Veja <a href="#running-on-amazon-ecs">Executando no Amazon ECS</a>.
</OptionFilter>

### Observabilidade com AWS Lambda Powertools

#### Logging

O gerador configura logging estruturado usando AWS Lambda Powertools. Você pode acessar o logger em seus manipuladores de rota:

```python
from .init import app, logger

@app.get("/items/{item_id}")
def read_item(item_id: int):
    logger.info("Fetching item", extra={"item_id": item_id})
    return {"item_id": item_id}
```

O logger inclui automaticamente:

- IDs de correlação para rastreamento de solicitações
- Caminho da solicitação, rota correspondente e método

#### Rastreamento

O rastreamento AWS X-Ray é configurado automaticamente. Você pode adicionar subsegmentos personalizados aos seus rastreamentos:

```python
from .init import app, tracer

@app.get("/items/{item_id}")
@tracer.capture_method
def read_item(item_id: int):
    # Creates a new subsegment
    with tracer.provider.in_subsegment("fetch-item-details"):
        # Your logic here
        return {"item_id": item_id}
```

<OptionFilter when={{ infra: 'http-ecs' }} description="X-Ray não produz rastreamentos no ECS">
:::caution[Sem rastreamentos no ECS]
O decorador e o subsegmento acima são executados sem erro em um contêiner, mas não produzem rastreamentos. Powertools desliga seu rastreador quando não está sendo executado no Lambda. Veja <a href="#observability">Observabilidade</a> para o que você obtém, e o que adicionar se precisar de rastreamentos.
:::
</OptionFilter>

#### Métricas

As métricas do CloudWatch são coletadas automaticamente para cada solicitação. Você pode adicionar métricas personalizadas:

```python
from .init import app, metrics
from aws_lambda_powertools.metrics import MetricUnit

@app.get("/items/{item_id}")
def read_item(item_id: int):
    metrics.add_metric(name="ItemViewed", unit=MetricUnit.Count, value=1)
    return {"item_id": item_id}
```

As métricas padrão incluem:

- Contagens de solicitações
- Contagens de sucesso/falha
- Métricas por rota (via uma dimensão `route` de `<method> <path>`)

### Tratamento de Erros

O gerador inclui tratamento de erros abrangente:

```python
from fastapi import HTTPException

@app.get("/items/{item_id}")
def read_item(item_id: int):
    if item_id < 0:
        raise HTTPException(status_code=400, detail="Item ID must be positive")
    return {"item_id": item_id}
```

Exceções não tratadas são capturadas pelo middleware e:

1. Registram a exceção completa com stack trace
2. Registram uma métrica de falha
3. Retornam uma resposta 500 segura ao cliente
4. Preservam o ID de correlação

:::tip[Modelos de Resposta]
É recomendado especificar modelos de resposta para suas operações de API para melhor geração de código se estiver usando o gerador `connection`. <Link path="guides/connection/react-fastapi#errors">Veja aqui para mais detalhes</Link>.
:::

### Acessando o Usuário Chamador

<OptionFilter when={{ infra: 'http-ecs' }} description="Identidade no ECS — o contexto do autorizador não chega">
No ECS não há Lambda Web Adapter e nenhum cabeçalho de contexto de solicitação do API Gateway: o API Gateway não encaminha as claims do autorizador para uma integração de load balancer privado. O autorizador ainda decide se uma solicitação chega ao contêiner, mas seus manipuladores não podem ler o chamador da solicitação como escrito abaixo.

Para ler a identidade do chamador em uma operação, mapeie o contexto do autorizador em um cabeçalho de solicitação em seu construto de API, e leia esse cabeçalho do `Request` do FastAPI.
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="Identidade nas variantes Lambda">
Quando sua API é protegida por autenticação, seus manipuladores de rota frequentemente precisam saber quem está chamando. O FastAPI gerado é executado dentro do AWS Lambda via o [Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter), que encaminha o contexto de solicitação do API Gateway como JSON no cabeçalho `x-amzn-request-context`. Você pode lê-lo do `Request` do FastAPI para extrair a identidade do chamador.

Como exemplo, vamos adicionar um endpoint `/me` que retorna detalhes sobre o usuário chamador. Implementaremos a extração como uma [dependência do FastAPI](https://fastapi.tiangolo.com/tutorial/dependencies/) para que possa ser reutilizada entre rotas. A forma do contexto de solicitação — e, portanto, como você extrai a identidade — depende tanto do seu método `auth` selecionado quanto se você implantou uma API REST ou HTTP.
</OptionFilter>

<OptionFilter when={{ auth: 'iam' }} description="Extração de identidade para APIs autenticadas por IAM">
Para autenticação `IAM`, procuramos o chamador no Cognito usando o sub extraído do contexto de solicitação do API Gateway, o que requer `boto3`. Adicione-o ao seu projeto de API:

<NxCommands commands={[`run my-api:add boto3${PY_VERSIONS.boto3}`]} />

Crie `identity.py` ao lado de `main.py`:

<TabItem label="REST API" _filter={{ infra: 'rest-lambda' }}>
```python
import json
import os
from typing import Annotated

from boto3 import client
from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel

cognito = client("cognito-idp")


class Identity(BaseModel):
    sub: str
    username: str


def get_identity(request: Request) -> Identity:
    # The Lambda Web Adapter forwards the API Gateway request context as JSON
    request_context_header = request.headers.get("x-amzn-request-context")
    if not request_context_header:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    request_context = json.loads(request_context_header)
    provider = request_context.get("identity", {}).get("cognitoAuthenticationProvider")

    sub = provider.split(":")[-1] if provider else None
    if not sub:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    users = cognito.list_users(
        # Assumes user pool id is configured in lambda environment
        UserPoolId=os.environ["USER_POOL_ID"],
        Limit=1,
        Filter=f'sub="{sub}"',
    ).get("Users", [])

    if len(users) != 1:
        raise HTTPException(status_code=403, detail=f"No user found with subjectId {sub}")

    return Identity(sub=sub, username=users[0]["Username"])


CurrentUser = Annotated[Identity, Depends(get_identity)]
```
</TabItem>

        raise HTTPException(status_code=403, detail=f"No user found with subjectId {sub}")

import json
from typing import Annotated

from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel


class Identity(BaseModel):
    sub: str
    username: str


def get_identity(request: Request) -> Identity:
    # The Lambda Web Adapter forwards the API Gateway request context as JSON

    if not request_context_header:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    request_context = json.loads(request_context_header)
    claims = request_context.get("authorizer", {}).get("claims", {})

    sub = claims.get("sub")
    username = claims.get("username")

    if not sub or not username:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    return Identity(sub=sub, username=username)

### Streaming

O FastAPI gerado suporta respostas de streaming prontas para uso ao usar uma REST API. A infraestrutura é configurada para usar o [AWS Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter) para executar seu FastAPI via uvicorn dentro do Lambda, com `ResponseTransferMode.STREAM` no API Gateway para todas as operações REST API, o que permite que o streaming funcione ao lado de operações não-streaming.

#### Usando `JsonStreamingResponse`

O `init.py` gerado exporta uma classe `JsonStreamingResponse` que fornece streaming type-safe com geração adequada de esquema OpenAPI. Isso garante que o <Link path="guides/connection/react-fastapi">gerador `connection`</Link> possa produzir métodos de cliente de streaming corretamente tipados.

```python
from pydantic import BaseModel
from .init import app, JsonStreamingResponse

class Chunk(BaseModel):
    message: str

async def generate_chunks():
    for i in range(100):
        yield Chunk(message=f"This is chunk {i}")

@app.post(
    "/stream",
    response_class=JsonStreamingResponse,
    responses={200: JsonStreamingResponse.openapi_response(Chunk, "Stream of chunks")},
)
async def my_stream() -> JsonStreamingResponse:
    return JsonStreamingResponse(generate_chunks())
```

A classe `JsonStreamingResponse`:

1. Serializa modelos Pydantic para o formato [JSON Lines](https://jsonlines.org/) (`application/jsonl`)
2. Fornece um auxiliar `openapi_response` que gera o esquema OpenAPI correto com `itemSchema`, permitindo que o <Link path="guides/connection/react-fastapi#consuming-a-stream">gerador `connection`</Link> produza métodos de cliente de streaming type-safe

#### Consumo

Para consumir um fluxo de respostas, você pode fazer uso do <Link path="guides/connection/react-fastapi#consuming-a-stream">gerador `connection`</Link> que fornecerá um método type-safe para iterar sobre seus chunks transmitidos.
</OptionFilter>

## Implantando seu FastAPI

O gerador FastAPI cria infraestrutura como código CDK ou Terraform com base no seu `iac` selecionado. Você pode usar isso para implantar seu FastAPI.

<OptionFilter not when={{ infra: 'http-ecs' }} description="Uso do CDK para as variantes Lambda">
O construto CDK para implantar sua API na pasta `common/constructs`. Você pode usar isso em uma aplicação CDK:

```ts {6-8}
import { MyApi } from '@my-scope/common-constructs';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string) {
    // Add the api to your stack
    const api = new MyApi(this, 'MyApi', {
      integrations: MyApi.defaultIntegrations(this).build(),
    });
  }
}
```

Isso configura:

1. Uma função AWS Lambda para cada operação na aplicação FastAPI
2. API Gateway HTTP/REST API como gatilho da função
3. Funções e permissões IAM
4. Grupo de logs CloudWatch
5. Configuração de rastreamento X-Ray
6. Namespace de métricas CloudWatch
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="Uso do CDK quando a API é executada no ECS — passe a VPC">
`defaultIntegrations` recebe a VPC em que seu serviço é executado, e constrói tudo dentro dela: o serviço ECS, o load balancer interno na frente dele, e o VPC link que o API Gateway alcança esse load balancer através. O construto nunca cria uma VPC, então você cria ou importa uma em sua stack.

```ts {10,13-15}
import { MyApi } from '@my-scope/common-constructs';
import { Stack } from 'aws-cdk-lib';
import { Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string) {
    super(scope, id);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    const api = new MyApi(this, 'MyApi', {
      integrations: MyApi.defaultIntegrations(this, { vpc }).build(),
    });
  }
}
```

Para usar uma VPC existente, procure-a com `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` e passe-a como `vpc`.

Passe `service` para alterar o próprio serviço de contêiner — seu `cpu`, `memoryLimitMiB`, `desiredCount`, `environment`, ou `grantTaskRole` para dar uma permissão à função de tarefa:

```ts
MyApi.defaultIntegrations(this, {
  vpc,
  service: {
    cpu: 512,
    memoryLimitMiB: 1024,
    grantTaskRole: (taskRole) => myTable.grantReadWriteData(taskRole),
  },
}).build();
```

Isso configura uma AWS API Gateway HTTP API com autenticação baseada no seu método `auth` escolhido, um serviço Amazon ECS executando seu contêiner, um load balancer interno na frente dele, e o VPC link que o API Gateway alcança esse load balancer através.
</OptionFilter>

<OptionFilter when={{ auth: 'custom' }} description="Uso do Autorizador Lambda Personalizado no CDK">
:::caution[Autorizador Lambda Personalizado]
Ao usar autenticação `Custom`, o construto cria um Lambda Authorizer internamente a partir do arquivo `authorizer.py` gerado, que **nega todas as solicitações por padrão**. Você deve implementar sua lógica de autorização nesse arquivo antes que sua API aceite qualquer tráfego.

Os resultados do autorizador são armazenados em cache por 5 minutos, com chave no cabeçalho `Authorization`, portanto, um token revogado pode ser aceito até que seu resultado em cache expire. Reduza a duração do cache na infraestrutura gerada se você precisar de revogação mais rápida.
:::
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="Como a hospedagem ECS funciona, o que custa e o que limita">
## Executando no Amazon ECS

Com `infra` definido como `http-ecs`, sua API é executada como um servidor uvicorn de longa duração em um contêiner em vez de em uma função Lambda atrás do Lambda Web Adapter. Uma solicitação segue este caminho:

1. Um chamador assina uma solicitação para a API Gateway HTTP API, que é o único ponto de entrada público. Cada rota carrega o autorizador para o `auth` que você escolheu, então uma solicitação não autenticada é rejeitada na borda.
2. O API Gateway encaminha a solicitação através de um VPC link, que é seu caminho privado para sua VPC.
3. O VPC link alcança um load balancer interno. O load balancer não tem endereço público, e sua única regra de entrada permite o grupo de segurança do VPC link na porta do listener.
4. O load balancer encaminha a solicitação para uma tarefa. A única regra de entrada das tarefas permite o grupo de segurança do load balancer na porta do contêiner, então nada mais na VPC pode abrir uma conexão para elas.

As tarefas são executadas em sub-redes privadas e nunca obtêm um endereço IP público. Nada neste caminho permite um intervalo de endereços de entrada.

Por padrão, o serviço, o load balancer e o VPC link vão nas sub-redes `PRIVATE_WITH_EGRESS` da VPC, que alcançam a AWS através de um NAT gateway. Passar `vpcSubnets: { subnetType: SubnetType.PRIVATE_ISOLATED }` para `defaultIntegrations` elimina o NAT gateway e sua cobrança por hora, mas sub-redes isoladas não têm rota de saída, então a VPC precisa de quatro VPC endpoints para as tarefas iniciarem: endpoints de interface para `ecr.api` e `ecr.dkr` para puxar a imagem, um endpoint de gateway S3 porque as camadas da imagem são objetos S3, e um endpoint de interface para `logs` para que o driver `awslogs` possa escrever. Sem eles, uma tarefa não pode puxar sua imagem e o ECS reverte a implantação no circuit breaker sem dizer por quê.

O VPC link, o load balancer, seu listener, o target group e o bucket em que o load balancer escreve seus logs de acesso são criados por um construto, `core/api/ecs-http-endpoint.ts` em `common/constructs`, que toda API hospedada no ECS compartilha. O construto da sua própria API nomeia seu serviço de contêiner e roteia cada operação para esse endpoint.

### O Que É Executado no Contêiner

`<module_name>/<api_name>_container/main.py` importa o app do seu `main.py`, então cada operação que você escreve é servida exatamente como está no Lambda. Ele adiciona duas coisas próprias:

- `GET /health`, que o target group do load balancer e a verificação de saúde do contêiner chamam. É declarado `include_in_schema=False`, então fica fora da sua especificação OpenAPI e, portanto, fora das rotas do API Gateway e dos clientes gerados. Também é deixado fora das métricas de solicitação, então a chamada do target group a cada 15 segundos não conta como uma solicitação de API.
- Um middleware que escreve as métricas que o próprio middleware da API coleta. No Lambda o manipulador faz isso no final de cada invocação; este servidor vive através de solicitações, então ele as libera por si mesmo.

As rotas do API Gateway ainda vêm da sua especificação OpenAPI, então uma operação que você adiciona é implantada uma vez que `nx build` tenha regenerado a especificação.

### Observabilidade

Logs e métricas funcionam como fazem no Lambda: o contêiner escreve em seu próprio grupo de logs CloudWatch, e as métricas são escritas no formato de métrica incorporado para o CloudWatch Logs extrair.

Uma coisa sobre métricas é diferente aqui, e vale a pena saber antes de ler um dashboard ou adicionar uma métrica própria. `metrics`, o objeto que a seção <a href="#metrics">Métricas</a> acima diz para você importar de `.init`, é um `Metrics` do Powertools, e cada objeto `Metrics` em um processo compartilha um armazenamento de métricas. No Lambda uma invocação possui esse armazenamento do início ao fim. Um servidor uvicorn lida com solicitações ao mesmo tempo, e tanto as métricas por solicitação da própria API quanto quaisquer que você adicione vão para esse único armazenamento, então duas solicitações em voo juntas podem ter suas métricas escritas em um documento e atribuídas a qualquer rota que foi adicionada primeiro. O documento da outra solicitação pode sair sem nenhuma dimensão `route`, contendo apenas as métricas adicionadas após a primeira liberação, e o Powertools registra `PowertoolsUserWarning: Dimension 'route' has already been added` quando isso acontece. Sob tráfego leve, onde as solicitações raramente se sobrepõem, você não verá isso.

Então trate `RequestCount` e `Success` por rota como aproximados no ECS. Se você precisar de uma métrica atribuída a exatamente uma solicitação, adicione-a a um `EphemeralMetrics` que você cria na solicitação e libera antes de retornar, que mantém um armazenamento próprio:

```python
from aws_lambda_powertools.metrics import EphemeralMetrics, MetricUnit

@app.get("/items/{item_id}")
def read_item(item_id: int):
    request_metrics = EphemeralMetrics()
    request_metrics.add_metric(name="ItemViewed", unit=MetricUnit.Count, value=1)
    request_metrics.flush_metrics()
    return {"item_id": item_id}
```

O rastreamento AWS X-Ray não funciona. `@tracer.capture_method` é um no-op fora do Lambda, e não há daemon X-Ray na tarefa para receber segmentos também. Adicione um como sidecar em seu serviço de contêiner se precisar de rastreamentos.

O log de acesso da API Gateway HTTP API registra cada solicitação que chega à API. O load balancer escreve seus próprios logs de acesso em um bucket que o construto `EcsHttpEndpoint` cria, que é onde você pode ver qual tarefa serviu uma solicitação e o que ela respondeu.

### Build e Varredura de Imagem

O gerador de contêiner fornece os alvos de imagem, nomeados após sua API:

- `<api-name>-container-docker` constrói uma imagem para a arquitetura de CPU na opção `architecture`, `linux/arm64` ou `linux/amd64`. A opção tem como padrão a arquitetura da máquina em que você executa o gerador, e você a define com `--architecture`. O alvo executa o alvo de bundle correspondente primeiro, `bundle-arm` ou `bundle-x86`, então a imagem contém seu pacote e suas dependências construídas para essa arquitetura.
- `<api-name>-container-trivy` varre essa imagem em busca de vulnerabilidades.

Veja <Link path="/guides/py-container">Python Container Service</Link> para como a imagem é construída, e <Link path="/guides/docker-bundling">Docker Bundling</Link> para como ela é publicada no momento da implantação.

### Implantando e Desmontando

`deploy-sandbox` implanta em <Link path="/guides/typescript-infrastructure#deploying-your-sandbox-stage">modo expresso do CloudFormation</Link>, que retorna uma vez que a configuração de cada recurso é aplicada em vez de esperar que o serviço ECS atinja um estado estável. Então o alvo pode terminar enquanto a primeira tarefa ainda está iniciando, e até que uma tarefa tenha passado duas verificações de saúde com quinze segundos de intervalo, o load balancer não tem alvo para enviar uma solicitação e responde `503`. Espere cerca de um minuto disso após o deploy retornar. Aguarde um ou dois minutos e chame novamente. Um `503` que nunca limpa é uma falha real em vez de um início lento: o circuit breaker de implantação do serviço o reverte quando nenhuma tarefa se torna saudável.

O ECS executa uma verificação de saúde própria dentro do contêiner. Ele chama `GET /health` a cada 30 segundos, e falhas nos primeiros 30 segundos após o início de uma tarefa não contam contra ela. Até que essa verificação relate pela primeira vez, `aws ecs describe-tasks` dá à tarefa um `healthStatus` de `UNKNOWN`, que se torna `HEALTHY` uma vez que passa. `UNKNOWN` significa que a verificação ainda não relatou em vez de que falhou.

A URL da API é uma saída de stack, mas não sob o nome que você adivinharia. O `CfnOutput` é criado dentro do seu construto de API e nada substitui seu ID lógico, então o CDK constrói a chave de saída a partir do caminho do construto mais um hash de oito caracteres: uma API adicionada como `new MyApi(this, 'MyApi', …)` produz `MyApiMyApiUrl` e esse hash, não `MyApiUrl`. `cdk deploy` imprime o valor, e um script deve corresponder ao sufixo em vez da chave inteira:

```bash
aws cloudformation describe-stacks --stack-name <stack-name> \
  --query "Stacks[0].Outputs[?contains(OutputKey, 'Url')].OutputValue" --output text
```

`destroy-sandbox` deixa o grupo de logs de acesso da HTTP API e a chave KMS gerenciada pelo cliente que o criptografa para trás. Nenhum define uma política de remoção, então o padrão `Retain` do CDK se aplica e o CloudFormation os pula em vez de excluí-los. Liste-os antes de desmontar a stack, já que uma stack excluída não relata mais seus recursos:

```bash
aws cloudformation describe-stack-resources --stack-name <stack-name> \
  --query "StackResources[?contains(LogicalResourceId, 'AccessLogs') && (ResourceType=='AWS::Logs::LogGroup' || ResourceType=='AWS::KMS::Key')].[ResourceType,PhysicalResourceId]" \
  --output text
```

Em seguida, remova-os com `aws logs delete-log-group --log-group-name <log-group-name>` e `aws kms schedule-key-deletion --key-id <key-id> --pending-window-in-days 7`, sendo sete dias a janela mais curta que o KMS aceita.

### Limites

- **Timeout de integração.** APIs HTTP do API Gateway limitam uma integração a cerca de 30 segundos. Uma operação que leva mais tempo do que isso falha no gateway, não importa quanto tempo o contêiner continue trabalhando.
- **Sem streaming.** Operações de streaming precisam da infraestrutura `rest-lambda`. Uma HTTP API não pode transmitir uma resposta.
- **Tamanho do payload.** Solicitações e respostas seguem o limite de 10 MB do API Gateway.
- **Um serviço para cada operação.** `integrationPattern` é `shared`: há um serviço de contêiner, e cada rota é roteada para ele. A opção sempre resolve para `shared` para esta infraestrutura, e `isolated` é ignorado com um aviso.

### Custo

O load balancer é o novo custo fixo comparado com Lambda, onde você paga por solicitação e nada quando ocioso. Valores mensais aproximados em us-east-1, antes da transferência de dados:

| Item | Aproximadamente |
| --- | --- |
| Load balancer interno | $16 mais unidades de capacidade do load balancer |
| Tarefa Fargate, 0.25 vCPU / 0.5 GB | $7 por tarefa em ARM64, e mais em X86_64, que o Fargate cobra a uma taxa mais alta por vCPU e por GB |
| NAT gateway, se sua VPC tiver um | $33 |
| VPC link | sem cobrança por hora |
| Armazenamento S3 para os logs de acesso do load balancer | centavos por GB por mês |

Então um serviço de uma tarefa custa aproximadamente $23 por mês em ARM64 antes de qualquer tráfego, e mais se a VPC que você passa tiver um NAT gateway. Os logs de acesso crescem com o tráfego: adicione uma regra de ciclo de vida a `endpoint.accessLogsBucket` para expirá-los. Verifique as páginas de preços do [Elastic Load Balancing](https://aws.amazon.com/elasticloadbalancing/pricing/) e [AWS Fargate](https://aws.amazon.com/fargate/pricing/) para preços atuais em sua Região.
