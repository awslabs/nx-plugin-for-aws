Este gerador adiciona um serviço HTTP em contêiner a um projeto TypeScript existente. Você obtém um pequeno servidor HTTP com uma rota `GET /health`, um Dockerfile e targets para executar o servidor localmente, construir sua imagem e escanear a imagem. Você também obtém código CDK ou Terraform que executa a imagem no [Amazon Elastic Container Service (Amazon ECS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html), o serviço AWS que executa e escala contêineres.

O serviço é executado no [AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), que executa cada contêiner sem servidores para você gerenciar. Ele é executado em sua própria VPC (nuvem privada virtual, uma rede isolada em sua conta AWS), atrás de um [Application Load Balancer](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html) (ALB) interno que apenas endereços dentro da VPC podem alcançar. Por padrão, uma [Amazon API Gateway HTTP API](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api.html) recebe solicitações de chamadores e as passa para o ALB através de um VPC link (conexão privada do API Gateway em uma VPC). Os chamadores obtêm um endpoint HTTPS autenticado, e o load balancer nunca fica exposto à internet.

## Executando Seu Serviço Localmente

O target `<name>-serve` executa o servidor em sua máquina, sem um contêiner:

<NxCommands commands={['run your-project:service-serve']} />

O servidor escuta na porta na variável de ambiente `PORT`. O target `<name>-serve` a define para uma porta que o gerador atribui, começando em 8081 e pulando portas que outros projetos em seu workspace já usam. Dentro do contêiner, o servidor escuta na porta 8080.

Verifique se o servidor está ativo com sua rota de saúde, que retorna status 200 e `{"status":"ok"}`:

```bash
curl http://localhost:<port>/health
```

O servidor também tem uma rota de exemplo que você substitui por suas próprias rotas. `GET /hello?name=<x>` retorna `{"message":"Hello, <x>!"}`, e `name` tem como padrão `world`. Qualquer outro caminho retorna status 404.

## Construindo e Escaneando a Imagem

O target `<name>-docker` constrói uma imagem linux/arm64 do seu serviço. Ele executa o target `bundle` primeiro, então a imagem contém o servidor empacotado. Em seguida, copia o `Dockerfile` e `.dockerignore` para a pasta de saída do bundle, `dist/<project root>/bundle/container/<name>`, e constrói a imagem com essa pasta como contexto de construção (os arquivos que a construção da imagem pode ler). Ele usa o mecanismo de contêiner com o qual seu workspace está configurado, `docker` ou [Finch](https://runfinch.com/). O target é executado como parte do target agregado `docker`, que constrói todas as imagens no projeto.

<NxCommands commands={['run your-project:service-docker']} />

Apenas o target group do load balancer (a lista de tarefas para as quais o load balancer envia solicitações) verifica `GET /health`, para decidir se uma tarefa está pronta para tráfego. O ECS ignora uma instrução `HEALTHCHECK` no Dockerfile. Para mais informações sobre como as imagens são construídas e publicadas, consulte <Link path="/guides/docker-bundling">Docker Bundling</Link>.

## Implantando Seu Serviço

### Adicionando o Serviço à Sua Infraestrutura

O construto e o módulo nunca criam uma VPC. Você cria ou importa uma em sua stack ou módulo raiz e a passa. As tarefas e o load balancer são executados em sub-redes privadas com saída, que alcançam serviços AWS através de um NAT gateway (um gateway gerenciado que permite que sub-redes privadas façam conexões de saída) ou através de VPC endpoints (conexões privadas de sua VPC para serviços AWS).

<Infrastructure>
<Fragment slot="cdk">
O construto CDK é criado em `common/constructs` e nomeado após seu serviço. Exemplo de uso com uma nova VPC:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyService } from '@my-scope/common-constructs';
import { Stack, StackProps } from 'aws-cdk-lib';
import { SubnetType, Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ApplicationStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    new MyService(this, 'MyService', {
      vpc,
      vpcSubnets: { subnetType: SubnetType.PRIVATE_WITH_EGRESS },
    });
  }
}
```

Para usar uma VPC existente, procure-a com `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` e passe-a como `vpc`.
</Fragment>
<Fragment slot="terraform">
O módulo Terraform é criado em `common/terraform`. A imagem do serviço é publicada no repositório de ativos compartilhado, então instancie o módulo `core/asset-ecr` uma vez por implantação e passe suas saídas para cada módulo de serviço. Também passe as saídas do módulo compartilhado `runtime_config_appconfig`, que contêm o aplicativo AWS AppConfig do qual o serviço lê sua <Link path="/guides/runtime-config">configuração de runtime</Link>:

```hcl title="packages/infra/src/main.tf"
module "asset_ecr" {
  source = "../../common/terraform/src/core/asset-ecr"
}

module "my_service" {
  source = "../../common/terraform/src/app/services/my-service"

  vpc_id     = aws_vpc.main.id
  subnet_ids = aws_subnet.private[*].id

  asset_ecr_repository_url = module.asset_ecr.repository_url
  asset_ecr_repository_arn = module.asset_ecr.repository_arn

  appconfig_application_id  = module.runtime_config_appconfig.application_id
  appconfig_application_arn = module.runtime_config_appconfig.application_arn
}
```

### Limites de Solicitação

O API Gateway para de esperar pelo seu serviço após 30 segundos e retorna um erro ao chamador. Você não pode aumentar este timeout de integração. O maior payload de solicitação que a HTTP API aceita é 10 MB, e você também não pode aumentar este limite. Ambos os valores vêm da página [Amazon API Gateway quotas for HTTP APIs](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-quotas.html).

Portanto, solicitações que demoram mais de 30 segundos e respostas que transmitem dados por um longo tempo não funcionam através da HTTP API. Para essas, defina `ingress` como `private` e chame o load balancer interno de dentro da VPC.
</OptionFilter>

### Executando Sem um NAT Gateway

Quando suas tarefas iniciam, o ECS puxa a imagem e envia logs em seu nome. Seu código de servidor também pode chamar serviços AWS. Em sub-redes privadas sem NAT gateway, cada uma dessas chamadas precisa de um VPC endpoint. Sem os endpoints corretos, as tarefas falham ao iniciar ou expiram quando chamam a AWS.

Crie estes endpoints na VPC, substituindo `<region>` pela sua Região AWS:

| Endpoint | Tipo | O que o usa |
| --- | --- | --- |
| `com.amazonaws.<region>.ecr.api` | Interface | ECS, para autenticar com o Amazon ECR e procurar a imagem |
| `com.amazonaws.<region>.ecr.dkr` | Interface | ECS, para puxar a imagem do Amazon ECR |
| `com.amazonaws.<region>.s3` | Gateway | ECS, para baixar camadas de imagem, que o Amazon ECR armazena no Amazon S3 |
| `com.amazonaws.<region>.logs` | Interface | A saída de log do contêiner, enviada para o Amazon CloudWatch Logs |
| `com.amazonaws.<region>.secretsmanager` | Interface | ECS, para ler os segredos que você passa para o contêiner quando uma tarefa inicia |
| `com.amazonaws.<region>.appconfigdata` | Interface | Seu código, para ler <Link path="/guides/runtime-config">configuração de runtime</Link> do AWS AppConfig |
| `com.amazonaws.<region>.sts` | Interface | Seu código, quando solicita credenciais temporárias do AWS STS (por exemplo, para assumir outra role) |

Os endpoints de interface precisam de um security group que permita HTTPS (porta 443) das tarefas. Para detalhes sobre os endpoints do Amazon ECR, consulte [Amazon ECR interface VPC endpoints](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html).

### Padrões de Segurança

A infraestrutura gerada aplica estas configurações por padrão:

- O load balancer é interno. Nenhum security group permite tráfego de entrada de `0.0.0.0/0` ou `::/0`.
- As tarefas são executadas em sub-redes privadas e nunca obtêm um endereço IP público.
- O load balancer aceita tráfego apenas do VPC link (`http-api`) ou do intervalo de endereços da VPC (`private`). As tarefas aceitam tráfego apenas do load balancer, na porta do contêiner.
- As tarefas podem enviar tráfego de saída apenas na porta 443. Conexões com bancos de dados adicionam a porta do banco de dados.
- A task role (a role como a qual seu código de servidor é executado) pode apenas ler configuração de runtime do AWS AppConfig até que você ou uma conexão conceda mais.
- A execution role (a role que o ECS usa para iniciar sua tarefa) pode apenas puxar a imagem do serviço, escrever em seu log group e ler os segredos que você lista.
- Os segredos alcançam o contêiner apenas como referências ao AWS Secrets Manager ou AWS Systems Manager Parameter Store, nunca como valores de ambiente simples.
- O contêiner tem um sistema de arquivos raiz somente leitura e é executado como uid 1000, um usuário não-root. O ECS Exec (acesso shell a uma tarefa em execução) está desativado.
- Uma implantação que falha em suas verificações de saúde para e reverte para a versão anterior.
- A HTTP API escreve logs de acesso e limita solicitações. Ela autentica com IAM, a menos que você escolha o contrário.
- Os logs são mantidos por um ano.

O código gerado suprime estas verificações do [Checkov](https://www.checkov.io/) (o Checkov escaneia código de infraestrutura em busca de configurações inseguras), e declara o motivo ao lado de cada supressão:

- `CKV_AWS_91` pede logs de acesso do load balancer. Os logs de acesso da HTTP API, ou os próprios logs do seu serviço, registram as solicitações em vez disso.
- `CKV_AWS_2` e `CKV_AWS_103` pedem um listener HTTPS com TLS. O load balancer escuta em HTTP simples porque é interno e apenas chamadores dentro da VPC podem alcançá-lo. Com `http-api`, o TLS termina no API Gateway.

O módulo Terraform também pula `CKV2_AWS_20` e `CKV_AWS_378` pela mesma razão do listener HTTP, e `CKV_AWS_150` porque a proteção contra exclusão do load balancer está desativada para que o serviço possa ser destruído.

### Chamando Seu Serviço

A URL do serviço é escrita na <Link path="/guides/runtime-config">configuração de runtime</Link> como `connection.services.<NameClassName>`, onde `<NameClassName>` é o nome do serviço em PascalCase. Para `--name=orders` a chave é `Orders`. Sem um nome, o nome do serviço é `<project>-service`, então para um projeto chamado `my-project` a chave é `MyProjectService`. A pasta de origem e o prefixo do target ainda são `service` nesse caso.

<Tabs syncKey="auth">
<TabItem label="IAM" _filter={{ ingress: 'http-api', auth: 'iam' }}>
Os chamadores assinam cada solicitação com [AWS Signature Version 4 (SigV4)](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv.html) para o serviço `execute-api`, usando credenciais AWS que podem chamar a API. O API Gateway rejeita uma solicitação sem uma assinatura válida antes que ela alcance seu serviço.

```ts title="packages/infra/src/stacks/application-stack.ts"
const service = new MyService(this, 'MyService', { vpc });
service.grantInvoke(myFunction);
```
</Fragment>
<Fragment slot="terraform">
Conceda a uma role permissão para chamar o serviço com uma política `execute-api:Invoke` no ARN de execução da API, que o módulo do seu serviço produz como `api_execution_arn`:

```hcl title="packages/infra/src/main.tf"

  role = aws_iam_role.caller.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = ["execute-api:Invoke"]
      Resource = ["${module.my_service.api_execution_arn}/*"]
    }]
  })
}
```
</Fragment>
</Infrastructure>

### Configuração Avançada

O serviço gerado define seu nome, `ingress` e `auth` para você. Os exemplos abaixo usam o construto genérico `EcsService` e o módulo `ecs-service` diretamente, para configurações que o serviço gerado não passa ou para escolher `ingress` e `auth` por instância.

No CDK, seu pacote `common-constructs` exporta `EcsService` ao lado do construto do seu serviço, então você o importa da mesma maneira: `import { EcsService } from '@my-scope/common-constructs'`. O construto gerado estende `EcsService` e passa todas as outras props, por exemplo `cluster`, `loadBalancer`, `environment`, `secrets` e `grantTaskRole`. Sua prop opcional `image` substitui a imagem construída do seu projeto. Ele não tem prop `auth`. Um serviço Cognito recebe `identity` em vez disso, e outros serviços sempre usam o `auth` com o qual foram gerados.

No Terraform, o módulo do seu serviço permite que você defina apenas algumas das variáveis do módulo `ecs-service`: `vpc_id`, `subnet_ids`, `cluster_arn`, `environment`, `secrets`, `task_role_policy_statements` e `tags`, mais `user_pool_id` e `user_pool_client_ids` para um serviço Cognito. Para definir qualquer outra variável, edite o bloco `module "ecs_service"` no módulo do seu serviço.

#### Imagem Pré-construída

Para executar uma imagem que já está construída, por exemplo de um registro público, passe seu URI. Nada é construído localmente. Para uma imagem em um repositório privado do Amazon ECR, o CDK concede à execution role acesso de pull nesse repositório. O Terraform concede acesso de pull apenas quando você também passa o ARN do repositório como `image_repository_arn`.

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'Prebuilt', {
  serviceName: 'Prebuilt',
  vpc,
  image: { imageUri: 'public.ecr.aws/my-org/my-image@sha256:<digest>' },
});
```

</Fragment>
<Fragment slot="terraform">

```hcl
module "prebuilt" {
  source = "../../common/terraform/src/core/container/ecs-service"

  service_name = "Prebuilt"
  vpc_id       = aws_vpc.main.id
  subnet_ids   = aws_subnet.private[*].id
  image_uri    = "public.ecr.aws/my-org/my-image@sha256:<digest>"
  # For an image in a private Amazon ECR repository, also pass:
  # image_repository_arn = aws_ecr_repository.my_image.arn
}
```

</Fragment>
</Infrastructure>

#### Worker Sem Load Balancer

Um worker lê de uma fila ou executa trabalhos em segundo plano, e nada o chama. Desative o load balancer para obter um serviço sem load balancer, sem HTTP API e sem URL.

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'Worker', {
  serviceName: 'Worker',
  vpc,
  image: { directory: '<path to the folder with the Dockerfile>' },

```

</Fragment>
<Fragment slot="terraform">

#### Vários Serviços em Uma Stack

Cada serviço cria seu próprio cluster ECS, a menos que você passe um. Para executar vários serviços em um cluster, passe o mesmo cluster para cada um.

Cada serviço HTTP API cria seu próprio VPC link, mesmo quando os serviços compartilham um cluster. O API Gateway permite 10 VPC links por conta por Região por padrão, e você pode solicitar um aumento.

<Infrastructure>
<Fragment slot="cdk">

```ts
const cluster = new Cluster(this, 'Cluster', { vpc });

new MyService(this, 'MyService', { vpc, cluster });
new MyOtherService(this, 'MyOtherService', { vpc, cluster });
```

</Fragment>
<Fragment slot="terraform">
Passe o mesmo `cluster_arn` para cada módulo `ecs-service`. A saída `cluster_arn` do primeiro serviço fornece um:

```hcl
cluster_arn = module.my_service.cluster_arn
```

</Fragment>
</Infrastructure>

#### Variáveis de Ambiente e Segredos

Configurações simples vão em `environment`. Nunca coloque valores secretos lá, porque qualquer pessoa que possa ler a definição da tarefa pode lê-los. Passe segredos como referências em vez disso. A execution role pode ler apenas os segredos que você lista.

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'MyService', {
  // ...
  environment: { LOG_LEVEL: 'info' },
  secrets: { API_KEY: Secret.fromSecretsManager(apiKeySecret) },
});
```

</Fragment>
<Fragment slot="terraform">

```hcl
environment = { LOG_LEVEL = "info" }
secrets     = { API_KEY = aws_secretsmanager_secret.api_key.arn }
```

</Fragment>
</Infrastructure>

#### Dimensionamento e Escala

Cada tarefa obtém 256 unidades de CPU (um quarto de uma vCPU) e 512 MiB de memória por padrão. O serviço inicia uma tarefa, e o autoscaling mantém entre uma e duas tarefas em execução, adicionando tarefas quando o uso médio de CPU ultrapassa 70%.

| Configuração | Prop CDK | Variável Terraform | Padrão |
| --- | --- | --- | --- |
| Unidades de CPU por tarefa | `cpu` | `cpu` | 256 |
| Memória por tarefa (MiB) | `memoryLimitMiB` | `memory` | 512 |
| Tarefas no início | `desiredCount` | `desired_count` | 1 |
| Menos tarefas | `minCapacity` | `min_capacity` | 1 |
| Mais tarefas | `maxCapacity` | `max_capacity` | 2 |
| CPU média alvo (%) | `targetCpuUtilizationPercent` | `target_cpu_utilization` | 70 |

#### Usuário do Contêiner

A definição da tarefa executa o contêiner como uid 1000, um usuário não-root. Isso corresponde ao usuário `node` que o Dockerfile fornecido define. Para executar como outro usuário, defina a prop `user` do CDK ou a variável `container_user` do Terraform. O Terraform rejeita `0` e `root`.

#### CORS e Throttling

Essas configurações se aplicam apenas com `ingress` definido como `http-api`. CORS (compartilhamento de recursos de origem cruzada) decide quais sites podem chamar seu serviço de um navegador. Por padrão, a HTTP API aceita solicitações de navegador de qualquer origem, com qualquer método, e com os cabeçalhos `authorization`, `content-type`, `x-amz-content-sha256`, `x-amz-date` e `x-amz-security-token`. Os últimos três são os cabeçalhos que uma assinatura SigV4 adiciona. A HTTP API também limita solicitações a uma taxa constante de 10.000 por segundo, com picos de até 5.000.

| Configuração | CDK | Variável Terraform | Padrão |
| --- | --- | --- | --- |
| Origens CORS permitidas | método `restrictCorsTo(...origins)`, ou prop `corsPreflight` | `cors_allow_origins` | qualquer origem (`["*"]`) |
| Outras configurações CORS | prop `corsPreflight` | none | qualquer método, e os cabeçalhos acima |
| Throttling | prop `throttle` | none | `{ rateLimit: 10000, burstLimit: 5000 }` |

Uma prop `corsPreflight` substitui todo o padrão, então liste todos os cabeçalhos que seus chamadores enviam. O método `restrictCorsTo` mantém as outras configurações CORS e altera apenas as origens permitidas:

```ts
const service = new MyService(this, 'MyService', { vpc });
service.restrictCorsTo('https://app.example.com');
```

No Terraform, `cors_allow_origins` e `container_user` são variáveis do módulo `ecs-service`. O módulo do seu serviço não as passa, então defina-as em seu bloco `module "ecs_service"`. Os valores de throttling são fixos em `ecs-service.tf`.

### Custo

Um container service cobra enquanto está ocioso, ao contrário de uma função Lambda. Essas partes cobram por hora, independentemente de alguém chamar o serviço ou não:

- Tarefas Fargate, por vCPU e por GB de memória. `desiredCount` e `minCapacity` mantêm pelo menos uma tarefa em execução.
- O Application Load Balancer, por hora e por unidade de capacidade do load balancer.
- Endpoints de interface VPC, por hora em cada Zona de Disponibilidade, ou um NAT gateway, por hora e por GB de dados que ele processa.
- Armazenamento de log no CloudWatch Logs e armazenamento de imagem no Amazon ECR.

A HTTP API cobra por solicitação. Para estimar o custo para sua Região e tráfego, use a [AWS Pricing Calculator](https://calculator.aws/).
