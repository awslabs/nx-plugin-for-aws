Este gerador adiciona um serviço HTTP em contêiner a um projeto TypeScript existente. Você obtém um pequeno servidor HTTP com uma rota `GET /health` e uma rota de exemplo `GET /hello`, um Dockerfile e targets para executar o servidor localmente, construir sua imagem e escanear a imagem. Você também obtém código CDK ou Terraform que executa a imagem no [Amazon Elastic Container Service (Amazon ECS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html), o serviço AWS que executa e escala contêineres.

## Como Isso Funciona

O serviço é executado no [AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), que executa cada contêiner sem servidores para você gerenciar. Cada cópia em execução do seu contêiner é uma tarefa ECS. As tarefas são executadas em sua própria VPC (nuvem privada virtual, uma rede isolada em sua conta AWS). Um security group (um conjunto de regras de firewall anexadas às tarefas) controla qual tráfego de rede pode alcançá-las e deixá-las.

O serviço é privado. Ele não tem load balancer, nenhuma API e nenhum endereço IP público. Seu security group não tem regra de entrada, então nada pode abrir uma conexão com o serviço até que você permita um chamador. O serviço ainda pode fazer chamadas de saída, por exemplo para um banco de dados ou para outros serviços AWS.

## Executando Seu Serviço Localmente

O target `<name>-serve` executa o servidor em sua máquina, sem um contêiner:

<NxCommands commands={['run your-project:service-serve']} />

O servidor escuta na porta na variável de ambiente `PORT`. O target `<name>-serve` a define para uma porta que o gerador atribui, começando em 8081 e pulando portas que outros projetos em seu workspace já usam. Dentro do contêiner, o servidor escuta na porta 8080.

O servidor escuta no endereço na variável de ambiente `HOST`, que tem como padrão `127.0.0.1`, então o target `<name>-serve` aceita conexões apenas da sua própria máquina. A imagem define `HOST=0.0.0.0`, então dentro de uma tarefa o servidor escuta na própria interface de rede da tarefa. O security group da tarefa ainda decide quem pode se conectar.

Verifique se o servidor está ativo com sua rota de saúde, que retorna status 200 e `{"status":"ok"}`:

```bash
curl http://localhost:<port>/health
```

O servidor também tem uma rota de exemplo que você substitui por suas próprias rotas. `GET /hello?name=<x>` retorna `{"message":"Hello, <x>!"}`, e `name` tem como padrão `world`. Qualquer outro caminho retorna status 404.

## Construindo e Escaneando a Imagem

O target `<name>-docker` constrói uma imagem linux/arm64 do seu serviço. Ele executa o target `bundle` primeiro, então a imagem contém o servidor empacotado. Em seguida, copia o `Dockerfile` e `.dockerignore` para a pasta de saída do bundle, `dist/<project root>/bundle/container/<name>`, e constrói a imagem com essa pasta como contexto de construção (os arquivos que a construção da imagem pode ler). Ele usa o mecanismo de contêiner com o qual seu workspace está configurado, `docker` ou [Finch](https://runfinch.com/). O target é executado como parte do target agregado `docker`, que constrói todas as imagens no projeto.

<NxCommands commands={['run your-project:service-docker']} />

No ECS, um comando de verificação de saúde é executado dentro do contêiner e chama `GET /health` na porta do contêiner. Ele não precisa de acesso de entrada. O ECS substitui uma tarefa cuja verificação de saúde continua falhando. O ECS ignora uma instrução `HEALTHCHECK` no Dockerfile. Para mais informações sobre como as imagens são construídas e publicadas, consulte <Link path="/guides/docker-bundling">Docker Bundling</Link>.

## Implantando Seu Serviço

### Adicionando o Serviço à Sua Infraestrutura

O construto e o módulo nunca criam uma VPC. Você cria ou importa uma em sua stack ou módulo raiz e a passa. As tarefas são executadas em sub-redes privadas com saída, que alcançam serviços AWS através de um NAT gateway (um gateway gerenciado que permite que sub-redes privadas façam conexões de saída) ou através de VPC endpoints (conexões privadas de sua VPC para serviços AWS).

<Infrastructure>
<Fragment slot="cdk">
O construto CDK é criado em `common/constructs` e nomeado após seu serviço. Exemplo de uso com uma nova VPC:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyService } from '@my-scope/common-constructs';
import { Stack, StackProps } from 'aws-cdk-lib';
import { SubnetType, Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ApplicationStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    new MyService(this, 'MyService', {
      vpc,
      vpcSubnets: { subnetType: SubnetType.PRIVATE_WITH_EGRESS },
    });
  }
}
```

Para usar uma VPC existente, procure-a com `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` e passe-a como `vpc`.
</Fragment>
<Fragment slot="terraform">
O módulo Terraform é criado em `common/terraform`. A imagem do serviço é publicada no repositório de ativos compartilhado, então instancie o módulo `core/asset-ecr` uma vez por implantação e passe suas saídas para cada módulo de serviço. Também passe as saídas do módulo compartilhado `runtime_config_appconfig`, que contêm o aplicativo AWS AppConfig do qual o serviço lê sua <Link path="/guides/runtime-config">configuração de runtime</Link>:

```hcl title="packages/infra/src/main.tf"
module "asset_ecr" {
  source = "../../common/terraform/src/core/asset-ecr"
}

module "my_service" {
  source = "../../common/terraform/src/app/services/my-service"

  vpc_id     = aws_vpc.main.id
  subnet_ids = aws_subnet.private[*].id

  asset_ecr_repository_url = module.asset_ecr.repository_url
  asset_ecr_repository_arn = module.asset_ecr.repository_arn

  appconfig_application_id  = module.runtime_config_appconfig.application_id
  appconfig_application_arn = module.runtime_config_appconfig.application_arn
}
```
</Fragment>
</Infrastructure>

### Executando Sem um NAT Gateway

Quando suas tarefas iniciam, o ECS puxa a imagem e envia logs em seu nome. Seu código de servidor também pode chamar serviços AWS. Em sub-redes privadas sem NAT gateway, cada uma dessas chamadas precisa de um VPC endpoint. Sem os endpoints corretos, as tarefas falham ao iniciar ou expiram quando chamam a AWS.

Crie estes endpoints na VPC, substituindo `<region>` pela sua Região AWS:

| Endpoint | Tipo | O que o usa |
| --- | --- | --- |
| `com.amazonaws.<region>.ecr.api` | Interface | ECS, para autenticar com o Amazon ECR e procurar a imagem |
| `com.amazonaws.<region>.ecr.dkr` | Interface | ECS, para puxar a imagem do Amazon ECR |
| `com.amazonaws.<region>.s3` | Gateway | ECS, para baixar camadas de imagem, que o Amazon ECR armazena no Amazon S3 |
| `com.amazonaws.<region>.logs` | Interface | A saída de log do contêiner, enviada para o Amazon CloudWatch Logs |
| `com.amazonaws.<region>.secretsmanager` | Interface | ECS, para ler os segredos que você passa para o contêiner quando uma tarefa inicia |
| `com.amazonaws.<region>.appconfigdata` | Interface | Seu código, para ler <Link path="/guides/runtime-config">configuração de runtime</Link> do AWS AppConfig |
| `com.amazonaws.<region>.sts` | Interface | Seu código, quando solicita credenciais temporárias do AWS STS (por exemplo, para assumir outra role) |

Os endpoints de interface precisam de um security group que permita HTTPS (porta 443) das tarefas. Para detalhes sobre os endpoints do Amazon ECR, consulte [Amazon ECR interface VPC endpoints](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html).

### Padrões de Segurança

A infraestrutura gerada aplica estas configurações por padrão:

- O security group do serviço não tem regra de entrada. Nenhum chamador dentro ou fora da VPC pode se conectar às tarefas até que você adicione uma regra.
- As tarefas são executadas em sub-redes privadas e nunca obtêm um endereço IP público.
- O gerador não cria load balancer nem API na frente do serviço.
- As tarefas podem enviar tráfego de saída apenas na porta 443. Conexões com bancos de dados adicionam a porta do banco de dados.
- A task role (a role como a qual seu código de servidor é executado) pode apenas ler configuração de runtime do AWS AppConfig até que você ou uma conexão conceda mais.
- A execution role (a role que o ECS usa para iniciar sua tarefa) pode apenas puxar a imagem do serviço, escrever em seu log group e ler os segredos que você lista.
- Os segredos alcançam o contêiner apenas como referências ao AWS Secrets Manager ou AWS Systems Manager Parameter Store, nunca como valores de ambiente simples.
- O contêiner tem um sistema de arquivos raiz somente leitura com uma pasta `/tmp` gravável, e é executado como uid 1000, um usuário não-root. O ECS Exec (acesso shell a uma tarefa em execução) está desativado.
- Uma implantação que falha em suas verificações de saúde para e reverte para a versão anterior.
- O log group é criptografado com uma chave AWS KMS, e os logs são mantidos por um ano.

### Permitindo que um Chamador Alcance Seu Serviço

Nada pode chamar o serviço como gerado. Se outra carga de trabalho na VPC precisar chamá-lo, por exemplo uma função Lambda ou outro serviço ECS, você adiciona uma regra de entrada ao security group do serviço você mesmo. O gerador não adiciona nenhuma regra de entrada. Permita um chamador nomeado por seu security group, na porta do contêiner, e nunca permita um intervalo de endereços.

<Infrastructure>
<Fragment slot="cdk">
O construto implementa `IConnectable`, então permita o security group do chamador através de suas `connections`:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { Port } from 'aws-cdk-lib/aws-ec2';

const svc = new MyService(this, 'MyService', { vpc });
svc.connections.allowFrom(callerSecurityGroup, Port.tcp(8080));
```

Se o security group do chamador estiver definido em seu aplicativo CDK e limitar o tráfego de saída, `allowFrom` também adiciona a regra de saída correspondente a ele.
</Fragment>
<Fragment slot="terraform">
Adicione uma regra de entrada ao security group do serviço, que o módulo do seu serviço produz como `security_group_id`, com o security group do chamador como origem:

```hcl title="packages/infra/src/main.tf"
resource "aws_vpc_security_group_ingress_rule" "caller_to_my_service" {
  security_group_id            = module.my_service.security_group_id
  referenced_security_group_id = aws_security_group.caller.id
  from_port                    = 8080
  to_port                      = 8080
  ip_protocol                  = "tcp"
}
```

Se o security group do chamador limitar o tráfego de saída, também adicione um `aws_vpc_security_group_egress_rule` no grupo do chamador para o security group do serviço.
</Fragment>
</Infrastructure>

O chamador se conecta ao endereço IP privado de uma tarefa. O gerador não configura service discovery, e o endereço de uma tarefa muda quando o ECS substitui a tarefa. Para dar aos chamadores um nome estável, configure o service discovery você mesmo, por exemplo com [Amazon ECS Service Connect](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect.html).

### Configuração Avançada

O serviço gerado define seu nome e imagem para você. Os exemplos abaixo usam o construto genérico `EcsService` e o módulo `ecs-service` diretamente, para configurações que o serviço gerado não passa.

No CDK, seu pacote `common-constructs` exporta `EcsService` ao lado do construto do seu serviço, então você o importa da mesma maneira: `import { EcsService } from '@my-scope/common-constructs'`. O construto gerado estende `EcsService` e passa todas as outras props, por exemplo `cluster`, `environment`, `secrets` e `grantTaskRole`. Sua prop opcional `image` substitui a imagem construída do seu projeto.

No Terraform, o módulo do seu serviço permite que você defina apenas algumas das variáveis do módulo `ecs-service`: `vpc_id`, `subnet_ids`, `cluster_arn`, `environment`, `secrets`, `task_role_policy_statements` e `tags`. Para definir qualquer outra variável, edite o bloco `module "ecs_service"` no módulo do seu serviço.

#### Imagem Pré-construída

Para executar uma imagem que já está construída, por exemplo de um registro público, passe seu URI. Nada é construído localmente. Para uma imagem em um repositório privado do Amazon ECR, o CDK concede à execution role acesso de pull nesse repositório. O Terraform concede acesso de pull apenas quando você também passa o ARN do repositório como `image_repository_arn`.

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'Prebuilt', {
  serviceName: 'Prebuilt',
  vpc,
  image: { imageUri: 'public.ecr.aws/my-org/my-image@sha256:<digest>' },
});
```

</Fragment>
<Fragment slot="terraform">

```hcl
module "prebuilt" {
  source = "../../common/terraform/src/core/container/ecs-service"

  service_name = "Prebuilt"
  vpc_id       = aws_vpc.main.id
  subnet_ids   = aws_subnet.private[*].id
  image_uri    = "public.ecr.aws/my-org/my-image@sha256:<digest>"
  # For an image in a private Amazon ECR repository, also pass:
  # image_repository_arn = aws_ecr_repository.my_image.arn
}
```

</Fragment>
</Infrastructure>

#### Variáveis de Ambiente e Segredos

Configurações simples vão em `environment`. Nunca coloque valores secretos lá, porque qualquer pessoa que possa ler a definição da tarefa pode lê-los. Passe segredos como referências em vez disso. A execution role pode ler apenas os segredos que você lista.

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'MyService', {

  environment: { LOG_LEVEL: 'info' },

```

</Fragment>
<Fragment slot="terraform">

```hcl
environment = { LOG_LEVEL = "info" }

```

#### Dimensionamento e Escala

Cada tarefa obtém 256 unidades de CPU (um quarto de uma vCPU) e 512 MiB de memória por padrão. O serviço inicia uma tarefa, e o autoscaling mantém entre uma e duas tarefas em execução, adicionando tarefas quando o uso médio de CPU ultrapassa 70%.

| Configuração | Prop CDK | Variável Terraform | Padrão |
| --- | --- | --- | --- |
| Unidades de CPU por tarefa | `cpu` | `cpu` | 256 |
| Memória por tarefa (MiB) | `memoryLimitMiB` | `memory` | 512 |
| Tarefas no início | `desiredCount` | `desired_count` | 1 |
| Menos tarefas | `minCapacity` | `min_capacity` | 1 |
| Mais tarefas | `maxCapacity` | `max_capacity` | 2 |
| CPU média alvo (%) | `targetCpuUtilizationPercent` | `target_cpu_utilization` | 70 |

A task role do construto ou módulo do seu serviço começa com acesso de leitura apenas à configuração de runtime. Adicione as permissões que seu código precisa:

#### Usuário do Contêiner

A definição da tarefa executa o contêiner como uid 1000, um usuário não-root. Isso corresponde ao usuário `node` que o Dockerfile fornecido define. Para executar como outro usuário, defina a prop `user` do CDK ou a variável `container_user` do Terraform. O Terraform rejeita `0` e `root`.

| Configuração | Prop CDK | Variável Terraform | Padrão |
| --- | --- | --- | --- |
| Usuário como o qual o contêiner é executado | `user` | `container_user` | `'1000'` (CDK), `"1000:1000"` (Terraform) |

No Terraform, `container_user` é uma variável do módulo `ecs-service`. O módulo do seu serviço não a passa, então defina-a em seu bloco `module "ecs_service"`.

### Custo

Um container service cobra enquanto está ocioso, ao contrário de uma função Lambda. Essas partes cobram por hora, independentemente de alguém chamar o serviço ou não:

- Tarefas Fargate, por vCPU e por GB de memória. `desiredCount` e `minCapacity` mantêm pelo menos uma tarefa em execução.
- Endpoints de interface VPC, por hora em cada Zona de Disponibilidade, ou um NAT gateway, por hora e por GB de dados que ele processa.
- Armazenamento de log no CloudWatch Logs e armazenamento de imagem no Amazon ECR.

Para estimar o custo para sua Região e tráfego, use a [AWS Pricing Calculator](https://calculator.aws/).

Em seguida, verifique no console AWS ou com a AWS CLI que o serviço e cluster ECS foram removidos. Com CDK, destroy mantém o log group do serviço e sua chave AWS KMS, porque o CDK mantém log groups e chaves a menos que uma política de remoção diga o contrário. Exclua-os você mesmo se não precisar mais dos logs. As imagens permanecem no Amazon ECR, no repositório de ativos CDK ou no repositório compartilhado `asset-ecr`. Exclua-as se você não precisar mais delas. A VPC é sua, então destruir o serviço a deixa no lugar.

## Conectando Seu Serviço

Use o gerador <Link path="/guides/connection">`connection`</Link> para conectar seu serviço a outros projetos em seu workspace:
