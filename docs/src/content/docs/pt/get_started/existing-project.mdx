Nem todo projeto começa com `pnpm create @aws/nx-workspace`. Se você já tem um [workspace Nx](https://nx.dev) — ou um monorepo ao qual você pode adicionar Nx — você pode adotar `@aws/nx-plugin` incrementalmente sem recriar seu projeto.

<Aside type="tip">
Você pode usar sua ferramenta de codificação agêntica de escolha para adicionar o plugin para você, usando o <Link path="get_started/building-with-ai">servidor MCP</Link>. Experimente o prompt:

> Add the Nx Plugin for AWS to this project.
</Aside>

## Adicionando Nx a um projeto não-Nx

Se seu projeto ainda não usa Nx, adicione-o primeiro com [`nx init`](https://nx.dev/recipes/adopting-nx/adding-to-existing-project). Este é um passo que o próprio Nx possui; o plugin se baseia em um workspace Nx funcional. Funciona em um pacote simples, um workspace npm/pnpm/yarn/bun, um Turborepo ou um monorepo Lerna:

<NxInitCommand />

Siga os prompts para adicionar Nx ao seu workspace. Para mais detalhes, consulte a [Documentação do Nx](https://nx.dev/recipes/adopting-nx/adding-to-existing-project).

<Aside type="note" title="pnpm workspaces">
pnpm executa scripts de instalação apenas para pacotes na lista de permissões, e `nx` precisa de seu script de instalação — sem ele, a instalação que `nx init` executa pode falhar, deixando um placeholder `set this to true or false` em `pnpm-workspace.yaml`. Adicione-o à lista de permissões antes de executar `nx init`:

```yaml title="pnpm-workspace.yaml"
allowBuilds:
  - nx
```
</Aside>

### Projetos não-Node (Python, Go, Java, Rust, …)

Nx e o plugin são distribuídos como pacotes npm, então um projeto sem ferramentas Node.js precisa de um `package.json` raiz mínimo antes que `nx init` possa fazer algo útil:

```json title="package.json"
{
  "name": "my-project",
  "private": true,
  "type": "module"
}
```

Crie esse arquivo, então execute `nx init` e [adicione o plugin](#adding-the-plugin) normalmente. Suas ferramentas de linguagem existentes não são tocadas — projetos Nx gerados pelo plugin (incluindo <Link path="guides/py-project">projetos Python</Link>) vivem ao lado do seu código existente, e você pode integrar seu build existente ao Nx incrementalmente.

Para trazer seus projetos existentes para o Nx, você tem algumas opções dependendo da linguagem:

- **Linguagens com um plugin Nx oficial** — [Java (Gradle ou Maven)](https://nx.dev/docs/technologies/java/introduction) e [.NET](https://nx.dev/docs/technologies/dotnet/introduction) têm plugins dedicados que inferem as tarefas dos seus projetos automaticamente. Adicione o relevante, por exemplo `nx add @nx/gradle`, `nx add @nx/maven` ou `nx add @nx/dotnet`.
- **Linguagens com um plugin da comunidade** — por exemplo [Go](https://nx.dev/plugin-registry) (`@nx-go/nx-go`) ou [Rust](https://nx.dev/plugin-registry) (`@monodon/rust`). Navegue pelo [Nx Plugin Registry](https://nx.dev/plugin-registry) para outros.
- **Qualquer outra linguagem** — adicione um `project.json` a cada projeto e defina seus targets para executar seus comandos de build existentes, para que `nx build <project>` (e `nx run-many`) os executem. Veja o <Link path="guides/workspace">guia de workspace</Link> para como `project.json` e targets são configurados.

### Projetos de pacote único

O plugin é projetado para monorepos — ele gera cada projeto em seu próprio diretório sob `packages/`. Se você está começando de um **projeto de pacote único** (um `package.json` na raiz com seu código-fonte diretamente abaixo dele, sem workspaces), mova seu pacote existente para `packages/` antes de adotar o plugin para que seu projeto fique ao lado dos que o plugin gera:

<Steps>

1. Crie um diretório `packages/<seu-pacote>/` e mova seu código-fonte, `package.json` e `tsconfig.json` para ele.
2. Crie um novo `package.json` raiz que atue como o manifesto do workspace em vez de um projeto em si:

   ```json title="package.json"
   {
     "name": "<your-workspace>",
     "private": true,
     "type": "module"
   }
   ```

3. Declare o workspace para que seu gerenciador de pacotes descubra projetos sob `packages/`. Para `pnpm`, adicione um `pnpm-workspace.yaml`:

   ```yaml title="pnpm-workspace.yaml"
   packages:
     - packages/*
   ```

   Para `npm`/`yarn`/`bun`, adicione um campo `workspaces` ao `package.json` raiz:

   ```json title="package.json"
   {
     "workspaces": ["packages/*"]
   }
   ```

4. Execute `nx init` (se ainda não o fez), então [adicione o plugin](#adding-the-plugin).

</Steps>

<Aside type="note" title="Gerenciador de pacotes">
Os projetos do plugin são gerados sob um diretório `packages/`. `pnpm` lê globs de workspace de `pnpm-workspace.yaml`; outros gerenciadores de pacotes leem o campo `workspaces` do `package.json` raiz — `init` atualiza o que seu workspace usa.
</Aside>

## Adicionando o plugin

Use [`nx add`](https://nx.dev/nx-api/nx/documents/add), que instala o plugin em uma versão compatível com sua instalação Nx e então executa seu gerador `init` para configurar seu workspace:

<NxCommands commands={['add @aws/nx-plugin']} />

Uma vez concluído, seu workspace está pronto — escolha os geradores que você precisa e comece a gerar projetos.

### O que este gerador configura

Adicionar o plugin faz as mudanças determinísticas que um workspace precisa para executar os geradores do plugin. Ele preserva o formato de módulo do seu workspace: um workspace cujo `package.json` raiz tem `type: "module"` permanece ESM, qualquer outra coisa permanece CommonJS, e o código gerado segue o mesmo padrão. Ele não sobrescreve arquivos existentes, e você pode precisar fazer algumas mudanças manuais após esta etapa dependendo da sua configuração existente.

Ele cria ou atualiza os seguintes arquivos:

<FileTree>
- aws-nx-plugin.config.mts registra seu provedor IaC escolhido (CDK ou Terraform) e motor de contêiner; geradores leem `iac.provider` daqui
- nx.json registra os geradores de sincronização (`@nx/js:typescript-sync` e `@aws/nx-plugin:ts#sync`) no target `compile` para que as referências de projeto TypeScript permaneçam sincronizadas
- tsconfig.json uma configuração TypeScript raiz referenciando os projetos do seu workspace, que a sincronização TypeScript do Nx mantém atualizada
- tsconfig.base.json as opções de compilador compartilhadas que os projetos TypeScript do plugin estendem (veja abaixo o que ele contém)
- pnpm-workspace.yaml (somente pnpm) lista de permissões dos scripts de build que as dependências do plugin precisam (`@swc/core`, `esbuild`, `nx`, `sharp`)
- package.json scripts de conveniência para tarefas comuns, além das devDependencies `@aws/nx-plugin`, `@aws/nx-plugin-mcp`, `nx`, `@nx/js`, `@nx/workspace`, `typescript` e Biome
- biome.json configuração padrão do formatador e linter Biome
- .mcp.json configura o servidor MCP para agentes de codificação suportados, a menos que desabilitado (também equivalentes .cursor/, .kiro/, .gemini/, .vscode/ e .codex/). Ele executa o próprio `@aws/nx-plugin-mcp` do workspace, então o servidor sempre corresponde à versão instalada no seu workspace
</FileTree>

A configuração do <Link path="get_started/building-with-ai">servidor MCP</Link> pode ser desabilitada com `--mcp=false`.

## Solução de problemas

#### `nx build <project>` não funciona mais para uma biblioteca TypeScript existente

A primeira execução de `ts#project` configura o plugin `@nx/js/typescript` para inferir o target de build TypeScript como `compile` (o plugin reserva `build` para orquestrar `lint`, `compile` e `test`). Bibliotecas existentes que dependem do target `build` inferido também são inferidas como `compile` — execute `nx run <project>:compile`, ou use `nx run-many --target build,compile`. Bibliotecas com um target `build` explícito em seu `project.json` não são afetadas.

#### `The workspace is out of sync`

As referências de projeto TypeScript precisam de sincronização. `init` registra os geradores de sincronização; execute:

<NxCommands commands={['sync']} />

#### `ERR_PNPM_IGNORED_BUILDS` durante a instalação

pnpm pula scripts de instalação para pacotes que não estão na lista de permissões. `init` adiciona à lista de permissões os que as ferramentas do plugin precisam (`@swc/core`, `esbuild`, `nx`, `sharp`) em `pnpm-workspace.yaml`, mas o bloqueio pode ocorrer durante o próprio `nx add @aws/nx-plugin` — antes que `init` tenha sido executado. Execute `pnpm approve-builds` e aprove os pacotes listados (ou adicione-os sob `allowBuilds:`), então execute novamente a instalação.

#### `nx sync` trava, ou `plugin worker ... exited before the connection was established`

Se duas versões diferentes de `nx` estão presentes na mesma árvore node_modules (execute `npm ls nx` para confirmar), seu IPC de plugin-worker entra em deadlock. O gerador `init` fixa a devDependency `nx` raiz na versão que os próprios pacotes `@nx/*` do plugin resolvem, mas uma instalação posterior de outro pacote `@nx/*` em uma versão de patch diferente pode reintroduzir a incompatibilidade. Alinhe cada entrada `nx` e `@nx/*` no seu `package.json` raiz para uma única versão e reinstale.

#### `ts.readConfigFile is not a function`

Seu workspace tem TypeScript 7 instalado, que [Nx ainda não suporta](https://nx.dev/docs/technologies/typescript/guides/typescript-7) — os plugins do Nx dependem da API de compilador em processo do TypeScript, que o TypeScript 7 não fornece mais. Fixe `typescript` no seu `package.json` raiz na versão que o plugin usa (o gerador `init` instala uma versão compatível) e reinstale.

#### `Recursive task invocation detected`

Seu `package.json` **raiz** está registrado como um projeto Nx (ele tem uma chave `"nx"`, que `nx init` adiciona para um repositório de pacote único) *e* contém um script `build` de `nx run-many --target build`. Nx então infere um target `build` na raiz que chama a si mesmo. Mova seu código-fonte para `packages/<seu-pacote>/` para que a raiz se torne um manifesto de workspace em vez de um projeto — veja [Projetos de pacote único](#single-package-projects). (Os próprios presets standalone do Nx evitam isso definindo `"nx": { "includedScripts": [] }` no pacote raiz; você pode fazer o mesmo como uma alternativa mais rápida.)

#### Erros TypeScript em seus projetos **existentes** após adicionar o plugin (`TS6059`, `TS7016`, `TS5011`, `NG4006`)

Os próprios projetos gerados pelo plugin carregam as configurações TypeScript que precisam em seu `tsconfig.lib.json` por projeto, então eles compilam independentemente do seu `tsconfig.base.json`. Esses erros aparecem em vez disso em um **projeto pré-existente seu** que herda um `tsconfig.base.json` que `init` criou (com `composite`/`emitDeclarationOnly`/`nodenext`) mas não é compatível com essas configurações — por exemplo, o compilador Angular rejeita `emitDeclarationOnly` (`NG4006`), ou um projeto que define `outDir` sem um `rootDir` agora precisa de um (`TS5011`). Adicione sobrescritas `tsconfig` por projeto redeclarando as opções conflitantes para esses projetos (por exemplo `"rootDir": "src"`), ou aponte os projetos do plugin e seus projetos para configurações base separadas.

`init` nunca reescreve um `tsconfig.base.json` existente, precisamente para que não possa silenciosamente quebrar os projetos que herdam dele — resolver essas incompatibilidades é uma decisão que apenas você pode tomar para sua base de código.

<Aside type="note" title="ESM e CommonJS">
O formato de módulo é em todo o workspace, lido do campo `type` do `package.json` raiz: `type: "module"` significa ESM, qualquer outra coisa (incluindo nenhum campo `type`) significa CommonJS. `init` preserva o que seu workspace usa, e os geradores TypeScript do plugin emitem código correspondente. Se você quiser mudar depois, altere o `type` raiz — mas essa é uma migração do seu código existente, não algo que `init` faz por você.
</Aside>
