Ce générateur ajoute un service HTTP conteneurisé à un projet TypeScript existant. Vous obtenez un petit serveur HTTP avec une route `GET /health` et une route d'exemple `GET /hello`, un Dockerfile et des cibles pour exécuter le serveur localement, construire son image et scanner l'image. Vous obtenez également du code CDK ou Terraform qui exécute l'image sur [Amazon Elastic Container Service (Amazon ECS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html), le service AWS qui exécute et met à l'échelle les conteneurs.

## Comment cela fonctionne

Le service s'exécute sur [AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), qui exécute chaque conteneur sans serveur à gérer. Chaque copie en cours d'exécution de votre conteneur est une tâche ECS. Les tâches s'exécutent dans votre propre VPC (cloud privé virtuel, un réseau isolé dans votre compte AWS). Un groupe de sécurité (un ensemble de règles de pare-feu attachées aux tâches) contrôle quel trafic réseau peut les atteindre et les quitter.

Le service est privé. Il n'a pas d'équilibreur de charge, pas d'API et pas d'adresse IP publique. Son groupe de sécurité n'a pas de règle entrante, donc rien ne peut ouvrir une connexion au service jusqu'à ce que vous autorisiez un appelant. Le service peut toujours effectuer des appels sortants, par exemple vers une base de données ou vers d'autres services AWS.

## Exécuter votre service localement

La cible `<name>-serve` exécute le serveur sur votre machine, sans conteneur :

<NxCommands commands={['run your-project:service-serve']} />

Le serveur écoute sur le port de la variable d'environnement `PORT`. La cible `<name>-serve` le définit sur un port que le générateur attribue, en commençant à 8081 et en sautant les ports que d'autres projets de votre espace de travail utilisent déjà. À l'intérieur du conteneur, le serveur écoute sur le port 8080.

Le serveur écoute sur l'adresse de la variable d'environnement `HOST`, qui vaut par défaut `127.0.0.1`, donc la cible `<name>-serve` accepte les connexions uniquement depuis votre propre machine. L'image définit `HOST=0.0.0.0`, donc à l'intérieur d'une tâche, le serveur écoute sur l'interface réseau propre de la tâche. Le groupe de sécurité de la tâche décide toujours qui peut se connecter.

Vérifiez que le serveur est actif avec sa route de santé, qui renvoie le statut 200 et `{"status":"ok"}` :

```bash
curl http://localhost:<port>/health
```

Le serveur a également une route d'exemple que vous remplacez par vos propres routes. `GET /hello?name=<x>` renvoie `{"message":"Hello, <x>!"}`, et `name` vaut `world` par défaut. Tout autre chemin renvoie le statut 404.

## Construire et scanner l'image

La cible `<name>-docker` construit une image linux/arm64 de votre service. Elle exécute d'abord la cible `bundle`, de sorte que l'image contient le serveur regroupé. Elle copie ensuite le `Dockerfile` et `.dockerignore` dans le dossier de sortie du bundle, `dist/<project root>/bundle/container/<name>`, et construit l'image avec ce dossier comme contexte de construction (les fichiers que la construction de l'image peut lire). Elle utilise le moteur de conteneur avec lequel votre espace de travail est configuré, `docker` ou [Finch](https://runfinch.com/). La cible s'exécute dans le cadre de la cible agrégée `docker`, qui construit toutes les images du projet.

<NxCommands commands={['run your-project:service-docker']} />

Sur ECS, une commande de vérification de santé s'exécute à l'intérieur du conteneur et appelle `GET /health` sur le port du conteneur. Elle n'a besoin d'aucun accès entrant. ECS remplace une tâche dont la vérification de santé continue d'échouer. ECS ignore une instruction `HEALTHCHECK` dans le Dockerfile. Pour plus d'informations sur la façon dont les images sont construites et publiées, consultez <Link path="/guides/docker-bundling">Docker Bundling</Link>.

## Déployer votre service

### Ajouter le service à votre infrastructure

Le construct et le module ne créent jamais de VPC. Vous en créez ou en importez un dans votre stack ou module racine et le transmettez. Les tâches s'exécutent dans des sous-réseaux privés avec sortie, qui atteignent les services AWS via une passerelle NAT (une passerelle gérée qui permet aux sous-réseaux privés d'établir des connexions sortantes) ou via des points de terminaison VPC (connexions privées de votre VPC aux services AWS).

<Infrastructure>
<Fragment slot="cdk">
Le construct CDK est créé dans `common/constructs` et nommé d'après votre service. Exemple d'utilisation avec un nouveau VPC :

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyService } from '@my-scope/common-constructs';
import { Stack, StackProps } from 'aws-cdk-lib';
import { SubnetType, Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ApplicationStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    new MyService(this, 'MyService', {
      vpc,
      vpcSubnets: { subnetType: SubnetType.PRIVATE_WITH_EGRESS },
    });
  }
}
```

Pour utiliser un VPC existant, recherchez-le avec `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` et transmettez-le comme `vpc`.
</Fragment>
<Fragment slot="terraform">
Le module Terraform est créé dans `common/terraform`. L'image du service est publiée dans le référentiel d'actifs partagé, donc instanciez le module `core/asset-ecr` une fois par déploiement et transmettez ses sorties à chaque module de service. Transmettez également les sorties du module partagé `runtime_config_appconfig`, qui contiennent l'application AWS AppConfig à partir de laquelle le service lit sa <Link path="/guides/runtime-config">configuration d'exécution</Link> :

```hcl title="packages/infra/src/main.tf"
module "asset_ecr" {
  source = "../../common/terraform/src/core/asset-ecr"
}

module "my_service" {
  source = "../../common/terraform/src/app/services/my-service"

  vpc_id     = aws_vpc.main.id
  subnet_ids = aws_subnet.private[*].id

  asset_ecr_repository_url = module.asset_ecr.repository_url
  asset_ecr_repository_arn = module.asset_ecr.repository_arn

  appconfig_application_id  = module.runtime_config_appconfig.application_id
  appconfig_application_arn = module.runtime_config_appconfig.application_arn
}
```

</Infrastructure>

### Exécution sans passerelle NAT

Lorsque vos tâches démarrent, ECS extrait l'image et envoie les journaux en leur nom. Le code de votre serveur peut également appeler des services AWS. Dans les sous-réseaux privés sans passerelle NAT, chacun de ces appels nécessite un point de terminaison VPC. Sans les bons points de terminaison, les tâches ne parviennent pas à démarrer ou expirent lorsqu'elles appellent AWS.

Créez ces points de terminaison dans le VPC, en remplaçant `<region>` par votre région AWS :

| Point de terminaison | Type | Ce qui l'utilise |
| --- | --- | --- |
| `com.amazonaws.<region>.ecr.api` | Interface | ECS, pour s'authentifier auprès d'Amazon ECR et rechercher l'image |
| `com.amazonaws.<region>.ecr.dkr` | Interface | ECS, pour extraire l'image d'Amazon ECR |
| `com.amazonaws.<region>.s3` | Passerelle | ECS, pour télécharger les couches d'image, qu'Amazon ECR stocke dans Amazon S3 |
| `com.amazonaws.<region>.logs` | Interface | La sortie de journal du conteneur, envoyée à Amazon CloudWatch Logs |
| `com.amazonaws.<region>.secretsmanager` | Interface | ECS, pour lire les secrets que vous transmettez au conteneur au démarrage d'une tâche |
| `com.amazonaws.<region>.appconfigdata` | Interface | Votre code, pour lire la <Link path="/guides/runtime-config">configuration d'exécution</Link> depuis AWS AppConfig |
| `com.amazonaws.<region>.sts` | Interface | Votre code, lorsqu'il demande des informations d'identification temporaires à AWS STS (par exemple pour assumer un autre rôle) |

Les points de terminaison d'interface nécessitent un groupe de sécurité qui autorise HTTPS (port 443) depuis les tâches. Pour plus de détails sur les points de terminaison Amazon ECR, consultez [Points de terminaison VPC d'interface Amazon ECR](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html).

### Paramètres de sécurité par défaut

L'infrastructure générée applique ces paramètres par défaut :

- Le groupe de sécurité du service n'a pas de règle entrante. Aucun appelant à l'intérieur ou à l'extérieur du VPC ne peut se connecter aux tâches jusqu'à ce que vous ajoutiez une règle.
- Les tâches s'exécutent dans des sous-réseaux privés et n'obtiennent jamais d'adresse IP publique.
- Le générateur ne crée pas d'équilibreur de charge ni d'API devant le service.
- Les tâches ne peuvent envoyer du trafic sortant que sur le port 443. Les connexions aux bases de données ajoutent le port de la base de données.
- Le rôle de tâche (le rôle sous lequel s'exécute le code de votre serveur) ne peut lire que la configuration d'exécution depuis AWS AppConfig jusqu'à ce que vous ou une connexion accordiez davantage.
- Le rôle d'exécution (le rôle qu'ECS utilise pour démarrer votre tâche) ne peut qu'extraire l'image du service, écrire dans son groupe de journaux et lire les secrets que vous listez.
- Les secrets atteignent le conteneur uniquement en tant que références à AWS Secrets Manager ou AWS Systems Manager Parameter Store, jamais en tant que valeurs d'environnement en clair.
- Le conteneur a un système de fichiers racine en lecture seule avec un dossier `/tmp` accessible en écriture, et s'exécute en tant qu'uid 1000, un utilisateur non root. ECS Exec (accès shell dans une tâche en cours d'exécution) est désactivé.
- Un déploiement qui échoue à ses vérifications de santé s'arrête et revient à la version précédente.
- Le groupe de journaux est chiffré avec une clé AWS KMS, et les journaux sont conservés pendant un an.

### Permettre à un appelant d'atteindre votre service

Rien ne peut appeler le service tel que généré. Si une autre charge de travail dans le VPC doit l'appeler, par exemple une fonction Lambda ou un autre service ECS, vous ajoutez vous-même une règle entrante au groupe de sécurité du service. Le générateur n'ajoute aucune règle entrante. Autorisez un appelant nommé par son groupe de sécurité, sur le port du conteneur, et n'autorisez jamais une plage d'adresses.

<Infrastructure>
<Fragment slot="cdk">
Le construct implémente `IConnectable`, donc autorisez le groupe de sécurité de l'appelant via ses `connections` :

```ts title="packages/infra/src/stacks/application-stack.ts"
import { Port } from 'aws-cdk-lib/aws-ec2';

const svc = new MyService(this, 'MyService', { vpc });
svc.connections.allowFrom(callerSecurityGroup, Port.tcp(8080));
```

Si le groupe de sécurité de l'appelant est défini dans votre application CDK et limite le trafic sortant, `allowFrom` ajoute également la règle sortante correspondante.
</Fragment>
<Fragment slot="terraform">
Ajoutez une règle entrante au groupe de sécurité du service, que le module de votre service sort sous `security_group_id`, avec le groupe de sécurité de l'appelant comme source :

```hcl title="packages/infra/src/main.tf"
resource "aws_vpc_security_group_ingress_rule" "caller_to_my_service" {
  security_group_id            = module.my_service.security_group_id
  referenced_security_group_id = aws_security_group.caller.id
  from_port                    = 8080
  to_port                      = 8080
  ip_protocol                  = "tcp"
}
```

Si le groupe de sécurité de l'appelant limite le trafic sortant, ajoutez également une `aws_vpc_security_group_egress_rule` sur le groupe de l'appelant vers le groupe de sécurité du service.
</Fragment>
</Infrastructure>

L'appelant se connecte à l'adresse IP privée d'une tâche. Le générateur ne configure pas de découverte de service, et l'adresse d'une tâche change lorsqu'ECS remplace la tâche. Pour donner aux appelants un nom stable, configurez vous-même la découverte de service, par exemple avec [Amazon ECS Service Connect](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect.html).

### Configuration avancée

Le service généré définit son nom et son image pour vous. Les exemples ci-dessous utilisent directement le construct générique `EcsService` et le module `ecs-service`, pour les paramètres que le service généré ne transmet pas.

En CDK, votre package `common-constructs` exporte `EcsService` à côté du construct de votre service, vous l'importez donc de la même manière : `import { EcsService } from '@my-scope/common-constructs'`. Le construct généré étend `EcsService` et transmet toutes les autres props, par exemple `cluster`, `environment`, `secrets` et `grantTaskRole`. Sa prop optionnelle `image` remplace l'image construite à partir de votre projet.

En Terraform, le module de votre service vous permet de définir uniquement certaines des variables du module `ecs-service` : `vpc_id`, `subnet_ids`, `cluster_arn`, `environment`, `secrets`, `task_role_policy_statements` et `tags`. Pour définir toute autre variable, modifiez le bloc `module "ecs_service"` dans le module de votre service.

Pour exécuter une image déjà construite, par exemple depuis un registre public, transmettez son URI. Rien n'est construit localement. Terraform accorde l'accès en extraction uniquement lorsque vous transmettez également l'ARN du référentiel sous `image_repository_arn`.

#### Variables d'environnement et secrets

Les paramètres simples vont dans `environment`. Ne mettez jamais de valeurs secrètes là, car toute personne pouvant lire la définition de tâche peut les lire. Transmettez plutôt les secrets en tant que références. Le rôle d'exécution ne peut lire que les secrets que vous listez.


</Fragment>

#### Dimensionnement et mise à l'échelle

Chaque tâche obtient 256 unités CPU (un quart de vCPU) et 512 Mio de mémoire par défaut. Le service démarre une tâche, et la mise à l'échelle automatique maintient entre une et deux tâches en cours d'exécution, en ajoutant des tâches lorsque l'utilisation moyenne du CPU dépasse 70 %.

| Paramètre | Prop CDK | Variable Terraform | Par défaut |
| --- | --- | --- | --- |
| Unités CPU par tâche | `cpu` | `cpu` | 256 |
| Mémoire par tâche (Mio) | `memoryLimitMiB` | `memory` | 512 |
| Tâches au démarrage | `desiredCount` | `desired_count` | 1 |
| Minimum de tâches | `minCapacity` | `min_capacity` | 1 |
| Maximum de tâches | `maxCapacity` | `max_capacity` | 2 |
| CPU moyen cible (%) | `targetCpuUtilizationPercent` | `target_cpu_utilization` | 70 |

#### Utilisateur du conteneur

La définition de tâche exécute le conteneur en tant qu'uid 1000, un utilisateur non root. Cela correspond à l'utilisateur `node` que le Dockerfile fourni définit. Pour exécuter en tant qu'autre utilisateur, définissez la prop CDK `user` ou la variable Terraform `container_user`. Terraform rejette `0` et `root`.

| Paramètre | Prop CDK | Variable Terraform | Par défaut |
| --- | --- | --- | --- |
| Utilisateur sous lequel le conteneur s'exécute | `user` | `container_user` | `'1000'` (CDK), `"1000:1000"` (Terraform) |

En Terraform, `container_user` est une variable du module `ecs-service`. Le module de votre service ne la transmet pas, alors définissez-la dans son bloc `module "ecs_service"`.

### Coût

Un service conteneurisé facture pendant qu'il est inactif, contrairement à une fonction Lambda. Ces parties facturent à l'heure, que quelqu'un appelle ou non le service :

- Tâches Fargate, par vCPU et par Go de mémoire. `desiredCount` et `minCapacity` maintiennent au moins une tâche en cours d'exécution.
- Points de terminaison VPC d'interface, par heure dans chaque zone de disponibilité, ou une passerelle NAT, par heure et par Go de données qu'elle traite.
- Stockage de journaux dans CloudWatch Logs et stockage d'images dans Amazon ECR.

Pour estimer le coût pour votre région et votre trafic, utilisez la [Calculatrice de tarification AWS](https://calculator.aws/).

Vérifiez ensuite dans la console AWS ou avec l'AWS CLI que le service et le cluster ECS ont disparu. Supprimez-les vous-même si vous n'avez plus besoin des journaux. Les images restent dans Amazon ECR, dans le référentiel d'actifs CDK ou le référentiel partagé `asset-ecr`. Supprimez-les si vous n'en avez plus besoin. Le VPC est le vôtre, donc la destruction du service le laisse en place.
