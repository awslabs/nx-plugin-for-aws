Générez un [Strands Agent](https://strandsagents.com/) TypeScript pour créer des agents IA avec des outils, et déployez-le optionnellement sur [Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/). Par défaut, le générateur utilise [tRPC](https://trpc.io/) sur WebSocket pour tirer parti du [support de streaming bidirectionnel d'AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-websocket.html) pour une communication en temps réel et type-safe. Alternativement, vous pouvez choisir le protocole [Agent-to-Agent (A2A)](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-a2a.html) pour l'interopérabilité avec d'autres agents compatibles A2A, ou le protocole [AG-UI](https://docs.ag-ui.com/) pour une intégration frontend directe via [CopilotKit](https://docs.copilotkit.ai/aws-strands).

## Qu'est-ce que Strands ?

[Strands](https://strandsagents.com/docs/user-guide/quickstart/overview/) est un framework léger pour créer des agents IA. Les fonctionnalités clés incluent :

- **Léger et personnalisable** : Boucle d'agent simple qui ne vous gêne pas
- **Prêt pour la production** : Observabilité complète, traçage et options de déploiement à grande échelle
- **Agnostique du modèle et du fournisseur** : Prend en charge de nombreux modèles de différents fournisseurs
- **Outils communautaires** : Ensemble puissant d'outils contribués par la communauté
- **Support multi-agents** : Techniques avancées comme les équipes d'agents et les agents autonomes
- **Modes d'interaction flexibles** : Support conversationnel, streaming et non-streaming

## Travailler avec votre Agent

### Protocole

Le protocole serveur de votre agent détermine comment il communique. Vous pouvez choisir entre :

- **HTTP** (par défaut) : Utilise [tRPC](https://trpc.io/) sur WebSocket pour une communication en temps réel et type-safe. Idéal pour les intégrations client personnalisées et un contrôle précis de l'API de l'agent.
- **A2A** : Utilise le protocole [Agent-to-Agent (A2A)](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-a2a.html) pour une communication inter-agents standardisée. Idéal lorsque votre agent doit être découvrable et invocable par d'autres agents compatibles A2A.
- **AG-UI** : Utilise le [protocole AG-UI](https://docs.ag-ui.com/) (SSE sur POST) via [`@ag-ui/aws-strands`](https://www.npmjs.com/package/@ag-ui/aws-strands) pour une intégration frontend directe avec [CopilotKit](https://docs.copilotkit.ai/aws-strands). Idéal lorsque vous souhaitez une interface de chat riche avec streaming, visualisation des appels d'outils et gestion d'état.

Le protocole est défini dans l'infrastructure CDK/Terraform, et le code de l'application est généré en conséquence.

<OptionFilter when={{ protocol: 'http' }} description="tRPC over WebSocket details">
### tRPC sur WebSocket (protocole HTTP)

L'Agent TypeScript utilise [tRPC](https://trpc.io/) sur WebSocket, tirant parti du [support de streaming bidirectionnel d'AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-websocket.html) pour permettre une communication en temps réel et type-safe entre les clients et votre agent.

Puisque tRPC prend en charge les procédures Query, Mutation et Subscription sur WebSocket, vous pouvez définir n'importe quel nombre de procédures. Par défaut, une seule procédure de souscription nommée `invoke` est définie pour vous dans `router.ts`.
</OptionFilter>

### Ajouter des outils

Les outils sont des fonctions que l'agent IA peut appeler pour effectuer des actions. Vous pouvez ajouter de nouveaux outils dans le fichier `agent.ts` :

```typescript
import { Agent, tool } from '@strands-agents/sdk';
import { z } from 'zod';

const letterCounter = tool({
  name: 'letter_counter',
  description: 'Count occurrences of a specific letter in a word',
  inputSchema: z.object({
    word: z.string().describe('The input word to search in'),
    letter: z.string().length(1).describe('The specific letter to count'),
  }),
  callback: (input) => {
    const { word, letter } = input;
    const count = word.toLowerCase().split(letter.toLowerCase()).length - 1;
    return `The letter '${letter}' appears ${count} time(s) in '${word}'`;
  },
});

// Add tools to your agent
export const getAgent = async () => {
  return new Agent({
    systemPrompt: 'You are a helpful assistant with access to various tools.',
    tools: [letterCounter],
  });
};
```

Le framework Strands gère automatiquement :
- La validation des entrées à l'aide de schémas Zod
- La génération de schémas JSON pour l'appel d'outils
- La gestion des erreurs et le formatage des réponses

### Configuration du modèle

Par défaut, les agents Strands utilisent Claude 4 Sonnet, mais vous pouvez facilement basculer entre les fournisseurs de modèles :

```typescript
import { Agent } from '@strands-agents/sdk';
import { BedrockModel } from '@strands-agents/sdk/models/bedrock';
import { OpenAIModel } from '@strands-agents/sdk/models/openai';

// Use Bedrock
const bedrockModel = new BedrockModel({
  modelId: 'anthropic.claude-sonnet-4-20250514-v1:0',
});
let agent = new Agent({ model: bedrockModel });
let response = await agent.invoke('What can you help me with?');

// Alternatively, use OpenAI by just switching model provider
const openaiModel = new OpenAIModel({
  apiKey: process.env.OPENAI_API_KEY,
  modelId: 'gpt-4o',
});
agent = new Agent({ model: openaiModel });
response = await agent.invoke('What can you help me with?');
```

Consultez la [documentation Strands sur les fournisseurs de modèles](https://strandsagents.com/docs/user-guide/concepts/model-providers/) pour plus d'options de configuration.

## Serveur A2A (protocole A2A)

Le fichier `index.ts` généré monte le [Strands A2A Express Server](https://strandsagents.com/docs/user-guide/concepts/multi-agent/agent-to-agent) sur une application Express afin que l'agent généré expose les points de terminaison du protocole A2A ainsi qu'un contrôle de santé `/ping`. ## Serveur AG-UI (protocole AG-UI)

Le fichier `index.ts` généré enveloppe votre `Agent` Strands dans un [`@ag-ui/aws-strands`](https://www.npmjs.com/package/@ag-ui/aws-strands) `StrandsAgent` et crée une application Express via `createStrandsApp()`. ### Gestion de session

L'option `session` contrôle comment votre agent persiste l'état de conversation (historique des messages, état des outils, etc.) entre les invocations, en utilisant le [SessionManager](https://strandsagents.com/docs/user-guide/concepts/agents/session-management/) du SDK Strands :

- **`s3`** (par défaut) : L'infrastructure CDK/Terraform provisionne un bucket S3 dédié pour les données de session, chiffré avec une clé KMS dédiée et avec tout accès public bloqué ; les journaux d'accès au serveur sont délivrés à un groupe de journaux CloudWatch Logs via la même clé. Le rôle IAM de l'agent reçoit un accès en lecture/écriture/liste/suppression au bucket et un accès de déchiffrement/génération-de-clé-de-données à la clé, et le nom du bucket est enregistré aux côtés de l'ARN de l'agent dans la configuration du runtime AppConfig.
- **`in-memory`** : Aucun bucket n'est provisionné. L'état de conversation est conservé en mémoire uniquement pendant la durée de vie du processus en cours d'exécution et ne survit pas aux redémarrages ou à la réduction d'échelle.

Ceci est implémenté dans le fichier `session.ts` généré, qui exporte une fonction `getSessionManager()` résolvant un `SessionManager` pour la session actuelle.

L'ID de session lui-même provient de la session AgentCore Runtime (propagée via l'en-tête `x-amzn-bedrock-agentcore-runtime-session-id` pour A2A/AG-UI, ou le contexte de connexion WebSocket pour HTTP/tRPC) et est lié à un contexte basé sur [`AsyncLocalStorage`](https://nodejs.org/api/async_context.html#class-asynclocalstorage) afin que `getCurrentSessionId()` puisse le résoudre n'importe où dans la requête — y compris dans tous les clients MCP ou A2A en aval connectés via le <Link path="/guides/connection">générateur `connection`</Link>, de sorte que toute la chaîne d'appels partage une session cohérente.

:::note[AG-UI : sessions et threads]
Le protocole AG-UI a son propre identifiant de conversation, `threadId`, dans le corps de la requête. `@ag-ui/aws-strands` met en cache un agent Strands par `threadId` et appelle `sessionManagerProvider` **une fois par thread** — la première fois que ce thread est vu.

Le fichier `index.ts` généré passe donc `sessionManagerProvider: (input) => getSessionManager(input.threadId)`, en clé l'état de conversation sur ce même identifiant de thread afin que le fournisseur et le cache de l'adaptateur soient toujours d'accord.

`getSessionManager()` se replie sur l'ID de session AgentCore actuel lorsqu'il est appelé sans argument, ce qui est la façon dont les protocoles HTTP et A2A l'utilisent.
:::

:::caution[Isolation de session]
L'ID de session et `threadId` sont tous deux fournis par l'appelant, donc aucun ne peut à lui seul identifier à qui appartient la conversation. AgentCore Runtime autorise les invocations contre l'ARN de ressource du runtime de l'agent plutôt que contre des sessions individuelles, et valide le format d'un ID de session sans le lier à l'identité de l'appelant — [la portée d'une session à un utilisateur est la responsabilité de l'agent](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-instances-security.html).

Avec `auth=cognito`, l'infrastructure générée définit `requestHeaderConfiguration.allowlistedHeaders: ['Authorization']`, de sorte que le JWT de l'appelant — déjà validé par l'autoriseur AgentCore — atteint votre code d'agent en tant qu'en-tête de requête ordinaire. Le point d'entrée du serveur lit sa revendication `sub` et la lie pour la requête, et `session.ts` construit la clé de stockage à partir de celle-ci via `getSessionStorageKey()`, produisant `u-<sub>-<conversationId>`.

Les requêtes sans revendication utilisable sont rejetées avec un 401 plutôt que de se replier sur un espace de noms non délimité. Sous `nx dev`, il n'y a pas d'autoriseur devant l'agent, donc les requêtes non authentifiées se replient sur un seul utilisateur local à la place — ce repli est contrôlé par `LOCAL_DEV`, que seules les cibles `-dev` définissent. La vérification de signature est ignorée lors du décodage de la revendication, puisque AgentCore Runtime a déjà [validé le jeton lors de l'autorisation entrante](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-oauth.html).

Sur le chemin AG-UI, le middleware supprime également l'alias `thread_id` du protocole après l'avoir plié dans `threadId`. L'adaptateur mappe `thread_id` sur `threadId` en premier-clé-gagne lorsqu'il analyse le corps, donc laisser l'alias en place permettrait à un client de faire passer en contrebande un identifiant de thread non délimité au-delà de la réécriture — gardez les deux étapes ensemble si vous personnalisez cela.

Avec `auth=iam`, SigV4 identifie le principal appelant à AgentCore Runtime plutôt qu'à votre code d'agent, donc l'état de conversation est clé sur l'ID de session seul et `bedrock-agentcore:InvokeAgentRuntime` est la limite — accordez-le à des backends de confiance, ou utilisez des principaux IAM par utilisateur afin qu'IAM applique la portée.

`getSessionStorageKey()` aplatit également les séparateurs de chemin, donc un ID de conversation ne peut pas traverser hors de son espace de noms.
:::

#### Alternative : restreindre les sessions à leur propriétaire

L'espace de noms clé le stockage par appelant, donc la conversation d'un utilisateur n'est jamais retournée à un autre. L'ID de session lui-même est toujours ce que le client a envoyé, ce qui importe dans deux cas :

- Un ID de session sélectionne la [microVM](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html) servant la requête, donc son système de fichiers, `/tmp` et les caches en processus sont partagés par chaque requête se résolvant à cette session. Deux appelants envoyant le même ID partagent ceux-ci même avec des clés de stockage séparées.
- L'espace de noms partitionne les conversations ; il ne décide pas quelles sessions un utilisateur est autorisé à reprendre.

Si l'un ou l'autre vous importe, faites en sorte que votre application possède l'ID de session à la place : émettez-le depuis une API, enregistrez à qui il appartient, et vérifiez cette propriété dans l'agent.

**1. Créer des sessions via votre API**

Ajoutez une procédure qui démarre une conversation. Elle génère l'ID de session, résout l'appelant à partir de son propre contexte de requête, et stocke la paire — par exemple dans une table créée avec le générateur <Link path="guides/ts-dynamodb">`ts#dynamodb`</Link> :

| Attribut | Exemple | Notes |
| --- | --- | --- |
| `sessionId` | `a5f1…` | Clé de partition — l'agent recherche un propriétaire à partir de l'ID de session qui lui est donné |
| `userId` | `<sub>` | L'appelant authentifié qui possède la session |
| `createdAt`, `title` | … | Tout ce dont votre interface utilisateur a besoin pour lister les conversations |

Ajoutez un index secondaire sur `userId` si vous souhaitez également lister les propres sessions d'un utilisateur.

```ts
export const createSession = publicProcedure
  .output(z.object({ sessionId: z.string() }))
  .mutation(async ({ ctx }) => {
    const sessionId = randomUUID().replaceAll('-', '');
    await sessionEntity.put({ sessionId, userId: callerSub(ctx.event) }).go();
    return { sessionId };
  });
```

Résolvez l'appelant à partir du contexte de requête vérifié plutôt qu'à partir d'un champ d'entrée, afin qu'il ne puisse pas être fourni par le navigateur. <Link path="guides/trpc">Implementing Custom Middleware</Link> montre comment pour les API authentifiées IAM et Cognito. Une deuxième procédure interrogeant l'index permet à l'interface utilisateur d'offrir à un utilisateur ses propres conversations sans voir celles de quelqu'un d'autre.

**2. Valider la propriété dans l'agent**

L'agent reçoit l'ID de session, et avec `auth=cognito` le JWT de l'appelant. Recherchez la session, comparez son propriétaire à l'appelant, et refusez la requête s'ils diffèrent :

```ts
const session = await getSession(sessionId);
if (session?.userId !== getCurrentUserId()) {
  res.status(403).json({ error: 'Session does not belong to the caller' });
  return;
}
```

L'API décide qui possède une session ; l'agent l'applique. Vérifier aux deux endroits signifie qu'un ID de session qui fuit est toujours refusé lors de la prochaine invocation, et tout futur client de l'agent hérite de la même règle.

:::caution
Générez un ID de session opaque et aléatoire et stockez le mappage. En dériver un à partir de valeurs fournies par l'utilisateur — un nom de conversation, un e-mail — est prévisible, donc un appelant peut atterrir sur une session qui ne lui a pas été donnée.
:::

:::note[Développement local]
Lors de l'exécution locale (`LOCAL_DEV=true`, défini automatiquement par la cible `-dev`), les données de session sont toujours stockées sur disque sous `tmp/agents/strands/<agent-name>` à la racine de l'espace de travail, quelle que soit l'option `session` configurée, pour plus de commodité.
:::
</OptionFilter>

## Invoquer votre Agent

La communication de l'agent est transmise via tRPC sur WebSocket. En tant que tel, il est recommandé d'utiliser la factory de client type-safe générée dans `client.ts`.

<OptionFilter when={{ protocol: 'http' }} description="tRPC-over-WebSocket client factory invocation details">
### Invoquer le serveur local

Vous pouvez invoquer un agent en cours d'exécution localement en utilisant la méthode factory `.local` de la factory de client.

Vous pouvez, par exemple, créer un fichier nommé `scripts/test.ts` dans votre espace de travail qui importe le client :

```typescript
// scripts/test.ts
import { AgentClient } from '../packages/<project>/src/agent/client.js';

const client = AgentClient.local({ url: 'http://localhost:8081/ws' });

client.invoke.subscribe({ prompt: 'what is 1 plus 1?' }, { onData: console.log });
```

:::tip[Test rapide]
Exécutez avec `tsx` comme moyen rapide de tester votre agent.

<PackageManagerExecCommand commands={['tsx scripts/test.ts']} />
:::

### Invoquer l'agent déployé

<Snippet name="agent/runtime-arn" parentHeading="Invoquer l'agent déployé" />

#### NodeJS

Le fichier `client.ts` généré inclut une factory de client type-safe qui peut être utilisée pour invoquer votre agent déployé.

:::caution[Authentification par en-tête HTTP]
La factory de client utilise des en-têtes HTTP dans la négociation WebSocket pour authentifier les requêtes vers Bedrock AgentCore Runtime. Cela n'est pas possible dans un navigateur, et par conséquent ce client n'est pas adapté aux environnements de navigateur. Consultez la section "Navigateur" ci-dessous pour plus de détails concernant l'invocation depuis un navigateur.
:::

<Tabs syncKey="auth">
<TabItem label="IAM" _filter={{ auth: 'iam' }}>
##### Authentification IAM

Vous pouvez invoquer votre agent déployé en passant son ARN à la méthode factory `withIamAuth` :

```typescript
import { AgentClient } from './agent/client.js';

const client = AgentClient.withIamAuth({
  agentRuntimeArn: 'arn:aws:bedrock-agentcore:us-west-2:123456789012:runtime/my-agent',
});

client.invoke.subscribe({ prompt: 'what is 1 plus 1?' }, {
  onData: (message) => console.log(message),
  onError: (error) => console.error(error),
  onComplete: () => console.log('Done'),
});
```

:::note[Informations d'identification AWS]
Cela utilisera la chaîne de fournisseur d'informations d'identification AWS par défaut pour authentifier les requêtes, donc l'environnement dans lequel ce qui précède est exécuté doit avoir des informations d'identification AWS configurées, avec accès pour invoquer le runtime.
:::
</TabItem>

<TabItem label="Cognito" _filter={{ auth: 'cognito' }}>
##### Authentification JWT / Cognito

Utilisez la méthode factory `withJwtAuth` pour vous authentifier avec le jeton d'accès JWT / Cognito.

```typescript
const client = AgentClient.withJwtAuth({
  agentRuntimeArn: 'arn:aws:bedrock-agentcore:us-west-2:123456789012:runtime/my-agent',
  accessTokenProvider: async () => `<access-token>`,
});

client.invoke.subscribe({ prompt: 'what is 1 plus 1?' }, {
  onData: console.log,
});
```

Le `accessTokenProvider` doit retourner le jeton utilisé pour authentifier la requête. Vous pouvez, par exemple, obtenir un jeton dans cette méthode pour vous assurer que des informations d'identification fraîches sont réutilisées lorsque tRPC redémarre une connexion WebSocket. Ce qui suit démontre l'utilisation du SDK AWS pour obtenir le jeton de Cognito :

```typescript
import { CognitoIdentityProvider } from "@aws-sdk/client-cognito-identity-provider";

const cognito = new CognitoIdentityProvider();

const jwtClient = AgentClient.withJwtAuth({
  agentRuntimeArn: 'arn:aws:bedrock-agentcore:us-west-2:123456789012:runtime/my-agent',
  accessTokenProvider: async () => {
    const response = await cognito.adminInitiateAuth({
      UserPoolId: '<user-pool-id>',
      ClientId: '<user-pool-client-id>',
      AuthFlow: 'ADMIN_NO_SRP_AUTH',
      AuthParameters: {
        USERNAME: '<username>',
        PASSWORD: '<password>',
      },
    });
    return response.AuthenticationResult!.AccessToken!;
  },
});
```
