[FastAPI](https://fastapi.tiangolo.com/) est un framework pour créer des API en Python.

Le générateur FastAPI crée une nouvelle FastAPI avec une infrastructure AWS CDK ou Terraform configurée. Le backend généré est exposé via une API AWS API Gateway. Il configure [AWS Lambda Powertools](https://docs.powertools.aws.dev/lambda/python/latest/) pour l'observabilité, incluant la journalisation structurée et les métriques CloudWatch.

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambda hosting">
Le backend utilise AWS Lambda pour un déploiement serverless, et le traçage AWS X-Ray est également configuré.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="ECS hosting">
Votre API s'exécute comme un serveur uvicorn de longue durée dans un conteneur sur Amazon ECS, derrière une API Gateway HTTP API, plutôt que dans une fonction Lambda. Voir <a href="#running-on-amazon-ecs">Running on Amazon ECS</a> pour ce que cela change, y compris pourquoi le traçage X-Ray ne produit aucune trace là-bas.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="ECS hosting is experimental">
:::caution[Expérimental]
`http-ecs` est expérimental. Sa sortie générée peut changer entre les versions sans migration pour transférer un espace de travail existant, donc attendez-vous à réconcilier ces changements vous-même lors de la mise à niveau.

Il nécessite le fournisseur IaC CDK : le support Terraform n'est pas encore implémenté. Si l'espace de travail se résout en Terraform, le générateur échoue avec un message nommant la correction.

`integrationPattern` est toujours `shared` ici. Passer `--integrationPattern=isolated` avec `http-ecs` n'échoue pas : le générateur avertit que l'option est ignorée et utilise `shared`. En exécutant le générateur de manière interactive, il demande `integrationPattern` avant `infra`, avec `isolated` présélectionné, donc cet avertissement est ce que vous voyez si vous laissez la présélection seule et choisissez ensuite `http-ecs`. Dans le générateur de commandes sur cette page, choisir `http-ecs` désactive `isolated` et l'efface s'il était sélectionné, donc la commande qu'il écrit ne porte jamais le flag.

L'option `architecture` définit si le conteneur s'exécute sur `ARM64` ou `X86_64`, et les wheels Python dans son bundle le suivent. Omettez-la pour utiliser l'architecture de la machine sur laquelle vous exécutez le générateur. Voir <Link path="/guides/py-container#cpu-architecture">CPU Architecture</Link> dans le guide des conteneurs.

## Sortie du générateur

Le générateur créera la structure de projet suivante dans le répertoire `<directory>/<api-name>` :

<FileTree>

- project.json Configuration du projet et cibles de build
- pyproject.toml Configuration du projet Python et dépendances
- run.sh Script de démarrage Lambda Web Adapter pour démarrer l'application FastAPI via uvicorn
- \<module_name>
  - \_\_init\_\_.py Initialisation du module
  - init.py Configure l'application FastAPI et configure le middleware powertools
  - main.py Implémentation de l'API
- scripts
  - generate_open_api.py Script pour générer un schéma OpenAPI à partir de l'application FastAPI

</FileTree>

<OptionFilter when={{ infra: 'http-ecs' }} description="Files that differ when the API runs on ECS">
Avec `infra` défini sur `http-ecs`, l'API s'exécute comme son propre serveur HTTP plutôt que derrière le Lambda Web Adapter, donc `run.sh` n'est pas généré. À sa place, vous obtenez un dossier de conteneur à l'intérieur de votre module, nommé d'après votre API :

<FileTree>
- \<module_name>
  - \<api_name>_container
    - main.py Point d'entrée : ajoute `GET /health`, écrit les métriques que l'API collecte, et démarre uvicorn sur `HOST` et `PORT`. Le bundle, l'image et la cible `serve` démarrent tous à partir de ce fichier
    - Dockerfile Définition de l'image du conteneur
    - .dockerignore Fichiers exclus du contexte de build de l'image
</FileTree>

Vos `init.py`, `main.py` et les opérations que vous y ajoutez sont les mêmes pour chaque valeur `infra`.
</OptionFilter>

## Implémenter votre FastAPI

L'implémentation principale de l'API se trouve dans `main.py`. C'est là que vous définissez vos routes API et leurs implémentations. Voici un exemple :

```python
from pydantic import BaseModel
from .init import app, tracer

class Item(BaseModel):
  name: str

@app.get("/items/{item_id}")
@tracer.capture_method
def get_item(item_id: int) -> Item:
    return Item(name=f"Item {item_id}")

@app.post("/items")
@tracer.capture_method
def create_item(item: Item) -> Item:
    return item
```

Le générateur configure automatiquement plusieurs fonctionnalités :

1. Intégration AWS Lambda Powertools pour l'observabilité
2. Middleware de gestion des erreurs
3. Corrélation requête/réponse
4. Collection de métriques

<OptionFilter not when={{ infra: 'http-ecs' }} description="Streaming, which needs a REST API">
Le streaming type-safe est également configuré, pour l'infrastructure `rest-lambda` uniquement.
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="How the Lambda variants serve the app">
L'application est servie dans une fonction Lambda par le [Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter) exécutant uvicorn.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="How the ECS variant serves the app">
L'application est servie par uvicorn dans le conteneur, sans Lambda Web Adapter. Voir <a href="#running-on-amazon-ecs">Running on Amazon ECS</a>.
</OptionFilter>

### Observabilité avec AWS Lambda Powertools

#### Journalisation

Le générateur configure la journalisation structurée en utilisant AWS Lambda Powertools. Vous pouvez accéder au logger dans vos gestionnaires de route :

```python
from .init import app, logger

@app.get("/items/{item_id}")
def read_item(item_id: int):
    logger.info("Fetching item", extra={"item_id": item_id})
    return {"item_id": item_id}
```

Le logger inclut automatiquement :

- Les ID de corrélation pour le traçage des requêtes
- Le chemin de la requête, la route correspondante et la méthode

#### Traçage

Le traçage AWS X-Ray est configuré automatiquement. Vous pouvez ajouter des sous-segments personnalisés à vos traces :

```python
from .init import app, tracer

@app.get("/items/{item_id}")
@tracer.capture_method
def read_item(item_id: int):
    # Creates a new subsegment
    with tracer.provider.in_subsegment("fetch-item-details"):
        # Your logic here
        return {"item_id": item_id}
```

<OptionFilter when={{ infra: 'http-ecs' }} description="X-Ray produces no traces on ECS">
:::caution[Aucune trace sur ECS]
Le décorateur et le sous-segment ci-dessus s'exécutent sans erreur dans un conteneur, mais ne produisent aucune trace. Powertools désactive son traceur lorsqu'il ne s'exécute pas dans Lambda. Voir <a href="#observability">Observability</a> pour ce que vous obtenez, et ce qu'il faut ajouter si vous avez besoin de traces.
:::
</OptionFilter>

#### Métriques

Les métriques CloudWatch sont collectées automatiquement pour chaque requête. Vous pouvez ajouter des métriques personnalisées :

```python
from .init import app, metrics
from aws_lambda_powertools.metrics import MetricUnit

@app.get("/items/{item_id}")
def read_item(item_id: int):
    metrics.add_metric(name="ItemViewed", unit=MetricUnit.Count, value=1)
    return {"item_id": item_id}
```

Les métriques par défaut incluent :

- Nombre de requêtes
- Nombre de succès/échecs
- Métriques par route (via une dimension `route` de `<method> <path>`)

### Gestion des erreurs

Le générateur inclut une gestion complète des erreurs :

```python
from fastapi import HTTPException

@app.get("/items/{item_id}")
def read_item(item_id: int):
    if item_id < 0:
        raise HTTPException(status_code=400, detail="Item ID must be positive")
    return {"item_id": item_id}
```

Les exceptions non gérées sont capturées par le middleware et :

1. Enregistrent l'exception complète avec la trace de pile
2. Enregistrent une métrique d'échec
3. Retournent une réponse 500 sécurisée au client
4. Préservent l'ID de corrélation

:::tip[Modèles de réponse]
Il est recommandé de spécifier des modèles de réponse pour vos opérations API pour une meilleure génération de code si vous utilisez le générateur `connection`. <Link path="guides/connection/react-fastapi#errors">Voir ici pour plus de détails</Link>.
:::

### Accéder à l'utilisateur appelant

<OptionFilter when={{ infra: 'http-ecs' }} description="Identity on ECS — the authorizer context does not arrive">
Sur ECS, il n'y a pas de Lambda Web Adapter et pas d'en-tête de contexte de requête API Gateway : API Gateway ne transmet pas les revendications de l'autorisateur à une intégration de load balancer privé. L'autorisateur décide toujours si une requête atteint le conteneur, mais vos gestionnaires ne peuvent pas lire l'appelant à partir de la requête comme écrit ci-dessous.

Pour lire l'identité de l'appelant dans une opération, mappez le contexte de l'autorisateur sur un en-tête de requête dans votre construct API, et lisez cet en-tête à partir de la `Request` FastAPI.
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="Identity on the Lambda variants">
Lorsque votre API est protégée par authentification, vos gestionnaires de route ont souvent besoin de savoir qui appelle. La FastAPI générée s'exécute dans AWS Lambda via le [Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter), qui transmet le contexte de requête API Gateway sous forme de JSON dans l'en-tête `x-amzn-request-context`. Vous pouvez le lire depuis la `Request` FastAPI pour extraire l'identité de l'appelant.

Par exemple, ajoutons un endpoint `/me` qui retourne des détails sur l'utilisateur appelant. Nous implémenterons l'extraction comme une [dépendance FastAPI](https://fastapi.tiangolo.com/tutorial/dependencies/) afin qu'elle puisse être réutilisée entre les routes. La forme du contexte de requête — et donc comment vous extrayez l'identité — dépend à la fois de votre méthode `auth` sélectionnée et du fait que vous ayez déployé une API REST ou HTTP.
</OptionFilter>

<OptionFilter when={{ auth: 'iam' }} description="Extraction d'identité pour les API authentifiées par IAM">
Pour l'authentification `IAM`, nous recherchons l'appelant dans Cognito en utilisant le sub extrait du contexte de requête API Gateway, ce qui nécessite `boto3`. Ajoutez-le à votre projet API :

<NxCommands commands={[`run my-api:add boto3${PY_VERSIONS.boto3}`]} />

Créez `identity.py` à côté de `main.py` :

<Tabs syncKey="http-rest">
<TabItem label="REST API" _filter={{ infra: 'rest-lambda' }}>
```python
import json
import os
from typing import Annotated

from boto3 import client
from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel

cognito = client("cognito-idp")


class Identity(BaseModel):
    sub: str
    username: str


def get_identity(request: Request) -> Identity:
    # The Lambda Web Adapter forwards the API Gateway request context as JSON
    request_context_header = request.headers.get("x-amzn-request-context")
    if not request_context_header:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    request_context = json.loads(request_context_header)
    provider = request_context.get("identity", {}).get("cognitoAuthenticationProvider")

    sub = provider.split(":")[-1] if provider else None
    if not sub:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    users = cognito.list_users(
        # Assumes user pool id is configured in lambda environment
        UserPoolId=os.environ["USER_POOL_ID"],
        Limit=1,
        Filter=f'sub="{sub}"',
    ).get("Users", [])

    if len(users) != 1:
        raise HTTPException(status_code=403, detail=f"No user found with subjectId {sub}")

    return Identity(sub=sub, username=users[0]["Username"])


CurrentUser = Annotated[Identity, Depends(get_identity)]
```
</TabItem>

from boto3 import client

    sub: str
    username: str

    # The Lambda Web Adapter forwards the API Gateway request context as JSON
    request_context_header = request.headers.get("x-amzn-request-context")
    if not request_context_header:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    request_context = json.loads(request_context_header)
    amr = (
        request_context.get("authorizer", {})
        .get("iam", {})
        .get("cognitoIdentity", {})
        .get("amr", [])
    )
    sign_in = next((s for s in amr if ":CognitoSignIn:" in s), None)
    sub = sign_in.split(":")[-1] if sign_in else None

    if not sub:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

        # Assumes user pool id is configured in lambda environment
        UserPoolId=os.environ["USER_POOL_ID"],
        Limit=1,
        Filter=f'sub="{sub}"',
    ).get("Users", [])

    if len(users) != 1:
        raise HTTPException(status_code=403, detail=f"No user found with subjectId {sub}")

    return Identity(sub=sub, username=users[0]["Username"])

Créez `identity.py` à côté de `main.py` :

```python
import json
from typing import Annotated

from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel


class Identity(BaseModel):
    sub: str
    username: str


def get_identity(request: Request) -> Identity:
    # The Lambda Web Adapter forwards the API Gateway request context as JSON
    request_context_header = request.headers.get("x-amzn-request-context")
    if not request_context_header:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    request_context = json.loads(request_context_header)
    claims = request_context.get("authorizer", {}).get("claims", {})

    sub = claims.get("sub")
    username = claims.get("username")

    if not sub or not username:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    return Identity(sub=sub, username=username)


CurrentUser = Annotated[Identity, Depends(get_identity)]
```

import json
from typing import Annotated

from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel


class Identity(BaseModel):
    sub: str
    username: str


def get_identity(request: Request) -> Identity:

### Streaming

La FastAPI générée prend en charge les réponses en streaming prêtes à l'emploi lors de l'utilisation d'une API REST. L'infrastructure est configurée pour utiliser le [AWS Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter) pour exécuter votre FastAPI via uvicorn dans Lambda, avec `ResponseTransferMode.STREAM` dans API Gateway pour toutes les opérations d'API REST, ce qui permet au streaming de fonctionner aux côtés d'opérations non-streaming.

#### Utilisation de `JsonStreamingResponse`

Le `init.py` généré exporte une classe `JsonStreamingResponse` qui fournit un streaming type-safe avec une génération de schéma OpenAPI appropriée. Cela garantit que le <Link path="guides/connection/react-fastapi">générateur `connection`</Link> peut produire des méthodes client de streaming correctement typées.

```python
from pydantic import BaseModel
from .init import app, JsonStreamingResponse

class Chunk(BaseModel):
    message: str

async def generate_chunks():
    for i in range(100):
        yield Chunk(message=f"This is chunk {i}")

@app.post(
    "/stream",
    response_class=JsonStreamingResponse,
    responses={200: JsonStreamingResponse.openapi_response(Chunk, "Stream of chunks")},
)
async def my_stream() -> JsonStreamingResponse:
    return JsonStreamingResponse(generate_chunks())
```

La classe `JsonStreamingResponse` :

1. Sérialise les modèles Pydantic au format [JSON Lines](https://jsonlines.org/) (`application/jsonl`)
2. Fournit un helper `openapi_response` qui génère le schéma OpenAPI correct avec `itemSchema`, permettant au <Link path="guides/connection/react-fastapi#consuming-a-stream">générateur `connection`</Link> de produire des méthodes client de streaming type-safe

#### Consommation

Pour consommer un flux de réponses, vous pouvez utiliser le <Link path="guides/connection/react-fastapi#consuming-a-stream">générateur `connection`</Link> qui fournira une méthode type-safe pour itérer sur vos chunks streamés.
</OptionFilter>

## Déployer votre FastAPI

Le générateur FastAPI crée une infrastructure en tant que code CDK ou Terraform en fonction de votre `iac` sélectionné. Vous pouvez l'utiliser pour déployer votre FastAPI.

<Fragment slot="cdk">
<OptionFilter not when={{ infra: 'http-ecs' }} description="CDK usage for the Lambda variants">
Le construct CDK pour déployer votre API dans le dossier `common/constructs`. Vous pouvez l'utiliser dans une application CDK :

```ts {6-8}
import { MyApi } from '@my-scope/common-constructs';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string) {
    // Add the api to your stack
    const api = new MyApi(this, 'MyApi', {
      integrations: MyApi.defaultIntegrations(this).build(),
    });
  }
}
```

Cela configure :

1. Une fonction AWS Lambda pour chaque opération dans l'application FastAPI
2. API Gateway HTTP/REST API comme déclencheur de fonction
3. Rôles IAM et permissions
4. Groupe de logs CloudWatch
5. Configuration du traçage X-Ray
6. Espace de noms de métriques CloudWatch
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="CDK usage when the API runs on ECS — pass the VPC">
`defaultIntegrations` prend le VPC dans lequel votre service s'exécute, et construit tout à l'intérieur : le service ECS, le load balancer interne devant lui, et le VPC link par lequel API Gateway atteint ce load balancer. Le construct ne crée jamais de VPC, vous devez donc en créer ou en importer un dans votre stack.

```ts {10,13-15}
import { MyApi } from '@my-scope/common-constructs';
import { Stack } from 'aws-cdk-lib';
import { Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string) {
    super(scope, id);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    const api = new MyApi(this, 'MyApi', {
      integrations: MyApi.defaultIntegrations(this, { vpc }).build(),
    });
  }
}
```

Pour utiliser un VPC existant, recherchez-le avec `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` et passez-le comme `vpc`.

Passez `service` pour modifier le service de conteneur lui-même — son `cpu`, `memoryLimitMiB`, `desiredCount`, `environment`, ou `grantTaskRole` pour donner une permission au rôle de tâche :

```ts
MyApi.defaultIntegrations(this, {
  vpc,
  service: {
    cpu: 512,
    memoryLimitMiB: 1024,
    grantTaskRole: (taskRole) => myTable.grantReadWriteData(taskRole),
  },
}).build();
```

Cela configure une API Gateway HTTP API AWS avec authentification basée sur votre méthode `auth` choisie, un service Amazon ECS exécutant votre conteneur, un load balancer interne devant lui, et le VPC link par lequel API Gateway atteint ce load balancer.
</OptionFilter>

<OptionFilter when={{ auth: 'custom' }} description="Utilisation CDK de l'autorisateur Lambda personnalisé">
:::caution[Autorisateur Lambda personnalisé]
Lors de l'utilisation de l'authentification `Custom`, le construct crée un autorisateur Lambda en interne à partir du fichier `authorizer.py` généré, qui **refuse toutes les requêtes par défaut**. Vous devez implémenter votre logique d'autorisation dans ce fichier avant que votre API n'accepte du trafic.

Les résultats de l'autorisateur sont mis en cache pendant 5 minutes, indexés sur l'en-tête `Authorization`, donc un jeton révoqué peut être accepté jusqu'à l'expiration de son résultat en cache. <OptionFilter when={{ infra: 'http-ecs' }} description="How ECS hosting works, what it costs and what it limits">
## Running on Amazon ECS

Avec `infra` défini sur `http-ecs`, votre API s'exécute comme un serveur uvicorn de longue durée dans un conteneur plutôt que dans une fonction Lambda derrière le Lambda Web Adapter. Une requête suit ce chemin :

1. Un appelant signe une requête vers l'API Gateway HTTP API, qui est le seul point d'entrée public. Chaque route porte l'autorisateur pour l'`auth` que vous avez choisi, donc une requête non authentifiée est rejetée à la périphérie.
2. API Gateway transmet la requête via un VPC link, qui est son chemin privé dans votre VPC.
3. Le VPC link atteint un load balancer interne. Le load balancer n'a pas d'adresse publique, et sa seule règle entrante autorise le groupe de sécurité du VPC link sur le port d'écoute.
4. Le load balancer transmet la requête à une tâche. La seule règle entrante des tâches autorise le groupe de sécurité du load balancer sur le port du conteneur, donc rien d'autre dans le VPC ne peut ouvrir une connexion vers elles.

Les tâches s'exécutent dans des sous-réseaux privés et n'obtiennent jamais d'adresse IP publique. Rien dans ce chemin n'autorise une plage d'adresses entrante.

Par défaut, le service, le load balancer et le VPC link vont dans les sous-réseaux `PRIVATE_WITH_EGRESS` du VPC, qui atteignent AWS via une passerelle NAT. Passer `vpcSubnets: { subnetType: SubnetType.PRIVATE_ISOLATED }` à `defaultIntegrations` supprime la passerelle NAT et ses frais horaires, mais les sous-réseaux isolés n'ont pas de route sortante, donc le VPC a alors besoin de quatre endpoints VPC pour que les tâches démarrent : des endpoints d'interface pour `ecr.api` et `ecr.dkr` pour extraire l'image, un endpoint de passerelle S3 car les couches d'image sont des objets S3, et un endpoint d'interface pour `logs` afin que le pilote `awslogs` puisse écrire. Sans eux, une tâche ne peut pas extraire son image et ECS annule le déploiement sur le disjoncteur sans dire pourquoi.

Le VPC link, le load balancer, son écouteur, le groupe cible et le bucket dans lequel le load balancer écrit ses journaux d'accès sont créés par un seul construct, `core/api/ecs-http-endpoint.ts` dans `common/constructs`, que chaque API hébergée sur ECS partage. Le construct propre de votre API nomme son service de conteneur et route chaque opération vers ce endpoint.

### Ce qui s'exécute dans le conteneur

`<module_name>/<api_name>_container/main.py` importe l'application depuis votre `main.py`, donc chaque opération que vous écrivez est servie exactement comme elle l'est sur Lambda. Il ajoute deux choses qui lui sont propres :

- `GET /health`, que le groupe cible du load balancer et le contrôle de santé du conteneur appellent. Il est déclaré `include_in_schema=False`, donc il reste en dehors de votre spécification OpenAPI et donc en dehors des routes API Gateway et des clients générés. Il est également exclu des métriques de requête, donc l'appel du groupe cible toutes les 15 secondes ne compte pas comme une requête API.
- Un middleware qui écrit les métriques que le middleware propre de l'API collecte. Sur Lambda, le gestionnaire fait cela à la fin de chaque invocation ; ce serveur vit à travers les requêtes, donc il les vide lui-même.

Les routes API Gateway proviennent toujours de votre spécification OpenAPI, donc une opération que vous ajoutez est déployée une fois que `nx build` a régénéré la spécification.

### Observabilité

Les journaux et les métriques fonctionnent comme ils le font sur Lambda : le conteneur écrit dans son propre groupe de journaux CloudWatch, et les métriques sont écrites au format de métrique intégré pour que CloudWatch Logs les extraie.

Une chose concernant les métriques est différente ici, et il vaut la peine de le savoir avant de lire un tableau de bord ou d'ajouter une métrique de votre propre chef. `metrics`, l'objet que la section <a href="#metrics">Métriques</a> ci-dessus vous dit d'importer depuis `.init`, est un `Metrics` Powertools, et chaque objet `Metrics` dans un processus partage un seul magasin de métriques. Sur Lambda, une invocation possède ce magasin du début à la fin. Un serveur uvicorn gère les requêtes en même temps, et les métriques par requête propres de l'API et celles que vous ajoutez vont dans ce seul magasin, donc deux requêtes en vol ensemble peuvent avoir leurs métriques écrites dans un seul document et attribuées à la route qui a été ajoutée en premier. Le document de l'autre requête peut sortir sans dimension `route` du tout, ne contenant que les métriques ajoutées après le premier vidage, et Powertools enregistre `PowertoolsUserWarning: Dimension 'route' has already been added` quand cela se produit. Sous un trafic léger, où les requêtes se chevauchent rarement, vous ne le verrez pas.

Donc traitez `RequestCount` et `Success` par route comme approximatifs sur ECS. Si vous avez besoin d'une métrique attribuée à exactement une requête, ajoutez-la à un `EphemeralMetrics` que vous créez dans la requête et videz avant de retourner, qui conserve un magasin qui lui est propre :

```python
from aws_lambda_powertools.metrics import EphemeralMetrics, MetricUnit

@app.get("/items/{item_id}")
def read_item(item_id: int):
    request_metrics = EphemeralMetrics()
    request_metrics.add_metric(name="ItemViewed", unit=MetricUnit.Count, value=1)
    request_metrics.flush_metrics()
    return {"item_id": item_id}
```

Le traçage AWS X-Ray ne le fait pas. `@tracer.capture_method` est une no-op en dehors de Lambda, et il n'y a pas non plus de démon X-Ray dans la tâche pour recevoir des segments. Ajoutez-en un comme sidecar dans votre service de conteneur si vous avez besoin de traces.

Le journal d'accès de l'API Gateway HTTP API enregistre chaque requête qui atteint l'API. Le load balancer écrit ses propres journaux d'accès dans un bucket que le construct `EcsHttpEndpoint` crée, c'est là que vous pouvez voir quelle tâche a servi une requête et ce qu'elle a répondu.

### Build et scan d'image

Le générateur de conteneur fournit les cibles d'image, nommées d'après votre API :

- `<api-name>-container-docker` construit une image linux/arm64, exécutant d'abord le bundle pour que l'image contienne votre package et ses dépendances.
- `<api-name>-container-trivy` scanne cette image pour les vulnérabilités.

Voir <Link path="/guides/py-container">Python Container Service</Link> pour comment l'image est construite, et <Link path="/guides/docker-bundling">Docker Bundling</Link> pour comment elle est publiée au moment du déploiement.

### Limites

- **Timeout d'intégration.** Les API Gateway HTTP APIs plafonnent une intégration à environ 30 secondes. Une opération qui prend plus de temps que cela échoue à la passerelle quelle que soit la durée pendant laquelle le conteneur continue de fonctionner.
- **Pas de streaming.** Les opérations de streaming nécessitent l'infrastructure `rest-lambda`. Une HTTP API ne peut pas streamer une réponse.
- **Taille de charge utile.** Les requêtes et les réponses suivent la limite de 10 Mo d'API Gateway.
- **Un service pour chaque opération.** `integrationPattern` est `shared` : il y a un seul service de conteneur, et chaque route y est routée. L'option se résout toujours à `shared` pour cette infrastructure, et `isolated` est ignoré avec un avertissement.

### Coût

Le load balancer est le nouveau coût fixe par rapport à Lambda, où vous payez par requête et rien lorsqu'il est inactif. Chiffres mensuels approximatifs dans us-east-1, avant transfert de données :

| Élément | Approximativement |
| --- | --- |
| Load balancer interne | 16 $ plus les unités de capacité du load balancer |
| Tâche Fargate, 0,25 vCPU / 0,5 Go arm64 | 7 $ par tâche |
| Passerelle NAT, si votre VPC en a une | 33 $ |
| VPC link | pas de frais horaires |
| Stockage S3 pour les journaux d'accès du load balancer | centimes par Go par mois |

Donc un service à une tâche coûte environ 23 $ par mois avant tout trafic, et plus si le VPC que vous passez a une passerelle NAT. Les journaux d'accès augmentent avec le trafic : ajoutez une règle de cycle de vie à `endpoint.accessLogsBucket` pour les faire expirer. Consultez les pages de tarification [Elastic Load Balancing](https://aws.amazon.com/elasticloadbalancing/pricing/) et [AWS Fargate](https://aws.amazon.com/fargate/pricing/) pour les prix actuels dans votre région.
