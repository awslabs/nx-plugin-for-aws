[tRPC](https://trpc.io/) est un framework pour créer des API en TypeScript avec une sécurité de type de bout en bout. Avec tRPC, les mises à jour des entrées et sorties des opérations d'API sont immédiatement reflétées dans le code client et sont visibles dans votre IDE sans avoir besoin de reconstruire votre projet.

Le générateur d'API tRPC crée une nouvelle API tRPC avec une configuration d'infrastructure AWS CDK ou Terraform. Le backend généré est exposé via une API AWS API Gateway, et inclut la validation de schéma avec [Zod](https://zod.dev/). Il configure [AWS Lambda Powertools](https://docs.powertools.aws.dev/lambda/typescript/latest/) pour l'observabilité, incluant la journalisation structurée et les métriques CloudWatch.

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambda hosting">
Le traçage AWS X-Ray est également configuré.

Vos procédures s'exécutent sur AWS Lambda, il n'y a donc pas de serveur à gérer et vous ne payez que pour les requêtes que vous servez.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="ECS hosting">
Vos procédures s'exécutent en tant que serveur HTTP de longue durée dans un conteneur sur Amazon ECS, derrière une API Gateway HTTP API. Voir <a href="#running-on-amazon-ecs">Exécution sur Amazon ECS</a> pour ce que cela change, y compris pourquoi le traçage X-Ray ne produit aucune trace là-bas.
</OptionFilter>

## Sortie du générateur

Le générateur créera la structure de projet suivante dans le répertoire `<directory>/<api-name>` :

<FileTree>
  - src
    - index.ts Package entrypoint re-exporting the router, context, client and schema
    - init.ts Backend tRPC initialisation
    - handler.ts Lambda handler entrypoint
    - router.ts tRPC router definition
    - schema Schema definitions using Zod
      - index.ts Barrel re-exporting every schema
      - echo.ts Example definitions for the input and output of the "echo" procedure
      - z-async-iterable.ts Zod helper for subscriptions (REST API only)
    - procedures Procedures (or operations) exposed by your API
      - echo.ts Example procedure
    - middleware
      - index.ts Barrel re-exporting the middleware, and the procedure context type
      - error.ts Middleware for error handling

      - tracer.ts middleware for configuring AWS Powertools for Lambda tracing
      - metrics.ts middleware for configuring AWS Powertools for Lambda metrics
    - local-server.ts tRPC standalone adapter entrypoint for local development server

  - tsconfig.lib.json TypeScript configuration for the library sources
  - tsconfig.spec.json TypeScript configuration for the tests

  - package.json Project manifest defining the project's package name and dependencies

## Implémenter votre API tRPC

À un niveau élevé, les API tRPC consistent en un routeur qui délègue les requêtes à des procédures spécifiques. Chaque procédure a une entrée et une sortie, définies comme un schéma Zod.

### Schéma

Le répertoire `src/schema` contient les types qui sont partagés entre votre code client et serveur. Dans ce package, ces types sont définis en utilisant [Zod](https://zod.dev/), une bibliothèque de déclaration et de validation de schéma TypeScript-first.

Un exemple de schéma pourrait ressembler à ceci :

```ts
import { z } from 'zod';

// Schema definition
export const UserSchema = z.object({
  name: z.string(),
  height: z.number(),
  dateOfBirth: z.string().datetime(),
});

// Corresponding TypeScript type
export type User = z.TypeOf<typeof UserSchema>;
```

Étant donné le schéma ci-dessus, le type `User` est équivalent au TypeScript suivant :

```ts
interface User {
  name: string;
  height: number;
  dateOfBirth: string;
}
```

Les schémas sont partagés par le code serveur et client, fournissant un seul endroit à mettre à jour lors de modifications des structures utilisées dans votre API.

Les schémas sont automatiquement validés par votre API tRPC au moment de l'exécution, ce qui évite de créer manuellement une logique de validation personnalisée dans votre backend.

Zod fournit des utilitaires puissants pour combiner ou dériver des schémas tels que `.merge`, `.pick`, `.omit` et plus encore. Vous pouvez trouver plus d'informations sur le [site de documentation Zod](https://zod.dev/?id=basic-usage).

### Routeur et procédures

Votre routeur tRPC est défini dans `src/router.ts`, qui enregistre toutes les procédures. Chaque procédure définit l'entrée, la sortie et l'implémentation attendues.

<OptionFilter not when={{ infra: 'http-ecs' }} description="The Lambda entry point">
Le point d'entrée du gestionnaire Lambda se trouve dans `src/handler.ts`, qui transmet les requêtes à votre routeur.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="The container entry point">
Le point d'entrée est `src/<api-name>-container/server.ts`, le serveur HTTP que le conteneur exécute, qui transmet les requêtes à votre routeur.
</OptionFilter>

Le routeur exemple généré pour vous a une seule opération, appelée `echo` :

```ts
import { echo } from './procedures/echo.js';

export const appRouter = router({
  echo,
});
```

L'exemple de procédure `echo` est généré pour vous dans `src/procedures/echo.ts` :

```ts
export const echo = publicProcedure
  .input(EchoInputSchema)
  .output(EchoOutputSchema)
  .query((opts) => ({ message: opts.input.message }));
```

Pour décomposer ce qui précède :

- `publicProcedure` définit une méthode publique sur l'API, incluant le middleware configuré dans `src/middleware`. Ce middleware inclut l'intégration AWS Lambda Powertools pour la journalisation, le traçage et les métriques.
- `input` accepte un schéma Zod qui définit l'entrée attendue pour l'opération. Les requêtes envoyées pour cette opération sont automatiquement validées par rapport à ce schéma.
- `output` accepte un schéma Zod qui définit la sortie attendue pour l'opération. Vous verrez des erreurs de type dans votre implémentation si vous ne retournez pas une sortie conforme au schéma.
- `query` accepte une fonction qui définit l'implémentation de votre API. Cette implémentation reçoit `opts`, qui contient l'`input` passé à votre opération, ainsi que d'autres contextes configurés par le middleware, disponibles dans `opts.ctx`. La fonction passée à `query` doit retourner une sortie conforme au schéma `output`.

L'utilisation de `query` pour définir l'implémentation indique que l'opération n'est pas mutative. Utilisez ceci pour définir des méthodes de récupération de données. Pour implémenter une opération mutative, utilisez plutôt la méthode `mutation`.

Si vous ajoutez une nouvelle procédure, assurez-vous de l'enregistrer en l'ajoutant au routeur dans `src/router.ts`.

<OptionFilter when={{ infra: 'rest-lambda' }} description="Streaming subscriptions — REST API only, uses SSE">
### Subscriptions (Streaming)

Les subscriptions tRPC vous permettent de diffuser des données du serveur au client en utilisant [Server-Sent Events (SSE)](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events). Lorsque vous sélectionnez `rest-lambda` comme type de calcul, le générateur configure automatiquement l'infrastructure requise pour le streaming, ainsi qu'un gestionnaire Lambda de streaming et l'assistant de schéma `ZodAsyncIterable`.

Pour définir une procédure de subscription, utilisez la méthode `.subscription` avec une fonction générateur asynchrone. Utilisez l'assistant `ZodAsyncIterable` de `src/schema/z-async-iterable.ts` pour définir le schéma de sortie :

```ts
import { publicProcedure } from '../init.js';
import { z } from 'zod';
import { ZodAsyncIterable } from '../schema/z-async-iterable.js';

const InputSchema = z.object({ query: z.string() });
const ChunkSchema = z.object({ text: z.string() });

export const myStream = publicProcedure
  .input(InputSchema)
  .output(
    ZodAsyncIterable({
      yield: ChunkSchema,
    }),
  )
  .subscription(async function* (opts) {
    // Yield data to the client as it becomes available
    for (const chunk of await getResults(opts.input.query)) {
      yield { text: chunk };
    }
  });
```

Enregistrez la subscription dans votre routeur comme n'importe quelle autre procédure :

```ts
export const appRouter = router({
  echo,
  myStream,
});
```

L'infrastructure générée utilise un gestionnaire Lambda de streaming avec `ResponseTransferMode.STREAM` dans API Gateway pour toutes les opérations d'API REST, ce qui permet aux subscriptions de fonctionner aux côtés des requêtes et mutations régulières.
</OptionFilter>

## Personnaliser votre API tRPC

### Erreurs

Dans votre implémentation, vous pouvez retourner des réponses d'erreur aux clients en lançant une `TRPCError`. Celles-ci acceptent un `code` qui indique le type d'erreur, par exemple :

```ts
throw new TRPCError({
  code: 'NOT_FOUND',
  message: 'The requested resource could not be found',
});
```

### Organiser vos opérations

Au fur et à mesure que votre API grandit, vous souhaiterez peut-être regrouper les opérations connexes.

Vous pouvez regrouper les opérations en utilisant des routeurs imbriqués, par exemple :

```ts
import { getUser } from './procedures/users/get.js';
import { listUsers } from './procedures/users/list.js';

const appRouter = router({
   users: router({
      get: getUser,
      list: listUsers,
   }),
   ...
})
```

Les clients reçoivent alors ce regroupement d'opérations, par exemple l'invocation de l'opération `listUsers` dans ce cas pourrait ressembler à ceci :

```ts
client.users.list.query();
```

### Journalisation

Le logger AWS Lambda Powertools est configuré dans `src/middleware/logger.ts`, et peut être accédé dans une implémentation d'API via `opts.ctx.logger`. Vous pouvez l'utiliser pour journaliser dans CloudWatch Logs, et/ou contrôler des valeurs supplémentaires à inclure dans chaque message de journal structuré. Par exemple :

```ts {5}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      opts.ctx.logger.info('Operation called with input', opts.input);

      return ...;
   });
```

Pour plus d'informations sur le logger, veuillez vous référer à la [documentation AWS Lambda Powertools Logger](https://docs.powertools.aws.dev/lambda/typescript/latest/core/logger/).

### Enregistrer des métriques

Les métriques AWS Lambda Powertools sont configurées dans `src/middleware/metrics.ts`, et peuvent être accédées dans une implémentation d'API via `opts.ctx.metrics`. Vous pouvez l'utiliser pour enregistrer des métriques dans CloudWatch sans avoir besoin d'importer et d'utiliser le SDK AWS, par exemple :

```ts {5}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      opts.ctx.metrics.addMetric('Invocations', 'Count', 1);

      return ...;
   });
```

Pour plus d'informations, veuillez vous référer à la [documentation AWS Lambda Powertools Metrics](https://docs.powertools.aws.dev/lambda/typescript/latest/core/metrics/).

### Affiner le traçage X-Ray

Le traceur AWS Lambda Powertools est configuré dans `src/middleware/tracer.ts`, et peut être accédé dans une implémentation d'API via `opts.ctx.tracer`. Vous pouvez l'utiliser pour ajouter des traces avec AWS X-Ray afin de fournir des informations détaillées sur les performances et le flux des requêtes d'API. Par exemple :

```ts {5-7}
export const echo = publicProcedure
   .input(...)
   .output(...)
   .query(async (opts) => {
      const subSegment = opts.ctx.tracer.getSegment()!.addNewSubsegment('MyAlgorithm');
      // ... my algorithm logic to capture
      subSegment.close();

      return ...;
   });
```

Pour plus d'informations, veuillez vous référer à la [documentation AWS Lambda Powertools Tracer](https://docs.powertools.aws.dev/lambda/typescript/latest/core/tracer/).

<OptionFilter when={{ infra: 'http-ecs' }} description="X-Ray produces no traces on ECS">
:::caution[Aucune trace sur ECS]
Les appels ci-dessus s'exécutent sans erreur dans un conteneur, mais ne produisent aucune trace. Powertools désactive son traceur lorsqu'il ne s'exécute pas dans Lambda, donc `getSegment()` retourne un sous-segment de substitution qui n'est jamais envoyé nulle part. Voir <a href="#observability">Observabilité</a> pour ce que vous obtenez, et ce qu'il faut ajouter si vous avez besoin de traces.
:::
</OptionFilter>

### Implémenter un middleware personnalisé

Vous pouvez ajouter des valeurs supplémentaires au contexte fourni aux procédures en implémentant un middleware.

À titre d'exemple, implémentons un middleware pour extraire des détails sur l'utilisateur appelant notre API dans `src/middleware/identity.ts`.

<OptionFilter when={{ auth: 'iam', infra: ['rest-lambda', 'http-lambda'] }} description="Identity middleware example for IAM-authenticated APIs on Lambda">
Cet exemple présente un middleware d'identité pour l'authentification `IAM`. Nous recherchons l'appelant dans Cognito en utilisant le sub extrait de l'événement API Gateway.

La recherche utilise le client Cognito Identity Provider, qui n'est pas une dépendance d'une API tRPC générée. Installez-le d'abord dans votre projet d'API :

<InstallCommand pkg={`@aws-sdk/client-cognito-identity-provider@${TS_VERSIONS['@aws-sdk/client-cognito-identity-provider']}`} project="@my-scope/my-api" />

Tout d'abord, nous définissons ce que nous ajouterons au contexte :

```ts
export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}
```

Notez que nous définissons une propriété supplémentaire _optionnelle_ au contexte. tRPC gère l'assurance que cela est défini dans les procédures qui ont correctement configuré ce middleware.

Ensuite, nous implémenterons le middleware lui-même. Il a la structure suivante :

```ts
export const createIdentityPlugin = () => {
   const t = initTRPC.context<...>().create();
   return t.procedure.use(async (opts) => {
      // Add logic here to run before the procedure

      const response = await opts.next(...);

      // Add logic here to run after the procedure

      return response;
   });
};
```

Dans notre cas, nous voulons extraire des détails sur l'utilisateur Cognito appelant. Nous le ferons en extrayant l'ID de sujet de l'utilisateur (ou "sub") de l'événement API Gateway, et en récupérant les détails de l'utilisateur depuis Cognito. L'implémentation varie selon que l'événement a été fourni à notre fonction par une API REST ou une API HTTP :

<TabItem label="REST API" _filter={{ infra: 'rest-lambda' }}>
```ts
import { CognitoIdentityProvider } from '@aws-sdk/client-cognito-identity-provider';
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEvent } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext & CreateAWSLambdaContextOptions<APIGatewayProxyEvent>
    >()
    .create();

  const cognito = new CognitoIdentityProvider();

  return t.procedure.use(async (opts) => {
    const cognitoAuthenticationProvider =
      opts.ctx.event.requestContext?.identity?.cognitoAuthenticationProvider;

    let sub: string | undefined = undefined;
    if (cognitoAuthenticationProvider) {
      const providerParts = cognitoAuthenticationProvider.split(':');
      sub = providerParts[providerParts.length - 1];
    }

    if (!sub) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `Unable to determine calling user`,
      });
    }

    const { Users } = await cognito.listUsers({
      // Assumes user pool id is configured in lambda environment
      UserPoolId: process.env.USER_POOL_ID!,
      Limit: 1,
      Filter: `sub="${sub}"`,
    });

    if (!Users || Users.length !== 1) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: `No user found with subjectId ${sub}`,
      });
    }

    // Provide the identity to other procedures in the context
    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username: Users[0].Username!,
        },
      },
    });
  });
};
```

import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEventV2WithIAMAuthorizer } from 'aws-lambda';

Lorsque vous déployez avec `auth: 'cognito'`, l'autorisateur Cognito d'API Gateway vérifie le JWT que l'appelant fournit dans l'en-tête `Authorization` et place les revendications vérifiées sur l'événement Lambda. Notre middleware lit simplement ces revendications — pas d'appels SDK AWS supplémentaires, pas de vérification JWT manuelle.

Tout d'abord, nous définissons ce que nous ajouterons au contexte :

```ts
export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}
```

Notez que nous définissons une propriété supplémentaire _optionnelle_ sur le contexte. tRPC gère l'assurance que cela est défini dans les procédures qui ont correctement configuré ce middleware.

Ensuite, le middleware lui-même. Le type d'événement et l'emplacement des revendications diffèrent entre une API REST et une API HTTP, donc l'implémentation dépend de votre `infra` sélectionné :

<Tabs syncKey="http-rest">
<TabItem label="REST API" _filter={{ infra: 'rest-lambda' }}>
L'autorisateur Cognito User Pools d'une API REST place les revendications à `event.requestContext.authorizer.claims` :

```ts
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEvent } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext & CreateAWSLambdaContextOptions<APIGatewayProxyEvent>
    >()
    .create();

  return t.procedure.use(async (opts) => {
    const claims = opts.ctx.event.requestContext?.authorizer?.claims as
      | Record<string, string>
      | undefined;

    const sub = claims?.sub;
    const username = claims?.username ?? claims?.['cognito:username'];

    if (!sub || !username) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: 'Unable to determine calling user',
      });
    }

    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username,
        },
      },
    });
  });
};
```
</TabItem>
<TabItem label="HTTP API" _filter={{ infra: 'http-lambda' }}>
L'autorisateur JWT d'une API HTTP fournit un événement payload-v2 dont les revendications se trouvent un niveau plus profond, à `event.requestContext.authorizer.jwt.claims`. Le contexte doit être typé sur `APIGatewayProxyEventV2WithJWTAuthorizer` pour correspondre à celui utilisé par le `publicProcedure` généré — sinon `.concat()` échoue avec l'erreur `Context mismatch` de tRPC :

```ts
import { initTRPC, TRPCError } from '@trpc/server';
import type { CreateAWSLambdaContextOptions } from '@trpc/server/adapters/aws-lambda';
import type { APIGatewayProxyEventV2WithJWTAuthorizer } from 'aws-lambda';

export interface IIdentityContext {
  identity?: {
    sub: string;
    username: string;
  };
}

export const createIdentityPlugin = () => {
  const t = initTRPC
    .context<
      IIdentityContext &
        CreateAWSLambdaContextOptions<APIGatewayProxyEventV2WithJWTAuthorizer>
    >()
    .create();

  return t.procedure.use(async (opts) => {
    const claims = opts.ctx.event.requestContext?.authorizer?.jwt?.claims as
      | Record<string, string>
      | undefined;

    const sub = claims?.sub;
    const username = claims?.username ?? claims?.['cognito:username'];

    if (!sub || !username) {
      throw new TRPCError({
        code: 'FORBIDDEN',
        message: 'Unable to determine calling user',
      });
    }

    return await opts.next({
      ctx: {
        ...opts.ctx,
        identity: {
          sub,
          username,
        },
      },
    });
  });
};
```
</TabItem>
</Tabs>

Vous pouvez ensuite mélanger le plugin dans n'importe quelle procédure qui a besoin de l'identité de l'appelant :

```ts
import { publicProcedure } from '../init.js';
import { createIdentityPlugin } from '../middleware/identity.js';
import { z } from 'zod';

export const me = publicProcedure
  .concat(createIdentityPlugin())
  .output(z.object({ sub: z.string(), username: z.string() }))
  .query(({ ctx }) => ({
    sub: ctx.identity!.sub,
    username: ctx.identity!.username,
  }));
```

:::tip[Aucune vérification de jeton requise]
Vous n'avez pas besoin de `aws-jwt-verify` ou d'une autre bibliothèque de vérification JWT ici — l'autorisateur Cognito User Pools d'API Gateway a déjà vérifié la signature, l'émetteur, les portées et l'expiration au moment où votre Lambda s'exécute. Si l'une de ces vérifications échoue, API Gateway retourne `401 Unauthorized` et votre gestionnaire n'est jamais invoqué.
:::

<OptionFilter when={{ infra: 'http-ecs' }} description="How ECS hosting works, what it costs and what it limits">
## Exécution sur Amazon ECS

Avec `infra` défini sur `http-ecs`, vos procédures s'exécutent en tant que serveur HTTP de longue durée dans un conteneur plutôt que dans une fonction Lambda. Une requête suit ce chemin :

1. Un appelant signe une requête vers l'API Gateway HTTP API, qui est le seul point d'entrée public. Chaque route porte l'autorisateur pour l'`auth` que vous avez choisi, donc une requête non authentifiée est rejetée à la périphérie.
2. API Gateway transmet la requête via un lien VPC, qui est son chemin privé dans votre VPC.
3. Le lien VPC atteint un équilibreur de charge interne. L'équilibreur de charge n'a pas d'adresse publique, et sa seule règle entrante autorise le groupe de sécurité du lien VPC sur le port d'écoute.
4. L'équilibreur de charge transmet la requête à une tâche. La seule règle entrante des tâches autorise le groupe de sécurité de l'équilibreur de charge sur le port du conteneur, donc rien d'autre dans le VPC ne peut ouvrir une connexion vers elles.

Les tâches s'exécutent dans des sous-réseaux privés et n'obtiennent jamais d'adresse IP publique. Rien dans ce chemin n'autorise une plage d'adresses entrante.

Par défaut, le service, l'équilibreur de charge et le lien VPC vont dans les sous-réseaux `PRIVATE_WITH_EGRESS` du VPC, qui atteignent AWS via une passerelle NAT. Passer `vpcSubnets: { subnetType: SubnetType.PRIVATE_ISOLATED }` à `defaultIntegrations` supprime la passerelle NAT et ses frais horaires, mais les sous-réseaux isolés n'ont pas de route sortante, donc le VPC a alors besoin de quatre points de terminaison VPC pour que les tâches démarrent : des points de terminaison d'interface pour `ecr.api` et `ecr.dkr` pour extraire l'image, un point de terminaison de passerelle S3 car les couches d'image sont des objets S3, et un point de terminaison d'interface pour `logs` afin que le pilote `awslogs` puisse écrire. Sans eux, une tâche ne peut pas extraire son image et ECS annule le déploiement sur le disjoncteur sans dire pourquoi.

Le lien VPC, l'équilibreur de charge, son écouteur, le groupe cible et le bucket dans lequel l'équilibreur de charge écrit ses journaux d'accès sont créés par un seul construct, `core/api/ecs-http-endpoint.ts` dans `common/constructs`, que chaque API hébergée sur ECS partage. Le construct propre de votre API nomme son service de conteneur et route chaque opération vers ce point de terminaison.

### Ce qui s'exécute dans le conteneur

`src/<api-name>-container/server.ts` est un serveur `node:http` avec deux tâches. `GET /health` répond `{"status":"ok"}`, ce que le groupe cible de l'équilibreur de charge et la vérification de santé du conteneur appellent. Toute autre requête va à l'[adaptateur autonome tRPC](https://trpc.io/docs/server/adapters/standalone), qui la résout par rapport à votre routeur.

Il n'y a pas d'événement API Gateway dans le conteneur, donc le contexte de procédure ne porte aucun champ `event`, `context` ou `info` : pour `http-ecs`, l'`IMiddlewareContext` fourni ne nomme que ce que le middleware y met. L'autorisateur décide toujours si une requête atteint le conteneur, mais ses revendications n'arrivent pas avec la requête, donc les exemples de middleware d'identité ci-dessus ne s'appliquent pas. Pour lire l'identité de l'appelant dans une procédure, mappez le contexte de l'autorisateur sur un en-tête de requête dans votre construct d'API et lisez cet en-tête.

### Observabilité

Les journaux et les métriques fonctionnent comme sur Lambda : le conteneur écrit dans son propre groupe de journaux CloudWatch, et le plugin de métriques publie les métriques de chaque requête au format de métrique intégré pour que CloudWatch Logs les extraie.

Le plugin de métriques construit un objet de métriques pour chaque requête et le transmet à vos procédures en tant que `opts.ctx.metrics`, donc une métrique qu'une requête ajoute n'est jamais publiée avec celle d'une autre. Cela compte plus ici que sur Lambda, où une invocation possède les métriques du début à la fin ; ce serveur gère les requêtes en même temps. Ajoutez vos propres métriques via `opts.ctx.metrics` plutôt qu'un objet `Metrics` propre, qui partagerait un magasin à travers chaque requête dans le processus.

Le traçage AWS X-Ray ne fonctionne pas. Powertools désactive son traceur en dehors de Lambda, et il n'y a pas de démon X-Ray dans la tâche pour recevoir les segments, donc les appels `opts.ctx.tracer` s'exécutent sans erreur et ne produisent aucune trace. Ajoutez un démon en tant que sidecar dans votre service de conteneur si vous en avez besoin.

Le journal d'accès de l'API Gateway HTTP API enregistre chaque requête qui atteint l'API. L'équilibreur de charge écrit ses propres journaux d'accès dans un bucket que le construct `EcsHttpEndpoint` crée, c'est là que vous pouvez voir quelle tâche a servi une requête et ce qu'elle a répondu.

### Construction et analyse d'image

Le générateur de conteneur fournit les cibles d'image, nommées d'après votre API :

- `<api-name>-container-docker` construit une image linux/arm64, en exécutant d'abord `bundle` pour que l'image contienne le serveur groupé.
- `<api-name>-container-trivy` analyse cette image pour les vulnérabilités.

Voir <Link path="/guides/ts-container">TypeScript Container Service</Link> pour comment l'image est construite, et <Link path="/guides/docker-bundling">Docker Bundling</Link> pour comment elle est publiée au moment du déploiement.

### Déploiement et démontage

`deploy-sandbox` déploie en <Link path="/guides/typescript-infrastructure#deploying-your-sandbox-stage">mode express CloudFormation</Link>, qui retourne une fois que la configuration de chaque ressource est appliquée plutôt que d'attendre que le service ECS atteigne un état stable. Ainsi, la cible peut se terminer pendant que la première tâche démarre encore, et jusqu'à ce qu'une tâche ait réussi deux vérifications de santé espacées de quinze secondes, l'équilibreur de charge n'a pas de cible à laquelle envoyer une requête et répond `503`. Attendez une minute ou deux et réessayez. Un `503` qui ne se résout jamais est un véritable échec plutôt qu'un démarrage lent : le disjoncteur de déploiement du service l'annule lorsqu'aucune tâche ne devient saine.

L'URL de l'API est une sortie de stack, mais pas sous le nom que vous devineriez. Le `CfnOutput` est créé à l'intérieur de votre construct d'API et rien ne remplace son ID logique, donc CDK construit la clé de sortie à partir du chemin du construct plus un hachage de huit caractères : une API ajoutée comme `new MyApi(this, 'MyApi', …)` produit `MyApiMyApiUrl` et ce hachage, pas `MyApiUrl`. `cdk deploy` imprime la valeur, et un script devrait correspondre au suffixe plutôt qu'à la clé entière :

```bash
aws cloudformation describe-stacks --stack-name <stack-name> \
  --query "Stacks[0].Outputs[?contains(OutputKey, 'Url')].OutputValue" --output text
```

`destroy-sandbox` laisse derrière lui le groupe de journaux d'accès de l'API HTTP et la clé KMS gérée par le client qui le chiffre. Aucun ne définit de politique de suppression, donc la valeur par défaut de CDK `Retain` s'applique et CloudFormation les ignore plutôt que de les supprimer. Listez-les avant de démonter la stack, car une stack supprimée ne rapporte plus ses ressources :

```bash
aws cloudformation describe-stack-resources --stack-name <stack-name> \
  --query "StackResources[?contains(LogicalResourceId, 'AccessLogs') && (ResourceType=='AWS::Logs::LogGroup' || ResourceType=='AWS::KMS::Key')].[ResourceType,PhysicalResourceId]" \
  --output text
```

Ensuite, supprimez-les avec `aws logs delete-log-group --log-group-name <log-group-name>` et `aws kms schedule-key-deletion --key-id <key-id> --pending-window-in-days 7`, sept jours étant la fenêtre la plus courte que KMS accepte.

### Limites

- **Délai d'intégration.** Les API Gateway HTTP plafonnent une intégration à environ 30 secondes. Une procédure qui prend plus de temps que cela échoue à la passerelle, peu importe combien de temps le conteneur continue de travailler.
- **Pas de streaming.** Les subscriptions tRPC nécessitent l'infrastructure `rest-lambda`. Une API HTTP ne peut pas diffuser une réponse.
- **Taille de charge utile.** Les requêtes et les réponses suivent la limite de 10 Mo d'API Gateway.
- **Un service pour chaque opération.** `integrationPattern` est `shared` : il y a un service de conteneur, et chaque route y est routée. L'option se résout toujours à `shared` pour cette infrastructure, et `isolated` est ignoré avec un avertissement.

### Coût

L'équilibreur de charge est le nouveau coût fixe par rapport à Lambda, où vous payez par requête et rien en inactivité. Chiffres mensuels approximatifs dans us-east-1, avant transfert de données :

| Élément | Approximativement |
| --- | --- |
| Équilibreur de charge interne | 16 $ plus unités de capacité d'équilibreur de charge |
| Tâche Fargate, 0,25 vCPU / 0,5 GB arm64 | 7 $ par tâche |
| Passerelle NAT, si votre VPC en a une | 33 $ |
| Lien VPC | pas de frais horaires |
| Stockage S3 pour les journaux d'accès de l'équilibreur de charge | centimes par Go par mois |

Donc un service à une tâche coûte environ 23 $ par mois avant tout trafic, et plus si le VPC que vous passez a une passerelle NAT. Les journaux d'accès augmentent avec le trafic : ajoutez une règle de cycle de vie à `endpoint.accessLogsBucket` pour les faire expirer. Consultez les pages de tarification [Elastic Load Balancing](https://aws.amazon.com/elasticloadbalancing/pricing/) et [AWS Fargate](https://aws.amazon.com/fargate/pricing/) pour les prix actuels dans votre région.

L'image définit `HOST=0.0.0.0` pour que le serveur écoute sur l'interface réseau propre de la tâche, où le groupe de sécurité de la tâche décide qui peut se connecter.

Vérifiez que le serveur est actif avec sa route de santé, qui retourne le statut 200 et `{"status":"ok"}` :

```bash
curl http://localhost:2022/health
```

## Invoquer votre API tRPC

Vous pouvez créer un client tRPC pour invoquer votre API de manière type-safe. Si vous appelez votre API tRPC depuis un autre backend, vous pouvez utiliser le client dans `src/client/index.ts`, par exemple :

```ts
import { createMyApiClient } from '@my-scope/my-api';

const client = createMyApiClient({ url: 'https://my-api-url.example.com/' });

await client.echo.query({ message: 'Hello world!' });
```

Si vous appelez votre API depuis un site web React, envisagez d'utiliser le générateur <Link path="guides/connection/react-trpc">Connection</Link> pour configurer le client.
