## Tâche 1 : Exécuter tout localement

Démarrez la pile locale complète — le serveur de développement game-ui avec une Game API locale et un Story Agent AG-UI local (qui à son tour démarre le serveur MCP Inventory) — avec une seule commande :

<NxCommands commands={["dev game-ui"]} />

La cible `dev` sur `game-ui` a `dependsOn` sur `game-api:dev` et `dungeon_adventure.story:agent-dev`, donc Nx démarre le serveur local de chaque projet en parallèle. Grâce aux connexions que nous avons configurées dans le Module 1, ceux-ci démarrent à leur tour le serveur MCP Inventory et DynamoDB Local. Assurez-vous que votre moteur de conteneurs est en cours d'exécution, puis ouvrez le serveur de développement dans un navigateur.

<Aside type="tip" title="Pas de connexion en local">
En mode `local-dev`, le composant `CognitoAuth` ignore le flux de connexion Cognito (il n'y a pas de pool d'utilisateurs en cours d'exécution localement), vous arriverez donc directement sur le jeu sans vous connecter. Vous créerez un vrai compte lorsque nous déploierons sur AWS à la fin de ce module.
</Aside>

<Aside type="caution" title="Gardez le serveur de développement en cours d'exécution">
Laissez le serveur de développement en cours d'exécution pour le reste de ce module — il recharge à chaud chaque modification ci-dessous.
</Aside>

## Tâche 2 : Où CopilotKit est déjà configuré

Lorsque vous avez exécuté le générateur `connection` pour `game-ui → story` dans le <Link path="get_started/tutorials/dungeon-game/1">Module 1</Link>, l'intégration AG-UI du site web Shadcn a été générée pour vous. Cela vaut la peine d'y jeter un coup d'œil rapide :

<FileTree>
- packages/game-ui/src/
  - components/
    - AguiProvider.tsx Single `CopilotKitProvider` registered with every AG-UI agent.
    - copilot/
      - index.tsx Re-exports themed `CopilotChat` / `CopilotSidebar` / `CopilotPopup`.
      - ShadcnAssistantMessage.tsx, ShadcnUserMessage.tsx, ShadcnChatInput.tsx, ShadcnCursor.tsx, copilot.css
  - hooks/
    - useAguiStoryAgent.tsx Instantiates an `@ag-ui/client` `HttpAgent` pointing at the deployed Story Agent and pads `threadId` to AgentCore's 33-character minimum session id.

</FileTree>

Tout ce que nous devons faire est de déposer un `<CopilotChat agentId="agent" threadId={...} />` dans une route. Pour plus de détails sur la façon dont l'intégration est assemblée, consultez le <Link path="guides/connection/react-agui">guide de connexion React → AG-UI</Link>.

## Tâche 4 : Créer les routes du jeu

Nous avons besoin de deux routes — une pour choisir un héros, une pour jouer. Les deux utilisent des composants shadcn et le chat CopilotKit ; il n'y a pas d'interface de chat faite à la main.

<Tabs>
<TabItem label="routes/index.tsx">
<E2EDiff before="dungeon-adventure/4/routes/index.tsx.old.template" after="dungeon-adventure/4/routes/index.tsx.template" lang="tsx" />

C'est le sélecteur de jeu : formulaire de nouveau jeu (shadcn `Input` + `Button` + `Card`) plus une liste "Continuer" alimentée par `useGameApi().games.query` avec `useInfiniteQuery` — une sentinelle `<div>` en bas surveillée par un `IntersectionObserver` appelle automatiquement `fetchNextPage()` lorsqu'elle est défilée dans la vue, et des spinners à côté du titre et en dessous de la liste affichent l'état de chargement. Démarrer un jeu `saveGame` la paire `(playerName, genre)` (pour qu'elle apparaisse la prochaine fois) et navigue vers la route de jeu.
</TabItem>
<TabItem label="routes/game/$playerName.tsx">
<E2ECode path="dungeon-adventure/4/routes/game/$playerName.tsx.template" lang="tsx" />

C'est la route de jeu. Elle construit le `threadId` déterministe (``{player}-{genre}`` complété à 33 caractères — le hook AG-UI l'enverra tel quel comme identifiant de session AgentCore), rend `<CopilotChat agentId="agent" threadId={threadId} />`, et superpose l'inventaire de `useGameApi().inventory.query` par-dessus. Au montage, `useGameApi().actions.query({ sessionId: threadId })` lit l'historique de conversation que l'agent a stocké dans S3 et — s'il y en a — appelle `agent.setMessages(...)` pour réhydrater le chat ; sinon il envoie un message utilisateur d'amorçage pour lancer l'histoire. `agent.messages` est souscrit via `useAgent({ updates: [OnMessagesChanged] })` donc chaque nouveau tour récupère également la requête d'inventaire (les appels d'outils MCP mutent DynamoDB directement).

<Aside type="tip" title="Attendez `isFetching`, pas `isLoading`">
Le cache par défaut de React Query conserve le premier résultat pendant 5 minutes, donc une visite de retour voit initialement la liste vide périmée du tout premier chargement. Nous définissons `staleTime: 0` + `refetchOnMount: 'always'` et protégeons le `useEffect` d'hydratation sur `!isFetching && isSuccess` pour que le chemin de ré-amorçage ne se déclenche que sur un thread véritablement vide.
</Aside>

<Aside type="tip" title="Les threadIds déterministes rendent /game/$playerName?genre=... partageable">
Revisiter la même URL — que ce soit après un rechargement, un redéploiement, ou sur un autre appareil — se résout au même `threadId`, donc l'agent continue de raconter la même histoire.
</Aside>

<Aside type="tip" title="Paramètres de chemin">
La syntaxe `$playerName` indique à `@tanstack/react-router` de traiter `playerName` comme un [paramètre de chemin](https://tanstack.com/router/v1/docs/framework/react/guide/path-params). `validateSearch` rend `genre` fortement typé par rapport à notre enum.
</Aside>
</TabItem>
</Tabs>

## Tâche 5 : Déployer sur AWS

Votre jeu est complet et vous avez testé chaque élément localement. Maintenant, déployons-le sur AWS pour que vous puissiez y jouer de n'importe où.

### Construire votre code

<PackageManagerShortCommand commands={["build"]} />

### Déployer votre application

<NxCommands commands={['deploy-sandbox infra']} />

:::caution[Bootstrap requis]
Si c'est le premier déploiement CDK dans votre compte/région AWS, bootstrappez-le d'abord :

<NxCommands commands={['bootstrap infra']} />
:::

La cible `deploy-sandbox` déploie l'étape sandbox définie dans `packages/infra/src/main.ts`.

Votre premier déploiement prendra environ 6 minutes pour se terminer car il attend que toutes les ressources se stabilisent complètement. Les déploiements suivants sont plus rapides. Pour accélérer l'itération pendant le développement, vous pouvez opter pour le [mode express CloudFormation](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cloudformation-express-mode.html) en passant le flag `--express`, qui termine chaque opération de ressource dès que sa configuration est appliquée plutôt que d'attendre la stabilisation complète.

## Tâche 6 : Mélanger les composants locaux et déployés

Vous avez vu les deux extrêmes du spectre : tout local (`dev`) et tout déployé. Pendant le développement quotidien, il est souvent utile de mélanger les deux — par exemple, itérer sur le code du site web contre l'API et l'agent *réels* déployés, ou exécuter l'API localement contre la table DynamoDB *réelle*.

La clé est la variable d'environnement `RUNTIME_CONFIG_APP_ID`. Lorsqu'un projet s'exécute **sans** `LOCAL_DEV=true`, les recherches de configuration d'exécution récupèrent leur configuration depuis AWS AppConfig en utilisant cet identifiant d'application — la valeur `RuntimeConfigApplicationId` de vos sorties CDK.

Chaque site web a une cible `load-runtime-config` qui télécharge le `runtime-config.json` déployé (pool Cognito, points de terminaison API, ARN de l'agent) dans le serveur de développement local. Quelques combinaisons utiles :

- **Site web local → backend déployé.** Tirez la configuration déployée une fois, puis exécutez la cible `serve` simple pour que l'interface utilisateur communique avec l'API et l'agent déployés :

  <NxCommands commands={["load-runtime-config game-ui"]} />
  <NxCommands commands={["serve game-ui"]} />

- **API locale → table DynamoDB réelle.** Exécutez la cible `serve` simple avec `RUNTIME_CONFIG_APP_ID` défini sur l'identifiant d'application déployé :

  <NxCommands env={{RUNTIME_CONFIG_APP_ID:"<RuntimeConfigApplicationId from CDK outputs>"}} commands={["serve game-api"]} />

Cette flexibilité vous permet de tester exactement la partie sur laquelle vous travaillez, contre les composants — locaux ou déployés — qui ont du sens.
