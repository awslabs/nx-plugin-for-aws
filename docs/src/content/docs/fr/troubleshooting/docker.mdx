Cette page fournit des conseils de dépannage pour les problèmes que vous pourriez rencontrer avec les builds Docker produits par les générateurs. Consultez le <Link path="/guides/docker-bundling">guide Docker Bundling</Link> pour comprendre le modèle qu'ils suivent.

## Builds Multi-Plateformes

Les générateurs tels que <Link path="/guides/ts-agent">`ts#agent`</Link>, <Link path="/guides/py-agent">`py#agent`</Link>, <Link path="/guides/ts-mcp-server">`ts#mcp-server`</Link> et <Link path="/guides/py-mcp-server">`py#mcp-server`</Link> produisent des images pour `linux/arm64` (Graviton), quelle que soit l'architecture de l'hôte.

Les générateurs de services conteneurisés, <Link path="/guides/ts-container">`ts#container`</Link> et <Link path="/guides/py-container">`py#container`</Link>, prennent plutôt une option `architecture`. Si elle est omise, il s'agit de l'architecture de la machine sur laquelle vous avez exécuté le générateur, de sorte que ces images se construisent nativement. Vous rencontrez les symptômes ci-dessous lorsque vous la définissez sur l'architecture que votre machine n'est pas, ou lorsque vous construisez une image générée par une autre machine.

Construire une image `arm64` sur un hôte `x86_64` — ou une image `amd64` sur Apple Silicon — nécessite la prise en charge des [builds multi-plateformes](https://docs.docker.com/build/building/multi-platform/) dans votre installation Docker locale.

Si les builds multi-plateformes ne sont pas configurés, le symptôme dépend du `Dockerfile` :

- **Le `Dockerfile` contient une étape `RUN`** (les générateurs TypeScript exécutent `RUN npm install` pour les dépendances non empaquetables) : le build échoue en cours de route avec

  ```bash
  exec /bin/sh: exec format error
  ```

- **Le `Dockerfile` utilise uniquement `COPY`** (générateurs Python) : le build réussit, mais `docker run` échoue plus tard avec

  ```bash
  exec /usr/local/bin/python: exec format error
  ```

- **L'image de base n'est pas disponible pour la plateforme cible** : le build échoue à l'étape `FROM` avec `no match for platform in manifest`.

### Activer les Builds Multi-Plateformes

**Docker Desktop** (Mac / Windows / Linux) est livré avec l'émulation [QEMU](https://www.qemu.org/) activée par défaut — aucune configuration supplémentaire n'est généralement requise.

**Les hôtes Linux** (y compris les runners CI) nécessitent l'enregistrement des gestionnaires QEMU binfmt auprès du noyau. Installez-les une fois par machine :

```bash
docker run --privileged --rm tonistiigi/binfmt --install all
```

Vérifiez que les plateformes prises en charge correspondent à ce que votre projet cible :

```bash
docker buildx inspect --bootstrap
```

La ligne `Platforms:` devrait inclure `linux/arm64`.

Un service conteneurisé que vous êtes sur le point de créer peut éviter l'émulateur à la place : générez-le pour l'architecture de votre propre machine. <Link path="/guides/ts-container">`ts#container`</Link> et <Link path="/guides/py-container">`py#container`</Link> le font par défaut, et `--architecture=ARM64` ou `--architecture=X86_64` choisit délibérément. Cela détermine l'architecture sur laquelle le service se déploie, c'est donc un choix de conception, pas une solution de contournement de build. Déplacer un service qui existe déjà nécessite également une modification de son infrastructure fournie — consultez la section Architecture CPU de l'un ou l'autre guide.

:::tip[Environnements CI]
GitHub Actions, GitLab CI et les fournisseurs similaires n'enregistrent généralement **pas** les gestionnaires QEMU par défaut. Ajoutez une étape telle que [`docker/setup-qemu-action`](https://github.com/docker/setup-qemu-action) avant toute cible `nx build` / `nx docker` qui produit une image multi-architecture.
:::

## Builds Lents sur Architectures Émulées

Construire une image `arm64` sur un hôte `x86_64` (ou vice versa) utilise QEMU pour émuler chaque instruction, ce qui peut être plusieurs fois plus lent qu'un build natif. Les générateurs atténuent cela en effectuant la résolution des dépendances **en dehors** du `Dockerfile` — voir <Link path="/guides/docker-bundling">Docker Bundling</Link>. Si vous constatez toujours des builds Docker lents :

- Assurez-vous d'exécuter les cibles `bundle` / `docker` via Nx (`nx docker my-project`) afin que le bundle soit mis en cache entre les exécutions.
- Sur CI, envisagez un runner ARM natif (par exemple `ubuntu-24.04-arm` de GitHub Actions) pour éviter complètement QEMU.

## Contexte de Build Manquant lors de `cdk deploy` / `nx apply`

La cible `docker` générée écrit son contexte de build dans `dist/packages/<project>/docker/...` (Python) ou `dist/packages/<project>/bundle/...` (TypeScript), et l'infrastructure en tant que code générée pointe vers ce répertoire. Si ce répertoire n'existe pas lorsque vous effectuez un synth ou un apply, vous verrez des erreurs comme `ENOENT` ou "directory does not exist".

Les générateurs déclarent la cible `docker` comme dépendance de `build`, donc `nx build` (ou les cibles `nx deploy` / `nx apply` générées) produiront le contexte de build avant que CDK ou Terraform ne s'exécute. Si vous invoquez `cdk` ou `terraform` directement, exécutez d'abord l'étape docker :

```bash
nx run my-project:docker
```
