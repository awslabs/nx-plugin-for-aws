#### `-dev` vs `-serve`

Le générateur ajoute deux cibles qui exécutent le même serveur sur le même port. Elles ne diffèrent que par l'environnement qu'elles définissent :

| Cible | Environnement | Utilisation |
| --- | --- | --- |
| `<your-agent-name>-dev` | `PORT`, `LOCAL_DEV=true` | Développement local |
| `<your-agent-name>-serve` | `PORT` | Exercer le chemin de code déployé localement |

**Utilisez `<your-agent-name>-dev` pour le développement local.** `LOCAL_DEV=true` bascule l'agent sur ses chemins de code locaux : l'état de session est écrit sur le disque sous `tmp/agents/` à la racine de l'espace de travail, et tous les serveurs MCP connectés sont atteints via HTTP direct plutôt que via AgentCore. C'est également la cible que la cible `dev` au niveau du projet agrège, et celle que la cible `<your-agent-name>-chat` s'attend à trouver en cours d'exécution.

`<your-agent-name>-serve` exécute le même chemin de code que votre agent déployé, qui résout le stockage de session et les ARN de runtime connectés à partir de la <Link path="guides/runtime-config">Configuration d'exécution</Link> dans AppConfig. Cela nécessite que `RUNTIME_CONFIG_APP_ID` soit défini sur l'identifiant d'application AppConfig d'un déploiement (affiché en tant que `RuntimeConfigApplicationId` par la pile déployée), ainsi que des informations d'identification AWS autorisées à le lire :

```bash
RUNTIME_CONFIG_APP_ID=<app-id> nx run your-project:agent-serve
```

:::caution[`-serve` nécessite une configuration déployée]
Démarré sans `RUNTIME_CONFIG_APP_ID`, `<your-agent-name>-serve` accepte les requêtes mais chaque invocation échoue avec `RUNTIME_CONFIG_APP_ID is not set — cannot resolve connected agent ARNs from AppConfig.`

Définissez `LOCAL_DEV=true` pour emprunter les chemins de code locaux à la place — c'est ce que `<your-agent-name>-dev` fait déjà pour vous.
:::
