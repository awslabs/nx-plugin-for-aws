No todos los proyectos comienzan con `pnpm create @aws/nx-workspace`. Si ya tienes un [espacio de trabajo Nx](https://nx.dev) — o un monorepo al que puedes agregar Nx — puedes adoptar `@aws/nx-plugin` de forma incremental sin recrear tu proyecto.

<Aside type="tip">
Puedes usar tu herramienta de codificación agéntica de preferencia para agregar el plugin por ti, usando el <Link path="get_started/building-with-ai">servidor MCP</Link>. Prueba el prompt:

> Add the Nx Plugin for AWS to this project.
</Aside>

## Agregar Nx a un proyecto no-Nx

Si tu proyecto aún no usa Nx, agrégalo primero con [`nx init`](https://nx.dev/recipes/adopting-nx/adding-to-existing-project). Este es un paso que Nx mismo posee; el plugin se construye sobre un espacio de trabajo Nx funcional. Funciona en un paquete simple, un espacio de trabajo npm/pnpm/yarn/bun, un monorepo Turborepo o Lerna:

<NxInitCommand />

Sigue las indicaciones para agregar Nx a tu espacio de trabajo. Para más detalles consulta la [Documentación de Nx](https://nx.dev/recipes/adopting-nx/adding-to-existing-project).

<Aside type="note" title="pnpm workspaces">
pnpm solo ejecuta scripts de instalación para paquetes en la lista de permitidos, y `nx` necesita su script de instalación — sin él, la instalación que realiza `nx init` puede fallar, dejando un marcador de posición `set this to true or false` en `pnpm-workspace.yaml`. Agrégalo a la lista de permitidos antes de ejecutar `nx init`:

```yaml title="pnpm-workspace.yaml"
allowBuilds:
  - nx
```
</Aside>

### Proyectos no-Node (Python, Go, Java, Rust, …)

Nx y el plugin se distribuyen como paquetes npm, por lo que un proyecto sin herramientas Node.js necesita un `package.json` raíz mínimo antes de que `nx init` pueda hacer algo útil:

```json title="package.json"
{
  "name": "my-project",
  "private": true,
  "type": "module"
}
```

Crea ese archivo, luego ejecuta `nx init` y [agrega el plugin](#agregar-el-plugin) como de costumbre. Tus herramientas de lenguaje existentes no se tocan — los proyectos Nx generados por el plugin (incluyendo <Link path="guides/py-project">proyectos Python</Link>) viven junto a tu código existente, y puedes conectar tu compilación existente a Nx de forma incremental.

Para traer tus proyectos existentes bajo Nx, tienes algunas opciones dependiendo del lenguaje:

- **Lenguajes con un plugin oficial de Nx** — [Java (Gradle o Maven)](https://nx.dev/docs/technologies/java/introduction) y [.NET](https://nx.dev/docs/technologies/dotnet/introduction) tienen plugins dedicados que infieren las tareas de tus proyectos automáticamente. Agrega el relevante, por ejemplo `nx add @nx/gradle`, `nx add @nx/maven` o `nx add @nx/dotnet`.
- **Lenguajes con un plugin de la comunidad** — por ejemplo [Go](https://nx.dev/plugin-registry) (`@nx-go/nx-go`) o [Rust](https://nx.dev/plugin-registry) (`@monodon/rust`). Explora el [Registro de Plugins de Nx](https://nx.dev/plugin-registry) para otros.
- **Cualquier otro lenguaje** — agrega un `project.json` a cada proyecto y define sus targets para ejecutar tus comandos de compilación existentes, para que `nx build <project>` (y `nx run-many`) los ejecuten. Consulta la <Link path="guides/workspace">guía del espacio de trabajo</Link> para ver cómo se configuran `project.json` y los targets.

### Proyectos de un solo paquete

El plugin está diseñado para monorepos — genera cada proyecto en su propio directorio bajo `packages/`. Si estás comenzando desde un **proyecto de un solo paquete** (un `package.json` en la raíz con tu código fuente directamente debajo, sin espacios de trabajo), mueve tu paquete existente a `packages/` antes de adoptar el plugin para que tu proyecto se ubique junto a los que genera el plugin:

<Steps>

1. Crea un directorio `packages/<tu-paquete>/` y mueve tu código fuente, `package.json` y `tsconfig.json` dentro de él.
2. Crea un nuevo `package.json` raíz que actúe como el manifiesto del espacio de trabajo en lugar de un proyecto en sí:

   ```json title="package.json"
   {
     "name": "<your-workspace>",
     "private": true,
     "type": "module"
   }
   ```

3. Declara el espacio de trabajo para que tu gestor de paquetes descubra proyectos bajo `packages/`. Para `pnpm`, agrega un `pnpm-workspace.yaml`:

   ```yaml title="pnpm-workspace.yaml"
   packages:
     - packages/*
   ```

   Para `npm`/`yarn`/`bun`, agrega un campo `workspaces` al `package.json` raíz en su lugar:

   ```json title="package.json"
   {
     "workspaces": ["packages/*"]
   }
   ```

4. Ejecuta `nx init` (si no lo has hecho), luego [agrega el plugin](#agregar-el-plugin).

</Steps>

<Aside type="note" title="Gestor de paquetes">
Los proyectos del plugin se generan bajo un directorio `packages/`. `pnpm` lee los globs del espacio de trabajo desde `pnpm-workspace.yaml`; otros gestores de paquetes leen el campo `workspaces` del `package.json` raíz — `init` actualiza el que use tu espacio de trabajo.
</Aside>

## Agregar el plugin

Usa [`nx add`](https://nx.dev/nx-api/nx/documents/add), que instala el plugin en una versión compatible con tu instalación de Nx y luego ejecuta su generador `init` para configurar tu espacio de trabajo:

<NxCommands commands={['add @aws/nx-plugin']} />

Una vez que se complete, tu espacio de trabajo está listo — elige los generadores que necesites y comienza a generar proyectos.

### Qué configura este generador

Agregar el plugin realiza los cambios determinísticos que un espacio de trabajo necesita para ejecutar los generadores del plugin. Preserva el formato de módulo de tu espacio de trabajo: un espacio de trabajo cuyo `package.json` raíz tiene `type: "module"` permanece ESM, cualquier otra cosa permanece CommonJS, y el código generado sigue el mismo patrón. No sobrescribe archivos existentes, y es posible que necesites hacer algunos cambios manuales después de este paso dependiendo de tu configuración existente.

Crea o actualiza los siguientes archivos:

<FileTree>
- aws-nx-plugin.config.mts registra tu proveedor de IaC elegido (CDK o Terraform) y motor de contenedores; los generadores leen `iac.provider` desde aquí
- nx.json registra los generadores de sincronización (`@nx/js:typescript-sync` y `@aws/nx-plugin:ts#sync`) en el target `compile` para que las referencias de proyecto TypeScript permanezcan sincronizadas
- tsconfig.json una configuración TypeScript raíz que referencia los proyectos de tu espacio de trabajo, que la sincronización TypeScript de Nx mantiene actualizada
- tsconfig.base.json las opciones de compilador compartidas que los proyectos TypeScript del plugin extienden (ver abajo para lo que contiene)
- pnpm-workspace.yaml (solo pnpm) lista de permitidos de los scripts de compilación que las dependencias del plugin necesitan (`@swc/core`, `esbuild`, `nx`, `sharp`)
- package.json scripts de conveniencia para tareas comunes, más las dependencias de desarrollo `@aws/nx-plugin`, `@aws/nx-plugin-mcp`, `nx`, `@nx/js`, `@nx/workspace`, `typescript` y Biome
- biome.json configuración predeterminada del formateador y linter Biome
- .mcp.json configura el servidor MCP para agentes de codificación compatibles a menos que se deshabilite (también equivalentes .cursor/, .kiro/, .gemini/, .vscode/ y .codex/). Ejecuta el propio `@aws/nx-plugin-mcp` del espacio de trabajo, por lo que el servidor siempre coincide con la versión instalada en tu espacio de trabajo
</FileTree>

La configuración del <Link path="get_started/building-with-ai">servidor MCP</Link> se puede deshabilitar con `--mcp=false`.

## Solución de problemas

#### `nx build <project>` ya no funciona para una biblioteca TypeScript existente

La primera ejecución de `ts#project` configura el plugin `@nx/js/typescript` para inferir el target de compilación TypeScript como `compile` (el plugin reserva `build` para orquestar `lint`, `compile` y `test`). Las bibliotecas existentes que dependen del target inferido `build` también se infieren como `compile` — ejecuta `nx run <project>:compile`, o usa `nx run-many --target build,compile`. Las bibliotecas con un target `build` explícito en su `project.json` no se ven afectadas.

#### `The workspace is out of sync`

Las referencias de proyecto TypeScript necesitan sincronización. `init` registra los generadores de sincronización; ejecuta:

<NxCommands commands={['sync']} />

#### `ERR_PNPM_IGNORED_BUILDS` durante la instalación

pnpm omite scripts de instalación para paquetes que no están en la lista de permitidos. `init` agrega a la lista de permitidos los que las herramientas del plugin necesitan (`@swc/core`, `esbuild`, `nx`, `sharp`) en `pnpm-workspace.yaml`, pero el bloqueo puede activarse durante `nx add @aws/nx-plugin` mismo — antes de que `init` se haya ejecutado. Ejecuta `pnpm approve-builds` y aprueba los paquetes listados (o agrégalos bajo `allowBuilds:`), luego vuelve a ejecutar la instalación.

#### `nx sync` se cuelga, o `plugin worker ... exited before the connection was established`

Si dos versiones diferentes de `nx` están presentes en el mismo árbol node_modules (ejecuta `npm ls nx` para confirmar), su IPC de plugin-worker entra en deadlock. El generador `init` fija la devDependency `nx` raíz a la versión que resuelven los propios paquetes `@nx/*` del plugin, pero una instalación posterior de otro paquete `@nx/*` en una versión de parche diferente puede reintroducir la discrepancia. Alinea cada entrada `nx` y `@nx/*` en tu `package.json` raíz a una sola versión y reinstala.

#### `ts.readConfigFile is not a function`

Tu espacio de trabajo tiene TypeScript 7 instalado, que [Nx aún no soporta](https://nx.dev/docs/technologies/typescript/guides/typescript-7) — los plugins de Nx dependen de la API de compilador en proceso de TypeScript, que TypeScript 7 ya no proporciona. Fija `typescript` en tu `package.json` raíz a la versión que usa el plugin (el generador `init` instala una versión compatible) y reinstala.

#### `Recursive task invocation detected`

Tu `package.json` **raíz** está registrado como un proyecto Nx (tiene una clave `"nx"`, que `nx init` agrega para un repositorio de un solo paquete) *y* lleva un script `build` de `nx run-many --target build`. Nx entonces infiere un target `build` en la raíz que se llama a sí mismo. Mueve tu código fuente a `packages/<tu-paquete>/` para que la raíz se convierta en un manifiesto del espacio de trabajo en lugar de un proyecto — consulta [Proyectos de un solo paquete](#proyectos-de-un-solo-paquete). (Los propios presets independientes de Nx evitan esto estableciendo `"nx": { "includedScripts": [] }` en el paquete raíz; puedes hacer lo mismo como una alternativa más rápida.)

#### Errores de TypeScript en tus proyectos **existentes** después de agregar el plugin (`TS6059`, `TS7016`, `TS5011`, `NG4006`)

Los propios proyectos generados del plugin llevan las configuraciones TypeScript que necesitan en su `tsconfig.lib.json` por proyecto, por lo que se compilan independientemente de tu `tsconfig.base.json`. Estos errores aparecen en cambio en un **proyecto preexistente tuyo** que hereda un `tsconfig.base.json` que `init` creó (con `composite`/`emitDeclarationOnly`/`nodenext`) pero no es compatible con esas configuraciones — por ejemplo, el compilador Angular rechaza `emitDeclarationOnly` (`NG4006`), o un proyecto que establece `outDir` sin un `rootDir` ahora necesita uno (`TS5011`). Agrega sobrescrituras de `tsconfig` por proyecto redeclarando las opciones conflictivas para esos proyectos (por ejemplo `"rootDir": "src"`), o apunta los proyectos del plugin y tus proyectos a configuraciones base separadas.

`init` nunca reescribe un `tsconfig.base.json` existente, precisamente para que no pueda romper silenciosamente los proyectos que heredan de él — resolver estas discrepancias es una decisión que solo tú puedes tomar para tu código base.

<Aside type="note" title="ESM y CommonJS">
El formato de módulo es a nivel de espacio de trabajo, leído del campo `type` del `package.json` raíz: `type: "module"` significa ESM, cualquier otra cosa (incluyendo ningún campo `type`) significa CommonJS. `init` preserva el que use tu espacio de trabajo, y los generadores TypeScript del plugin emiten código coincidente. Si más tarde quieres cambiar, cambia el `type` raíz — pero esa es una migración de tu código existente, no algo que `init` haga por ti.
</Aside>
