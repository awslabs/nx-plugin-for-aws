export const setupScriptUrl = `${import.meta.env.SITE}${import.meta.env.BASE_URL.replace(/\/$/, '')}/greengrass/setup-tutorial.sh`;

El script de configuración crea la identidad AWS IoT para un dispositivo central, lanza una instancia EC2 Ubuntu 26.04 x86_64 e instala el núcleo Greengrass clásico en ella a través de AWS Systems Manager. Registra lo que creó en `.greengrass-tutorial.env`, vinculado a tu cuenta, Región y prefijo, para que su operación `cleanup` elimine exactamente esos recursos más adelante.

| Recurso | Nombre | Creado por |
| --- | --- | --- |
| Grupo de cosas IoT | `<prefix>-group` | Script |
| Cosa IoT | `<prefix>-core` | Script |
| Rol de intercambio de tokens y su política de acceso | `<prefix>-token-exchange`, `<prefix>-token-exchangeAccess` | Script |
| Alias de rol IoT | `<prefix>-alias` | Script |
| Política IoT del dispositivo | `<prefix>-device-policy` | Script |
| Instancia EC2 | Etiquetada `Name=<prefix>-core` | Script |
| Certificado del dispositivo y clave privada | Generados en la instancia | Instalador del núcleo |
| Política IoT para el alias de rol | `GreengrassTESCertificatePolicy<prefix>-alias` | Instalador del núcleo |

El instalador se ejecuta en la instancia con las credenciales temporales del perfil de instancia. La clave privada del dispositivo se crea en la instancia y permanece bajo `/greengrass/v2`. El comando remoto que el script envía a través de Systems Manager contiene solo nombres de recursos, por lo que ninguna clave o credencial entra en el historial de comandos de Systems Manager.

## Tarea 1: Crear el perfil de instancia

El script no crea el perfil de instancia. Tú lo posees, por lo que controlas lo que el instalador puede hacer. Su rol necesita `AmazonSSMManagedInstanceCore`, para que Systems Manager pueda ejecutar el comando de instalación, más una política temporal para la ruta `--provision true` del instalador.

```bash
export TUTORIAL_ACCOUNT_ID=$(aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" \
  sts get-caller-identity --query Account --output text)

cat > /tmp/greengrass-tutorial-ec2-trust.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Principal": { "Service": "ec2.amazonaws.com" }, "Action": "sts:AssumeRole" }
  ]
}
EOF

aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam create-role \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --assume-role-policy-document file:///tmp/greengrass-tutorial-ec2-trust.json
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam attach-role-policy \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore
```

La política temporal del instalador sigue la [política IAM mínima para el instalador](https://docs.aws.amazon.com/greengrass/v2/developerguide/provision-minimal-iam-policy.html). La declaración `CreateIoTResources` es la oficial. La declaración IAM es más estrecha que la declaración oficial `CreateTokenExchangeRole`: el script crea el rol de intercambio de tokens y su política `<role>Access` antes de que se ejecute el instalador, por lo que el instalador solo las lee y nunca necesita `iam:CreateRole`, `iam:CreatePolicy` o `iam:AttachRolePolicy`.

```bash
cat > /tmp/greengrass-tutorial-installer.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReuseTokenExchangeRole",
      "Effect": "Allow",
      "Action": ["iam:GetRole", "iam:PassRole", "iam:GetPolicy"],
      "Resource": [
        "arn:aws:iam::${TUTORIAL_ACCOUNT_ID}:role/${TUTORIAL_PREFIX}-token-exchange",
        "arn:aws:iam::${TUTORIAL_ACCOUNT_ID}:policy/${TUTORIAL_PREFIX}-token-exchangeAccess",
        "arn:aws:iam::aws:policy/${TUTORIAL_PREFIX}-token-exchangeAccess"
      ]
    },
    {
      "Sid": "CreateIoTResources",
      "Effect": "Allow",
      "Action": [
        "iot:AddThingToThingGroup",
        "iot:AttachPolicy",
        "iot:AttachThingPrincipal",
        "iot:CreateKeysAndCertificate",
        "iot:CreatePolicy",
        "iot:CreateRoleAlias",
        "iot:CreateThing",
        "iot:CreateThingGroup",
        "iot:DescribeEndpoint",
        "iot:DescribeRoleAlias",
        "iot:DescribeThingGroup",
        "iot:GetPolicy"
      ],
      "Resource": "*"
    }
  ]
}
EOF

aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam put-role-policy \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --policy-name greengrass-installer-bootstrap \
  --policy-document file:///tmp/greengrass-tutorial-installer.json
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam create-instance-profile \
  --instance-profile-name "${TUTORIAL_PREFIX}-instance"
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam add-role-to-instance-profile \
  --instance-profile-name "${TUTORIAL_PREFIX}-instance" \
  --role-name "${TUTORIAL_PREFIX}-instance"
```

La Tarea 4 elimina `greengrass-installer-bootstrap` nuevamente una vez que el dispositivo está aprovisionado.

## Tarea 2: Seleccionar la imagen Ubuntu 26.04 x86_64

Canonical publica sus IDs de imagen actuales como parámetros públicos de Systems Manager. Lee el de Ubuntu 26.04 en amd64, luego confirma el propietario, la arquitectura y el nombre antes de usarlo:

```bash
export TUTORIAL_AMI_ID=$(aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ssm get-parameter \
  --name /aws/service/canonical/ubuntu/server/26.04/stable/current/amd64/hvm/ebs-gp3/ami-id \
  --query Parameter.Value --output text)

aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ec2 describe-images \
  --image-ids "$TUTORIAL_AMI_ID" \
  --query 'Images[0].[OwnerId,Architecture,Name]' --output text
```

La salida debe mostrar el propietario `099720109477` (Canonical), arquitectura `x86_64` y un nombre que contenga `ubuntu-resolute-26.04-amd64-server`. El script verifica los mismos tres valores y rechaza cualquier otra imagen.

Ubuntu 26.04 se usa por dos razones. Incluye `python3.14`, que es el intérprete que fija el paso `Run` de la receta generada. También incluye `sudo-rs` como el `sudo` predeterminado, que puede evitar que los componentes IPC se inicien bajo Nucleus 2.18.3 porque se pierde el entorno IPC. El script instala `openjdk-21-jre-headless`, `unzip`, `python3.14` y el paquete `sudo` clásico, que proporciona `/usr/bin/sudo.ws`, luego selecciona `/usr/bin/sudo.ws` como `sudo` y verifica la selección antes de instalar el núcleo. En la imagen Canonical, tanto `sudo` como `sudo-rs` están preinstalados, por lo que el cambio de alternativas es el paso efectivo. Consulta las <Link path="guides/greengrass-component#solución-de-problemas-y-límites-de-servicio">notas de solución de problemas del componente</Link>.

## Tarea 3: Descargar y ejecutar el script de configuración

Descarga el script desde este sitio de documentación, léelo y luego ejecútalo desde la raíz del espacio de trabajo:

<Code lang="bash" code={`curl -fsSLo setup-greengrass-tutorial.sh ${setupScriptUrl}\nchmod +x setup-greengrass-tutorial.sh\nless setup-greengrass-tutorial.sh`} />

El mismo archivo está registrado en el repositorio en `docs/public/greengrass/setup-tutorial.sh`.

```bash
./setup-greengrass-tutorial.sh setup \
  --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" --prefix "$TUTORIAL_PREFIX" \
  --ami-id "$TUTORIAL_AMI_ID" --instance-profile "${TUTORIAL_PREFIX}-instance"
```

Pasa `--subnet-id <subnet-id>` cuando la Región no tenga VPC predeterminada. Pasa `--instance-type` para cambiar el `t3.small` predeterminado.

El script realiza estos pasos en orden y escribe el archivo de estado después de cada recurso creado:

1. Resuelve la identidad del llamador, valida la imagen y verifica que el perfil de instancia exista.
2. Verifica que ninguno de los recursos en la tabla anterior exista todavía. Un grupo de cosas, cosa, rol, política o alias de rol existente bajo el prefijo detiene el script antes de que cree algo.
3. Crea el grupo de cosas y la cosa, el rol de intercambio de tokens con su política de acceso, el alias de rol y la política IoT del dispositivo. La política IoT es la [política mínima del dispositivo central](https://docs.aws.amazon.com/greengrass/v2/developerguide/device-auth.html#greengrass-core-minimal-iot-policy) de la guía del desarrollador, más `iot:Publish` en `arn:aws:iot:<region>:<account-id>:topic/tutorial/greengrass/heartbeat`.
4. Lanza la instancia con el perfil de instancia e IMDSv2 requerido, espera a que se registre con Systems Manager y envía un comando `AWS-RunShellScript` que instala los requisitos previos, cambia `sudo`, descarga `greengrass-nucleus-latest.zip` y ejecuta el instalador con `--provision true --setup-system-service true`, los nombres de cosa, grupo, política, rol y alias anteriores, y `--component-default-user ggc_user:ggc_group`.
5. Sondea el comando hasta que finaliza, luego registra el certificado que el instalador adjuntó a la cosa y espera a que el dispositivo central aparezca en Greengrass.

La configuración tarda unos diez minutos. Cuando termine, carga los valores registrados en tu shell y mantén el archivo de estado fuera de Git:

```bash
source .greengrass-tutorial.env
echo .greengrass-tutorial.env >> .gitignore
```

El archivo de estado exporta `TUTORIAL_THING_NAME`, `TUTORIAL_THING_GROUP_ARN`, `TUTORIAL_TOKEN_EXCHANGE_ROLE_ARN`, `TUTORIAL_INSTANCE_ID`, `TUTORIAL_CERTIFICATE_ARN` y la identidad a la que está vinculado. El Módulo 3 pasa dos de ellos al stack de CDK.

<Aside type="note" title="Reejecuciones y fallos">
Ejecutar `setup` nuevamente después de una ejecución exitosa informa la instancia existente y no cambia nada. Si una ejecución se detiene a mitad de camino, por ejemplo porque el comando de instalación falla, el archivo de estado registra hasta dónde llegó y una reejecución se niega a continuar. Ejecuta `cleanup` con el mismo perfil, Región y prefijo, corrige la causa y luego ejecuta `setup` nuevamente. La limpieza solo toca los recursos que registra el archivo de estado, tolera objetos que ya no existen y se detiene ante cualquier otro error.
</Aside>

## Tarea 4: Eliminar los permisos temporales del instalador

El instalador ha terminado. Elimina la política de arranque para que la instancia mantenga solo el acceso a Systems Manager:

```bash
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" iam delete-role-policy \
  --role-name "${TUTORIAL_PREFIX}-instance" \
  --policy-name greengrass-installer-bootstrap
```

## Tarea 5: Verificar el dispositivo

El núcleo registra el dispositivo central en su primer inicio. Confírmalo desde la nube:

```bash
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" greengrassv2 get-core-device \
  --core-device-thing-name "$TUTORIAL_THING_NAME" \
  --query '{status: status, coreVersion: coreVersion, platform: platform, architecture: architecture}'
```

Espera `HEALTHY`, `linux` y `amd64`. Para leer un registro en la instancia, envía un comando de Systems Manager con un archivo de parámetros. La primera línea es un shebang, que `AWS-RunShellScript` respeta:

```bash
cat > /tmp/greengrass-tutorial-command.json <<'EOF'
{ "commands": ["#!/bin/bash", "tail -n 20 /greengrass/v2/logs/greengrass.log"] }
EOF

TUTORIAL_COMMAND_ID=$(aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ssm send-command \
  --instance-ids "$TUTORIAL_INSTANCE_ID" --document-name AWS-RunShellScript \
  --parameters file:///tmp/greengrass-tutorial-command.json \
  --query Command.CommandId --output text)
sleep 5
aws --profile "$TUTORIAL_AWS_PROFILE" --region "$TUTORIAL_AWS_REGION" ssm get-command-invocation \
  --command-id "$TUTORIAL_COMMAND_ID" --instance-id "$TUTORIAL_INSTANCE_ID" \
  --query StandardOutputContent --output text
```

El Módulo 3 usa el mismo patrón para leer el registro del propio componente.
