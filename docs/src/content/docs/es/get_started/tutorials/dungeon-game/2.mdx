## Tarea 1: Implementar la API del juego

Implementaremos las siguientes APIs en esta sección:

1. `saveGame` - crear o actualizar un juego.
2. `queryGames` - devolver una lista paginada de los juegos guardados del jugador que ha iniciado sesión.
3. `queryInventory` - devolver una lista paginada de elementos en el inventario de un jugador.
4. `queryActions` - devolver el historial de conversación para un juego dado.

:::note[Dónde vive cada pieza de estado]
- `games` e `inventory` están en **DynamoDB** (a través de ElectroDB) — las lambdas de la API del juego y el servidor MCP de inventario los leen/escriben.
- `actions` (transcripción del chat) está en **S3** — el `S3SessionManager` del Story Agent escribe un blob JSON por turno, y `queryActions` en la API del juego los lee de vuelta para que la UI pueda reproducir el historial al recargar la página. No hay un procedimiento `saveAction`; el agente es el único escritor.
:::

:::tip[Todo está limitado al jugador que ha iniciado sesión]
Ambos almacenes están indexados por el llamador, por lo que un jugador nunca puede ver las aventuras de otro:

- **Games** están particionados en DynamoDB por el `sub` de Cognito del usuario, por lo que `queryGames` consulta esa partición en lugar de escanear la tabla. Dos jugadores también pueden elegir el mismo nombre de héroe sin colisionar.
- **Conversations** están espaciadas por el agente, por lo que las claves se ven como `session_u-<sub>-<threadId>/…`.
- **Inventory** está indexado por la sesión del agente llamador más el nombre del jugador. El servidor MCP de inventario lee esa sesión del contexto de la solicitud en lugar de confiar en el `playerName` que el modelo pasa — un argumento del modelo no es un límite de confianza.

Ni el `userId` ni el espacio de nombres se toman del cuerpo de la solicitud — el sitio web podría mentir al respecto. `requireUserId` en `identity.ts` lee el llamador del contexto del autorizador IAM que el Cognito Identity Pool puebla (`requestContext.authorizer.iam.cognitoIdentity.amr`, que contiene una entrada `…:CognitoSignIn:<sub>`). Ese valor es producido por el intercambio de tokens del Identity Pool, por lo que es confiable en lugar de ser proporcionado por el navegador, y las solicitudes sin él son rechazadas. Consulta <Link path="guides/trpc">Implementing Custom Middleware</Link> para la versión reutilizable de esto como un plugin de tRPC.
:::

## Tarea 4: Probar la API del juego localmente

No es necesario desplegar en AWS para probar nuestra API — el objetivo `dev` ejecuta la API del juego contra [DynamoDB Local](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DynamoDBLocal.html). Debido a que conectamos la API del juego al proyecto `DungeonDb` en el Módulo 1, este objetivo también inicia DynamoDB Local automáticamente.

Primero, corrige cualquier problema de lint:

<PackageManagerShortCommand commands={["lint"]} />

Luego construye la base de código:

<PackageManagerShortCommand commands={["build"]} />

### Iniciar el servidor local

Inicia la API del juego localmente con el objetivo `dev`, que también arranca DynamoDB Local:

<NxCommands commands={["dev game-api"]} />

<Aside type="tip" title="Primera ejecución">
La primera ejecución descarga la imagen del contenedor de DynamoDB Local, lo que puede tomar un momento. Deja el servidor ejecutándose en esta terminal y abre una segunda terminal para los comandos `curl` a continuación.
</Aside>

### Probar la API

Una vez que tu servidor esté en funcionamiento, consulta la lista (vacía) de juegos:

```bash
curl -X GET 'http://localhost:2022/games.query?input=%7B%7D'
```

:::note[Codificación de URL]
El `%7B%7D` que pasamos para probar la API es un objeto JSON vacío codificado en URI (`{}`).
:::

Verás una lista vacía:

```json
{"result":{"data":{"items":[],"cursor":null}}}
```

Ahora guarda un juego:

```bash
curl -X POST 'http://localhost:2022/games.save' \
  -H 'Content-Type: application/json' \
  -d '{"playerName":"Alice","genre":"zombie"}'
```

El guardado devuelve el juego persistido (con la marca de tiempo `lastUpdated` que la entidad establece por ti):

```json
{"result":{"data":{"playerName":"Alice","genre":"zombie","lastUpdated":"..."}}}
```

Consulta nuevamente para confirmar que está persistido en DynamoDB Local:

```bash
curl -X GET 'http://localhost:2022/games.query?input=%7B%7D'
```

Esta respuesta ahora incluye el juego guardado:

```json
{"result":{"data":{"items":[{"playerName":"Alice","genre":"zombie","lastUpdated":"..."}],"cursor":null}}}
```

Puedes detener el servidor local (`Ctrl+C`) una vez que hayas terminado.

## Tarea 5: Probar el servidor MCP de inventario localmente

Podemos probar las herramientas del servidor MCP con el [MCP Inspector](https://github.com/modelcontextprotocol/inspector) usando el objetivo generado `mcp-server-inspect`:

<NxCommands commands={["mcp-server-inspect inventory"]} />

Esto sirve el servidor MCP localmente (arrancando DynamoDB Local también) y lanza el MCP Inspector en `http://localhost:6274` preconfigurado para conectarse a él. Haz clic en **Connect**, cambia a la pestaña **Tools**, haz clic en **List Tools**, y prueba `add-to-inventory` (por ejemplo, `playerName: Alice`, `itemName: Rusty Sword`, `emoji: ⚔️`) seguido de `list-inventory-items` para verlo persistido en DynamoDB Local. Detén el servidor (`Ctrl+C`) cuando hayas terminado.
