Genera un agente de IA en Python para construir agentes con herramientas, y opcionalmente despliégalo en [Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/). Elige el framework del agente con la opción `framework`: [Strands](https://strandsagents.com/) (el predeterminado) o [LangChain](https://docs.langchain.com/oss/python/langchain/overview) (construido sobre [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview)).

El generador expone tu agente a través de un `protocol` de servidor. Ambos frameworks soportan [HTTP](https://fastapi.tiangolo.com/) (el predeterminado), el protocolo [Agent-to-Agent (A2A)](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-a2a.html) para interoperabilidad con otros agentes compatibles con A2A, y el protocolo [AG-UI](https://docs.ag-ui.com/) para integración directa con frontend a través de [CopilotKit](https://docs.copilotkit.ai/).

## Trabajar con tu Agente

Puedes editar `agent.py` para agregar herramientas, configurar el modelo y personalizar el prompt del sistema. La API depende del framework que elegiste.

### Agregar Herramientas

Las herramientas son funciones que el agente de IA puede llamar para realizar acciones. Ambos frameworks usan un enfoque basado en decoradores para definir herramientas, derivan el nombre y descripción de la herramienta del nombre de la función y docstring, y generan el esquema de entrada a partir de tus anotaciones de tipo.

<Tabs syncKey="agent-framework">
<TabItem label="Strands" _filter={{ framework: 'strands' }}>
```python
from strands import Agent, tool

@tool
def calculate_sum(numbers: list[int]) -> int:
    """Calculate the sum of a list of numbers"""
    return sum(numbers)

@tool
def get_weather(city: str) -> str:
    """Get weather information for a city"""
    # Your weather API integration here
    return f"Weather in {city}: Sunny, 25°C"

# Add tools to your agent
agent = Agent(
    system_prompt="You are a helpful assistant with access to various tools.",
    tools=[calculate_sum, get_weather],
)
```
</TabItem>
<TabItem label="LangChain" _filter={{ framework: 'langchain' }}>
```python
from langchain.agents import create_agent
from langchain_aws import ChatBedrockConverse
from langchain_core.tools import tool

@tool
def calculate_sum(numbers: list[int]) -> int:
    """Calculate the sum of a list of numbers"""
    return sum(numbers)

@tool
def get_weather(city: str) -> str:
    """Get weather information for a city"""
    # Your weather API integration here
    return f"Weather in {city}: Sunny, 25°C"

# Add tools to your agent
agent = create_agent(
    model=ChatBedrockConverse(model=MODEL_ID, region_name=REGION),
    tools=[calculate_sum, get_weather],
    system_prompt="You are a helpful assistant with access to various tools.",
)
```
</TabItem>

### Configuración del Modelo

<Tabs syncKey="agent-framework">

bedrock_model = BedrockModel(
    model_id="anthropic.claude-sonnet-4-20250514-v1:0",
    region_name="us-west-2",
    temperature=0.3,

## Protocolo

El protocolo del servidor de tu agente determina cómo se comunica. Todas las opciones son servidas por [FastAPI](https://fastapi.tiangolo.com/) — el punto de entrada difiere:

- **HTTP** (predeterminado): Un servidor FastAPI estándar con un endpoint `/invocations` personalizado, CORS y streaming. Mejor para integraciones de cliente personalizadas.
- **A2A**: Un servidor [Agent-to-Agent](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-a2a.html) montado en una aplicación FastAPI (Strands usa el [Strands A2A Server](https://strandsagents.com/docs/user-guide/concepts/multi-agent/agent-to-agent); LangChain usa el [`a2a-sdk`](https://a2a-protocol.org/) agnóstico del framework). Mejor cuando tu agente necesita ser descubrible e invocable por otros agentes compatibles con A2A.
- **AG-UI**: El [protocolo AG-UI](https://docs.ag-ui.com/) sobre SSE (Strands usa `ag-ui-strands`; LangChain usa `ag-ui-langgraph`). Mejor para integración directa con frontend con [CopilotKit](https://docs.copilotkit.ai/) en un sitio web React.

El punto de entrada del servidor difiere según el framework (Strands produce un `Agent` gestionado por contexto, mientras que LangChain impulsa un grafo `create_agent` compilado), pero el contrato externo para cada protocolo es el mismo.

Todos los protocolos exponen `/ping` para el contrato de verificación de salud del runtime AgentCore. Los agentes A2A escuchan en el puerto `9000`; los agentes HTTP y AG-UI escuchan en el puerto `8080`. El Dockerfile y la infraestructura generados están configurados para ti.

## Servidor FastAPI (protocolo HTTP)

El servidor HTTP generado incluye:
- Configuración de aplicación FastAPI con middleware CORS
- Middleware de manejo de errores
- Generación de esquema OpenAPI
- Endpoint de verificación de salud (`/ping`)
- Endpoint de invocación del agente (`/invocations`)

### Personalizar Entradas y Salidas de Invocación con Pydantic

El endpoint de invocación del agente usa modelos [Pydantic](https://docs.pydantic.dev/) para definir y validar los esquemas de solicitud y respuesta. Puedes personalizar estos modelos en `main.py` para que coincidan con los requisitos de tu agente.

#### Definir Modelos de Entrada

El modelo `InvokeInput` predeterminado acepta un prompt.

```python
from pydantic import BaseModel

class InvokeInput(BaseModel):
    prompt: str
```

Puedes extender este modelo para incluir cualquier campo adicional que tu agente necesite.

El ID de sesión se extrae del encabezado HTTP `x-amzn-bedrock-agentcore-runtime-session-id`, consistente con el [contrato de sesión de Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-service-contract.html). Si el encabezado no se proporciona, se genera un UUID aleatorio como respaldo.

:::caution[Organización del Código]
Probablemente querrás abstraer parte o todo el ID de sesión del llamador si los usuarios van a invocar tu agente directamente. Por ejemplo, puedes usar el ID de usuario autenticado como parte del ID de sesión.

También vale la pena señalar que dependiendo de tu caso de uso, es posible que necesites implementar autorización para sesiones, por ejemplo, asegurando que los usuarios solo puedan acceder a sus propias sesiones y no a las de otros usuarios.
:::

#### Definir Modelos de Salida

Para respuestas de streaming, el generador proporciona `JsonStreamingResponse` que serializa automáticamente modelos Pydantic al formato JSON Lines (`application/jsonl`). Este formato es compatible con la especificación de streaming de OpenAPI 3.2 y funciona sin problemas con el cliente TypeScript generado.

Por defecto, el agente produce objetos `StreamChunk` que contienen el texto de respuesta del agente:

```python
class StreamChunk(BaseModel):
    content: str
```

Puedes personalizar el modelo `StreamChunk` para adaptarlo a tus necesidades:

```python
from pydantic import BaseModel

class StreamChunk(BaseModel):
    content: str
    timestamp: str
    token_count: int
```

:::note[Limitación de Streaming de FastAPI]
Ten en cuenta que dado que FastAPI actualmente no admite la generación de una especificación OpenAPI para respuestas de streaming, debemos establecer explícitamente el modelo de respuesta para cada operación de streaming, es decir:

```python
@app.post(
    "/invocations",
    response_class=JsonStreamingResponse,
    responses={200: JsonStreamingResponse.openapi_response(StreamChunk)},
)
async def invoke(input: InvokeInput) -> JsonStreamingResponse:
    return JsonStreamingResponse(handle_invoke(input))
```
:::

Hay una [solicitud de función abierta para soporte nativo en FastAPI](https://github.com/fastapi/fastapi/discussions/14362).
</OptionFilter>

## Servidor A2A (protocolo A2A)

El `main.py` generado monta un servidor A2A en una aplicación FastAPI padre que también expone `/ping`. Los agentes Strands usan el `A2AServer` de Strands; los agentes LangChain envuelven el grafo compilado en un `AgentExecutor` de [`a2a-sdk`](https://a2a-protocol.org/). Cuando se despliega en AgentCore, el punto de entrada resuelve el ARN público del runtime desde AppConfig y lo anuncia en la tarjeta del agente.

La mayoría de los usuarios no necesitarán modificar este archivo; edita `agent.py` para cambiar herramientas o el prompt del sistema. El servidor A2A completa la tarjeta del agente (`/.well-known/agent-card.json`) a partir del `name` y `description` del agente.
</OptionFilter>

<OptionFilter when={{ protocol: 'ag-ui' }} description="AG-UI / CopilotKit server details">
## Servidor AG-UI (protocolo AG-UI)

El `main.py` generado expone un único endpoint POST que transmite eventos [AG-UI](https://docs.ag-ui.com/) a través de Server-Sent Events (SSE), así como `/ping` para la verificación de salud del runtime AgentCore. El cableado depende del framework:

- **Strands**: envuelve tu `Agent` en un `ag_ui_strands.StrandsAgent`, construido dentro de un manejador `lifespan` de FastAPI (para que la construcción ocurra al inicio del contenedor/sesión en lugar de en el momento de la importación), y servido desde un bucle `/invocations` de FastAPI hecho a mano.
- **LangChain**: envuelve el grafo compilado en un `ag_ui_langgraph.LangGraphAgent`, construido de la misma manera dentro de `lifespan`, y servido desde un bucle `/invocations` de FastAPI hecho a mano.

La mayoría de los usuarios no necesitarán modificar este archivo — edita `agent.py` para cambiar herramientas o el prompt del sistema.

:::tip[Conectar a un sitio web React]
Los agentes AG-UI están diseñados para ser consumidos directamente por un frontend. Usa el <Link path="/guides/connection/react-agui">generador `connection`</Link> para conectar tu sitio web React al agente con un proveedor [CopilotKit](https://docs.copilotkit.ai/) y un cliente [AG-UI HttpAgent](https://docs.ag-ui.com/).
:::
</OptionFilter>

### Desarrollo Local

Esto usa `uv run` para ejecutar tu Agente usando el [Bedrock AgentCore Python SDK](https://github.com/aws/bedrock-agentcore-sdk-python).

### Chatear con tu Agente

El generador configura un target Nx `<your-agent-name>-chat` que te lleva a un chat interactivo de terminal con tu agente.

El target de chat se ejecuta de forma independiente. Por defecto se conecta a tu agente ejecutándose localmente, así que primero inicia el target `<your-agent-name>-dev` del agente (en una terminal separada):

<NxCommands commands={['agent-dev your-project']} />

Luego, en otra terminal, inicia el chat:

<NxCommands commands={['run your-project:agent-chat']} />

El generador emite un `scripts/<your-agent-name>/chat.ts` para cada protocolo. Se conecta al agente local por defecto, o a tu agente desplegado cuando se establece `RUNTIME_CONFIG_APP_ID` (consulta [Chatear con tu agente desplegado](#chatear-con-tu-agente-desplegado) a continuación).

Para agentes **HTTP**, el script de chat usa un cliente TypeScript con seguridad de tipos generado a partir de la especificación OpenAPI del agente. El generador también emite:

- `scripts/<your-agent-name>_openapi.py` — un pequeño script que exporta la especificación OpenAPI del agente
- Un target Nx `<your-agent-name>-openapi` que lo ejecuta
- Un target Nx `<your-agent-name>-generate-client` que produce un cliente TypeScript con seguridad de tipos bajo `scripts/<your-agent-name>/generated/`

Cuando personalices la forma de entrada del agente (por ejemplo, agregar nuevos campos a `InvokeInput`), actualiza `chat.ts` para pasar los nuevos campos al invocar el agente y el resto funciona automáticamente.

## Desplegar tu Agente en Bedrock AgentCore Runtime

<Snippet name="agent/bedrock-deployment" parentHeading="Desplegar tu Agente en Bedrock AgentCore Runtime" />

### Targets de Bundle y Docker

Para construir tu Agente para Bedrock AgentCore Runtime, se agrega un target `bundle` a tu proyecto, que:

- Exporta tus dependencias de Python a un archivo `requirements.txt` usando `uv export`
- Instala dependencias para la plataforma objetivo (`aarch64-manylinux_2_28`) usando `uv pip install`

También se agrega un target `docker` específico para tu Agente, que copia el `Dockerfile` y los artefactos empaquetados en un directorio de contexto docker. Esto coloca el `Dockerfile` junto con la salida construida, permitiendo que CDK construya la imagen Docker directamente usando `AgentRuntimeArtifact.fromAsset`.

### Observabilidad

Tu agente se configura automáticamente con observabilidad usando [AWS Distro for Open Telemetry](https://aws.amazon.com/otel/) (ADOT), configurando la auto-instrumentación en tu `Dockerfile`.

Puedes encontrar trazas en la Consola AWS de CloudWatch, seleccionando "GenAI Observability" en el menú. Ten en cuenta que para que las trazas se completen necesitarás habilitar [Transaction Search](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Transaction-Search.html).

Para más detalles, consulta la [documentación de AgentCore sobre observabilidad](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-configure.html).

### Gestión de Sesiones

La opción `session` se mapea a un concepto de persistencia subyacente diferente dependiendo del framework elegido: el concepto de [gestión de sesiones](https://strandsagents.com/docs/user-guide/concepts/agents/session-management/) de Strands para el framework `strands`, o el concepto de [checkpointer](https://docs.langchain.com/oss/python/langgraph/persistence) de LangGraph para el framework `langchain`.

<OptionFilter when={{ framework: 'strands' }} description="Strands session management (session.py)">
La opción `session` controla cómo tu agente persiste el estado de la conversación (historial de mensajes, estado de herramientas, etc.) entre invocaciones, usando el [SessionManager](https://strandsagents.com/docs/user-guide/concepts/agents/session-management/) del SDK de Strands:

- **`s3`** (predeterminado): La infraestructura CDK/Terraform aprovisiona un bucket S3 dedicado para datos de sesión, cifrado con una clave KMS dedicada y con todo el acceso público bloqueado; los registros de acceso al servidor se entregan a un grupo de registros de CloudWatch Logs a través de la misma clave. El rol IAM del agente recibe acceso de lectura/escritura/lista/eliminación al bucket y acceso de descifrado/generación-de-clave-de-datos a la clave, y el nombre del bucket se registra junto con el ARN del agente en la configuración del runtime de AppConfig.
- **`in-memory`**: No se aprovisiona ningún bucket. El estado de la conversación se mantiene en memoria solo durante la vida útil del proceso en ejecución y no sobrevive a reinicios o reducciones de escala.

Esto se implementa en el `session.py` generado, que exporta una función `get_session_manager()` que resuelve un `SessionManager` para la sesión actual.

El ID de sesión en sí proviene de la sesión de AgentCore Runtime (propagada a través del encabezado `x-amzn-bedrock-agentcore-runtime-session-id`) y está vinculado a un contexto basado en [`contextvars.ContextVar`](https://docs.python.org/3/library/contextvars.html) para que `get_current_session_id()` pueda resolverlo en cualquier lugar de la solicitud — incluyendo en cualquier cliente MCP o A2A descendente conectado a través del <Link path="/guides/connection">generador `connection`</Link>, por lo que toda la cadena de llamadas comparte una sesión consistente.

:::note[AG-UI: sesiones y threads]
El protocolo AG-UI tiene su propio identificador de conversación, `thread_id`, en el cuerpo de la solicitud. `ag-ui-strands` almacena en caché un agente Strands por `thread_id` y llama a `session_manager_provider` **una vez por thread** — la primera vez que se ve ese thread.

El `main.py` generado por lo tanto pasa `session_manager_provider=lambda input_data: get_session_manager(input_data.thread_id)`, vinculando el estado de la conversación a ese mismo thread id para que el proveedor y la caché del adaptador siempre estén de acuerdo.

`get_session_manager()` recurre al ID de sesión actual de AgentCore cuando se llama sin un argumento, que es como lo usan los protocolos HTTP y A2A.

El endpoint AG-UI vincula la sesión dos veces — una vez en el middleware, y nuevamente dentro del cuerpo de respuesta de streaming. Ambos son necesarios: el `BaseHTTPMiddleware` de Starlette sale de su contexto antes de que se consuma el cuerpo de `StreamingResponse`, por lo que la segunda vinculación es lo que mantiene la sesión visible para las llamadas MCP y A2A descendentes realizadas durante el streaming.
:::

:::caution[Aislamiento de sesiones]
El ID de sesión y el `thread_id` son ambos proporcionados por el llamador, por lo que ninguno puede por sí solo identificar de quién es la conversación. AgentCore Runtime autoriza invocaciones contra el ARN del recurso del runtime del agente en lugar de contra sesiones individuales, y valida el formato de un ID de sesión sin vincularlo a la identidad del llamador — [delimitar una sesión a un usuario es responsabilidad del agente](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-instances-security.html).

Con `auth=cognito`, la infraestructura generada establece `requestHeaderConfiguration.allowlistedHeaders: ['Authorization']`, por lo que el JWT del llamador — ya validado por el autorizador de AgentCore — llega a tu código de agente como un encabezado de solicitud ordinario. El punto de entrada del servidor lee su claim `sub` y lo vincula para la solicitud, y `session.py` construye la clave de almacenamiento a partir de él a través de `get_session_storage_key()`, produciendo `u-<sub>-<conversation_id>`.

Las solicitudes sin un claim utilizable se rechazan con un 401 en lugar de recurrir a un espacio de nombres sin delimitar. Bajo `nx dev` no hay autorizador frente al agente, por lo que las solicitudes no autenticadas recurren a un único usuario local en su lugar — ese respaldo está protegido por `LOCAL_DEV`, que solo los targets `-dev` establecen. La verificación de firma se omite al decodificar el claim, ya que AgentCore Runtime ya [validó el token durante la autorización entrante](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-oauth.html).

Con `auth=iam`, SigV4 identifica al principal llamador a AgentCore Runtime en lugar de a tu código de agente, por lo que el estado de la conversación se vincula solo al ID de sesión y `bedrock-agentcore:InvokeAgentRuntime` es el límite — concédelo a backends de confianza, o usa principales IAM por usuario para que IAM aplique la delimitación.

`get_session_storage_key()` también aplana los separadores de ruta, por lo que un ID de conversación no puede atravesar fuera de su espacio de nombres.
:::

#### Alternativa: restringir sesiones a su propietario

El uso de espacios de nombres vincula el almacenamiento por llamador, por lo que la conversación de un usuario nunca se devuelve a otro. El ID de sesión en sí sigue siendo lo que el cliente envió, lo cual importa en dos casos:

- Un ID de sesión selecciona la [microVM](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html) que sirve la solicitud, por lo que su sistema de archivos, `/tmp` y cachés en proceso son compartidos por cada solicitud que se resuelve a esa sesión. Dos llamadores que envían el mismo ID comparten esos incluso con claves de almacenamiento separadas.
- El uso de espacios de nombres particiona conversaciones; no decide qué sesiones se le permite reanudar a un usuario.

Si cualquiera de estos te importa, haz que tu aplicación sea dueña del ID de sesión en su lugar: emítelo desde una API, registra a quién pertenece y verifica esa propiedad en el agente.

**1. Crear sesiones a través de tu API**

Agrega un procedimiento que inicie una conversación. Genera el ID de sesión, resuelve el llamador desde su propio contexto de solicitud y almacena el par — por ejemplo en una tabla creada con el generador <Link path="guides/py-dynamodb">`py#dynamodb`</Link>:

| Atributo | Ejemplo | Notas |
| --- | --- | --- |
| `sessionId` | `a5f1…` | Clave de partición — el agente busca un propietario desde el ID de sesión que se le da |
| `userId` | `<sub>` | El llamador autenticado que posee la sesión |
| `createdAt`, `title` | … | Cualquier cosa que tu UI necesite para listar conversaciones |

Agrega un índice secundario en `userId` si también quieres listar las propias sesiones de un usuario.

Resuelve el llamador desde el contexto de solicitud verificado en lugar de desde un campo de entrada, para que no pueda ser proporcionado por el navegador. <Link path="guides/trpc">Implementar Middleware Personalizado</Link> muestra cómo para APIs autenticadas tanto con IAM como con Cognito, y la API en sí puede estar en cualquier lenguaje. Un segundo procedimiento que consulta el índice permite que la UI ofrezca a un usuario sus propias conversaciones sin ver las de nadie más.

**2. Validar propiedad en el agente**

El agente recibe el ID de sesión, y con `auth=cognito` el JWT del llamador. En `SessionIdMiddleware`, busca la sesión y compara `session["userId"]` contra `get_current_user_id()`, devolviendo un `403` cuando difieren en lugar de continuar al manejador.

La API decide quién posee una sesión; el agente lo hace cumplir. Verificar en ambos lugares significa que un ID de sesión que se filtra aún se rechaza en la siguiente invocación, y cualquier cliente futuro del agente hereda la misma regla.

:::caution
Genera un ID de sesión opaco y aleatorio y almacena el mapeo. Derivar uno de valores proporcionados por el usuario — un nombre de conversación, un correo electrónico — es predecible, por lo que un llamador puede llegar a una sesión que no se le dio.
:::

:::note[Desarrollo Local]
Al ejecutarse localmente (`LOCAL_DEV=true`, establecido automáticamente por el target `-dev`), los datos de sesión siempre se almacenan en disco bajo `tmp/agents/strands/<agent-name>` en la raíz del workspace, independientemente de la opción `session` configurada, por conveniencia.
:::
</OptionFilter>

<OptionFilter when={{ framework: 'langchain' }} description="LangChain session management (session.py)">
La opción `session` controla cómo el checkpointer de LangGraph de tu agente persiste el estado de la conversación:

- **`s3`** (predeterminado): El agente desplegado usa un `S3CheckpointSaver` con el bucket de sesión aprovisionado, almacenando checkpoints y escrituras pendientes bajo el prefijo `checkpoints/`. Esta clase vive en `s3_checkpoint_saver_langchain.py` en el proyecto compartido de conexión de agentes.
- **`dynamodb-s3`**: La infraestructura CDK/Terraform aprovisiona una tabla DynamoDB para checkpoints, configurada como se recomienda en la [documentación de AWS sobre el uso de DynamoDB como almacén de checkpoints para agentes LangGraph](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ddb-langgraph-checkpoint.html) (esquema unificado `PK`/`SK`, facturación `PAY_PER_REQUEST`, recuperación point-in-time, y un atributo `ttl`), más un bucket S3 para descargar checkpoints de más de 350KB. Ambos están cifrados con una clave KMS dedicada; los registros de acceso al servidor del bucket se entregan a un grupo de registros de CloudWatch Logs a través de la misma clave. El rol IAM del agente recibe acceso de lectura/escritura a la tabla y al bucket, y los nombres de la tabla/bucket se registran junto con el ARN del agente en la configuración del runtime de AppConfig.
- **`in-memory`**: No se aprovisiona ninguna tabla ni bucket. El estado de la conversación se mantiene en memoria solo durante la vida útil del proceso en ejecución y no sobrevive a reinicios o reducciones de escala.

Esto se implementa en el `session.py` generado, que exporta una función `get_checkpointer()` llamada desde `create_agent(..., checkpointer=get_checkpointer())` de `agent.py`.

A diferencia de Strands, el checkpointer no se resuelve por sesión. Se crea una vez, y LangGraph selecciona la conversación para leer y escribir usando el `thread_id` en la configuración pasada en el momento de la invocación. Qué valor termina como ese `thread_id` depende del protocolo:

- **HTTP**: `main.py` establece `{"configurable": {"thread_id": session_id}}`, por lo que el ID de sesión de AgentCore *es* el ID de thread de LangGraph.
- **AG-UI**: `ag-ui-langgraph` establece el `thread_id` desde el `thread_id` en el cuerpo de la solicitud, por lo que el estado de la conversación se vincula al thread de AG-UI. El ID de sesión aún está vinculado al contexto para llamadas MCP y A2A descendentes, pero **no** selecciona la conversación.

:::caution[Aislamiento de sesiones]
El identificador que selecciona la conversación almacenada es proporcionado por el llamador — el ID de sesión de AgentCore para HTTP, o el `thread_id` de AG-UI para AG-UI. Ninguno puede por sí solo identificar de quién es la conversación. AgentCore Runtime autoriza invocaciones contra el ARN del recurso del runtime del agente en lugar de contra sesiones individuales, y valida el formato de un ID de sesión sin vincularlo a la identidad del llamador — [delimitar una sesión a un usuario es responsabilidad del agente](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-instances-security.html).

Con `auth=cognito`, la infraestructura generada establece `requestHeaderConfiguration.allowlistedHeaders: ['Authorization']`, por lo que el JWT del llamador — ya validado por el autorizador de AgentCore — llega a tu código de agente como un encabezado de solicitud ordinario. Debido a que LangGraph selecciona la conversación desde la configuración en lugar de un proveedor de sesión, `main.py` delimita el `thread_id` de la configuración en sí con `get_session_storage_key(session_id, user_id)`.

Las solicitudes sin un claim `sub` utilizable se rechazan con un 401 en lugar de recurrir a un espacio de nombres sin delimitar. Bajo `nx dev` no hay autorizador frente al agente, por lo que las solicitudes no autenticadas recurren a un único usuario local en su lugar — ese respaldo está protegido por `LOCAL_DEV`, que solo los targets `-dev` establecen. La verificación de firma se omite al decodificar el claim, ya que AgentCore Runtime ya [validó el token durante la autorización entrante](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-oauth.html).

Con `auth=iam`, SigV4 identifica al principal llamador a AgentCore Runtime en lugar de a tu código de agente, por lo que las conversaciones se vinculan solo al identificador del llamador y `bedrock-agentcore:InvokeAgentRuntime` es el límite — concédelo a backends de confianza.
:::

:::note[Desarrollo Local]
Al ejecutarse localmente (`LOCAL_DEV=true`, establecido automáticamente por el target `-dev`), `get_checkpointer()` siempre devuelve un [`AsyncSqliteSaver`](https://reference.langchain.com/python/langgraph.checkpoint.sqlite/aio/AsyncSqliteSaver) respaldado por una base de datos SQLite local bajo `tmp/agents/langchain/<agent-name>` en la raíz del workspace, independientemente de la opción `session` configurada, por conveniencia.
:::
</OptionFilter>
</OptionFilter>

## Invocar tu Agente

<OptionFilter when={{ protocol: 'http' }} description="FastAPI HTTP invocation details">
### Invocar el Servidor Local

Para invocar un Agente ejecutándose localmente a través del target `<your-agent-name>-serve`, puedes enviar una simple solicitud POST a `/invocations` en el puerto en el que se está ejecutando tu agente local. Por ejemplo, con `curl`:

```bash
curl -N -X POST http://localhost:8081/invocations \
  -d '{"prompt": "what is 3 + 5?"}' \
  -H "Content-Type: application/json"
```

:::note[Bandera de Streaming de Curl]
El argumento `-N` dado a `curl` deshabilita el almacenamiento en búfer del flujo de salida, para que puedas ver la respuesta de streaming en tiempo real.
:::

```bash

  -d '{"prompt": "what is 3 + 5?"}' \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <access-token>"

Puedes obtener el token de acceso usando el comando `cognito-idp admin-initiate-auth` de AWS CLI, por ejemplo:

  --user-pool-id <user-pool-id> \
  --client-id <user-pool-client-id> \
  --auth-flow ADMIN_NO_SRP_AUTH \
  --auth-parameters USERNAME=<username>,PASSWORD=<password> \
  --region <region> \
  --query 'AuthenticationResult.AccessToken' \
  --output text
```
