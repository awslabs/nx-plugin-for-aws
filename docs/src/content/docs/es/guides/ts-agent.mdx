Genera un [Strands Agent](https://strandsagents.com/) en TypeScript para construir agentes de IA con herramientas, y opcionalmente despliégalo en [Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/). Por defecto, el generador utiliza [tRPC](https://trpc.io/) sobre WebSocket para aprovechar el [soporte de streaming bidireccional de AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-websocket.html) para comunicación en tiempo real con seguridad de tipos. Alternativamente, puedes elegir el protocolo [Agent-to-Agent (A2A)](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-a2a.html) para interoperabilidad con otros agentes compatibles con A2A, o el protocolo [AG-UI](https://docs.ag-ui.com/) para integración directa con el frontend a través de [CopilotKit](https://docs.copilotkit.ai/aws-strands).

## ¿Qué es Strands?

[Strands](https://strandsagents.com/docs/user-guide/quickstart/overview/) es un framework ligero para construir agentes de IA. Las características clave incluyen:

- **Ligero y personalizable**: Bucle de agente simple que no se interpone en tu camino
- **Listo para producción**: Observabilidad completa, trazabilidad y opciones de despliegue para escalar
- **Agnóstico de modelo y proveedor**: Soporta muchos modelos diferentes de varios proveedores
- **Herramientas impulsadas por la comunidad**: Conjunto poderoso de herramientas contribuidas por la comunidad
- **Soporte multi-agente**: Técnicas avanzadas como equipos de agentes y agentes autónomos
- **Modos de interacción flexibles**: Soporte conversacional, streaming y no-streaming

## Trabajar con tu Agent

### Protocolo

El protocolo del servidor de tu agente determina cómo se comunica. Puedes elegir entre:

- **HTTP** (predeterminado): Utiliza [tRPC](https://trpc.io/) sobre WebSocket para comunicación en tiempo real con seguridad de tipos. Mejor para integraciones de cliente personalizadas y control detallado sobre la API del agente.
- **A2A**: Utiliza el protocolo [Agent-to-Agent (A2A)](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-a2a.html) para comunicación estandarizada entre agentes. Mejor cuando tu agente necesita ser descubrible e invocable por otros agentes compatibles con A2A.
- **AG-UI**: Utiliza el [protocolo AG-UI](https://docs.ag-ui.com/) (SSE sobre POST) a través de [`@ag-ui/aws-strands`](https://www.npmjs.com/package/@ag-ui/aws-strands) para integración directa con el frontend con [CopilotKit](https://docs.copilotkit.ai/aws-strands). Mejor cuando deseas una interfaz de chat rica con streaming, visualización de llamadas a herramientas y gestión de estado.

El protocolo se establece en la infraestructura CDK/Terraform, y el código de la aplicación se genera en consecuencia.

<OptionFilter when={{ protocol: 'http' }} description="tRPC over WebSocket details">
### tRPC sobre WebSocket (protocolo HTTP)

El TypeScript Agent utiliza [tRPC](https://trpc.io/) sobre WebSocket, aprovechando el [soporte de streaming bidireccional de AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-websocket.html) para habilitar comunicación en tiempo real con seguridad de tipos entre clientes y tu agente.

Dado que tRPC soporta procedimientos Query, Mutation y Subscription sobre WebSocket, puedes definir cualquier número de procedimientos. Por defecto, se define un único procedimiento de suscripción llamado `invoke` en `router.ts`.

### Agregar herramientas

Las herramientas son funciones que el agente de IA puede llamar para realizar acciones. Puedes agregar nuevas herramientas en el archivo `agent.ts`:

```typescript
import { Agent, tool } from '@strands-agents/sdk';
import { z } from 'zod';

const letterCounter = tool({
  name: 'letter_counter',
  description: 'Count occurrences of a specific letter in a word',
  inputSchema: z.object({
    word: z.string().describe('The input word to search in'),
    letter: z.string().length(1).describe('The specific letter to count'),
  }),
  callback: (input) => {
    const { word, letter } = input;
    const count = word.toLowerCase().split(letter.toLowerCase()).length - 1;
    return `The letter '${letter}' appears ${count} time(s) in '${word}'`;
  },
});

// Add tools to your agent
export const getAgent = async () => {
  return new Agent({
    systemPrompt: 'You are a helpful assistant with access to various tools.',
    tools: [letterCounter],
  });
};
```

El framework Strands maneja automáticamente:
- Validación de entrada usando esquemas Zod
- Generación de esquema JSON para llamadas a herramientas
- Manejo de errores y formato de respuesta

### Configuración del modelo

Por defecto, los agentes Strands usan Claude 4 Sonnet, pero puedes cambiar fácilmente entre proveedores de modelos:

```typescript
import { Agent } from '@strands-agents/sdk';
import { BedrockModel } from '@strands-agents/sdk/models/bedrock';
import { OpenAIModel } from '@strands-agents/sdk/models/openai';

// Use Bedrock
const bedrockModel = new BedrockModel({
  modelId: 'anthropic.claude-sonnet-4-20250514-v1:0',
});
let agent = new Agent({ model: bedrockModel });
let response = await agent.invoke('What can you help me with?');

// Alternatively, use OpenAI by just switching model provider
const openaiModel = new OpenAIModel({
  apiKey: process.env.OPENAI_API_KEY,
  modelId: 'gpt-4o',
});
agent = new Agent({ model: openaiModel });
response = await agent.invoke('What can you help me with?');
```

Consulta la [documentación de Strands sobre proveedores de modelos](https://strandsagents.com/docs/user-guide/concepts/model-providers/) para más opciones de configuración.

### Gestión de sesiones

La opción `session` controla cómo tu agente persiste el estado de la conversación (historial de mensajes, estado de herramientas, etc.) entre invocaciones, usando el [SessionManager](https://strandsagents.com/docs/user-guide/concepts/agents/session-management/) del SDK de Strands:

- **`s3`** (predeterminado): La infraestructura CDK/Terraform aprovisiona un bucket S3 dedicado para datos de sesión, cifrado con una clave KMS dedicada y con todo el acceso público bloqueado; los registros de acceso al servidor se entregan a un grupo de registros de CloudWatch Logs a través de la misma clave. El rol IAM del agente recibe acceso de lectura/escritura/lista/eliminación al bucket y acceso de descifrado/generación-de-clave-de-datos a la clave, y el nombre del bucket se registra junto con el ARN del agente en la configuración del runtime de AppConfig.
- **`in-memory`**: No se aprovisiona ningún bucket. El estado de la conversación se mantiene en memoria solo durante la vida del proceso en ejecución y no sobrevive a reinicios o scale-in.

Esto se implementa en el `session.ts` generado, que exporta una función `getSessionManager()` que resuelve un `SessionManager` para la sesión actual.

El ID de sesión en sí proviene de la sesión del AgentCore Runtime (propagado a través del encabezado `x-amzn-bedrock-agentcore-runtime-session-id` para A2A/AG-UI, o el contexto de conexión WebSocket para HTTP/tRPC) y está vinculado a un contexto basado en [`AsyncLocalStorage`](https://nodejs.org/api/async_context.html#class-asynclocalstorage) para que `getCurrentSessionId()` pueda resolverlo en cualquier lugar de la solicitud — incluyendo en cualquier cliente MCP o A2A descendente conectado a través del <Link path="/guides/connection">generador `connection`</Link>, para que toda la cadena de llamadas comparta una sesión consistente.

:::note[AG-UI: sesiones e hilos]
El protocolo AG-UI tiene su propio identificador de conversación, `threadId`, en el cuerpo de la solicitud. `@ag-ui/aws-strands` almacena en caché un agente Strands por `threadId` y llama a `sessionManagerProvider` **una vez por hilo** — la primera vez que se ve ese hilo.

El `index.ts` generado por lo tanto pasa `sessionManagerProvider: (input) => getSessionManager(input.threadId)`, vinculando el estado de la conversación a ese mismo id de hilo para que el proveedor y la caché del adaptador siempre estén de acuerdo.

`getSessionManager()` recurre al ID de sesión actual de AgentCore cuando se llama sin un argumento, que es como lo usan los protocolos HTTP y A2A.
:::

:::caution[Aislamiento de sesiones]
El ID de sesión y `threadId` son ambos proporcionados por el llamador, por lo que ninguno puede por sí solo identificar de quién es la conversación. AgentCore Runtime autoriza invocaciones contra el ARN del recurso del runtime del agente en lugar de contra sesiones individuales, y valida el formato de un ID de sesión sin vincularlo a la identidad del llamador — [delimitar una sesión a un usuario es responsabilidad del agente](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-instances-security.html).

Con `auth=cognito`, la infraestructura generada establece `requestHeaderConfiguration.allowlistedHeaders: ['Authorization']`, por lo que el JWT del llamador — ya validado por el autorizador de AgentCore — llega a tu código de agente como un encabezado de solicitud ordinario. El punto de entrada del servidor lee su claim `sub` y lo vincula para la solicitud, y `session.ts` construye la clave de almacenamiento a partir de él a través de `getSessionStorageKey()`, produciendo `u-<sub>-<conversationId>`.

Las solicitudes sin un claim utilizable se rechazan con un 401 en lugar de recurrir a un espacio de nombres sin delimitar. Bajo `nx dev` no hay autorizador frente al agente, por lo que las solicitudes no autenticadas recurren a un único usuario local en su lugar — ese recurso está protegido por `LOCAL_DEV`, que solo los targets `-dev` establecen. La verificación de firma se omite al decodificar el claim, ya que AgentCore Runtime ya [validó el token durante la autorización entrante](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-oauth.html).

En la ruta AG-UI, el middleware también elimina el alias `thread_id` del protocolo después de plegarlo en `threadId`. El adaptador mapea `thread_id` a `threadId` con la primera clave ganando cuando analiza el cuerpo, por lo que dejar el alias en su lugar permitiría a un cliente contrabandear un id de hilo sin delimitar más allá de la reescritura — mantén ambos pasos juntos si personalizas esto.

Con `auth=iam`, SigV4 identifica al principal llamador a AgentCore Runtime en lugar de a tu código de agente, por lo que el estado de la conversación se vincula solo al ID de sesión y `bedrock-agentcore:InvokeAgentRuntime` es el límite — concédelo a backends confiables, o usa principales IAM por usuario para que IAM aplique la delimitación.

`getSessionStorageKey()` también aplana los separadores de ruta, por lo que un ID de conversación no puede atravesar fuera de su espacio de nombres.
:::

#### Alternativa: restringir sesiones a su propietario

El uso de espacios de nombres vincula el almacenamiento por llamador, por lo que la conversación de un usuario nunca se devuelve a otro. El ID de sesión en sí sigue siendo lo que el cliente envió, lo cual importa en dos casos:

- Un ID de sesión selecciona la [microVM](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html) que sirve la solicitud, por lo que su sistema de archivos, `/tmp` y cachés en proceso son compartidos por cada solicitud que se resuelve a esa sesión. Dos llamadores que envían el mismo ID comparten esos incluso con claves de almacenamiento separadas.
- El uso de espacios de nombres particiona conversaciones; no decide qué sesiones se le permite reanudar a un usuario.

Si cualquiera de estos te importa, haz que tu aplicación sea dueña del ID de sesión en su lugar: emítelo desde una API, registra a quién pertenece y verifica esa propiedad en el agente.

**1. Crear sesiones a través de tu API**

Agrega un procedimiento que inicie una conversación. Genera el ID de sesión, resuelve el llamador desde su propio contexto de solicitud y almacena el par — por ejemplo en una tabla creada con el generador <Link path="guides/ts-dynamodb">`ts#dynamodb`</Link>:

| Attribute | Example | Notes |
| --- | --- | --- |
| `sessionId` | `a5f1…` | Clave de partición — el agente busca un propietario desde el ID de sesión que se le da |
| `userId` | `<sub>` | El llamador autenticado que posee la sesión |
| `createdAt`, `title` | … | Cualquier cosa que tu UI necesite para listar conversaciones |

Agrega un índice secundario en `userId` si también quieres listar las propias sesiones de un usuario.

```ts
export const createSession = publicProcedure
  .output(z.object({ sessionId: z.string() }))
  .mutation(async ({ ctx }) => {
    const sessionId = randomUUID().replaceAll('-', '');
    await sessionEntity.put({ sessionId, userId: callerSub(ctx.event) }).go();
    return { sessionId };
  });
```

Resuelve el llamador desde el contexto de solicitud verificado en lugar de desde un campo de entrada, para que no pueda ser proporcionado por el navegador. <Link path="guides/trpc">Implementing Custom Middleware</Link> muestra cómo para APIs autenticadas tanto con IAM como con Cognito. Un segundo procedimiento que consulta el índice permite que la UI ofrezca a un usuario sus propias conversaciones sin ver las de nadie más.

**2. Validar la propiedad en el agente**

El agente recibe el ID de sesión, y con `auth=cognito` el JWT del llamador. Busca la sesión, compara su propietario contra el llamador y rechaza la solicitud si difieren:

```ts
const session = await getSession(sessionId);
if (session?.userId !== getCurrentUserId()) {
  res.status(403).json({ error: 'Session does not belong to the caller' });
  return;
}
```

La API decide quién posee una sesión; el agente lo hace cumplir. Verificar en ambos lugares significa que un ID de sesión que se filtra aún se rechaza en la siguiente invocación, y cualquier cliente futuro del agente hereda la misma regla.

:::caution
Genera un ID de sesión opaco y aleatorio y almacena el mapeo. Derivar uno de valores proporcionados por el usuario — un nombre de conversación, un correo electrónico — es predecible, por lo que un llamador puede llegar a una sesión que no se le dio.
:::

:::note[Desarrollo local]
Cuando se ejecuta localmente (`LOCAL_DEV=true`, establecido automáticamente por el target `-dev`), los datos de sesión siempre se almacenan en disco bajo `tmp/agents/strands/<agent-name>` en la raíz del workspace, independientemente de la opción `session` configurada, por conveniencia.
:::
</OptionFilter>

## Invocar tu Agent

La comunicación del agente se transmite a través de tRPC sobre WebSocket. Como tal, se recomienda usar la fábrica de cliente con seguridad de tipos generada en `client.ts`.

// scripts/test.ts
import { AgentClient } from '../packages/<project>/src/agent/client.js';

### Invocar el Agent desplegado

<Snippet name="agent/runtime-arn" parentHeading="Invocar el Agent desplegado" />

#### NodeJS

El archivo `client.ts` generado incluye una fábrica de cliente con seguridad de tipos que puede usarse para invocar tu agente desplegado.

:::caution[Autenticación de encabezado HTTP]
La fábrica de cliente usa encabezados HTTP en el handshake WebSocket para autenticar solicitudes a Bedrock AgentCore Runtime. Esto no es posible en un navegador, y por lo tanto este cliente no es adecuado para entornos de navegador. Consulta la sección "Navegador" a continuación para detalles sobre la invocación desde un navegador.
:::

<Tabs syncKey="auth">
<TabItem label="IAM" _filter={{ auth: 'iam' }}>
##### Autenticación IAM

Puedes invocar tu agente desplegado pasando su ARN al método de fábrica `withIamAuth`:

```typescript
import { AgentClient } from './agent/client.js';

const client = AgentClient.withIamAuth({
  agentRuntimeArn: 'arn:aws:bedrock-agentcore:us-west-2:123456789012:runtime/my-agent',
});

client.invoke.subscribe({ prompt: 'what is 1 plus 1?' }, {
  onData: (message) => console.log(message),
  onError: (error) => console.error(error),
  onComplete: () => console.log('Done'),
});
```

:::note[Credenciales AWS]
Esto usará la cadena de proveedores de credenciales AWS predeterminada para autenticar solicitudes, por lo que el entorno en el que se ejecuta lo anterior debe tener credenciales AWS configuradas, con acceso para invocar el runtime.
:::
</TabItem>

<TabItem label="Cognito" _filter={{ auth: 'cognito' }}>
##### Autenticación JWT / Cognito

Usa el método de fábrica `withJwtAuth` para autenticar con el token de acceso JWT / Cognito.

```typescript
const client = AgentClient.withJwtAuth({
  agentRuntimeArn: 'arn:aws:bedrock-agentcore:us-west-2:123456789012:runtime/my-agent',
  accessTokenProvider: async () => `<access-token>`,
});

client.invoke.subscribe({ prompt: 'what is 1 plus 1?' }, {
  onData: console.log,
});
```

El `accessTokenProvider` debe devolver el token usado para autenticar la solicitud. Puedes, por ejemplo, obtener un token dentro de este método para asegurar que se reutilicen credenciales frescas cuando tRPC reinicie una conexión WebSocket. Lo siguiente demuestra el uso del SDK de AWS para obtener el token de Cognito:

```typescript
import { CognitoIdentityProvider } from "@aws-sdk/client-cognito-identity-provider";

const cognito = new CognitoIdentityProvider();

const jwtClient = AgentClient.withJwtAuth({
  agentRuntimeArn: 'arn:aws:bedrock-agentcore:us-west-2:123456789012:runtime/my-agent',
  accessTokenProvider: async () => {
    const response = await cognito.adminInitiateAuth({
      UserPoolId: '<user-pool-id>',
      ClientId: '<user-pool-client-id>',
      AuthFlow: 'ADMIN_NO_SRP_AUTH',
      AuthParameters: {
        USERNAME: '<username>',
        PASSWORD: '<password>',
      },
    });
    return response.AuthenticationResult!.AccessToken!;
  },
});
```
