Este generador agrega un servicio HTTP en contenedor a un proyecto Python existente. Obtienes un pequeño servidor [FastAPI](https://fastapi.tiangolo.com/), ejecutado por el servidor web [uvicorn](https://www.uvicorn.org/), con una ruta `GET /health`, un Dockerfile y targets para ejecutar el servidor localmente, construir su imagen y escanear la imagen. También obtienes código CDK o Terraform que ejecuta la imagen en [Amazon Elastic Container Service (Amazon ECS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html), el servicio de AWS que ejecuta y escala contenedores.

El servicio se ejecuta en [AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), que ejecuta cada contenedor sin servidores que debas administrar. Se ejecuta en tu propia VPC (nube privada virtual, una red aislada en tu cuenta de AWS), detrás de un [Application Load Balancer](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html) (ALB) interno al que solo pueden acceder direcciones dentro de la VPC. Por defecto, una [Amazon API Gateway HTTP API](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api.html) recibe solicitudes de los llamadores y las pasa al ALB a través de un VPC link (la conexión privada de API Gateway a una VPC). Los llamadores obtienen un endpoint HTTPS autenticado, y el balanceador de carga nunca se expone a internet.

## Salida del Generador

El generador agrega los siguientes archivos a tu proyecto. La carpeta de origen se nombra según la opción `name` en snake_case (por ejemplo `my_service` para `--name=my-service`), o `service` si la omites:

<FileTree>
  - your-project/
    - your_module/
      - service/ (o el nombre que elegiste)
        - \_\_init\_\_.py Inicialización del paquete Python
        - main.py Aplicación FastAPI con `GET /health` y la ruta de ejemplo `GET /echo`, servida por uvicorn en `PORT`

Por ejemplo, los targets son `service-serve`, `service-docker` y `service-trivy` sin un nombre, y `orders-serve`, `orders-docker` y `orders-trivy` para `--name=orders`. ## Ejecutar Tu Servicio Localmente

El target `<name>-serve` ejecuta el servidor en tu máquina, sin un contenedor:

<NxCommands commands={['run your-project:service-serve']} />

El servidor escucha en el puerto de la variable de entorno `PORT`. El target `<name>-serve` lo establece en un puerto que el generador asigna, comenzando en 8081 y omitiendo puertos que otros proyectos en tu workspace ya usan. Dentro del contenedor, el servidor escucha en el puerto 8080.

Verifica que el servidor esté activo con su ruta de salud, que devuelve estado 200 y `{"status":"ok"}`:

```bash
curl http://localhost:<port>/health
```

El servidor también tiene una ruta de ejemplo que reemplazas con tus propias rutas. `GET /echo?message=<x>` devuelve `{"message":"<x>"}`. El parámetro `message` es obligatorio y puede tener como máximo 1024 caracteres. Una solicitud sin él, o con un valor más largo, obtiene estado 422.

## Construir y Escanear la Imagen

El target `<name>-docker` construye una imagen linux/arm64 de tu servicio. Primero ejecuta el target `bundle-arm`, que escribe tu código y sus dependencias linux/arm64 en `dist/<project root>/bundle-arm`. El target agregado `bundle` depende de `bundle-arm`. Luego, el target `<name>-docker` copia esa carpeta, el `Dockerfile` y el `.dockerignore` en `dist/<project root>/docker/<name>`, y construye la imagen con esa carpeta como contexto de construcción (los archivos que la construcción de la imagen puede leer). Usa el motor de contenedores con el que tu workspace está configurado, `docker` o [Finch](https://runfinch.com/). El target se ejecuta como parte del target agregado `docker`, que construye cada imagen en el proyecto.

<NxCommands commands={['run your-project:service-docker']} />

Solo el grupo de destino del balanceador de carga (la lista de tareas a las que el balanceador de carga envía solicitudes) verifica `GET /health`, para decidir si una tarea está lista para el tráfico. ECS ignora una instrucción `HEALTHCHECK` en el Dockerfile. Para más información sobre cómo se construyen y publican las imágenes, consulta <Link path="/guides/docker-bundling">Docker Bundling</Link>.

## Desplegar Tu Servicio

### Agregar el Servicio a Tu Infraestructura

El constructo y el módulo nunca crean una VPC. Tú creas o importas una en tu stack o módulo raíz y la pasas. Las tareas y el balanceador de carga se ejecutan en subredes privadas con egreso, que alcanzan los servicios de AWS a través de un NAT gateway (una puerta de enlace administrada que permite a las subredes privadas realizar conexiones salientes) o a través de VPC endpoints (conexiones privadas desde tu VPC a los servicios de AWS).

<Infrastructure>
<Fragment slot="cdk">
El constructo CDK se crea en `common/constructs` y se nombra según tu servicio. Ejemplo de uso con una nueva VPC:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyService } from '@my-scope/common-constructs';
import { Stack, StackProps } from 'aws-cdk-lib';
import { SubnetType, Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ApplicationStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    new MyService(this, 'MyService', {
      vpc,
      vpcSubnets: { subnetType: SubnetType.PRIVATE_WITH_EGRESS },
    });
  }
}
```

Para usar una VPC existente, búscala con `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` y pásala como `vpc`.
</Fragment>
<Fragment slot="terraform">
El módulo Terraform se crea en `common/terraform`. La imagen del servicio se publica en el repositorio de activos compartido, así que instancia el módulo `core/asset-ecr` una vez por despliegue y pasa sus salidas a cada módulo de servicio. También pasa las salidas del módulo compartido `runtime_config_appconfig`, que contienen la aplicación AWS AppConfig de la que el servicio lee su <Link path="/guides/runtime-config">configuración de runtime</Link>:

```hcl title="packages/infra/src/main.tf"
module "asset_ecr" {
  source = "../../common/terraform/src/core/asset-ecr"
}

module "my_service" {
  source = "../../common/terraform/src/app/services/my-service"

  vpc_id     = aws_vpc.main.id
  subnet_ids = aws_subnet.private[*].id

  asset_ecr_repository_url = module.asset_ecr.repository_url
  asset_ecr_repository_arn = module.asset_ecr.repository_arn

  appconfig_application_id  = module.runtime_config_appconfig.application_id
  appconfig_application_arn = module.runtime_config_appconfig.application_arn
}
```

### Límites de Solicitud

API Gateway deja de esperar a tu servicio después de 30 segundos y devuelve un error al llamador. No puedes aumentar este tiempo de espera de integración. La carga útil de solicitud más grande que la HTTP API acepta es de 10 MB, y tampoco puedes aumentar este límite. Ambos valores provienen de la página [Amazon API Gateway quotas for HTTP APIs](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-quotas.html).

Por lo tanto, las solicitudes que se ejecutan durante más de 30 segundos, y las respuestas que transmiten datos durante mucho tiempo, no funcionan a través de la HTTP API. Para esas, establece `ingress` en `private` y llama al balanceador de carga interno desde dentro de la VPC.
</OptionFilter>

### Ejecutar Sin un NAT Gateway

Cuando tus tareas se inician, ECS extrae la imagen y envía registros en su nombre. Tu código de servidor también puede llamar a servicios de AWS. En subredes privadas sin NAT gateway, cada una de estas llamadas necesita un VPC endpoint. Sin los endpoints correctos, las tareas fallan al iniciarse o se agotan al llamar a AWS.

Crea estos endpoints en la VPC, reemplazando `<region>` con tu región de AWS:

| Endpoint | Tipo | Qué lo usa |
| --- | --- | --- |
| `com.amazonaws.<region>.ecr.api` | Interface | ECS, para autenticarse con Amazon ECR y buscar la imagen |
| `com.amazonaws.<region>.ecr.dkr` | Interface | ECS, para extraer la imagen de Amazon ECR |
| `com.amazonaws.<region>.s3` | Gateway | ECS, para descargar capas de imagen, que Amazon ECR almacena en Amazon S3 |
| `com.amazonaws.<region>.logs` | Interface | La salida de registro del contenedor, enviada a Amazon CloudWatch Logs |
| `com.amazonaws.<region>.secretsmanager` | Interface | ECS, para leer los secretos que pasas al contenedor cuando se inicia una tarea |
| `com.amazonaws.<region>.appconfigdata` | Interface | Tu código, para leer la <Link path="/guides/runtime-config">configuración de runtime</Link> de AWS AppConfig |
| `com.amazonaws.<region>.sts` | Interface | Tu código, cuando solicita credenciales temporales de AWS STS (por ejemplo, para asumir otro rol) |

Los interface endpoints necesitan un grupo de seguridad que permita HTTPS (puerto 443) desde las tareas. Para detalles sobre los endpoints de Amazon ECR, consulta [Amazon ECR interface VPC endpoints](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html).

### Valores Predeterminados de Seguridad

La infraestructura generada aplica estas configuraciones por defecto:

- El balanceador de carga es interno. Ningún grupo de seguridad permite tráfico entrante desde `0.0.0.0/0` o `::/0`.
- Las tareas se ejecutan en subredes privadas y nunca obtienen una dirección IP pública.
- El balanceador de carga acepta tráfico solo desde el VPC link (`http-api`) o desde el rango de direcciones de la VPC (`private`). Las tareas aceptan tráfico solo desde el balanceador de carga, en el puerto del contenedor.
- Las tareas solo pueden enviar tráfico saliente en el puerto 443. Las conexiones a bases de datos agregan el puerto de la base de datos.
- El rol de tarea (el rol con el que se ejecuta tu código de servidor) solo puede leer la configuración de runtime de AWS AppConfig hasta que tú o una conexión otorguen más.
- El rol de ejecución (el rol que ECS usa para iniciar tu tarea) solo puede extraer la imagen del servicio, escribir en su grupo de registros y leer los secretos que enumeras.
- Los secretos llegan al contenedor solo como referencias a AWS Secrets Manager o AWS Systems Manager Parameter Store, nunca como valores de entorno planos.
- El contenedor tiene un sistema de archivos raíz de solo lectura y se ejecuta como uid 1000, un usuario no root. ECS Exec (acceso de shell a una tarea en ejecución) está desactivado.
- Un despliegue que falla sus verificaciones de salud se detiene y revierte a la versión anterior.
- La HTTP API escribe registros de acceso y limita las solicitudes. Se autentica con IAM a menos que elijas lo contrario.
- Los registros se conservan durante un año.

El código generado suprime estas verificaciones de [Checkov](https://www.checkov.io/) (Checkov escanea el código de infraestructura en busca de configuraciones inseguras), y establece la razón junto a cada supresión:

- `CKV_AWS_91` solicita registros de acceso del balanceador de carga. Los registros de acceso de la HTTP API, o los registros propios de tu servicio, registran las solicitudes en su lugar.
- `CKV_AWS_2` y `CKV_AWS_103` solicitan un listener HTTPS con TLS. El balanceador de carga escucha en HTTP plano porque es interno y solo los llamadores dentro de la VPC pueden alcanzarlo. Con `http-api`, TLS termina en API Gateway.

El módulo Terraform también omite `CKV2_AWS_20` y `CKV_AWS_378` por la misma razón del listener HTTP, y `CKV_AWS_150` porque la protección contra eliminación del balanceador de carga está desactivada para que el servicio pueda ser destruido.

### Llamar a Tu Servicio

La URL del servicio se escribe en la <Link path="/guides/runtime-config">configuración de runtime</Link> como `connection.services.<NameClassName>`, donde `<NameClassName>` es el nombre del servicio en PascalCase. Para `--name=orders` la clave es `Orders`. Sin un nombre, el nombre del servicio es `<project>-service`, así que para un proyecto llamado `my-project` la clave es `MyProjectService`. La carpeta de origen y el prefijo del target siguen siendo `service` en ese caso.

<Tabs syncKey="auth">
<TabItem label="IAM" _filter={{ ingress: 'http-api', auth: 'iam' }}>
Los llamadores firman cada solicitud con [AWS Signature Version 4 (SigV4)](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv.html) para el servicio `execute-api`, usando credenciales de AWS que pueden llamar a la API. API Gateway rechaza una solicitud sin una firma válida antes de que llegue a tu servicio.

<Infrastructure>
<Fragment slot="cdk">
Otorga permiso a un rol o función para llamar al servicio con `grantInvoke`:

```ts title="packages/infra/src/stacks/application-stack.ts"
const service = new MyService(this, 'MyService', { vpc });
service.grantInvoke(myFunction);
```
</Fragment>
<Fragment slot="terraform">
Otorga permiso a un rol para llamar al servicio con una política `execute-api:Invoke` en el ARN de ejecución de la API, que el módulo de tu servicio emite como `api_execution_arn`:

```hcl title="packages/infra/src/main.tf"
resource "aws_iam_role_policy" "invoke_my_service" {
  role = aws_iam_role.caller.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = ["execute-api:Invoke"]
      Resource = ["${module.my_service.api_execution_arn}/*"]
    }]
  })
}
```
</Fragment>
</Infrastructure>
</TabItem>
<TabItem label="Cognito" _filter={{ ingress: 'http-api', auth: 'cognito' }}>

<Infrastructure>
<Fragment slot="cdk">

```ts title="packages/infra/src/stacks/application-stack.ts"

  identity: { userPool, userPoolClient },

```

</Fragment>
</Infrastructure>
</TabItem>

### Configuración Avanzada

El servicio generado establece su nombre, `ingress` y `auth` por ti. Los ejemplos a continuación usan el constructo `EcsService` genérico y el módulo `ecs-service` directamente, para configuraciones que el servicio generado no pasa o para elegir `ingress` y `auth` por instancia.

En CDK, tu paquete `common-constructs` exporta `EcsService` junto al constructo de tu servicio, así que lo importas de la misma manera: `import { EcsService } from '@my-scope/common-constructs'`. El constructo generado extiende `EcsService` y pasa todas las demás props, por ejemplo `cluster`, `loadBalancer`, `environment`, `secrets` y `grantTaskRole`. Su prop opcional `image` reemplaza la imagen construida desde tu proyecto. No tiene prop `auth`. Un servicio Cognito toma `identity` en su lugar, y otros servicios siempre usan el `auth` con el que fueron generados.

En Terraform, el módulo de tu servicio te permite establecer solo algunas de las variables del módulo `ecs-service`: `vpc_id`, `subnet_ids`, `cluster_arn`, `environment`, `secrets`, `task_role_policy_statements` y `tags`, más `user_pool_id` y `user_pool_client_ids` para un servicio Cognito. Para establecer cualquier otra variable, edita el bloque `module "ecs_service"` en el módulo de tu servicio.

Para ejecutar una imagen que ya está construida, por ejemplo de un registro público, pasa su URI. Nada se construye localmente. Para una imagen en un repositorio privado de Amazon ECR, CDK otorga al rol de ejecución acceso de extracción en ese repositorio. Terraform otorga acceso de extracción solo cuando también pasas el ARN del repositorio como `image_repository_arn`.

#### Varios Servicios en Un Stack

Cada servicio crea su propio clúster ECS a menos que pases uno. Para ejecutar varios servicios en un clúster, pasa el mismo clúster a cada uno.

Cada servicio HTTP API crea su propio VPC link, incluso cuando los servicios comparten un clúster. API Gateway permite 10 VPC links por cuenta por región de forma predeterminada, y puedes solicitar un aumento.

<Infrastructure>
<Fragment slot="cdk">

```ts
const cluster = new Cluster(this, 'Cluster', { vpc });

new MyService(this, 'MyService', { vpc, cluster });
new MyOtherService(this, 'MyOtherService', { vpc, cluster });
```

</Fragment>
<Fragment slot="terraform">
Pasa el mismo `cluster_arn` a cada módulo `ecs-service`. La salida `cluster_arn` del primer servicio te da uno:

```hcl
cluster_arn = module.my_service.cluster_arn
```

</Fragment>
</Infrastructure>

#### Variables de Entorno y Secretos

Las configuraciones planas van en `environment`. Nunca pongas valores secretos allí, porque cualquiera que pueda leer la definición de tarea puede leerlos. Pasa los secretos como referencias en su lugar. El rol de ejecución solo puede leer los secretos que enumeras.

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'MyService', {
  // ...
  environment: { LOG_LEVEL: 'info' },
  secrets: { API_KEY: Secret.fromSecretsManager(apiKeySecret) },
});
```

</Fragment>
<Fragment slot="terraform">

```hcl
environment = { LOG_LEVEL = "info" }
secrets     = { API_KEY = aws_secretsmanager_secret.api_key.arn }
```

</Fragment>
</Infrastructure>

#### Dimensionamiento y Escalado

Cada tarea obtiene 256 unidades de CPU (un cuarto de una vCPU) y 512 MiB de memoria por defecto. El servicio inicia una tarea, y el autoescalado mantiene entre una y dos tareas en ejecución, agregando tareas cuando el uso promedio de CPU supera el 70%.

| Configuración | Prop CDK | Variable Terraform | Predeterminado |
| --- | --- | --- | --- |
| Unidades de CPU por tarea | `cpu` | `cpu` | 256 |
| Memoria por tarea (MiB) | `memoryLimitMiB` | `memory` | 512 |
| Tareas al inicio | `desiredCount` | `desired_count` | 1 |
| Mínimo de tareas | `minCapacity` | `min_capacity` | 1 |

#### Usuario del Contenedor

La definición de tarea ejecuta el contenedor como uid 1000, un usuario no root. El Dockerfile proporcionado coincide: crea un usuario `app` con uid y gid 1000 y establece `USER 1000:1000`. Para ejecutar como otro usuario, establece la prop `user` de CDK o la variable `container_user` de Terraform. Terraform rechaza `0` y `root`.

| Usuario con el que se ejecuta el contenedor | `user` | `container_user` | `'1000'` (CDK), `"1000:1000"` (Terraform) |

#### CORS y Limitación

Estas configuraciones se aplican solo con `ingress` establecido en `http-api`. CORS (intercambio de recursos de origen cruzado) decide qué sitios web pueden llamar a tu servicio desde un navegador. Por defecto, la HTTP API acepta solicitudes de navegador desde cualquier origen, con cualquier método, y con los encabezados `authorization`, `content-type`, `x-amz-content-sha256`, `x-amz-date` y `x-amz-security-token`. Los últimos tres son los encabezados que agrega una firma SigV4. La HTTP API también limita las solicitudes a una tasa constante de 10,000 por segundo, con ráfagas de hasta 5,000.

| Configuración | CDK | Variable Terraform | Predeterminado |
| --- | --- | --- | --- |
| Orígenes CORS permitidos | Método `restrictCorsTo(...origins)`, o prop `corsPreflight` | `cors_allow_origins` | cualquier origen (`["*"]`) |
| Otras configuraciones CORS | Prop `corsPreflight` | none | cualquier método, y los encabezados anteriores |
| Limitación | Prop `throttle` | none | `{ rateLimit: 10000, burstLimit: 5000 }` |

Una prop `corsPreflight` reemplaza todo el valor predeterminado, así que enumera cada encabezado que tus llamadores envían. El método `restrictCorsTo` mantiene las otras configuraciones CORS y cambia solo los orígenes permitidos:

```ts
const service = new MyService(this, 'MyService', { vpc });
service.restrictCorsTo('https://app.example.com');
```

En Terraform, `cors_allow_origins` y `container_user` son variables del módulo `ecs-service`. El módulo de tu servicio no las pasa, así que establécelas en su bloque `module "ecs_service"`. Los valores de limitación están fijos en `ecs-service.tf`.

### Costo

Un container service factura mientras está inactivo, a diferencia de una función Lambda. Estas partes facturan por hora, independientemente de si alguien llama al servicio o no:

- Tareas Fargate, por vCPU y por GB de memoria. `desiredCount` y `minCapacity` mantienen al menos una tarea en ejecución.
- El Application Load Balancer, por hora y por unidad de capacidad del balanceador de carga.
- Interface VPC endpoints, por hora en cada zona de disponibilidad, o un NAT gateway, por hora y por GB de datos que procesa.
- Almacenamiento de registros en CloudWatch Logs, y almacenamiento de imágenes en Amazon ECR.

La HTTP API factura por solicitud. Para estimar el costo para tu región y tráfico, usa la [AWS Pricing Calculator](https://calculator.aws/).
