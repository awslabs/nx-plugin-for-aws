Este generador agrega un servicio HTTP en contenedor a un proyecto TypeScript existente. Obtienes un pequeño servidor HTTP con una ruta `GET /health` y una ruta de ejemplo `GET /hello`, un Dockerfile y targets para ejecutar el servidor localmente, construir su imagen y escanear la imagen. También obtienes código CDK o Terraform que ejecuta la imagen en [Amazon Elastic Container Service (Amazon ECS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html), el servicio de AWS que ejecuta y escala contenedores.

## Cómo Funciona Esto

El servicio se ejecuta en [AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), que ejecuta cada contenedor sin servidores que debas administrar. Cada copia en ejecución de tu contenedor es una tarea ECS. Las tareas se ejecutan en tu propia VPC (nube privada virtual, una red aislada en tu cuenta de AWS). Un grupo de seguridad (un conjunto de reglas de firewall adjuntas a las tareas) controla qué tráfico de red puede alcanzarlas y salir de ellas.

El servicio es privado. No tiene balanceador de carga, ni API ni dirección IP pública. Su grupo de seguridad no tiene regla de entrada, por lo que nada puede abrir una conexión al servicio hasta que permitas un llamador. El servicio aún puede realizar llamadas salientes, por ejemplo a una base de datos o a otros servicios de AWS.

## Ejecutar tu Servicio Localmente

El target `<name>-serve` ejecuta el servidor en tu máquina, sin un contenedor:

<NxCommands commands={['run your-project:service-serve']} />

El servidor escucha en el puerto de la variable de entorno `PORT`. El target `<name>-serve` lo establece en un puerto que el generador asigna, comenzando en 8081 y omitiendo puertos que otros proyectos en tu workspace ya usan. Dentro del contenedor, el servidor escucha en el puerto 8080.

El servidor escucha en la dirección de la variable de entorno `HOST`, que por defecto es `127.0.0.1`, por lo que el target `<name>-serve` acepta conexiones solo desde tu propia máquina. La imagen establece `HOST=0.0.0.0`, por lo que dentro de una tarea el servidor escucha en la interfaz de red propia de la tarea. El grupo de seguridad de la tarea aún decide quién puede conectarse.

Verifica que el servidor esté activo con su ruta de salud, que devuelve el estado 200 y `{"status":"ok"}`:

```bash
curl http://localhost:<port>/health
```

El servidor también tiene una ruta de ejemplo que reemplazas con tus propias rutas. `GET /hello?name=<x>` devuelve `{"message":"Hello, <x>!"}`, y `name` tiene como valor predeterminado `world`. Cualquier otra ruta devuelve el estado 404.

## Construir y Escanear la Imagen

El target `<name>-docker` construye una imagen linux/arm64 de tu servicio. Ejecuta primero el target `bundle`, por lo que la imagen contiene el servidor empaquetado. Luego copia el `Dockerfile` y `.dockerignore` en la carpeta de salida del bundle, `dist/<project root>/bundle/container/<name>`, y construye la imagen con esa carpeta como contexto de construcción (los archivos que la construcción de la imagen puede leer). Usa el motor de contenedores con el que tu workspace está configurado, `docker` o [Finch](https://runfinch.com/). El target se ejecuta como parte del target agregado `docker`, que construye cada imagen en el proyecto.

<NxCommands commands={['run your-project:service-docker']} />

En ECS, un comando de verificación de salud se ejecuta dentro del contenedor y llama a `GET /health` en el puerto del contenedor. No necesita acceso de entrada. ECS reemplaza una tarea cuya verificación de salud sigue fallando. ECS ignora una instrucción `HEALTHCHECK` en el Dockerfile. Para más información sobre cómo se construyen y publican las imágenes, consulta <Link path="/guides/docker-bundling">Docker Bundling</Link>.

## Desplegar tu Servicio

### Agregar el Servicio a tu Infraestructura

El constructo y el módulo nunca crean una VPC. Tú creas o importas una en tu stack o módulo raíz y la pasas. Las tareas se ejecutan en subredes privadas con salida, que alcanzan los servicios de AWS a través de una puerta de enlace NAT (una puerta de enlace administrada que permite a las subredes privadas realizar conexiones salientes) o a través de endpoints de VPC (conexiones privadas desde tu VPC a los servicios de AWS).

<Infrastructure>
<Fragment slot="cdk">
El constructo CDK se crea en `common/constructs` y se nombra según tu servicio. Ejemplo de uso con una nueva VPC:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyService } from '@my-scope/common-constructs';
import { Stack, StackProps } from 'aws-cdk-lib';
import { SubnetType, Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ApplicationStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    new MyService(this, 'MyService', {
      vpc,
      vpcSubnets: { subnetType: SubnetType.PRIVATE_WITH_EGRESS },
    });
  }
}
```

Para usar una VPC existente, búscala con `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` y pásala como `vpc`.
</Fragment>
<Fragment slot="terraform">
El módulo Terraform se crea en `common/terraform`. La imagen del servicio se publica en el repositorio de activos compartido, así que instancia el módulo `core/asset-ecr` una vez por despliegue y pasa sus salidas a cada módulo de servicio. También pasa las salidas del módulo compartido `runtime_config_appconfig`, que contienen la aplicación AWS AppConfig de la que el servicio lee su <Link path="/guides/runtime-config">configuración de runtime</Link>:

```hcl title="packages/infra/src/main.tf"
module "asset_ecr" {
  source = "../../common/terraform/src/core/asset-ecr"
}

module "my_service" {
  source = "../../common/terraform/src/app/services/my-service"

  vpc_id     = aws_vpc.main.id
  subnet_ids = aws_subnet.private[*].id

  asset_ecr_repository_url = module.asset_ecr.repository_url
  asset_ecr_repository_arn = module.asset_ecr.repository_arn

  appconfig_application_id  = module.runtime_config_appconfig.application_id
  appconfig_application_arn = module.runtime_config_appconfig.application_arn
}
```
</Fragment>
</Infrastructure>

### Ejecutar sin una Puerta de Enlace NAT

Cuando tus tareas se inician, ECS extrae la imagen y envía registros en su nombre. Tu código de servidor también puede llamar a servicios de AWS. En subredes privadas sin puerta de enlace NAT, cada una de estas llamadas necesita un endpoint de VPC. Sin los endpoints correctos, las tareas no se inician o se agotan cuando llaman a AWS.

Crea estos endpoints en la VPC, reemplazando `<region>` con tu región de AWS:

| Endpoint | Tipo | Qué lo usa |
| --- | --- | --- |
| `com.amazonaws.<region>.ecr.api` | Interface | ECS, para autenticarse con Amazon ECR y buscar la imagen |
| `com.amazonaws.<region>.ecr.dkr` | Interface | ECS, para extraer la imagen de Amazon ECR |
| `com.amazonaws.<region>.s3` | Gateway | ECS, para descargar capas de imagen, que Amazon ECR almacena en Amazon S3 |
| `com.amazonaws.<region>.logs` | Interface | La salida de registro del contenedor, enviada a Amazon CloudWatch Logs |
| `com.amazonaws.<region>.secretsmanager` | Interface | ECS, para leer los secretos que pasas al contenedor cuando se inicia una tarea |
| `com.amazonaws.<region>.appconfigdata` | Interface | Tu código, para leer la <Link path="/guides/runtime-config">configuración de runtime</Link> de AWS AppConfig |
| `com.amazonaws.<region>.sts` | Interface | Tu código, cuando solicita credenciales temporales de AWS STS (por ejemplo, para asumir otro rol) |

Los endpoints de interfaz necesitan un grupo de seguridad que permita HTTPS (puerto 443) desde las tareas. Para obtener detalles sobre los endpoints de Amazon ECR, consulta [Endpoints de VPC de interfaz de Amazon ECR](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html).

### Valores Predeterminados de Seguridad

La infraestructura generada aplica estas configuraciones de forma predeterminada:

- El grupo de seguridad del servicio no tiene regla de entrada. Ningún llamador dentro o fuera de la VPC puede conectarse a las tareas hasta que agregues una regla.
- Las tareas se ejecutan en subredes privadas y nunca obtienen una dirección IP pública.
- El generador no crea balanceador de carga ni API frente al servicio.
- Las tareas solo pueden enviar tráfico saliente en el puerto 443. Las conexiones a bases de datos agregan el puerto de la base de datos.
- El rol de tarea (el rol con el que se ejecuta tu código de servidor) solo puede leer la configuración de runtime de AWS AppConfig hasta que tú o una conexión otorguen más permisos.
- El rol de ejecución (el rol que ECS usa para iniciar tu tarea) solo puede extraer la imagen del servicio, escribir en su grupo de registros y leer los secretos que enumeras.
- Los secretos llegan al contenedor solo como referencias a AWS Secrets Manager o AWS Systems Manager Parameter Store, nunca como valores de entorno simples.
- El contenedor tiene un sistema de archivos raíz de solo lectura con una carpeta `/tmp` escribible, y se ejecuta como uid 1000, un usuario no root. ECS Exec (acceso de shell a una tarea en ejecución) está desactivado.
- Un despliegue que falla sus verificaciones de salud se detiene y revierte a la versión anterior.
- El grupo de registros está cifrado con una clave de AWS KMS, y los registros se conservan durante un año.

### Permitir que un Llamador Alcance tu Servicio

Nada puede llamar al servicio tal como se genera. Si otra carga de trabajo en la VPC necesita llamarlo, por ejemplo una función Lambda u otro servicio ECS, tú mismo agregas una regla de entrada al grupo de seguridad del servicio. El generador no agrega ninguna regla de entrada. Permite un llamador nombrado por su grupo de seguridad, en el puerto del contenedor, y nunca permitas un rango de direcciones.

<Infrastructure>
<Fragment slot="cdk">
El constructo implementa `IConnectable`, así que permite el grupo de seguridad del llamador a través de sus `connections`:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { Port } from 'aws-cdk-lib/aws-ec2';

const svc = new MyService(this, 'MyService', { vpc });
svc.connections.allowFrom(callerSecurityGroup, Port.tcp(8080));
```

Si el grupo de seguridad del llamador está definido en tu aplicación CDK y limita el tráfico saliente, `allowFrom` también agrega la regla saliente correspondiente a él.
</Fragment>
<Fragment slot="terraform">
Agrega una regla de entrada al grupo de seguridad del servicio, que el módulo de tu servicio emite como `security_group_id`, con el grupo de seguridad del llamador como fuente:

```hcl title="packages/infra/src/main.tf"
resource "aws_vpc_security_group_ingress_rule" "caller_to_my_service" {
  security_group_id            = module.my_service.security_group_id
  referenced_security_group_id = aws_security_group.caller.id
  from_port                    = 8080
  to_port                      = 8080
  ip_protocol                  = "tcp"
}
```

Si el grupo de seguridad del llamador limita el tráfico saliente, también agrega un `aws_vpc_security_group_egress_rule` en el grupo del llamador hacia el grupo de seguridad del servicio.
</Fragment>
</Infrastructure>

El llamador se conecta a la dirección IP privada de una tarea. El generador no configura descubrimiento de servicios, y la dirección de una tarea cambia cuando ECS reemplaza la tarea. Para dar a los llamadores un nombre estable, configura el descubrimiento de servicios tú mismo, por ejemplo con [Amazon ECS Service Connect](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect.html).

### Configuración Avanzada

El servicio generado establece su nombre e imagen por ti. Los ejemplos a continuación usan el constructo genérico `EcsService` y el módulo `ecs-service` directamente, para configuraciones que el servicio generado no pasa.

En CDK, tu paquete `common-constructs` exporta `EcsService` junto al constructo de tu servicio, por lo que lo importas de la misma manera: `import { EcsService } from '@my-scope/common-constructs'`. El constructo generado extiende `EcsService` y pasa todas las demás props, por ejemplo `cluster`, `environment`, `secrets` y `grantTaskRole`. Su prop opcional `image` reemplaza la imagen construida desde tu proyecto.

En Terraform, el módulo de tu servicio te permite establecer solo algunas de las variables del módulo `ecs-service`: `vpc_id`, `subnet_ids`, `cluster_arn`, `environment`, `secrets`, `task_role_policy_statements` y `tags`. Para establecer cualquier otra variable, edita el bloque `module "ecs_service"` en el módulo de tu servicio.

#### Imagen Preconstruida

Para ejecutar una imagen que ya está construida, por ejemplo de un registro público, pasa su URI. No se construye nada localmente. Para una imagen en un repositorio privado de Amazon ECR, CDK otorga al rol de ejecución acceso de extracción en ese repositorio. Terraform otorga acceso de extracción solo cuando también pasas el ARN del repositorio como `image_repository_arn`.


</Fragment>

#### Variables de Entorno y Secretos

Las configuraciones simples van en `environment`. Nunca pongas valores secretos allí, porque cualquiera que pueda leer la definición de tarea puede leerlos. Pasa los secretos como referencias en su lugar. El rol de ejecución solo puede leer los secretos que enumeras.

<Infrastructure>
<Fragment slot="cdk">

```ts
new EcsService(this, 'MyService', {
  // ...
  environment: { LOG_LEVEL: 'info' },
  secrets: { API_KEY: Secret.fromSecretsManager(apiKeySecret) },
});
```

</Fragment>
<Fragment slot="terraform">

```hcl
environment = { LOG_LEVEL = "info" }
secrets     = { API_KEY = aws_secretsmanager_secret.api_key.arn }
```

#### Dimensionamiento y Escalado

Cada tarea obtiene 256 unidades de CPU (un cuarto de una vCPU) y 512 MiB de memoria de forma predeterminada. El servicio inicia una tarea, y el autoescalado mantiene entre una y dos tareas en ejecución, agregando tareas cuando el uso promedio de CPU supera el 70%.

| Configuración | Prop CDK | Variable Terraform | Predeterminado |
| --- | --- | --- | --- |
| Unidades de CPU por tarea | `cpu` | `cpu` | 256 |
| Memoria por tarea (MiB) | `memoryLimitMiB` | `memory` | 512 |
| Tareas al inicio | `desiredCount` | `desired_count` | 1 |
| Mínimo de tareas | `minCapacity` | `min_capacity` | 1 |
| Máximo de tareas | `maxCapacity` | `max_capacity` | 2 |
| CPU promedio objetivo (%) | `targetCpuUtilizationPercent` | `target_cpu_utilization` | 70 |

#### Permisos del Rol de Tarea

El rol de tarea del constructo o módulo de tu servicio comienza con acceso de lectura solo a la configuración de runtime. Agrega los permisos que tu código necesita:

```ts
new EcsService(this, 'MyService', {

```

</Fragment>

```hcl

  Effect   = "Allow"
```

#### Usuario del Contenedor

La definición de tarea ejecuta el contenedor como uid 1000, un usuario no root. Esto coincide con el usuario `node` que establece el Dockerfile proporcionado. Para ejecutar como otro usuario, establece la prop `user` de CDK o la variable `container_user` de Terraform. Terraform rechaza `0` y `root`.

| Configuración | Prop CDK | Variable Terraform | Predeterminado |
| --- | --- | --- | --- |
| Usuario con el que se ejecuta el contenedor | `user` | `container_user` | `'1000'` (CDK), `"1000:1000"` (Terraform) |

En Terraform, `container_user` es una variable del módulo `ecs-service`. El módulo de tu servicio no la pasa, así que establécela en su bloque `module "ecs_service"`.

### Costo

Un servicio de contenedor factura mientras está inactivo, a diferencia de una función Lambda. Estas partes facturan por hora, independientemente de si alguien llama al servicio o no:

- Tareas Fargate, por vCPU y por GB de memoria. `desiredCount` y `minCapacity` mantienen al menos una tarea en ejecución.
- Endpoints de VPC de interfaz, por hora en cada zona de disponibilidad, o una puerta de enlace NAT, por hora y por GB de datos que procesa.
- Almacenamiento de registros en CloudWatch Logs y almacenamiento de imágenes en Amazon ECR.

Para estimar el costo para tu región y tráfico, usa la [Calculadora de Precios de AWS](https://calculator.aws/).

<Fragment slot="terraform">

Luego verifica en la consola de AWS o con la CLI de AWS que el servicio y clúster ECS se hayan eliminado. Con Terraform, destroy también elimina el grupo de registros del servicio y programa su clave de AWS KMS para eliminación después de 7 días. Con CDK, destroy mantiene el grupo de registros del servicio y su clave de AWS KMS, porque CDK mantiene los grupos de registros y las claves a menos que una política de eliminación indique lo contrario. Elimínalos tú mismo si ya no necesitas los registros. Las imágenes permanecen en Amazon ECR, en el repositorio de activos de CDK o el repositorio compartido `asset-ecr`. Elimínalas si ya no las necesitas. La VPC es tuya, por lo que destruir el servicio la deja en su lugar.
