[FastAPI](https://fastapi.tiangolo.com/) es un framework para construir APIs en Python.

El generador de FastAPI crea una nueva FastAPI con configuración de infraestructura AWS CDK o Terraform. El backend generado se expone a través de una API de AWS API Gateway. Configura [AWS Lambda Powertools](https://docs.powertools.aws.dev/lambda/python/latest/) para observabilidad, incluyendo logging estructurado y métricas de CloudWatch.

<OptionFilter not when={{ infra: 'http-ecs' }} description="Lambda hosting">
El backend utiliza AWS Lambda para despliegue serverless, y el trazado de AWS X-Ray también está configurado.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="ECS hosting">
Tu API se ejecuta como un servidor uvicorn de larga duración en un contenedor en Amazon ECS, detrás de una API Gateway HTTP API, en lugar de en una función Lambda. Consulta <a href="#ejecución-en-amazon-ecs">Ejecución en Amazon ECS</a> para ver qué cambia, incluyendo por qué el trazado de X-Ray no produce trazas allí.
</OptionFilter>

:::tip[Tipo de API]
Selecciona `rest-lambda` (predeterminado) como tu `infra` si tienes la intención de construir cualquier operación de streaming.
:::

:::tip[Patrón de Integración]
La opción `integrationPattern` tiene como valor predeterminado `isolated`, que crea un Lambda por operación de FastAPI. Selecciona `shared` si prefieres un único Lambda handler compartido para toda la API, con anulaciones opcionales por operación.

Con `infra` establecido en `http-ecs` la opción es siempre `shared`, ya que un servicio de contenedor responde a cada operación.
:::

<OptionFilter when={{ infra: 'http-ecs' }} description="ECS hosting is experimental">
:::caution[Experimental]
`http-ecs` es experimental. Su salida generada puede cambiar entre versiones sin una migración para llevar un espacio de trabajo existente, así que espera reconciliar esos cambios tú mismo cuando actualices.

Necesita el proveedor de IaC CDK: el soporte de Terraform aún no está implementado. Si el espacio de trabajo se resuelve a Terraform, el generador falla con un mensaje que indica la solución.

`integrationPattern` es siempre `shared` aquí. Pasar `--integrationPattern=isolated` junto con `http-ecs` no falla: el generador advierte que la opción se ignora y usa `shared`. Al ejecutar el generador de forma interactiva, pregunta por `integrationPattern` antes de `infra`, con `isolated` preseleccionado, por lo que esa advertencia es lo que ves si dejas la preselección y luego eliges `http-ecs`. En el constructor de comandos de esta página, elegir `http-ecs` desactiva `isolated` y lo borra si estaba seleccionado, por lo que el comando que escribe nunca lleva la bandera.

La opción `architecture` establece si el contenedor se ejecuta en `ARM64` o `X86_64`, y las wheels de Python en su bundle lo siguen. Omítela para usar la arquitectura de la máquina en la que ejecutas el generador. Consulta <Link path="/guides/py-container#cpu-architecture">CPU Architecture</Link> en la guía de contenedores.
:::
</OptionFilter>

## Salida del Generador

El generador creará la siguiente estructura de proyecto en el directorio `<directory>/<api-name>`:

<FileTree>

- project.json Configuración del proyecto y objetivos de construcción
- pyproject.toml Configuración del proyecto Python y dependencias
- run.sh Script de arranque de Lambda Web Adapter para iniciar la aplicación FastAPI a través de uvicorn
- \<module_name>
  - \_\_init\_\_.py Inicialización del módulo
  - init.py Configura la aplicación FastAPI y configura el middleware de powertools
  - main.py Implementación de la API
- scripts
  - generate_open_api.py Script para generar un esquema OpenAPI desde la aplicación FastAPI

</FileTree>

<OptionFilter when={{ infra: 'http-ecs' }} description="Files that differ when the API runs on ECS">
Con `infra` establecido en `http-ecs` la API se ejecuta como su propio servidor HTTP en lugar de detrás del Lambda Web Adapter, por lo que `run.sh` no se genera. En su lugar obtienes una carpeta de contenedor dentro de tu módulo, nombrada según tu API:

<FileTree>
- \<module_name>
  - \<api_name>_container
    - main.py Punto de entrada: agrega `GET /health`, escribe las métricas que recopila la API, e inicia uvicorn en `HOST` y `PORT`. El bundle, la imagen y el objetivo `serve` todos comienzan desde este archivo
    - Dockerfile Definición de imagen de contenedor
    - .dockerignore Archivos excluidos del contexto de construcción de la imagen
</FileTree>

Tu `init.py`, `main.py` y las operaciones que les agregues son las mismas para cada valor de `infra`.
</OptionFilter>

## Implementar tu FastAPI

La implementación principal de la API está en `main.py`. Aquí es donde defines tus rutas de API y sus implementaciones. Aquí hay un ejemplo:

```python
from pydantic import BaseModel
from .init import app, tracer

class Item(BaseModel):
  name: str

@app.get("/items/{item_id}")
@tracer.capture_method
def get_item(item_id: int) -> Item:
    return Item(name=f"Item {item_id}")

@app.post("/items")
@tracer.capture_method
def create_item(item: Item) -> Item:
    return item
```

El generador configura varias características automáticamente:

1. Integración de AWS Lambda Powertools para observabilidad
2. Middleware de manejo de errores
3. Correlación de solicitud/respuesta
4. Recopilación de métricas

<OptionFilter not when={{ infra: 'http-ecs' }} description="Streaming, which needs a REST API">
El streaming con seguridad de tipos también está configurado, solo para la infraestructura `rest-lambda`.
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="How the Lambda variants serve the app">
La aplicación se sirve en una función Lambda mediante el [Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter) ejecutando uvicorn.
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="How the ECS variant serves the app">
La aplicación se sirve mediante uvicorn en el contenedor, sin Lambda Web Adapter. Consulta <a href="#running-on-amazon-ecs">Ejecución en Amazon ECS</a>.
</OptionFilter>

### Observabilidad con AWS Lambda Powertools

#### Logging

El generador configura logging estructurado usando AWS Lambda Powertools. Puedes acceder al logger en tus manejadores de ruta:

```python
from .init import app, logger

@app.get("/items/{item_id}")
def read_item(item_id: int):
    logger.info("Fetching item", extra={"item_id": item_id})
    return {"item_id": item_id}
```

El logger incluye automáticamente:

- IDs de correlación para el rastreo de solicitudes
- Ruta de solicitud, ruta coincidente y método

#### Trazado

El trazado de AWS X-Ray se configura automáticamente. Puedes agregar subsegmentos personalizados a tus trazas:

```python
from .init import app, tracer

@app.get("/items/{item_id}")
@tracer.capture_method
def read_item(item_id: int):
    # Creates a new subsegment
    with tracer.provider.in_subsegment("fetch-item-details"):
        # Your logic here
        return {"item_id": item_id}
```

<OptionFilter when={{ infra: 'http-ecs' }} description="X-Ray produces no traces on ECS">
:::caution[Sin trazas en ECS]
El decorador y el subsegmento anterior se ejecutan sin error en un contenedor, pero no producen trazas. Powertools desactiva su tracer cuando no se está ejecutando en Lambda. Consulta <a href="#observability">Observabilidad</a> para ver qué obtienes y qué agregar si necesitas trazas.
:::
</OptionFilter>

#### Métricas

Las métricas de CloudWatch se recopilan automáticamente para cada solicitud. Puedes agregar métricas personalizadas:

```python
from .init import app, metrics
from aws_lambda_powertools.metrics import MetricUnit

@app.get("/items/{item_id}")
def read_item(item_id: int):
    metrics.add_metric(name="ItemViewed", unit=MetricUnit.Count, value=1)
    return {"item_id": item_id}
```

Las métricas predeterminadas incluyen:

- Conteos de solicitudes
- Conteos de éxito/fallo
- Métricas por ruta (a través de una dimensión `route` de `<method> <path>`)

### Manejo de Errores

El generador incluye manejo de errores integral:

```python
from fastapi import HTTPException

@app.get("/items/{item_id}")
def read_item(item_id: int):
    if item_id < 0:
        raise HTTPException(status_code=400, detail="Item ID must be positive")
    return {"item_id": item_id}
```

Las excepciones no manejadas son capturadas por el middleware y:

1. Registran la excepción completa con el stack trace
2. Registran una métrica de fallo
3. Devuelven una respuesta 500 segura al cliente
4. Preservan el ID de correlación

:::tip[Modelos de Respuesta]
Se recomienda especificar modelos de respuesta para tus operaciones de API para una mejor generación de código si usas el generador `connection`. <Link path="guides/connection/react-fastapi#errors">Consulta aquí para más detalles</Link>.
:::

### Acceder al Usuario que Llama

<OptionFilter when={{ infra: 'http-ecs' }} description="Identity on ECS — the authorizer context does not arrive">
En ECS no hay Lambda Web Adapter ni encabezado de contexto de solicitud de API Gateway: API Gateway no reenvía las claims del autorizador a una integración de balanceador de carga privado. El autorizador aún decide si una solicitud llega al contenedor en absoluto, pero tus manejadores no pueden leer el llamador de la solicitud como se escribe a continuación.

Para leer la identidad del llamador en una operación, mapea el contexto del autorizador a un encabezado de solicitud en tu constructo de API, y lee ese encabezado desde el `Request` de FastAPI.
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="Identity on the Lambda variants">
Cuando tu API está protegida por autenticación, tus manejadores de ruta a menudo necesitan saber quién está llamando. La FastAPI generada se ejecuta dentro de AWS Lambda a través del [Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter), que reenvía el contexto de solicitud de API Gateway como JSON en el encabezado `x-amzn-request-context`. Puedes leerlo desde el `Request` de FastAPI para extraer la identidad del llamador.

Como ejemplo, agreguemos un endpoint `/me` que devuelva detalles sobre el usuario que llama. Implementaremos la extracción como una [dependencia de FastAPI](https://fastapi.tiangolo.com/tutorial/dependencies/) para que pueda reutilizarse en todas las rutas. La forma del contexto de solicitud — y por lo tanto cómo extraes la identidad — depende tanto de tu método `auth` seleccionado como de si desplegaste una REST o HTTP API.
</OptionFilter>

<OptionFilter when={{ auth: 'iam' }} description="Extracción de identidad para APIs autenticadas con IAM">
Para autenticación `IAM`, buscamos al llamador en Cognito usando el sub extraído del contexto de solicitud de API Gateway, lo que requiere `boto3`. Agrégalo a tu proyecto de API:

<NxCommands commands={[`run my-api:add boto3${PY_VERSIONS.boto3}`]} />

Crea `identity.py` junto a `main.py`:

<Tabs syncKey="http-rest">
<TabItem label="REST API" _filter={{ infra: 'rest-lambda' }}>
```python
import json
import os
from typing import Annotated

from boto3 import client
from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel

cognito = client("cognito-idp")


class Identity(BaseModel):
    sub: str
    username: str


def get_identity(request: Request) -> Identity:
    # The Lambda Web Adapter forwards the API Gateway request context as JSON
    request_context_header = request.headers.get("x-amzn-request-context")
    if not request_context_header:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    request_context = json.loads(request_context_header)
    provider = request_context.get("identity", {}).get("cognitoAuthenticationProvider")

    sub = provider.split(":")[-1] if provider else None
    if not sub:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    users = cognito.list_users(
        # Assumes user pool id is configured in lambda environment
        UserPoolId=os.environ["USER_POOL_ID"],
        Limit=1,
        Filter=f'sub="{sub}"',
    ).get("Users", [])

    if len(users) != 1:
        raise HTTPException(status_code=403, detail=f"No user found with subjectId {sub}")

    return Identity(sub=sub, username=users[0]["Username"])


CurrentUser = Annotated[Identity, Depends(get_identity)]
```
</TabItem>

from typing import Annotated

from boto3 import client
from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel

cognito = client("cognito-idp")


class Identity(BaseModel):
    sub: str
    username: str


def get_identity(request: Request) -> Identity:
    # The Lambda Web Adapter forwards the API Gateway request context as JSON
    request_context_header = request.headers.get("x-amzn-request-context")
    if not request_context_header:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    request_context = json.loads(request_context_header)
    amr = (
        request_context.get("authorizer", {})
        .get("iam", {})
        .get("cognitoIdentity", {})
        .get("amr", [])
    )
    sign_in = next((s for s in amr if ":CognitoSignIn:" in s), None)
    sub = sign_in.split(":")[-1] if sign_in else None

    if not sub:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    users = cognito.list_users(
        # Assumes user pool id is configured in lambda environment
        UserPoolId=os.environ["USER_POOL_ID"],
        Limit=1,
        Filter=f'sub="{sub}"',
    ).get("Users", [])

    if len(users) != 1:
        raise HTTPException(status_code=403, detail=f"No user found with subjectId {sub}")

    return Identity(sub=sub, username=users[0]["Username"])

Con `auth: 'cognito'`, el autorizador de Cognito User Pools de API Gateway verifica el JWT que el llamador proporciona en el encabezado `Authorization` y coloca los claims verificados en el contexto de solicitud.

```python
import json
from typing import Annotated

from fastapi import Depends, HTTPException, Request
from pydantic import BaseModel


class Identity(BaseModel):
    sub: str
    username: str


def get_identity(request: Request) -> Identity:
    # The Lambda Web Adapter forwards the API Gateway request context as JSON
    request_context_header = request.headers.get("x-amzn-request-context")
    if not request_context_header:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    request_context = json.loads(request_context_header)
    claims = request_context.get("authorizer", {}).get("claims", {})

    sub = claims.get("sub")
    username = claims.get("username")

    if not sub or not username:
        raise HTTPException(status_code=403, detail="Unable to determine calling user")

    return Identity(sub=sub, username=username)


CurrentUser = Annotated[Identity, Depends(get_identity)]
```

from pydantic import BaseModel

    username: str

### Streaming

La FastAPI generada admite respuestas de streaming de forma predeterminada cuando se usa una REST API. La infraestructura está configurada para usar el [AWS Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter) para ejecutar tu FastAPI a través de uvicorn dentro de Lambda, con `ResponseTransferMode.STREAM` en API Gateway para todas las operaciones de REST API, lo que permite que el streaming funcione junto con operaciones que no son de streaming.

#### Usar `JsonStreamingResponse`

El `init.py` generado exporta una clase `JsonStreamingResponse` que proporciona streaming con seguridad de tipos con generación adecuada de esquema OpenAPI. Esto asegura que el <Link path="guides/connection/react-fastapi">generador `connection`</Link> pueda producir métodos de cliente de streaming correctamente tipados.

```python
from pydantic import BaseModel
from .init import app, JsonStreamingResponse

class Chunk(BaseModel):
    message: str

async def generate_chunks():
    for i in range(100):
        yield Chunk(message=f"This is chunk {i}")

@app.post(
    "/stream",
    response_class=JsonStreamingResponse,
    responses={200: JsonStreamingResponse.openapi_response(Chunk, "Stream of chunks")},
)
async def my_stream() -> JsonStreamingResponse:
    return JsonStreamingResponse(generate_chunks())
```

La clase `JsonStreamingResponse`:

1. Serializa modelos Pydantic al formato [JSON Lines](https://jsonlines.org/) (`application/jsonl`)
2. Proporciona un helper `openapi_response` que genera el esquema OpenAPI correcto con `itemSchema`, permitiendo que el <Link path="guides/connection/react-fastapi#consuming-a-stream">generador `connection`</Link> produzca métodos de cliente de streaming con seguridad de tipos

#### Consumo

Para consumir un stream de respuestas, puedes hacer uso del <Link path="guides/connection/react-fastapi#consuming-a-stream">generador `connection`</Link> que proporcionará un método con seguridad de tipos para iterar sobre tus chunks transmitidos.
</OptionFilter>

<OptionFilter not when={{ infra: 'http-ecs' }} description="CDK usage for the Lambda variants">
El constructo CDK para desplegar tu API en la carpeta `common/constructs`. Puedes usar esto en una aplicación CDK:

```ts {6-8}
import { MyApi } from '@my-scope/common-constructs';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string) {
    // Add the api to your stack
    const api = new MyApi(this, 'MyApi', {
      integrations: MyApi.defaultIntegrations(this).build(),
    });
  }
}
```

Esto configura:

1. Una función AWS Lambda para cada operación en la aplicación FastAPI
2. API Gateway HTTP/REST API como el disparador de la función
3. Roles IAM y permisos
4. Grupo de logs de CloudWatch
5. Configuración de trazado de X-Ray
6. Namespace de métricas de CloudWatch
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="CDK usage when the API runs on ECS — pass the VPC">
`defaultIntegrations` toma la VPC en la que se ejecuta tu servicio, y construye todo dentro de ella: el servicio ECS, el balanceador de carga interno frente a él, y el enlace VPC a través del cual API Gateway alcanza ese balanceador de carga. El constructo nunca crea una VPC, por lo que creas o importas una en tu stack.

```ts {10,13-15}
import { MyApi } from '@my-scope/common-constructs';
import { Stack } from 'aws-cdk-lib';
import { Vpc } from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string) {
    super(scope, id);

    const vpc = new Vpc(this, 'Vpc', { natGateways: 1 });

    const api = new MyApi(this, 'MyApi', {
      integrations: MyApi.defaultIntegrations(this, { vpc }).build(),
    });
  }
}
```

Para usar una VPC existente, búscala con `Vpc.fromLookup(this, 'Vpc', { vpcId: '<vpc-id>' })` y pásala como `vpc`.

Pasa `service` para cambiar el servicio de contenedor en sí — su `cpu`, `memoryLimitMiB`, `desiredCount`, `environment`, o `grantTaskRole` para dar un permiso al rol de tarea:

```ts
MyApi.defaultIntegrations(this, {
  vpc,
  service: {
    cpu: 512,
    memoryLimitMiB: 1024,
    grantTaskRole: (taskRole) => myTable.grantReadWriteData(taskRole),
  },
}).build();
```

Esto configura una AWS API Gateway HTTP API con autenticación basada en tu método `auth` elegido, un servicio Amazon ECS ejecutando tu contenedor, un balanceador de carga interno frente a él, y el enlace VPC a través del cual API Gateway alcanza ese balanceador de carga.
</OptionFilter>

<OptionFilter when={{ auth: 'custom' }} description="Uso de Lambda Authorizer personalizado con CDK">
:::caution[Lambda Authorizer Personalizado]
Cuando se usa autenticación `Custom`, el constructo crea un Lambda Authorizer internamente desde el archivo `authorizer.py` generado, que **deniega todas las solicitudes por defecto**. Debes implementar tu lógica de autorización en ese archivo antes de que tu API acepte cualquier tráfico.

Los resultados del autorizador se almacenan en caché durante 5 minutos, con clave en el encabezado `Authorization`, por lo que un token revocado puede ser aceptado hasta que expire su resultado en caché. Reduce la duración del caché en la infraestructura generada si necesitas una revocación más rápida.
:::
</OptionFilter>

<OptionFilter when={{ infra: 'http-ecs' }} description="How ECS hosting works, what it costs and what it limits">
## Ejecución en Amazon ECS

Con `infra` establecido en `http-ecs`, tu API se ejecuta como un servidor uvicorn de larga duración en un contenedor en lugar de en una función Lambda detrás del Lambda Web Adapter. Una solicitud toma esta ruta:

1. Un llamador firma una solicitud a la API Gateway HTTP API, que es el único punto de entrada público. Cada ruta lleva el autorizador para el `auth` que elegiste, por lo que una solicitud no autenticada se rechaza en el borde.
2. API Gateway reenvía la solicitud a través de un enlace VPC, que es su ruta privada hacia tu VPC.
3. El enlace VPC alcanza un balanceador de carga interno. El balanceador de carga no tiene dirección pública, y su única regla de entrada permite el grupo de seguridad del enlace VPC en el puerto del listener.
4. El balanceador de carga reenvía la solicitud a una tarea. La única regla de entrada de las tareas permite el grupo de seguridad del balanceador de carga en el puerto del contenedor, por lo que nada más en la VPC puede abrir una conexión a ellas.

Las tareas se ejecutan en subredes privadas y nunca obtienen una dirección IP pública. Nada en esta ruta permite un rango de direcciones de entrada.

Por defecto, el servicio, el balanceador de carga y el enlace VPC van en las subredes `PRIVATE_WITH_EGRESS` de la VPC, que alcanzan AWS a través de un NAT gateway. Pasar `vpcSubnets: { subnetType: SubnetType.PRIVATE_ISOLATED }` a `defaultIntegrations` elimina el NAT gateway y su cargo por hora, pero las subredes aisladas no tienen ruta de salida, por lo que la VPC entonces necesita cuatro endpoints VPC para que las tareas se inicien: endpoints de interfaz para `ecr.api` y `ecr.dkr` para extraer la imagen, un endpoint de gateway S3 porque las capas de imagen son objetos S3, y un endpoint de interfaz para `logs` para que el driver `awslogs` pueda escribir. Sin ellos, una tarea no puede extraer su imagen y ECS revierte el despliegue en el circuit breaker sin decir por qué.

El enlace VPC, el balanceador de carga, su listener, el grupo de destino y el bucket al que el balanceador de carga escribe sus logs de acceso son creados por un constructo, `core/api/ecs-http-endpoint.ts` en `common/constructs`, que cada API alojada en ECS comparte. El constructo de tu propia API nombra su servicio de contenedor y enruta cada operación a ese endpoint.

### Qué se Ejecuta en el Contenedor

`<module_name>/<api_name>_container/main.py` importa la aplicación desde tu `main.py`, por lo que cada operación que escribes se sirve exactamente como está en Lambda. Agrega dos cosas propias:

- `GET /health`, que el grupo de destino del balanceador de carga y la verificación de salud del contenedor llaman. Se declara `include_in_schema=False`, por lo que se mantiene fuera de tu especificación OpenAPI y por lo tanto fuera de las rutas de API Gateway y los clientes generados. También se deja fuera de las métricas de solicitud, por lo que la llamada del grupo de destino cada 15 segundos no cuenta como una solicitud de API.
- Un middleware que escribe las métricas que el propio middleware de la API recopila. En Lambda el handler hace eso al final de cada invocación; este servidor vive a través de solicitudes, por lo que las vacía él mismo.

Las rutas de API Gateway aún provienen de tu especificación OpenAPI, por lo que una operación que agregues se despliega una vez que `nx build` ha regenerado la especificación.

### Observabilidad

Los logs y las métricas funcionan como lo hacen en Lambda: el contenedor escribe en su propio grupo de logs de CloudWatch, y las métricas se escriben en el formato de métrica embebida para que CloudWatch Logs las extraiga.

Una cosa sobre las métricas es diferente aquí, y vale la pena saberlo antes de leer un dashboard o agregar una métrica propia. `metrics`, el objeto que la sección <a href="#metrics">Métricas</a> anterior te dice que importes desde `.init`, es un `Metrics` de Powertools, y cada objeto `Metrics` en un proceso comparte un almacén de métricas. En Lambda una invocación posee ese almacén de principio a fin. Un servidor uvicorn maneja solicitudes al mismo tiempo, y tanto las métricas por solicitud de la propia API como cualquiera que agregues van a ese único almacén, por lo que dos solicitudes en vuelo juntas pueden tener sus métricas escritas en un documento y atribuidas a la ruta que se agregó primero. El documento de la otra solicitud puede salir sin dimensión `route` en absoluto, conteniendo solo las métricas agregadas después del primer vaciado, y Powertools registra `PowertoolsUserWarning: Dimension 'route' has already been added` cuando sucede. Bajo tráfico ligero, donde las solicitudes rara vez se superponen, no lo verás.

Así que trata `RequestCount` y `Success` por ruta como aproximados en ECS. Si necesitas una métrica atribuida a exactamente una solicitud, agrégala a un `EphemeralMetrics` que crees en la solicitud y vacíes antes de devolver, que mantiene un almacén propio:

```python
from aws_lambda_powertools.metrics import EphemeralMetrics, MetricUnit

@app.get("/items/{item_id}")
def read_item(item_id: int):
    request_metrics = EphemeralMetrics()
    request_metrics.add_metric(name="ItemViewed", unit=MetricUnit.Count, value=1)
    request_metrics.flush_metrics()
    return {"item_id": item_id}
```

El trazado de AWS X-Ray no lo hace. `@tracer.capture_method` es un no-op fuera de Lambda, y tampoco hay un demonio X-Ray en la tarea para recibir segmentos. Agrega uno como sidecar en tu servicio de contenedor si necesitas trazas.

El log de acceso de la API Gateway HTTP API registra cada solicitud que llega a la API. El balanceador de carga escribe sus propios logs de acceso en un bucket que el constructo `EcsHttpEndpoint` crea, que es donde puedes ver qué tarea sirvió una solicitud y qué respondió.

### Construcción y Escaneo de Imagen

El generador de contenedor proporciona los objetivos de imagen, nombrados según tu API:

- `<api-name>-container-docker` construye una imagen para la arquitectura de CPU en la opción `architecture`, `linux/arm64` o `linux/amd64`. La opción tiene como valor predeterminado la arquitectura de la máquina en la que ejecutas el generador, y la estableces con `--architecture`. El objetivo ejecuta primero el objetivo de bundle correspondiente, `bundle-arm` o `bundle-x86`, por lo que la imagen contiene tu paquete y sus dependencias construidas para esa arquitectura.
- `<api-name>-container-trivy` escanea esa imagen en busca de vulnerabilidades.

Consulta <Link path="/guides/py-container">Python Container Service</Link> para ver cómo se construye la imagen, y <Link path="/guides/docker-bundling">Docker Bundling</Link> para ver cómo se publica en tiempo de despliegue.

### Despliegue y Desmontaje

`deploy-sandbox` despliega en <Link path="/guides/typescript-infrastructure#deploying-your-sandbox-stage">modo express de CloudFormation</Link>, que retorna una vez que se aplica la configuración de cada recurso en lugar de esperar a que el servicio ECS alcance un estado estable. Por lo tanto, el objetivo puede finalizar mientras la primera tarea aún se está iniciando, y hasta que una tarea haya pasado dos verificaciones de salud con quince segundos de diferencia, el balanceador de carga no tiene destino al que enviar una solicitud y responde `503`. Espera aproximadamente un minuto después de que el despliegue retorne. Espera un minuto o dos y llama de nuevo. Un `503` que nunca se despeja es un fallo real en lugar de un inicio lento: el circuit breaker de despliegue del servicio lo revierte cuando ninguna tarea se vuelve saludable.

ECS ejecuta una verificación de salud propia dentro del contenedor. Llama a `GET /health` cada 30 segundos, y los fallos en los primeros 30 segundos después de que una tarea se inicia no cuentan en su contra. Hasta que esa verificación reporte por primera vez, `aws ecs describe-tasks` da a la tarea un `healthStatus` de `UNKNOWN`, que se convierte en `HEALTHY` una vez que pasa. `UNKNOWN` significa que la verificación aún no ha reportado en lugar de que falló.

La URL de la API es una salida de stack, pero no bajo el nombre que adivinarías. El `CfnOutput` se crea dentro de tu constructo de API y nada anula su ID lógico, por lo que CDK construye la clave de salida desde la ruta del constructo más un hash de ocho caracteres: una API agregada como `new MyApi(this, 'MyApi', …)` produce `MyApiMyApiUrl` y ese hash, no `MyApiUrl`. `cdk deploy` imprime el valor, y un script debe coincidir con el sufijo en lugar de la clave completa:

```bash
aws cloudformation describe-stacks --stack-name <stack-name> \
  --query "Stacks[0].Outputs[?contains(OutputKey, 'Url')].OutputValue" --output text
```

`destroy-sandbox` deja atrás el grupo de logs de acceso de la HTTP API y la clave KMS administrada por el cliente que lo cifra. Ninguno establece una política de eliminación, por lo que se aplica el valor predeterminado de CDK de `Retain` y CloudFormation los omite en lugar de eliminarlos. Enuméralos antes de desmontar el stack, ya que un stack eliminado ya no reporta sus recursos:

```bash
aws cloudformation describe-stack-resources --stack-name <stack-name> \
  --query "StackResources[?contains(LogicalResourceId, 'AccessLogs') && (ResourceType=='AWS::Logs::LogGroup' || ResourceType=='AWS::KMS::Key')].[ResourceType,PhysicalResourceId]" \
  --output text
```

Luego elimínalos con `aws logs delete-log-group --log-group-name <log-group-name>` y `aws kms schedule-key-deletion --key-id <key-id> --pending-window-in-days 7`, siendo siete días la ventana más corta que KMS acepta.

### Límites

- **Tiempo de espera de integración.** Las API Gateway HTTP APIs limitan una integración a aproximadamente 30 segundos. Una operación que toma más tiempo que eso falla en el gateway sin importar cuánto tiempo siga trabajando el contenedor.
- **Sin streaming.** Las operaciones de streaming necesitan la infraestructura `rest-lambda`. Una HTTP API no puede transmitir una respuesta.
- **Tamaño de payload.** Las solicitudes y respuestas siguen el límite de 10 MB de API Gateway.
- **Un servicio para cada operación.** `integrationPattern` es `shared`: hay un servicio de contenedor, y cada ruta se enruta a él. La opción siempre se resuelve a `shared` para esta infraestructura, y `isolated` se ignora con una advertencia.

### Costo

El balanceador de carga es el nuevo costo fijo en comparación con Lambda, donde pagas por solicitud y nada cuando está inactivo. Cifras mensuales aproximadas en us-east-1, antes de transferencia de datos:

| Elemento | Aproximadamente |
| --- | --- |
| Balanceador de carga interno | $16 más unidades de capacidad del balanceador de carga |
| Tarea Fargate, 0.25 vCPU / 0.5 GB | $7 por tarea en ARM64, y más en X86_64, que Fargate factura a una tasa más alta por vCPU y por GB |
| NAT gateway, si tu VPC tiene uno | $33 |
| Enlace VPC | sin cargo por hora |
| Almacenamiento S3 para los logs de acceso del balanceador de carga | centavos por GB al mes |

Así que un servicio de una tarea cuesta aproximadamente $23 al mes en ARM64 antes de cualquier tráfico, y más si la VPC que pasas tiene un NAT gateway. Los logs de acceso crecen con el tráfico: agrega una regla de ciclo de vida a `endpoint.accessLogsBucket` para que expiren. Consulta las páginas de precios de [Elastic Load Balancing](https://aws.amazon.com/elasticloadbalancing/pricing/) y [AWS Fargate](https://aws.amazon.com/fargate/pricing/) para precios actuales en tu Región.
