#### `-dev` vs `-serve`

El generador agrega dos targets que ejecutan el mismo servidor en el mismo puerto. Solo difieren en el entorno que establecen:

| Target | Entorno | Usar para |
| --- | --- | --- |
| `<your-agent-name>-dev` | `PORT`, `LOCAL_DEV=true` | Desarrollo local |
| `<your-agent-name>-serve` | `PORT` | Ejercitar la ruta de código desplegada localmente |

**Usa `<your-agent-name>-dev` para desarrollo local.** `LOCAL_DEV=true` cambia el agente a sus rutas de código locales: el estado de sesión se escribe en disco bajo `tmp/agents/` en la raíz del workspace, y cualquier servidor MCP conectado se alcanza a través de HTTP directo en lugar de a través de AgentCore. También es el target que el target `dev` a nivel de proyecto agrega, y el que el target `<your-agent-name>-chat` espera encontrar en ejecución.

`<your-agent-name>-serve` ejecuta la misma ruta de código que tu agente desplegado, que resuelve el almacenamiento de sesión y los ARNs de runtime conectados desde <Link path="guides/runtime-config">Runtime Configuration</Link> en AppConfig. Eso requiere que `RUNTIME_CONFIG_APP_ID` esté configurado con el id de aplicación de AppConfig de un despliegue (generado como `RuntimeConfigApplicationId` por el stack desplegado), junto con credenciales de AWS con permiso para leerlo:

```bash
RUNTIME_CONFIG_APP_ID=<app-id> nx run your-project:agent-serve
```

:::caution[`-serve` necesita configuración desplegada]
Iniciado sin `RUNTIME_CONFIG_APP_ID`, `<your-agent-name>-serve` acepta solicitudes pero cada invocación falla con `RUNTIME_CONFIG_APP_ID is not set — cannot resolve connected agent ARNs from AppConfig.`

Establece `LOCAL_DEV=true` para tomar las rutas de código locales en su lugar — que es lo que `<your-agent-name>-dev` ya hace por ti.
:::
